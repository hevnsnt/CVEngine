# Pipeline

Add a target and cvENGINE runs one pipeline for it. Stages run in order and each records its own result, so you can see exactly what was covered. If discovery fails, the scan fails. If a later stage fails, that stage is named in the scan's error and the scan still completes, so the hosts it found stay in the inventory.

## Targets

A target is a domain, an IP address, a CIDR range (`10.0.0.0/24`), a dashed range (`192.168.1.1-192.168.1.20`, or the last-octet shorthand `192.168.1.1-20`), or a URL, which is reduced to its host. Every host is validated before it is stored. Targets queue first in, first out.

## Stages

1. **Discovery.** [bbot](https://github.com/blacklanternsecurity/bbot) finds domains, subdomains, and IPs and streams them into the inventory as it runs. *Standard* mode, the default, enumerates subdomains, fingerprints web hosts with safe modules and takes a front-page screenshot of each ([gowitness](https://github.com/sensepost/gowitness), shown on the host page and in the Hosts gallery; a screenshot is only taken of a host that answers over HTTP). *Deep* mode runs everything bbot has, including brute forcing and spidering, and takes hours. *Passive* keeps discovery to public sources (later stages still connect to the hosts it finds). The mode chosen when a target is added, or changed later in the Targets page's Discovery column, is stored on the target (`Domain.discovery_mode`; targets from before it was stored are standard) and used by every scan that starts on its own: the work conductor, the AI assessment review, a moved target, a Tailscale sweep. The weekly deep sweep leaves passive and manual targets out, and a manual only target (*Just add them, do not scan yet*) is never scanned automatically, nor are the hosts certificate transparency finds under it. Discover and Scan on a target run in its stored mode. A bare IP skips bbot and gets a reverse-DNS lookup and a read of its certificate.
2. **Inventory.** [nmap](https://nmap.org) fingerprints each IP once per window (`-sV -O`) on the top 1,000 ports plus 37 high-risk ones that nmap's ranking leaves out, such as Redis, MongoDB, the Docker and Kubernetes APIs, and etcd. It records ports, services, products, versions, CPEs, the distribution read from the banner, and the OS. Only open ports are correlated, and a port that closes is marked closed. By default, [naabu](https://github.com/projectdiscovery/naabu) finds every open port of each address first (a full 65,535-port SYN sweep at a polite rate), and nmap fingerprints just those instead of guessing from its own top-1,000 list; `CVENGINE_NAABU=0` turns this off and falls back to nmap's own top-1,000 guess alone. Its scripts also read banners and SSH, TLS, HTTP, SMB, NetBIOS, and RDP details, plus each database's own pre-authentication greeting (MySQL, Microsoft SQL Server, MongoDB, Redis, Memcached, and CouchDB), which fills in a version or product nmap's own probe missed. They name the Windows build, computer, and domain from RDP, SMB, and Microsoft SQL Server's own NTLM negotiation, and they raise two findings: an FTP server that accepts anonymous sign-in (with its listing as evidence) and an RDP server that does not require Network Level Authentication.
3. **RDP screenshot.** A server the inventory stage showed accepts a connection without Network Level Authentication gets one pre-authentication login-screen capture, with no credentials sent, stored and read by the AI model for a signed-in account (see [Configuration](CONFIGURATION.md#settings-in-the-app)). A server that requires NLA is never attempted.
4. **Exposure checks.** One connection with no credentials to Redis, Memcached, PostgreSQL, MySQL, MongoDB, Elasticsearch, and CouchDB ports (an empty password for the default `postgres` and `root` accounts, never a password list). A server that answers is reported as a critical finding.
5. **nuclei, technology pass.** [nuclei](https://github.com/projectdiscovery/nuclei) HTTP and technology templates fingerprint each host.
6. **WAF fingerprint.** On by default (`CVENGINE_WAFW00F=0` turns it off). [wafw00f](https://github.com/EnableSecurity/wafw00f) names the web application firewall in front of each web host with a few requests (up to 25 hosts per scan, 60 seconds each; it runs only when a host answered over HTTP and the binary is present), and the product is stored as a technology of the host (a product, never a version). A generic block that names no product, and a host with nothing in front of it, store nothing. Some of its requests carry attack-looking strings, so a firewall may log them. bbot's own WAF events are stored the same way.
7. **Web route checks.** For each web host, cvENGINE sends one plain anonymous GET to a handful of common routes (`/`, `/login`, `/admin`, `/api`, and paths bbot found) and labels each `open`, `login`, `session_required`, `sso`, or `redirect`. The response is scanned in memory for sensitive data such as cloud keys, personal data, and internal identifiers. Only the type, a count, and a masked sample are stored. The page's headers, generator tag, and script names, plus the comment banners of up to four scripts the host serves itself, name the technologies and libraries it runs (jQuery, Bootstrap, AngularJS, and others) with versions, so an old library is correlated like any other technology.
8. **Version and identity probes.** A product the earlier stages saw without a version (nginx, Next.js, jQuery, an nmap service with no version) is a lead. cvENGINE asks the host for the missing fact with safe, read-only probes chosen by rule, with no AI: see [Version and identity probes](#version-and-identity-probes).
9. **WordPress detection and WPScan.** Every host that shows any sign of WordPress is probed and scanned with [WPScan](https://wpscan.com/), and nothing is skipped silently: see [WordPress and WPScan](#wordpress-and-wpscan).
10. **node2shell.** Off by default (`CVENGINE_NODE2SHELL=1` turns it on). Hosts fingerprinted as Node.js (or a framework on it), Bun or Envoy are checked for CVE-2026-111497 (`CVENGINE_NODE2SHELL_SCOPE=all` checks every web host) with [Assetnote's own read-only detector](https://github.com/assetnote/node2shell-scanner) (see [Configuration](CONFIGURATION.md#settings-in-the-app)).
11. **CVE correlation.** The inventory is matched against the CVE store.
12. **nuclei, AI-targeted pass.** Your AI model sees the technology names found on each host and picks nuclei tags from those the installed templates use. A built-in technology map always adds its tags. Hosts with the same choice are scanned together, and each host's fire and smoke CVE matches get a template test.
13. **Triage, validation, and changes.** See below.

The daily hygiene task also asks the Internet Archive, once a week per target, for the URLs it saved. A `.php` page or a `/wp-content/` path says a host ran PHP or WordPress at some point. That is kept as historical evidence only: search finds the host and labels it *seen in web archive*, and it is never treated as a current technology.

**Hygiene** runs as its own task when the scan finishes: TLS certificates (expiry, trust chain, hostname, self-signed, legacy protocols), SPF, DKIM, DMARC, and CAA, plus the checks of [MailFail](https://github.com/ACK-J/MailFail) re-implemented server side: records receivers ignore, report addresses on domains anyone can register, unauthorized DMARC reports, weak DKIM and ARC keys, Microsoft 365 Direct Send exposure, MTA-STS, TLS reporting, DANE, DNSSEC, BIMI, and MailChannels lockdown. None sends mail. `CVENGINE_HYGIENE_RDAP=0` turns off the registry lookups. A name with no DMARC record of its own is held to its organizational domain's policy (RFC 7489 section 6.6.3, including `sp`), so a mail subdomain under an apex that publishes `p=reject` is not reported as missing DMARC.

**Cleartext administration services** are part of the same hygiene run (check names `cleartext_*`, stored like the other hygiene findings, so status, assignee, comments, triage, reports, the host score and the API work as for every other one). They are decided from what the scans already stored, with no probe of their own: an open TCP port nmap named `telnet` (`cleartext_telnet`), `ftp` (`cleartext_ftp`), or rexec, rlogin and rsh on 512 to 514 (`cleartext_rservices`; UDP 514 is syslog and is not counted), and a login page the route check saw over `http://` on a host with no HTTPS service (`cleartext_http_login`: no open TLS web port and no HTTPS route). A port with a TLS tunnel (`telnets`, `ftps`, an `ssl/` service) is not reported. FTP is not reported when nmap read a certificate from the port (its `ssl-cert` script negotiates AUTH TLS), which shows the server offers TLS, not that it insists on it. The FTP finding without that evidence says plainly that it is unencrypted unless TLS is enforced. A port nmap named from its port table without fingerprinting it is reported, and the finding says so. Telnet, FTP and the r-services are medium on an internal host and high on a public one (a public address is judged from the address alone, as the host score does; the finding's evidence says which it used); a login page over plain HTTP is low and medium. There is one finding per host and check, naming every port and address; a closed, filtered or unanswered port is never a finding, a host the organization excluded or the project archived has none, a CDN edge address is skipped, and so is a tailnet address (the Tailscale check `ts_remote_admin_exposed` reports remote administration there). A finding resolves at the next hygiene run after the port closes, and a fixed one that returns reopens. `CVENGINE_HYGIENE_CLEARTEXT=0` turns the check off: no finding is made and the open ones resolve at the next run. Not covered: SNMP v1 and v2c in general (it needs an SNMP request the stored data does not hold; a device that answers the default `public` community is already reported by the [UDP sweep](#keeping-scans-fast-and-polite) as `udp_snmp_public`), and whether an FTP server that offers AUTH TLS also accepts a plain login.

By default nuclei runs the whole installed template library, in the broad scans and when a match is validated. Nuclei's denial-of-service templates stay excluded (`-etags dos`), out-of-band (interactsh) checks stay off (`-ni`), and the AI-written templates always stay read-only. A superuser can turn the whole library off under **Settings, Scan policy, Nuclei templates** ([Configuration](CONFIGURATION.md#settings-in-the-app)): then every nuclei run uses a snapshot of the installed templates that passed read-only and destination checks, which means plain GET, HEAD or OPTIONS requests to the scanned host only, no payloads, bodies, code or out-of-band checks. A template may follow redirects on the same host, up to three (nuclei's `host-redirects`, which the technology detection template uses); one that follows redirects to other hosts is left out. The AI-written templates may not follow redirects at all. Changing the setting is recorded in the audit log and makes hosts due for a new nuclei pass. An install that never changed the setting before the library became the default follows the new default.

### runZero between scans

A project with a runZero token is also synced from [runZero](CONFIGURATION.md#runzero), outside any scan. The sync stores runZero's OS, hardware, tags and CVE reports on the addresses cvENGINE already holds and, if the project turned import on, adds runZero addresses it does not know as targets through the Add targets path (exclusions, private-range policy and organization uniqueness included). runZero's CVE reports only raise the confidence of a match this pipeline already made; they never create or confirm one.

### Inventory details

- **Port discovery.** By default [naabu](https://github.com/projectdiscovery/naabu) sweeps all 65,535 TCP ports of each address (SYN, 1,000 packets a second) and nmap fingerprints only the open ports it found plus ports already known open. If naabu is off (`CVENGINE_NAABU=0`), missing, fails, or sees more than 500 open ports on one address, nmap falls back to the top 1,000 ports plus 37 high-risk ones.
- **Scripts.** nmap runs at version intensity 7 with 20 reviewed scripts: banner, SSH host key and algorithms, TLS certificate, HTTP headers, title, server header and generator, anonymous FTP, RDP NTLM and encryption, SMB OS discovery, NetBIOS, SQL Server NTLM and Browser service information, and the MySQL, MongoDB, Redis, Memcached, and CouchDB greetings. nmap's `-sV` also runs its own version scripts. Their output is dropped before storage, because only the reviewed scripts are trusted to be read-only.
- **The background port sweep** fingerprints what it finds with `-sV` only: no scripts and no OS guess until the next regular scan.
- **What queues for memory.** bbot, nuclei, nmap (including the background full port and UDP sweeps), naabu, route checks, and template tests wait in the memory-aware queue. wafw00f, WPScan, testssl.sh, RDP screenshots, node2shell, and the database checks do not.
- **Per-host limits.** At most 10 CVE template tests per host. Route checks make up to 20 requests per host, 1,500 per scan, 0.2 seconds apart.

## Triage and validation

CVE matches, scanner findings, open databases, open admin routes, routes exposing credentials, and hygiene findings of medium severity or worse are queued for triage, within daily caps. Each finding carries a classification (`confirmed`, `likely`, `needs_validation`, `likely_false_positive`, `not_applicable`), why it matters, how to fix it, when it was first and last seen, and every check that ran. Nothing is deleted or hidden: a likely false positive sorts last. Without an AI provider, findings read "not triaged" and validation still runs.

**Fixed rules keep the model honest.** Hard evidence sets a floor the model cannot go below. A template hit, a database that answered, a distribution tracker that lists the package as vulnerable, a scanner finding whose template matcher fired at medium severity or higher, a CVE template check, a failed deterministic hygiene check, and a route serving a credential are `confirmed`. A version inside a CVE's affected range is at least `needs_validation`. An open admin route is at least `likely`. The model alone can never confirm a finding. A reply that breaks the answer schema is sent back to the model once with the exact reason, and the second answer is used. If that is also rejected, the finding shows a diagnostic you can copy (the reason and the number of attempts, never the reply text) and a later pass retries it.

**One question per kind of evidence.** The model sees cleaned, structured evidence (product, version, advisory range, template id, counts) with hostnames redacted. Findings with the same evidence share one saved answer.

**Validation runs by itself.** cvENGINE reproduces a finding with one of five read-only checks and records the exact command and result: a vetted nuclei template, `nmap -sV` on the one port, a HEAD request for the version banner, the credential-less database check, or a version and identity probe (see [below](#version-and-identity-probes)). A hit confirms the finding. A check that does not reproduce it never lowers it, because templates can miss behind a WAF or on another virtual host. A banner that only shows a version is recorded as `observed`. Every five minutes a dedicated worker queues up to 20 findings: fire first, then smoke, then every other CVE match (`CVENGINE_AUTO_VALIDATE_ALL_MATCHES=0` leaves those out). A project has at most 10 active jobs, 5 of them cold. Checks are not repeated within 24 hours.

**Validate now.** Matches are validated automatically, so this is for jumping the queue: on any CVE match, **Validate now** (or the API) has the AI plan the checks, runs them, and has the AI review the evidence. The plan can only choose checks the scope and template policy already allow. When a CVE cannot be answered from outside, such as a local kernel flaw, the match records that no external check applies.

**When nothing can be checked from outside**, cvENGINE asks the AI once for at most three short, read-only commands a person with shell access to the host could run themselves, such as checking for a package, a process, or a config path named in the advisory, with what the output would mean. It is suggestion only, unverified by this tool, shown under **Confirm it yourself** beside the usual "no check exists" message, never a classification or evidence of anything. The model is told never to suggest a command that changes the host or needs a credential, and to say so plainly when it is not confident of the exact way to detect a given product rather than invent one.

A daily sweep (triage 04:41 UTC, validation 05:17 UTC) catches whatever is left.

### How the AI investigates a lead

A finding is judged with everything cvENGINE holds about its host (`cveFeed/host_context.py`): technologies with their versions and where each was seen, the ports with product, version, extra info, banner, HTTP and TLS facts, the front page's headers and title, CDN, WAF, hosting and CNAME hints, certificates, the operating system guess and its runners-up, what runZero and the host inventory reporter said, what probes found or found hidden, earlier check results and the host's other CVE matches. It goes to the model as a second untrusted block, cleaned and capped, with no host name or address. The model is told, in order: is the advisory's product the product the host runs (nginx is not ingress-nginx or nginx-ui), is the version inside the range and did a probe state it or only a banner, is the host behind a CDN or WAF (then the Server header, X-Powered-By and error pages describe the edge, a tag such as `cloudflare` names the edge and not an application, and the origin version is unknowable from here), and does the advisory need local state (then the host inventory reporter decides, not a network check).

**Closing a match needs concrete grounds.** A version inside an advisory's range stays a floor the model cannot clear, unless the application itself verified a ground from the host's metadata: a probe identified a look-alike product (the host's error page is plain nginx and the advisory names ingress-nginx), (and the host does not itself run the look-alike), or a CDN, WAF or hosting edge answers for the host on DNS-level evidence (its CNAME, its name, the CDN flag on an address: a response header such as `cf-ray` is the host's own say-so and counts for nothing) and the match rests on a web response (an SSH, database or mail banner is never the edge's). A match that has standing (worked by a person, a template hit, a distribution verdict, a host report) is never cleared this way. Then the model's `likely_false_positive` or `not_applicable` stands, with its reason. A banner or tag that states no version is never a reason to close a finding, and a template hit or a distribution's "vulnerable" verdict still floors it. When probes or an edge change what is known, the question is asked again without erasing the earlier validation record.

### Version and identity probes

The probe catalogue (`cveFeed/probes.py`) is data: an id, the products it helps with, the requests it makes and the patterns that read the answers. The application renders every request; no model writes one. Each probe sends only GETs (or an nmap service probe), no cookie and no credential, caps its requests, response size (256 KB) and time, goes through the same safe-address gate, exclusions, scan stop and pause as every other check, and logs to the activity feed.

| Probe | Finds |
| --- | --- |
| `headers-root` | The front page's `Server` header and the modules it lists (an Apache header names its PHP, OpenSSL and mod_wsgi versions), `X-Powered-By`, `X-AspNet-Version`, framework headers, `Via`, every generator meta tag and plugin comment, library versions in script names, and the CDN or WAF edge that answered |
| `error-page` | The footer of the server's own error page: `nginx/1.24.0`, Apache, Tomcat, Jetty, IIS Detailed Error; the Kubernetes `default backend - 404`; Express, Spring Boot and Next.js signatures |
| `nginx-variants` | nginx-ui and Nginx Proxy Manager (and its API version) as opposed to plain nginx |
| `nextjs-version` | The Next.js version a framework script states (`window.next={version:"..."}`) |
| `html-libraries` | jQuery, Bootstrap, AngularJS and other versions from script names and banners |
| `drupal-changelog`, `joomla-manifest` | Those products' version files |
| `robots-txt` | CMS hints in `robots.txt` |
| `wordpress-detect` | WordPress, by its login page, REST API (and the `Link: <.../wp-json/>; rel="https://api.w.org/"` header), generator tag, readme and core asset versions |
| `nmap-version-all` | `nmap -sV --version-all` on one port with the reviewed safe scripts for its service (`http-server-header`, `http-headers`, `http-generator`, `ssl-cert`, `banner`; `ssh2-enum-algos`, `ssh-hostkey`; `mysql-info`, `redis-info` and the like) |

**What is recorded.** Each result is a `ProbeObservation` (host, probe, product, version, identity variant, source, confidence, outcome) in the project: `found`, `hidden` (the product answers and states no version, which is a result: the AI is told the version is unknowable from outside), `edge` (only a CDN or WAF answered), `challenged` (the edge refused the scanner) or `absent`. A found version is also written as the host's technology (`nginx:1.24.0`; an nmap probe updates the Port row), the host is correlated again, and the deterministic rules then create a versioned match or none. A version is never guessed. Facts found inside the freshness window (`CVENGINE_TTL_PROBE`, 72 hours) are carried onto the next scan's host rows.

**No AI needed.** `plan_for_host` picks the probes for each lead by rule (at most five per host, one web base URL, no nmap probe where a CDN answers). In a validation request the AI may choose among the checks offered and reasons over their results, but a probe is always part of the plan when one applies, and a request ends with "no executable check" only when none does. The plan then says why: a kernel, driver or hardware advisory needs the host inventory reporter, since no network probe can read it. `CVENGINE_PROBE_MAX_HOSTS` (default 60) bounds the hosts probed per scan.

**Parsing.** Versions are read from what a service states and nothing else: `Apache-Coyote/1.1` is a connector's protocol version, not Tomcat's; `Jetty(9.4.51.v20230217)` and every `Name/version` token of an Apache `Server` header are read; a CPE technology (`cpe:/a:apache:http_server:2.4.41`, what Shodan's InternetDB gives bbot) and `Bootstrap:v3.3.7` are normalized to name and version; nmap's `tunnel="ssl"` marks a TLS web service on any port (so port 8444 is asked over HTTPS), its `ssl-cert` output fills the port's TLS facts, and a version that stops being stated (`server_tokens off`) is cleared from the port instead of kept.

### WordPress and WPScan

WPScan is the primary WordPress assessment. A host is a candidate when anything suggests WordPress: a technology tag, a front page fingerprint, a `wp-login.php` login form, a crawled `/wp-content/` URL, a page title or label, the web archive's memory of the host, or an earlier probe. A cheap read-only probe (`wordpress-detect`: `/`, `/wp-login.php`, `/wp-json/`, and `/readme.html` once positive) confirms it with browser-like request headers, follows apex and `www` redirects inside the host's group, reads a signature in the headers or the body, and is also run on every name that shares a candidate's address and on other web hosts up to `CVENGINE_WP_PROBE_MAX_HOSTS` (default 100). WPScan then runs on every candidate and every grouped name that probes positive, positive probes first.

Every candidate ends in a recorded state, shown on the host page and counted in `get_system_status` (`wordpress`: hosts, scanned, never scanned, with the reasons): `scanned` (when, findings, whether vulnerability data was checked, next scan), `detected` (not scanned yet), `candidate`, `blocked` (the edge challenged the scanner), `failed` (with the reason; retried at the next scan), `waiting` (over the per-scan limit), `unavailable` (WPScan not installed) or `not_wordpress`. When an edge answers with a challenge (`cf-mitigated`, "Just a moment", an Akamai, Sucuri or Imperva block page, or a 202, 403, 429 or 503 with no origin signature), cvENGINE does not push against it (a plain 429 or 503 is asked again once), records that the edge challenged the scanner, and tells the owner to allow the scanner's address or user agent in the WAF or bot rules. It never tries to solve a challenge or get past a WAF.

WPScan runs in two passes. The quick pass (in the scan) runs `--enumerate ap,at,cb,dbe,u1-10` with passive plugin and theme detection, a random user agent and a 100 ms throttle: the core, the plugins and themes the pages reference, config backups, database exports and author ids. In WPScan 4 plugin and theme detection fall back to the global mode unless they are set, so they are set explicitly: mixed mode with `ap` asks for every plugin slug WPScan knows. The thorough pass (`wpscan_thorough` on its own `wpscan_queue`) then runs mixed detection with timthumbs on each scanned host, one site at a time and one pass per project, for as long as it needs (`CVENGINE_WPSCAN_THOROUGH_TIMEOUT`, 12 hours; WPScan writes a partial report before the process is killed). A site that finished is not asked again for 30 days (`CVENGINE_TTL_WPSCAN_THOROUGH`, 24 hours after a partial one). It never blocks the scan, stops while scanning is paused and resumes, and shows `pending`, `running`, `done`, `partial`, `blocked` or `failed` on the host page and in `get_system_status`. A scan that WPScan could not finish still keeps what it read. WPScan exits 4 with `NotWordPress` only when it says so; a positive probe that WPScan could not confirm is `failed` ("WPScan could not see WordPress, the probe did"), because a WAF may serve it a decoy page. Plugin and theme versions need no API token. The quick pass checks at most 20 sites per scan, 15 minutes each, and the whole stage has a one hour budget (`CVENGINE_WPSCAN_MAX_SITES`, `CVENGINE_WPSCAN_TIMEOUT`, `CVENGINE_WPSCAN_STAGE_SECONDS`); a candidate beyond either limit is recorded as `waiting` and goes first next time. When the token's daily budget (25 requests on the free plan) is spent, the remaining sites are still scanned without it and say "not checked: API token budget exhausted"; such a run is repeated after a day, a clean run after a week (`CVENGINE_TTL_WPSCAN`, `CVENGINE_TTL_WPSCAN_PARTIAL`). Its findings (core, plugin and theme vulnerabilities with CVE ids and the fixed version, exposed backups and database exports, usernames, XML-RPC, outdated components) are normal findings with remediation text. The core, every plugin and every theme with a version also become sightings: a CVE for a plugin matches only when the plugin's slug or title (read from its own readme) equals the advisory's product or package name and its version is inside a bounded range (`wp-plugin` matches).

### TLS audit

[testssl.sh](https://testssl.sh) (GPLv2, run as a separate program) tests what a handshake cannot show: the protocols and cipher categories a server offers, forward secrecy, renegotiation and the TLS vulnerabilities that have names (Heartbleed, CCS injection, ROBOT, POODLE, FREAK, DROWN, Logjam, SWEET32, Ticketbleed, RC4, CRIME, Winshock, BEAST, Lucky13, BREACH). It is a slow background sweep, never part of a scan: `testssl_sweep` runs daily at 02:20 UTC on its own `testssl_queue`, tests one port at a time (about a minute each), the longest-waiting first, at most 40 per run (`CVENGINE_TESTSSL_MAX_TARGETS`), one sweep at a time, and stops while scanning is paused. A target is retested after 14 days (`CVENGINE_TTL_TESTSSL`); one that could not be tested is asked again after three days.

Targets are the TLS ports nmap found open on a host (443, 8443, 9443, 993, 995, 465, 636, and any port nmap called ssl or https), and 443 for a host with no port data. Mail and directory ports are tested with their STARTTLS dialect (SMTP on 25 and 587, IMAP, POP3, FTP, LDAP). Each target is tested at the address `cveFeed.pinned_transport` vetted (`--ip`, with `--nodns none`), so a name pointed at a prohibited address after it was stored is never contacted, and excluded and archived hosts are skipped. testssl.sh runs with a bare environment: no application secret reaches it.

What it records:

* **Configuration findings** (hygiene findings named `tlsa_*`): SSLv2 or SSLv3 offered, NULL, anonymous, export, low-strength and 3DES ciphers, no forward secrecy, missing secure renegotiation, weak Diffie-Hellman parameters, and every named vulnerability testssl.sh reports as vulnerable or potentially vulnerable, at testssl.sh's own severity. TLS 1.0 and 1.1 stay with the certificate check above (`tls_legacy_protocol`), and the certificate's own problems with `tls_*`. A finding resolves only when a later test of the same port ran and no longer reports it; a test that could not answer changes nothing.
* **Observations**: one per vulnerability test (found or absent) and one summary per port with the protocols offered, kept as `ProbeObservation` rows (kinds `tls-vuln` and `tls-audit`).
* **Hard CVE evidence.** A vulnerability testssl.sh proves is a CVE match (source `testssl`, one per CVE the test names) with the test result as evidence, and counts like a template confirmation: the AI cannot rule it out. Only results that say VULNERABLE count (Heartbleed answered with memory, a ROBOT oracle, an accepted export cipher, an accepted renegotiation); "potentially vulnerable" and mitigated results (BEAST, Lucky13, BREACH, SWEET32's 64-bit block warning) are findings, never CVE matches. A later test that finds the service no longer vulnerable closes the match unless a person already works it, and the next scan's host row gets the match back from the stored observation until then.

The x86-64 image bundles the openssl build that ships with testssl.sh, which still speaks SSLv2, SSLv3 and export ciphers. On arm64 testssl.sh uses the system openssl, which has those protocols compiled out: results for them are not reliable there.

### Other sites and applications on a host

Two slow background sweeps look for OTHER APPLICATIONS that could carry a known CVE. They are not content discovery: GET only, no body, no cookie, no credential, redirects never followed, a small curated set of questions, and a cap on what one host or address is asked. Both run on their own `vhost_queue` (a beat task each, `vhost_sweep` hourly and `subdir_apps_sweep` every 30 minutes, a few addresses or hosts per run), stop while scanning is paused, skip excluded and archived hosts and any address the scannable gate refuses, wait between requests (`CVENGINE_SLOW_WEB_GAP`, 1 second across all workers, and `CVENGINE_SLOW_WEB_HOST_GAP`, 2 seconds per host), and ask each question once per week (the service ledger: `vhost`, `subapp`). `CVENGINE_VHOST=0` and `CVENGINE_SUBDIR_APPS=0` turn them off.

**Virtual hosts** (`cveFeed/vhost_scan.py`). One address can serve several sites, told apart by the Host header (and the TLS server name). For each web address of a project (not a CDN or shared-platform address), the sweep asks `/` once with each name the project ALREADY knows that is not yet recorded as answering there: the hosts stored for the project, the names in the certificates seen on that address and the reverse names discovery recorded for it, and the names certificate transparency found. There is no wordlist and nothing is guessed. A name is asked only when it is in scope (equal to or under a domain target of the project; a host-scoped target covers its own name only): a name outside it is never asked and never added, whatever a certificate lists. At most 20 names per address and 5 addresses per run (`CVENGINE_VHOST_MAX_NAMES`, `CVENGINE_VHOST_MAX_IPS`). The answer (status, title, length, redirect target; never the body) is compared with the address's own default response and with the name's own site (its stored front-page route check, else one GET at its own address): `distinct` is another application, `default_site` (the address ignores the name) and `same_app` (the application the name already serves elsewhere) add nothing. A distinct application is recorded as a `ProbeObservation` of kind `vhost` (host the name, product the address, evidence the classification) and added to the project as a host row of its own (like the rows certificate transparency creates) linked to the address, so names that resolve to the same addresses stay one host with aliases exactly as the Hosts page already merges them; what its page states (a product and a version, in its headers and markers) becomes the host's technologies, which the correlation reads. A later answer that is no longer distinct unlinks the address and says so in the record. The host page shows "Also served here" on the host that holds the address.

**Applications under subdirectories** (`cveFeed/subdir_apps.py`). A product installed under a path (`/jira`, `/grafana`, `/owa`) is invisible to a check that reads only the front page. For each web host (and each distinct virtual host, asked at its own address with its own name) the sweep sends one GET per path of the curated list `web/cveFeed/data/subdir_apps.json`, which holds each path, the product it indicates and the signatures that confirm it, plus at most 10 directories the host's own crawled URLs, archived URLs, `robots.txt` and `sitemap.xml` already show, and three fixed requests (a path no site serves, as the baseline, `/robots.txt` and `/sitemap.xml`). At most `CVENGINE_SUBDIR_MAX_REQUESTS` requests per host per sweep (60) and `CVENGINE_SUBDIR_MAX_HOSTS` hosts per run (6). Only 200, 301, 302, 401 and 403 count as something being there, and an answer the server gives to every path (the baseline, or the front page) is not a mount. What answers is read from the response (title, a header, a marker in the body, a redirect to the product's login): a signature names the product, and a version pattern of that product reads the version when the page states one. A path that only answered is a **lead** (stored with its status, never a technology); a confirmed product that states no version is recorded as `hidden`, like a version probe does; a confirmed product AND a stated version is a Technology (`Jenkins:2.401.3`) of the host and the host is correlated again, so the CVE match rule above applies unchanged (a bare path hit is never a finding). No favicon hash is used. Results are `ProbeObservation` rows of kind `subapp` (an application that is gone at a later sweep becomes `absent`), shown on the host's Web tab as "Applications under subdirectories", and the versioned ones follow the host onto each new scan's rows. An edge that challenges or blocks a request (a Cloudflare challenge, an Akamai, Sucuri or Imperva block page) is recorded as `challenged` with what to allow and is never retried or worked around: that host or address is left alone until the next window.

### Authenticated checks

By default every request is anonymous. For an application the owner may test, an App Admin or the organization's admin can store request headers and a cookie for a target (the **Sign-in** button on the Targets page or `PUT /api/v1/projects/{slug}/targets/{id}/auth-credential`; the MCP server can list and revoke them but never takes a value, so a secret does not pass through a model's context), and Nuclei and the web route check then also see the signed-in application. Use a dedicated low-privilege test account, never a person's session, and choose an expiry of 30, 90 or 120 days (or `never`, which must be chosen on purpose): a session ends, and a stored value past its expiry is simply not sent (the target shows it as expired, and the list shows the days left). The web route check verifies TLS on the same connection that carries the sign-in. Nuclei does not verify TLS on its requests, and a separate preflight cannot secure a later connection. Its signed-in HTTPS pass therefore withholds stored credentials by default, including when a preflight certificate would verify; anonymous Nuclei checks still run. A plain `http` origin must be explicitly configured. The owner can switch **Trust this certificate anyway** on per stored sign-in (`allow_untrusted_certificate`, off by default, App Admin or organization admin, audited as `target.auth_credential.untrusted_certificate`): the sign-in is then also sent over a connection whose certificate does not verify, which means anyone in the network path can read it, so leave it off unless you know the server and the network. Stored sign-ins that existed before this switch keep it off, so one for a self-signed host stops being sent until the switch is turned on. Scans send read-only requests (the Nuclei template read-only policy still applies), but an application can change state on a GET, so keep the account's data disposable.

**What is stored.** A label, up to ten header name and value pairs, an optional cookie string, the `scheme:port` origins it may go to (default `https:443`; plain `http` only if named), a mandatory expiry (30, 90 or 120 days from saving, or an explicit never, in which case none is stored), and the scope it is for, always chosen explicitly: one named host of the target, or all hosts of the target (the target's own name and every subdomain of it), which the page marks with a warning that the credential will be sent to every host of the target that is in scope and on the allowed origins. A blank host never means the whole target. The values are encrypted at rest with the same field key as every other secret (`make rotate-field-key` re-encrypts them), are write-only (every read returns the header and cookie names, never a value; sending a blank value for a name already stored keeps it), and are never logged: the audit log records the label, the header names and the origins. A value must be 6 to 2,000 characters on one line, because a shorter one could not be told apart from ordinary text when it is removed from stored evidence.

**Scope.** A credential is attached to a request only when its destination host is exactly the host it was stored for (or, for a target-wide one, the target's name or one of its subdomains, and never for a host-only target's subdomains), the destination scheme and port are one of its origins, and it has not expired. That check runs after the normal vetting (pinned addresses, `scannable_hosts`, exclusions, archived hosts) and the global pause, never widens it, and applies per request: a different host, a different port or scheme, a third-party host and another target or project never receive it, and a redirect is never followed with it.

**Where it is used.**

- **Nuclei** (the blanket and targeted passes, the weekly deep pass and the CVE template checks). The plain pass runs as before; then the same selection (tags, severities, the approved read-only template library) runs again over explicit `scheme://host[:port]` URLs of exactly the covered origins. The values are written to a nuclei secrets file (`-sf`, the `static` format of nuclei's authenticated scans, one `Header` secret per credential limited to the listed domains) in a private temporary directory (0700, file 0600) that is deleted when the run ends, never on the command line, in the environment or in a log; the run also gets `-dr` (no redirects), because nuclei would otherwise carry custom headers wherever a redirect leads. This was checked against the nuclei 3.11.1 source (`-sf` and `-dr` exist, secrets are looked up per request on the request's host and port, 80 and 443 are treated alike); it was not run against a real nuclei in the build. Two limits: nuclei cannot tell `http://host` from `https://host` on the default ports, so two credentials that would need those two get only the HTTPS one, and a template that hardcodes `http://{{Hostname}}` would send the values over plain HTTP to the same host (the read-only policy and the explicit HTTPS targets make this rare, but it is possible).
- **Web route check** (`cveFeed/route_auth.py`). Each covered route is asked once more with the headers and cookie, one GET with no redirect followed, and the answer is stored in the route's evidence as `authenticated` (state, status, title, redirect target, when), beside the anonymous state, which is unchanged. The body of a signed-in page is never searched for sensitive data and never stored. When a route still shows a login page, the activity line says the stored session may no longer be valid.
- **Not used**, deliberately: the version and identity probes and the WordPress probe (they follow redirects between names, and what they look for is on the public front page), WPScan, bbot, nmap and the TLS and hygiene checks.

**Findings.** A finding saved from a signed-in request carries the tag `seen-while-authenticated` (also `seen_while_authenticated` in the findings API), its activity line says so, and a route's `authenticated` evidence is marked `seen_while_authenticated`. Every stored request, response, curl command and extracted value of a signed-in result has the header values, the cookie and cookie values, the part of a value after its scheme word (`Bearer abc` gives `abc`) and their URL, JSON and base64 forms replaced with `[redacted]` before it is saved, and the same applies to error text. Signed-in nuclei runs have their own ledger keys (`nuclei-auth`, 24 hours, `CVENGINE_TTL_NUCLEI_AUTH`; `route-auth-signed`, 24 hours, `CVENGINE_TTL_ROUTE_AUTH_SIGNED`) that include the credential's revision, so a replaced credential is used at once. An HTTPS Nuclei origin gets no sign-in unless the credential's "Trust this certificate anyway" is on; the withheld origin is recorded (`nuclei-auth-refused`, same revision key) and the host's check coverage says the sign-in is not sent instead of listing the check as planned. That switch also permits the web route check to use a certificate it cannot verify and must only be enabled when the owner accepts the risk to stored credentials. A signed-in nuclei pass always runs on this server, never on a Sentinel: the stored sign-in does not leave it.

### OpenVAS (optional)

With the optional OpenVAS add-on switched on (Settings > OpenVAS, [OpenVAS](OPENVAS.md)), a background sweep on its own `openvas_queue` runs Greenbone's scanner against the hosts an App Admin listed for an opted-in project, one GVM task at a time, each host once a week, and stores what names a CVE. It is not a scan stage: it runs beside the pipeline, and after CVE correlation of a scan its findings are carried onto that scan's host rows from the stored observations (`openvas_scan.carry_forward`, a no-op while the add-on is off). Only a quality of detection of 80 or more is hard evidence (a CVE match with `template_result` `vulnerable`); a lower one is stored as an unconfirmed finding. While the add-on is off nothing is scheduled and nothing runs.

## AI review every three hours

With an AI model connected, cvENGINE reviews each project's inventory, matched CVEs, findings, scans, and recent activity every three hours and queues the most useful due action: triage, validation, or a discovery on a stored target. One action per project per run, at most 100 model calls and 20 actions per review. The server rechecks scope, exclusions, active scans, the pause switch, and queue caps first, and the model never supplies a target or a command.

**Host-assessment coverage top-up, every 5 minutes.** Topping up hosts missing a core scan stage (nmap, the light nuclei pass, CVE correlation, the targeted nuclei pass) is a deterministic backlog to drain, not a judgment call, so it no longer competes for the three-hour review's one action per project: a separate sweep (`cveFeed.coverage_topup`, task `top_up_host_assessments`) runs every 5 minutes, and for every project with free host-assessment capacity (under its cap of 5 and the instance cap of 20, both of which grow with the live Sentinels' slots, see below), not bug-bounty-blocked and not paused, queues the next due hosts up to that free capacity, with no model call. A project that just picked up dozens of new subdomains from one discovery run drains in hours rather than the days the old one-host-per-three-hour-window pace would have taken.

The same review right-sizes scanner concurrency. With two hours of memory samples and enough completed scans, a controller proposes one step up or down and the AI must confirm that exact step. The result stays inside the `HEAVY_TUNE_MIN_<KIND>` and `HEAVY_TUNE_MAX_<KIND>` bounds you set ([CONFIGURATION.md](CONFIGURATION.md)), with a six-hour cooldown and an automatic step back after memory pressure. The **Scheduler health** tab shows each run and its decisions.

## Changes

Each host keeps a snapshot of its IPs, open ports, services, versions, and technologies. When a scan finishes, hosts are compared with their snapshots and the differences go into the Changes log, which the Changes page, the API (`list_changes`), and the host score read. A target's first scan only records a baseline, so the log starts quiet.

| Kind | Meaning |
| --- | --- |
| `host_new`, `host_returned`, `host_retired` | A host appeared, came back, or was retired |
| `port_opened`, `port_closed` | An open port appeared or went away |
| `service_changed` | The product or version of a port changed |
| `tech_added`, `tech_removed`, `tech_version_changed` | The host's technologies changed |
| `cert_changed` | The host presents a different certificate |
| `auth_changed`, `sensitive_found` | A route's anonymous answer changed, or it started serving a type of sensitive data |
| `screenshot_changed` | The front page visibly changed. The Changes page shows both screenshots side by side. |
| `zombie_host`, `zombie_cleared`, `zombie_route`, `route_retired` | See below |

**Zombie and retired hosts.** A host that stops resolving and whose last web address no longer answers is retired. If that address still answers a plain request with the old name, it is flagged as a zombie instead and scores higher until its name resolves again. A route that answered and now returns 404 or 410 is retired, and one that answers again is a zombie route.

**Re-test on change.** A new host, a new port, a changed service or technology, a route whose auth changed, or a zombie host queues a re-test with the CVE checks forced, up to 25 hosts per scan (`CVENGINE_RETEST_MAX_HOSTS`). A five-minute sweep drains the rest.

**Archive and rediscovery.** A person can archive a host, which keeps its findings and history but leaves routine scanning, and can pin a host to protect it. A daily review also archives retired hosts that stay gone: two meaningful negative observations at least 30 days apart, with no positive one between them. DNS errors, wildcard answers, missing probes, exclusions, and paused scanning never count as absence. Every day cvENGINE rechecks the hosts it archived itself, and a name that resolves again or an IP whose known port answers again is restored and reassessed. A host a person archived stays archived until someone restores it.

**Hosts that never get a scannable IP.** A separate, shorter-timeline path (`cveFeed.unresolved_archive`) handles a different case from the one above: a host that is still enumerated every run (it never vanished, so `retired_at` stays unset) but has never once resolved to a scannable IP, so its host assessments keep ending inconclusive for lack of resolution. Each finished assessment updates a streak on the host (first-failure timestamp, last-failure timestamp, a count); one successful resolution resets it, so a host that resolves fine and is simply waiting its turn for an assessment is never swept up here. A daily, checkpointed review (same shape as the 30-day one, `cvengine-daily-unresolved-archive-review`) archives a host once that streak has lasted `CVENGINE_TTL_UNRESOLVED_HOST` (hours, default 72, which is 3 days) with no success (a name that resolves only into a private network counts too: this server cannot scan it), skipping a pinned, excluded, or currently queued or running host. Once archived this way it lands on the same daily rediscovery sweep as every other archived host (it keys off `archived_at` alone, not the reason), so it is rechecked once a day and restored and reassessed automatically if it starts resolving.

## One host, many names

Names that resolve to exactly the same set of addresses are one host in a project: `example.com` and `www.example.com` on the same servers. The project's own target name is shown (otherwise the shortest), the other names appear as **Also answers to**, and CVE matches, findings, and exposure are counted once. Names behind a CDN or shared edge address, names with a different set of addresses, names that never resolved, and the same addresses in another project stay separate hosts. The dashboard, Hosts page, history, and API count the same way.

## Host score

Every host has a score from 0 to 100 and the reasons behind it, shown as "Why the score is N" on the Hosts page. Hosts, search, and the attack-surface map sort highest first. The score adds capped components: CVE matches (fire 40, smoke 20, ice 5, plus 10 for an AI-confirmed fire match, up to 50; matches with an unknown CVE version range add 1 each, at most 2), open findings (up to 25), hygiene issues such as an expired certificate or a weak SPF, DKIM, DMARC or TLS setting (critical 20, high 15, medium 8, low 3, plus 2 for each further medium or worse issue, up to 20), web route auth (up to 15), sensitive data (up to 25), a public IP (10), recent change (up to 10), and zombies (up to 15). It is recomputed after each scan, when a verdict is saved, and daily.

## CVE intelligence

1. **Feed.** The [cve.now](https://cve.now) feed brings CVSS and affected version ranges. Each sync adds new CVEs and refreshes up to 10 more, either ones that have matches or ones published in the last 90 days that arrived with no affected-product data, so a CVE that gains an exploit or a new range updates its matches. An hourly task covers the last 14 days of the feed.
2. **Exploitation sources.** An hourly task (`sync_threat_intel`) also reads sources that cover the whole history: [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) and [ENISA EUVD](https://euvd.enisa.europa.eu/) (exploited in the wild), optionally [VulnCheck KEV](https://docs.vulncheck.com/community/vulncheck-kev/introduction) (needs `CVENGINE_VULNCHECK_API_KEY`), [FIRST EPSS](https://www.first.org/epss/) (probability of exploitation), [Exploit-DB](https://gitlab.com/exploit-database/exploitdb) (public exploit code), and [Metasploit](https://github.com/rapid7/metasploit-framework) (weaponized modules). A source only adds evidence: a CVE missing from one never loses what another reported, and the CVE detail names each source. A CVE these sources name that is not stored is imported from its [CVE List V5](https://github.com/CVEProject/cvelistV5) record, up to 2,000 an hour, known exploited first, so the whole exploited history is in within hours.
3. **Tier** (see [Fire, smoke, and ice](FIRE-SMOKE-ICE.md)). *Fire*: known exploited, has a public exploit, has CVSS 9.0 or higher, or has EPSS of 0.1 or more with CVSS 7.0 or higher. *Smoke*: CVSS 7.0 or higher, or EPSS of 0.1 or more. *Ice*: everything else.
4. **Match.** A match is a finding, so it needs hard evidence about the host: the product it runs is the *same product* the CVE names **and** its version is inside a bounded affected range. Other evidence only attaches to a match that exists: a template hit, a distribution tracker verdict, a report from the host's own inventory, or runZero reporting the same CVE.
   - **Same product.** CPE equality, the same normalised name, or a known alias (`Next.js` and the npm package `next`). A shorter name matches a longer one only when the extra words describe the same product (`server`, `http`, `daemon`, `framework`, `core`, a vendor in front such as `Apache` or `F5`) or name an edition or service of it: `apache` is `Apache HTTP Server`, `nginx` is `NGINX Open Source` and `NGINX Plus`, `Grafana` is `Grafana OSS`, `GitLab` is `GitLab CE/EE`, `Postfix` is `Postfix smtpd`, `FortiOS` is `Fortinet FortiOS` and `Exchange Server` is `Microsoft Exchange Server 2016 Cumulative Update 14`. Anything else around a name is another product: `nginx` is not `ingress-nginx`, `nginx-ui` or `NGINX Ingress Controller`, `php` is not `phpMyAdmin`, `cloudflare` is not a plugin that works with it, `WordPress` is not one of its plugins, `jquery-ui-rails` (a gem with its own version numbers) is not jQuery UI, and a bare `Apache` banner is not Tomcat or Log4j. A technology stored as a CPE (`cpe:/a:openbsd:openssh:7.2p2`) or a banner token (`OpenSSH_9.6p1 Ubuntu-3ubuntu13.5`) is read as its product and version first. An entry for another product is never range-tested, so a version is never compared with the wrong product's ranges.
   - **No version, no match.** A product seen with no version (a bare `nginx` fingerprint) says nothing about which of its hundreds of advisories apply, so it never creates a match. It stays on the host as a technology or port and is listed as an *unverified product* (the host page, the host record's `unverified_products`, and `unversioned_products(host)` in code) for whatever finds the version: a banner read, a version probe, a host inventory. Once a version is known the product matches like any other.
   - **No usable bound, no match.** An advisory that names the product but gives no version bound ("all versions", "unspecified", a git range) cannot be tested against the host's version, so it is not evidence either. Two exceptions, both kept as low-confidence candidates that need validation (never an "affected" verdict): a version older than every branch an advisory lists for a fire or smoke CVE (end-of-life branches get no fix), and a CISA KEV advisory with no usable bound (Apache HTTP Server CVE-2021-41773, Jenkins CVE-2024-23897 and similar) for a host running that product at a known version, stored with `evidence.unbounded`. That one is a *version unknown* match: marked for review (Needs validation, reason "Version of the CVE is not known: review when the affected versions are published"), ice whatever the CVE's tier, at most 2 points of host score, never sent to the model, and re-evaluated when the CVE gains a range (see [CVE intake](CVE-INTAKE.md#a-cve-with-no-known-version-range)). An unbounded advisory of any other CVE stays unmatched, but the host is still template-tested when the CVE is fire or smoke.
   - **Operating systems.** An OS fingerprint (`Ubuntu`, `Windows Server`, an nmap `cpe:/o:` record) never matches a CVE by name from outside, and a CVE whose product is only an operating-system kernel or component (Linux kernel records with no network vector, Windows kernel and Win32k) is `local_only` and never matched: only a match the host reports itself (source `host`) can place its kernel or patch level, and such a match is never closed automatically. A kernel flaw reachable over a network, or on the KEV list, is not host-only. nmap's OS CPE does not turn an application into an OS: `Microsoft HTTPAPI httpd` and `Linux telnetd` stay applications.
   - **Existing data.** After every update, `correlate_cves` and the authoring task close the open matches the old rules made on a name alone ("Closed automatically: no version evidence ..."), and the periodic `reconcile_invalid_correlations` closes wrong-product and OS matches by re-reading the sighting each was made from. A match is kept when anything vouches for it: a person worked it (remediation other than open), assigned it, commented on it or asked for a validation, the AI confirmed it, or it has a template hit, a distribution "vulnerable" verdict, a runZero report or a host report. The closure also settles the match's triage row ("not applicable") and refreshes the dashboard counts. Closed matches are not counted in heat, scores, dashboards or notifications, and a later correlation does not reopen them unless the evidence changes (a version appears). A match whose version moved out of range or whose product is gone is closed. Each match stores its evidence.
5. **Distro backports.** Linux distributions fix CVEs without changing the upstream version. cvENGINE reads the distribution and package release from the banner and, for Ubuntu and Debian, compares it with the fixed version from the [Debian security tracker](https://security-tracker.debian.org) and [OSV](https://osv.dev), labeling the match *patched by distro*, *vulnerable per distro tracker*, or *version-only*. Other distributions, such as RHEL, are recognized and stay version-only. Matches are labeled, never dropped.
6. **Auto-fire (optional, off by default).** After a feed sync stores new CVEs, each new fire or smoke CVE is handled once (a run that ended in an error is retried for 48 hours). The AI confirms its matches, and the ones it calls affected or uncertain are tested on their hosts. Hosts that run the CVE's product with no version found have no match, but they are tested too: a template test is a hard check that needs no version. The cap is set under **Settings, AI model** (default 200 hosts per CVE, counted for each project separately).
7. **Test.** An installed nuclei template for the CVE runs on matched hosts once it passes the read-only and destination checks. When none exists, the AI can draft one, and a draft stays a draft until a person reviews it. The reviewer adds an independent positive and negative HTTP response fixture in `web/cveFeed/reviewed_fixtures/CVE-YYYY-NNNN.json`, citing an HTTPS source, and runs `python manage.py review_generated_template <id>`. Only a draft that detects the positive response and rejects the negative one is installed. This covers fixed-path, read-only HTTP detectors, and fixture success proves the detector's behavior, not that a live host is affected. A hit is saved as evidence linked to the CVE, and a tool error is recorded as an error, never as a clean result.

CVE matches appear under **CVE matches** and in **Findings** with a remediation status (open, in progress, fixed, accepted risk). Agents read and update it through the [API](AGENT-API.md).

## Detection strategies

Every CVE has one detection record, shared by all organizations, that says how to tell whether a product is affected: **remote
checks** (a version in an affected range, an HTTP marker, an installed nuclei template, a reviewed nmap script, a TLS property, a
service on a port) and **local checks** on the host itself (a package older than the fixed release, a file that contains a version, a
configuration setting, a service state). Read it with `GET /api/v1/cves/{id}/detection`, the MCP tool `get_cve_detection`, or the
`detection` field of `get_cve`.

A strategy is data, never a program. Every check is one of the kinds above with parameters from an allowlist (HTTP `GET` and `HEAD`
only, nmap scripts from the reviewed list, plain package and file names with no `..`), so whatever runs a check does it with its own
primitive for that kind; nothing in a strategy is a shell command. Each record carries `safety: read_only`.

Records are written by a task every 30 minutes (`author_cve_detections`), hottest first (known exploited, public exploit, high
exploit probability, then score), so a new CVE from any feed gets one within the hour and the back catalog fills in behind it:

1. The **rules author** reads the CVE's own affected products and ranges, and any installed nuclei template. No AI, no cost.
2. The **AI author** is asked once per CVE, for the hot ones only (known exploited, exploit probability or public exploit, or a
   critical score), and only within the daily budget (**Settings, AI model**, default 25 a day; `CVENGINE_DETECTION_AI_PER_DAY` applies when no AI settings exist), spread over the 30 minute runs (the daily budget divided by 48, at least one a run). It sees feed text only, never a project
   or an asset, and its answer is parsed against the schema: a check that does not validate is dropped on its own, and the reason is
   kept on the record. Its checks are added after the rules' checks with an `ai-` id and never replace them. A failed ask is retried
   after a week when the model returned nothing it could parse. An answer that parsed but failed validation is kept with its reasons and not asked again. The same task refreshes the nuclei templates outside the schedule, at most every 3 hours, when a hot CVE from the last two days has no installed template.

A `manual` record is never overwritten. When a CVE's affected data changes, the rules checks are rewritten and the AI checks kept.
`manage.py author_cve_detections [--ai]` fills the whole catalog at once.

The policy the AI follows for each new CVE (scope first: `external`, `local_only`, `unclear`; then the record), when a record is revised, and how an administrator adds facts are in [CVE-INTAKE.md](CVE-INTAKE.md). A CVE only usable from the host itself (`local_only`) is never matched to a host.

### Validating a match

Each detection record also says how to decide a match, so nobody has to rediscover it per CVE:

- `validation.remote_determinable` is `yes` (a nuclei template, an HTTP marker or a reviewed nmap script, at high or medium confidence, can decide it from outside), `partial` (only the reported version or the exposed service, which a backported fix can fool) or `no` (there is no remote check, or the attack vector is local or physical and nothing remote can decide it). `validation.max_remote_state` is the best a remote check can reach on the triage scale: `confirmed` (validated), `likely` or `needs_validation`.
- `validation.validated_when`, `needs_validation_when`, `likely_false_positive_when` and `not_applicable_when` list what moves a match to each state, and `recommended_tools` names the tools (nuclei, nmap, curl, openssl, the package manager, grep, systemctl).
- Every remote check has a `how`: the tool, the invocation with `<TARGET>` and `<PORT>` to fill in, and how to decide from the output. Every local check has `commands`: one read-only command per platform (Debian, Red Hat, Alpine, other Linux, Windows) with the shell, whether it needs elevated rights, an `explain` sentence for a person logged in to the host, and a structured `expect` (`version_lt`, `exit_code`, `output_equals`) that a future authenticated scan can evaluate without parsing prose.

The commands are rendered by the application from the validated parameters of each check, with every value quoted; a model never writes one, and a record read from a seed or a model reply has its commands thrown away and rendered again.

### Seeding the catalog

Building the catalog from the cve.now feed takes one request per CVE, so a new install used to spend hours rebuilding what another instance already had. A **seed** is the whole catalog as one file: every CVE (fire, smoke and ice) with its scores, exploitation signals, affected ranges and references, plus its detection record. On first start it is the first step of the first-run chain, ahead of the feed sync, and an install that still has fewer than 5,000 CVEs is offered it again when a worker starts (at most once a day). cvENGINE downloads the seed published as the `cve-seed` release of this repository, checks it against its manifest (count, size, sha256), imports the CVEs it lacks and their detection records, runs the correlation if there are already hosts, and the incremental feed carries on from there. Detection records marked `manual` are never exported or imported. A CVE already present is never overwritten, nothing in the file is trusted (each field is typed and clipped, each strategy is validated again), and offline or a failed check only means the feed builds the catalog up gradually, as before.

- Maintainer: on an instance with the full catalog, `make export-cve-seed` writes `web/cve-seed.jsonl.gz` and its manifest (it first writes any missing detection records), and `scripts/publish-cve-seed.sh` uploads both to the `cve-seed` release.
- Anyone: `manage.py import_cve_seed [file | --url https://...]` imports a file or the published seed by hand.
- `CVENGINE_CVE_SEED=off` turns the automatic load off; `CVENGINE_CVE_SEED_URL` points it at your own mirror (https, with the `.manifest.json` beside it).

## Keeping scans fast and polite

- **One run per host.** A successful scanner run is reused inside its window: 168 hours (7 days) for nmap, bbot, route checks, naabu, firewall identification, the UDP scan, deep nuclei, WPScan, other sites and subdirectory applications, cloud storage, third-party suppliers, OpenVAS and archived-URL lookups, 14 days for the full port sweep (as a coverage window) and the TLS audit, 72 hours for version and identity probes, and 24 hours for nuclei, the certificate watch, hygiene, re-tests, WordPress detection probes, node2shell, RDP screenshots and signed-in checks. A run that could not finish is asked again sooner (WPScan 24 hours, TLS audit 3 days, UDP and cloud storage 24 hours, suppliers 24 hours, OpenVAS 3 days). Failed or skipped work never counts as coverage, and a Redis claim keeps two pipelines off the same asset. Set the windows with `CVENGINE_TTL_*` in hours ([CONFIGURATION.md](CONFIGURATION.md)).
- **Parents are reused.** A target under one already discovered (`www.example.com` after `example.com`) skips bbot when its parent finished in the last 7 days.
- **Memory aware.** Heavy jobs wait in a queue that hands out memory by estimated cost. If memory runs short, the largest job stops first and bbot, nuclei, and nmap retry lighter. Watch it under **Settings, Resources**.
- **Egress proxy.** **Settings, Proxy** sends the traffic of scans that run on this server to the targets through a proxy (`http`, `https`, `socks5` or `socks5h`, one URL per line, one picked per request in turn; `cveFeed.egress_proxy`). Through it: the in-process web probes and checks (route, version and identity probes, vhost and subdirectory sweeps, cloud storage and supplier checks, the certificate and MTA-STS reads), which still vet and pin the destination first and then ask the proxy for that numeric address only (an HTTP CONNECT or SOCKS5 request to the IP, or for plain HTTP an absolute-URI request to it, with the original `Host` and TLS name); the HTTP checks of the database exposure step; and nuclei (`-proxy`), bbot (its `web.http_proxy`, so its passive modules' calls to outside services too), WPScan (`--proxy`), testssl.sh (`--proxy`) and wafw00f (`-p`). Not through it, because they need raw sockets or speak their own protocol: nmap, naabu, the UDP sweeps, the database wire-protocol checks, RDP screenshots, the liveness checks and OpenVAS, and name lookups, which come from this server. A Sentinel runs on its own machine and keeps its own egress; the setting does not reach it. Calls to outside services (CVE feeds, AI providers, Shodan, GitHub, HackerOne, runZero, Tailscale, crt.sh) are not proxied. A proxy that fails fails the request, never falling back to a direct connection, and a tool no listed proxy suits does not run. Loopback, this stack's own services and private, link-local and tailnet addresses are never proxied (`CVENGINE_PROXY_PRIVATE=1` sends the private ones through it too); `CVENGINE_PROXY_BYPASS` adds more (see [Configuration](CONFIGURATION.md)).
- **Rescan a host.** **Rescan host** (or `assess_host`) runs a full, fresh assessment of one host: DNS, ports, exposure, nuclei, firewall fingerprint, routes, correlation, AI triage, and TLS, ignoring recent results but keeping scope, exclusions, and resource limits. Progress shows stage by stage, and you can stop it.
- **New hosts between scans.** When the certificate watch sees a new hostname, a short pipeline runs on up to 200 new hosts: the same stages a scan ends with (nmap, RDP screenshot, exposure checks, technology pass, firewall fingerprint, route checks, version and identity probes, WPScan, node2shell if enabled, correlation, targeted pass, triage, and change recording). Agents can start it with `rescan_hosts`.
- **Background full port scan.** A slow task sweeps all 65,535 TCP ports of one in-scope IP at a time (10 minutes per host at most), oldest first. A host nmap gave up on at that limit is a failed sweep (it backs off and is retried, nothing is closed on a half answer), not a clean zero. The sweep only learns that a port is open: it never overwrites what a fingerprinting pass recorded for that port (distro, CPEs, TLS tunnel, service name). Ports it finds are fingerprinted and the host is re-tested. `CVENGINE_FULLSCAN=0` turns it off. Every firing first checks instance-wide whether any project (not bug-bounty-blocked) still has a host missing its core first pass; if so the whole firing is deferred and logged ("Full-port scan deferred: N hosts across M projects still need a first pass") rather than spending a 65,535-port sweep on one address while basic coverage is incomplete elsewhere. A backlog that is only bounty-blocked, or only there because scanning is paused instance-wide, does not gate: see [Host-assessment coverage top-up](#ai-review-every-three-hours).
- **Other sites and subdirectory applications.** Two slow sweeps on their own `vhost_queue` ask the project's known names at its web addresses and the well-known application paths of its web hosts, a few at a time, once a week each (see [Other sites and applications on a host](#other-sites-and-applications-on-a-host)). `CVENGINE_VHOST=0` and `CVENGINE_SUBDIR_APPS=0` turn them off.
- **Background UDP scan.** The TCP sweep never looks at UDP, and DNS, NTP, SNMP, IKE, IPMI, SSDP and memcached all speak it, so a second slow sweep (`cveFeed.udp_scan`) scans a short curated list of UDP ports with `nmap -sU -sV`. It rides the same beat firing as the full port scan (which queues it), runs on its own queue (`udp_queue`) under its own heavy job (`nmap-udp-bg`, one at a time, behind everything else), takes one IP at a time, and scans each IP at most once a week (`CVENGINE_TTL_UDP_SCAN`, hours). It uses the full port scan's gate exactly: in-scope, not CDN, a scannable address (private ones only with `CVENGINE_ALLOW_PRIVATE_TARGETS` or as the project's own tailnet device), no excluded, archived or blocked name, not a shared platform's edge, re-checked just before nmap starts; it stops while scanning is paused, and it skips a project whose bug bounty engagement has not confirmed automated testing (the same check as the cloud storage sweep). Like the full port scan it also defers its whole firing, instance-wide, while any project still has a host missing its core first pass. It is on by default, as part of the slow, low-priority scanning; `CVENGINE_UDPSCAN=0` turns it off.
  - **Ports.** 53 DNS, 67 and 68 DHCP, 69 TFTP, 123 NTP, 137 NetBIOS, 161 SNMP, 500 IKE, 514 syslog, 623 IPMI, 1194 OpenVPN, 1812 and 1813 RADIUS, 1900 SSDP, 4500 IPsec NAT-T, 5060 SIP, 5353 mDNS and 11211 memcached. `CVENGINE_UDPSCAN_PORTS` replaces the list.
  - **Politeness.** `--max-retries 1`, `--max-rate 20` packets a second (`CVENGINE_UDPSCAN_MAX_RATE`), version intensity 3 (nmap's default is 7), no host discovery, no DNS, a host timeout of 20 minutes (`CVENGINE_UDPSCAN_HOST_TIMEOUT_MIN`), and only the reviewed scripts: `nbstat`, `snmp-sysdescr`, `snmp-info`, `ntp-info`, `upnp-info` and `ipmi-version`, each one request and read-only. `ntp-monlist` is deliberately not run: nmap files it under intrusive, and the target records the request.
  - **What counts as open.** UDP has no handshake. A port that replies is `open`; one that sends an ICMP port-unreachable is `closed`; silence is `open|filtered` (nmap cannot tell open but quiet from dropped by a firewall). `-sV` sends its probes to the silent ports and promotes the ones that answer to `open`, so only a port that answered is stored as `open`, and only those count as exposed surface, heat, search results, change tracking and CVE evidence. A silent port is stored as `open|filtered` only on a host that answered other probes (a firewall that drops everything produces no rows), is never counted anywhere, and is shown on the host's Services tab as a note. A port that was open and goes silent stays open for one more sweep, then becomes `open|filtered`: one lost datagram is not a closed port.
  - **Protocol.** Ports are keyed by number and protocol, so UDP 161 and TCP 161 are two rows on one address. Everything that connects (nuclei, the database, RDP and TLS checks, web routes) reads TCP ports only; evidence, CVE correlation, the host page and the counts read every protocol.
  - **Evidence for CVE matching.** An open UDP service that names a product and version (nmap's own probes; the SNMP sysDescr of Cisco IOS, IOS XE and Junos; the SSDP server string of MiniUPnPd and the portable UPnP SDK; the NTP readvar version) is correlated exactly like a TCP service. A kernel string in a sysDescr is not a product and is not used. When a UDP service appears or changes, the hosts on the address go through the re-test pipeline once (one re-test per host per day).
  - **Findings** (check names `udp_*`, stored like the other hygiene findings with the fix in the text and in the evidence, resolved when a later sweep no longer shows the service): memcached answering on UDP 11211 (high: reflection and amplification, and an unauthenticated cache); SNMP answering the default `public` community, proven by `snmp-sysdescr` getting a reply (high); NTP answering control queries, proven by `ntp-info` (low); SSDP answering on 1900 (medium); IPMI answering on 623, proven by `ipmi-version` (high, RAKP hash disclosure, CVE-2013-4786). Findings are computed from the stored ports of every address a host has, so a host with two addresses keeps what the other showed.
  - **It needs raw sockets.** nmap `-sU` sends its own packets, so the worker needs `CAP_NET_RAW`. The celery container runs as root with Docker's default capabilities, which include it, and the TCP SYN scans already depend on it. A worker without it (a hardened `cap_drop`, an unprivileged runtime) does not scan UDP: the firing records the reason, the activity feed says so once a day, and the system status shows `udp_scan` as `unavailable` with the reason and lists it under problems. It never fails silently and never stamps an IP as scanned.
- **Paced deep nuclei.** Every 10 minutes one due host gets the approved broad template set on its name and up to 20 nonstandard ports, which covers an inventory of about 1,000 hosts each week.
- **Weekly deep discovery.** Daily, each apex domain without a deep discovery in the last 7 days gets one, up to 50 per run. If only its subdomains were targets, the apex is added. This is the one automatic rediscovery without an AI model.
- **Pause everything.** An App Admin can **Pause all scanning** from **All projects, Activity**. The pause survives restarts: work that touches targets or spends AI budget waits, running scanners stop cooperatively (including a running OpenVAS task, local or on a Sentinel, which the OpenVAS step stops on its next run, within 15 minutes), and running scans are marked aborted. An update's own drain pause stops new work but lets what is running finish. A step that something else calls directly, such as CVE correlation inside a scan, simply runs in line. Bookkeeping that touches no target keeps running (the feeds, notifications, pruning, rescoring). **Resume** releases the queue.

### Cloud storage exposure

A slow background sweep (its own queue, `bucketscan_queue`, daily at 01:38 UTC, never part of a scan) looks for AWS S3, Google Cloud Storage and Azure Blob storage that belongs to a project's domains and is public or dangling. It reads only the storage platforms' documented endpoints, never a project host: anonymous HTTPS `GET` and `HEAD` on port 443, no credentials, no signature, one listing page (20 keys at most) and one `HEAD` of a listed object that does not look sensitive. Object content is never downloaded, nothing is written, and the storage endpoints (shared platforms) are never port-scanned. Each name is resolved once through the same vetted transport as the other probes, so an answer in a prohibited range is never connected to.

Candidate buckets, in order of ownership confidence (the tier is kept on the finding):

1. **cname.** A host of the project has a CNAME to a storage endpoint: `<bucket>.s3.amazonaws.com` and its regional and website forms, `c.storage.googleapis.com` (the host name is then the bucket), `<account>.blob.core.windows.net`.
2. **served.** A host answers with a storage `Server` header (`AmazonS3`, `UploadServer`); the bucket is inferred from the host name.
3. **reference.** A storage URL in data cvENGINE already holds: crawled and archived endpoints, page URLs, route redirects, stored scanner responses. An Azure container is tested only when such a URL names it.
4. **guess.** Permutations of the label of each target's registrable domain (`example`, `example-backup`, `example-assets`, `example-dev` and 37 more suffixes, plus the domain itself and its `www.` form at S3) checked at S3 and GCS. Azure account names are never guessed. Turn guesses off with `CVENGINE_BUCKETS_GUESS=0`.

| Result | Finding |
| --- | --- |
| Public listing, tier cname or served | High; critical when the listed names look like backups, database dumps or keys |
| Public listing, tier reference, name carries the project's own domain label | The same as above |
| Public listing, tier reference otherwise | Medium, "ownership unconfirmed" |
| Public listing, tier guess | Medium, never worse: "name guess, ownership unconfirmed, verify the bucket is yours" |
| Name not registered (S3 `NoSuchBucket`, Azure account with no DNS name), tier cname or reference | High, a takeover: anyone can register the name. A GCS name with a dot is medium, because only a verified domain owner may create it |
| Not registered, tier served or guess | Nothing: an inferred name proves nothing |
| Exists, listing refused | An observation (info) on the host, never a finding |

The findings are hygiene findings (check names `bkt_listing` and `bkt_takeover`), so status, assignee, comments, triage, notifications and the API work as for every other finding; the hygiene task leaves them alone. At most 20 object names are stored, and a name segment that looks like a secret (a provider key id, a token, a JWT, `key=value` with a secret word, a long random token) is stored as `[redacted]`. A finding resolves when a later check of the same bucket ran and no longer finds it, or when the reference that led to it is gone (a removed CNAME is the fix for a takeover); a check that gets no answer changes nothing and is asked again the next day.

Politeness: one global request rate shared by every worker (`CVENGINE_BUCKETS_RPS`, 2 a second by default, at most 5), at most `CVENGINE_BUCKETS_MAX_PER_SWEEP` buckets per project per sweep (strongest tier first, longest waiting first), a weekly window per bucket (`CVENGINE_TTL_BUCKETS`), one sweep at a time, and a stop while scanning is paused. Excluded names, hosts of an excluded domain, archived hosts, hosts that resolve to a prohibited address and projects whose bug bounty engagement has not confirmed automated testing are skipped.

### Third-party suppliers

A project can list the **third-party suppliers** it depends on and cannot fix for itself (a hosting provider, a payment processor, an outsourced portal). They are checked from the outside, passively, so the project can see what they run and ask them about it. A supplier is **not an owned host**: it is a row of its own (name, tier critical, high or normal, the exact domain names to look at, a contact and notes), per project, and its results are rows of their own. It never becomes a target, a host or a scan input, and none of this reaches discovery, bbot, nmap, naabu, nuclei, subdomain enumeration, host assessments, remediation assignment, SLA clocks, hygiene lists, stats or the oldest-open figure. Only an organization admin or an App Admin can add or remove a supplier; members and auditors can read. A name that is one of the project's own targets (or under one) is refused (an owned domain belongs in Targets), and so are addresses, ranges, wildcards, URLs, names with a port or a path, private names (`.local`, `.internal`, `.lan` and the like) and a name an organization excluded.

**The host card.** Each listed name gets a Shodan-style card, refreshed by every check and kept when a later check cannot read a section:

- the response headers of the front page (raw, cookies' values never), the `Server` and `X-Powered-By` banners, the page title, and whether plain HTTP answers;
- the TLS certificate (subject, issuer, names, validity and days left, key, signature, trust problem) and the negotiated protocol and cipher;
- the **technology stack with versions where the response states them**: web server, language, framework, CMS, JavaScript libraries, read with the same fingerprinting owned hosts use (`cveFeed.fingerprint` through `route_auth.classify`: headers, generator tags, markers in the page, script names), from the one front page a browser would get. No other page is read for it;
- the addresses the name resolved to, whether it handles mail, the edge in front of it, and when it was last checked and last answered.

**Technology search.** Search all of a project's suppliers by technology (`php`, `node`, `nginx 1.1`; commas for any-of) on the Suppliers page, `GET projects/{slug}/suppliers/hosts?tech=`, or the `search_supplier_technology` tool. A term is matched anywhere in the technology name and version and in the raw `Server` and `X-Powered-By` banners, so the answer to "which vendors run PHP?" is one query, and the page can copy a plain-text message to the supplier about what they announce ("please confirm this is on a supported, patched version"). Nothing is sent from cvENGINE.

**Findings** are secondary and informational, kept apart from every other finding table (`SupplierFinding`: severity, evidence, first seen, last seen, status `open`, `accepted` or `resolved`, and a plain-text note about what to ask the supplier). A finding resolves by itself when a later check that could decide it no longer finds it (a check that got no answer changes nothing), and a resolved one that returns reopens. Four checks, all passive:

| Check | What it reads | Findings |
| --- | --- | --- |
| TLS | One certificate read of the name on port 443 (`hygiene.probe_tls` and `hygiene.evaluate_cert`) | Expired or expiring, name mismatch, untrusted or self-signed chain, SHA-1 signature, short key, TLS 1.0 or 1.1 accepted. The heavy testssl.sh audit is never run against a supplier |
| Email | SPF, DKIM, DMARC, MTA-STS and the MailFail checks, DNS only, plus the one MTA-STS policy file over verified HTTPS, for a name that handles mail | The owned-host rules at low or worse; a missing MTA-STS policy is low for a supplier |
| Headers and pages | The front page over HTTPS and HTTP, then one plain GET per path of a fixed list of 11 (`/wp-login.php`, `/administrator/`, `/phpmyadmin/`, `/manager/html`, `/server-status`, `/login`, `/solr/`, `/console/`, `/owa/`, `/remote/login`, `/admin/`) | Missing HSTS, missing security headers, plain HTTP served, and an administration or login page that answers with the product's own wording (a catch-all 200 is not a finding). Never a guessed path |
| Known CVEs | The versions the card shows, against the CVE catalog with the same matching and evidence rules as owned hosts (`correlation`, `match_policy`), stricter: only a version inside a bounded affected range, never a product name alone, never an unbounded advisory, and nothing behind an edge that rewrites the banner | One informational finding per announced product and version, naming its CVEs. A distribution build is one step lower ("fixes may be backported"). Never validated: nothing is tried against the supplier and no finding can be marked as exploited |

**Safety**, the same rules as the other slow sweeps. Every name is resolved once and every address must be public; a loopback, private, link-local, cloud metadata or otherwise prohibited address refuses the whole name, even with `CVENGINE_ALLOW_PRIVATE_TARGETS` set, and every connection goes to those vetted numeric addresses through the pinned transport. Only ports 443 and 80 are used, only the listed names are resolved or asked (no subdomain, neighbour or mail host), there is no port scan, and an edge that challenges a request is recorded and never worked around. The sweep (`supplier_sweep`, its own `supplier_queue`, daily at 03:52 UTC, `CVENGINE_SUPPLIERS=0` turns it off) stops while scanning is paused, skips a project whose bug bounty engagement has not confirmed automated testing, shares the slow web client's global request gap with the other slow web sweeps, checks each supplier once a week (`CVENGINE_TTL_SUPPLIER`, hours; a supplier that answered nothing is asked again after 24 hours, `CVENGINE_TTL_SUPPLIER_FAILED`), runs one sweep at a time through a Redis claim, and is capped: suppliers per project, names per supplier and requests per sweep (`CVENGINE_SUPPLIERS_MAX_PER_PROJECT`, `_MAX_DOMAINS`, `_MAX_REQUESTS`; [Configuration](CONFIGURATION.md)). A supplier too big for what is left of a sweep's request budget waits for the next one. A new supplier has no card until the next daily sweep.

### Shared platform addresses

A name on Netlify, Vercel, GitHub Pages, Heroku, or a CDN edge answers on addresses that belong to the platform. cvENGINE recognizes them from the name's CNAME, the `Server` header, or the CDN flag and never points nmap, nuclei or the full-port sweep at them (the host's name is still scanned). The host record says so.

### Shared provider domains

A tenant of a multi-tenant provider owns only its own subdomain. For `acme.jfrog.com`, the registrable domain `jfrog.com` belongs to the provider and all its customers, so cvENGINE never promotes it to an apex or enumerates it. A curated list (`SHARED_DOMAINS` in `web/targetApp/shared_domains.py`) marks such domains, and a target under one is **host scoped**: bbot runs with strict scope, the apex sweep skips it, and the certificate watch asks only about that host. Each target has a **scope mode**: `auto` (the list decides), `host`, or `parent` (for a domain you control that sits on the list).

### Excluded hosts

An organization can remove a host and exclude it (**Remove & exclude**, or the API). An exclusion matches the exact host name, case-insensitively, and every stage skips an excluded host in every project of that organization. Adding it as a target is refused. The Hosts page shows names that point at the same addresses as one host, so **Remove & exclude** offers to take those other names with it (otherwise the next name would simply take its place on the page). To drop a whole domain, put `-example.com` on a line in **Add targets** (a paste is checked against its size cap, 10,000 lines and 100 exclusion lines, before any exclusion is applied, so a refused paste removes nothing) (or call `exclude_host` with `include_subdomains`): the name, every name under it (`www.example.com`, `a.b.example.com`, never `notexample.com`) and every target named like them are removed in every project of the organization you can write to, their running scans are stopped, and nothing under that domain is discovered, scanned or added again. A line such as `-com` or `-co.uk` is refused. **Delete host data** removes a host from one project only and leaves it free to be found again. **Move host** (the host page's Manage tab, or `move_host`) hands a host to another project you can write to, in this organization or another: it is added there as a target and scanned from scratch, its data is deleted from the project it left, and that project's scans skip the exact name from then on. Moving it back lifts that. **A target moves with its history.** Moving a target (`example.com`, however many hosts it holds) to another project of the same organization points it at the new project instead of deleting it and discovering it again: its scans, hosts, findings, CVE matches, notes, labels, state, triage and assessments all come with it, and the next scan there updates the same records. A target holding other hosts asks first (the page names them and says how many; `move_host` needs `whole_target: true`), and every target of the project under it goes too. A queued or running scan of it is stopped, and with discovery on it is scanned in the new project. A row the destination already holds for the same host (a label, say) stays, and the moved one is dropped. The old project keeps the target names blocked, so its other targets do not start tracking them. Moving it back lifts that. A single host under a larger target, and any move to another organization (whose targets, addresses and ports are separate records), still delete the host's data here and add it there to be scanned from scratch. Removals that a scan already under way gets in the way of (it writes a row for a target that is being deleted) are run again until they settle, and an exclusion is recorded before anything is deleted so no new scan picks the names up.

## Check coverage

With this many checks, a host record says which ones apply to it and which of those have run: `check_coverage` on every host in `hosts`, `search` and the MCP `list_hosts` and `search_hosts` ([Agent API](AGENT-API.md#hosts-and-search)), and "NN of NNN applicable checks done" under **Overview** on the host page. It is accounting only: it reads what the checks already recorded, and runs, queues and changes nothing.

**Only checks that apply are counted.** A host with no TLS port is not counted against the TLS audit, a host that shows no sign of WordPress not against WPScan, a host that is not web not against the web checks, the UDP sweep only for addresses it would scan (not a CDN or shared platform edge, nor an address a scanner may not use), a check whose switch is off (`CVENGINE_NAABU=0`, `CVENGINE_VHOST=0`, and so on) not at all, the slow sweeps (UDP, other sites, subdirectory applications, TLS audit) not for a project whose bug bounty engagement has not confirmed automated testing, and the checks that run on a target as a whole (discovery, certificate transparency, the web archive, email authentication, the weekly deep discovery) only on the host that is the target. An excluded or archived host has no applicable check. A name is never resolved to decide this: only stored facts are read.

**Three states.** `done`: the check applies and ran inside its window, which is the ledger window of its kind (`cveFeed.ledger`, with its `CVENGINE_TTL_<KIND>` override); a check with no ledger kind (the database exposure check, CVE correlation) is judged by the time its scan stage finished against seven days. `due`: it applies and never ran, ran longer ago than its window, or its last attempt failed (the `detail` says which). `not_applicable`: it does not apply (the `detail` says why). A check on several addresses or ports is `done` only when every one is covered. A run of any template revision counts, and the thorough WPScan pass waits for the quick pass.

**Where a run is read from** (all existing rows, no migration): the service ledger (`ServiceRun`) for nmap, naabu, wafw00f, the nuclei passes, WPScan, version probes, node2shell, RDP screenshots, the TLS audit, other sites, subdirectory applications, OpenVAS and the signed-in passes; the address row for the full port sweep; `RouteAuth` for the route check; `TlsCertificate` for the certificate check; `ScanActivity` of the host's scan for the stages with no ledger kind. A page of hosts is read in a fixed number of batched queries, never one per host or per check, and every query is limited to the page's own projects.

**Hosts inside a declared internal network.** A host whose name is an address inside a network its project declared internal is scanned only by the internal scan driver (`cveFeed/internal_scan.py`), through a Sentinel inside the network, so the external rules above would call nearly every check not applicable (a scanner may not be pointed at the address from this server). Such a host is judged by `INTERNAL_PLANS` instead: only what the internal scan runs applies (the nmap fingerprint, the UDP sweep, both nuclei passes, the TLS audit of each TLS port, WPScan on a site that shows WordPress, CVE correlation, and OpenVAS where the project opted in), read from the same ledger kinds and scan stages as any host (the internal driver records `nmap-fast`, `testssl` and `udp-scan` runs itself, a `*-failed` kind when a Sentinel answered and the test did not complete, and nothing when no Sentinel answered). Every other check is `not_applicable` with the reason that the internal scan does not run it. A due check on a host with no live Sentinel inside the network says so in its `detail`, so a quiet host is not mistaken for a clean one. The host's `check_coverage.internal` is the declared network (`null` for any other host).

**Adding a check.** Everything is in one module, `web/cveFeed/check_coverage.py`:

1. Give the new check a ledger kind in `DEFAULT_TTL_HOURS` (`cveFeed/ledger.py`), even when 24 hours is right, so its window is visible.
2. Write a `plan_<name>(host, evidence)` function: return the text saying why the check does not apply to this host, or a list of `Unit` (the addresses, ports, CVEs or the host itself it is judged on, each with its recorded runs: `evidence.ledger_runs(kinds, project_id, asset)` for a ledger asset, `evidence.head_runs(...)` for an asset like `host|...`, `evidence.stage_runs(scan_id, stage)` for a scan stage). Read only what `HostFacts` already holds (ports, technologies, web bases, scannable addresses, probe rows); if a rule needs a new stored fact, add it to `HostFacts` and to the batched queries in `load`.
3. Add a `Check(id, label, plan, kinds=..., sweeps=..., stages=...)` line to `CHECKS`, in the order it should read.
4. A kind, sweep or scan stage that is deliberately not a per-host check (a retry window, a scheduler, project-wide work) goes in `EXCLUDED` with its reason instead.

`tests/test_check_coverage.py` reads the code and fails when a ledger kind (a `DEFAULT_TTL_HOURS` key, a `ledger.record` or `fresh` call, a `*SERVICE*` constant), a `ledger.sweep_claim` name or a `_stage(...)` name in `cveFeed/discovery.py` is in neither `CHECKS` nor `EXCLUDED`, so a new feature cannot skip the checklist. Add the applicability rule to `ApplicabilityTests` as well.

## The work conductor

Scans used to start only when someone asked or when a daily or weekly sweep ran, so for most of the day nothing was running even with a thousand hosts to look after. Now a watchdog runs every minute and keeps the discovery queue topped up: when fewer than `CVENGINE_WORK_DEPTH` scans (default 3) are running or queued, it starts discovery, in the mode stored on each target (standard unless it was added or set otherwise: a passive target stays passive, a deep one deep), of the targets that have gone longest without one: never scanned first, then the stalest. It starts at most one per project per round so no project starves the others, and it never picks a target scanned within `CVENGINE_WORK_MIN_GAP_HOURS` (default 2), one that already has a scan going, one an organization excluded, one set to manual only (added with "just add them, do not scan yet", or changed to it on the Targets page: only a person starts a scan of it), a project whose bug bounty engagement has not confirmed that automated testing is allowed (or is paused or finished, or whose program scope changed since the acknowledgement), a target the program's scope does not name ([Bug bounty](BUG-BOUNTY.md#the-scan-gate): the full port sweep, the weekly deep nuclei lane, OpenVAS, certificate transparency and the other sweeps ask the same shared check), or anything at all while scanning is paused (an update's pause included). Each start is logged in the target's project activity. A big Add targets paste queues only its first `CVENGINE_BULK_DISCOVER_NOW` targets (50) and leaves the rest to this conductor, so one request cannot queue hundreds of scans ahead of every other project's. Set `CVENGINE_WORK_DEPTH=0` to turn it off. The system status (`get_system_status`, App Admin) shows its depth, the scans running and queued, and its last round, and reports a problem when targets exist, scanning is not paused and nothing is running or queued.

The other work that keeps the instance busy has its own schedule, below: validation of fire and smoke matches, re-tests of changed hosts, the paced full port scan and deep nuclei, triage, and the AI review every three hours.

## Keeping the Sentinels fed, and hosts with no address

- **Hosts with no scannable address are not a backlog.** A name that resolves to nothing (dangling DNS), or only to a private address, has nothing to scan from this server. Once an assessment found that, the host leaves the first-pass backlog (`coverage_topup`, `assessment_review.host_coverage_due`) instead of holding the project's few assessment slots, and instead of making the full-port and UDP sweeps wait for ever (`backlog_exists`). `unresolved_archive.recheck` resolves such a host again every six hours (DNS only) and records why on `HostState.resolution_note`: `private address (...)` (it points inside a private network, which this server cannot scan; like a dangling name it is archived after `CVENGINE_TTL_UNRESOLVED_HOST`, 3 days by default, and the daily rediscovery of archived hosts looks at it again; to scan it, declare the range in the project's internal networks and put a Sentinel with `network:internal` inside it) or `no DNS answer`. A host that resolves again is due at once. The dashboard's coverage counts them apart ("N with no address to scan (...)") from the hosts that are still waiting their turn.
- **A Sentinel always has twice its capacity queued behind what it runs.** `feed_sentinels` (every minute) compares the tasks waiting for a Sentinel with twice the live Sentinels' slots and, when short, queues more host assessments in the projects they cover. The assessment caps (`host_assessment.caps`: 20 in all and 5 per project on their own) grow with the Sentinels (20 plus three per live Sentinel slot in all, and the larger of 5 and three per slot that covers the project), and `DISCOVERY_CONCURRENCY` now defaults to 8, because a pipeline that waits on a Sentinel holds a worker slot while it waits. The caps count pipeline runs, and the feed puts the due hosts of one target in one run of up to `CVENGINE_ASSESS_BATCH` hosts (32 by default), so each stage hands a Sentinel tasks that name many hosts instead of one small task per host; every host keeps its own assessment row and outcome.
- **IPv6** addresses are scanned with `nmap -6` (nmap takes one address family per run; a mixed list runs once per family and the reports are merged). Cloudflare's published ranges are a shared edge for both families and are never scanned.

## Sentinel dispatch

A Sentinel is a scanner agent a person runs on their own network ([Architecture](ARCHITECTURE.md#sentinels), [Agent API](AGENT-API.md#sentinels-scan-stage-agents)). Before a scan stage runs one of its tools itself, it asks `agentapi.sentinel_dispatch` whether a live, eligible Sentinel with free capacity and the right capability covers the project. If none does (the case for every project without Sentinels, which pays one cheap check), the stage runs exactly as it always did. If one does, the stage creates one `SentinelTask`, waits for it, parses the typed result into the shape the local tool's output has, and stores it with the same persistence function a local run uses. On a timeout or a reported failure the stage falls back to running the tool locally. A Sentinel's result is data: nothing it reports is executed, and a result is held to the addresses and targets that were dispatched (anything else is dropped). A nuclei pass on a Sentinel skips denial-of-service templates (`-etags dos`) and runs the approved-template snapshot the server runs, which it fetches from `GET /api/v1/sentinel/template-policy` and `/bundle`.

| Stage | Task kind | What goes to the Sentinel |
| --- | --- | --- |
| Inventory, nmap fingerprint (stage 2) | `nmap` | A chunk of up to 64 addresses |
| Inventory, naabu port sweep (stage 2) | `naabu` | A chunk of up to 64 addresses |
| nuclei, technology pass (stage 5) | `nuclei_light` | Up to 64 resolvable targets, tags, severities |
| nuclei, AI-targeted pass (stage 12) | `nuclei_targeted` | The same, for the chosen tags |
| Weekly deep nuclei | `nuclei_deep` | The host and its nonstandard ports |
| WPScan quick pass (stage 9) | `wpscan` | One site and the project's WPScan token, which is scrubbed from the stored task when it ends. The Sentinel returns WPScan's raw report and exit code and the server classifies them, so a dispatched site reads exactly like a local one |
| TLS audit (testssl.sh sweep) | `testssl` | One host and port (never a chunk), returning testssl.sh's own finding items |
| UDP scan | `nmap_udp` | One address, returning nmap's raw XML |
| OpenVAS sweep | `openvas` | Its own path: the sweep tracks the task over many ticks instead of waiting ([OpenVAS](OPENVAS.md)) |
| Internal range discovery | `discover` | One /24 chunk |

Not dispatched: bbot discovery, the RDP screenshot, the exposure checks, wafw00f, route checks, version probes, node2shell, the cloud storage, other sites and subdirectory sweeps, supplier checks, hygiene, the thorough WPScan pass (it can run for hours, longer than a stage can wait), and any nuclei pass that uses a stored sign-in (the sign-in never leaves this server).

**How long a stage waits.** Three separate budgets, all in seconds and shown on the Sentinels page and by `get_sentinel_dispatch`. A Sentinel with a free slot almost always claims a task within its poll interval, so a task nobody claims inside `CVENGINE_SENTINEL_CLAIM_TIMEOUT` (8) falls back to local execution. When every live Sentinel is at its concurrency limit the task is not given up on: it waits for a slot for `CVENGINE_SENTINEL_QUEUE_TIMEOUT` (300), or until the last live Sentinel goes away. Once a Sentinel has claimed the task, the stage waits for the result up to a ceiling for the kind, counted from the claim: nmap 900, naabu 600, nuclei technology pass 900, targeted pass 1,800, deep pass 3,600, testssl 600, UDP 900, WPScan 1,800, discovery 1,200, plus a few seconds for each target beyond the first (nmap 15, naabu 10, nuclei 20, 30 and 60). `CVENGINE_SENTINEL_DISPATCH_TIMEOUT` replaces every ceiling with one number. A Sentinel that stops heartbeating loses its task after five minutes, which ends the wait early. Every hand-off and check-in writes one line to the AI activity feed (**Live** and **Activity**), naming the Sentinel and the outcome, or saying that no Sentinel answered and the stage ran locally.

### Internal networks

A project can declare a private network internal. Its addresses may then be added as targets, and the external pipeline never touches them: this server may not scan a private address, and the work conductor skips them. `cveFeed/internal_scan.py` is the one pipeline for such a target, and every step is a Sentinel task for a Sentinel that holds `network:internal` (granted by the server). There is no local fallback: with no such Sentinel the scan fails and says so, and the next sweep tries again. The steps, in order: the host record for the address (no network access), the nmap fingerprint, the TLS audit of each TLS port, the UDP sweep, the nuclei technology pass, WPScan on the sites that pass tagged as WordPress, CVE correlation, then the AI-targeted nuclei pass. Route checks, probes, hygiene, the database checks and screenshots do not run. OpenVAS reaches an internal network through its own opt-in batch. A daily sweep queues every internal target without a clean scan in the last `CVENGINE_INTERNAL_SCAN_DAYS` (7), or one whose last scan failed at least an hour ago, at most `CVENGINE_INTERNAL_SCAN_MAX` (20) a run and only where a live internal Sentinel exists; a scan can also be started by hand on the target. A second sweep discovers live hosts in each declared range, one /24 chunk per Sentinel task, and adds the answering addresses as targets. What an internal host is judged on in the check coverage is described under [Check coverage](#check-coverage).

## Restarts and stuck jobs

A worker killed mid-task (a restart, an update, an out-of-memory kill) leaves work "queued" or "running" that nothing will ever finish, which holds capacity slots and can block an update's drain wait. Three things recover it.

- **Unacknowledged messages come back at startup.** Before its workers start, each worker container returns every broker message a worker had taken and never acknowledged to the front of its queue (`manage.py requeue_unacked`), so queued scans, assessments and validations that never started run after an update instead of waiting for the broker's 12 hour visibility timeout.
- **Lost queue messages are sent again.** Every 15 minutes the stuck job cleanup (`reap_stuck_jobs`) queues again a host assessment waiting longer than 30 minutes and a discovery scan waiting longer than 30 minutes when the broker holds no message for it, at most once every 2 hours each. A row whose task a queue or worker still holds is left alone, because a long queue after a bulk add is only waiting its turn. Nothing is queued again while scanning is paused.
- **Dead jobs are closed.** A scan or host assessment marked running whose Celery task exists nowhere (not queued, not held, not running) is closed within one cleanup tick once it is older than two minutes, and only when the broker could be asked. As a backstop by age, a host assessment still queued after 12 hours or running after 6 (a batch of hosts: six hours per four hosts, never beyond the discovery queue's time limit), a validation job queued after 6 hours or running after 2, and an activity row running after 11 hours are marked failed with the reason (`CVENGINE_ASSESSMENT_QUEUED_HOURS`, `_RUNNING_HOURS`, `CVENGINE_VALIDATION_QUEUED_HOURS`, `_RUNNING_HOURS`, `CVENGINE_ACTIVITY_RUNNING_HOURS`). A validation job that is expired is due again at once while it has attempts left. While scanning is paused, queued jobs are left alone on purpose and only running ones expire. A late result from a worker that was written off is dropped, never mixed in.

## The bug bounty gate

A project that works a bug bounty program ([Bug bounty](BUG-BOUNTY.md#the-scan-gate)) is scanned automatically only when its engagement says so: the policy was acknowledged and the program's scope has not changed since, the person confirmed that the policy allows automated scanning, and the engagement is `watching` or `active` (not paused or done). An engagement that does not meet all of these blocks its whole project, not only the program's targets, and a project with no engagement is never blocked. One shared check, `cveFeed.bounty_gate`, answers for every unattended entry point: the work conductor, certificate transparency, archived-host rediscovery, host assessments and the coverage top-up (and the first-pass backlog that the full port and UDP sweeps wait on), the new-hosts and re-test pipelines, the full TCP port sweep, the UDP sweep, the weekly deep Nuclei lane, the thorough WPScan pass, OpenVAS, the cloud storage sweep, both other-sites sweeps, the TLS audit, the supplier sweep, template tests, and the validation and hygiene sweeps. The check coverage counts the checks it holds back as not applicable. A scan you start by hand is not held to the project check.

The gate also works per host (`cveFeed.bounty_scope.ScopeIndex`), for every host a scanner is aimed at and whoever started the scan: a host the program lists as out of scope, or does not list at all, is never scanned, and a host that is only ambiguous is scanned once it has been added or imported as a target of the project.
