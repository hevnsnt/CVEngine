# Pipeline

Add a target and cvENGINE runs one pipeline for it. Stages run in order and each records its own result, so you can see exactly what was covered. If discovery fails, the scan fails. If a later stage fails, that stage is named in the scan's error and the scan still completes, so the hosts it found stay in the inventory.

## Targets

A target is a domain, an IP address, a CIDR range (`10.0.0.0/24`), a dashed range (`192.168.1.1-192.168.1.20`, or the last-octet shorthand `192.168.1.1-20`), or a URL, which is reduced to its host. Every host is validated before it is stored. Targets queue first in, first out.

## Stages

1. **Discovery.** [bbot](https://github.com/blacklanternsecurity/bbot) finds domains, subdomains, and IPs and streams them into the inventory as it runs. *Standard* mode, the default, enumerates subdomains, fingerprints web hosts with safe modules and tries a front-page screenshot of each ([gowitness](https://github.com/sensepost/gowitness): an older, best-effort capture that the host page shows only where the browser stage below has taken none; it is only attempted for a host that answers over HTTP, and never follows a redirect; when the module cannot start, the discovery writes a "Screenshots unavailable" line to the activity feed, and the browser stage is not affected). *Deep* mode runs everything bbot has, including brute forcing and spidering (except bbot's `trufflehog` module, which checks every secret it finds against the issuer's live API and is therefore off unless `CVENGINE_BBOT_TRUFFLEHOG=1` is set for a project that is not a bug bounty project; see [Configuration](CONFIGURATION.md)), and takes hours. *Passive* keeps discovery to public sources (later stages still connect to the hosts it finds). The mode chosen when a target is added, or changed later in the Targets page's Discovery column, is stored on the target (`Domain.discovery_mode`; targets from before it was stored are standard) and used by every scan that starts on its own: the work conductor, a moved target, a Tailscale sweep. The weekly deep sweep leaves passive and manual targets out, and a manual only target (*Just add them, do not scan yet*) is never scanned automatically: not by the work conductor, the first-run wizard repeating a target, a recovered queued scan or a Tailscale sweep, and its hosts (found by certificate transparency, or by a scan before it was set to manual only) are left out of the coverage top-up and the Sentinel refresh, the AI review's host assessments, the full port and UDP sweeps, the weekly deep nuclei lane, the daily hygiene check, the thorough WPScan pass, the TLS audit, the cloud storage check, the virtual host and subdirectory application sweeps, the hourly screenshot backfill and OpenVAS's own selection; the new-hosts pipeline (and with it the re-tests and the RDP and web screenshot stages) does not run unless a person asked for it. Only a person's own request reaches them: Discover once a mode is chosen (which ends manual only), a rescan of named hosts, assess this host, Take screenshot, and a host in the project's OpenVAS forced hosts (`forced_hosts`). Scan answers 409 for a manual only target until a mode is chosen. A host that a target which is not manual only also holds (a row under each, or its own name stored under a second target) is not held back: it is that target's to scan. The re-tests that follow a person's rescan of hosts under a manual only target are refused as inconclusive by the new-hosts pipeline (they are not started on their own) and are tried again with a growing delay for up to three attempts, which the pipeline refuses the same way, and then marked failed. A scan the system queued for a target that was set to manual only before its turn came fails with that reason instead of running. A passive target's certificate transparency finds are recorded and not connected to, and its internal-range scan is not started on the daily schedule (an internal scan is nmap and nuclei through a Sentinel). The hosts a passive *discovery* finds still go through the later stages, as above. Scan runs in the target's stored mode (and answers 409 for a manual only target until a mode is chosen). Discover runs in the mode chosen next to the button, the stored one by default (a manual only target has none: the choice starts empty and Discover waits for a mode), and keeps the mode it ran in on the target; a scan already going keeps the mode it started in, and an internal target's scan, which has no mode, leaves the stored one unchanged. REST and MCP `discover_target` say both: `discovery_mode` is what is stored afterwards, `scan_mode` what the returned scan runs in. A bare IP skips bbot and gets a reverse-DNS lookup and a read of its certificate. A name's addresses come from a Sentinel's answer (the discovery run's resolutions, or a `dns_resolve` lookup of the new hosts); an answer one Sentinel alone gives that would add or replace a host's addresses, or move the host onto or off the do-not-scan list, is held as unconfirmed until a second Sentinel or three consistent runs confirm it, and the host keeps its addresses meanwhile ([DNS answers are cross-checked](SENTINELS.md#dns-answers-are-cross-checked)).
2. **Inventory.** [nmap](https://nmap.org) fingerprints each IP once per window (`-sV -O`) on the top 1,000 ports plus 37 high-risk ones that nmap's ranking leaves out, such as Redis, MongoDB, the Docker and Kubernetes APIs, and etcd. It records ports, services, products, versions, CPEs, the distribution read from the banner, and the OS. Only open ports are correlated, and a port that closes is marked closed. By default, [naabu](https://github.com/projectdiscovery/naabu) finds every open port of each address first (a full 65,535-port SYN sweep at a polite rate), and nmap fingerprints just those instead of guessing from its own top-1,000 list; `CVENGINE_NAABU=0` turns this off and falls back to nmap's own top-1,000 guess alone. Its scripts also read banners and SSH, TLS, HTTP, SMB, NetBIOS, and RDP details, plus each database's own pre-authentication greeting (MySQL, Microsoft SQL Server, MongoDB, Redis, Memcached, and CouchDB), which fills in a version or product nmap's own probe missed. They name the Windows build, computer, and domain from RDP, SMB, and Microsoft SQL Server's own NTLM negotiation, and they raise two findings: an FTP server that accepts anonymous sign-in (with its listing as evidence) and an RDP server that does not require Network Level Authentication.
3. **Screenshots.** Two things happen after nmap, in the same place for every kind of run (a full discovery, a host assessment, **Rescan host**, hosts the certificate watch finds, a retest). *Web pages:* every host with a responding web port gets its web pages queued for a real browser, see [Web screenshots](#web-screenshots); the stage only queues, so the scan does not wait for the pictures. *RDP:* a server the inventory stage showed accepts a connection without Network Level Authentication gets one pre-authentication login-screen capture, with no credentials sent, stored and read by the AI model for a signed-in account (see [Configuration](CONFIGURATION.md#settings-in-the-app)). A server that requires NLA is never attempted, and its row now says so: *NLA required, no pre-auth screen*.
4. **Exposure checks.** One connection with no credentials to Redis, Memcached, PostgreSQL, MySQL, MongoDB, Elasticsearch, and CouchDB ports (an empty password for the default `postgres` and `root` accounts, never a password list). A server that answers is reported as a critical finding.
5. **nuclei, technology pass.** [nuclei](https://github.com/projectdiscovery/nuclei) HTTP and technology templates fingerprint each host. Each `http/technologies` result is a technology of the host, with the version the template extracted (`Name:version`). The host's link to it keeps where it came from (`source` `nuclei`, when it was seen) and the CPE the template's metadata names (`info.metadata` `vendor` and `product`, else `classification.cpe`, read from the Sentinel library's template index for a Sentinel's line, which carries none: `tomcat-detect` is `cpe:2.3:a:apache:tomcat`, `default-apache2-page` `cpe:2.3:a:apache:http_server`), so correlation matches the technology CPE first (`source_versions.technology_cpes`, `evidence.cpe` on the match) and `tech:` finds it by that CPE. A template that names its product by the matcher that fired (`tech-detect`, the WAF and favicon templates) states no CPE: the server derives one from the name with its own name normalisation (`cveFeed.tech_links.derived_cpe`: the CPE the product alias data cites for the name, else the vendor and product the technology and panel templates' own metadata name for it, `wordpress` is `cpe:2.3:a:wordpress:wordpress`, `atlassian-jira` `cpe:2.3:a:atlassian:jira`; none for a name two vendors use, a service, or a word too short or generic to name one product) and keeps it under `source` `nuclei:derived`. A derived CPE never replaces a CPE a template stated, and in correlation it only adds the records it names: a record the name reaches without it still counts (`evidence.cpe_derived` on the match). A result a Sentinel held through an update is linked the same way when it is adopted (`cveFeed.nuclei_scan.TechLinks`, [Where a technology came from](#where-a-technology-came-from)). The exposed-panel templates (`http/exposed-panels`, tag `panel`) that the template passes run often read the product's exact version from its login page too (Grafana, Jenkins, FortiNAC, FortiClient EMS): an info-level panel hit that extracts a version is also stored as a version reading of the host, under the product the template names, and one that extracts none as an identity reading and a technology with no version, see [Versions already received](#versions-already-received). Then the **network detection pass** (`cveFeed/network_detection.py`, stage `nuclei_netdetect_scan`, only when the scan has such a port) identifies the services that do not speak HTTP: nuclei's `network/detection/` templates run on each open non-web TCP port of a class they cover (SSH, FTP, SMTP, IMAP, POP3, Telnet, MySQL, Redis, MongoDB, RDP, VNC, and ports nmap left unnamed, where the ActiveMQ, RabbitMQ, JDWP, Java RMI, SAP and other templates live). No TLS, SMB, Microsoft SQL Server, PostgreSQL, LDAP or Memcached port is sent: no `network/detection` template speaks to them. It is a `nuclei_light` task with `network_detection: true`, which only a Sentinel that declared contract 10 runs and is handed: each port gets only the allowlisted templates of its class whose reviewed path is under `network/detection/` (raw tcp, one at a time, at most 240 seconds a port and three ports a task, `dos`, `default-login`, `bruteforce`, `fuzz` and `intrusive` always excluded; never `network/cves` or a template that sends a credential). With no such Sentinel live the stage waits and the ports stay due. An unattended scan of a bug bounty project that has not confirmed automated testing sends nothing, and a host outside the program's scope is never a target. What it reads is stored before correlation: a product nmap did not name is written on the port, a version is added to the same product nmap named without one, and nmap's own product and version are never changed; a versioned product the template names on a port nmap read as another product is stored as a first-party reading (`vsrc:nuclei`), matched like any technology. A version is taken only from what a template extracted, only when it is shaped like a release and is the product's own (VNC's `RFB 003.008`, rsync's `RSYNCD: 31.0`, SSH's protocol `2.0` or the JVM a debug port names are not). A port is covered for 7 days (`nuclei-netdetect`), one only partly checked is asked again after a day, and a class with no check after a week.
6. **WAF fingerprint.** On by default (`CVENGINE_WAFW00F=0` turns it off). [wafw00f](https://github.com/EnableSecurity/wafw00f) names the web application firewall in front of each web host with a few requests (up to 25 hosts per scan, 60 seconds each; it runs only when a host answered over HTTP and the binary is present), and the product is stored as a technology of the host (a product, never a version). A generic block that names no product, and a host with nothing in front of it, store nothing. Some of its requests carry attack-looking strings, so a firewall may log them. bbot's own WAF events are stored the same way.
7. **Web route checks.** For each web host, cvENGINE sends one plain anonymous GET to a handful of common routes (`/`, `/login`, `/admin`, `/api`, and paths bbot found) and labels each `open`, `login`, `session_required`, `sso`, or `redirect`. If a server sends gzip or deflate even when identity was requested, the route probe reads at most 64 KiB of decompressed page content; malformed compressed responses are treated as probe errors. The other readers of a response body (the MTA-STS policy file of the email checks and the supplier checks, and the cloud storage checks) are a Sentinel's too and decode gzip and deflate the same way, through one helper of the scanner library (`cvengine_scanner.probes.transport.read_body`), with the byte cap on the decompressed output. The response is scanned in memory for sensitive data such as cloud keys, personal data, and internal identifiers. Only the type, a count, and a masked sample are stored. The page's headers, generator tag, and script names name the technologies and libraries it runs, and the front page's scripts are read for the version their own files state (see [JavaScript library versions](#javascript-library-versions)), so an old library is correlated like any other technology.
8. **Version and identity probes.** A product the earlier stages saw without a version (nginx, Next.js, jQuery, an nmap service with no version) is a lead. cvENGINE asks the host for the missing fact with safe, read-only probes chosen by rule, with no AI: see [Version and identity probes](#version-and-identity-probes).
9. **WordPress detection and WPScan.** Every host that shows any sign of WordPress is probed and scanned with [WPScan](https://wpscan.com/), and nothing is skipped silently: see [WordPress and WPScan](#wordpress-and-wpscan).
10. **node2shell.** Off by default (`CVENGINE_NODE2SHELL=1` turns it on). Hosts fingerprinted as Node.js (or a framework on it), Bun or Envoy are checked for CVE-2026-111497 (`CVENGINE_NODE2SHELL_SCOPE=all` checks every web host) with [Assetnote's own read-only detector](https://github.com/assetnote/node2shell-scanner) (see [Configuration](CONFIGURATION.md#settings-in-the-app)).
11. **CVE correlation.** The inventory is matched against the CVE store.
12. **nuclei, AI-targeted pass.** Your AI model sees the technology names found on each host and picks nuclei tags from those the templates of the release the Sentinels run use (read from the template index of the scanner library: the server keeps no copy of the templates). A built-in technology map always adds its tags. The AI's choice is an AI job the reviewer container answers (`nuclei_targeting`, [AI-REVIEWER.md](AI-REVIEWER.md)): the pass does not wait for it, so a host profile the AI has not answered for yet is scanned with the map's tags, and the answer, kept per host profile for seven days, is used by every later pass over the same hosts. Hosts with the same choice are scanned together, and each host's fire and smoke CVE matches get a template test.
13. **Triage, validation, and changes.** See below.

The daily hygiene task also asks the Internet Archive, once a week per target, for the URLs it saved. A `.php` page or a `/wp-content/` path says a host ran PHP or WordPress at some point. That is kept as historical evidence only: a bare word in search finds the host and labels it *seen in web archive*; it is never treated as a current technology, never a CVE candidate, and `tech:` does not count it.

**Hygiene** runs as its own task when the scan finishes: TLS certificates (expiry, trust chain, hostname, self-signed, legacy protocols), SPF, DKIM, DMARC, and CAA, plus the checks of [MailFail](https://github.com/ACK-J/MailFail) re-implemented server side: records receivers ignore, report addresses on domains anyone can register, unauthorized DMARC reports, weak DKIM and ARC keys, Microsoft 365 Direct Send exposure, MTA-STS, TLS reporting, DANE, DNSSEC, BIMI, and MailChannels lockdown. None sends mail. `CVENGINE_HYGIENE_RDAP=0` turns off the registry lookups. A name with no DMARC record of its own is held to its organizational domain's policy (RFC 7489 section 6.6.3, including `sp`), so a mail subdomain under an apex that publishes `p=reject` is not reported as missing DMARC. A missing SPF or DMARC record is not reported on one lookup: the first sighting is stored as `pending` with the DNS answers as evidence and opens only when the next run sees it too, so a one-off timeout never opens a finding. `CVENGINE_HYGIENE_CONFIRM_RESOLVERS` (off by default) names extra resolvers that confirm it in one run instead; those resolvers are then sent the names being checked. A weak policy a subdomain inherits is reported once, on the organizational domain.

**Cleartext administration services** are part of the same hygiene run (check names `cleartext_*`, stored like the other hygiene findings, so status, assignee, comments, triage, reports, the host score and the API work as for every other one). They are decided from what the scans already stored, with no probe of their own: an open TCP port nmap named `telnet` (`cleartext_telnet`), `ftp` (`cleartext_ftp`), or rexec, rlogin and rsh on 512 to 514 (`cleartext_rservices`; UDP 514 is syslog and is not counted), and a login page the route check saw over `http://` on a host with no HTTPS service (`cleartext_http_login`: no open TLS web port and no HTTPS route). A port with a TLS tunnel (`telnets`, `ftps`, an `ssl/` service) is not reported. FTP is not reported when nmap read a certificate from the port (its `ssl-cert` script negotiates AUTH TLS), which shows the server offers TLS, not that it insists on it. The FTP finding without that evidence says plainly that it is unencrypted unless TLS is enforced. A port nmap named from its port table without fingerprinting it is reported, and the finding says so. Telnet, FTP and the r-services are medium on an internal host and high on a public one (a public address is judged from the address alone, as the host score does; the finding's evidence says which it used); a login page over plain HTTP is low and medium. There is one finding per host and check, naming every port and address; a closed, filtered or unanswered port is never a finding, a host the organization excluded or the project archived has none, a CDN edge address is skipped, and so is a tailnet address (the Tailscale check `ts_remote_admin_exposed` reports remote administration there). A finding resolves at the next hygiene run after the port closes, and a fixed one that returns reopens. `CVENGINE_HYGIENE_CLEARTEXT=0` turns the check off: no finding is made and the open ones resolve at the next run. Not covered: SNMP v1 and v2c in general (it needs an SNMP request the stored data does not hold; a device that answers the default `public` community is already reported by the [UDP sweep](#keeping-scans-fast-and-polite) as `udp_snmp_public`), and whether an FTP server that offers AUTH TLS also accepts a plain login. It sends nothing, so it also works for a host inside a declared internal network: the ports a Sentinel's nmap stored are read like any other, and the daily hygiene sweep (which skips a bug bounty project that has not confirmed automated testing) reaches that target. In the [check coverage](#check-coverage) it is the **Cleartext services** check: it applies to a host with an open Telnet, FTP, rlogin, rsh or rexec port (or a web route already checked, for the login page rule) and is judged by the target's hygiene run (the `hygiene` ledger window, 24 hours) or the `host_hygiene` stage of the host's scan.

By default nuclei runs the whole template library baked into the Sentinel image, in the broad scans and when a match is validated, except the checks that send credentials (`default-login` and `bruteforce`, which post default usernames and passwords to login forms): those run only when an App Admin turns on **Allow checks that send credentials** under **Settings, Scan policy**, and the targeted pass never picks those tags otherwise. Nuclei's denial-of-service templates stay excluded (`-etags dos`), out-of-band (interactsh) checks stay off (`-ni`), and the AI-written templates always stay read-only. A superuser can turn the whole library off under **Settings, Scan policy, Nuclei templates** ([Configuration](CONFIGURATION.md#settings-in-the-app)): then every nuclei run uses a snapshot of the installed templates that passed read-only and destination checks, which means plain GET, HEAD or OPTIONS requests to the scanned host only, no payloads, bodies, code or out-of-band checks. A template may follow redirects on the same host, up to three (nuclei's `host-redirects`, which the technology detection template uses); one that follows redirects to other hosts is left out. The AI-written templates may not follow redirects at all. Changing the setting is recorded in the audit log and makes hosts due for a new nuclei pass. An install that never changed the setting before the library became the default follows the new default. The rule that leaves a template out reads its text, and it fails closed, so a few community templates are left out while the switch is off although they send no real credential: `CVE-2023-41954`, `CVE-2021-34622` and `CVE-2021-34624` (a multipart `reg_password_present` flag set to `true`), `CVE-2021-24527` (a "Reset Password" button label), `CVE-2023-25194` (the JAAS flag `useFirstPass`), `CVE-2021-31589` (an XSS payload in the `login[password]` field), `CVE-2020-29390` (an empty `PW=` in a request line) and `CVE-2023-44353` (`inPassword=bar`, a test value). They run again when an App Admin turns the switch on.

### runZero between scans

A project with a runZero token is also synced from [runZero](CONFIGURATION.md#runzero), outside any scan. The sync stores runZero's OS, hardware, tags, CVE reports and the services it read a product version on (its services export, by port) on the addresses cvENGINE already holds and, if the project turned import on, adds runZero addresses it does not know as targets through the Add targets path (exclusions, private-range policy and organization uniqueness included). runZero's CVE reports only raise the confidence of a match this pipeline already made; they never create or confirm one. Its operating system, versioned services and hardware firmware become third-party version readings of the host ([`vsrc:runzero`](#versions-already-received)): a service is matched only while it is fresh and nothing our own scans saw names its product or contradicts its port, and no port row is ever made from it.

### Inventory details

- **Port discovery.** By default [naabu](https://github.com/projectdiscovery/naabu) sweeps all 65,535 TCP ports of each address (SYN, 1,000 packets a second) and nmap fingerprints only the open ports it found plus ports already known open. If naabu is off (`CVENGINE_NAABU=0`), missing, fails, or sees more than 500 open ports on one address, nmap falls back to the top 1,000 ports plus 37 high-risk ones.
- **Scripts.** nmap runs at version intensity 7 with 20 reviewed scripts: banner, SSH host key and algorithms, TLS certificate, HTTP headers, title, server header and generator, anonymous FTP, RDP NTLM and encryption, SMB OS discovery, NetBIOS, SQL Server NTLM and Browser service information, and the MySQL, MongoDB, Redis, Memcached, and CouchDB greetings. nmap's `-sV` also runs its own version scripts. Their output is dropped before storage, because only the reviewed scripts are trusted to be read-only. Everything the pass reads reaches the host (Sentinel contract version 5): the banner, the TLS tunnel mark (so a TLS service is stored as TLS and an FTP server that offers AUTH TLS is not reported as plain FTP), the CPEs (which feed technologies and CVE correlation like the product and version do), the certificate summary and the script output, the OS accuracy and runner-up guesses, and the closed port the path check probes. A TCP port that the run probed and that is not open now is closed by the pass. Anything a result had to cut (more than 500 ports of a host, clipped banners and script output, nmap's host time limit) is listed with it (`cuts`) and shown on the scan's activity feed and on the host, never silent; so are the cuts of nuclei (findings kept, a stopped run: its targets stay due), bbot and secrets results. A Sentinel of contract version 4 sends none of this and is stored as before.
- **The background port sweep** fingerprints what it finds with `-sV` only: no scripts and no OS guess until the next regular scan.
- **What queues for memory.** bbot, nuclei, nmap (including the background full port and UDP sweeps), naabu, route checks, and template tests wait in the memory-aware queue. The screenshot browser waits there too (one browser at a time, about 450 MB; see [Web screenshots](#web-screenshots)). wafw00f, WPScan, testssl.sh, RDP screenshots, node2shell, and the database checks do not.
- **Per-host limits.** At most 10 CVE template tests per host. Route checks make up to 20 requests per host, 1,500 per scan, 0.2 seconds apart.

## Triage and validation

CVE matches, scanner findings, open databases, open admin routes, routes exposing credentials, and hygiene findings of medium severity or worse are queued for triage, within daily caps. Each finding carries a classification (`confirmed`, `likely`, `needs_validation`, `likely_false_positive`, `not_applicable`), why it matters, how to fix it, when it was first and last seen, and every check that ran. Nothing is deleted or hidden: a likely false positive sorts last. Without an AI provider, findings read "not triaged" and validation still runs.

**Fixed rules keep the model honest.** Hard evidence sets a floor the model cannot go below. A template hit, a database that answered, a distribution tracker that lists the package as vulnerable, a scanner finding whose template matcher fired at medium severity or higher, a CVE template check, a failed deterministic hygiene check, and a route serving a credential are `confirmed`. A version inside a CVE's affected range is at least `needs_validation`. An open admin route is at least `likely`. The model alone can never confirm a finding. A reply that breaks the answer schema is sent back to the model once with the exact reason, and the second answer is used. If that is also rejected, the finding shows a diagnostic you can copy (the reason and the number of attempts, never the reply text) and a later pass retries it.

**One question per kind of evidence.** The model sees cleaned, structured evidence (product, version, advisory range, template id, counts) with hostnames redacted. Findings with the same evidence share one saved answer, with three limits, because the model was shown what the host it was asked about said (a banner, a page title, a certificate, a path, a response) and that is not part of the shared key. First, an answer that would close a finding (`likely_false_positive`, `not_applicable`) is reused only inside the project it was reached in, and for every kind but a CVE match only on the same host. Anywhere else the stored closing answer is not applied: the finding asks its own question (counted against the usual limits) and shows `needs_validation` with a note only until that answer is in. Second, a model's `needs_validation` from another project is not applied where the finding's own question could rate it higher (a version string alone is `needs_validation` at most, so that one is shared), nor from another host to a CVE match with hard evidence the shared key does not carry (a runZero report, the host's own inventory, a validation hit): the finding asks its own question, one per project for a CVE match, and keeps its legacy verdict while it waits. Third, across projects only the classification is shared: the model's reason, impact, remediation and advice are shown in the app, the API, MCP and reports only in the project the answer was reached in, and other findings show "Assessed from a matching finding elsewhere". Inside the project, an answer from another host never closes a finding a person is assigned to or working on, or a CVE match with hard evidence (a runZero report, the host's own inventory, a validation hit). An answer that raises attention (`confirmed`, `likely`, `needs_validation`) is still shared, but the model's suggested step down in severity is shown only where the answer was reached. Correlation follows the same rule: a new CVE match may start as affected or uncertain from an earlier answer for the same CVE, product and version, never as not affected, and never as uncertain when it has hard evidence (that would keep it off the fire page); a rescan of the same host keeps that host's own answer through its earlier finding. An automatic closure of a wrong-product or operating-system sighting is about that one host's sighting and is never shared at all. After the 1.3.3 update the first correlation reviews, once, what earlier versions shared across organizations (an instance with one organization only loses other projects' notes and the shared closing rows): findings another organization's answer closed, or left at needs validation, ask their own question, CVE matches started closed from the shared table become unjudged, another project's notes are replaced by the fixed note, and a host's own closure is kept. Each project with a change gets one activity line with its counts; `manage.py release_shared_closures` shows the same review as a dry run (`--apply` runs it by hand). **Secrets are masked before they leave.** A key or token a scanner found (the value a nuclei token template extracted, the secret bbot's `badsecrets` printed) is replaced in every prompt by its provider class, length and a short keyed fingerprint (`AIza…[redacted 39 chars, google_api_key, fp:1a2b3c4d]`), so the model can still tell that a Google API key is exposed without being given it. A last pass over the text of every prompt of every AI feature, and over every reply before it is stored, masks the well-known secret shapes (cloud, Git host, chat, payment and mail provider keys, JWTs, private key blocks with a key body, the password of a URL, `password=`, `api_key=` and similar key and value pairs with a plausible value, bearer tokens) wherever they appear (`cveFeed/secret_redaction.py`). The drafting of a nuclei template keeps its reply literal (a template may need a JWT or a Basic credential as written) and masks only its prompt. An image sent to a vision model (an RDP screenshot) cannot be masked. Extracted values of a template tagged only `exposure`, `leak` or `disclosure` are masked when they are 12 or more characters without spaces and do not read as a version (`Apache/2.4.49`). The stored finding and what the app and the API show are not changed by this.

**Validation runs by itself.** cvENGINE reproduces a finding with one of six read-only checks and records the exact command and result: a vetted nuclei template, `nmap -sV` on the one port, a HEAD request for the version banner, the credential-less database check, a version and identity probe (see [below](#version-and-identity-probes)), or, for a match on a client-side JavaScript library, the script read (see [JavaScript library versions](#javascript-library-versions)). A hit confirms the finding. A check that does not reproduce it never lowers it, because templates can miss behind a WAF or on another virtual host. A banner that only shows a version is recorded as `observed`. Every five minutes a dedicated worker queues up to 20 findings: fire first, then smoke, then every other CVE match (`CVENGINE_AUTO_VALIDATE_ALL_MATCHES=0` leaves those out). The lane of a CVE match is the heat it would have once proven (`threat.validation_heat`): a known-exploited match whose version is not proven shows smoke but is validated in the fire lane, because a hit is what makes it fire, and a CVE that is neither on the KEV nor exploited is ice (proof would not change its heat) ([Fire, smoke, and ice](FIRE-SMOKE-ICE.md#from-the-feed-to-your-hosts)). OpenVAS selects and orders its hosts by the same heat. A project has at most 10 active jobs, 5 of them cold. Checks are not repeated within 24 hours.

**Validate now.** Matches are validated automatically, so this is for jumping the queue: on any CVE match, **Validate now** (or the API) has the AI plan the checks, runs them, and has the AI review the evidence. The plan can only choose checks the scope and template policy already allow. The plan is an AI job the reviewer container answers (`validation_plan`): the request waits for it in the queue, holding no worker, and goes on with the deterministic plan (the vetted template and the version and identity probes) when the answer has not come within ten minutes, the reviewer is off, the planning budget is spent or the AI fails. When a CVE cannot be answered from outside, such as a local kernel flaw, the match records that no external check applies.

**Retest on fix.** A finding marked fixed is checked again by the same check that proved it (the `hit` or `reaffirmed` steps of its validation), on a Sentinel, through the same runners, the same daily check budget and the same validation queue as any validation; the server runs nothing itself. A result of "does not reproduce" is believed only when a Sentinel also connected to the host's address, so a host that was down is `Fixed, not verified` and is tried again later (a day, then two, four and seven days; six tries). A finding with no stored check or evidence stays `Marked fixed, cannot be re-checked automatically`. A retest that still reproduces the finding reopens it and keeps the new request and answer as its proof. See [Front end](FRONTEND.md#retest-on-fix) and [Agent API](AGENT-API.md).

**When nothing can be checked from outside**, cvENGINE asks the AI once for at most three short, read-only commands a person with shell access to the host could run themselves, such as checking for a package, a process, or a config path named in the advisory, with what the output would mean. It is suggestion only, unverified by this tool, shown under **Confirm it yourself** beside the usual "no check exists" message, never a classification or evidence of anything. The model is told never to suggest a command that changes the host or needs a credential, and to say so plainly when it is not confident of the exact way to detect a given product rather than invent one.

**Changed evidence is triaged again.** A correlation outside a scan (a version or identity probe, a version source, a panel version, a Recog reading, a KEV or range re-read) that creates a match or moves one (its version, its range result, the distribution's answer) tracks it once the write is committed and asks the question again within the triage caps (`retriage_matches`): its triage row takes the signature of what it holds now, so it is never left `triaged` on evidence it no longer has. A scan's own correlation leaves that to the scan's triage stage. A CVE whose record is refreshed has its matches tracked and asked, and findings the backfill gives a first triage row queue their project's sweep at once. A new detection record for a CVE (a new remote ceiling or new guidance, from the model or a person) asks its current matches that already hold an answer again, under a fresh-review nonce made from the record, so the same answer is clamped by the new ceiling; the record is deliberately not part of the evidence signature, which would re-ask (and hold at smoke) every match of every CVE with a record at the first scan after an update. Hot validation compares a finished validation with the finding's evidence as it is now, described afresh, not with the signature its row last stored.

**A validation learns its AI answer.** A validation queues its triage question for the AI reviewer container and finishes before the answer lands, so its result read `deferred`. The record now names the question's AI job (`ai_job_id`), and the answer, a refusal or an expiry updates its `ai_state` (`completed`, `failed`, `unavailable`), status and classification.

**The model is told when the evidence was shortened.** The triage payload is bounded (3,000 characters a text, 40 fields, 20 list items, four levels); when a bound cut something, the prompt says what, and that what was cut is unknown, not absent.

A sweep catches whatever is left: triage every hour at minute 41 (the findings still pending, those in error after a provider failure, and the not-triaged ones once a provider is set), validation daily at 05:17 UTC. Rows outside the current inventory (a match a later scan replaced, a finding closed since) are not swept and are not counted as waiting: `list_triage?current=true` leaves them out, and the triage backlog signal counts only the current inventory.

### How the AI investigates a lead

A finding is judged with everything cvENGINE holds about its host (`cveFeed/host_context.py`): technologies with their versions and where each was seen, the ports with product, version, extra info, banner, HTTP and TLS facts, the front page's headers and title, CDN, WAF, hosting and CNAME hints, certificates, the operating system guess and its runners-up, what runZero and the host inventory reporter said, what probes found or found hidden, earlier check results and the host's other CVE matches. It goes to the model as a second untrusted block, cleaned and capped, with no host name or address. The model is told, in order: is the advisory's product the product the host runs (nginx is not ingress-nginx or nginx-ui), is the version inside the range and did a probe state it or only a banner, is the host behind a CDN or WAF (then the Server header, X-Powered-By and error pages describe the edge, a tag such as `cloudflare` names the edge and not an application, and the origin version is unknowable from here), and does the advisory need local state (then the host inventory reporter decides, not a network check).

**Closing a match needs concrete grounds.** A version inside an advisory's range stays a floor the model cannot clear, unless the application itself verified a ground from the host's metadata: a probe identified a look-alike product (the host's error page is plain nginx and the advisory names ingress-nginx), (and the host does not itself run the look-alike), or a CDN, WAF or hosting edge answers for the host on DNS-level evidence (its CNAME, its name, the CDN flag on an address: a response header such as `cf-ray` is the host's own say-so and counts for nothing) and the match rests on a web response (an SSH, database or mail banner is never the edge's). A match that has standing (worked by a person, a template hit, a distribution verdict, a host report) is never cleared this way. Then the model's `likely_false_positive` or `not_applicable` stands, with its reason. A banner or tag that states no version is never a reason to close a finding, and a template hit or a distribution's "vulnerable" verdict still floors it. When probes or an edge change what is known, the question is asked again without erasing the earlier validation record.

### Version and identity probes

The probe catalogue (`cveFeed/probes.py`) is data: an id, the products it helps with, the requests it makes and the patterns that read the answers. The application renders every request; no model writes one. Each probe sends only GETs (or an nmap service probe), no cookie and no credential, caps its requests, response size (256 KB) and time, goes through the same safe-address gate, exclusions, scan stop and pause as every other check, and logs to the activity feed.

| Probe | Finds |
| --- | --- |
| `headers-root` | The front page's `Server` header and the modules it lists (an Apache header names its PHP, OpenSSL and mod_wsgi versions), `X-Powered-By`, `X-AspNet-Version`, framework headers, `Via`, every generator meta tag and plugin comment, the libraries its scripts are (a version in a file name only as a low-confidence hint, never one in a query string), and the CDN or WAF edge that answered |
| `error-page` | The footer of the server's own error page: `nginx/1.24.0`, Apache, Tomcat, Jetty, IIS Detailed Error; the Kubernetes `default backend - 404`; Express, Spring Boot and Next.js signatures |
| `nginx-variants` | nginx-ui and Nginx Proxy Manager (and its API version) as opposed to plain nginx |
| `nextjs-version` | The Next.js version a framework script states (`window.next={version:"..."}`) |
| `html-libraries` | jQuery, jQuery UI, jQuery Migrate, Bootstrap, AngularJS and other versions from the script files themselves, every copy on the page and the one that runs (see [JavaScript library versions](#javascript-library-versions)) |
| `drupal-changelog`, `joomla-manifest` | Those products' version files |
| `robots-txt` | CMS hints in `robots.txt` |
| `wordpress-detect` | WordPress, by its login page, REST API (and the `Link: <.../wp-json/>; rel="https://api.w.org/"` header), generator tag, readme and core asset versions |
| `nmap-version-all` | `nmap -sV --version-all` on one port with the reviewed safe scripts for its service (`http-server-header`, `http-headers`, `http-generator`, `ssl-cert`, `banner`; `ssh2-enum-algos`, `ssh-hostkey`; `mysql-info`, `redis-info` and the like) |

**What is recorded.** Each result is a `ProbeObservation` (host, probe, product, version, identity variant, source, confidence, outcome) in the project: `found`, `hidden` (the product answers and states no version, which is a result: the AI is told the version is unknowable from outside), `edge` (only a CDN or WAF answered), `challenged` (the edge refused the scanner) or `absent`. A found version is also written as the host's technology (`nginx:1.24.0`; an nmap probe updates the Port row), the host is correlated again, and the deterministic rules then create a versioned match or none. A version is never guessed. Facts found inside the freshness window (`CVENGINE_TTL_PROBE`, 72 hours) are carried onto the next scan's host rows.

**No AI needed.** `plan_for_host` picks the probes for each lead by rule (at most five per host, one web base URL, no nmap probe where a CDN answers). In a validation request the AI may choose among the checks offered and reasons over their results, but a probe is always part of the plan when one applies, and a request ends with "no executable check" only when none does. The plan then says why: a kernel, driver or hardware advisory needs the host inventory reporter, since no network probe can read it. `CVENGINE_PROBE_MAX_HOSTS` (default 60) bounds the hosts probed per scan.

**Parsing.** Versions are read from what a service states and nothing else: `Apache-Coyote/1.1` is a connector's protocol version, not Tomcat's; `Jetty(9.4.51.v20230217)` and every `Name/version` token of an Apache `Server` header are read; a CPE technology (`cpe:/a:apache:http_server:2.4.41`, what Shodan's InternetDB gives bbot) and `Bootstrap:v3.3.7` are normalized to name and version; nmap's `tunnel="ssl"` marks a TLS web service on any port (so port 8444 is asked over HTTPS), its `ssl-cert` output fills the port's TLS facts, and a version that stops being stated (`server_tokens off`) is cleared from the port instead of kept.

### A .php link is a lead

A page that links to a `.php` URL does not show that its server runs PHP: the link may point at another site (a donation form, a partner's shop), and a link on the same site may be a path the server rewrites or answers with its catch-all page. The scanner library names PHP for any such link (the fingerprint source `page:.php link`), and the server applies one rule to it wherever it arrives: the route check's front-page fingerprints, the `headers-root` probe's observations and a supplier check's technologies (`web/cveFeed/php_tells.py`):

- a link to another host or origin is ignored outright (where the server holds the page; a Sentinel's fingerprint does not say where the link pointed, so it is treated as a same-origin link at most);
- a same-origin link is a **lead**: kept in the route answer's evidence (`leads`, state `unverified`) and as a `lead` probe row, never a technology, never a CVE candidate, never counted on the threat card;
- it becomes PHP only when the server says so itself: an `X-Powered-By: PHP` header, PHP in the `Server` header, a `PHPSESSID` cookie, a PHP error or `phpinfo()` page, or another route of the same host (a linked `.php` URL among them) that answered 2xx, not as the server's catch-all page, with one of those signs. The PHP technology then says how (`cookie:PHPSESSID on /shop/cart.php`);
- an ASP.NET or IIS stack (`X-AspNet-Version`, `X-Powered-By: ASP.NET`, an ASP.NET session cookie, an IIS `Server` header) makes the lead weaker still (state `contradicted`).

The update step `backfill_php_link_tells` applies the rule to what is stored: route answers carrying the marker get their lead, the probe rows become leads, the bare `PHP` technology links the route check made on hosts whose routes do not confirm PHP are removed, and those hosts are correlated again, so their version-unknown PHP candidates close and leave the threat card and the situations. The web archive's `.php` URLs are history of the same kind ([Stages](#stages)): never a technology, and `tech:` does not count them.

### JavaScript library versions

A library's version is read from the file itself (`cveFeed/js_libraries.py`), by the web route check on each front page and by the `html-libraries` probe:

- **The file states it.** Its comment banner (`/*! jQuery v3.2.1 | (c) JS Foundation`, `jQuery JavaScript Library v3.2.1`, `jQuery UI - v1.12.1`, `jQuery Migrate v3.3.2`, `Bootstrap v4.6.0`, AngularJS, React, Vue.js, Lodash, Moment.js, Underscore.js, Swiper, DataTables) or, when a bundler stripped the banner, code only the library's own file has: jQuery's `jQuery.fn = jQuery.prototype = {jquery: version` with the version string it names, `$.ui.version`, `jQuery.migrateVersion`, Bootstrap 3's `Modal.VERSION`. A plugin that says `Requires jQuery v1.7` or a `Datepicker for Bootstrap v1.9.0` banner is not that library. This is `version_source: body` (confidence 0.9 for a banner, 0.8 for code).
- **A query string is never a version the file confirms.** WordPress and most themes put their own asset version in `?ver=` (`jquery.min.js?ver=1.0.4` is a theme at 1.0.4, not jQuery 1.0.4). It is recorded on the copy as `query_version` and never used for the copy's version. A stored version equal to it is closed only when that script's own file was read and states another version or none; when the file was never read (reading off, a budget spent, a refused or failing host) it stays a candidate at the file-name confidence with a note saying so, never dropped.
- **A file name is a hint.** `jquery-3.4.1.min.js` or a CDN path (`/ajax/libs/jquery/3.4.1/`, `/npm/jquery@3.4.1/`) gives the version only when the file cannot be read or states none (`version_source: filename`, confidence 0.4). A match on it alone is capped at that confidence and, like every version-only match, held at needs validation.
- **Another tool's version is checked against the page.** A library version only technology detection named (httpx and Wappalyzer, the nuclei technology pass or bbot: source `scan` on the host page) is a candidate at the file-name confidence (0.4, `version_source: other`, with a note), never hard evidence, held at needs validation. **File evidence informs and caps; only a redirect alias closes.** The page's own files never close such a version: static reading cannot prove a page loads nothing else at run time (a `document.write`, a script tag appended by jQuery, a `fetch` followed by `eval`, `createElementNS`, a contextual fragment), so even when every script of the front page on every web port was read whole, its files state another version and no loader was recognised, the match stays open with a note saying what the file states (`js_libraries.STATES_NOTE`: a script whose own `?ver=` or file name its file contradicts; `CONTRADICTS_NOTE`: the library's files on a page read whole state another version that the page explains). Under the KEV heat policy an inferred version is smoke at most, so it never pages. The read still decides the note: whether every script was read whole (`js_libraries.every_script_read`: not served, refused, failing, over the six-script budget, third-party, cut at 300 KB, a second library or copy anywhere in a file (`whole_body`), a run-time loader (`runtime_loaders`) in a file, inline or in the page's markup, inline code not read: `script_page.unread`, `inline_unread`, `loaders`), whether the page explains the version (`script_page.url_versions`, or another library's version on the page), whether the library's code is recognised wherever it appears (`js_libraries.CLOSABLE`: jQuery, jQuery UI, jQuery Migrate), and whether the file states anything at all (a build without its banner proves nothing). The rule reads the front page only (every web port's `/`). Library matches an earlier build closed on the page's files, an absence or a cache-buster (`js_libraries.FILE_KINDS`), and validation's fixed-version script-read closures, are reopened once after the upgrade (`library_reopen.reopen_once`, from the first correlation; automatic closures on matches nobody worked only, never a redirect alias, nothing paged, one activity line per project). The page counts only when the front page of every web port of the host was read by the route check in the last 8 days (up to 300 KB), answered a page (2xx, or the 404 or 410 a hosted site serves for `/`), is whole (not cut, within 80 scripts, 2,000 script tags and 100 inline scripts) and is the site itself. This holds for every library in `js_libraries.LIBRARIES`, and for no other product. A match a redirect alias closed reopens on any fresh reading that no longer supports the closure; the reason is about one host's page and is never shared with or seeded into another match, and nothing a person or a check vouches for is closed.
- **A host that only redirects serves no libraries.** When every current front page of a host answers a permanent redirect (301 or 308) and at least one of them leads to another host the project inventories (`blog.example.com` answering 301 to `example.com`, a host of the same project), the page it leads to belongs to that other host. The probes follow a redirect within the host's group (apex and www); for the host that redirected they read only its own redirect answer (its `Server` and other headers), never the page it leads to: none of that page's scripts, `Server` header or generator tags is recorded for it (the other host's own probes record them). Correlation matches no library version stored for such a host, whichever tool saw it after following the redirect; the match closes at the next correlation or reconcile sweep with the reason "the host only redirects to example.com" (unless a person worked it) and reopens when the host serves a page of its own again. A redirect to a host the project does not inventory closes nothing: the CVE would silently leave the project, so the match stays open until that host is in the inventory. A redirect to the host itself (`http` to `https`, `/` to `/en/`) changes nothing, and a host is not judged an alias when any front page answers anything else (a page, a 403, or a temporary redirect: 302, 303, 307) or when it has a web port whose front page the route check has not read (an application on 8443 beside a 443 that redirects away).
- **One script, one library.** A script is the library its own file name is (`bootstrap.min.js` is Bootstrap and nothing else; `jquery.fancybox.js` is a plugin, not jQuery); a bundle that carries several libraries names each in its banners.
- **Several copies.** Every copy on the page is kept (`copies`: url, version, source, order, state). The page is read the way a browser tokenizes it: a `<script>` inside an HTML comment or inside another script's text is not a script, and a copy that is not the page's ordinary load is a `fallback` that never replaces the copy that loaded: one an inline `document.write` loads only when an earlier one failed (`window.jQuery || document.write(...)`), a `nomodule` script (old browsers only) or one whose type a consent manager switches later (`type="text/plain"`). Up to 80 scripts with a source are read from a page; inline scripts do not count, and a library hint is replaced only by a library the page's scripts were resolved for. Scripts run in document order (`defer` and module scripts after the rest), and a later full copy replaces the global the earlier one set, so the last copy is `effective` and the earlier ones `shadowed`, but only when that last copy's own file was read and states its version: a copy that was not served, was not read or states no version may never load, and a file name is never trusted over what a file states, so such a set is `copies_unresolved` instead. An `async` copy or an inline `jQuery.noConflict(true)` after a copy does the same. The effective copy is matched as usual; a shadowed copy and a fallback stay candidates at confidence 0.4 with the note "shadowed by 3.7.1 loaded later; older code or closures may still use it" (never hidden), and each copy of an unresolved set at 0.5 at most; all of them are held at needs validation. Within one version the copy whose file states it is the evidence, whichever copy is last. Every current front page of the host (https and http, the route check and the probe) adds the copies it read, so a version one of them read from a file is never lost. The match evidence carries `script_url`, `script_sha256` (of a complete body), `version_source`, `version_confidence`, `copy_state` and the copies; the AI triage and the host page's Services tab show them.
- **What is read.** Only scripts the page itself references, on port 80, 443 or the page's own: its own host; another host of the same registrable site, and only when the target is not host scoped and that host is one of the project's own inventoried hosts held by a target that is neither manual only nor passive (it then passes the address check, the organization's exclusions and archived hosts, and a bug bounty program's scope); or a public library CDN (code.jquery.com, cdnjs, jsDelivr, unpkg, Google and Microsoft's, the Bootstrap CDN). A tenant of a shared platform (the public suffix list's private section and cvENGINE's own list: `herokuapp.com`, `blogspot.com`, `onrender.com`, `github.io` and the like) is its own site. A third-party or analytics script and a `data:` source are never fetched, and nothing is read for a passive or manual only target or when `CVENGINE_SCRIPT_BODY_READ=0`. At most six scripts per host (all its web bases together), 40 per script host 0.5 seconds apart, `CVENGINE_SCRIPT_READ_MAX_REQUESTS` (300) and `CVENGINE_SCRIPT_READ_MAX_SECONDS` (600) per scan, each script URL once per scan, and 300 KB of decoded body each (gzip and deflate decoded within the cap), through the same pinned, anonymous, proxy-aware GET as every route check, with no redirect followed to anywhere the probe gate refuses. What a script said is cached by URL with its ETag or length, per project (a public CDN file for everyone): a day for a site's own file or a CDN URL with no version in it, 30 days for a versioned CDN file. A forced re-test or a validation re-check reads past the cache and sends the stored ETag (`If-None-Match`), so a fixed library is seen as fixed at once.
- **Validating a library match.** `nmap -sV` and a HEAD cannot see a library inside a page, so a CVE match on one of these libraries (its advisory names the library itself and not its server-side code, `detection.client_libraries`) is validated by the **script read** (`script_read`) instead: the front page of every web base of the host (https, http and any other web port: correlation merges the copies of all of them) and the scripts each loads are read again with the `html-libraries` read, past the script cache, under every gate above (script reading on, not a passive or manual only target, not a name held only under a target set to one host, the address check, exclusions and archived hosts, the bug bounty scope and, for a run the system started, the project's confirmation of automated testing, the per-host and per-scan budgets). A redirect is followed only on the host itself, so a redirect to another host is seen with its status. The server never fetches an internal host's page: such a match (and one the gates hold back) stays as it was, with the reason on its step; reading it through a Sentinel inside the network is planned for 1.4. Every connection of the read goes through the pinned transport, so it is counted, logged and paced by this server's egress governor like any other in-process connection; a port the governor or the skip list holds is not read and nothing is concluded (the step is `failed` and tried again later). One read of a host serves every library match of it for ten minutes (a host with three jQuery CVEs is read once), and nothing is stored on the host, so the other matches' evidence does not move. The step records the fresh evidence (each base's answer, `version`, `version_source`, `version_confidence`, every copy and its state, what was not read). Only what is truly false is closed:
  - the copy that runs states, in its own file, a version inside the range: `reaffirmed`. Never a hit: the version is on the page, but whether the page is exploitable depends on how it uses the library (the jQuery XSS flaws need attacker-controlled HTML to reach its DOM-manipulation functions), so no hard evidence is recorded and the version-only ceiling still holds;
  - closed (`Closed automatically: fresh script read`, through the same guarded closure as a different-product match, kept on this host only and never shared with another), in one case only, a redirect alias: every current root of the host (each web base now and each current root route) answers a permanent redirect (301 or 308) to another host that is one of the project's own inventoried hosts, and the match was made from a script of the front page (`version_source` body or filename, with its `script_url`); a temporary redirect (302, 307), a redirect to a host outside the inventory, and a version another tool named (it may have been seen on a deeper route the host still serves) never close this way. A fixed version never closes a match: even when the match's own file states one fixed version and every script of every page was read whole, searched end to end and shows no loader, a page can still load another copy at run time that no static read sees, so the read is `observed`, with what the file states;
  - never closed, only `observed`: an absence of any kind (the match's own script now 404s, the library is no longer on the page, moved into a bundle or behind a loader: the next scan's ordinary stale closure retires a match that is really gone), a temporary redirect (302, 307: a login page), an affected copy that is only shadowed or a fallback, copies whose order is unknown, a file not read or cut short, a web base that did not answer, a page or file that loads scripts at run time, an error page. A match a person worked (remediation, an assignee, a comment, a manual validation) or other evidence stands for is never closed: the step says so. An edge challenge is `blocked`; a read that failed is `failed` and retried later.
  - **Validate now** always reads the page again (the ten-minute reuse serves only runs the system started), runs for a person in a bug bounty project that has not confirmed automated testing (an automatic request there reads nothing), and on a match a script read closed reads again instead of returning the closure: a read that finds the library inside the range again, as the copy that runs or as any copy or file of the page, reopens it (its verdict and classification are cleared, so triage judges it again; a copy that may not run gives it no more than confidence 0.4). Every hop of the read's own requests, redirects included, passes the bug bounty program's scope, the one-host target rule and a host-scoped target's own host, besides the address, exclusion and archive gate; a script on a port this server's egress governor holds is recorded as `held`.
  - An advisory about the server-side code of a library of the same name (React Server Components, `react-server-dom-*`, `react-dom/server`, Next.js, `vue-server-renderer`, server-side rendering: CVE-2025-55182) is not the browser library: it keeps its ordinary record and checks.
- **Earlier data.** A version stored before 1.3.2 from a script name or `?ver=` string (source `script:name`) cannot be told apart any more: it stays a candidate at confidence 0.4 with a note, and the host's front page is checked again at the next scan, inside its 7-day window, so its files are read. A version is closed only when the file itself states another one (or none) and the stored string came from the script's query or name; a match a person already worked is never closed this way.

### WordPress and WPScan

WPScan is the primary WordPress assessment. A host is a candidate when anything suggests WordPress: a technology tag, a front page fingerprint, a `wp-login.php` login form, a crawled `/wp-content/` URL, a page title or label, the web archive's memory of the host, or an earlier probe. A cheap read-only probe (`wordpress-detect`: `/`, `/wp-login.php`, `/wp-json/`, and `/readme.html` once positive), run by a Sentinel as an `http_probe` task (this server asks the site nothing; with no Sentinel able to take it the sites stay due and are never read as not WordPress), confirms it with browser-like request headers, follows apex and `www` redirects inside the host's group, reads a signature in the headers or the body, and is also run on every name that shares a candidate's address and on other web hosts up to `CVENGINE_WP_PROBE_MAX_HOSTS` (default 100). WPScan then runs on every candidate and every grouped name that probes positive, positive probes first.

Every candidate ends in a recorded state, shown on the host page and counted in `get_system_status` (`wordpress`: hosts, scanned, never scanned, with the reasons): `scanned` (when, findings, whether vulnerability data was checked, next scan), `detected` (not scanned yet), `candidate`, `blocked` (the edge challenged the scanner), `failed` (with the reason; retried at the next scan), `waiting` (over the per-scan limit), `unavailable` (WPScan not installed), `unreachable` (the site did not answer the scan; asked again at the next scan), `redirected` (the site sends visitors to another site; a name that is another target of the project is scanned in the same run, and the redirect is asked again after six hours, never held for the week a scanned site rests), `not_scannable` (WordPress hosted on wordpress.com, which WPScan does not scan; looked at again after a day) or `not_wordpress`. A site that did not answer, but that the WordPress probe read within the last day, is `failed` and retried, not a quiet skip; when two or more sites of a scan were attempted and every one read as down, the stage stays failed and names the Sentinel, because its own DNS or route out may be broken. When an edge answers with a challenge (`cf-mitigated`, "Just a moment", an Akamai, Sucuri or Imperva block page, or a 202, 403, 429 or 503 with no origin signature), cvENGINE does not push against it (a plain 429 or 503 is asked again once), records that the edge challenged the scanner, and tells the owner to allow the scanner's address or user agent in the WAF or bot rules. It never tries to solve a challenge or get past a WAF.

The WordPress scan runs on a Sentinel only (task kind `wpscan`, never on this server, whatever `CVENGINE_LOCAL_FALLBACK` says). Its quick pass runs in the scan: the core, the plugins and themes the pages reference, config backups, database exports and author ids, with passive plugin and theme detection, a random user agent and a throttle. The thorough pass (task kind `wpscan_thorough`, on its own `wpscan_queue`, also on a Sentinel only) then asks each scanned host for every plugin slug the scanner knows (mixed detection with timthumbs), one site at a time and one pass per project, for as long as it needs (`CVENGINE_WPSCAN_THOROUGH_TIMEOUT`, 12 hours; a partial report is written before the limit). A site that finished is not asked again for 30 days (`CVENGINE_TTL_WPSCAN_THOROUGH`, 24 hours after a partial one). It never blocks the scan, stops while scanning is paused and resumes, and shows `pending`, `running`, `done`, `partial`, `blocked` or `failed` on the host page and in `get_system_status`. With no scanner able to take either kind the sites wait and stay due: a thorough site stays `pending`, nothing is recorded as done. A scan that could not finish still keeps what it read. The scan exits 4 with `NotWordPress` only when it says so; a positive probe that the scan could not confirm is `failed` ("the scan could not see WordPress, the probe did"), because a WAF may serve it a decoy page. Plugin and theme versions need no API token. The stage sends at most 20 sites per scan, and the whole stage has a one hour budget (`CVENGINE_WPSCAN_MAX_SITES`, `CVENGINE_WPSCAN_STAGE_SECONDS`); a candidate beyond either limit is recorded as `waiting` and goes first next time. When the token's daily budget (25 requests on the free plan) is spent, the remaining sites are still scanned without it and say "not checked: API token budget exhausted"; such a run is repeated after a day, a clean run after a week (`CVENGINE_TTL_WPSCAN`, `CVENGINE_TTL_WPSCAN_PARTIAL`). Its findings (core, plugin and theme vulnerabilities with CVE ids and the fixed version, exposed backups and database exports, usernames, XML-RPC, outdated components) are normal findings with remediation text. The core, every plugin and every theme with a version also become sightings: a CVE for a plugin matches only when the plugin's slug or title (read from its own readme) equals the advisory's product or package name and its version is inside a bounded range (`wp-plugin` matches).

### When discovery finds no web pages

A standard or deep discovery turns each host into a URL with bbot's `http` module. If a discovery finds five or more hosts and bbot reports no `URL` and no `HTTP_RESPONSE` event at all, the activity feed says so ("found N hosts but bbot reported no web page for any of them"), and the discovery records no endpoint, HTTP status or page title. Screenshots and the route checks make their own requests, so they are not affected; what is lost is only what bbot would have recorded. The cause is inside bbot's own run, which happens on a Sentinel, so the evidence is in its scan directory there. In the built-in `scanner` container (`docker compose exec scanner bash`; for an external Sentinel, its own container):

```
ls -t ~/.bbot/scans | head -3                      # the newest scan directories; the activity line names the one to read
S=~/.bbot/scans/<that name>
grep -iE 'hard-failed|soft-failed|blasthttp|setup' $S/scan.log | head -40   # did the http module start? cvENGINE only reports soft failures
ls $S; grep -c '"type": *"URL"' $S/output.json; grep -c '"type": *"HTTP_RESPONSE"' $S/output.json
bbot -t www.<the target> -m http -y --json 2>&1 | grep -E '"type": *"(URL|HTTP_RESPONSE)"|hard-failed|rror' | head   # the web module by hand on one host
/opt/bbot-venv/bin/python -c "import blasthttp; print(blasthttp.__file__)"   # the native HTTP engine the module uses
curl -sI https://www.<the target> | head -3; env | grep -i proxy; dpkg --print-architecture   # can the scanner reach the web, is a proxy in the way, which build
```

The same questions in the app: **Settings, Proxy** (a proxy that is down makes every web request of the built-in scanner's bbot fail), the activity feed around the scan ("ran out of memory; retrying as passive" means the web module never ran, and `docker compose logs scanner | grep -i 'out of memory'` on the host shows the same for the built-in scanner), and the discovery mode of the target (passive never visits a host).

### Web screenshots

The only screenshots cvENGINE used to take were a side effect of a full bbot discovery, so a host that was rescanned, found by certificate transparency, retested or only ever assessed never got one, and a rescan could hide the one it had. A real browser now takes them, in a stage of its own, and the pictures are kept by host, port and scheme, not on a scan's row.

- **Which pages.** For every host, each open TCP port nmap or naabu identified as HTTP or HTTPS, or that is a well-known web port (80, 443, 3000, 8000, 8008, 8080, 8081, 8443, 8888, 9443), and the page the host's own URL names: at most six per host, HTTPS on 443 first, then 80, then the rest by number. The page is asked for by its **name** (so virtual hosts and SNI are right), follows redirects and records where it ended up. A host behind a CDN is photographed on 80 and 443 only, not on the edge's other ports. A picture shown twice (80 redirecting to 443) is listed once.
- **When.** The **Web screenshots** stage queues the pages after nmap (up to 50 per scan, `CVENGINE_SCREENSHOT_MAX_PER_SCAN`). The **Take screenshot** button on the host page (`POST projects/{slug}/hosts/{id}/screenshot`, `screenshot_host`) queues all of a host's pages now, whatever their age, and for a host nothing is known about tries 443 and 80. An hourly backfill (`screenshot_backfill`, minute 41) queues hosts that have no picture, then pictures older than 72 hours (`CVENGINE_SCREENSHOT_TTL_HOURS`) and failures older than 24 hours (`CVENGINE_SCREENSHOT_RETRY_HOURS`), at most 20 per project and 100 overall per run, taking the projects in turn so one big project cannot starve the others. It does nothing while scanning is paused or an update drains, for a bug bounty project that has not confirmed automated testing, or without the browser.
- **One drain, a Sentinel's browser.** Planning a page only writes a `HostScreenshot` row with outcome `queued`. One task (`drain_screenshots`, on its own `screenshot_queue`, consumed by the classic worker) takes the queued rows, a person's requests first and then the oldest, and hands them to Sentinels in tasks of at most six pages as the `web_screenshot` kind (contract version 3). **The server runs no browser**: the kind is `NEVER_LOCAL`, so whatever `CVENGINE_LOCAL_FALLBACK` says, with no Sentinel able to take it the pages stay queued (the Take screenshot button and the host page say "Waiting for a scanner") until one can. A second drain while one runs returns at once and the running one picks up what was queued meanwhile. On the Sentinel a child process (`client/shot_child.py`) runs one Chromium and takes one page at a time, each in a fresh browser context (no cookies or storage, downloads refused, no permission granted, service workers blocked, dialogs and pop-ups dismissed, HTTPS errors ignored on purpose, 1280 by 800), 8 to 60 seconds per page (`CVENGINE_SCREENSHOT_TIMEOUT`, default 20). The child runs as the image's unprivileged user with a private working directory and none of the Sentinel's environment.
- **What is judged where.** The server decides the pages (name, scheme, port) and the **scope policy** each task carries (`probe_scope.for_screenshots`: the listed hosts, the organization's exclusions and archived names, the address rules; for a project that works no bug bounty program `open_web` is true, so a page's own fonts, scripts and redirects may reach any public host that is not excluded; for a bug bounty project only the listed hosts are reachable, so a third-party asset outside the program's scope is not loaded and a page can look unstyled). The bug bounty gate, the exclusion check and the in-scope check are repeated on the server just before the task is dispatched. The Sentinel enforces the policy on every connection.
- **Every address is vetted, on every hop, by the Sentinel.** The browser can connect nowhere itself: all its traffic, loopback included, goes to a loopback proxy in the Sentinel client (`client/shotproxy.py`, authenticated by a per-task secret, one connection per request). For each connection the proxy asks the page's guard (`client/shot.py`): the task's scope policy for the name, this Sentinel's own address floor and the policy's address rules for every address the name resolves to (a name with one internal address is refused), and this installation's own services (the compose service names and the addresses they resolve to), then connects **to the address it vetted**, through the Sentinel's probe proxy when one is set and never directly instead of it. So a redirect to `127.0.0.1`, a cloud metadata address or an excluded host never leaves the proxy, whatever the hop and however the DNS answer changes in between. A refused plain HTTP request is closed without an answer, so the browser never draws a page of ours. The Sentinel records what it touched and what it refused in the result (`touched`, `refused`, `dropped_requests`). Each page's last attempt keeps the reason: `blocked: redirects to X, which is not visited: ...`.
- **What comes back is not trusted.** A Sentinel answers each page with an outcome, a reason, the final URL, status and title, and the picture as base64. The server never uses a name a Sentinel reports (it names every file itself, as a new file with `O_EXCL | O_NOFOLLOW`), drops any page id the task did not name, and checks every picture before opening it: base64, at most the task's byte cap (2 MiB), the PNG signature, a good `IHDR` checksum, sides of at most 4096 pixels and the closing `IEND` chunk (`agentapi/web_screenshot_results.py`). A picture that fails becomes an error for that page; a flat single-color picture is `blank`. The Sentinel brings a picture under the cap before it sends it (a smaller PNG of the same page); the server refuses one that is still over (`The picture is larger than the size allowed`).
- **What is kept.** `HostScreenshot` is one row per project, host, scheme and port: the picture and a 320-pixel thumbnail (`screenshots/<project id>/<host>/<scheme>-<port>-<time>.png`), its hash, the final URL, the HTTP status, the title, when it was taken and the outcome of the last attempt with a plain reason (`queued`, `ok`, `blank`, `timeout`, `unreachable`, `tls_error`, `blocked`, `nla_required`, `unavailable`, `error`). A failed attempt keeps the earlier picture. One earlier picture is kept for comparison and older ones are deleted; a picture over 2 MB is never stored (`CVENGINE_SCREENSHOT_MAX_BYTES`; the Sentinel reduces it first); a project may hold 500 MB (`CVENGINE_SCREENSHOT_PROJECT_MB`: the comparison copies go first, then new pictures are refused with that reason). A host with no responding web port gets no row, a port that stopped being a web page loses its failed row, and deleting or moving a host takes its pictures with it.
- **Served and shown.** Pictures are served by the authenticated view (`/cve/<project>/hosts/<id>/screenshot/`), which finds the row by the project and the host's name and never by a path the caller names; the files are not reachable under `/media/` by anyone but an App Admin. The host page shows each captured page with its final URL, status and title, the real reason for each page that has none, and the **Take screenshot** button; the Gallery shows the best picture of each host. Where the browser has no picture of a host, the discovery screenshot of the newest row of the same name that has one is shown instead, so a rescan no longer hides it. A picture has alt text: "Screenshot of https://host:443 (final URL), captured date".
- **RDP.** `rdp_shot` is unchanged (a server that accepts a connection without NLA is captured and read by the AI). A server nmap showed insists on NLA now has a row with the outcome `nla_required`, shown on the port as "RDP login screen: not captured, NLA is required". VNC and a capture from inside an internal network (a Sentinel kind) are not part of this.
- **Hardening and the risk that remains.** The browser's UDP is closed (`--force-webrtc-ip-handling-policy=disable_non_proxied_udp`, `--disable-quic`: WebRTC would otherwise send UDP straight from the browser, around the proxy, to any address a page names), it has one renderer with a heap ceiling, and the Sentinel measures the browser and **every process it started** (by parent pid) against `CVENGINE_SENTINEL_SHOT_MAX_RSS_MB` (1500): a page over it is stopped and recorded `too_big`. **Chromium's sandbox.** The browser runs with its own sandbox (`chromium_sandbox=True`; Playwright's default is without it) as the Sentinel image's unprivileged user: each renderer runs in a user namespace and a PID namespace of its own, under Chromium's own seccomp filter, with no file system and no network of its own. A user namespace is what Docker's default seccomp profile refuses, so the Sentinel container runs with Playwright's seccomp profile (`config/seccomp/playwright-chromium.json`: Docker's default plus `clone`, `setns` and `unshare`, vendored unchanged from Playwright v1.64.1): the `scanner` service here, and the `sentinel` service of the Sentinel repository's compose file. No server container carries it any more (`web`, `celery` and `celery-beat` keep Docker's default). It is checked, never assumed: the Sentinel starts the browser once at every start (one line in its log), and every task checks again before its first page (a renderer must exist in its own user and PID namespace under more seccomp filters than the browser, and no process may carry `--no-sandbox`). **It fails closed:** when the sandbox cannot start (a container without the profile, a host kernel or AppArmor rule without unprivileged user namespaces, the browser running as root) no page is opened, that Sentinel takes no picture, and the result says why (`sandbox.engaged` false): the host page, `get_system_status` (a problem, `screenshots.sandbox.state` `failed`) and the activity feed show the reason, and the pages stay queued for another scanner. There is no setting that turns the sandbox off. `CVENGINE_SCREENSHOTS=0` turns screenshots off altogether. **What is accepted:** the sandbox takes the renderer off the network and the file system, but the browser process and its network service still run as the Sentinel's unprivileged user with the container's ordinary network access, so an exploit chain that escapes the sandbox reaches whatever that user can reach from the Sentinel container (its state volume holds the Sentinel's token: the child gets none of the Sentinel's environment, but the file is readable by the same user). Moving the screenshots to the Sentinel takes this risk off the server and its database, broker and secrets, and puts it on the machine the operator chose to run scans from. The seccomp profile lets every process in that container create user namespaces, which widens the kernel interface it can reach: that is the trade Playwright documents for running Chromium sandboxed in Docker. The Chromium build changes only when Playwright is bumped and the Sentinel image is rebuilt (the Sentinel repository pins it and checks the version it launches; there is no checksum of Playwright's download to pin).
- **Status.** `get_system_status` shows, per project, the hosts with a web page, the hosts with a picture, what is queued, what failed, what was blocked and the last capture error, and for administrators whether screenshots are on, how many pages are queued and what the last Sentinel result said of Chromium's sandbox (`sandbox`: `state` engaged, failed, unchecked or off, with the reason and when).
- **AppArmor.** On a host whose AppArmor refuses user namespaces (Ubuntu 24.04 and later, recent Debian and Kali) the browser cannot start its sandbox even with the seccomp profile. The scanner then says so in plain words (*the host's AppArmor profile blocks Chromium's sandbox*), stops declaring `web_screenshot` so the pages stay queued, and tries again every ten minutes; the fix is the AppArmor profile in `config/apparmor/cvengine-scanner` ([DEPLOYMENT.md](DEPLOYMENT.md#screenshots-and-apparmor)).
- **If it is switched off or missing.** `CVENGINE_SCREENSHOTS=0` turns the stage, the button and the backfill off. With no Sentinel that declares `web_screenshot` (an image without the browser, a Sentinel on an older contract, the kind switched off in its settings, or none online), queued pages wait and the host page says "Waiting for a scanner"; nothing is photographed from the server. A Sentinel container without its seccomp profile (one started from an old compose file, or by hand) cannot start Chromium's sandbox: it takes no picture and says why until it is recreated with the profile (`docker compose up -d`), see Chromium's sandbox above.

### SSH inspection

What runs. After the port stage, every open TCP port that is 22 or whose detected service, product or banner is SSH is read by a Sentinel (task kind `ssh_probe`, up to 25 address and port pairs per task, `CVENGINE_SSH_PROBE_MAX_ENDPOINTS` per scan; `CVENGINE_SSH_PROBE=0` turns it off). The Sentinel runs one command, `sshamble scan` with the single check `badkeys-blocklist` ([sshamble](https://github.com/runZeroInc/sshamble) by runZero, BSD-2-Clause; the client refuses every other command line). That is a **host key check**: the tool connects, reads the server's own handshake (banner and software version, host key algorithms and sizes, the authentication methods it offers, the key exchange, cipher and MAC lists) and compares the host keys with the [badkeys](https://badkeys.info) blocklist, which the Sentinel refreshes daily (`CVENGINE_BADKEYS_REFRESH=0` stops that on an air-gapped Sentinel; the check then reads "not checked", never "clean"). **Nothing logs in.** No password, key or user name is ever sent: the forbidden flags (users, passwords, private keys, interactive sessions, client versions) are not in the one fixed command line. The server installs no SSH tool and opens no connection itself.

What is stored. The banner, algorithms and offered methods are inventory facts (`ProbeObservation` rows of kind `ssh`), not findings: weak algorithms and password authentication being on are already reported by the template checks. A host key on the blocklist is one finding per host name and endpoint, severity high, set by the server (a Sentinel's own severity is ignored), and a later complete inspection that finds the key off the list closes it. An endpoint the Sentinel could not read, or a check that could not run, is never clean: it is stored as unverified and the endpoint stays due. An endpoint is inspected once a week (`CVENGINE_TTL_SSH_PROBE`, 168 hours), sooner when its banner or version changed, and a day later after an incomplete inspection.

### Java runtime

Why. A CVE in the JDK or JRE itself (an unauthenticated RCE in OpenJDK 17.0.6 and every later 17.x, say) names the runtime, not the Tomcat, Jenkins or Confluence on top of it, and cvENGINE almost never knew which Java a host runs: such a CVE matched nothing. Almost no install runs the host inventory reporter, so this reads the runtime from outside and never depends on an inventory (`cveFeed/java_runtime.py`, parsers in the scanner library's `cvengine_scanner/java.py`).

What is read, and how far it is trusted. Each reading is one `JavaRuntime` row of the host: the version (one spelling: `8u392`, `17.0.9`, `21.0.2`, or the line alone, `17`), the major line, the vendor (Oracle, Eclipse Temurin, Azul, Amazon Corretto, Red Hat, Microsoft, IBM Semeru, BellSoft Liberica, SAP Machine, Debian, Ubuntu, OpenJDK, or unknown), the source, the confidence, the port or URL, the evidence (what the host said, clipped, shown as text) and when it was first and last seen.

| Source | Confidence | Where it runs | What it reads |
| --- | --- | --- | --- |
| `jdwp` | exact | the fingerprint pass (nmap's `jdwp-version`, a version script `-sV` runs by itself at intensity 7 on a port that hung up on its first probe), and the Sentinel kind `java_runtime` on an open debug port (5005 to 5010, 8000, 8787, 9009) nmap left unidentified | the 14-byte `JDWP-Handshake`, then the one read-only command `VirtualMachine.Version`; no other JDWP command exists in the code. The fingerprint pass now scans 5005 to 5010, 8787 and 9009 too |
| `actuator` | exact | `java_runtime` (Sentinel), only on a host identified as Spring | `/actuator/env/java.version`, `/actuator/info` (`java`), `/actuator/metrics/jvm.info` (its `version`, `vendor`, `runtime` tags), Boot 1's `/env/java.version`; never the whole environment |
| `jolokia` | exact | `java_runtime`, only on a host identified as Spring, Jolokia, Hawtio, ActiveMQ or Karaf | `/jolokia/version`, and only when that is Jolokia's own answer the Runtime MXBean's `VmVersion` and `VmVendor` (a Java 8 HotSpot's `25.392-b08` is 8u392) |
| `status_page` | exact | `java_runtime`, only on a host identified as that product | Solr `/solr/admin/info/system?wt=json`, GeoServer `/geoserver/rest/about/status.json` (its `jvm` and `system-properties` modules), Druid `/status/properties` (the `java.*` keys only), Elasticsearch and OpenSearch `/_nodes/jvm` (filtered to the version fields) |

A web check is asked only of a host already identified as its product (a technology or a port product); a JDWP port only when nmap named it jdwp or left an open debug port unnamed. An answer is read only when it is the exact JSON shape its reader expects (a login page, a catch-all page or an error never gives a reading), and only its Java version and vendor fields are read: an actuator `env` or Druid's properties carry secrets, and nothing else of them leaves the Sentinel. Every request is a bounded GET (pinned vetted address, redirects only inside the host's group and the scope policy, no cookie, no credential), one host's requests 0.5 s apart.

Gates and schedule. The kind runs on a Sentinel only (`sentinel_dispatch.NEVER_LOCAL`; with none it waits). Every host passes the organization's exclusions (fail closed), archived hosts, a bug bounty program's scope and, on the work planner's path, its automated-testing confirmation; every address the address rules; the dispatcher applies the do-not-scan list. It is a stage of the host pipeline after the version probes (`java_runtime`), and the work planner keeps it going on hosts already in the inventory (check `java-runtime`): a host is read once a week (`CVENGINE_TTL_JAVA_RUNTIME`), again after a day when a read failed, at most 60 hosts per scan, 50 web hosts and 25 debug ports per task. After an update the upgrade backfill `backfill_java_runtimes` stores what the existing hosts already give away and correlates them, and the planner finds the `java-runtime` check due on every Java host that never had it, so the reads catch up within its normal budget. `CVENGINE_JAVA_RUNTIME=0` turns the reads off.

An open JDWP port is also a finding: **Java debug port (JDWP) open to the network**, critical, one per host name and endpoint (`source` `java-runtime`, template `jdwp-exposed`). JDWP has no authentication, so anyone who reaches it can run code in that JVM. A later complete read where something else answers closes it.

Correlation. A CVE whose affected products name the Java runtime (`java_runtime.is_runtime_item`: `oracle:jdk`, `oracle:jre`, `oracle:java_se`, Oracle's "Java SE JDK and JRE", OpenJDK, Eclipse Temurin, Azul Zulu, Amazon Corretto, the Red Hat and Microsoft builds of OpenJDK, IBM Semeru, Liberica, SapMachine, GraalVM for JDK, and a distribution's runtime package such as `java-17-openjdk` or `openjdk-17`) is tested against the host's readings, one match per host and CVE (source `java`, product "Java runtime"):

- An exact reading inside the range is a version match like any banner's: version only, so needs validation at most and smoke at most, and not "version proven" (`match_policy` decides that, and does not count a runtime reading). A Red Hat, Debian or Ubuntu build of OpenJDK is judged by that distribution's tracker (`java-17-openjdk`, `openjdk-17`), as any distribution package: a Red Hat fix the installed build cannot be compared with is `backport`. An exact reading outside every range is no match.
- With no exact reading, a host where Java is clear (an inference, a stated line, a Java product: Tomcat, Jetty, Jenkins, the Atlassian products, Spring, WebLogic, WildFly, GlassFish ...) is a **Java runtime of unknown version** candidate when the CVE affects a line the host can run: `evidence.java_unknown`, which `match_policy.is_version_unknown` reads like an advisory without a range. It needs validation, it is ice and the lowest priority, it never fires, and no AI triage or automatic validation is spent on it. An inferred reading inside the range raises its confidence (0.5) and says so; one outside it lowers it (0.4) and says it is affected only if the bundled runtime was replaced; a line the host states, or a Jenkins minimum, that excludes every affected line removes it. The explanation leads with what an outside check could not see, then a validate plan the host owner runs (`match_explain`, `confirm_guide`): `pgrep -a java`, `jcmd <PID> VM.version`, `readlink -f /proc/<PID>/exe` and that binary's `-version`, and the JDK's `release` file. Its trade-off: every Java host is a candidate for every runtime CVE until a version is read, which adds review-only rows at the bottom of the needs-validation list; they add nothing to a host's heat or score.
- A host where nothing says Java is never matched.

A runtime CVE is correlated the moment it is ingested, whatever its heat (`tasks.auto_fire_new_cves`), and a CVE update that changes its ranges is correlated again as any CVE is: no manual step. Search hosts by Java with `tech:java` (every host that runs Java: a product that runs on a JVM, from the same list as above, or a runtime read; `java:any` is the same search) and `tech:java@unknown` (one whose runtime version nothing has read: the hosts to ask, or to run the host inventory reporter on; also `java:unknown`), or by the runtime read with `java:` (a line, release, vendor or source: `java:17`, `java:17.0.9`, `java:8u392`, `java:temurin`, `java:jdwp`). `tech:` asks the same of any product ([SEARCH.md](SEARCH.md#what-a-host-runs)); the host payload carries `java_runtimes` (REST and MCP) and the host page lists them under its technologies.

Not read: a TLS fingerprint of Java's own TLS stack (JSSE). No JARM is collected today, and the published JARM values of JDK 11, 17 and 21 defaults could not be sourced reliably enough to tell lines apart, so nothing is inferred from TLS.

### Version sources

Why. cvENGINE missed CVEs in components it never put a version on, although many products say their exact version to anyone who asks: Grafana's `/api/health`, Jira's `serverInfo`, Vault's health check, the Docker Engine API's `/version`, a Prometheus exporter's `/metrics`. What is asked, and how far it is trusted. An entry is asked only of a host already identified as its product (a technology or a port product its `leads` name: asked on that port, else on the host's first web base) or on a port of its own (Docker's 2375 and 2376, etcd's 2379, Nomad's 4646, Consul's 8500, Vault's 8200, Kubernetes' 6443, Envoy's 9901, a Prometheus exporter's 9090 to 9100, 9115 and RabbitMQ's 15692) whose service the port scan left generic: never every path on every host, at most six entries a host. An answer is read only when it has the exact shape its reader expects (the JSON fields, their types, a version that looks like one), so a login page, a catch-all page, an error or another product's answer never gives a reading. An entry with a thin shape (Gitea's one field, SonarQube's plain text, a metrics page) also asks a control path that cannot exist next to it (`.../cvengine-control-<12 hex>`): when the same reader reads that too, the host answers every path that way and nothing is believed (`cvengine_scanner.soft404` compares whole bodies, which never leave the Sentinel here, so the reader is the comparison). A reading is `exact` (the software states its own version), `inferred` (a line or a presence that follows from what it states) or `weak` (a presence that may be something else), the Java runtime's words.

What the Sentinel returns. Never a body: only the dotted JSON fields a request names (each a scalar clipped to 200 characters, or a container's type and size), 1,024 characters of text from the first occurrence of a literal, the `*_info` samples with only their version-like labels (`version`, `vendor`, `runtime`, `revision`, `goversion`, `implementation`, `*_version`; no value, no other sample, no other label), and the response headers the request names (never a cookie or an authorization header). An actuator `env`, Consul's `DebugConfig` or Nomad's agent configuration carry secrets: only their version fields leave the Sentinel. The server cleans every answer again (`agentapi/probe_results.clean_version_read`), keeps only the entries and paths it asked (`bind`), and stores no answer, only the readings.

Where readings go. `ProbeObservation` rows of the host (probe `vsrc:<entry>`, or `vsrc:passive` for the stored headers; `evidence.confidence`, `line_only`, `component`, what the host said):

- A product (kind `version`) is also a technology of the host (`Grafana:10.2.3`), so correlation matches it like any product it knows (name, aliases, a Red Hat host's tracker), version only: a version read this way never proves a version on its own (`match_policy.version_read_from_component`), so it needs validation at most and stays under the triage ceilings and the heat cap like any banner.
- A language runtime (kind `runtime`: Python, Go, Node.js, PHP, Ruby, .NET Framework, Erlang/OTP) is never a technology. It is matched against the CVEs whose own record names the runtime by vendor and product (`version_catalogue.RUNTIMES`: `python:python`, the PSF's `CPython`, `golang:go` and every package of the Go CNA's "Go standard library" except the toolchain's `cmd/...`, `nodejs:node.js`, `php:php`, `ruby-lang:ruby`, Microsoft's `.net_framework`, Erlang's `OTP`), one match per host and CVE, source `runtime`, by the Java runtime's rules: an exact version inside a range is a version match (a distribution's build string, `PHP/8.1.2-1ubuntu2.14`, is judged by that distribution's tracker); a line, an inferred reading or a runtime clearly present with no version (Python under gunicorn, a Ruby WEBrick, the .NET line of `X-AspNet-Version`, an OTP line) is at most a **runtime of unknown version** candidate (`evidence.runtime_unknown`: needs validation, ice, never fire, no AI or validation spend) with the host owner's commands (`python3 -VV`, `go version <BINARY>`, `ruby -v`, the .NET Framework `Release` registry value, `erl`'s `otp_release`), and never `version_in_range` true; a weak presence matches nothing, and Go, PHP and Node.js are never version-unknown candidates (a Go binary's release is read or nothing is said; a PHP or Node.js site without its version says nothing about it). A CVE the host's technology, port or Java runtime already matched is not matched twice. A runtime CVE is correlated the moment it is ingested, whatever its heat.
- A `jvm_info` sample is a Java runtime reading (`JavaRuntime`, source `metrics`): the Java runtime keeps its own table and matcher ([Java runtime](#java-runtime)), with the same confidence words and the same unknown-version treatment.

Exposures. An entry with an exposure files a finding (source `version-source`, template `<entry>-exposed`, one per host name, entry and URL) when its answer has the entry's shape: **Docker Engine API open without authentication** (critical), **Nomad API answers anonymous requests** (critical, medium when ACLs are on), **etcd client API reachable without a client certificate** (high), **Envoy admin interface reachable without authentication** (high), **Kubernetes API server reachable** (low), **Prometheus metrics readable without authentication** (info), **Go expvar debug page readable without authentication** (low). A later complete read that finds no such answer closes it; a read that could not complete changes nothing. A template check's finding that already reports the same exposure on the host (Docker API, Prometheus metrics, expvar templates) is not filed twice.

Gates and schedule. The kind runs on a Sentinel only (`sentinel_dispatch.NEVER_LOCAL`; with none it waits). Every host passes the organization's exclusions (fail closed), archived hosts, a bug bounty program's scope and, on the work planner's path, its automated-testing confirmation; a host whose name points at an address a scanner may not use is left out; the dispatcher applies the do-not-scan list. It is a stage of the host pipeline after the Java runtime reads (`version_sources`), and the work planner keeps it going on hosts already in the inventory (check `version-sources`): a host is read once a week (`CVENGINE_TTL_VERSION_SOURCE`), again after a day when a read could not complete, at most 60 hosts per scan and 100 read entries per task, one host's requests 0.5 s apart. After an update the upgrade backfill `backfill_version_sources` stores what the existing hosts' stored headers and technologies state and correlates the hosts that gained a runtime, and the planner finds the `version-sources` check due on every host it applies to. `CVENGINE_VERSION_SOURCES=0` turns the reads off (the stored-header readings and the runtime correlation stay on).

Search hosts with `component:` (`component:grafana`, `component:docker@24`, `component:tomcat`, `component:junos@21.4`), `runtime:` (`runtime:python`, `runtime:go@1.21`, `runtime:dotnet`) and `vsource:` (`vsource:prometheus-metrics`, `vsource:header`, `vsource:snmp`, `vsource:bundled`, and for the readings of [data already received](#versions-already-received) `vsource:nmap`, `vsource:webserver`, `vsource:testssl`, `vsource:wpscan`, `vsource:db-probe`, `vsource:shodan-idb`, `vsource:runzero`, `vsource:reported`, or `vsource:recog` for [Recog's banner readings](#recog-banner-fingerprints)); the host payload carries `version_sources` (REST and MCP) and the host page lists them under its technologies.

### Versions already received

Why. **What a source skipped this scan found last time stays.** Hosts are stored once per scan. A source the service ledger says covered a host inside its window (the nuclei technology pass, the firewall fingerprint, the WordPress scan) is not run on it again, and the technologies its last run found are carried onto the new row (`cveFeed/tech_carry.py`) as a set difference: from the row of the scan that last ran that source on the host, every technology the new row lacks, less a product the new row already names at any version. A row another source already filled (bbot's `cloudflare`, `hsts`) still gets them, so the earlier pass's `WordPress:7.1.4` and its matches stay current. A name written in another case reuses the row of the same product and version (`cveFeed/tech_rows.py`: `Caddy` and `caddy`, `PHP:8.1.2` and `php:8.1.2` are one row).

**A version the network detection pass filled.** The version the pass adds to a port nmap named without one is also a first-party reading (`vsrc:nuclei`, `evidence.on_port`: the port is matched, so it is not a second technology), and a later port scan that names the same product without a version keeps the port's version while that reading is inside the pass's 7-day window; once the pass no longer reads it, the next port scan clears it. A product the pass names without a version on a port nmap read as another product is an identity reading (outcome `hidden`: shown, searched and a lead, never a technology). MariaDB's handshake prefix (`5.5.5-10.11.19`, `cpe:/a:mariadb:mariadb:5.5.5-10.11.19`) is taken off the stored version and CPEs, so the port reads as MariaDB 10.11.19.

**The freshness rule for third-party readings.** Passive data is older than our own scans and may describe a host as it was months ago. A third-party reading of a source that may match (runZero's: the customer's own active scanner; never Shodan InternetDB, which matches nothing, [below](#shodan-readings-are-leads)) is matched only while all three hold; otherwise it is shown (`matched` false once it is too old) and matched to nothing, so the next correlation closes a match it made:

1. it is at most 90 days old (`REPORTED_MAX_AGE_DAYS`: its source's own date, else when cvENGINE received it);
2. nothing first-party names the same product on the host: a technology, a port's product or CPE (a closed port counts: our scan saw the product and saw it go) or a first-party reading. **A first-party reading always wins**, whatever version it states and however recent the third-party one is, and a product our own scan saw without a version is not given the third-party version either (a service that stopped stating its version may have been upgraded);
3. when it names a port, our own scan of that port does not show it closed or answering with another product.

A hint (runZero's hardware firmware) is never matched, whatever its age.

A match it makes (runZero's only) is correlation source `tech` with `evidence.reported`, `reported_by`, `reported_at` (and `undated`), the CPE first (`_match_candidates` tries the CPE's product and vendor, then the name), its confidence at most 0.5 (`REPORTED_CONFIDENCE`), never a proven version, and it holds a new KEV match like any stale fingerprint (a reported reading is never counted as a fresh read). A match whose only basis is a reported reading is **ice** whatever the CVE's KEV listing, with the reason "the version was only reported by a third party", until a first-party read or a check confirms it (`threat.match_heat`, `match_policy.is_reported_only`); its "How it was found" and explanation name the provider ("reported by runZero"), never our own fingerprint. A reading belongs to the project of the host it was stored for: the discovery's target, or the project whose runZero sync wrote the address's block (each block now records its project; a block written before that counts only for a project with a runZero token of its own or its organization's), and correlation reads only the host's own project's readings.

**CPEs.** A first-party reading made from a CPE keeps it, and correlation matches the technology it made CPE first, as it matches a port by `Port.cpe` (`evidence.cpe` on the match). A runZero CPE is matched CPE first under the freshness rule; a Shodan one is never matched.

After an update the upgrade backfill `backfill_source_versions` re-reads what is still stored: every current host's ports and runZero blocks, the Shodan InternetDB CPEs the discovery feed kept (`DiscoveryEvent`; the CPE technology an earlier discovery stored on the host under its normalized name is taken off the current host row, and the reported reading replaces it) and the replies the database exposure findings kept. It then correlates the hosts that gained or lost a reading. testssl.sh banners and WordPress scan headers were never stored, so they are read from the next audit and scan.

#### Shodan readings are leads

Shodan's InternetDB is keyed by IP address and says nothing about which host answers there. Behind Cloudflare it returned WordPress 7.0.9 and Redis for a host that runs neither, and cvENGINE once matched a KEV CVE from it. The rule, in `cveFeed/source_versions.py`: *we do not trust Shodan findings, they guide our own tooling and checks.*

- **No match.** `collect_reported` and `in_use` skip every `vsrc:shodan-idb` row. No CVE match, no technology, no product count (`tech:`, `component:`, `os:`, the threat digest and the Overview threat cards). The readings stay stored and are found with `vsource:shodan-idb`.
- **A lead queues our own check**, with the mechanisms that already exist: WordPress is asked first by the WordPress probe (`wpscan_scan.detect` puts a host Shodan named WordPress on at the front of the probe, after the hosts with a sign of our own; the probe's answer decides, and a host is scanned only when the probe reads WordPress); any other product goes to `version_sources.host_products`, so the catalogue's version source reads (`version_read`) ask for it on its port or web base, from the host pipeline and from the work planner (`check_coverage.plan_versions`). Nothing new scans: only Sentinels send anything.
- **A first-party negative beats a lead.** The WordPress probe's `not_wordpress` (observation outcome `absent`), a closed port or another product on the lead's port rules it out: no more checks are queued from it, and the host page says "Reported by Shodan, ruled out by our probe". A product our own scan names is "also found by our own scan".
- **A shared edge address is not the host.** When the host's addresses are a CDN or shared platform (a provider's published range such as Cloudflare's, the CDN flag, the CNAME, name or Server header: `hosting`), the host page says "Shodan data for a shared edge address (Cloudflare), probably another site" and no check is queued from it.
- **The host page** (and `shodan_leads` in the host payload) lists the readings under "Reported by Shodan (unverified lead)", never under the products seen on the host.
- **Cleanup.** An open CVE match whose only basis is a Shodan reading (`evidence.reported` with `reported_by` `shodan_idb`, or a `reading_id` of a `vsrc:shodan-idb` row) is closed automatically as a **false positive** with the note "Closed automatically: based only on Shodan InternetDB data for the host's address, which cvENGINE uses as a lead, not as a finding; our own checks did not confirm WordPress 7.0.9 on this host.", on the next correlation of the host and once for every host by the upgrade backfill `cleanup_shodan_matches` (`python3 manage.py cleanup_shodan_matches [--apply]`; idempotent, in batches). A match a person worked, or one with a template hit, the distribution's tracker or a validation hit, is left alone.

The upgrade backfill `backfill_shodan_cpes` stores every Shodan CPE the discovery feed kept as a reading under its "vendor product" label, relabels the readings stored before, turns a technology stored as a raw CPE (`cpe:/o:canonical:ubuntu_linux`) or under a CPE's bare product name (`http server`) into the reading it is and removes it, and correlates the hosts that moved. `backfill_technology_names` folds the technology rows that differ only in case onto one, takes MariaDB's prefix off the stored port versions and correlates those hosts.

### Where a technology came from

Every pass that links a technology to a host writes the link through one function (`cveFeed/tech_links.py`) with a `source` from one vocabulary: `nuclei` (a technology template; `cpe` is the CPE its metadata states), `nuclei:derived` (a template that names products by matcher; `cpe` derived from the name), `vsrc:panel` (a panel template's product without a version), `bbot` (discovery), `probe` (the version and identity probes, the virtual host sweep, the subdirectory applications, the WordPress probe), `vsrc` (a version source of the catalogue), `route` (the web route check's front-page fingerprint), `waf` (the WAF fingerprint) and `wpscan` (the WordPress scan). runZero links no technology (its readings are third-party readings). A reading of a technology the host already has refreshes the link's `observed_at`; a link stored before sources were recorded takes the source of the first pass that reads it again, and keeps it empty until then. A CPE a source states is written on the link even when another source linked the technology first; a derived one only fills a link without a CPE or replaces a derived one; a reading without a CPE never clears one. A link carried onto a later scan's row (the light pass's reuse, a copied discovery, folded spellings) keeps its source, CPE and time. The host record shows them (`technology_details`: `source`, `cpe`, `cpe_derived`, `observed_at`, [AGENT-API.md](AGENT-API.md)).

The upgrade backfill `backfill_template_identities` reads the other stored template findings (`cveFeed/template_identity.py`, 500 a pass, resumable): a technology template's finding gives its template's CPE to the technology of the same name on the host's current row, and a panel finding without a version becomes an identity reading and a technology with no version; the hosts that changed are correlated again.

The upgrade backfill `backfill_panel_versions` reads the panel findings already stored the same way: every info-level nuclei finding tagged `panel` with extracted values, newest first (one per host, template and port), by its template id, name and tags (old findings kept no template metadata, so the installed template of that id gives the vendor and product). The readings go on the host's current row, under the same never-a-downgrade rule, and the hosts that gained or changed one are correlated again.

#### Version category scripts

nmap's version scan runs the scripts of its `version` category by itself (they cannot be selected, and they are never among the reviewed scripts); since 1.4 a Sentinel sends what they printed as the port's `version_scripts` (`Port.extra['version_scripts']`). Most of them only fill the port row nmap already writes, so only the ones whose output states a product and its version in a fixed form are read (`source_versions.VERSION_SCRIPT_READERS`, the forms each script's own documentation in nmap's `scripts/` prints): `vmware-version` (`Server version: VMware ESXi 7.0.3`, `Build: 21930508`), `amqp-info` (`product: RabbitMQ`, `version: 2.4.0`, top-level lines only), `docker-version` (`Version: 1.11.2`) and `wdb-version` (`VxWorks version: VxWorks5.4.2`, the VxWorks release behind the debug agent the port row names). `rpcinfo`'s program table, `hnap-info`'s device page, `xmpp-info`'s capabilities and the others state no version of their own and are only searched (`banner:`, `tech:`).

**VMware ESXi by build.** VMware's advisories name each ESXi fix by its patch release and build (`ESXi70U3s-24585291` is build 24585291 of 7.0 Update 3), and nmap's port row says only `VMware ESXi SOAP API 7.0.3`. The `vmware-version` reading carries the build in its version (`VMware ESXi:7.0.3-21930508`; a vCenter reading keeps its release, its advisories name update letters, and the build in its evidence), and correlation reads an ESXi record's ranges by build (`correlation.esxi_ranges`, applied when the CVEs are read, as NetScaler's builds are): each fix covers its own update from that update's first build to the fix's build (8.0 Update 2 patched by `ESXi80U2d-24585300` is not affected though it is below Update 3's fix), the updates below the lowest fix are affected whole, and a release read without its build is unknown inside its update, never "not affected". A record cve.now passed on as bare versions (`7.0 before ESXi70U1c-17325551`, CVE-2021-21974) is read the same way when every line has this form; a 6.x patch id (`ESXi670-202102401-SG`) names no build, so a version of that line is unknown and a version of another line is outside it.

After an update the upgrade backfill `backfill_version_scripts` reads the version category script output the stored ports already keep and the firmware hint of the stored runZero blocks (their services come with the next sync), then correlates the hosts that moved and every host whose port or technology names VMware ESXi.

### Recog banner fingerprints

Why. A banner nmap stored but could not name (`220 ProFTPD 1.3.5e Server (Debian)` on a port nmap called `ftp` with no product), or named without a version, still states the product and its release. [Rapid7 Recog](https://github.com/rapid7/recog) (BSD-2-Clause) keeps fingerprint databases that map such banners to a product, vendor, version and CPE. `cveFeed/recog.py` runs them on the server over the banners already stored; nothing is sent. The databases are vendored unchanged in `web/cveFeed/data/recog/` (only the eleven it reads, with Recog's `LICENSE` and `COPYING`), pinned to one upstream commit in `manifest.json` with the SHA-256 of each file, and refreshed by hand with `python3 scripts/update_recog.py <commit>`. CI never reaches the network.

| Recog database (`matches`) | Stored text it reads |
| --- | --- |
| `http_header.server` (`http_servers.xml`) | `Subdomain.webserver`, a port's `http-server-header` lines and the `Server` line of its `http-headers` output, a live route's `Server` header (`RouteAuth.evidence`) |
| `http_header.cookie` (`http_cookies.xml`) | each `Set-Cookie` line of `http-headers`; a cookie a live route set, by name (the route probe keeps no value) |
| `ssh.banner` | `Port.banner` starting `SSH-2.0-`, without that prefix |
| `smtp.banner`, `ftp.banner` | `Port.banner` starting `220`, without the code; SMTP or FTP by the port's service name, number or the greeting's words |
| `pop3.banner`, `imap4.banner` | `Port.banner` starting `+OK` or `* OK` (and a leading `[CAPABILITY ...]`), without it |
| `telnet.banner` | `Port.banner` of a telnet port |
| `snmp.sys_description` | the UDP sweep's `snmp-sysdescr` output, without the uptime line |
| `mysql.banners` | `mysql-info`'s `Version:` |
| `ntp.banner` (Recog's `ntp.readvar`) | `ntp-info`'s lines, rebuilt in readvar's own `version="...", processor="...", system="..."` form |

Recog's x509 databases are not vendored: none of their fingerprints states a version (the appliance certificates they name are read from `data/network_identities.json`, below). Recog has no RDP database, and nothing stored holds a DNS `version.bind` answer.

How a pattern is read. Recog's patterns are Ruby regular expressions. `recog.translate` reads them the Ruby way in Python: `^` and `$` match at every line (`re.MULTILINE`), `REG_DOT_NEWLINE` and `REG_MULTILINE` are Ruby's `/m` (`re.DOTALL`), `REG_ICASE` is `re.IGNORECASE`, and `(?<name>`, `\h`, `\z`, `\Z`, `(?m)` and the POSIX bracket classes are rewritten. A fingerprint is loaded only when its pattern compiles, has no group repeated without bound around content that also repeats without bound with no literal each repetition must contain (`(.+)*`: the shape of catastrophic backtracking), and matches each of Recog's own `<example>` entries with the values the example states. The rest are skipped and counted (`recog.stats()`, printed by the backfill): at the pinned commit 1,976 of 1,978 load and 2 are refused as backtracking risks. A banner is clipped to 1,024 characters and NUL bytes are dropped before any pattern sees it. The databases are loaded once per process (about a quarter of a second); a banner no pattern matches costs about 2 ms. As in Recog, the first fingerprint of a database that matches is the answer.

What is stored. Each service (and service component) Recog names with a version is a `vsrc:recog` reading (`cveFeed.source_versions.recog_readings`): first-party, exact, a technology of the host (`ProFTPD:1.3.5e`), the CPE Recog gives (`service.cpe23`, its `{service.version}` filled in) kept so correlation matches it CPE first, as a port's `Port.cpe`. A product named only by generic words keeps its vendor (`Apache HTTPD`, `Microsoft IIS`). A protocol's version (`Apache-Coyote/1.1`) is no reading, as everywhere (`data/product_aliases.json` `protocol_versions`). An operating system (`os.*`) is a `hint`: shown and searched, never a technology and never matched, as an operating system is not matched by name. A network operating system whose CVE records use its own name is a product reading instead, as an SNMP sysDescr's Cisco IOS and runZero's network OS are: Cisco IOS, IOS XE, IOS XR, NX-OS, FortiOS, Junos OS, PAN-OS, SonicOS and RouterOS (`recog.NETWORK_OS`).

**Recog never overrides a first-party version.** A product a port row (its product, version or CPEs), another version reading of the host (`vsrc:nmap`, `vsrc:webserver`, `vsrc:passive`, `vsrc:snmp`, `vsrc:testssl`, a version source entry) or a technology already states with a version is left out, whatever version Recog reads: Recog only adds products the other readers did not read, or read without a version. The readings are derived like `vsrc:nmap`: refreshed with the host's other stored-data readings (`version_sources.refresh_host`, after them, so they are what it gives way to, and after a UDP sweep with the SNMP readings) and dropped when the banner no longer says it. `vsource:recog` finds them, and `tech:<product>` (with `@known` or a release) reads them like any version reading.

After an update the upgrade backfill `backfill_recog_readings` reads every current host's stored banners with Recog and correlates the hosts that gained or lost a reading.

**Identities: a product with no version.** Recog often names the product and nothing more (a `Server` header that hides its version), and a product without a version used to be dropped. A service, its component or a network operating system Recog names with no version is now an identity reading (`cveFeed/identity_readings.py`: a `version` row with outcome `hidden`, shown under `version_sources`, found by `tech:`, `component:` and `vsource:`, a lead for the version source reads and for correlation, never a technology and never a match), unless a port, another reading or a technology already names the product. Recog's `hw.*` fields (the device model and its version) are read too, as a hint: shown and searched, never matched. An operating system or a device named with no version adds nothing.

**An unidentified service's nmap fingerprint is read.** When nmap's probes name no service it keeps the raw replies as a fingerprint (`SF-Port80-TCP:V=...%r(GetRequest,16F,"HTTP/1\.0\x20301...")`), stored as the port's banner and never decoded. `cveFeed/servicefp.py` decodes it (the `SF:` wrapping undone, `\xNN` and the other escapes unescaped; a reply the banner's clip cut short is read as far as it goes) and keeps the text in `Port.extra['servicefp']`, which `banner:` and `tech:` search (`banner:"Server: nginx"`). The greeting the NULL or GenericLines probe got is read by Recog's SSH, FTP, SMTP, POP3, IMAP and telnet databases, and the first HTTP reply's headers by the header readers (`vsrc:nmap`: the `Server`, `X-Powered-By` and version headers) and Recog's `http_header.server` and `http_header.cookie` databases. A Sentinel with the matching scanner library sends the fingerprint up to 4,096 characters (the banner script's text stays at 1,024), so the first reply's headers are not cut, and the output of the scripts nmap's version scan runs on its own (its `version` category, never one of the reviewed scripts) as `version_scripts`, kept in `Port.extra['version_scripts']` and searched by `banner:` and `tech:` (the ones with a fixed product and version form are read as readings: [version category scripts](#version-category-scripts)); a server reads up to 4,096 characters either way.

**Network operating systems and appliances (`cveFeed/identities.py`).** A FortiGate's port scan says `Fortinet FortiOS 6.2 - 7.2` in its OS guess and its management certificate is the factory one (`CN=FG101FTK...,O=Fortinet`), and neither became a product. The OS guess and its runners-up at 85% accuracy or more (only where the guess can be believed: `os_detection.guess_believed`), each open port's certificate (`Port.tls`, ssl-cert's subject and issuer) and an operating system CPE nmap gave a port are read against `web/cveFeed/data/network_identities.json`: the network operating systems whose CVE records name them (FortiOS, PAN-OS, SonicOS, Junos OS, Cisco IOS, IOS XE, IOS XR, NX-OS, ASA, RouterOS) and a curated table of appliance default certificates (Fortinet's serial-number CN, Palo Alto's serial-number issuer, SonicWall's management certificate, Cisco ASA's and IOS's self-signed ones, Sophos's appliance certificate), each entry with its source. Each is an identity reading under `vsrc:nmap` with the system's operating system CPE: `os:fortios`, `tech:fortios` and `component:fortios` find the host, the edge appliance build read for FortiOS and PAN-OS is warranted by it ([Edge appliance builds](#edge-appliance-builds)), and correlation takes it as a lead (the targeted checks), never a match. A versioned OS CPE (`cpe:/o:paloaltonetworks:pan-os:10.2.9`) is a version reading.

**The SSH banner the SSH inspection read (`vsrc:ssh`).** The banner the Sentinel's SSH inspection reads (`SSH-2.0-OpenSSH_8.9p1 Ubuntu-3ubuntu0.6`) was kept only as the inspection's evidence. It is read by Recog's SSH database, else for the OpenSSH release it names, and stored as a first-party reading of that port (a technology, matched CPE first), less what the port row already states at the same version.

After an update the upgrade backfill `backfill_identities` decodes the fingerprints the ports already store, reads every current host's stored data again (OS guesses, certificates, OS CPEs, Recog identities and hardware, fingerprint headers) and the SSH banners the inspections stored, and correlates the hosts that gained or lost a reading.

### Edge appliance builds

Why. Most CISA KEV entries are in internet-facing VPN and edge appliances, and cvENGINE already names them (a WAF or edge signature, a favicon, a certificate's vendor, wafw00f), but a product named without a version is only a lead: it matches no advisory. Public scanners pin the build from what the appliance's static files say about themselves. `cveFeed/edge_builds.py` adds those reads to the version source catalogue (five entries, `edge_builds.sources()`), with the tables that map each fingerprint to a release in `web/cveFeed/data/edge_fingerprints.json`: every table names its source, the commit or document it was read from and its licence, and every entry cites its line.

How a reading is matched. An exact build is a product reading like any version source's: it becomes a technology (`NetScaler ADC:13.1-48.47`), matched version only under the triage ceilings and the heat cap. NetScaler's own CVE records give the train as `introduced` and only the build as the bound (`introduced 13.1, fixed 49.15`): correlation reads such a NetScaler bound inside the train (13.1-49.15), and reads the vendors' version forms in order (`13.1-48.47`, PAN-OS's hotfix `10.2.9-h1` after `10.2.9`, Ivanti's service release `22.7R2.5` after `22.7R2.4`). A range is stored with outcome `range` and confidence `inferred` and never becomes a technology or a version in range: `edge_builds.collect_matches` matches it against the CVEs whose own record names the product by vendor and product, as NVD and the vendors name them (`fortinet:fortios`, `paloaltonetworks:pan-os` / Palo Alto Networks PAN-OS, `citrix:netscaler_gateway` and `netscaler_application_delivery_controller` / NetScaler ADC and Gateway, `ivanti:connect_secure`, `pulsesecure:pulse_connect_secure` / Pulse Connect Secure). A CVE no release of the range reaches is not matched; one it can reach is a match of source `build_range` with `evidence.range_read` and the range: version unknown, needs validation, ice, never fire, the reason "Build read only as a range". A range only adds such candidates: a product named without a version matched nothing before and still does.

Safety. GET of the static files and the front page above only, asked only of a host already identified as that product (no port warrants an edge entry), with the version source reads' gates, caps and schedule: no login post, no credential, no path any of these products' vulnerabilities is reached by. Each entry also asks a control path next to its first request, so a host that answers every path the same way (a catch-all, a soft 404, a redirect to the login page) reads nothing, and a digest read's answer that a redirect served carries no digest. The `netscaler-gzip` entry needs a Sentinel of contract 8 (`version_digest`): while none can take it, that entry is left out and the host's other reads go ahead.

Left out. Cisco ASA and FTD (the version `/CSCOSSLC/config-auth` once stated was itself a vulnerability, CVE-2014-3398, and is gone; no public table for its WebVPN files), SonicWall SMA and SSL-VPN, F5 BIG-IP, Check Point, MOVEit Transfer and Sophos XG: no public fingerprint whose source and licence allow it here was found, or none that is reliable.

Adding an entry. One `Source` in `cveFeed/version_catalogue.py` (requests, a reader that accepts only the exact shape, `leads` and `ports`, `verified`, an `Exposure` if an anonymous answer is itself a finding) and a test in `tests/test_version_sources.py` with a real-shaped answer and a wrong-shaped or catch-all one. A new language runtime is a `Runtime` in `RUNTIMES`. No Sentinel change: a request is only a path, a read mode, the fields or literal, and the headers.

### AI model servers and agent dashboards

Why. Ollama, llama.cpp's `llama-server`, vLLM and the agent gateways (OpenClaw, Hermes Agent) are often started on a GPU box or a laptop with their bind changed to `0.0.0.0` and no authentication: whoever reaches one runs prompts on its hardware, pulls, pushes or deletes its models, runs code through a workflow or a job, or drives an agent that runs tools on the host. Several have known exploited flaws (Ollama's CVE-2024-37032 "Probllama", Langflow's CVE-2025-3248 and n8n's CVE-2025-68613 on CISA's KEV list, Ray's CVE-2023-48022 "ShadowRay", OpenClaw's CVE-2026-25253). `cveFeed/ai_servers.py` adds twenty entries to the [version source](#version-sources) catalogue (`ai_servers.sources()`), so the reads run on a Sentinel (`version_read`), with the same gates, caps and weekly schedule, and the readings become technologies and correlation evidence like any other.

Discovery. naabu sweeps every port; the fingerprint pass (`cvengine_scanner.flags.EXTRA_PORTS`) also scans the default ports nmap's top thousand leaves out (`flags.AI_PORTS`): 7860 (Gradio, Langflow), 8188 (ComfyUI), 8265 (Ray), 9119 (Hermes Agent), 11434 (Ollama) and 18789 (OpenClaw). An entry is asked on its own default port when the port scan left the service generic or named the web framework the product runs on (uvicorn, aiohttp, Node.js, gunicorn for Dify, axum for TGI, echo or fiber for LocalAI, libevhtp for Triton: `Source.servers`), or of a host a technology, a port product or a nuclei detection already names as the product (on the product's own port when the host serves pages there).

Safety. Every request is a GET of a status or metadata path; nothing that runs a model, pulls or deletes one, calls a tool, signs in or opens a WebSocket is ever asked (a test holds every entry to that: no inference, workflow run, webhook, setup step or sign-in route, and no method or body field), no token or password is sent, and the Sentinel returns only the named fields. A JSON field may index an array (`models.0.name`: the library's `version_read`), so a model's name comes back and nothing else of the list. Model names, ids and titles are host text: only a name made of letters, digits and `._:/@+-` is shown (at most ten, 60 characters each), anything else is only counted, so no instruction or markup a host writes reaches a finding or the AI.

Believing an answer. Each reader takes only its product's own shape; a thin answer (vLLM's one-field `/version`, Flowise's) is believed only next to the product's own signal, so a catch-all that answers every path with the same JSON or page reads nothing. The exposure is rated by what the answer shows (`Exposure.rate`): an answer that shows the server asks for a key or a sign-in (a 401, `protected`, `auth_required`, a master key) files nothing and closes an earlier finding of the entry. A nuclei finding that already reports the same exposure at the same or a higher severity (`vllm-openai-api-exposed`, `langflow-api-exposure`, `flowise-chatflows-exposure`, `ray-dashboard`) is not filed twice; nuclei's medium Ollama and LiteLLM checks are not twins, so the higher rating here is kept. For the five added entries nuclei has detections (`huggingface-tei-tgi-detect`, `localai-detect`, `nvidia-triton-detect`, `dify-panel`, `n8n-panel`, which name the host and so lead to the entry) and one exposure, `n8n-config` (medium: `/rest/settings` discloses configuration). It is not a twin: an n8n with no owner is a different, critical claim, and a twin would hide it.

CVE names. The readings are named as the records name the products (`Ollama`, `vLLM`, `llama.cpp`, `LiteLLM`, `ComfyUI`, `Open WebUI`, `Langflow`, `OpenClaw`, `Ray`, `AnythingLLM`, `Gradio`, `Hermes Agent`, `Text Generation Inference`, `LocalAI`, `Triton Inference Server`, `Dify`, `n8n`), and `web/cveFeed/data/product_aliases.json` reaches huntr's `owner/repo` spellings (`ollama/ollama`, `berriai/litellm`, `comfyanonymous/comfyui`, `ray-project/ray`, `huggingface/text-generation-inference`, `mudler/localai`, `langgenius/dify`...) and NVIDIA's `NVIDIA Triton Inference Server` (CPE `nvidia:triton_inference_server`). `Ray` is held to Anyscale's records (`restrict`). Search: `tech:ollama`, `tech:vllm`, `tech:llama.cpp`, `tech:openclaw`, `tech:n8n`, `tech:dify`, `tech:localai`, `tech:"triton inference server"` find the hosts, `@unknown` the ones read without a version; `component:` and `vsource:ollama` work as for every version source.

Not covered. MCP servers over HTTP or SSE (a GET of an SSE endpoint is a held-open stream, and nuclei's `exposed-mcp-*` checks already report them). Triton's gRPC port (8001) and metrics port (8002) are not read; NVIDIA advisories that write "All versions prior to 25.07" as text are not read as a range yet.

#### llama.cpp build numbers

llama.cpp names its releases by build tag (`b5662`): the server's `/props` says `build_info: b5662-a1b2c3d` and `llama-server --version` prints `version: 5662`. Its advisories write their bounds the same way: the CVE List records of the GitHub CNA say `< b5662` (CVE-2025-49847), `< b5721` (CVE-2025-52566), `< b3561` (CVE-2024-42477, under the old vendor name ggerganov), and cve.now stores ranges such as `introduced b1046, fixed b2731` (CVE-2024-58399) or `introduced b10398, fixed b11301` next to a `0.1.0` to `0.6.0` range (CVE-2026-116829). A version bound must start with a digit, so before this every such range was unknown and the CVE List's text bound was dropped at ingest. Now, for an affected entry that names llama.cpp only (`correlation.is_llamacpp`: product or package `llama.cpp`, `llama_cpp`, `ggml-org/llama.cpp` or `ggerganov/llama.cpp`, of ggml-org, ggml, ggerganov or no vendor), a build tag is read as its build number: in stored ranges when correlation reads them (`correlation.clean_affected`, `llamacpp_range`) and in a CVE List record's version texts when it is converted (`intel._llamacpp_builds`: `< b5662` becomes `< 5662`, a `lessThan: b5662` becomes `fixed: 5662`). The reading states the build number as llama.cpp's version (`llama.cpp:5662`), so a host on build 5661 is in range of CVE-2025-49847 and one on 5662 is not. A tag means nothing for any other product (`parse_version` is unchanged, and llama-cpp-python's ranges stay as they are); a commit is still never a bound (CVE-2025-53630 stays unbounded), and a build number is never inside a 0.x range. The update step `backfill_llamacpp_builds` reads the record again for the stored llama.cpp blocks kept with no range.

### Windows release from NTLM

Why. A Windows service that offers NTLM sign-in states the system's version before anyone signs in, and nmap already reads it: `rdp-ntlm-info` and `ms-sql-ntlm-info` print `Product_Version: 10.0.20348` on the port (`Port.extra['scripts']`), and `smb-os-discovery` names the system on the address (`Windows Server 2019 Standard 17763`). It was display text only (`cveFeed.service_intel`'s host facts), and an operating system never matched a CVE (`match_policy`). `cveFeed/windows_builds.py` reads it as the Windows release it names. `http-ntlm-info`, `smtp-ntlm-info`, `imap-ntlm-info`, `pop3-ntlm-info`, `telnet-ntlm-info` and `nntp-ntlm-info` print the same field and are read the same way when their output is stored (they are not in the scanner's reviewed script list today). nmap's OS guess (`-O`, `IpAddress.os_guess`) never makes a reading. Nothing here sends a request.

The table. `web/cveFeed/data/windows_builds.json` maps a build to its releases, server and client, under the names Microsoft's CVE records use (and the spellings NVD's CPE products and older records use; a `(Server Core installation)` suffix and a `for x64-based Systems` platform are ignored): 6.0.6003 Windows Server 2008 SP2 / Vista, 6.1.7601 Windows Server 2008 R2 SP1 / Windows 7 SP1, 6.2.9200 Windows Server 2012 / Windows 8, 6.3.9600 Windows Server 2012 R2 / Windows 8.1, 10.0.14393 Windows Server 2016 / Windows 10 Version 1607, 10.0.17763 Windows Server 2019 / Windows 10 Version 1809, 10.0.20348 Windows Server 2022, 10.0.25398 Windows Server 2022 23H2 Edition, 10.0.26100 Windows Server 2025 / Windows 11 Version 24H2, and the other Windows 10 (1507 to 22H2) and Windows 11 (21H2 to 25H2) releases. Each release cites its Microsoft lifecycle page and states its end of support (the last security update without a paid Extended Security Updates subscription, a Long-Term Servicing edition included) and the end of ESU where there is one. A build the table does not list makes no reading.

Server or client. One build is often both (10.0.17763). `smb-os-discovery`'s system name decides it (`Windows Server ...` or `Windows 10 ...`); when nothing read does, both releases are kept, each reading says `ambiguous` and names the other, and a CVE naming either is a candidate once.

The reading. One version source reading per release (`ProbeObservation`, probe `vsrc:ntlm`, kind `hint`, `release_only`): product the release name (`Windows Server 2022`), version the build (`10.0.20348`), the scripts and the port it came from, refreshed with the other stored-data readings and dropped when the scripts no longer say it. It is shown with the host's readings ("patch level unknown") and never becomes a technology, so no name-and-version match can ever read it. Search: `vsource:ntlm`; `tech:"windows server 2022"` and `tech:windows` find it; `tech:windows@unknown` finds it and `tech:windows@known` does not (a `release_only` reading states the release, not the patch level); `tech:"windows server 2022"@10.0.20348` finds it, a full build with a revision (`@10.0.20348.2762`) does not.

Release known, patch level unknown. NTLM states the release, never its update revision (UBR: the `.2762` of `10.0.20348.2762`). Microsoft's records state ranges such as `10.0.20348.0` to `< 10.0.20348.2762`, so reading the build as `10.0.20348.0` would put every host inside every range: it is never read that way. `windows_builds.collect_matches` makes a candidate (source `windows`) for a CVE only when all of these hold:

1. its own affected entry names the release (vendor Microsoft, or none);
2. that entry's range covers the release, comparing the build with the range's first three components only (`10.0.0` to `< 10.0.22000.3197` covers 10.0.20348; `< 10.0.20348.0` does not; a range with no upper bound covers nothing);
3. its CVSS vector is network-reachable with no user interaction (`AV:N`, not `UI:R`, `UI:P` or `UI:A`), and it is not local-only (`cveFeed.locality`);
4. it is on the CISA KEV list, or rated 9.0 or more.

The last two rules are the noise limit. A Windows release is named by hundreds of CVE records (244 name Windows Server 2022 with a range that covers it in the published seed, 135 of them `AV:N`), and every candidate costs a person the same minute to settle, so only the ones an outside attacker can reach and that are exploited or critical are raised. A flaw that needs a user to open a file or a page (`UI:R`: MSHTML, SmartScreen, mark-of-the-web) is left out: an outside check speaks only to the host's own listening services. A typical Windows Server 2022 host gets 31 candidates (8 KEV, 23 critical); Windows Server 2019 36, 2016 35, 2012 R2 34, 2025 10, a Windows 10 22H2 client 14. The match carries `evidence.windows_patch_unknown`, which `match_policy.is_version_unknown` reads like `java_unknown`: needs validation, ice, never fire, never validated or AI-triaged automatically, and it never raises the host's heat on its own. `version_in_range` is None and `matched_version` empty; the evidence keeps the release, the build, the range, the fixed build, which limit let it in (`kev` or `critical`) and the scripts that read it.

End of support. A release past Microsoft's end of support gets no update after that day without ESU: Windows Server 2008 R2 and Windows 7 on 14 January 2020 (ESU to 10 January 2023), Windows Server 2012 and 2012 R2 on 10 October 2023 (ESU to 13 October 2026). A CVE published after that day that names the release is very likely unpatched unless the host has ESU: the candidate's confidence is 0.5 instead of 0.4, it stays version unknown, and the explanation says "end of support" and adds the ESU licence check.

Settling it. The explanation (`match_explain`) and the guide (`confirm_guide`) give the read-only commands a host owner runs in cmd or PowerShell, no administrator rights needed: `ver` (the whole build, `10.0.20348.2762`), `reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion" /v UBR` (the revision, in hexadecimal), `[System.Environment]::OSVersion.Version` with the registry's `UBR` in PowerShell, and `Get-HotFix` for the cumulative update to quote; past end of support, `slmgr.vbs /dlv` for an ESU licence. A revision at or above the fixed build's (2762 for `10.0.20348.2762`) is patched; below it is affected. One question ("Which Windows update revision (UBR) does this host run?") settles every Windows candidate of a host in its validation plan.

After an update the upgrade backfill `backfill_windows_builds` reads the stored script output of every current host that has any, stores the readings and correlates those hosts against the stored Windows CVEs.

### TLS audit

[testssl.sh](https://testssl.sh) (GPLv2, run as a separate program) tests what a handshake cannot show: the protocols and cipher categories a server offers, forward secrecy, renegotiation and the TLS vulnerabilities that have names (Heartbleed, CCS injection, ROBOT, POODLE, FREAK, DROWN, Logjam, SWEET32, Ticketbleed, RC4, CRIME, Winshock, BEAST, Lucky13, BREACH). It is a slow background sweep, never part of a scan: `testssl_sweep` runs daily at 02:20 UTC on its own `testssl_queue`, tests one port at a time (about a minute each), the longest-waiting first, at most 40 per run (`CVENGINE_TESTSSL_MAX_TARGETS`), one sweep at a time, and stops while scanning is paused. A target is retested after 14 days (`CVENGINE_TTL_TESTSSL`); one that could not be tested is asked again after three days.

Targets are the TLS ports nmap found open on a host (443, 8443, 9443, 993, 995, 465, 636, and any port nmap called ssl or https), and 443 for a host with no port data. Mail and directory ports are tested with their STARTTLS dialect (SMTP on 25 and 587, IMAP, POP3, FTP, LDAP). Each target is tested at the address `cveFeed.pinned_transport` vetted (`--ip`, with `--nodns none`), so a name pointed at a prohibited address after it was stored is never contacted, and excluded and archived hosts are skipped. testssl.sh runs with a bare environment: no application secret reaches it.

What it records:

* **Configuration findings** (hygiene findings named `tlsa_*`): SSLv2 or SSLv3 offered, NULL, anonymous, export, low-strength and 3DES ciphers, no forward secrecy, missing secure renegotiation, weak Diffie-Hellman parameters, and every named vulnerability testssl.sh reports as vulnerable or potentially vulnerable (how each reads, and its severity, is under *How a TLS audit finding reads* below). TLS 1.0 and 1.1 stay with the certificate check above (`tls_legacy_protocol`), and the certificate's own problems with `tls_*`. A finding resolves only when a later test of the same port ran and no longer reports it; a test that could not answer changes nothing.
* **Observations**: one per vulnerability test (found or absent) and one summary per port with the protocols offered, kept as `ProbeObservation` rows (kinds `tls-vuln` and `tls-audit`).
* **Hard CVE evidence.** A vulnerability testssl.sh proves is a CVE match (source `testssl`, one per CVE the test names) with the test result as evidence, and counts like a template confirmation: the AI cannot rule it out. Only proven results count (Heartbleed answered with memory, a ROBOT oracle, an accepted export cipher, an accepted renegotiation); "likely", "probably", "potentially" and mitigated results (BEAST, Lucky13, BREACH, SWEET32's 64-bit block warning) are findings, never CVE matches. A later test that finds the service no longer vulnerable closes the match unless a person already works it, and the next scan's host row gets the match back from the stored observation until then.

**How a TLS audit finding reads** (`cveFeed.tls_audit.build_finding`, `cveFeed.tls_catalogue`). A heuristic is not a proof, and the finding says which one it is.

* **Confidence.** A result is *proven* when the test answered plainly `VULNERABLE` (a heartbeat answered with memory, an accepted early ChangeCipherSpec, an accepted export cipher) and a configuration result (a protocol or cipher category offered) is a direct observation. Its title reads "OpenSSL CCS injection (CVE-2014-0224) confirmed on host:port". A "likely", "probably", "seems" or "potentially" result (testssl.sh's `likely VULNERABLE with 00` for CCS injection is a server, often a load balancer, CDN or TLS terminator, answering the probe with a 0x00 byte instead of an alert) is *possible*: "Possible OpenSSL CCS injection (CVE-2014-0224) on host:port, not confirmed". A test that reports a precondition (CBC suites for BEAST and Lucky13, 64-bit blocks for SWEET32, HTTP compression for BREACH, or a result that says "mitigated") is an *exposure*: "BEAST (CVE-2011-3389): precondition present on host:port, not confirmed exploitable". The evidence records `confidence` (`confirmed` or `unconfirmed`), `state`, `proven`, the CVEs, the host and port.
* **Description.** One plain sentence translates testssl.sh's result string (`tls_catalogue.describe_result`, written from testssl.sh 3.2's own source: the CCS, Heartbleed, ROBOT, renegotiation, CRIME, BREACH, POODLE, FREAK, DROWN, Logjam, Winshock, SWEET32, RC4, BEAST, Lucky13 and fallback results, the protocol and cipher categories, and the generic `likely|probably|seems|potentially VULNERABLE` and `VULNERABLE (NOT ok)` forms with their detail suffixes). The raw string is kept as `evidence.result` and drawn, folded, as **testssl.sh output**; it is never the description.
* **The catalogue.** Every test cvENGINE records, and `tlsa_no_handshake`, has an entry: its name with the CVE, what it is and what an attacker needs, the exact read-only commands to confirm it with the finding's host and port (for CCS injection `nmap -Pn -p 443 --script ssl-ccs-injection host` and `testssl.sh --ccs host:443`; a STARTTLS port gets `--starttls`), and the fix with fixed versions. The finding page shows them under **Confirm it yourself** and **What to do**. cvENGINE never runs these commands: the audit runs on a Sentinel, and the commands are for a person to run.
* **Severity.** A result that is not proven is never above Medium and never above its test's own ceiling; testssl.sh's own severity stays in `evidence.testssl_severity` and on the page ("Severity reported by testssl.sh"). A proven result is rated at testssl.sh's severity held to the test's ceiling: Heartbleed Critical; CCS injection (needs a man-in-the-middle and a vulnerable OpenSSL on both ends), ROBOT, FREAK, DROWN, Logjam and Ticketbleed High; client-initiated renegotiation, CRIME, POODLE, RC4 and BEAST Medium; SWEET32 and Lucky13 Low. Configuration results keep testssl.sh's severity, except where it overrates (insecure renegotiation is Medium, low-strength ciphers Medium, 3DES Low, export ciphers High).
* **Triage.** A proven or configuration result is hard evidence for the AI triage ("testssl.sh confirmed it on the server"). An unconfirmed result is not: it sets no floor, so the AI's `needs_validation` stands instead of being raised to `confirmed` with "a deterministic check failed". Every other hygiene finding keeps the old rule.
* **Existing findings.** After an update the upgrade backfill `rewrite_tls_findings` rewrites the open `tlsa_*` findings from their stored evidence (plain description, title, severity, confidence), with no new test; closed findings and a person's status, assignee and notes are not touched. It can be run by hand (`python3 manage.py rewrite_tls_findings`, a dry run until `--apply`), and again changes nothing.

The x86-64 Sentinel image bundles the openssl build that ships with testssl.sh, which still speaks SSLv2, SSLv3 and export ciphers. On arm64 testssl.sh uses the system openssl, which has those protocols compiled out: results for them are not reliable there.

### Other sites and applications on a host

Two slow background sweeps look for OTHER APPLICATIONS that could carry a known CVE. They are not content discovery: GET only, no body, no cookie, no credential, redirects never followed, a small curated set of questions, and a cap on what one host or address is asked. Both run on their own `vhost_queue` (a beat task each, `vhost_sweep` hourly and `subdir_apps_sweep` every 30 minutes, a few addresses or hosts per run), stop while scanning is paused, skip excluded and archived hosts and any address the scannable gate refuses, wait between requests (`CVENGINE_SLOW_WEB_GAP`, 1 second across all workers, and `CVENGINE_SLOW_WEB_HOST_GAP`, 2 seconds per host), and ask each question once per week (the service ledger: `vhost`, `subapp`). `CVENGINE_VHOST=0` and `CVENGINE_SUBDIR_APPS=0` turn them off.

**Virtual hosts** (`cveFeed/vhost_scan.py`). One address can serve several sites, told apart by the Host header (and the TLS server name). For each web address of a project (not a CDN or shared-platform address), the sweep asks `/` once with each name the project ALREADY knows that is not yet recorded as answering there: the hosts stored for the project, the names in the certificates seen on that address and the reverse names discovery recorded for it, and the names certificate transparency found. There is no wordlist and nothing is guessed. A name is asked only when it is in scope (equal to or under a domain target of the project; a host-scoped target covers its own name only): a name outside it is never asked and never added, whatever a certificate lists. At most 20 names per address and 5 addresses per run (`CVENGINE_VHOST_MAX_NAMES`, `CVENGINE_VHOST_MAX_IPS`). The answer (status, title, length, redirect target; never the body) is compared with the address's own default response and with the name's own site (its stored front-page route check, else one GET at its own address): `distinct` is another application, `default_site` (the address ignores the name) and `same_app` (the application the name already serves elsewhere) add nothing. A distinct application is recorded as a `ProbeObservation` of kind `vhost` (host the name, product the address, evidence the classification) and added to the project as a host row of its own (like the rows certificate transparency creates) linked to the address, so names that resolve to the same addresses stay one host with aliases exactly as the Hosts page already merges them; what its page states (a product and a version, in its headers and markers) becomes the host's technologies, which the correlation reads. A later answer that is no longer distinct unlinks the address and says so in the record. The host page shows "Also served here" on the host that holds the address.

**Applications under subdirectories** (`cveFeed/subdir_apps.py`). A product installed under a path (`/jira`, `/grafana`, `/owa`) is invisible to a check that reads only the front page. For each web host (and each distinct virtual host, asked at its own address with its own name) the sweep sends one GET per path of the curated list `web/cveFeed/data/subdir_apps.json`, which holds each path, the product it indicates and the signatures that confirm it, plus at most 10 directories the host's own crawled URLs, archived URLs, `robots.txt` and `sitemap.xml` already show, and three fixed requests (a path no site serves, as the baseline, `/robots.txt` and `/sitemap.xml`). At most `CVENGINE_SUBDIR_MAX_REQUESTS` requests per host per sweep (60) and `CVENGINE_SUBDIR_MAX_HOSTS` hosts per run (6). Only 200, 301, 302, 401 and 403 count as something being there, and an answer the server gives to every path (the baseline, or the front page) is not a mount. What answers is read from the response (title, a header, a marker in the body, a redirect to the product's login): a signature names the product, and a version pattern of that product reads the version when the page states one. A path that only answered is a **lead** (stored with its status, never a technology); a confirmed product that states no version is recorded as `hidden`, like a version probe does; a confirmed product AND a stated version is a Technology (`Jenkins:2.401.3`) of the host and the host is correlated again, so the CVE match rule above applies unchanged (a bare path hit is never a finding). No favicon hash is used. Results are `ProbeObservation` rows of kind `subapp` (an application that is gone at a later sweep becomes `absent`), shown on the host's Web tab as "Applications under subdirectories", and the versioned ones follow the host onto each new scan's rows. An edge that challenges or blocks a request (a Cloudflare challenge, an Akamai, Sucuri or Imperva block page) is recorded as `challenged` with what to allow and is never retried or worked around: that host or address is left alone until the next window.

### Authenticated checks

By default every request is anonymous. For an application the owner may test, an App Admin or the organization's admin can store request headers and a cookie for a target (the **Sign-in** button on the Targets page or `PUT /api/v1/projects/{slug}/targets/{id}/auth-credential`; the MCP server can list and revoke them but never takes a value, so a secret does not pass through a model's context), and Nuclei and the web route check then also see the signed-in application. Use a dedicated low-privilege test account, never a person's session, and choose an expiry of 30, 90 or 120 days (or `never`, which must be chosen on purpose): a session ends, and a stored value past its expiry is simply not sent (the target shows it as expired, and the list shows the days left). The web route check verifies TLS on the same connection that carries the sign-in. Nuclei does not verify TLS on its requests, and a separate preflight cannot secure a later connection. Its signed-in HTTPS pass therefore withholds stored credentials by default, including when a preflight certificate would verify; anonymous Nuclei checks still run. A plain `http` origin must be explicitly configured. The owner can switch **Trust this certificate anyway** on per stored sign-in (`allow_untrusted_certificate`, off by default, App Admin or organization admin, audited as `target.auth_credential.untrusted_certificate`): the sign-in is then also sent over a connection whose certificate does not verify, which means anyone in the network path can read it, so leave it off unless you know the server and the network. Stored sign-ins that existed before this switch keep it off, so one for a self-signed host stops being sent until the switch is turned on. Scans send read-only requests (the Nuclei template read-only policy still applies), but an application can change state on a GET, so keep the account's data disposable.

**What is stored.** A label, up to ten header name and value pairs, an optional cookie string, the `scheme:port` origins it may go to (default `https:443`; plain `http` only if named), a mandatory expiry (30, 90 or 120 days from saving, or an explicit never, in which case none is stored), and the scope it is for, always chosen explicitly: one named host of the target, or all hosts of the target (the target's own name and every subdomain of it), which the page marks with a warning that the credential will be sent to every host of the target that is in scope and on the allowed origins. A blank host never means the whole target. The values are encrypted at rest with the same field key as every other secret (`make rotate-field-key` re-encrypts them), are write-only (every read returns the header and cookie names, never a value; sending a blank value for a name already stored keeps it), and are never logged: the audit log records the label, the header names and the origins. A value must be 6 to 2,000 characters on one line, because a shorter one could not be told apart from ordinary text when it is removed from stored evidence.

**Scope.** A credential is attached to a request only when its destination host is exactly the host it was stored for (or, for a target-wide one, the target's name or one of its subdomains, and never for a host-only target's subdomains), the destination scheme and port are one of its origins, and it has not expired. That check runs after the normal vetting (pinned addresses, `scannable_hosts`, exclusions, archived hosts) and the global pause, never widens it, and applies per request: a different host, a different port or scheme, a third-party host and another target or project never receive it, and a redirect is never followed with it.

**Where it is used.**

- **Nuclei** (the blanket and targeted passes, the weekly deep pass and the CVE template checks). The plain pass runs as before; then the same selection (tags, severities, the approved read-only template library) runs again over explicit `scheme://host[:port]` URLs of exactly the covered origins. The values are written to a nuclei secrets file (`-sf`, the `static` format of nuclei's authenticated scans, one `Header` secret per credential limited to the listed domains) in a private temporary directory (0700, file 0600) that is deleted when the run ends, never on the command line, in the environment or in a log; the run also gets `-dr` (no redirects), because nuclei would otherwise carry custom headers wherever a redirect leads. This was checked against the nuclei 3.11.1 source (`-sf` and `-dr` exist, secrets are looked up per request on the request's host and port, 80 and 443 are treated alike); it was not run against a real nuclei in the build. Two limits: nuclei cannot tell `http://host` from `https://host` on the default ports, so two credentials that would need those two get only the HTTPS one, and a template that hardcodes `http://{{Hostname}}` would send the values over plain HTTP to the same host (the read-only policy and the explicit HTTPS targets make this rare, but it is possible).
- **Web route check** (`cveFeed/route_auth.py`). Each covered route is asked once more with the headers and cookie, one GET with no redirect followed, and the answer is stored in the route's evidence as `authenticated` (state, status, title, redirect target, when), beside the anonymous state, which is unchanged. The body of a signed-in page is never searched for sensitive data and never stored. When a route still shows a login page, the activity line says the stored session may no longer be valid.
- **Not used**, deliberately: the version and identity probes and the WordPress probe (they follow redirects between names, and what they look for is on the public front page), WPScan, bbot, nmap and the TLS and hygiene checks.

**Findings.** A finding saved from a signed-in request carries the tag `seen-while-authenticated` (also `seen_while_authenticated` in the findings API), its activity line says so, and a route's `authenticated` evidence is marked `seen_while_authenticated`. Every stored request, response, curl command and extracted value of a signed-in result has the header values, the cookie and cookie values, the part of a value after its scheme word (`Bearer abc` gives `abc`) and their URL, JSON and base64 forms replaced with `[redacted]` before it is saved, and the same applies to error text. Signed-in nuclei runs have their own ledger keys (`nuclei-auth`, 24 hours, `CVENGINE_TTL_NUCLEI_AUTH`; `route-auth-signed`, 24 hours, `CVENGINE_TTL_ROUTE_AUTH_SIGNED`) that include the credential's revision, so a replaced credential is used at once. An HTTPS Nuclei origin gets no sign-in unless the credential's "Trust this certificate anyway" is on; the withheld origin is recorded (`nuclei-auth-refused`, same revision key) and the host's check coverage says the sign-in is not sent instead of listing the check as planned. That switch also permits the web route check to use a certificate it cannot verify and must only be enabled when the owner accepts the risk to stored credentials. A signed-in nuclei pass always runs on this server, never on a Sentinel: the stored sign-in does not leave it.

### OpenVAS (optional)

With the optional OpenVAS add-on switched on (Settings > OpenVAS, [OpenVAS](OPENVAS.md)), a background sweep on its own `openvas_queue` runs Greenbone's scanner against the hosts an App Admin listed for an opted-in project, one GVM task at a time, each host once a week, and stores what names a CVE. It is not a scan stage: it runs beside the pipeline, and after CVE correlation of a scan its findings are carried onto that scan's host rows from the stored observations (`openvas_scan.carry_forward`, a no-op while the add-on is off). Only a quality of detection of 80 or more is hard evidence (a CVE match with `template_result` `vulnerable`); a lower one is stored as an unconfirmed finding. While the add-on is off nothing is scheduled and nothing runs.

## How many scans run at once

A few numbers decide how much a single server does at once (every scan itself runs on a Sentinel), and **Settings, configMaxxing, Scan concurrency** (App Admins) sets all of them. A value saved there wins over the environment variable, and the environment variable wins over the built-in default.

- **Hosts assessed at once** (`DISCOVERY_CONCURRENCY`): the autoscale ceiling of the discovery worker, a celery gevent pool. Each task is one discovery or one host assessment from start to finish, so this is also how many hosts are assessed at once. It is resized live with celery's `autoscale` remote control (sent after a save and checked every 30 seconds; the worker's own reply is what the page reports; the worker adds one slot a second while messages wait, up to the ceiling, and gives slots back when there is less work than slots, at the earliest 30 seconds after its last scale-up; the consumer's prefetch follows the ceiling, which is what bounds acks_late tasks such as a discovery run, and an acknowledgement lost to a dropped broker connection still frees its slot (`reNgine/broker_acks.py`); `reNgine/gevent_autoscale.py` is the autoscaler, because celery's own one ran a gevent worker at one task at a time for as long as that task ran) and read from the database by `celery-entrypoint.sh` at every start.
- **Hosts per assessment batch** (`CVENGINE_ASSESS_BATCH`): how many hosts one assessment run carries ([CONFIGURATION.md](CONFIGURATION.md)); read at each dispatch.
- **Discovery scans kept running** (`CVENGINE_WORK_DEPTH`): the work conductor's depth, below.
- Sentinels have their own limits (slots per Sentinel on the Sentinels page) and are the best way to scale; see [SENTINELS.md](SENTINELS.md).

### Auto-tuning

These numbers, and the Scan pacing ones that are about throughput (chunks of one stage at once, the hours before a target is rescanned and before a Sentinel refresh), are tuned by `cveFeed.autotune` unless a person pinned them by saving a value. A number saved on the page, or set in `.env` to anything other than the built-in default, pins its setting. It aims high, then scales back: about ten minutes after each restart or update, once memory and the Sentinels have reported, every setting goes up to the target `size_for` works out for this machine (CPU cores, the scanning container's memory budget against each scanner kind's real peak, Postgres connections, free disk, the live Sentinels' slots, the size of the instance; a fact not reported yet gives a documented optimistic value). Every ten minutes the `autotune` task then takes a measurement (`cveFeed.autotune_signals`: memory free and memory kills, which scanner kinds waited for their turn, database connections, CPU load, the discovery worker's busy slots and queue, Sentinel slots and timed-out waits, the assessment backlog, the conductor's last round, scanner failures that point at load) and the controller (`cveFeed.autotune_policy`) backs a setting off at once and fast when it sees trouble for it, brings one above its current target down to it at once (the Sentinels left, the database filled up), and probes back up one step at a time only after two healthy hours with work waiting, never to a level that caused trouble in the last day. Every few hours, with an AI provider, an AI advisor sees the same numbers (numbers only) and may pick a value inside the range the controller allows; its answer is validated like any untrusted input. Nothing changes while scanning is paused or an update is applied. Mode Auto (default) applies, Suggest only recommends, Off does nothing; `CVENGINE_AUTOTUNE=0` is the kill switch. The formulas, the rules and the knobs are in [CONFIGURATION.md](CONFIGURATION.md#auto-tuning).


### When the workers or the pool are the problem

The auto-tuner and the work conductor run on the Celery lanes, so they stop with them. The **watchdog** ([WATCHDOG.md](WATCHDOG.md)) runs outside the lanes: it recreates a lane that has stopped answering, and when `DISCOVERY_CONCURRENCY` in `.env` is 1 to 3 (which holds hosts back while Sentinels idle, and which the auto-tuner never moves) it raises the pool to the auto-tune minimum of 4 through the saved layer and lets go when `.env` is fixed. It never overrides a value a person saved in Settings.
## Host-assessment coverage top-up

**Every 5 minutes.** Topping up hosts missing a core scan stage (nmap, the light nuclei pass, CVE correlation, the targeted nuclei pass) is a deterministic backlog to drain, not a judgment call: a sweep (`cveFeed.coverage_topup`, task `top_up_host_assessments`) runs every 5 minutes, and for every project with free host-assessment capacity (under its cap of 5 and the instance cap of 20, both of which grow with the live Sentinels' slots, see below), not bug-bounty-blocked and not paused, queues the next due hosts up to that free capacity, with no model call. A project that just picked up dozens of new subdomains from one discovery run drains in hours.

The three-hourly AI assessment review that 1.3 ran beside it is retired in 1.4: the AI reviewer's operations check ([AI-REVIEWER.md](AI-REVIEWER.md#operations-check-in-detail)) watches coverage, idle Sentinels, failures and the server's own health instead, and the auto-tuner (above) owns scanner concurrency.

## Changes

Each host keeps a snapshot of its IPs, open ports, services, versions, and technologies. When a scan finishes, hosts are compared with their snapshots and the differences go into the Changes log, which the Changes page, the API (`list_changes`), and the host score read. A target's first scan only records a baseline, so the log starts quiet.

| Kind | Meaning |
| --- | --- |
| `host_new`, `host_returned`, `host_retired` | A host appeared, came back, or was retired |
| `port_opened`, `port_closed` | An open port appeared or went away |
| `service_changed` | The product or version of a port changed |
| `tech_added`, `tech_removed`, `tech_version_changed` | The host's technologies changed |
| `cert_changed` | The host presents a different certificate |
| `auth_changed`, `sensitive_found` | A route's anonymous answer changed, or it started serving a type of sensitive data |
| `screenshot_changed` | The front page visibly changed. The Changes page shows both screenshots side by side. |
| `zombie_host`, `zombie_cleared`, `zombie_route`, `route_retired` | See below |

**Zombie and retired hosts.** A host that stops resolving and whose last web address no longer answers is retired. If that address still answers a plain request with the old name, it is flagged as a zombie instead and scores higher until its name resolves again. A route that answered and now returns 404 or 410 is retired, and one that answers again is a zombie route.

**Re-test on change.** A new host, a new port, a changed service or technology, a route whose auth changed, or a zombie host queues a re-test with the CVE checks forced, up to 25 hosts per scan (`CVENGINE_RETEST_MAX_HOSTS`). A five-minute sweep drains the rest.

**Archive and rediscovery.** A person can archive a host, which keeps its findings and history but leaves routine scanning, and can pin a host to protect it. A daily review also archives retired hosts that stay gone: two meaningful negative observations at least 30 days apart, with no positive one between them. DNS errors, wildcard answers, missing probes, exclusions, and paused scanning never count as absence. Every day cvENGINE rechecks the hosts it archived itself, and a name that resolves again or an IP whose known port answers again is restored and reassessed. A host a person archived stays archived until someone restores it.

**Hosts that never get a scannable IP.** A separate, shorter-timeline path (`cveFeed.unresolved_archive`) handles a different case from the one above: a host that is still enumerated every run (it never vanished, so `retired_at` stays unset) but has never once resolved to a scannable IP, so its host assessments keep ending inconclusive for lack of resolution. Each finished assessment updates a streak on the host (first-failure timestamp, last-failure timestamp, a count); one successful resolution resets it, so a host that resolves fine and is simply waiting its turn for an assessment is never swept up here. A daily, checkpointed review (same shape as the 30-day one, `cvengine-daily-unresolved-archive-review`) archives a host once that streak has lasted `CVENGINE_TTL_UNRESOLVED_HOST` (hours, default 72, which is 3 days) with no success (a name that resolves only into a private network counts too: this server cannot scan it), skipping a pinned, excluded, or currently queued or running host. Once archived this way it lands on the same daily rediscovery sweep as every other archived host (it keys off `archived_at` alone, not the reason), so it is rechecked once a day and restored and reassessed automatically if it starts resolving.

## One host, many names

Names that resolve to exactly the same set of addresses are one host in a project: `example.com` and `www.example.com` on the same servers. The project's own target name is shown (otherwise the shortest), the other names appear as **Also answers to**, and CVE matches, findings, and exposure are counted once. Names behind a CDN or shared edge address, names with a different set of addresses, names that never resolved, and the same addresses in another project stay separate hosts. The dashboard, Hosts page, history, and API count the same way.

## Host score

Every host has a score from 0 to 100 and the reasons behind it, shown as "Why the score is N" on the Hosts page. Hosts, search, and the attack-surface map sort highest first. The score adds capped components: CVE matches at the heat they show on the host (fire 40, smoke 20, ice 5, plus 10 for an AI-confirmed fire match, up to 50; under the KEV heat policy a KEV CVE whose version is not proven is smoke and adds 20, and a CVE neither on the KEV nor exploited is ice and adds 5 whatever its CVSS; matches with an unknown CVE version range add 1 each, at most 2), open findings (up to 25; under the KEV heat policy a finding that names CVEs counts by its heat: fire 25, smoke 10, ice 3), hygiene issues such as an expired certificate or a weak SPF, DKIM, DMARC or TLS setting (critical 20, high 15, medium 8, low 3, plus 2 for each further medium or worse issue, up to 20), web route auth (up to 15), sensitive data (up to 25), a public IP (10), recent change (up to 10), and zombies (up to 15). It is recomputed after each scan, when a verdict is saved, daily, and once when a worker sees a heat policy (`CVENGINE_HEAT_POLICY` or Settings, configMaxxing, Heat policy; under legacy also `CVENGINE_VERSION_ONLY_MAX_HEAT`) different from the one it last recorded.

## CVE intelligence

1. **Feed.** The [cve.now](https://cve.now) feed brings CVSS and affected version ranges. Each sync (every 30 minutes, one at a time) adds new CVEs from the newest-first listing, then applies what cve.now changed: its delta listing (`/api/v1/entries?since=`, kept with its ETag in the `feed:cve_now_changes` row) names every entry it wrote since the last read, oldest first, and each stored CVE it names is read again (at most 900 a run, 0.5 s apart, under cve.now's 120 entry reads a minute: a day cve.now rewrites tens of thousands of entries is caught up in a few runs) and rewritten, so a CVE that gains an exploit or a new range updates its matches. An entry cve.now withdrew or merged into another (a tombstone) is closed like a rejected one: it leaves the correlation pool and its open matches close. A recent entry the catalog lacks is created; an old one is left to the inventory import below. A few CVEs with open matches, and recent ones that arrived with no affected-product data, not read for a day are read again as a safety net. Every new CVE is matched against the current inventory at once, whatever its tier (`correlate_new_cves`; the hot ones through auto-fire), and the CVEs marked for re-correlation drain in batches until none is left (`correlate_refreshed_cves`). Every six hours the older CVEs of the products current hosts run with a known version are read too (`import_inventory_cve_history`, `cveFeed/catalog_import.py`): the catalogue's names for each product are searched on cve.now (a tracked technology by its slug, any other as a quoted name, one publication year at a time past the newest 400 results), at most `CVENGINE_INVENTORY_IMPORT_PER_RUN` entries a run, and a product read in full is not asked again for a week. An hourly task reads back from a little before the coverage watermark (how far the feed is known to be complete) to the head: the newest-first listing as deep as cve.now lists without a key (the newest 400), then by date windows (each past UTC day from cve.now's archive page, today from its `since` delta listing), and moves the watermark only when the whole window was listed and stored. Today's delta names every change, not only new entries, so on a day cve.now rewrites many entries it can run past its page budget (100 pages): the walk then still reads the archive days below it and moves the watermark up to where today began, and today's new CVEs come through the sync's own delta read and, the day after, the day's archive page. That is a normal walk, not a failed one.
   Each feed records when it last ran and last succeeded (`cveFeed/feed_health.py`: the cve.now sync, its changes, the coverage walk, the inventory import, the distribution fixes, threat intelligence, each threat-intelligence source with its last error); System status (`feeds`) shows them and raises a problem for a failure, a feed that has not succeeded for a few of its runs, changes applied more than 6 hours behind, a coverage watermark more than a day behind, or entries the feed lists that cannot be read.
2. **Exploitation sources.** An hourly task (`sync_threat_intel`) also reads sources that cover the whole history: [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) and [ENISA EUVD](https://euvd.enisa.europa.eu/) (exploited in the wild), optionally [VulnCheck KEV](https://docs.vulncheck.com/community/vulncheck-kev/introduction) (needs `CVENGINE_VULNCHECK_API_KEY`), [FIRST EPSS](https://www.first.org/epss/) (probability of exploitation), [Exploit-DB](https://gitlab.com/exploit-database/exploitdb) (public exploit code), and [Metasploit](https://github.com/rapid7/metasploit-framework) (weaponized modules). A source only adds evidence: a CVE missing from one never loses what another reported, and the CVE detail names each source. A CVE these sources name that is not stored is imported from its [CVE List V5](https://github.com/CVEProject/cvelistV5) record, up to 2,000 an hour, known exploited first, so the whole exploited history is in within hours. A CVE that CISA's catalog listed before and no longer lists (read whole that run) loses its KEV flag when no other source lists it. The same run takes a bounded step of each CVE List re-read walk (`CVENGINE_RECORD_REREAD_PER_RUN`): blocks cve.now passed on as bare versions, Cisco's and Oracle's exact builds, and open ranges, so a CVE whose record could not be read when it was stored is read later. An upper bound the record writes as text that is no version (`lessThan: "Apache HTTP Server 2.4*"`, issue 696) never makes an open range: the range is left out (the block keeps the lower bound in `upper_unreadable`, version unknown), whether it came from the conversion or from cve.now. A bound that is a distribution package build (`0:8.7p1-38.el9_4.4`, versionType `rpm` or `deb`) is typed `RPM` or `DEB` and never compared with an upstream version; the distribution data decides those hosts.
3. **Tier** (see [Fire, smoke, and ice](FIRE-SMOKE-ICE.md)), by the heat policy (`CVENGINE_HEAT_POLICY`, `kev` by default). A CVE on the KEV or with a public exploit is *fire*; any other CVE is *ice*, whatever its CVSS or EPSS (both stay visible). That is the CVE's tier. On a host, a fire CVE is *fire* when the flaw is confirmed (`match_policy.has_hard_evidence`: a behavioural template hit, the distribution tracker, the host's report, runZero or a validation hit) and *smoke* while only a version says so, even one read from the library's own file or a vendor-built service's banner (1.3.5); it becomes fire when proof lands. `CVENGINE_HEAT_POLICY=legacy` restores the old tiers (*fire*: known exploited, a public exploit, CVSS 9.0 or higher, or EPSS of 0.1 or more with CVSS 7.0 or higher; *smoke*: CVSS 7.0 or higher or EPSS of 0.1 or more; a version-only match held to `CVENGINE_VERSION_ONLY_MAX_HEAT`). What is correlated and template-tested follows the old tiers under either policy (`threat.attention_tier`).
4. **Match.** A match is a finding, so it needs hard evidence about the host: the product it runs is the *same product* the CVE names **and** its version is inside a bounded affected range. Other evidence only attaches to a match that exists: a template hit, a distribution tracker verdict, a report from the host's own inventory, or runZero reporting the same CVE.
   - **Same product.** CPE equality, the same normalised name, or a known alias (`Next.js` and the npm package `next`). A shorter name matches a longer one only when the extra words describe the same product (`server`, `http`, `daemon`, `framework`, `core`, a vendor in front such as `Apache` or `F5`) or name an edition or service of it: `apache` is `Apache HTTP Server`, `nginx` is `NGINX Open Source` and `NGINX Plus`, `Grafana` is `Grafana OSS`, `GitLab` is `GitLab CE/EE`, `Postfix` is `Postfix smtpd`, `FortiOS` is `Fortinet FortiOS` and `Exchange Server` is `Microsoft Exchange Server 2016 Cumulative Update 14`. Anything else around a name is another product: `nginx` is not `ingress-nginx`, `nginx-ui` or `NGINX Ingress Controller`, `php` is not `phpMyAdmin`, `cloudflare` is not a plugin that works with it, `WordPress` is not one of its plugins, `jquery-ui-rails` (a gem with its own version numbers) is not jQuery UI, and a bare `Apache` banner is not Tomcat or Log4j. A technology stored as a CPE (`cpe:/a:openbsd:openssh:7.2p2`) or a banner token (`OpenSSH_9.6p1 Ubuntu-3ubuntu13.5`) is read as its product and version first. An entry for another product is never range-tested, so a version is never compared with the wrong product's ranges.
   - **Names and aliases.** The names a CVE record uses are not the names scanners print: nmap says `Apache httpd`, Cisco's own records say `Cisco Adaptive Security Appliance (ASA) Software`, its newer ones `Cisco Secure Firewall Adaptive Security Appliance (ASA) Software`, NVD `adaptive_security_appliance_software`, and an SNMP agent only `Cisco Adaptive Security Appliance`. One function decides whether a name reaches a record (`correlation.named_hits`, which matching and the coverage report both use), in this order: the CPE nmap gave (its product exactly, and its vendor or another spelling of it: nmap's `cpe:/a:igor_sysoev:nginx` is F5's nginx, `pocoo` is `pallets`; a record that names no vendor counts only when its own product name starts with the CPE's vendor, `Apache Tomcat` for `cpe:/a:apache:tomcat`), then the name by the rules above, then the aliases of `web/cveFeed/data/product_aliases.json`, then a name that leads with the record's own vendor (`Fortra GoAnywhere MFT` for Fortra's `GoAnywhere MFT`, `QNAP QTS` for `QNAP Systems Inc.`'s `QTS`: the record must name that vendor, by its whole first words, so `Progress` is not `Progressive Labs`). Every alias cites the CPE or CVE record that spells the product that way and names its vendors: an alias reaches a record only when the record names one of them or names no vendor, so it never merges two vendors' products (`Ivanti Connect Secure` is Pulse Connect Secure renamed; `Citrix Gateway` is NetScaler; a GlobalProtect portal is PAN-OS; `Outlook Web App` is Exchange Server). The file also holds the collisions found while measuring the published catalogue: a bare name another vendor uses for something else may only reach its own vendor (`Express` is the Node.js framework, not Ubiquiti's UniFi Express or `@fastify/express`; `.NET Framework` is Microsoft's, not Go's `net/http` or `golang.org/x/net`), and a record of a product two vendors use that names no vendor (`iOS`) never confirms either, so `Cisco IOS` never reaches Apple's iOS and `Apple iOS` never reaches Cisco's IOS. `Oracle HTTP Server` never reaches Apache's HTTP Server. A stored technology name an earlier build kept with its nuclei template word (`Nginx version`) is read without it. After the update `backfill_name_aliases` (a dry run unless `--apply`, run once by the update backfills) correlates again the current hosts carrying a name these rules touch.
   - **Coverage.** `manage.py technology_coverage` (and, for an App Admin, the `technology_coverage` tool and `GET technology-coverage`) measures what is left: the technology names and port products of the current hosts that reach no CVE record (`unmatched`, with the hosts they are seen on and `near`, the catalogue products that share a word with each, where an alias would point), the names seen without a version that do connect, the most CVEs first (`unversioned`: leads for a new version source), the names that reach more than one vendor's products (`ambiguous`; spellings of one vendor across renames count once), and the names that are not software a host runs (`services`: a CDN, a load balancer, a hosting platform, an analytics script or a protocol, listed in `web/cveFeed/data/service_names.json`, which can never carry a CVE and so are kept out of `unmatched`). A `product/version` Server-header token stored as a name (`nginx/1.28.3`) is read as the product and its version, as correlation reads it. It writes nothing. `--seed` reads a CVE seed file instead of the stored catalogue and `--names` a JSON list of names instead of the hosts, so a release's naming gaps can be measured without an inventory. A new alias goes in the data file with its evidence and a test in `tests/test_tech_normalisation.py`.
   - **No version, no match.** A product seen with no version (a bare `nginx` fingerprint) says nothing about which of its hundreds of advisories apply, so it never creates a match. It stays on the host as a technology or port and is listed as an *unverified product* (the host page, the host record's `unverified_products`, and `unversioned_products(host)` in code) for whatever finds the version: a banner read, a version probe, a host inventory. Once a version is known the product matches like any other.
   - **No usable bound, no match.** An advisory that names the product but gives no version bound ("all versions", "unspecified", a git range) cannot be tested against the host's version, so it is not evidence either. Two exceptions, both kept as low-confidence candidates that need validation (never an "affected" verdict): a version older than every branch an advisory lists for a fire or smoke CVE (end-of-life branches get no fix), and a CISA KEV advisory with no usable bound (Apache HTTP Server CVE-2021-41773, Jenkins CVE-2024-23897 and similar) for a host running that product at a known version, stored with `evidence.unbounded`. That one is a *version unknown* match: marked for review (Needs validation, reason "Version of the CVE is not known: review when the affected versions are published"), ice whatever the CVE's tier, at most 2 points of host score, never sent to the model, and re-evaluated when the CVE gains a range (see [CVE intake](CVE-INTAKE.md#a-cve-with-no-known-version-range)). An unbounded advisory of any other CVE stays unmatched, but the host is still template-tested when the CVE is fire or smoke.
   - **Operating systems.** An OS fingerprint (`Ubuntu`, `Windows Server`, an nmap `cpe:/o:` record) never matches a CVE by name from outside, and a CVE whose product is only an operating-system kernel or component (Linux kernel records with no network vector, Windows kernel and Win32k) is `local_only` and never matched: only a match the host reports itself (source `host`) can place its kernel or patch level, and such a match is never closed automatically. A kernel flaw reachable over a network, or on the KEV list, is not host-only. nmap's OS CPE does not turn an application into an OS: `Microsoft HTTPAPI httpd` and `Linux telnetd` stay applications.
   - **Existing data.** After every update, `correlate_cves` and the authoring task close the open matches the old rules made on a name alone ("Closed automatically: no version evidence ..."), and the periodic `reconcile_invalid_correlations` closes wrong-product and OS matches by re-reading the sighting each was made from. A match is kept when anything vouches for it: a person worked it (remediation other than open), assigned it, commented on it or asked for a validation, the AI confirmed it, or it has a template hit, a distribution "vulnerable" verdict, a runZero report or a host report. The closure also settles the match's triage row ("not applicable") and refreshes the dashboard counts. Closed matches are not counted in heat, scores, dashboards or notifications, and a later correlation does not reopen them unless the evidence changes (a version appears). A match whose version moved out of range or whose product is gone is closed. Each match stores its evidence.
5. **Distro backports.** Linux distributions fix CVEs without changing the upstream version. cvENGINE reads the distribution and package release from the banner and compares it with the distribution's own fixed version: for Ubuntu and Debian from the [Debian security tracker](https://security-tracker.debian.org) and [OSV](https://osv.dev), for RHEL and the distributions that follow its errata (CentOS, Rocky Linux, AlmaLinux) from the [Red Hat Security Data API](https://access.redhat.com/hydra/rest/securitydata/). The match is labeled *patched by distro*, *vulnerable per distro tracker*, or *version-only*. Matches are labeled, never dropped. The sources are read daily and an answer counts for 20 hours (under the schedule, so a CVE is asked again the next day); rows are stored in bulk, and the Debian tracker (one large file) is downloaded again only when it changed (ETag, If-Modified-Since) or a CVE never looked up is asked about.
   - **Reading the build.** A banner names the build in several forms, each read into (distribution, release, source package, exact build): nmap's `8.9p1 Ubuntu 3ubuntu0.6`, an SSH server's own `SSH-2.0-OpenSSH_8.9p1 Ubuntu-3ubuntu0.6`, a dpkg version (`PHP/8.1.2-1ubuntu2.14`, `2.4.62-1~deb12u2`), BIND's `9.18.18-0ubuntu0.22.04.2-Ubuntu`, an rpm release (`.el9_4`, `.amzn2`, SUSE's `150400.6.11.1`), Alpine's `-r16`, and FreeBSD's `OpenSSH_9.4 FreeBSD-20230316`. The release is what the banner or OS CPE states, else what the build's own versioning names (`ubuntu0.22.04.1`, `~18.04.3`, `+deb12u3`), else the release that alone published that build: `web/cveFeed/data/distro_packages.json`, built by `scripts/build_distro_packages.py` from Launchpad's publishing history and the Debian archive, with a citation for every (distribution, release, package) (`cveFeed/distro_releases.py`). `8.9p1-3ubuntu0.x` is jammy, Debian's `9.2p1-2` is bookworm; `nginx/1.18.0 (Ubuntu)` names no release, because focal and jammy both ship 1.18.0. The reading is stored on the port (`Port.distro`, `distro_release`, `package_release`, `extra['distro']`), shown on the host page and in the host record's `ports[].distro`, searchable (`distro:jammy`, `pkg:openssh@1:8.9p1-3ubuntu0.6`, see [Search](SEARCH.md)), and named in the match explanation ("Judged by Ubuntu 22.04 (jammy)'s own fixed build 1:8.9p1-3ubuntu0.10: the installed openssh 8.9p1-3ubuntu0.6 is older"). Banners are untrusted: each field is clipped to 512 characters, control and invisible characters are removed, every pattern is anchored, a build longer than its column is dropped rather than cut, and a record that names two distributions names none.
   - **What judges it.** Only Ubuntu, Debian and the Red Hat family have synced fix data. A banner that names only the distribution (`Apache/2.4.52 (Ubuntu)`) is a hint: its match can read "vulnerable per distro tracker" when the release has no fix yet, but is never shown as patched, because the installed build is not known; a technology seen in the web response of a host whose every reading names one Debian or Ubuntu release is judged the same way. A build another publisher made (deb.sury.org's PHP, nginx.org's `1~jammy`, Debian backports) and any distribution without synced data (Alpine, Amazon Linux, SUSE, FreeBSD) keep the version-only answer, with `evidence.distro.third_party` or `tracker: not_synced` saying why. A distribution reading only labels or demotes a match the upstream range already made: it never puts a version in range.
   - **Red Hat.** The distribution daily sync (`sync_distro_fixes`) asks Red Hat only about CVEs with an open match on a Red Hat family host, at most 300 a run, each record capped at 4 MB, and keeps every answer (including "no record") for 24 hours; the request carries only the CVE id. For each RHEL major release Red Hat says whether the package is *Not affected*, *Affected*, *Fix deferred* or *Will not fix*, or names the fixed build and its advisory (RHSA). RHEL 8 and later ship some packages as module streams (`httpd:2.4`, `php:7.4`): a stream applies to an upstream version inside it, and its fixed rpm build is read from the advisory's [OSV](https://osv.dev) record (`RHSA-...`, at most 100 a run). *Not affected* is *patched by distro* (not affected), like Debian's. *Affected*, *Fix deferred* and *Will not fix* are *vulnerable per distro tracker* (no fix yet), like an open Debian issue. A release with a fix is compared with the host's rpm build when the build is known (an `.el8` release in the banner, or the host's inventory report): older is vulnerable, at or past the fix is patched. A banner such as `Apache/2.4.37 (Red Hat Enterprise Linux)` does not show the build, so that match is *backport*: "distro fix available, confirm the installed build (fixed in httpd-2.4.37-65.module+el8.10.0+22069+b47f5c72.1, RHSA-2024:4720)". The fixed build and advisory are on `evidence.distro_fix`. A backport match is never proof: it is version-only (needs validation at most, smoke at most when hot, never fire, under either heat policy and whatever `CVENGINE_VERSION_ONLY_MAX_HEAT` says), its confidence is at most 0.5, and triage asks about it after every match with no distribution answer. The RHEL major release comes from nmap's OS CPE (`cpe:/o:redhat:enterprise_linux:8`), an `.el8` tag, or the operating system the host's addresses report; with no release known, all of Red Hat's releases must agree, or the release whose fixed build is the host's upstream version names it, else the match stays *version-only*. A technology seen in the host's web response (Apache, OpenSSL, PHP from httpx) is judged against the host's Red Hat family distribution when its open services, its `Server` header or its reported OS name RHEL, CentOS, Rocky or Alma and nothing names another distribution (`evidence.distro.basis` is `host`). A product that is not the distribution's package, such as a Software Collection or a vendor's own build, can be misjudged this way; a version newer than Red Hat's fixed build is left *version-only* for that reason.
6. **Auto-fire (optional, off by default).** After a feed sync stores new CVEs, each new fire or smoke CVE is handled once (a run that ended in an error is retried for 48 hours). The AI confirms its matches, and the ones it calls affected or uncertain are tested on their hosts. Hosts that run the CVE's product with no version found have no match, but they are tested too: a template test is a hard check that needs no version. The cap is set under **Settings, AI model** (default 200 hosts per CVE, counted for each project separately).
7. **Test.** An installed nuclei template for the CVE runs on matched hosts once it passes the read-only and destination checks. When none exists, the AI can draft one, and a draft stays a draft until the system validates it without a person: the built-in scanner checks syntax and a benign loopback control, the AI writes a fixture response of an affected and of a fixed host from the CVE data that the template's matchers must match and not match (evaluated offline), and a second AI pass must agree. Only then is it installed as valid. A rejection records its plain reason, a retry is bounded with back-off, and a draft still pending after seven days is closed as expired, not validated ([the lifecycle](AI-REVIEWER.md#ai-written-templates-validated-by-the-system-never-by-a-person)). A draft is never run on a host by the server. An App Admin or an agent can read every AI-written template, get a review report, retire one (its confirmations are read again) or revise it as a new draft that passes the same gates ([reviewing them](AI-REVIEWER.md#reviewing-retiring-and-revising-an-ai-written-template)). The server runs no template itself: every template test goes to the built-in scanner, and with none live the hosts stay due. A hit is saved as evidence linked to the CVE, and a tool error is recorded as an error, never as a clean result.

CVE matches appear under **CVE matches** and in **Findings** with a remediation status (open, in progress, fixed, accepted risk, false positive), and closing one (fixed, accepted risk, false positive) keeps a note on why with who and when ([Closing a finding](AGENT-API.md#triage-and-remediation)). A closed match is out of the host's heat, score and exposure counts, is not paged as fire, and keeps its status and note across rescans. Agents read and update it through the [API](AGENT-API.md). A CVE match is stored per host: the same jQuery file on six sibling subdomains is six matches, and each host keeps its own triage, validation, status and audit. The **Findings** page shows those six as one row (the same client-side library file on one site; servers, CMSs and other server-side products are never grouped; `cveFeed/finding_groups.py`, the rule is under [Grouped findings](AGENT-API.md#grouped-findings)) with **Show every host** to list them apart, and the dashboard's **CVE matches** counter stays per host with the grouped number beside it ("in N"). Reports, CSV exports, scores and heat stay per host.

## Detection strategies

Every CVE has one detection record, shared by all organizations, that says how to tell whether a product is affected: **remote
checks** (a version in an affected range, an HTTP marker, an installed nuclei template, a reviewed nmap script, a TLS property, a
service on a port) and **local checks** on the host itself (a package older than the fixed release, a file that contains a version, a
configuration setting, a service state). Read it with `GET /api/v1/cves/{id}/detection`, the MCP tool `get_cve_detection`, or the
`detection` field of `get_cve`.

A strategy is data, never a program. Every check is one of the kinds above with parameters from an allowlist (HTTP `GET` and `HEAD`
only, nmap scripts from the reviewed list, plain package and file names with no `..`), so whatever runs a check does it with its own
primitive for that kind; nothing in a strategy is a shell command. Each record carries `safety: read_only`.

Records are written by a task every 30 minutes (`author_cve_detections`), hottest first (known exploited, public exploit, high
exploit probability, then score), so a new CVE from any feed gets one within the hour and the back catalog fills in behind it:

1. The **rules author** reads the CVE's own affected products and ranges, and any installed nuclei template. No AI, no cost. A
   client-side JavaScript library cvENGINE reads from script files (the libraries of [JavaScript library versions](#javascript-library-versions):
   jQuery, jQuery UI, Bootstrap, AngularJS and the rest) gets a `script_version` check (the version read from the files the page loads by
   the `html-libraries` read, never `nmap -sV`), host checks only for the system-wide packages that ship it (Debian and Ubuntu `libjs-jquery`
   and `node-jquery`, Fedora and EPEL `js-jquery`, and the like; a package of one release line, such as `libjs-bootstrap` (3.x),
   `libjs-bootstrap4` and `libjs-bootstrap5`, only for a range of its own line) and no check at all for a package that vendors it, by its
   exact name (`jquery-rails`): a copy a website bundles is not a package and only the script read finds it. A separate package named after
   the library (`lodash.merge`) keeps its own checks.
2. The **AI author** is asked once per CVE, for the hot ones only (known exploited, exploit probability or public exploit, or a
   critical score), and only within the daily budget (**Settings, AI model**, default 25 a day; `CVENGINE_DETECTION_AI_PER_DAY` applies when no AI settings exist), spread over the 30 minute runs (the daily budget divided by 48, at least one a run). It sees feed text only, never a project
   or an asset, and its answer is parsed against the schema: a check that does not validate is dropped on its own, and the reason is
   kept on the record. Its checks are added after the rules' checks with an `ai-` id and never replace them. A failed ask is retried
   after a week when the model returned nothing it could parse. An answer that parsed but failed validation is kept with its reasons and not asked again.

A `manual` record is never overwritten. When a CVE's affected data changes, the rules checks are rewritten and the AI checks kept.
`manage.py author_cve_detections [--ai]` fills the whole catalog at once. The records of client-library CVEs written before 1.3.3 (an
nmap banner check and package checks named after every packaging, such as `jquery` and `components/jquery`) are rewritten once by the same
task, with no manual step: a durable cursor walks the records, so a record imported later from an older seed is corrected too. The rules'
checks are replaced and a `revision_note` says so; a model-written record keeps its own checks and words and is queued for the model's own
revision within the daily budget; a `manual` record is left alone.

The policy the AI follows for each new CVE (scope first: `external`, `local_only`, `unclear`; then the record), when a record is revised, and how an administrator adds facts are in [CVE-INTAKE.md](CVE-INTAKE.md). A CVE only usable from the host itself (`local_only`) is never matched to a host.

### Service features and preconditions

Some flaws are reachable only when a service has a feature on: the nginx HTTP/2 module flaws need HTTP/2 (CVE-2026-123007, CVE-2026-123633), Terrapin needs an SSH algorithm, an SMBv3 compression flaw needs compression. A version match cannot tell, so a Sentinel reads the feature where it already talks to the service, and correlation and triage use the reading (`cveFeed/service_features.py`).

- **Readings.** Any Sentinel result kind may carry an optional `service_features` list: `{host, port, transport, feature, value, detail}`. The vocabulary (which features, which values) and its validator are the Sentinel library's `cvengine_scanner.features` (`FEATURES`, `clean_features`), one copy for both sides; `sentinel_broker.clean_result` cleans the list for every kind, and the kind's ingest stores it with `service_features.ingest(project, items, source, allowed=..., covered=...)`: only the project's own hosts, only the endpoints the task asked about, and a reading a task took before and did not repeat is removed (unknown, never "no"). The first feature is `http2`: the `hygiene_check` certificate handshake offers ALPN `h2, http/1.1`, and the server's choice is the reading (`yes` for h2; `no` for http/1.1, or for a server that chose nothing), with the ALPN answer as `detail`. The handshake that reads the certificate is the same one, so it costs no connection. A legacy TLS 1.0 / 1.1 server, and a server that aborts on the offer, have no reading. Cleartext HTTP/2 (h2c) is not probed: nginx and most servers need explicit configuration for it, and a plain-HTTP port stays unknown. Readings are `ServiceFeature` rows, one per host, port and feature, shown on the host page per port, in the certificate list (HTTP/2 column) and in REST and MCP (`service_features` on a host, `http2` on a certificate).
- **Which CVEs need a feature.** One rule table, `detection_classes.FEATURE_RULES`: the advisory's wording that makes the feature a precondition, the wording that says the flaw does not need it, the wording that names a way to the feature no Sentinel reads, and the reading values that expose the host and rule it out. For HTTP/2 the rule reads "when HTTP/2 is enabled", "configurations that use HTTP/2", "configured to use HTTP/2", "the HTTP/2 module", `ngx_http_v2_module`, `mod_http2`, nginx's `http2` listen option and Apache's `Protocols ... h2`. HTTP/2 named only as the flaw's protocol ("a crafted HTTP/2 request", "the HTTP/2 implementation in Tomcat") is no precondition: such an advisory says nothing of HTTP/2 having to be turned on. An advisory that also names HTTP/1.1 needs nothing, and one that names h2c keeps the precondition but is never ruled out. The rules write the result as `requires_features` on the detection record; a person's manual record can set `requires_features: {"http2": false}` (or `true`) to correct the rule; a model's answer never sets it.
- **What a reading does.** For a match of such a CVE, the host's readings of the last 14 days decide, in one place for every feature. *Ruled out*: every HTTPS port the host is known to have (443, 8443, 9443, or a TLS tunnel nmap read as HTTP) was read and none offers HTTP/2. The match is closed as not applicable through the same deterministic path as a different-product match (`correlation.invalid_identity_reason`, `close_invalid_correlation`: this host only, never shared), with the reason in words: "Closed automatically: precondition not met: the host does not offer HTTP/2 (on 443: ALPN http/1.1), which this CVE needs. The advisory says: ...". A template hit, a distribution tracker verdict or a person's standing keeps the match open, as for every deterministic closure. *Exposed*: a port offers HTTP/2. The match's confidence rises by 0.05, at most to 0.9, and its explanation says "the host offers it (on 443: ALPN h2): a precondition holds, which is not proof of the flaw". Its classification does not move: a match that stands on a version string alone stays at needs validation (`triage.ceiling`). *Unknown*: no fresh reading, an HTTPS port not read, or an edge. Nothing changes.
- **Edges.** Behind a CDN, WAF or reverse proxy the TLS handshake, and so ALPN, is the edge's: CloudFront offers h2 whatever the origin nginx does. A host with any edge indicator (`host_context.edge_for`: its CNAME, a CDN flag on the host or an address, a WAF fingerprint, edge response headers, a probe that saw an edge page) reads as unknown for HTTP/2, neither ruled out nor raised. That is wider than the DNS-verified edge that lets the AI clear a match, on purpose: a header is the host's own say-so, but here it can only keep a match open. A reading is the origin's when nothing names an edge in front of the host (a host that is an address, and not a CDN address, is the origin address itself).
- **When it applies.** Correlation applies the reading to every new or moved match. A new reading applies at once: `ingest` re-evaluates the current matches of the hosts whose readings changed (`service_features.reevaluate`), closing the ones it rules out, reopening (unjudged, its triage row pending again) one an earlier reading closed when no reading rules it out now, and moving the confidence of the rest. The AI triage is shown each needed feature with the advisory's sentence and the host's state (`preconditions` in the prompt), and the state is in the match's signature, so a changed reading asks again. The match page's explanation (`match_explain.explain`) carries `preconditions` too.
- **Adding a feature.** A vocabulary entry in `cvengine_scanner.features`, the reading in the Sentinel kind that takes it (items in its result's `service_features`), a call to `service_features.ingest` from that kind's server ingest, a `service_features.SERVER` entry (label, the ports that must be read before the feature is ruled out, whether an edge answers it) and a rule in `FEATURE_RULES` (plus its words in `FEATURE_PREFILTER`). HTTP/3 is the nearest: the `Alt-Svc: h3` header a web probe already reads, and the advisory's "when HTTP/3 / QUIC is enabled".

### Service features: SSH, SMTP, SMB and RDP

Why. Some flaws are reachable only when the service has a feature on: Terrapin needs an SSH cipher mode, SMBGhost needs SMB 3.1.1 compression, EternalBlue needs SMBv1, the Exim BDAT flaws need CHUNKING, BlueKeep needs a server that lets an unauthenticated client reach the RDP channels. A version match cannot tell; a reading of the feature can (the same mechanism as HTTP/2, `cveFeed.service_features`).

What runs, on the Sentinel only:

| Feature | Read by | What is sent |
| --- | --- | --- |
| `ssh_terrapin`, `ssh_cbc`, `ssh_aes_gcm` | the fingerprint pass (`nmap`: the `ssh2-enum-algos` tables) and the SSH inspection (`ssh_probe`: the sshamble record) | nothing new: the server's KEXINIT, sent before any login |
| `ssh_auth_methods` | `ssh_probe` | nothing new; never a credential |
| `rdp_nla` | the fingerprint pass (`rdp-enum-encryption`) | nothing new: one X.224 Connection Request per security protocol, which nmap already sends |
| `smtp_chunking`, `smtp_starttls`, `smtp_smtputf8`, `smtp_8bitmime`, `smtp_pipelining`, `smtp_auth` | the fingerprint pass, on each cleartext SMTP port it found open | one `EHLO`, then `QUIT`: never MAIL FROM, AUTH or STARTTLS |
| `smb_dialect`, `smb_compression`, `smb_signing`, `smbv1` | the fingerprint pass, on port 445 when open | one SMB2 NEGOTIATE (2.0.2 to 3.1.1, with the compression context) and one SMB1 NEGOTIATE (NT LM 0.12 only): no session setup |

The follow-up probes reach only the addresses the fingerprint task named, through the Sentinel's vetted connection path and its own floor, at most 64 endpoints and 120 seconds a task. The fingerprint task itself passed the bug bounty gate and the exclusions before it was sent.

What is stored. The readings name the address; `cveFeed.address_features` stores them for every host name of the project's current inventory at that address (`ServiceFeature` rows, source `nmap` or `ssh_probe`). A service read again without one of its readings loses the old one (unknown, never "no"). An `smtp_auth` list read before STARTTLS carries `tls_unread`: it can show a mechanism but never rule one out.

What they decide. The rules (`detection_classes.FEATURE_RULES`) read the advisory's own words:

| Rule | Advisories | Exposed | Ruled out |
| --- | --- | --- | --- |
| `ssh_terrapin` | CVE-2023-48795 ("Terrapin") | `exposed` | `strict_kex`, `no_affected_mode` |
| `ssh_cbc_mode` | CVE-2008-5161 (SSH, CBC mode) | `yes` | `no` |
| `ssh_aes_gcm` | CVE-2013-4548 ("when an AES-GCM cipher is used") | `yes` | `no` |
| `smtp_bdat` | CVE-2017-16943, CVE-2017-16944 (BDAT) | `yes` | `no` |
| `smtp_auth_ntlm` | CVE-2023-42114, CVE-2023-42116, CVE-2020-12783 (NTLM, SPA) | `ntlm` | a list without `ntlm` and without `tls_unread` |
| `smtp_starttls_injection` | CVE-2011-0411, CVE-2021-33515 | `yes` | `no` |
| `smbv1_server` | CVE-2017-0143 to CVE-2017-0148, CVE-2017-11780, CVE-2020-1301 | `yes` | `no` |
| `smb_compression` | CVE-2020-0796, CVE-2020-1206 | `yes` | `no` |
| `rdp_unauthenticated` | CVE-2019-0708, CVE-2019-1181, CVE-2019-1182, CVE-2019-1222, CVE-2019-1226 | `not_required` | `required` |

A match is closed ("Closed automatically: precondition not met") only when every relevant port of the host was read in the last 14 days and each reading rules it out; a later reading that exposes it reopens it. An exposing reading raises the confidence and never lifts a version-only match above the triage ceiling. The SMTP rules hold only for an advisory about a mail server, and the SMB compression rule reads SMBGhost's and SMBleed's exact wording or SMB compression named outright. Exim's CVE-2023-42115 needs the EXTERNAL authenticator by Exim's own advisory, but its CVE text does not say so: a person can record that on its detection strategy.

### Validating a match

Each detection record also says how to decide a match, so nobody has to rediscover it per CVE:

- `validation.remote_determinable` is `yes` (a nuclei template, an HTTP marker or a reviewed nmap script, at high or medium confidence, can decide it from outside), `partial` (only the reported version or the exposed service, which a backported fix can fool, or for a client-side library the version its script file states, which says nothing about how the page uses it) or `no` (there is no remote check, or the attack vector is local or physical and nothing remote can decide it). `validation.max_remote_state` is the best a remote check can reach on the triage scale: `confirmed` (validated), `likely` or `needs_validation`.
- `validation.validated_when`, `needs_validation_when`, `likely_false_positive_when` and `not_applicable_when` list what moves a match to each state, and `recommended_tools` names the tools (nuclei, the `html-libraries probe`, nmap, curl, openssl, the package manager, grep, systemctl). A client-library record also has `validation.remote_note`: how the version is read (from the script file itself, never a `?ver=` string or the file name alone) and that a hit proves the version is on the page, not that the page is exploitable. The match page and the AI's prompts (triage and validation planning, as `how_checked`) quote it.
- A `script_version` check (`{library, ranges}`, the library one of the keys of `cveFeed/js_libraries.py`'s `LIBRARIES`, its product always that library's own name) renders as the `html-libraries probe` with how to repeat the read by hand. A `version_banner` check whose product is one of these libraries (an older or model-written record) renders the same way.
- Every remote check has a `how`: the tool, the invocation with `<TARGET>` and `<PORT>` to fill in, and how to decide from the output (a `version_banner` with source `http_header` is a `curl -I` of the Server header, with source `technology` a technology fingerprint, otherwise nmap). The guidance for one match (`confirm` in `get_finding`, `cveFeed/confirm_guide.py`) fills in the real host, port and URL. A language package's local check runs on the platform `app` (the application's source or deployment directory: `npm ls`, `composer show`, `mvn dependency:tree`, a lockfile `grep`), never on an OS package manager. Every local check has `commands`: one read-only command per platform (Debian, Red Hat, Alpine, other Linux, Windows) with the shell, whether it needs elevated rights, an `explain` sentence for a person logged in to the host, and a structured `expect` (`version_lt`, `exit_code`, `output_equals`) that a future authenticated scan can evaluate without parsing prose.

The commands are rendered by the application from the validated parameters of each check, with every value quoted; a model never writes one, and a record read from a seed or a model reply has its commands thrown away and rendered again.

### Seeding the catalog

Building the catalog from the cve.now feed takes one request per CVE, so a new install used to spend hours rebuilding what another instance already had. A **seed** is the whole catalog as one file: every CVE (fire, smoke and ice) with its scores, exploitation signals, affected ranges and references, plus its detection record. On first start it is the first step of the first-run chain, ahead of the feed sync, and an install that still has fewer than 5,000 CVEs is offered it again when a worker starts (at most once a day). cvENGINE downloads the seed published as the `cve-seed` release of this repository, checks it against its manifest (count, size, sha256), imports the CVEs it lacks and their detection records, runs the correlation if there are already hosts, and the incremental feed carries on from there. Detection records marked `manual` are never exported or imported. A CVE already present is never overwritten, nothing in the file is trusted (each field is typed and clipped, each strategy is validated again), and offline or a failed check only means the feed builds the catalog up gradually, as before.

- **In the app (App Admin, no command line).** **Settings, AI model, CVE catalog seed**.
  - **Create seed file** runs the export as a background task, one job at a time (an import waits for it). The card shows what it is doing, then the numbers: CVEs, fire, smoke and ice, how many have a detection record, size, SHA-256, and what the privacy check kept out. **Download seed file** and **Download manifest** stream the two files (App Admin only, every download is in the audit log). The files sit in a private folder of the web and worker containers (`CVENGINE_SEED_DIR`, default `~/.config/cvengine/seed`, mode 0700, never served by the proxy), one seed at a time: the next export replaces it and a seed older than 24 hours is removed.
  - **Import a seed file** takes a seed (`cve-seed.jsonl.gz`, at most 256 MB) and, optionally, its `.manifest.json`. With the manifest the size, SHA-256 and count are checked before anything is imported; without it the file is still validated line by line and the card says the checksum was not checked. A worker then imports it with the same validation as the command line (`seed.import_seed`), shows the counts, and removes the upload. Importing twice changes nothing.
  - Both actions are in the audit log (`cve_seed.build`, `cve_seed.created`, `cve_seed.download`, `cve_seed.import`, `cve_seed.imported`) with counts, sizes and checksums, never a record's text.
- **What the export leaves out.** A seed is for sharing with another cvENGINE install, so it holds public CVE data and the shared detection records, never your hosts, findings, projects or organizations. Detection records marked `manual` are never written. Before a record is written every string in it (keys included) is checked (`cveFeed/seed_scrub.py`): for the names of this instance's organizations and projects (five characters or more, not a generic word such as "default"), its domains, host names and IP addresses; for secret shapes (private keys, cloud and provider keys, tokens, bearer and JWT strings, credentials in URLs); and, in the model-written fields only (the summary and the detection record), for assignments such as `password=...`, long random-looking tokens, private network addresses where a host would be, and paths inside this install. A record whose CVE fields fail is dropped; one whose detection record fails is written without it. A tenant name that appears in more than 50 records' public feed text (a project named after a vendor) is treated as public there and still refused in the model-written fields. The manifest's `dropped` block says how many were dropped, by reason (`tenant_name`, `tenant_host`, `tenant_address`, `private_address`, `secret`, `internal_path`), with the CVE ids (at most 200) and never the text found; `manual_withheld` counts the manual records. The check is a safety net, not a guarantee: look at the numbers before sharing the file outside your organization.
- Command line: `manage.py import_cve_seed [file | --url https://...]` imports a file or the published seed by hand; a `<file>.manifest.json` beside a local file is checked first. `make export-cve-seed` writes `web/cve-seed.jsonl.gz` and its manifest (it first writes any missing detection records), with the same privacy check, and `scripts/publish-cve-seed.sh` uploads both to the `cve-seed` release (maintainers only).
- `CVENGINE_CVE_SEED=off` turns the automatic load off; `CVENGINE_CVE_SEED_URL` points it at your own mirror (https, with the `.manifest.json` beside it).

## Keeping scans fast and polite

- **One run per host.** A successful scanner run is reused inside its window: 168 hours (7 days) for nmap, bbot, route checks, naabu, firewall identification, the UDP scan, deep nuclei, WPScan, other sites and subdirectory applications, cloud storage, third-party suppliers, OpenVAS and archived-URL lookups, 14 days for the full port sweep (as a coverage window) and the TLS audit, 72 hours for version and identity probes, and 24 hours for nuclei, the certificate watch, hygiene, re-tests, WordPress detection probes, node2shell, RDP screenshots and signed-in checks. A run that could not finish is asked again sooner (WPScan 24 hours, TLS audit 3 days, UDP and cloud storage 24 hours, suppliers 24 hours, OpenVAS 3 days). Failed or skipped work never counts as coverage, and a Redis claim keeps two pipelines off the same asset. Set the windows with `CVENGINE_TTL_*` in hours ([CONFIGURATION.md](CONFIGURATION.md)).
- **Parents are reused.** A target under one already discovered (`www.example.com` after `example.com`) skips bbot when its parent finished in the last 7 days.
- **Memory aware.** Heavy jobs wait in a queue that hands out memory by estimated cost. If memory runs short, the largest job stops first and bbot, nuclei, and nmap retry lighter. Watch it under **Settings, Resources**.
- **Egress proxy.** **Settings, Proxy** sends the traffic of the built-in scanner to the targets through a proxy (`http`, `https`, `socks5` or `socks5h`, one URL per line, one picked per request in turn; `cveFeed.egress_proxy`). Since 1.4 this server runs no scan and sends no probe to a target, so nothing leaves the server through it: the server hands the list, the bypass list and the private-address choice to the built-in scanner in its settings, and to no other Sentinel. Through it: nuclei, bbot's web modules (so its passive modules' calls to outside services too), WPScan, testssl.sh and wafw00f. Not through it, because they need raw sockets: nmap, naabu and the UDP sweeps. A Sentinel you run yourself keeps its own egress; the setting does not reach it. Calls to outside services made by this server (CVE feeds, AI providers, Shodan, GitHub, HackerOne, runZero, Tailscale, crt.sh) are not proxied. A proxy that fails fails the request, never falling back to a direct connection, and a tool no listed proxy suits does not run. Loopback, this stack's own services and private, link-local and tailnet addresses are never proxied (`CVENGINE_PROXY_PRIVATE=1` sends the private ones through it too); `CVENGINE_PROXY_BYPASS` adds more (see [Configuration](CONFIGURATION.md)).
- **Rescan a host.** **Rescan host** (or `assess_host`) runs a full, fresh assessment of one host: DNS, ports, exposure, nuclei, firewall fingerprint, routes, correlation, AI triage, and TLS, ignoring recent results but keeping scope and exclusions. Progress shows stage by stage, and you can stop it. A person's rescan is never refused because the queue is full: it goes to the front of the discovery queue (`host_assessment.PERSON_PRIORITY`, ahead of every assessment the top-up queued, and never put off for the scans' share of the pool), and its pipeline's Sentinel tasks are offered before the top-up's (`sentinel_dispatch.PERSON_PRIORITY`, above fire). When the host is already waiting in the queue (the top-up queued it, alone or in a batch), that row is moved to the front instead of a second one being made, and the button reads **Rescan now** until you press it; a host already being scanned is left as it is. The caps on host assessments in flight still hold the top-up and the AI host review's recommendations.
- **New hosts between scans.** When the certificate watch sees a new hostname, a short pipeline runs on up to 200 new hosts: the same stages a scan ends with (nmap, screenshots, exposure checks, technology pass, firewall fingerprint, route checks, version and identity probes, WPScan, node2shell if enabled, correlation, targeted pass, triage, and change recording). Agents can start it with `rescan_hosts`.
- **Background full port scan.** A slow task sweeps all 65,535 TCP ports of one in-scope IP at a time (10 minutes per host at most), oldest first. A host nmap gave up on at that limit is a failed sweep (it backs off and is retried, nothing is closed on a half answer), not a clean zero. The sweep only learns that a port is open: it never overwrites what a fingerprinting pass recorded for that port (distro, CPEs, TLS tunnel, service name). Ports it finds are fingerprinted (`-sV --version-intensity 7`, nmap's default and the inventory stage's intensity: a port nmap names early costs the same as at 5, a port it cannot name is sent 48 probes instead of 27) and the host is re-tested. `CVENGINE_FULLSCAN=0` turns it off. Every firing first checks instance-wide whether any project (not bug-bounty-blocked) still has a host missing its core first pass; if so the whole firing is deferred and logged ("Full-port scan deferred: N hosts across M projects still need a first pass") rather than spending a 65,535-port sweep on one address while basic coverage is incomplete elsewhere. A backlog that is only bounty-blocked, or only there because scanning is paused instance-wide, does not gate: see [Host-assessment coverage top-up](#host-assessment-coverage-top-up).
- **Other sites and subdirectory applications.** Two slow sweeps on their own `vhost_queue` ask the project's known names at its web addresses and the well-known application paths of its web hosts, a few at a time, once a week each (see [Other sites and applications on a host](#other-sites-and-applications-on-a-host)). `CVENGINE_VHOST=0` and `CVENGINE_SUBDIR_APPS=0` turn them off.
- **Background UDP scan.** The TCP sweep never looks at UDP, and DNS, NTP, SNMP, IKE, IPMI, SSDP and memcached all speak it, so a second slow sweep (`cveFeed.udp_scan`) scans a short curated list of UDP ports with `nmap -sU -sV`. It rides the same beat firing as the full port scan (which queues it), runs on its own queue (`udp_queue`) under its own heavy job (`nmap-udp-bg`, one at a time, behind everything else), takes one IP at a time, and scans each IP at most once a week (`CVENGINE_TTL_UDP_SCAN`, hours). It uses the full port scan's gate exactly: in-scope, not CDN, a scannable address (private ones only with `CVENGINE_ALLOW_PRIVATE_TARGETS` or as the project's own tailnet device), no excluded, archived or blocked name, not a shared platform's edge, re-checked just before nmap starts; it stops while scanning is paused, and it skips a project whose bug bounty engagement has not confirmed automated testing (the same check as the cloud storage sweep). Like the full port scan it also defers its whole firing, instance-wide, while any project still has a host missing its core first pass. It is on by default, as part of the slow, low-priority scanning; `CVENGINE_UDPSCAN=0` turns it off.
  - **Ports.** 53 DNS, 67 and 68 DHCP, 69 TFTP, 123 NTP, 137 NetBIOS, 161 SNMP, 500 IKE, 514 syslog, 623 IPMI, 1194 OpenVPN, 1812 and 1813 RADIUS, 1900 SSDP, 4500 IPsec NAT-T, 5060 SIP, 5353 mDNS and 11211 memcached. The list is fixed in the scanner library (`cvengine_scanner.flags.UDP_PORTS`); the 1.3 variable `CVENGINE_UDPSCAN_PORTS` is ignored.
  - **Politeness.** `--max-retries 1`, `--max-rate 20` packets a second (fixed in the scanner library), version intensity 3 (nmap's default is 7), no host discovery, no DNS, the kind's 900 second ceiling per address, and only the reviewed scripts: `nbstat`, `snmp-sysdescr`, `snmp-info`, `ntp-info`, `upnp-info` and `ipmi-version`, each one request and read-only. `ntp-monlist` is deliberately not run: nmap files it under intrusive, and the target records the request.
  - **What counts as open.** UDP has no handshake. A port that replies is `open`; one that sends an ICMP port-unreachable is `closed`; silence is `open|filtered` (nmap cannot tell open but quiet from dropped by a firewall). `-sV` sends its probes to the silent ports and promotes the ones that answer to `open`, so only a port that answered is stored as `open`, and only those count as exposed surface, heat, search results, change tracking and CVE evidence. A silent port is stored as `open|filtered` only on a host that answered other probes (a firewall that drops everything produces no rows), is never counted anywhere, and is shown on the host's Services tab as a note. A port that was open and goes silent stays open for one more sweep, then becomes `open|filtered`: one lost datagram is not a closed port.
  - **Protocol.** Ports are keyed by number and protocol, so UDP 161 and TCP 161 are two rows on one address. Everything that connects (nuclei, the database, RDP and TLS checks, web routes) reads TCP ports only; evidence, CVE correlation, the host page and the counts read every protocol.
  - **Evidence for CVE matching.** An open UDP service that names a product and version (nmap's own probes; the SNMP sysDescr of Cisco IOS, IOS XE and Junos; the SSDP server string of MiniUPnPd and the portable UPnP SDK; the NTP readvar version) is correlated exactly like a TCP service. A kernel string in a sysDescr is not a product and is not used as one. After every sweep the sysDescr is also read into version readings of each host on the address (more formats, the Windows build and the kernel as hints never matched: [Version sources](#version-sources), "SNMP agents"). When a UDP service appears or changes, the hosts on the address go through the re-test pipeline once (one re-test per host per day).
  - **Findings** (check names `udp_*`, stored like the other hygiene findings with the fix in the text and in the evidence, resolved when a later sweep no longer shows the service): memcached answering on UDP 11211 (high: reflection and amplification, and an unauthenticated cache); SNMP answering the default `public` community, proven by `snmp-sysdescr` getting a reply (high); NTP answering control queries, proven by `ntp-info` (low); SSDP answering on 1900 (medium); IPMI answering on 623, proven by `ipmi-version` (high, RAKP hash disclosure, CVE-2013-4786). Findings are computed from the stored ports of every address a host has, so a host with two addresses keeps what the other showed.
  - **It needs raw sockets.** nmap `-sU` sends its own packets, so it runs on a Sentinel with `NET_RAW` (kind `nmap_udp`; the built-in scanner keeps that capability). Nothing of it runs in the celery container, which needs no scanning privileges.
- **Paced deep nuclei.** Every 10 minutes one due host gets the approved broad template set on its name and up to 20 nonstandard ports, which covers an inventory of about 1,000 hosts each week.
- **Weekly deep discovery.** Daily, each apex domain without a deep discovery in the last 7 days gets one, up to 50 per run. If only its subdomains were targets, the apex is added. This is the one automatic rediscovery without an AI model.
- **Pause everything.** An App Admin can press **Stop all scanning** at the top of the **Scans** page (in any project, or All projects; it is also on **All projects, Activity**). The button then reads **Resume all scanning**. The pause survives restarts: work that touches targets or spends AI budget waits, running scanners stop cooperatively (including a running OpenVAS task, local or on a Sentinel, which the OpenVAS step stops on its next run, within 15 minutes), and running scans are marked aborted. An update's own drain pause stops new work but lets what is running finish. A step that something else calls directly, such as CVE correlation inside a scan, simply runs in line. Bookkeeping that touches no target keeps running (the feeds, notifications, pruning, rescoring). **Resume all scanning** releases the queue; scans that were stopped are not restarted.

### Cloud storage exposure

A slow background sweep (its own queue, `bucketscan_queue`, daily at 01:38 UTC, never part of a scan) looks for AWS S3, Google Cloud Storage and Azure Blob storage that belongs to a project's domains and is public or dangling. It reads only the storage platforms' documented endpoints, never a project host: anonymous HTTPS `GET` and `HEAD` on port 443, no credentials, no signature, one listing page (20 keys at most) and one `HEAD` of a listed object that does not look sensitive. Object content is never downloaded, nothing is written, and the storage endpoints (shared platforms) are never port-scanned. Each name is resolved once through the same vetted transport as the other probes, so an answer in a prohibited range is never connected to.

Candidate buckets, in order of ownership confidence (the tier is kept on the finding):

1. **cname.** A host of the project has a CNAME to a storage endpoint: `<bucket>.s3.amazonaws.com` and its regional and website forms, `c.storage.googleapis.com` (the host name is then the bucket), `<account>.blob.core.windows.net`.
2. **served.** A host answers with a storage `Server` header (`AmazonS3`, `UploadServer`); the bucket is inferred from the host name.
3. **reference.** A storage URL in data cvENGINE already holds: crawled and archived endpoints, page URLs, route redirects, stored scanner responses. An Azure container is tested only when such a URL names it.
4. **guess.** Permutations of the label of each target's registrable domain (`example`, `example-backup`, `example-assets`, `example-dev` and 37 more suffixes, plus the domain itself and its `www.` form at S3) checked at S3 and GCS. Azure account names are never guessed. Turn guesses off with `CVENGINE_BUCKETS_GUESS=0`.

| Result | Finding |
| --- | --- |
| Public listing, tier cname or served | High; critical when the listed names look like backups, database dumps or keys |
| Public listing, tier reference, name carries the project's own domain label | The same as above |
| Public listing, tier reference otherwise | Medium, "ownership unconfirmed" |
| Public listing, tier guess | Medium, never worse: "name guess, ownership unconfirmed, verify the bucket is yours" |
| Name not registered (S3 `NoSuchBucket`, Azure account with no DNS name), tier cname or reference | High, a takeover: anyone can register the name. A GCS name with a dot is medium, because only a verified domain owner may create it |
| Not registered, tier served or guess | Nothing: an inferred name proves nothing |
| Exists, listing refused | An observation (info) on the host, never a finding |

The findings are hygiene findings (check names `bkt_listing` and `bkt_takeover`), so status, assignee, comments, triage, notifications and the API work as for every other finding; the hygiene task leaves them alone. At most 20 object names are stored, and a name segment that looks like a secret (a provider key id, a token, a JWT, `key=value` with a secret word, a long random token) is stored as `[redacted]`. A finding resolves when a later check of the same bucket ran and no longer finds it, or when the reference that led to it is gone (a removed CNAME is the fix for a takeover); a check that gets no answer changes nothing and is asked again the next day.

Politeness: one global request rate shared by every worker (`CVENGINE_BUCKETS_RPS`, 2 a second by default, at most 5), at most `CVENGINE_BUCKETS_MAX_PER_SWEEP` buckets per project per sweep (strongest tier first, longest waiting first), a weekly window per bucket (`CVENGINE_TTL_BUCKETS`), one sweep at a time, and a stop while scanning is paused. Excluded names, hosts of an excluded domain, archived hosts, hosts that resolve to a prohibited address and projects whose bug bounty engagement has not confirmed automated testing are skipped.

### Third-party suppliers

A project can list the **third-party suppliers** it depends on and cannot fix for itself (a hosting provider, a payment processor, an outsourced portal). They are checked from the outside, passively, so the project can see what they run and ask them about it. A supplier is **not an owned host**: it is a row of its own (name, tier critical, high or normal, the exact domain names to look at, a contact and notes), per project, and its results are rows of their own. It never becomes a target, a host or a scan input, and none of this reaches discovery, bbot, nmap, naabu, nuclei, subdomain enumeration, host assessments, remediation assignment, SLA clocks, hygiene lists, stats or the oldest-open figure. Only an organization admin or an App Admin can add or remove a supplier; members and auditors can read. A name that is one of the project's own targets (or under one) is refused (an owned domain belongs in Targets), and so are addresses, ranges, wildcards, URLs, names with a port or a path, private names (`.local`, `.internal`, `.lan` and the like) and a name an organization excluded.

**The host card.** Each listed name gets a Shodan-style card, refreshed by every check and kept when a later check cannot read a section:

- the response headers of the front page (raw, cookies' values never), the `Server` and `X-Powered-By` banners, the page title, and whether plain HTTP answers;
- the TLS certificate (subject, issuer, names, validity and days left, key, signature, trust problem) and the negotiated protocol and cipher;
- the **technology stack with versions where the response states them**: web server, language, framework, CMS, JavaScript libraries, read with the same fingerprinting owned hosts use (`cvengine_scanner.fingerprint` through `route_auth.classify`: headers, generator tags, markers in the page, script names: a version in a script's file name as a hint, never one in its query string), from the one front page a browser would get. No other page is read for it;
- the addresses the name resolved to, whether it handles mail, the edge in front of it, and when it was last checked and last answered.

**Technology search.** Search all of a project's suppliers by technology (`php`, `node`, `nginx 1.1`; commas for any-of) on the Suppliers page, `GET projects/{slug}/suppliers/hosts?tech=`, or the `search_supplier_technology` tool. A term is matched anywhere in the technology name and version and in the raw `Server` and `X-Powered-By` banners, so the answer to "which vendors run PHP?" is one query, and the page can copy a plain-text message to the supplier about what they announce ("please confirm this is on a supported, patched version"). Nothing is sent from cvENGINE.

**Findings** are secondary and informational, kept apart from every other finding table (`SupplierFinding`: severity, evidence, first seen, last seen, status `open`, `accepted` or `resolved`, and a plain-text note about what to ask the supplier). A finding resolves by itself when a later check that could decide it no longer finds it (a check that got no answer changes nothing), and a resolved one that returns reopens. Four checks, all passive:

| Check | What it reads | Findings |
| --- | --- | --- |
| TLS | One certificate read of the name on port 443 (read by a Sentinel, judged by `hygiene.evaluate_cert`) | Expired or expiring, name mismatch, untrusted or self-signed chain, SHA-1 signature, short key, TLS 1.0 or 1.1 accepted. The heavy testssl.sh audit is never run against a supplier |
| Email | SPF, DKIM, DMARC, MTA-STS and the MailFail checks, DNS only, plus the one MTA-STS policy file over verified HTTPS, for a name that handles mail | The owned-host rules at low or worse; a missing MTA-STS policy is low for a supplier |
| Headers and pages | The front page over HTTPS and HTTP, then one plain GET per path of a fixed list of 11 (`/wp-login.php`, `/administrator/`, `/phpmyadmin/`, `/manager/html`, `/server-status`, `/login`, `/solr/`, `/console/`, `/owa/`, `/remote/login`, `/admin/`) | Missing HSTS, missing security headers, plain HTTP served, and an administration or login page that answers with the product's own wording (a catch-all 200 is not a finding). Never a guessed path |
| Known CVEs | The versions the card shows, against the CVE catalog with the same matching and evidence rules as owned hosts (`correlation`, `match_policy`), stricter: only a version inside a bounded affected range, never a product name alone, never an unbounded advisory, and nothing behind an edge that rewrites the banner | One informational finding per announced product and version, naming its CVEs. A distribution build is one step lower ("fixes may be backported"). Never validated: nothing is tried against the supplier and no finding can be marked as exploited |

**Safety**, the same rules as the other slow sweeps. Every name is resolved once and every address must be public; a loopback, private, link-local, cloud metadata or otherwise prohibited address refuses the whole name, even with `CVENGINE_ALLOW_PRIVATE_TARGETS` set, and every connection goes to those vetted numeric addresses through the pinned transport. Only ports 443 and 80 are used, only the listed names are resolved or asked (no subdomain, neighbour or mail host), there is no port scan, and an edge that challenges a request is recorded and never worked around. The sweep (`supplier_sweep`, its own `supplier_queue`, daily at 03:52 UTC, `CVENGINE_SUPPLIERS=0` turns it off) stops while scanning is paused, skips a project whose bug bounty engagement has not confirmed automated testing, shares the slow web client's global request gap with the other slow web sweeps, checks each supplier once a week (`CVENGINE_TTL_SUPPLIER`, hours; a supplier that answered nothing is asked again after 24 hours, `CVENGINE_TTL_SUPPLIER_FAILED`), runs one sweep at a time through a Redis claim, and is capped: suppliers per project, names per supplier and requests per sweep (`CVENGINE_SUPPLIERS_MAX_PER_PROJECT`, `_MAX_DOMAINS`, `_MAX_REQUESTS`; [Configuration](CONFIGURATION.md)). A supplier too big for what is left of a sweep's request budget waits for the next one. A new supplier has no card until the next daily sweep.

### Shared platform addresses

A name on Netlify, Vercel, GitHub Pages, Heroku, or a CDN edge answers on addresses that belong to the platform. cvENGINE recognizes them from the name's CNAME, the `Server` header, or the CDN flag and never points nmap, nuclei or the full-port sweep at them (the host's name is still scanned). The host record says so.

### Shared provider domains

A tenant of a multi-tenant provider owns only its own subdomain. For `acme.jfrog.com`, the registrable domain `jfrog.com` belongs to the provider and all its customers, so cvENGINE never promotes it to an apex or enumerates it. A curated list (`SHARED_DOMAINS` in `web/targetApp/shared_domains.py`) marks such domains, and a target under one is **host scoped**: bbot runs with strict scope, the apex sweep skips it, and the certificate watch asks only about that host. Each target has a **scope mode**: `auto` (the list decides), `host`, or `parent` (for a domain you control that sits on the list).

### Exact-host targets

A target whose scope mode is `host` is exactly that one host. Choose it when you add the target, by writing it with a leading `=` in **Add targets** (`=example.com`, `=app.example.com`) or with the dialog's **Scope** choice (`scope_mode: "host"` through the API), or later on the Targets page. Nothing changes for a target added without it: `example.com` still means the domain and everything under it, as before. For an exact-host target:

- bbot runs with strict scope, and an event that names any other host is dropped before it reaches the inventory or the live feed;
- no name under it is stored under the target, whether bbot, the certificate watch or a reused discovery of a parent target found it, and the certificate watch does not query crt.sh for it at all;
- the new-hosts pipeline and **Rescan hosts** take only the target itself;
- the nuclei passes, the TLS and email hygiene checks, the testssl audit, OpenVAS, finding validation (the automatic sweep does not pick such a finding, and a queued or requested validation of it is skipped with "its target is set to this host only"), an agent's network checks, the full port and UDP sweeps, the virtual host and subdirectory application sweeps, the web archive lookup and the scheduled screenshots never reach a name under it, including one stored before the target was narrowed (that row stays in the inventory until it is archived or removed, but nothing scans it through this target; a name another target still holds is scanned as that target's). The bucket check is not narrowed: it asks the storage provider about a bucket a host's data names, never the host itself;
- host assessments (and the coverage top-up that queues them) refuse a name under it, as they already did for any host-scoped target;
- its parent domain is never promoted by the weekly deep sweep.

A name under it can still be its own target (add `www.example.com` too), and for `=app.example.com` another target that covers it (an unmarked `example.com`) still discovers and scans `www.app.example.com` as its own. An `auto` tenant of a shared provider domain stays as it was: host scoped (strict bbot, never its parent) but still watched for its own tree in certificate transparency.

### Excluded hosts

An organization can remove a host and exclude it (**Remove & exclude**, or the API). An exclusion matches the exact host name, case-insensitively, and every stage skips an excluded host in every project of that organization. Adding it as a target is refused. The Hosts page shows names that point at the same addresses as one host, so **Remove & exclude** offers to take those other names with it (otherwise the next name would simply take its place on the page). To drop a whole domain, put `-example.com` on a line in **Add targets** (a paste is checked against its size cap, 10,000 lines and 100 exclusion lines, before any exclusion is applied, so a refused paste removes nothing) (or call `exclude_host` with `include_subdomains`): the name, every name under it (`www.example.com`, `a.b.example.com`, never `notexample.com`) and every target named like them are removed in every project of the organization you can write to, their running scans are stopped, and nothing under that domain is discovered, scanned or added again. A line such as `-com` or `-co.uk` is refused. **Delete host data** removes a host from one project only and leaves it free to be found again. **Move host** (the host page's Manage tab, or `move_host`) hands a host to another project you can write to, in this organization or another: it is added there as a target and scanned from scratch, its data is deleted from the project it left, and that project's scans skip the exact name from then on. Moving it back lifts that. **A target moves with its history.** Moving a target (`example.com`, however many hosts it holds) to another project of the same organization points it at the new project instead of deleting it and discovering it again: its scans, hosts, findings, CVE matches, notes, labels, state, triage and assessments all come with it, and the next scan there updates the same records. A target holding other hosts asks first (the page names them and says how many; `move_host` needs `whole_target: true`), and every target of the project under it goes too. A queued or running scan of it is stopped, and with discovery on it is scanned in the new project. A row the destination already holds for the same host (a label, say) stays, and the moved one is dropped. The old project keeps the target names blocked, so its other targets do not start tracking them. Moving it back lifts that. A single host under a larger target, and any move to another organization (whose targets, addresses and ports are separate records), still delete the host's data here and add it there to be scanned from scratch. Removals that a scan already under way gets in the way of (it writes a row for a target that is being deleted) are run again until they settle, and an exclusion is recorded before anything is deleted so no new scan picks the names up.

## Check coverage

With this many checks, a host record says which ones apply to it and which of those have run: `check_coverage` on every host in `hosts`, `search` and the MCP `list_hosts` and `search_hosts` ([Agent API](AGENT-API.md#hosts-and-search)), and "NN of NNN applicable checks done" under **Overview** on the host page. It is accounting only (the [work planner](#the-work-planner) reads it to queue the due SSH and secrets checks): it reads what the checks already recorded, and runs, queues and changes nothing.

**A port no check exists for** (the nuclei service allowlist has no template for its service, such as Postgres) is named under `no_check` ("Port 9200: no check exists for this service") and in the host page's coverage line. It is not failed, not checked and not counted against the host; it is asked again after 7 days (ledger kind `nuclei-nocheck`) or when the allowlist gains a service class.

**Only checks that apply are counted.** A host with no TLS port is not counted against the TLS audit, a host that shows no sign of WordPress not against WPScan, a host that is not web not against the web checks, the UDP sweep only for addresses it would scan (not a CDN or shared platform edge, nor an address a scanner may not use), a check whose switch is off (`CVENGINE_NAABU=0`, `CVENGINE_VHOST=0`, and so on) not at all, the slow sweeps (UDP, other sites, subdirectory applications, TLS audit) not for a project whose bug bounty engagement has not confirmed automated testing, and the checks that run on a target as a whole (discovery, certificate transparency, the web archive, email authentication, the weekly deep discovery) only on the host that is the target. An excluded or archived host has no applicable check. A name is never resolved to decide this: only stored facts are read.

**Three states.** `done`: the check applies and ran inside its window, which is the ledger window of its kind (`cveFeed.ledger`, with its `CVENGINE_TTL_<KIND>` override); a check with no ledger kind (the database exposure check, CVE correlation) is judged by the time its scan stage finished against seven days. `due`: it applies and never ran, ran longer ago than its window, or its last attempt failed (the `detail` says which). `not_applicable`: it does not apply (the `detail` says why). A check on several addresses or ports is `done` only when every one is covered. A run of any template revision counts, and the thorough WPScan pass waits for the quick pass.

**Where a run is read from** (all existing rows, no migration): the service ledger (`ServiceRun`) for nmap, naabu, wafw00f, the nuclei passes, WPScan, version probes, node2shell, RDP screenshots, the TLS audit, other sites, subdirectory applications, OpenVAS and the signed-in passes; the address row for the full port sweep; `RouteAuth` for the route check; `TlsCertificate` for the certificate check; the `hygiene` ledger run of the host's target (or the `host_hygiene` stage) for the cleartext services check; `ScanActivity` of the host's scan for the stages with no ledger kind. A page of hosts is read in a fixed number of batched queries, never one per host or per check, and every query is limited to the page's own projects.

**Hosts inside a declared internal network.** A host whose name is an address inside a network its project declared internal is scanned only by the internal scan driver (`cveFeed/internal_scan.py`), through a Sentinel inside the network, so the external rules above would call nearly every check not applicable (a scanner may not be pointed at the address from this server). Such a host is judged by `INTERNAL_PLANS` instead: only what the internal scan runs applies (the nmap fingerprint, the UDP sweep, both nuclei passes, the TLS audit of each TLS port, WPScan on a site that shows WordPress, CVE correlation, OpenVAS where the project opted in, and the cleartext services check, which reads only the ports the Sentinel stored), read from the same ledger kinds and scan stages as any host (the internal driver records `nmap-fast`, `testssl` and `udp-scan` runs itself, a `*-failed` kind when a Sentinel answered and the test did not complete, and nothing when no Sentinel answered). Every other check is `not_applicable` with the reason that the internal scan does not run it. A due check on a host with no live Sentinel inside the network says so in its `detail`, so a quiet host is not mistaken for a clean one. The host's `check_coverage.internal` is the declared network (`null` for any other host).

**Adding a check.** Everything is in one module, `web/cveFeed/check_coverage.py`:

1. Give the new check a ledger kind in `DEFAULT_TTL_HOURS` (`cveFeed/ledger.py`), even when 24 hours is right, so its window is visible.
2. Write a `plan_<name>(host, evidence)` function: return the text saying why the check does not apply to this host, or a list of `Unit` (the addresses, ports, CVEs or the host itself it is judged on, each with its recorded runs: `evidence.ledger_runs(kinds, project_id, asset)` for a ledger asset, `evidence.head_runs(...)` for an asset like `host|...`, `evidence.stage_runs(scan_id, stage)` for a scan stage). Read only what `HostFacts` already holds (ports, technologies, web bases, scannable addresses, probe rows); if a rule needs a new stored fact, add it to `HostFacts` and to the batched queries in `load`.
3. Add a `Check(id, label, plan, kinds=..., sweeps=..., stages=...)` line to `CHECKS`, in the order it should read.
4. A kind, sweep or scan stage that is deliberately not a per-host check (a retry window, a scheduler, project-wide work) goes in `EXCLUDED` with its reason instead.

`tests/test_check_coverage.py` reads the code and fails when a ledger kind (a `DEFAULT_TTL_HOURS` key, a `ledger.record` or `fresh` call, a `*SERVICE*` constant), a `ledger.sweep_claim` name or a `_stage(...)` name in `cveFeed/discovery.py` is in neither `CHECKS` nor `EXCLUDED`, so a new feature cannot skip the checklist. Add the applicability rule to `ApplicabilityTests` as well.

## The work planner

Sentinel work used to exist only while some scan stage, host assessment or sweep was waiting for it: a Sentinel task has no life of its own, a Celery job creates it, waits for it and files what comes back. `secrets_scan` and `ssh_probe` (1.4) were stages of a full scan and nothing else, so a host scanned before 1.4 got neither until its whole target was scanned again, while the Sentinels' slots sat idle with nothing waiting. `check_coverage` knows per host which checks are due, but it is accounting only. The **work planner** (`cveFeed/work_planner.py`) turns "due" into Sentinel work, with no AI and nothing that waits on one.

- **Two beat tasks, no scan.** `work_planner_census` (every 5 minutes) reads `check_coverage` over every project's current inventory and keeps, in the cache, the due units of each planner kind with a sort key: one pass over 3,000 hosts is about 2 seconds, so it is a task of its own. `work_planner_tick` (every minute, and 3 seconds after a planned batch ends so a freed slot is refilled at once) measures the Sentinels and queues work; it reads only the cached census plus a bounded number of indexed queries. Overlapping ticks are refused by a short lock. Both run while scanning is paused so the Sentinels page can say so; the planner queues nothing then.
- **What it measures** (`sentinel_broker.planner_capacity`): the live Sentinels, per kind the slots and free slots of the Sentinels that may take it (a Sentinel's declared capabilities, its capability policy, a per-kind cap, "Paused after repeated failures" and the contract gate `sentinel_contract.can_run` are all in `SentinelEff.caps`), the tasks queued and the tasks held. The built-in scanner is the last resort: while an external Sentinel can take a kind, it adds no capacity for it. Work for an address inside a declared internal network is never planned (the coverage rules call it not applicable here).
- **How much it queues.** For each kind, the idle slots (free, minus tasks of other kinds already waiting for them) times `CVENGINE_PLANNER_QUEUE_FACTOR` (2) is the queue it wants; it queues the difference, never more than `CVENGINE_PLANNER_MAX_QUEUE_PER_SENTINEL` (10) tasks waiting per live Sentinel and `CVENGINE_PLANNER_BATCHES_PER_RUN` (12) batches in a run. With every slot busy it queues nothing. A backlog of thousands therefore fills the queue over a few runs and never floods it.
- **Behind everything else.** A batch is one Sentinel task of up to 25 endpoints (`ssh_probe`) or 25 web hosts (`secrets_scan`), run by `work_planner_batch` on `planner_queue` through the same entry the scan stage uses (`ssh_scan.run_for_hosts`, `secrets_scan.run_for_hosts`), so the scope policy, the do-not-scan guard (`sentinel_dispatch._refuse`, fail closed), the bug bounty gate, the ledger window, the claims and the storage apply unchanged, and no `ScanHistory` is created. Its tasks carry priority 0 (validation is 3, smoke 2, every scan stage 1), so a Sentinel takes them last, and `feed_sentinels` does not count them as first-pass work waiting (`waiting_tasks(planner=False)`).
- **Who first.** Organizations take turns, then projects inside each (one batch per turn, the position kept between runs), so a project with a thousand targets cannot take the queue. Inside a project: exposed hosts (an open port on an address a scanner may reach) first, more open ports first, web hosts that answered first for secrets, then never run before oldest run, then name.
- **What it leaves alone.** A host the coverage rules call not applicable (excluded, archived, internal, a CDN or shared edge), a manual-only target, a bug bounty project that has not confirmed automated testing, a project no live Sentinel covers, an address on the organization's do-not-scan list (checked at planning and again, fail closed, by the dispatch), a unit already queued or running (by the planner or a scan stage), a unit fresh in the ledger since the census, a unit of a batch that failed (30 minutes) or that a guard refused (6 hours), and a kind whose last three batches failed (10 minutes). `secrets_scan` is planned only for web hosts that already have route data (`RouteAuth`: `secrets_scan.plan` reads it); a due web host without it is counted as waiting for the route check, which stays a scan stage.
- **Switch and settings.** Settings, configMaxxing, **Work planner**: **Keep Sentinels busy with due checks** (`CVENGINE_WORK_PLANNER`, default on; instance wide, there is no per-project switch) and the three numbers above ([CONFIGURATION.md](CONFIGURATION.md)). Off, Sentinels work only on what scans send.
- **What the page says.** The Sentinels page counts *tasks waiting for a Sentinel, planner work included*, and has one line (`Planner: queued 25 SSH checks and 40 secret checks, 3,102 hosts still due for secret checks, next run in 40 s`, `Planner: nothing due`, `Planner: waiting, all Sentinel slots busy`, `Planner: off`) with a table of what is due by check behind a disclosure (`GET /api/v1/sentinels/live`, key `planner`, limited to the projects the viewer may read). Each run that queued something writes one Activity row; the tasks themselves write the usual hand-off lines.
- **Adding a kind.** Every Sentinel task kind is either in `work_planner.specs()` or in `work_planner.NOT_PLANNED` with its check and the reason; `tests/test_work_planner.py` fails for a new contract kind until it is placed.

## The work conductor

Scans used to start only when someone asked or when a daily or weekly sweep ran, so for most of the day nothing was running even with a thousand hosts to look after. Now a watchdog runs every minute and keeps the discovery queue topped up: when fewer than `CVENGINE_WORK_DEPTH` scans (default 3) are running or queued, it starts discovery, in the mode stored on each target (standard unless it was added or set otherwise: a passive target stays passive, a deep one deep), of the targets that have gone longest without one: never scanned first, then the stalest. It starts at most one per project per round so no project starves the others, and it never picks a target scanned within `CVENGINE_WORK_MIN_GAP_HOURS` (default 2), one that already has a scan going, one an organization excluded, one set to manual only (added with "just add them, do not scan yet", or changed to it on the Targets page: only a person starts a scan of it), a project whose bug bounty engagement has not confirmed that automated testing is allowed (or is paused or finished, or whose program scope changed since the acknowledgement), a target the program's scope does not name ([Bug bounty](BUG-BOUNTY.md#the-scan-gate): the full port sweep, the weekly deep nuclei lane, OpenVAS, certificate transparency and the other sweeps ask the same shared check), or anything at all while scanning is paused (an update's pause included). Each start is logged in the target's project activity. A big Add targets paste queues only its first `CVENGINE_BULK_DISCOVER_NOW` targets (50) and leaves the rest to this conductor, so one request cannot queue hundreds of scans ahead of every other project's. Set `CVENGINE_WORK_DEPTH=0` to turn it off. The depth can also be chosen under **Settings, configMaxxing, Scan concurrency** (**Discovery scans kept running**); a value saved there wins over the environment and is read at the conductor's next round, with no restart. The system status (`get_system_status`, App Admin) shows its depth, the scans running and queued, and its last round, and reports a problem when targets exist, scanning is not paused and nothing is running or queued.

The other work that keeps the instance busy has its own schedule, below: validation of fire and smoke matches, re-tests of changed hosts, the paced full port scan and deep nuclei, triage, and the AI review every three hours.

## Keeping the Sentinels fed, and hosts with no address

- **Hosts with no scannable address are not a backlog.** A name that resolves to nothing (dangling DNS), or only to a private address, has nothing to scan from this server. Once an assessment found that, the host leaves the first-pass backlog (`coverage_topup`, `assessment_review.host_coverage_due`) instead of holding the project's few assessment slots, and instead of making the full-port and UDP sweeps wait for ever (`backlog_exists`). `unresolved_archive.recheck` resolves such a host again every six hours (DNS only) and records why on `HostState.resolution_note`: `private address (...)` (it points inside a private network, which this server cannot scan; like a dangling name it is archived after `CVENGINE_TTL_UNRESOLVED_HOST`, 3 days by default, and the daily rediscovery of archived hosts looks at it again; to scan it, declare the range in the project's internal networks and put a Sentinel with `network:internal` inside it) or `no DNS answer`. A host that resolves again is due at once. The dashboard's coverage counts them apart ("N with no address to scan (...)") from the hosts that are still waiting their turn. A name that still resolves but now points at an address no scanner may touch (this computer, a private range, a cloud metadata address) is not sent to a Sentinel either: the activity feed says "Not scanned: resolves to a refused address" and the host is recorded as failed, not as scanned.
- **A Sentinel always has twice its capacity queued behind what it runs.** `feed_sentinels` (every minute) compares the tasks waiting for a Sentinel with twice the live Sentinels' slots and, when short, queues more host assessments in the projects they cover. The assessment caps (`host_assessment.caps`: 20 in all and 5 per project on their own) grow with the Sentinels (20 plus three per live Sentinel slot in all, and the larger of 5 and three per slot that covers the project), and `DISCOVERY_CONCURRENCY` now defaults to 8, because a pipeline that waits on a Sentinel holds a worker slot while it waits. The caps count pipeline runs, and the feed puts the due hosts of one target in one run of up to `CVENGINE_ASSESS_BATCH` hosts (8 by default), so each stage hands a Sentinel tasks that name many hosts instead of one small task per host; every host keeps its own assessment row and outcome.
- **IPv6** addresses are scanned with `nmap -6` (nmap takes one address family per run; a mixed list runs once per family and the reports are merged). Cloudflare's published ranges are a shared edge for both families and are never scanned.

## Sentinel dispatch

A Sentinel is a scanner agent: the built-in scanner every install starts, or one a person runs on their own network ([Architecture](ARCHITECTURE.md#sentinels), [Agent API](AGENT-API.md#sentinels-scan-stage-agents)). Since 1.4 every scan stage hands its work to one: it asks `agentapi.sentinel_broker.capacity_state` whether a live, eligible Sentinel with the right capability covers the project; if none does, the stage waits (`ScannerUnavailable`, nothing is recorded, the targets stay due); if one does, the stage creates one `SentinelTask`, waits for it, parses the typed result into the shape the tool's output has, and stores it with the persistence function the stage uses. On a timeout or a reported failure the targets stay due and are tried again; nothing runs here. A Sentinel's result is data: nothing it reports is executed, and a result is held to the addresses and targets that were dispatched (anything else is dropped). A nuclei pass on a Sentinel skips denial-of-service templates (`-etags dos`) and runs the approved-template snapshot the server runs, which it fetches from `GET /api/v1/sentinel/template-policy` and `/bundle`.

| Stage | Task kind | What goes to the Sentinel |
| --- | --- | --- |
| Inventory, nmap fingerprint (stage 2) | `nmap` | A chunk of up to 64 addresses |
| Inventory, naabu port sweep (stage 2) | `naabu` | A chunk of up to 64 addresses |
| nuclei, technology pass (stage 5) | `nuclei_light` | Up to 64 targets, tags, severities, the template policy and `external` (contract 11 Sentinels only: each builds the approved set from its baked templates and its library's template index, and refuses a name that resolves to an address no Sentinel may scan, naming it in `not_checked`) |
| nuclei, network detection pass (stage 5) | `nuclei_light` with `network_detection: true` (contract 10 Sentinels only) | Up to three non-web `host:port` targets, their service labels and a budget of 240 seconds a port |
| nuclei, AI-targeted pass (stage 12) | `nuclei_targeted` | The same, for the chosen tags |
| Weekly deep nuclei | `nuclei_deep` | The host and its nonstandard ports |
| WPScan quick pass (stage 9) | `wpscan` | One site and the project's WPScan token, which is scrubbed from the stored task when it ends. The Sentinel returns WPScan's raw report and exit code and the server classifies them |
| WPScan thorough pass | `wpscan_thorough` | One site, with its own time limit (hours) |
| TLS audit (testssl.sh sweep) | `testssl` | One host and port (never a chunk), returning testssl.sh's own finding items |
| UDP scan | `nmap_udp` | One address, returning nmap's raw XML |
| OpenVAS sweep | `openvas` | Its own path: the sweep tracks the task over many ticks instead of waiting ([OpenVAS](OPENVAS.md)) |
| Internal range discovery | `discover` | One /24 chunk |

The rows above are the classic stage-to-kind pairs. The rest of the 40 kinds are dispatched the same way by the stage that owns them: bbot discovery (`bbot_discovery`, streamed), the web screenshots (`web_screenshot`), the RDP screenshot (`rdp_shot`), Kingfisher's secret scan (`secrets_scan`), the SSH host key check (`ssh_probe`), wafw00f (`waf`), the version and identity probes (`http_probe`), the Java runtime reads (`java_runtime`), the version source reads (`version_read`), route checks (`route_probe`, `route_probe_signed`), node2shell, the database checks (`db_probe`), the cloud storage, other sites and subdirectory sweeps, supplier checks, hygiene and dangling-DNS checks, name lookups and retired-name checks, validation page reads, the scan path check and the AI template test. [SENTINELS.md](SENTINELS.md#what-a-sentinel-runs) lists every kind with its tool. A nuclei pass that uses a stored sign-in goes only to the built-in scanner (the sign-in never leaves this install except through its one-time secure read).

**No template set and no name lookup on the server.** The server keeps no copy of the nuclei templates and looks no target name up. A nuclei task names the policy in force (`template_policy` with `source: "index"`), and the Sentinel builds the approved set from the templates baked into its image and the template index of its scanner library (`cvengine_scanner/data/nuclei_template_index.json`, made for the release that image pins): only a file the index records with exactly its sha256 and an approving verdict runs. The server reads the same index for the tags the AI may pick, the products of the panel templates and the template that covers a CVE; a CVE template test names that template by its path and hash (`nuclei_validate` with `template_path`) and the Sentinel sends back the text it ran, which the server reads a hit with. A Sentinel older than contract 11 is offered no nuclei work; with none live the stages wait and the targets stay due. A name is judged only by the Sentinel that connects to it: a task that is not internal work says `external`, so even an internal Sentinel refuses a name that now points into a private network, and the stage writes the refusal to the activity feed. The TLS audit and the OpenVAS sweep name a host's newest stored address that a scanner may touch.

**Chunks run side by side.** A stage that splits into several tasks (nmap and naabu over more than 64 addresses, a nuclei pass over more than 64 targets) does not send them one after another. `dispatch_many` creates a window of chunk tasks up front and waits for all of them in one loop, one read of every task per half second, handing each result to the stage as it lands and creating the next chunk as a slot frees. The window is the smallest of the chunks left, the slots the stage already holds plus the project's free Sentinel slots (never more chunk tasks than slots, so a chunk never queues behind its own stage's chunks), twice the instance's Sentinel slots divided among the scans with a stage dispatching, and `CVENGINE_STAGE_PARALLEL` (default 4); the free slots and the other scans are read again at every refill, the instance's slot total when the stage starts. Each chunk keeps its own task, trace id and activity line ("part 2 of 8"). A chunk that fails or expires stays due alone, and the others carry on; when no live Sentinel is left, or one never claims a task, no more chunks are sent and the rest stay due. Results are applied as each chunk lands, whole chunks at a time: nmap inventory and naabu ports are per address and nuclei findings are de-duplicated, so the order does not matter. The nuclei passes hand the Sentinel wrapper 64 x `CVENGINE_STAGE_PARALLEL` targets per call (256 by default, enough to fill the window) and record each call in the ledger as it finishes. A stop or a global pause while the stage waits expires every chunk task still queued or claimed (none is left behind) and ends the stage as a stopped one. `CVENGINE_STAGE_PARALLEL=1` is the old serial behaviour. testssl, UDP and WPScan are one host per task and unchanged.

**How long a stage waits.** Three separate budgets, all in seconds and shown on the Sentinels page and by `get_sentinel_dispatch`. A Sentinel with a free slot almost always claims a task within its poll interval, so a task nobody claims inside `CVENGINE_SENTINEL_CLAIM_TIMEOUT` (8) is given up for this attempt and its targets stay due. When every live Sentinel is at its concurrency limit the task is not given up on: it waits for a slot for `CVENGINE_SENTINEL_QUEUE_TIMEOUT` (300), or until the last live Sentinel goes away. Once a Sentinel has claimed the task, the stage waits for the result up to a ceiling for the kind, counted from the claim: nmap 900, naabu 1,020, nuclei technology pass 900, targeted pass 1,800, deep pass 3,600, testssl 1,020, UDP 1,560, WPScan 1,800, discovery 1,200, plus a few seconds for each target beyond the first (nmap 90, naabu 150, nuclei 20, 30 and 60; for nmap and naabu the wait is never shorter than the time the Sentinel itself allows the chunk, which is what keeps a late result from being thrown away). `CVENGINE_SENTINEL_DISPATCH_TIMEOUT` replaces every ceiling with one number. A Sentinel that stops heartbeating loses its task after five minutes, which ends the wait early. Every hand-off and check-in writes one line to the AI activity feed (**Live** and **Activity**), naming the Sentinel and the outcome, or saying that no scanner could take the work and the target stays due.

### Internal networks

A project can declare a private network internal. Its addresses may then be added as targets, and the external pipeline never touches them: this server may not scan a private address, and the work conductor skips them. `cveFeed/internal_scan.py` is the one pipeline for such a target, and every step is a Sentinel task for a Sentinel that holds `network:internal` (granted by the server). There is no local fallback: with no such Sentinel the scan fails and says so, and the next sweep tries again. The steps, in order: the host record for the address (no network access), the nmap fingerprint, the TLS audit of each TLS port, the UDP sweep, the nuclei technology pass, WPScan on the sites that pass tagged as WordPress, CVE correlation, then the AI-targeted nuclei pass. Route checks, probes, hygiene, the database checks and screenshots do not run. OpenVAS reaches an internal network through its own opt-in batch. A daily sweep queues every internal target without a clean scan in the last `CVENGINE_INTERNAL_SCAN_DAYS` (7), or one whose last scan failed at least an hour ago, at most `CVENGINE_INTERNAL_SCAN_MAX` (20) a run and only where a live internal Sentinel exists; a scan can also be started by hand on the target. A second sweep discovers live hosts in each declared range, one /24 chunk per Sentinel task, and adds the answering addresses as targets. What an internal host is judged on in the check coverage is described under [Check coverage](#check-coverage).

### Port 25 and the server's own connections

Since 1.4 nothing is scanned from this server: no scan kind and no request to a target has a local path, so the server's own scan traffic is nil. The egress ledger, the connection log, the port-25 governor and the skip list that guarded local runs are gone with them; a provider that throttles port 25 sees only the server's mail notifications. Scans leave from the Sentinel that runs them (the built-in scanner's network, or another machine's); see [Cloud hosts and port 25](CONFIGURATION.md#cloud-hosts-and-port-25).

## Restarts and stuck jobs

A worker killed mid-task (a restart, an update, an out-of-memory kill) leaves work "queued" or "running" that nothing will ever finish, which holds capacity slots and can block an update's drain wait. Three things recover it.

- **Unacknowledged messages come back at startup.** Before its workers start, each worker container returns every broker message a worker had taken and never acknowledged to the front of its queue (`manage.py requeue_unacked`), so queued scans, assessments and validations that never started run after an update instead of waiting for the broker's 12 hour visibility timeout.
- **Lost queue messages are sent again.** Every 15 minutes the stuck job cleanup (`reap_stuck_jobs`) queues again a host assessment waiting longer than 30 minutes and a discovery scan waiting longer than 30 minutes when the broker holds no message for it, at most once every 2 hours each. A row whose task a queue or worker still holds is left alone, because a long queue after a bulk add is only waiting its turn. A discovery scan is sent again in the mode it was queued in (`ScanHistory.discovery_mode`; a scan from before the mode was recorded takes its target's, and a manual only target's is sent as passive), so a passive scan is never recovered as a standard one. Nothing is queued again while scanning is paused.
- **Dead jobs are closed.** A scan or host assessment marked running whose Celery task exists nowhere (not queued, not held, not running) is closed within one cleanup tick once it is older than two minutes, and only when the broker could be asked. As a backstop by age, a host assessment still queued after 12 hours or running after 6 (a batch of hosts: six hours per four hosts, never beyond the discovery queue's time limit), a validation job queued after 6 hours or running after 2, and an activity row running after 11 hours are marked failed with the reason (`CVENGINE_ASSESSMENT_QUEUED_HOURS`, `_RUNNING_HOURS`, `CVENGINE_VALIDATION_QUEUED_HOURS`, `_RUNNING_HOURS`, `CVENGINE_ACTIVITY_RUNNING_HOURS`). A validation job that is expired is due again at once while it has attempts left. While scanning is paused, queued jobs are left alone on purpose and only running ones expire. A late result from a worker that was written off is dropped, never mixed in.

## The bug bounty gate

A project that works a bug bounty program ([Bug bounty](BUG-BOUNTY.md#the-scan-gate)) is scanned automatically only when its engagement says so: the policy was acknowledged and the program's scope has not changed since, the person confirmed that the policy allows automated scanning, and the engagement is `watching` or `active` (not paused or done). An engagement that does not meet all of these blocks its whole project, not only the program's targets, and a project with no engagement is never blocked. One shared check, `cveFeed.bounty_gate`, answers for every unattended entry point: the work conductor, certificate transparency, archived-host rediscovery, host assessments and the coverage top-up (and the first-pass backlog that the full port and UDP sweeps wait on), the new-hosts and re-test pipelines, the full TCP port sweep, the UDP sweep, the weekly deep Nuclei lane, the thorough WPScan pass, OpenVAS, the cloud storage sweep, both other-sites sweeps, the TLS audit, the supplier sweep, template tests, and the validation and hygiene sweeps. The check coverage counts the checks it holds back as not applicable. A scan you start by hand is not held to the project check.

The gate also works per host (`cveFeed.bounty_scope.ScopeIndex`), for every host a scanner is aimed at and whoever started the scan: a host the program lists as out of scope, or does not list at all, is never scanned, and a host that is only ambiguous is scanned once it has been added or imported as a target of the project.
