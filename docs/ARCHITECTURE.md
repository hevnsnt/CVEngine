# Architecture

cvENGINE is one Docker Compose deployment. The scanners run inside the worker image, so nothing is split across machines.

## Services

| Service | Role |
| --- | --- |
| `web` | Django app: the interface, the REST API, and the MCP server (Gunicorn) |
| `celery` | Four gevent workers: discovery, CVE feed, a one-at-a-time validation lane, and everything else |
| `celery-beat` | The schedules: feeds, certificate watch, hygiene, sweeps, AI reviews, and housekeeping (see [PIPELINE.md](PIPELINE.md#schedules)) |
| `db` | PostgreSQL 18 |
| `redis` | Job broker, locks, cache, and the memory queue |
| `proxy` | nginx, terminates TLS on 443 and redirects 8082 to HTTPS |
| `tailscale` | Optional (`COMPOSE_PROFILES=tailscale`): a `tailscaled` sidecar in the celery container's network namespace, so scans reach a tailnet (see [TAILSCALE.md](TAILSCALE.md)) |

The worker image holds the scanners: [bbot](https://github.com/blacklanternsecurity/bbot), [nmap](https://nmap.org), [nuclei](https://github.com/projectdiscovery/nuclei), [naabu](https://github.com/projectdiscovery/naabu), [wafw00f](https://github.com/EnableSecurity/wafw00f) to name firewalls, and [WPScan](https://wpscan.com/) for WordPress sites. [aardwolf](https://github.com/skelsec/aardwolf) reads RDP login screens. Every scanner is pinned to a known-good version, so a rebuild does not change what a scan does (on x86-64 nmap is the nmap project's own release binary, on arm64 the same release is compiled from source; see [Updates](UPDATES.md#branches-and-releases)). Only nuclei's templates, WPScan's vulnerability database and the CVE feeds refresh at runtime. The old reNgine scan engine and the Go tools it used (httpx, subfinder, katana, and others) are gone. bbot downloads [gowitness](https://github.com/sensepost/gowitness) for deep-mode screenshots. See [THIRD-PARTY.md](../THIRD-PARTY.md).

**The live screen's cache.** What the Live page polls is cached in the shared Redis cache, not in each web worker, by *scope* rather than by user (`cveFeed/snapshot_cache.py`). The key is a hash of the project ids the request runs under (an App Admin hashes every project and carries an `all` marker), plus the selected project and organization, so two members of one project share an entry and different scopes never do. A snapshot is `{payload, etag, at, revision}`: fresh for 10 s (the headline and ticker counts, `cve:snap:stats:*`, `cve:snap:discovery-counts:*`), 5 s (the graph version), 2 s (graph-live; the running and queued scan counts of the headline poll are read fresh each time), and kept three times that to serve while one request refreshes it. A stale or missing entry is rebuilt by the request that wins a short lock (`cache.add`); the others serve the stale copy, or wait up to 2 s on a cold key. `bump_stats_revision` (a finding was closed) stores a new revision in the cache and every entry older than it is stale. A cache that does not answer never breaks a view: the answer is computed directly. The ETag of an endpoint is derived from the snapshot (computed once when it was built, never from the clocks in the body), so a `304` does not rerun the walk. nginx compresses JSON, scripts and styles (`config/nginx/rengine.conf`).

### The Live screen's cache

**The refresher (stage 1).** A poll should almost never compute. Every Live poll registers its scope as *hot* for a minute (`CVENGINE_LIVE_HOT_SECONDS`): the scope's key, the project ids the request runs under, and the parameters it was asked with, kept in one cache entry (`cve:snap:hot`, at most 500 scopes). A celery beat entry (`cvengine-live-refresh`, written by beat itself at each start from `CVENGINE_LIVE_REFRESH_SECONDS`, 5 s) runs `refresh_live_snapshots` on `live_cache_queue`, which only the celery container's classic worker consumes (its own queue, so a long sweep ahead of it in another queue never blocks it, and not on the discovery, feed or validation workers, whose slots scan work holds for hours; the number of workers is capped at four for memory). If a refresh finds no free slot it expires after three intervals and the Live screen computes on request until the next one runs. Each run recomputes, oldest first and within three intervals, the hot scopes' snapshots that are within one interval of going stale (`cveFeed/live_refresh.py`), stores them under the key a request would have used (`by: refresher`), pre-builds a graph payload whose version moved, and writes a heartbeat. A request that finds a refresher-made snapshot serves it even past its freshness window (up to three times the window or three intervals) while the heartbeat is younger than four intervals; it computes (single flight, as in stage 0) only when the cache is cold, when a finding was closed (`bump_stats_revision`, so the person who closed it sees it at once), or when the refresher has stopped. The running and queued scan counts of the headline poll are still read on every poll (a few cheap counts). `CVENGINE_LIVE_REFRESH=0` turns it all off. The refresher never touches a target; it only reads the database and writes the cache.

**Tenancy.** The refresher runs each scope inside the project ids stored with it (`tenancy.scope`, no user) and first recomputes the scope hash from them and the stored parameters: a recipe whose hash no longer matches (a project was created under an App Admin's all-projects view) is dropped, so a payload is never written under a key whose scope did not compute it. A user who loses access hashes a different set of ids on the next poll and reads another key; nothing in the cache is addressed by user.

**The per-user project list.** The three queries that resolve which projects a user may see (`roles.allowed_project_ids`) were run for every poll of every open tab. For the four Live polls only (`GET`, `tenancy/membership_cache.py`), the answer is kept per user for `CVENGINE_AUTH_CACHE_SECONDS` (15, at most 30). It is invalidated, not only expired: saving or deleting a project membership, an organization membership, a project or an organization stores a new epoch in the cache (`tenancy/signals.py`, once at once and again at commit), and a cached list is used only with the current epoch, so revoking access takes effect on the next poll in every worker. What bypasses the signals (raw SQL, a bulk `update()` of `Project.org`) takes effect within the TTL. An App Admin is never cached, and every other request, any method, reads the list fresh.

**Seeing it.** For an App Admin, `get_system_status` and `GET system/status` carry `system.live_cache`: whether the refresher is `running`, `silent` (a note when people are on the screen) or `off`, its interval, the hot scopes, its last run, and this hour's and the previous hour's counters (`hit`, `stale`, `miss`, `waited`, `refreshed`, the share served from the cache, and the same per snapshot). While the refresher runs, `miss` should be close to zero.

Ubuntu 26.04, Python 3.14, Django 5.2 LTS, PostgreSQL 18, nmap 7.993, and Go 1.27 for building the scanners.

## Sentinels

A Sentinel is a scanner a person runs on their own network: it registers itself as an `Agent` (`kind='scanner'`), pulls scan-stage work off a project's queue, runs it, and reports typed, clipped results back. It is exactly as untrusted as any other agent (see [TENANCY.md](TENANCY.md) and [AGENT-API.md](AGENT-API.md#agents-and-assigned-work)): nothing it reports is ever executed or built into a command. It runs ten kinds of scan-stage work (`SentinelTask.KINDS`): `nmap`, `naabu`, three nuclei passes (`nuclei_light`, `nuclei_targeted`, `nuclei_deep`), `testssl`, `nmap_udp`, `wpscan`, `openvas` and `discover` (a live-host sweep of a declared internal network), each a capability the Sentinel declares, plus `network:internal` when it sits inside a private network (the server grants that one, a Sentinel's own claim is ignored). The result shapes and limits for each kind are in [AGENT-API.md](AGENT-API.md#sentinels-scan-stage-agents); this section is the design.

**Internal networks.** A project administrator can declare a private network internal to a project (`cveFeed.models.InternalRange`, `projects/{slug}/internal-ranges`). The row is the only opt-in, and it changes exactly one thing: addresses inside it may be added as that project's targets (`agentapi.services._expand_target`). `targetApp.target_types.is_scannable_ip` is deliberately unchanged, so every local scanner still refuses those addresses; `sentinel_only_target` names them, and discovery is never queued for them (the work conductor skips them, a hand-started scan is a 409, `run_pipeline` refuses one that slipped through). Work on an address of a declared range is also claimable only by a Sentinel that holds the `network:internal` capability, which only the server grants (`Agent.network`, set from the enrollment or by an administrator, never from what the Sentinel claims; an outside Sentinel cannot reach it and would report an empty result as clean). **Scanning them.** `cveFeed.internal_scan` is the one pipeline for such a target, and every step in it is a `SentinelTask` for a Sentinel that holds `network:internal`: the host record for the address (no network access), an nmap fingerprint, a TLS audit of each TLS port found, the UDP exposure sweep, the nuclei technology pass, WPScan of the sites that pass tagged as WordPress, then CVE correlation and the AI-targeted nuclei pass, each the external pipeline's own function with only the execution seam changed. There is no local fallback: when no such Sentinel answers, the scan fails and says so, and the next sweep tries again. A scan is queued by starting one on the target by hand (the response says `internal: true`) or by the daily `internal_scan_sweep` (every target without a clean scan in `CVENGINE_INTERNAL_SCAN_DAYS`, default 7, or with a failed stage after a one-hour backoff, at most `CVENGINE_INTERNAL_SCAN_MAX` per run, only in a project where a live internal Sentinel exists). Stages that run from this server directly (route checks, probes, hygiene, database exposure, screenshots) never run for these hosts. Every local scanner (`run_nmap_xml`, `run_naabu`, `stream_nuclei`, `run_testssl`, `run_wpscan_process`) calls `target_types.refuse_local`, which raises while an `internal_scope` is active, so a stage that forgot its Sentinel seam fails loudly instead of connecting to a private address from this server. OpenVAS reaches a declared internal network through its own opt-in sweep: the project's internal targets are a batch of their own (`openvas_scan.internal_batch`), dispatched only when an internal Sentinel that runs the GVM stack exists, and never mixed with the external batch. WPScan runs through a Sentinel on the sites the Sentinel-run technology pass tagged as WordPress (`wpscan_scan.run_wpscan(internal=True)`: this server sends no WordPress probe or plugin lookup of its own, there is no local fallback, and no thorough pass is queued because it would run from here). **Finding the hosts.** `cveFeed.internal_discovery` sweeps a declared range for live hosts: one `discover` `SentinelTask` per /24 chunk (target `{cidr}`, claimable only by a Sentinel that holds `network:internal` and declares `discover`), a Sentinel-side ping sweep, and each answering address added as a project target by the ordinary `add_entries` (no discovery from this server) and scanned by the internal scan driver. The server keeps an address only if it lies inside the chunk it asked about, and never deletes a host that stops answering. A chunk nobody answered is an error on the range (`last_discovery_error`) and the sweep is retried, never read as an empty network. The sweep task `internal_discovery_sweep` runs daily and queues each range not swept in the last `CVENGINE_INTERNAL_DISCOVERY_DAYS` (default 7), on demand with `POST projects/{slug}/internal-ranges/{id}/discover`, at most `CVENGINE_INTERNAL_DISCOVERY_CHUNKS` chunks per run (default 64, a /18; a larger range resumes where it stopped). IPv6 ranges are not swept.

**What dispatches.** Identity, registration, enrollment, task queueing and leasing, the dispatch point in the scan pipeline and the admin UI serve every kind. The per-scan stages that offer their work to a Sentinel are the nmap fingerprint pass and naabu's port sweep (`nmap`, `naabu`), the nuclei technology pass and the AI-targeted pass (`nuclei_light`, `nuclei_targeted`), the testssl.sh TLS audit, the UDP exposure sweep and WPScan; the weekly deep Nuclei pass and OpenVAS dispatch from their own tasks (below). bbot, the bucket checks, the vhost and subdirectory sweeps, the weekly thorough WPScan pass and every other stage have no Sentinel path and always run on this server.

**What a Sentinel's token and results can do.** A Sentinel's token has its own scope, `sentinel`: it reaches only the Sentinel loop (`sentinel`, `sentinel/heartbeat`, `sentinel/tasks/...`, `sentinel/template-policy` and its bundle) and answers `403` everywhere else, including `/mcp/`, so a token taken from a Sentinel's machine is not its administrator's token. It lasts 90 days and its own heartbeat renews the same token in place while under 60 days are left; a Sentinel that was off for longer is enrolled again. Its results are bound to the task: an nmap host, naabu address or nuclei finding for an address that was not dispatched is dropped (`sentinel_broker._bind_to_task`), because ports and findings are stored per organization and a Sentinel scoped to one project must not write another's. The result route takes up to 24 MB (its own nginx location and `DATA_UPLOAD_MAX_MEMORY_SIZE`; every other route 4 MB). A nuclei task on a Sentinel runs with `-etags dos` and the approved-template snapshot the server runs (`GET sentinel/template-policy` and `/bundle`), and a nuclei pass with a stored sign-in is never dispatched.

**The weekly deep Nuclei pass dispatches too, past the per-scan pipeline.** `weekly_deep_nuclei` (`cveFeed/tasks.py`) is a standalone Celery-beat task, not a stage inside `discovery.py`'s `_run_stages`: it paces one host at a time through the broad, unrestricted template set, independent of any particular scan. It builds its nuclei `stream` the same way the per-scan passes do, `agentapi.sentinel_dispatch.wrap_nuclei_stream(scan, 'nuclei_deep')`, the function needed no change, since it was already generic over `kind`; only `SentinelTask.KINDS` carries the `nuclei_deep` name and `sentinel_broker._CLEANERS` the matching result cleaner (the same one `nuclei_light`/`nuclei_targeted` already use, since a deep-pass finding has the identical shape).

**The testssl.sh TLS audit.** Unlike the per-scan stages, testssl's sweep (`cveFeed.testssl_scan.sweep`) tests one `host:port` at a time, never a chunk, so `agentapi.sentinel_dispatch.try_testssl` dispatches a single target per `SentinelTask` (kind `testssl`). A Sentinel's report is testssl.sh's own raw finding items (`id`, `severity`, `finding`, `cve` - the four fields `evaluate()` reads), typed and clipped by a dedicated result cleaner, so no detection logic (CVE extraction, "proven" vs "may apply") is duplicated client-side: `evaluate()` reads a Sentinel's report exactly as it reads a local run's.

**The UDP exposure sweep.** Unlike every other dispatched kind, a Sentinel's `nmap -sU` report travels as nmap's own raw XML text (`SentinelTask` kind `nmap_udp`), not pre-parsed JSON: UDP's state vocabulary (`open|filtered`, extraports summarisation) and the NSE script output the sweep's own product identification reads are read correctly only by `cveFeed.nmap_scan.parse_xml`, so that one function - local or dispatched - is the sole place either kind of run's XML is ever turned into a record. Because this function also reads XML a remote agent reported, it refuses a custom ENTITY declaration outright before parsing (real nmap output never declares one) on top of `xmltodict`'s own default entity handling, which already blocks an external DTD/entity fetch - no new dependency, and it protects a local run's own XML parsing too, at no behavioural cost for a well-formed report.

The Sentinel's own GVM stack and GMP client, in the external `cvengine-sentinel` repository, run the `openvas` tasks this server dispatches (OpenVAS dispatch is described below); a Sentinel provisioned with the Light profile runs no such stack and never takes OpenVAS work.

Every dispatch attempt is visible in the AI activity feed, not just inferable from the Sentinels page's task counts: `agentapi.sentinel_dispatch.dispatch_or_none` logs one `run_check` activity line per `SentinelTask` ("Handed `kind` work for `host` to a Sentinel"), running while the wait is in progress and settled once it ends, naming the Sentinel and its outcome on success or a reported failure, or saying plainly that no Sentinel checked in and the stage ran locally on a timeout. This reuses the exact `kind`/`status` shape every other scan-stage line already uses (`cveFeed.activity.log`/`settle`), so it needs no change to the Live page or the Activity page: both already render any `run_check` line the same way.

A Sentinel's scope widens past one project: an organization-wide enrollment (`orgs/{slug}/sentinels/enroll`, an admin of that organization or an App Admin) covers every project of that organization, present and future, and an instance-wide one (`sentinels/enroll` with no project or org, App Admin only) covers the whole server. Both reuse the existing `scope: {orgs, projects, hosts}` shape unchanged for the first case (`agentapi.agent_scope.project_slugs_in_scope` already resolved `scope.orgs` dynamically at claim time, so this needed no new resolution logic) plus one new `instance: bool` flag for the second, checked only where scope is authorised (`agentapi.agent_scope.authorise`) and resolved (`project_slugs_in_scope`).

**The client is downloadable, in its own repository.** There is no per-OS package: the Sentinel client is a small, standalone Docker Compose service at [hevnsnt/cvengine-sentinel](https://github.com/hevnsnt/cvengine-sentinel) (its own Dockerfile, `docker-compose.yml` and `client/` package, kept separate from this codebase so provisioning a Sentinel never needs a clone of the full CVEngine source), and it runs identically on Linux, macOS and Windows hosts with nothing OS-specific to build or ship. Provisioning is one copy-pasteable blob rather than typing separate fields into a Sentinel's config: the Sentinels page's **Provision** button (or `?format=blob` on `sentinels/enroll`) base64-encodes `generate_enrollment`'s own payload (`agentapi.sentinel_broker.encode_enrollment_blob`; no new crypto, no custom framing, still a plain bearer token over HTTPS) into `CVENGINE_SENTINEL_BLOB`, which the client decodes once, trades for its own token at `sentinels/bootstrap`, and persists (0600, in a named Docker volume) so a restart never needs the blob again. The client's own main loop (`client/daemon.py` in the Sentinel repository) long-polls `sentinel/tasks/next`, accepts, runs the matching tool against only the task's own typed `target` (a fixed argv list built from a defensively validated address/host list, never a shell command: see that repository's `client/tools.py`), parses the tool's own output into the exact typed shapes `clean_result` expects, and reports back; a concurrent heartbeat thread matches `agent_broker.HEARTBEAT_SECONDS`, and SIGTERM finishes or releases in-flight tasks rather than abandoning them. The Sentinel image's own Dockerfile pins nmap, naabu and nuclei to the same versions `web/Dockerfile` pins here (checksum-verified nmap, the same Go module versions for naabu and nuclei), kept in sync by hand across the two repositories since the version-freshness tooling in this repository (`scripts/check_tool_versions.py`, `scripts/generate_sbom.py`) only covers files in this repository. The Provision form's **Where it runs** (external or internal) and **Size** (full or light) choices write the matching `.env` lines into the returned `setup` block: `CVENGINE_SENTINEL_NETWORK=external|internal` (the enrollment records the choice, and for an internal Sentinel the server grants `network:internal`; the line only tells the client where it sits) and `COMPOSE_PROFILES=openvas` for a Full Sentinel, which also runs the OpenVAS stack; `./setup.sh --light|--full --external|--internal --blob '...'` is the same as one command. The two choices can also be changed later from cvENGINE (below).

**Dispatch or local**, the one design decision that matters: before a scan stage (nmap's fingerprint pass, naabu's port sweep, a nuclei pass, the testssl.sh audit, the UDP sweep, WPScan) runs its tool, it asks `agentapi.sentinel_dispatch` whether a live, eligible, in-scope Sentinel exists for the project with free capacity and the right capability. A project with none gets a single cheap existence check and otherwise runs exactly as it did before Sentinels existed, which is the property a dedicated regression test enforces (`tests.test_sentinel_dispatch`). When one exists, the stage creates a `SentinelTask` and waits under three budgets: a short `CVENGINE_SENTINEL_CLAIM_TIMEOUT` (default 8s) for a Sentinel with a free slot to claim it; a queue wait, `CVENGINE_SENTINEL_QUEUE_TIMEOUT` (default 300s), when every live, eligible Sentinel is at its `max_concurrent` (a Sentinel at its limit is busy, not missing, so the task waits for a slot instead of running locally, and the wait ends early if the last live Sentinel goes away); and, counted from the moment a Sentinel claims the task, a completion budget that is a ceiling per kind (nmap 900s, naabu 600s, light nuclei 900s, targeted 1800s, deep 3600s, testssl 600s, UDP 900s, WPScan 1800s, discover 1200s; OpenVAS follows `CVENGINE_OPENVAS_MAX_HOURS`) plus an allowance for each target beyond the first (`CVENGINE_SENTINEL_DISPATCH_TIMEOUT`, when set, replaces every ceiling with one number). So a quiet or offline Sentinel costs a scan stage single-digit seconds, not the full completion budget, while a Sentinel that did pick the work up keeps the full budget to actually run it. A running task's lease is kept by the Sentinel's heartbeat and lost after five minutes without one (the task is marked `expired`), and a Sentinel not heard from for three minutes is offline and offered nothing. On success the stage parses the typed result into the exact shape the local tool's own output already takes, handing it to the exact same persistence function local execution uses (`cveFeed.nmap_scan.persist_inventory`, `cveFeed.naabu_scan.persist_open_ports`, or, for nuclei, a reconstructed result line run through the stage's own untouched per-line loop). On timeout, failure, or no Sentinel, the stage falls back to running the tool locally (nmap and naabu addresses beyond the first 64 of a chunk are run locally too; the exceptions are a target inside a declared internal network and an OpenVAS batch under `sentinel_only`, which never run locally): the subprocess-invoking code itself (`run_nmap_xml`, `run_naabu`, `stream_nuclei`) is never modified, only called from a different place depending on this one branch.

**Egress.** Scans that run on this server can leave through the proxy set under Settings, Proxy (`cveFeed.egress_proxy`, applied by the in-process probes and by nuclei, bbot, WPScan, testssl.sh and wafw00f; nmap, naabu and the other raw-socket tools stay direct). A Sentinel runs the same tools on its own machine and keeps its own egress, so a dispatched stage does not use the proxy; see [Pipeline](PIPELINE.md#keeping-scans-fast-and-polite).

**WPScan dispatch keeps classification server-side, not tool-shaped like nmap/naabu/nuclei.** A Sentinel runs WPScan and reports its raw, unclassified outcome - `{report, returncode, stderr_tail}`, the process's own JSON report and exit code, nothing pre-interpreted - because WPScan's own exit codes and `scan_aborted` text ARE the answer (not WordPress, blocked by an edge, a scan cut short but still useful), not a retry-worthy transient failure the way a dropped nmap probe is. `cveFeed.wpscan_scan._classify`, extracted from the function a local run already used, is the one place - local or dispatched - that turns an outcome into a report or a classified `NotWordPress`/`Blocked`/`RuntimeError`, so a dispatched site is classified exactly as a local one would be. The project's WPScan API token travels in the `SentinelTask.target` for this one dispatch - the same blast radius it already has today, since it already leaves this process into a local subprocess's environment - and `agentapi.sentinel_dispatch.dispatch_or_none` gained a generic `redact_target` parameter for it: once the task reaches a terminal state, the token is scrubbed from the stored row (`{'token': '***'}`) so it does not sit in the plaintext `target` `JSONField` for the rest of the task's retention window. The weekly thorough pass (`run_thorough`, up to a 12-hour timeout by default) is not dispatched: `dispatch_or_none`'s bounded wait fits a per-scan stage, not a pass that may legitimately run for hours.

**OpenVAS dispatch does not use `dispatch_or_none` at all**, because a GVM task can legitimately run for up to 24 hours per host (`max_hours()`, `CVENGINE_OPENVAS_MAX_HOURS`) - far past any bounded wait a scan stage can afford. Instead, `cveFeed.openvas_scan.tick` (the same beat step that already polls a local `gvmd` task over many 15-minute ticks) tries every due, opted-in project (`sweep_links()`/`next_batch()`, the same host selection and resolve/IP-exists guard a local run already uses) against `agentapi.sentinel_dispatch.any_scanner_for(project, 'openvas')` before ever opening a local GMP session; a project with no eligible Sentinel pays for nothing beyond that one query. When a Sentinel is eligible, `dispatch_to_sentinel` creates a `SentinelTask` (kind `openvas`) and an `OpenvasRun` that only tracks it (`OpenvasRun.sentinel_task`), under the exact same one-task-at-a-time constraint a local run already enforces; later ticks call `poll_sentinel` instead of the local `poll`, which asks the `SentinelTask`'s own status and, once `done`, imports its reported results through `_apply_import` - the one storage path both a local run's own `import_results` and a Sentinel's report feed into, so neither is any richer or poorer a record than the other. `OpenvasSettings.sentinel_only` (Settings > OpenVAS and Administration > OpenVAS, App Admin only) refuses the local fallback entirely: with it on, a due batch with no eligible Sentinel right now is simply left due - tried again next tick, never scanned on this server - rather than ever opening a local GMP session; off by default, so an install that never sets it behaves exactly as before this toggle existed. A local run already in progress when the toggle is turned on is left to finish, not abandoned mid-scan.

**Keeping Sentinels fed.** `feed_sentinels` (`cveFeed.coverage_topup`) runs every minute and, when the work waiting for Sentinels is less than twice their live slots, runs the coverage top-up over the projects a live Sentinel covers, so a Sentinel working through its tasks has the next ones already queued instead of idling until the five-minute top-up. When no host is missing its first pass, the same run refreshes the stalest hosts instead (`refresh_for_sentinels`: the hosts assessed longest ago, none inside `CVENGINE_SENTINEL_REFRESH_GAP_HOURS`, default 6), filling the same Sentinel-scaled cap, so a Sentinel is never left with nothing to do. It does nothing without a live Sentinel. The caps on host assessments in flight (20 overall and 5 per project) rise to three per Sentinel slot (`cveFeed.host_assessment.caps`) while Sentinels are live, since an assessment waits on one for most of its stages.

**Failing kinds are withheld.** A Sentinel that fails the last three tasks of one kind (`failing_kinds` in `agentapi.sentinel_broker`, read from the tasks it finished, no state of its own) has that kind taken out of its effective capabilities for 15 minutes. `capacity_state` then finds no Sentinel for the kind, so the stage runs on this server straight away (or, for an internal host, fails at once, since there is never a local fallback). The first task after the cool-off is the one more try. The Sentinels page shows `withheld_kinds` with the retry time.

**Settings, updates and versions.** A Sentinel's settings (`name`, `network`, `profile`, `disabled_kinds`, `max_concurrent`, `self_update`) can be set on its machine or from cvENGINE, and the most recent change wins (`agentapi.sentinel_settings`); the heartbeat reply carries the effective values back. A Sentinel reports its client version and its host-side updater's state, and an administrator can ask it to update now; `self_update` is `off`, `manual` or `automatic`, with an instance default. Whether each Sentinel runs the current client is checked against the head of the Sentinel repository's branch (`agentapi.sentinel_version`, refreshed every six hours by `refresh_sentinel_version`, never while a page is built). See [AGENT-API.md](AGENT-API.md#sentinels-scan-stage-agents) for the fields. Finished, failed and expired `SentinelTask` rows are deleted after `CVENGINE_AGENT_TASK_RETENTION_DAYS` (default 30) by the weekly maintenance; the audit log keeps the trail.

## Where the AI is used

- Triaging findings into confirmed, likely, needs validation, likely false positive, or not applicable. Fixed rules keep hard evidence from being dismissed. A reply the validator rejects is sent back to the model once with the reason.
- Confirming CVE matches when auto-fire is on, planning **Validate now** checks, and re-triaging their evidence.
- Choosing nuclei template tags and severities from those the installed templates use.
- Drafting a nuclei template when none exists for a CVE.
- Writing detection checks for the CVEs attackers use, from feed text only, within a daily budget.
- The three-hour coverage review and scanner capacity tuning.
- Reading RDP login-screen screenshots, and suggesting local checks for matches no external check can settle.
- Report text on the bug bounty page.

The AI never writes severity, CVSS, KEV, or EPSS data. It can suggest a one-step severity change, which is shown but not applied. Set the provider as described in [DEPLOYMENT.md](DEPLOYMENT.md#ai-models).
