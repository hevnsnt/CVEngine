# Architecture

cvENGINE is one Docker Compose deployment. The server runs no scan tool: every scan runs on a Sentinel, and each install starts one beside the server (the built-in scanner), so nothing needs a second machine to begin with.

## Services

| Service | Role |
| --- | --- |
| `web` | Django app: the interface, the REST API, and the MCP server (Gunicorn) |
| `celery` | Four gevent workers: discovery, CVE feed, a one-at-a-time validation lane, and everything else |
| `celery-beat` | The schedules: feeds, certificate watch, hygiene, sweeps, AI reviews, and housekeeping (see [PIPELINE.md](PIPELINE.md#schedules)) |
| `db` | PostgreSQL 18 |
| `redis` | Job broker, locks, cache, and the memory queue |
| `proxy` | nginx, terminates TLS on 443 and redirects 8082 to HTTPS |
| `tailscale` | Optional (`COMPOSE_PROFILES=tailscale`): a `tailscaled` sidecar in the celery container's network namespace, so scans reach a tailnet (see [TAILSCALE.md](TAILSCALE.md)) |

The server image carries one scan tool, [nuclei](https://github.com/projectdiscovery/nuclei), pinned and built in a throwaway stage: the server keeps its template set current and reads and checks templates with it, and runs no scan with it. The scan tools live in the **Sentinel image** (the [cvENGINE-sentinel](https://github.com/hevnsnt/cvENGINE-sentinel) repository, pinned by digest in `scanner.lock.json`): [nmap](https://nmap.org), nuclei, [naabu](https://github.com/projectdiscovery/naabu), [testssl.sh](https://github.com/testssl/testssl.sh), [WPScan](https://wpscan.com/), [wafw00f](https://github.com/EnableSecurity/wafw00f), [bbot](https://github.com/blacklanternsecurity/bbot) (which installs [gowitness](https://github.com/sensepost/gowitness) for older discovery-time screenshots), [Kingfisher](https://github.com/mongodb/kingfisher) for secret detection, [sshamble](https://github.com/runZeroInc/sshamble) for the SSH host key check, [aardwolf](https://github.com/skelsec/aardwolf) for RDP login screens and [Playwright](https://playwright.dev)'s headless Chromium for web screenshots (kind `web_screenshot`, see [Web screenshots](PIPELINE.md#web-screenshots)). Every tool is pinned to a known-good version, so a rebuild does not change what a scan does. Only nuclei's templates, WPScan's vulnerability database, the badkeys blocklist and the CVE feeds refresh at runtime. The old reNgine scan engine and the Go tools it used (httpx, subfinder, katana, and others) are gone. The complete list, with versions and licenses, is on the About page and in [THIRD-PARTY.md](../THIRD-PARTY.md).

### The Live screen's cache

**Stage 0: shared snapshots.** What the Overview polls is cached in the shared Redis cache, not in each web worker, by *scope* rather than by user (`cveFeed/snapshot_cache.py`). The key is a hash of the project ids the request runs under (an App Admin hashes every project and carries an `all` marker), plus the selected project and organization, so two members of one project share an entry and different scopes never do. A snapshot is `{payload, etag, at, revision}`: fresh for 10 s (the headline and ticker counts, `cve:snap:stats:*`, `cve:snap:discovery-counts:*`), 5 s (the graph version), 2 s (graph-live; the running and queued scan counts of the headline poll are read fresh each time), and kept three times that to serve while one request refreshes it. A stale or missing entry is rebuilt by the request that wins a short lock (`cache.add`); the others serve the stale copy, or wait up to 2 s on a cold key. `bump_stats_revision` (a finding was closed) stores a new revision in the cache and every entry older than it is stale. A cache that does not answer never breaks a view: the answer is computed directly. The ETag of an endpoint is derived from the snapshot (computed once when it was built, never from the clocks in the body), so a `304` does not rerun the walk. nginx compresses JSON, scripts and styles (`config/nginx/rengine.conf`).

**Cost-proportional freshness and one shared host list.** The headline and ticker snapshots (`stats`, `discovery-counts`) are kept fresh for ten times what their last computation took (at most 120 s, never less than the 10 s above), so a computation that takes eight seconds on a busy host is not repeated every 5 s by the refresher. Every write that moves a number on them drops them at once with a revision bump after commit (`snapshot_cache.bump_on_commit`): a finding or match closed or reopened, a scan that ended, a host or target deleted, archived, restored or moved, a project deleted. The collapsed host list (one row per host, `counts.rep_ids`) is read once per computation, and the snapshots of one scope that are being built share it through a snapshot of their own (`host-reps`, `counts.snapshot_rep_ids`, 5 s, not stretched by the cost rule: the live host count is never more than about 10 s old), so the headline counts, the ticker counts and the graph cost one collapse, not three to seven. A request that is not building a snapshot always reads the database. The graph payload of one version is built by one caller (`views.cached_graph`: a lock; the others wait up to 10 s, then are served the last good graph marked `stale: true`; the refresher never waits), not by every open graph at once.

**The refresher (stage 1).** A poll should almost never compute. Every Live poll registers its scope as *hot* for a minute (`CVENGINE_LIVE_HOT_SECONDS`): the scope's key, the project ids the request runs under, and the parameters it was asked with, kept in one cache entry (`cve:snap:hot`, at most 500 scopes and 24 per user: the first registered keep their place, so one member cannot fill the registry). Only an organization that actually narrowed the projects is part of a scope, and a `?domain=` or `?scan=` that names nothing the caller may see is answered as before but never registered, so a made-up parameter cannot mint scopes. Each recipe stores the project ids it runs under (a known limit: a user with very many projects makes a large registry entry). A celery beat entry (`cvengine-live-refresh`, written by beat itself at each start from `CVENGINE_LIVE_REFRESH_SECONDS`, 5 s) runs `refresh_live_snapshots` on `live_cache_queue`, which only the celery container's classic worker consumes (its own queue, so a long sweep ahead of it in another queue never blocks it, and not on the discovery, feed or validation workers, whose slots scan work holds for hours; the number of workers is capped at four for memory). If a refresh finds no free slot it expires after three intervals and the Live screen computes on request until the next one runs. Each run recomputes, oldest first, the hot scopes' snapshots that are within one interval of going stale (`cveFeed/live_refresh.py`), stores them under the key a request would have used (`by: refresher`), pre-builds a graph payload whose version moved (kept `GRAPH_CACHE_SECONDS`, 30 s, like a request-built one), and writes a heartbeat. A request that finds a refresher-made snapshot serves it even past its freshness window, for at most the longer of three times the window and three refresher intervals, while the heartbeat is no older than the longer of 15 s and four intervals (with `CVENGINE_LIVE_REFRESH_SECONDS=60` a graph-live snapshot can therefore be served at about 180 s; with the default 5 s, at about 15 s, and normally far fresher because the refresher renews it every interval); it computes (single flight, as in stage 0) only when the cache is cold, when a finding was closed (`bump_stats_revision`, so the person who closed it sees it at once), or when the refresher has stopped. The running and queued scan counts of the headline poll are still read on every poll (a few cheap counts). `CVENGINE_LIVE_REFRESH=0` turns it all off. The refresher never touches a target; it only reads the database and writes the cache.

**What it costs the classic worker.** The celery workers are gevent pools whose PostgreSQL driver does not yield, so every query of a refresh holds the worker's other tasks (notifications, WPScan, testssl, certificate transparency lookups, the worker inspection of the status page) for its duration. The refresher is therefore kept small on purpose: a run has a budget of at most 3 s and at most half an interval (checked between scopes, so one slow query can overshoot it), it takes the oldest snapshots first so every hot scope is served over a few runs, yields to the worker between scopes, leaves a scope that is not due alone (and graph-live of a scope nobody has polled for about 35 s), takes a token lock and never deletes one a later run holds, and **skips the whole run** when 3 or more refreshes already wait for a slot, when the classic worker's other queues hold 100 or more messages (a bulk certificate transparency add, say), or when the previous run overran its budget. Skips and overruns are counted (`skipped`, `overran` in `system.live_cache.polls`, `last_run`). A skipped or expired refresh costs only freshness: polls compute on request as in stage 0, and while the classic worker is down the beat messages expire after three intervals instead of piling up. **If the classic worker looks starved (a late notification, WPScan or testssl, the status page saying the classic worker is missing), set `CVENGINE_LIVE_REFRESH=0` and restart beat and the web workers first.**

**Tenancy.** The refresher runs each scope inside the project ids stored with it (`tenancy.scope`, no user) and first recomputes the scope hash from them and the stored parameters: a recipe whose hash no longer matches (a project was created under an App Admin's all-projects view) is dropped, so a payload is never written under a key whose scope did not compute it. A user who loses access hashes a different set of ids on the next poll and reads another key; nothing in the cache is addressed by user.

**The per-user project list.** The three queries that resolve which projects a user may see (`roles.allowed_project_ids`) were run for every poll of every open tab. For the four Live polls only (`GET`, `tenancy/membership_cache.py`), the answer is kept per user for `CVENGINE_AUTH_CACHE_SECONDS` (15, at most 30). It is invalidated, not only expired: saving or deleting a project membership, an organization membership, a project or an organization stores a new epoch in the cache (`tenancy/signals.py`: once when the row is saved or deleted and again when the transaction commits), and a cached list is used only with the current epoch, so revoking access takes effect on the next poll in every worker. What bypasses the signals (raw SQL, a bulk `update()` of `Project.org`) takes effect within the TTL. An App Admin is never cached, and every other request, any method, reads the list fresh.

**Seeing it.** For an App Admin, `get_system_status` and `GET system/status` carry `system.live_cache`: whether the refresher is `running`, `silent` (a note when people are on the screen) or `off`, its interval, the hot scopes, its last run, and this hour's and the previous hour's counters (`hit`, `stale`, `miss`, `waited`, `refreshed`, the share served from the cache, and the same per snapshot). While the refresher runs, `miss` should be close to zero.

## Sentinels

A Sentinel is a scanner a person runs on any machine they control, to add scan capacity and to reach private networks: it registers itself as an `Agent` (`kind='scanner'`), pulls scan-stage work off a project's queue, runs it, and reports typed, clipped results back. It is exactly as untrusted as any other agent (see [TENANCY.md](TENANCY.md) and [AGENT-API.md](AGENT-API.md#agents-and-assigned-work)): nothing it reports is ever executed or built into a command. It runs thirty-six kinds of scan-stage work (`SentinelTask.KINDS`, which is the contract's `kind_since`; the full list with the tool behind each is in [SENTINELS.md](SENTINELS.md#what-a-sentinel-runs)): the ten of contract version 1 (`nmap`, `naabu`, the three nuclei passes, `testssl`, `nmap_udp`, `wpscan`, `openvas`, `discover`), `waf` (version 2) and twenty-five more of version 3, among them `bbot_discovery` (streamed), `web_screenshot`, `secrets_scan`, `ssh_probe` and the in-process probes (`http_probe`, `route_probe`, `hygiene_check` and the rest) that carry a scope policy the Sentinel enforces at every hop. Each is a capability the Sentinel declares, plus `network:internal` when it sits inside a private network (the server grants that one, a Sentinel's own claim is ignored). The contract itself (`kind_since`, targets, results) lives in the scanner library and is read from the installed copy pinned in `web/requirements.txt`, not kept in this repository. The result shapes and limits for each kind are in [AGENT-API.md](AGENT-API.md#sentinels-scan-stage-agents); this section is the design.

**Internal networks.** A project administrator can declare a private network internal to a project (`cveFeed.models.InternalRange`, `projects/{slug}/internal-ranges`). The row is the only opt-in, and it changes exactly one thing: addresses inside it may be added as that project's targets (`agentapi.services._expand_target`). `targetApp.target_types.is_scannable_ip` is deliberately unchanged, so every local scanner still refuses those addresses; `sentinel_only_target` names them, and discovery is never queued for them (the work conductor skips them, a hand-started scan is a 409, `run_pipeline` refuses one that slipped through). Work on an address of a declared range is also claimable only by a Sentinel that holds the `network:internal` capability, which only the server grants (`Agent.network`, set from the enrollment or by an administrator, never from what the Sentinel claims; an outside Sentinel cannot reach it and would report an empty result as clean). **Scanning them.** `cveFeed.internal_scan` is the one pipeline for such a target, and every step in it is a `SentinelTask` for a Sentinel that holds `network:internal`: the host record for the address (no network access), an nmap fingerprint, a TLS audit of each TLS port found, the UDP exposure sweep, the nuclei technology pass, WPScan of the sites that pass tagged as WordPress, then CVE correlation and the AI-targeted nuclei pass, each the external pipeline's own function with only the execution seam changed. There is no local fallback: when no such Sentinel answers, the scan fails and says so, and the next sweep tries again. A scan is queued by starting one on the target by hand (the response says `internal: true`) or by the daily `internal_scan_sweep` (every target without a clean scan in `CVENGINE_INTERNAL_SCAN_DAYS`, default 7, or with a failed stage after a one-hour backoff, at most `CVENGINE_INTERNAL_SCAN_MAX` per run, only in a project where a live internal Sentinel exists). Stages that run from this server directly (route checks, probes, hygiene, database exposure, screenshots) never run for these hosts. Every local scanner (`run_nmap_xml`, `run_naabu`, `stream_nuclei`, `run_testssl`, `run_wpscan_process`) calls `target_types.refuse_local`, which raises while an `internal_scope` is active, so a stage that forgot its Sentinel seam fails loudly instead of connecting to a private address from this server. OpenVAS reaches a declared internal network through its own opt-in sweep: the project's internal targets are a batch of their own (`openvas_scan.internal_batch`), dispatched only when an internal Sentinel that runs the GVM stack exists, and never mixed with the external batch. WPScan runs through a Sentinel on the sites the Sentinel-run technology pass tagged as WordPress (`wpscan_scan.run_wpscan(internal=True)`: this server sends no WordPress probe or plugin lookup of its own, there is no local fallback, and no thorough pass is queued because it would run from here). **Finding the hosts.** `cveFeed.internal_discovery` sweeps a declared range for live hosts: one `discover` `SentinelTask` per /24 chunk (target `{cidr}`, claimable only by a Sentinel that holds `network:internal` and declares `discover`), a Sentinel-side ping sweep, and each answering address added as a project target by the ordinary `add_entries` (no discovery from this server) and scanned by the internal scan driver. The server keeps an address only if it lies inside the chunk it asked about, and never deletes a host that stops answering. A chunk nobody answered is an error on the range (`last_discovery_error`) and the sweep is retried, never read as an empty network. The sweep task `internal_discovery_sweep` runs daily and queues each range not swept in the last `CVENGINE_INTERNAL_DISCOVERY_DAYS` (default 7), on demand with `POST projects/{slug}/internal-ranges/{id}/discover`, at most `CVENGINE_INTERNAL_DISCOVERY_CHUNKS` chunks per run (default 64, a /18; a larger range resumes where it stopped). IPv6 ranges are not swept.

**What dispatches.** Everything. Identity, registration, enrollment, task queueing and leasing, the dispatch point in the scan pipeline and the admin UI serve every kind, and every stage that touches a target hands its work to a Sentinel: the per-scan stages (the port and service stage, the nuclei passes, the TLS audit, the UDP sweep, WPScan, the web probes, the screenshots), the background sweeps (the full-port sweep, buckets, virtual hosts, subdirectory applications, suppliers, hygiene, SSH, secrets) and discovery. The weekly deep Nuclei pass and OpenVAS dispatch from their own tasks (below). No stage runs a scan tool or sends a request to a target from this server (`sentinel_dispatch.NEVER_LOCAL` holds every kind but `discover`, which is Sentinel-only by design).

**What a Sentinel's token and results can do.** A Sentinel's token has its own scope, `sentinel`: it reaches only the Sentinel loop (`sentinel`, `sentinel/heartbeat`, `sentinel/tasks/...`, `sentinel/template-policy` and its bundle) and answers `403` everywhere else, including `/mcp/`, so a token taken from a Sentinel's machine is not its administrator's token. It lasts 90 days and its own heartbeat renews the same token in place while under 60 days are left; a Sentinel that was off for longer is enrolled again. Its results are bound to the task: an nmap host, naabu address or nuclei finding for an address that was not dispatched is dropped (`sentinel_broker._bind_to_task`), because ports and findings are stored per organization and a Sentinel scoped to one project must not write another's. The result route takes up to 24 MB (its own nginx location and `DATA_UPLOAD_MAX_MEMORY_SIZE`; every other route 4 MB). A nuclei task on a Sentinel runs with `-etags dos` and the approved-template snapshot the server runs (`GET sentinel/template-policy` and `/bundle`), and a nuclei pass with a stored sign-in is never dispatched.

**The weekly deep Nuclei pass dispatches too, past the per-scan pipeline.** `weekly_deep_nuclei` (`cveFeed/tasks.py`) is a standalone Celery-beat task, not a stage inside `discovery.py`'s `_run_stages`: it paces one host at a time through the broad, unrestricted template set, independent of any particular scan. It builds its nuclei `stream` the same way the per-scan passes do, `agentapi.sentinel_dispatch.wrap_nuclei_stream(scan, 'nuclei_deep')`, the function needed no change, since it was already generic over `kind`; only `SentinelTask.KINDS` carries the `nuclei_deep` name and `sentinel_broker._CLEANERS` the matching result cleaner (the same one `nuclei_light`/`nuclei_targeted` already use, since a deep-pass finding has the identical shape).

**The testssl.sh TLS audit.** Unlike the per-scan stages, testssl's sweep (`cveFeed.tls_audit.sweep`) tests one `host:port` at a time, never a chunk, so `agentapi.sentinel_dispatch.try_testssl` dispatches a single target per `SentinelTask` (kind `testssl`). A Sentinel's report is testssl.sh's own raw finding items (`id`, `severity`, `finding`, `cve` - the four fields `evaluate()` reads), typed and clipped by a dedicated result cleaner, so no detection logic (CVE extraction, "proven" vs "may apply") is duplicated client-side: `evaluate()` reads the Sentinel's report. The audit never runs on the server (`NEVER_LOCAL`): with no scanner able to take a target it stays due.

**The UDP exposure sweep.** Unlike every other dispatched kind, a Sentinel's `nmap -sU` report travels as nmap's own raw XML text (`SentinelTask` kind `nmap_udp`), not pre-parsed JSON: UDP's state vocabulary (`open|filtered`, extraports summarisation) and the NSE script output the sweep's own product identification reads are read correctly only by `cveFeed.nmap_scan.parse_xml`, so that one function - local or dispatched - is the sole place either kind of run's XML is ever turned into a record. Because this function also reads XML a remote agent reported, it refuses a custom ENTITY declaration outright before parsing (real nmap output never declares one) on top of `xmltodict`'s own default entity handling, which already blocks an external DTD/entity fetch - no new dependency, and it protects a local run's own XML parsing too, at no behavioural cost for a well-formed report.

The Sentinel's own GVM stack and GMP client, in the external `cvengine-sentinel` repository, run the `openvas` tasks this server dispatches (OpenVAS dispatch is described below); a Sentinel provisioned with the Light profile runs no such stack and never takes OpenVAS work.

Every dispatch attempt is visible in the AI activity feed, not just inferable from the Sentinels page's task counts: `agentapi.sentinel_dispatch.dispatch_or_none` logs one `run_check` activity line per `SentinelTask` ("Handed `kind` work for `host` to a Sentinel"), running while the wait is in progress and settled once it ends, naming the Sentinel and its outcome on success or a reported failure, or saying plainly that no scanner could take the work and the target stays due. This reuses the exact `kind`/`status` shape every other scan-stage line already uses (`cveFeed.activity.log`/`settle`), so it needs no change to the Overview or the Activity page: both already render any `run_check` line the same way.

A Sentinel's scope widens past one project: an organization-wide enrollment (`orgs/{slug}/sentinels/enroll`, an admin of that organization or an App Admin) covers every project of that organization, present and future, and an instance-wide one (`sentinels/enroll` with no project or org, App Admin only) covers the whole server. Both reuse the existing `scope: {orgs, projects, hosts}` shape unchanged for the first case (`agentapi.agent_scope.project_slugs_in_scope` already resolved `scope.orgs` dynamically at claim time, so this needed no new resolution logic) plus one new `instance: bool` flag for the second, checked only where scope is authorised (`agentapi.agent_scope.authorise`) and resolved (`project_slugs_in_scope`).

**The client is downloadable, in its own repository.** There is no per-OS package: the Sentinel client is a small, standalone Docker Compose service at [hevnsnt/cvengine-sentinel](https://github.com/hevnsnt/cvengine-sentinel) (its own Dockerfile, `docker-compose.yml` and `client/` package, kept separate from this codebase so provisioning a Sentinel never needs a clone of the full CVEngine source), and it runs identically on Linux, macOS and Windows hosts with nothing OS-specific to build or ship. Provisioning is one copy-pasteable blob rather than typing separate fields into a Sentinel's config: the Sentinels page's **Provision** button (or `?format=blob` on `sentinels/enroll`) base64-encodes `generate_enrollment`'s own payload (`agentapi.sentinel_broker.encode_enrollment_blob`; no new crypto, no custom framing, still a plain bearer token over HTTPS) into `CVENGINE_SENTINEL_BLOB`, which the client decodes once, trades for its own token at `sentinels/bootstrap`, and persists (0600, in a named Docker volume) so a restart never needs the blob again. The client's own main loop (`client/daemon.py` in the Sentinel repository) long-polls `sentinel/tasks/next`, accepts, runs the matching tool against only the task's own typed `target` (a fixed argv list built from a defensively validated address/host list, never a shell command: see that repository's `client/tools.py`), parses the tool's own output into the exact typed shapes `clean_result` expects, and reports back; a concurrent heartbeat thread matches `agent_broker.HEARTBEAT_SECONDS`, and SIGTERM finishes or releases in-flight tasks rather than abandoning them. The Sentinel image's own Dockerfile pins every scan tool (nmap, naabu, nuclei and its template bundle, testssl.sh, WPScan, wafw00f, bbot, Kingfisher, sshamble, Playwright's Chromium); the server image pins only nuclei (and the Go toolchain that builds it), so the two repositories no longer repeat each other's pins. Nothing in this repository watches the Sentinel's pins (`scripts/check_tool_versions.py` checks the server's own); the About page lists both sets and `tests/test_about_page.py` fails when a tool pinned in either Dockerfile is missing from it or listed at another version. The Provision form's **Where it runs** (external or internal) and **Size** (full or light) choices write the matching `.env` lines into the returned `setup` block: `CVENGINE_SENTINEL_NETWORK=external|internal` (the enrollment records the choice, and for an internal Sentinel the server grants `network:internal`; the line only tells the client where it sits) and `COMPOSE_PROFILES=openvas` for a Full Sentinel, which also runs the OpenVAS stack; `./setup.sh --light|--full --external|--internal --blob '...'` is the same as one command. The two choices can also be changed later from cvENGINE (below).

**Dispatch or wait**, the one design decision that matters: before a stage hands work over it asks `agentapi.sentinel_broker.capacity_state` whether a live, eligible, in-scope Sentinel exists for the project with the right capability (the built-in scanner counts as the last resort, [SENTINELS.md](SENTINELS.md#the-built-in-scanner-is-the-last-resort)). With none, the stage does not run the tool here and does not fail: it raises `ScannerUnavailable`, records nothing, and its targets stay due until a scanner is back ([SCANNER-ARCHITECTURE.md](SCANNER-ARCHITECTURE.md#the-scanner-offline-reading)). When one exists, the stage creates a `SentinelTask` and waits under three budgets: a short `CVENGINE_SENTINEL_CLAIM_TIMEOUT` (default 8s) for a Sentinel with a free slot to claim it; a queue wait, `CVENGINE_SENTINEL_QUEUE_TIMEOUT` (default 300s), when every live, eligible Sentinel is at its `max_concurrent` (a Sentinel at its limit is busy, not missing, so the task waits for a slot, and the wait ends early if the last live Sentinel goes away); and, counted from the moment a Sentinel claims the task, a completion budget that is a ceiling per kind (nmap 900s, naabu 1020s, light nuclei 900s, targeted 1800s, deep 3600s, testssl 600s, UDP 900s, WPScan 1800s, discover 1200s; OpenVAS follows `CVENGINE_OPENVAS_MAX_HOURS`) plus an allowance for each target beyond the first (`CVENGINE_SENTINEL_DISPATCH_TIMEOUT`, when set, replaces every ceiling with one number). A stage that waits does not hold a Celery worker (`CVENGINE_ASYNC_STAGES`, [SCANNER-ARCHITECTURE.md](SCANNER-ARCHITECTURE.md#asynchronous-stages-queue-q4)). A running task's lease is kept by the Sentinel's heartbeat and lost after five minutes without one (the task is marked `expired`), and a Sentinel not heard from for three minutes is offline and offered nothing. On success the stage parses the typed result into the shape the tool's own output has and hands it to the persistence function (`cveFeed.nmap_scan.persist_inventory`, `cveFeed.naabu_scan.persist_open_ports`, or, for nuclei, a reconstructed result line run through the stage's own per-line loop). On a timeout or a failure nothing is recorded as done and the target stays due; it is never run here. A target inside a declared internal network is only ever a task for a Sentinel that holds `network:internal`.

**Egress.** The server sends no scan traffic, so Settings, Proxy (`cveFeed.egress_proxy`) applies to the built-in scanner only: the server hands it the proxy in its settings (`sentinel_settings.builtin_vantage`), and nuclei, WPScan, testssl.sh, wafw00f and bbot there go through it while nmap, naabu and the other raw-socket tools stay direct. An external Sentinel keeps its own egress and is never sent the proxy; see [Pipeline](PIPELINE.md#keeping-scans-fast-and-polite).

**WPScan dispatch keeps classification server-side, not tool-shaped like nmap/naabu/nuclei.** A Sentinel runs WPScan and reports its raw, unclassified outcome - `{report, returncode, stderr_tail}`, the process's own JSON report and exit code, nothing pre-interpreted - because WPScan's own exit codes and `scan_aborted` text ARE the answer (not WordPress, blocked by an edge, a scan cut short but still useful), not a retry-worthy transient failure the way a dropped nmap probe is. `cveFeed.wpscan_scan._classify`, extracted from the function a local run already used, is the one place - local or dispatched - that turns an outcome into a report or a classified `NotWordPress`/`Blocked`/`RuntimeError`. The project's WPScan API token travels in the `SentinelTask.target` for this one dispatch - the same blast radius it already has today, since it already leaves this process into a local subprocess's environment - and `agentapi.sentinel_dispatch.dispatch_or_none` gained a generic `redact_target` parameter for it: once the task reaches a terminal state, the token is scrubbed from the stored row (`{'token': '***'}`) so it does not sit in the plaintext `target` `JSONField` for the rest of the task's retention window. The thorough pass (mixed plugin and theme detection, hours per site) is its own kind, `wpscan_thorough` (contract version 3), not a mode flag on `wpscan`: it has its own option set (the client's flag allow-list stays fixed per kind), its own time limit that travels in the target (`timeout_seconds`, 12 hours by default, `CVENGINE_WPSCAN_THOROUGH_TIMEOUT`, at most a day) and one task per project at a time (`wpscan_scan.run_thorough` keeps a Redis claim). It reuses the same result shape and `_classify`. The broker keeps the task's lease alive for that time plus the report grace and no longer (`sentinel_broker.max_runtime`), exactly like a streamed `bbot_discovery` run's own limit, so a Sentinel that is alive but never finishes still frees its slot and a lost one expires on the usual heartbeat rule. The server never runs either kind (`sentinel_dispatch.NEVER_LOCAL`): with no scanner able to take a thorough task, or none finishing it, the host stays `pending` and nothing is recorded as done.

**OpenVAS dispatch does not use `dispatch_or_none` at all**, because a GVM task can legitimately run for up to 24 hours per host (`max_hours()`, `CVENGINE_OPENVAS_MAX_HOURS`) - far past any bounded wait a scan stage can afford. Instead, `cveFeed.openvas_scan.tick` (the beat step that polls a Sentinel's OpenVAS task over many 15-minute ticks) tries every due, opted-in project (`sweep_links()`/`next_batch()`, the same host selection and resolve/IP-exists guard a local run already uses) against `agentapi.sentinel_dispatch.any_scanner_for(project, 'openvas')`; this server opens no GMP session and never runs a scan, so a project with no eligible Sentinel pays for nothing beyond that one query and its hosts stay due. When a Sentinel is eligible, `dispatch_to_sentinel` creates a `SentinelTask` (kind `openvas`) and an `OpenvasRun` that only tracks it (`OpenvasRun.sentinel_task`), one task at a time; later ticks call `poll_sentinel`, which asks the `SentinelTask`'s own status and, once `done`, imports its reported results through `_apply_import`. The add-on is off by default and costs nothing while off ([OPENVAS.md](OPENVAS.md)).

**Keeping Sentinels fed.** `feed_sentinels` (`cveFeed.coverage_topup`) runs every minute and, when the work waiting for Sentinels is less than twice their live slots, runs the coverage top-up over the projects a live Sentinel covers, so a Sentinel working through its tasks has the next ones already queued instead of idling until the five-minute top-up. When no host is missing its first pass, the same run refreshes the stalest hosts instead (`refresh_for_sentinels`: the hosts assessed longest ago, none inside `CVENGINE_SENTINEL_REFRESH_GAP_HOURS`, default 6), filling the same Sentinel-scaled cap, so a Sentinel is never left with nothing to do. It does nothing without a live Sentinel. The caps on host assessments in flight (20 overall and 5 per project) rise to three per Sentinel slot (`cveFeed.host_assessment.caps`) while Sentinels are live, since an assessment waits on one for most of its stages.

**Failing kinds are withheld.** A Sentinel that fails the last three tasks of one kind (`failing_kinds` in `agentapi.sentinel_broker`, read from the tasks it finished, no state of its own) has that kind taken out of its effective capabilities for 15 minutes. `capacity_state` then finds no Sentinel for the kind, so the stage waits for another scanner and its targets stay due (there is no local fallback for any kind). The first task after the cool-off is the one more try. The Sentinels page shows `withheld_kinds` with the retry time.

**Settings, updates and versions.** A Sentinel's settings (`name`, `network`, `profile`, `disabled_kinds`, `max_concurrent`, `self_update`, and from cvENGINE only the per-kind capability policy `kinds`: allow, deny or prefer, with a per-kind cap, `agentapi.sentinel_policy`) can be set on its machine or from cvENGINE, and the most recent change wins (`agentapi.sentinel_settings`); the heartbeat reply carries the effective values back (the policy as the older `disabled_kinds` list). A Sentinel reports its client version and its host-side updater's state, and an administrator can ask it to update now; `self_update` is `off`, `manual` or `automatic`, with an instance default. Whether each Sentinel runs the current client is checked against the head of the Sentinel repository's branch (`agentapi.sentinel_version`, refreshed every six hours by `refresh_sentinel_version`, never while a page is built). See [AGENT-API.md](AGENT-API.md#sentinels-scan-stage-agents) for the fields. Finished, failed and expired `SentinelTask` rows are deleted after `CVENGINE_AGENT_TASK_RETENTION_DAYS` (default 30) by the weekly maintenance; the audit log keeps the trail.

## Where the AI is used

- Triaging findings into confirmed, likely, needs validation, likely false positive, or not applicable. Fixed rules keep hard evidence from being dismissed. A reply the validator rejects is sent back to the model once with the reason.
- Confirming CVE matches when auto-fire is on, planning **Validate now** checks, and re-triaging their evidence.
- Choosing nuclei template tags and severities from those the installed templates use.
- Drafting a nuclei template when none exists for a CVE.
- Writing detection checks for the CVEs attackers use, from feed text only, within a daily budget.
- The advisor of the auto-tuner (a second opinion on the throughput settings, numbers only, every few hours; the deterministic controller tunes without it).
- Reading RDP login-screen screenshots, and suggesting local checks for matches no external check can settle.
- Report text on the bug bounty page.

The AI never writes severity, CVSS, KEV, or EPSS data. It can suggest a one-step severity change, which is shown but not applied. Set the provider as described in [DEPLOYMENT.md](DEPLOYMENT.md#ai-models).
