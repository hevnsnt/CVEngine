# cvENGINE 1.5.0: notes for the operator

What you need to know before and after you update from 1.4.2, in one place. The full account of each change is in [UPGRADE.md](UPGRADE.md#upgrading-to-150) and the [changelog](../CHANGELOG.md). The 1.4 notes stay in [1.4-OPERATOR-NOTES.md](1.4-OPERATOR-NOTES.md).

## Before you update

1. **Back up.** Copy `.env` (and your Compose env file, such as `.env.vps`) and `web/secret` somewhere safe, apart from the database dump ([DEPLOYMENT.md](DEPLOYMENT.md#backups)). The update takes its own dump just before it migrates.
2. **Check free disk.** About 14 GB where Docker keeps its images: the built-in scanner moves to an image pinned by digest, which is usually not on the host yet. The Update screen says it before you approve.
3. **Clear hand edits.** `git status --short` in the checkout must list nothing but `.env`: 1.4.2's update script runs the first press and stops on any changed tracked file. Commit it, or undo it with `git restore <file>`.
4. **Overlay check.** If you use your own Compose overlay (`CVENGINE_COMPOSE_FILES`), it must not give `POSTGRES_PASSWORD` to `web`, `celery` or `celery-beat`, publish `web`'s port 8000, or set `CVENGINE_TRUSTED_PROXIES` to a range. The update refuses the first, and its client address check warns about a range; the other two would let other containers choose the client address ([DEPLOYMENT.md](DEPLOYMENT.md#client-addresses-behind-a-host-proxy)).

Then update as usual: the Update button, `scripts/update.sh` or automatic deployment. Afterwards, update your external Sentinels from the Sentinels page.

## What the update does by itself

- **Renames to cvENGINE names.** `.env` lines move to `CVENGINE_*` (backup `.env.pre-cvengine-rename`), the certificate files, the proxy configuration (`config/nginx/cvengine.conf`) and the network get the new names. The Compose project, the volumes, the database and its owner role keep their names ([The rename](UPGRADE.md#the-rename-to-cvengine-names)).
- **New image.** `web`, `celery` and `celery-beat` run CPython 3.14.10 (no more garbage collector crashes), as uid 10002 with no capabilities, from the image's own copy of the source. A one-off `ownership` service hands the volumes and `web/secret` to that account ([UPGRADE.md](UPGRADE.md#the-server-runs-as-its-own-account-from-its-own-copy-of-the-source)).
- **Least privilege database role.** The server connects as `cvengine_app`, which can only read and write the application's tables. Only the one-off `migrate` service holds the owner's password. `db` and `redis` move to `data_network` and are recreated once ([Database roles](UPGRADE.md#database-roles-the-server-no-longer-runs-as-the-database-owner)).
- **Its own addresses.** The update finds this server's public addresses and writes `CVENGINE_SELF_ADDRESSES` to `.env` as a managed line, so the server never scans itself, even behind Cloudflare. A value you set is never changed; `CVENGINE_SELF_ADDRESSES_DETECT=0` turns the detection off.
- **Checks the proxy.** `nginx -t` on the new configuration before anything is migrated, and a real request through the proxy after the restart. A failure puts the previous version back or keeps the maintenance page up; it never reports done while the site answers 502.
- **Sizes the database** for the host's memory, re-enables the accounts the old input guard disabled, and generates the upstream secret a host proxy needs.

## The one step it cannot do: a host proxy in front

If a web server on the host (nginx, often behind Cloudflare) terminates TLS and forwards to the bundled proxy, every visitor arrives as one address until that web server sends the install's secret. After the update App Admins see a notice with the two lines to install, a **Copy** button and **Check again**. The same lines:

```bash
(umask 077; scripts/client-address-check.sh --snippet | sudo tee /etc/nginx/snippets/cvengine-client-address.conf >/dev/null)
```

Include the file in the `location` that proxies to cvENGINE, then `sudo nginx -t && sudo systemctl reload nginx`. The secret is `CVENGINE_UPSTREAM_SECRET`. With a separate Compose env file (`CVENGINE_COMPOSE_ENV_FILE`, such as `.env.vps`) the proxy loads the value in that file, not the one in `.env`; `--snippet` reads the file Compose reads, so use it rather than copying the value by hand. With nothing in front of the bundled proxy there is nothing to do. Details: [Client addresses behind a host proxy](DEPLOYMENT.md#client-addresses-behind-a-host-proxy).

## What changes for scanning

- **Internal Sentinels take only internal work.** A Sentinel inside a private network is handed a task only when every host it names is inside a declared internal range. External work goes to external Sentinels. There is no opt-out ([SENTINELS.md](SENTINELS.md#external-or-internal-full-or-light)).
- **Internal network page.** When a project has a declared internal range or an internal Sentinel, the left rail shows **Internal network** after Hosts: the internal hosts, each range with its last sweep and Sentinel, and their open findings.
- **Internal hosts show their name**, written `name (address)`, from the reverse DNS, mDNS or NetBIOS name the Sentinel inside the network reads. The address stays the identity.
- **Printers are scanned gently.** No Sentinel tool sends data to TCP 515 or 9100 to 9107 on any target, and a host whose fingerprint shows a printer gets only the read-only web pass on 80, 443 and 631 and CVE correlation. OpenVAS never scans one ([SENTINELS.md](SENTINELS.md#internal-networks)).
- **This server is never scanned.** Its own names are always excluded and its origin addresses are denied for every project and Sentinel. A shared CDN address (Cloudflare's edge, for one) is never denied, so sites behind the same CDN are still scanned.
- **Signed-in scanning on external Sentinels** is opt-in per sign-in: **Also send it to my external Sentinels** on the sign-in form. It needs the matching Sentinel client ([Stored sign-ins on external Sentinels](SENTINELS.md#stored-sign-ins-on-external-sentinels)).
- **Direct Send** on Microsoft 365 is reported only after a live SMTP test found it open, never from the MX record alone.
- **Greenbone images follow `stable`** on a Full Sentinel, pulled at every Sentinel update; they are no longer pinned by digest ([OPENVAS.md](OPENVAS.md#images-pins-and-updating)).

## Bans and Sentinels

- **The owner and live Sentinels are not banned silently.** When the input guard would ban an address that, in the last 24 hours, carried a signed-in App Admin session or a live Sentinel's calls, it raises an App Admin notice instead. Other bans work as before; **Settings, IP allowlist** lists them with **Lift ban**.
- **A banned Sentinel backs off.** A 403 that refuses an address carries `X-CVEngine-Refusal`. A current Sentinel reads it as a ban, not a dead token: it waits 30 seconds, doubling up to 10 minutes, and keeps running. Do not re-enroll it; lift the ban.
- **Screenshots on Ubuntu 24.04 and later.** AppArmor 4 blocks the screenshot browser's sandbox. The built-in scanner needs `config/apparmor/cvengine-scanner` and `docker-compose.apparmor.yml` ([Screenshots and AppArmor](DEPLOYMENT.md#screenshots-and-apparmor)); an external Sentinel's `install.sh` loads its own profile, or run `sudo scripts/apparmor.sh install` in its checkout.

## New settings worth knowing

| Variable | Default | What it does |
| --- | --- | --- |
| `CVENGINE_AI_MONTHLY_BUDGET_USD`, `CVENGINE_AI_DAILY_BUDGET_USD` | unset (no limit) | Stop AI spend when the dollar budget is reached, until the next UTC month or day. Settings, AI model wins over `.env` ([CONFIGURATION.md](CONFIGURATION.md#ai-budget)). |
| (Settings, AI model) **Use the bulk model for high-volume stages** | on | Triage, validation plans, CVE detection records, Nuclei targeting and the finding review use the provider's cheapest current model. Turn it off to keep every stage on the main model. |
| `CVENGINE_HOSTED_LICENSE_SAFE` | unset | `1` on a hosted service that sells cvENGINE: WPScan, Shodan InternetDB, the Internet Archive, Zero Wire and Cert Spotter are turned off ([Hosted license-safe mode](CONFIGURATION.md#hosted-license-safe-mode)). A self-hosted install leaves it unset. |
| `CVENGINE_SELF_ADDRESSES` | written by the update | This server's origin addresses, denied as scan targets. |
| `CVENGINE_DB_ALLOW_OWNER_FALLBACK` | off | `1` runs the server on the owner role when `cvengine_app` cannot be used. |
| `CVENGINE_LOG_MAX_FILE`, `CVENGINE_LOG_MAX_SIZE` | `5`, `50m` | Docker log rotation of every container. |

Every renamed variable is in [CONFIGURATION.md](CONFIGURATION.md#renamed-in-150).

## Keeping it safe

- **`make rotate-secrets`** rotates the database passwords, the app role, Redis, the field key and the Django secret in the right order and proves the site works afterwards. `ARGS=--dry-run` prints the plan. Everyone is signed out and two-step recovery codes must be made again ([Rotating secrets](CONFIGURATION.md#rotating-secrets)).
- **`make db-backup-schedule`** keeps a nightly dump in `backups/db` for 7 days, and **`make restore-check`** restores the newest one into a throwaway database to prove it works ([Nightly dump](DEPLOYMENT.md#nightly-dump)).
