# AI model usage

Once an AI model is connected, the account menu shows **AI Model Usage** (superusers), refreshed every 15 seconds. It records every completion cvENGINE requests from Anthropic, OpenAI, OpenRouter, Ollama, vLLM, or LM Studio:

- calls per day and per pipeline stage, including failed ones with a safe error category (a stage whose call the AI reviewer container makes, [AI-REVIEWER.md](AI-REVIEWER.md), is recorded when the container posts the answer, with the counts it reports for each call) (choose 24 hours, 7 days, or 30 days). The stages are `finding_triage`, `finding_triage_repair` (the second call after a rejected triage reply, so one triage can be two rows), `cve_confirmation`, `validation_plan`, `local_check_suggestion`, `cve_detection`, `nuclei_tag_selection`, `nuclei_targeting`, `template_generation`, `template_validation` (the fixture and the second-pass review of an AI-written template, [AI-REVIEWER.md](AI-REVIEWER.md#ai-written-templates-validated-by-the-system-never-by-a-person)), `assessment_review` (older rows: the three-hour assessment review is retired), `performance_review` (older rows: the three-hour capacity check is retired), `autotune_advisor` (the auto-tuner's advisor, capped by `CVENGINE_AUTOTUNE_AI_MAX_PER_DAY`), `rdp_screenshot`, `finding_review` and `operations_check` (the reviewer container's own two jobs, reported by the container after each call, a refusal included), `report_writing`, and `connection_test`; every call the product makes names its stage (`web/reNgine/ai_prompts.py` lists them and a test checks every call site), so `unspecified` appears only on older rows. The page shows the top 30 stages, the top 100 models, and the last 50 calls, a failed one with the provider's stop reason (`end_turn`, `max_tokens`, `refusal` ...) and a plain sentence for why, such as "The model answered with no text (it stopped at the token limit)" with what to change (raise `CVENGINE_AI_MAX_TOKENS` or lower Reasoning). **Call stages** also says which model answered each job ("Answered by": each model with its successful calls out of its calls, by the model the provider named), so a Nuclei request refused by one model and answered by the haiku default shows both: the refused call and the answered call are two rows, each under its stage. The stop reason is a word the provider sends, never text of the answer;
- for each stage, why its attempts failed (the error category and the stop reason), with a cut-off reply that the automatic retry then answered listed apart as *cut off, answered by the automatic retry* (it is not a failure), next to the models that answered;
- the model that answered, input, output, and cache tokens as the provider reports them, and latency;
- connection health: a recent successful call, a recent error, an old verification, or not yet verified. Changing the provider, model, server, or key resets it.

## Replies that are cut off (`output_truncated`)

A model can run out of reply room before it finishes (stop reason `max_tokens` or `length`), most often a long answer (a detection record, a template draft) or a model that spends the room thinking. cvENGINE handles it without anyone tuning a limit:

- Every stage has its own **answer room** (a finding triage 400 on a self-hosted server and 2048 on Anthropic, a template draft 6144, a detection record 8192, others 1024 to 4000), and the model's **thinking room** (by **Reasoning**, 2048 for a model that thinks unless told not to) is added on top, so thinking cannot use up the answer's room.
- A reply that is cut off is asked **once more, for every stage**, with twice the answer room plus the thinking room. The hard ceiling is **32768 tokens**: the Settings value **Reply limit** (`CVENGINE_AI_MAX_TOKENS`) is the base the retry grows from, the retry may exceed it only up to the ceiling, and a limit already at the ceiling is not retried. Never a third request.
- Both requests are rows on this page under the stage, with the stop reason. The first is recorded as `truncated_retried` (it is not a failure) once the retry is made. A reply that is cut off again is a failure, `output_truncated`, on the stage's own daily budget, and only these make the **AI calls are failing** alert, which names the stage. The next step then is to lower **Reasoning** for the model or choose one that thinks less, not to raise a limit.
- A CVE whose detection record the model cannot write is asked again after 6 hours, 1 day, 3 days and 7 days, then not again until the CVE changes or an administrator gives guidance; the record says *could not author, will retry after N hours*.

## Cost estimates

An App Admin enters the price for each exact provider and model ID: USD per million input and output tokens, cache rates, an HTTPS source URL, and the date checked. cvENGINE multiplies it by the tokens used to show a **known estimated cost**. Calls without token counts, without a matching price, or with cached tokens but no cache rate count separately as **unknown cost**, so the estimate never pretends to be complete. It is an estimate, not an invoice, and local models still cost the hardware they run on.

## Spend levers

**Cost by stage and day.** `GET /cve/api/settings/ai/usage` returns `cost_by_stage_day`: for every day, stage and model, the calls, failed calls, input, output, cache-read and cache-write tokens, the cache-read share (cache read over every prompt token) and, when a price for that model is entered on this page, its dollars (`list_usd`). No price ships with cvENGINE: with none entered, the row shows tokens only.

**Prompt caching (Anthropic only).** The fixed part of each request, the stage's system prompt, is marked for Anthropic's prompt cache; the data of the call (the CVE, the finding, the host) is in the user turn and is never marked. Both request paths do this: the server's own requests (validation plans), and the AI jobs the reviewer container runs (triage, detection records, local checks, templates), which carry their stage's lifetime in the job's options. The container's own two jobs (finding review, operations check) were already marked and now report their cache tokens. A cached read is billed at a fraction of the input price and a write at a premium (1.25 times for the 5 minute lifetime, 2 times for 1 hour), so each stage has its own lifetime in `reNgine/ai_profiles.STAGE_CACHE_TTL`: 1 hour for `cve_detection` (its authoring task runs every 30 minutes), 5 minutes for stages that come in bursts, and off for `nuclei_targeting` (its system prompt carries a tag list that differs between scans), `autotune_advisor`, `connection_test`, `rdp_screenshot` and `report_writing`. A prompt shorter than the model's minimum (`ai_profiles.cache_min_tokens`: 512 tokens for Haiku 5.5 and Sonnet 5.5) is sent unmarked. Only Anthropic's own host (`api.anthropic.com`) is sent the marker; a gateway or proxy is sent the request as before. `CVENGINE_AI_PROMPT_CACHE=off` turns it off on both paths. The cache-read share in the cost view shows whether it is working.

**Message Batches (not built).** Half price on input and output, with results within 24 hours. Evaluated for the stages that could wait (the detection backlog, template candidates, the tuning advisor) and not built in 1.4.

## Privacy

Only App Admins can see the page, call its API (`GET /cve/api/settings/ai/usage`), or change prices. The ledger stores no API keys, prompts, responses, targets, or provider error bodies, and the settings API reports whether a key is set, never its value. History starts when the feature is installed, and rows older than 400 days (`CVENGINE_AI_USAGE_RETENTION_DAYS`) are written each Sunday to a file only a superuser can download, then deleted from the database. Archives are kept 365 days (`CVENGINE_LOG_ARCHIVE_DAYS`).
