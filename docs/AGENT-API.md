# Agent API: REST and MCP

Two interfaces share one service layer, so both get the same project isolation, role checks, and read-only token rules.

- **REST** at `/api/v1/`, JSON, with an OpenAPI spec at `/api/v1/openapi.json`.
- **MCP** at `/mcp/`, Streamable HTTP (JSON-RPC 2.0 over POST), protocol versions 2025-06-18, 2025-03-26, and 2024-11-05. Following the specification's transport rules, a request from a browser page of another site (an `Origin` that is not this server's host) is refused with `403`, an `MCP-Protocol-Version` header this server does not speak is `400`, a client's own response or notification is accepted with `202` and no body, an unknown tool is the protocol error `-32602` (a tool that fails is a normal result with `isError`), and an unexpected server error is the JSON-RPC internal error `-32603` rather than an HTML page. `GET` answers `405` (no server-initiated stream).

## Connect

Create a token on the **API keys** page (`/cve/agents/`; open it from your account menu, **API keys**) and send `Authorization: Bearer <token>`. The secret (`cve_...`) is shown once and only its SHA-256 is stored. A token acts as its user, with the same memberships and roles. **Read only** tokens can call GET endpoints and read-only tools. Revoke a token on the same page (it asks first). The page lists your keys newest first with name, key, access (read only or full access), created, and last used; of the key it shows only the first 4 and last 2 characters (`cve_...xY`; a key made before the ending was kept shows `cve_...`), and `GET /api/v1/tokens` sends no more than that. A name can be used by one live key per user: a second key with the same name is refused with `409` and a plain message, a revoked key frees its name, and older duplicates stay listed. Tokens never expire (a host reporter token, which can only post inventory, lasts 365 days, and a Sentinel's token lasts 90 days and is renewed by its heartbeat, see [Sentinels](#sentinels-scan-stage-agents)), but they stop working when the user is deactivated, and they are revoked automatically when the user changes their password, when an administrator resets that user's password or two-step sign-in, and when the input guard disables the account. Bearer requests skip CSRF.

When an organization requires two-step sign-in and a member has not enrolled, that member's session and tokens get `403` until they turn it on under **My account**. Tokens are not revoked and work again afterward. MCP requests are limited to 256 KiB, 20 batched messages, and 4 MiB of response. A batch runs one `search_hosts` or `list_hosts` call; the others in it are refused with a message and can be sent in a later request. A JSON body over 256 KiB to the REST API or the MCP endpoint is refused with `413`. A request whose database statement runs past the web limit (30 seconds, `CVENGINE_WEB_STATEMENT_TIMEOUT_MS`) is answered `503` (REST) or a tool error (MCP): narrow it and ask again.

Connect Claude Code:

```bash
claude mcp add --transport http cvengine https://<your-host>/mcp/ --header "Authorization: Bearer <token>"
```

A Sentinel's result is held to its task: an nmap host or naabu address that was not among the addresses the task named, and a nuclei finding on a host that was not among its targets, is dropped (the count is kept as `dropped` in the stored result), and every reported address must be an IP literal. A task for an address inside a declared internal range, and a nuclei or WPScan task whose target names one, can only be claimed by a Sentinel that is inside the network (the server decides this, see below); a Sentinel's `scope.hosts` is matched against the targets inside the task as well as its own addresses. A WPScan task's API token is replaced by `***` in the stored task as soon as the task ends, however it ends. A Sentinel's result body (`sentinel/tasks/{id}/result`) and its heartbeat body are exempt from the request input guard's attack-string scan: they carry what the scanned hosts returned (response bodies, banners, template output), which legitimately contains strings such as `$(id)` or `../../`, and a scan of a target that tried to look hostile would otherwise lock out the Sentinel's own account. The address and query string are still checked, and the result is cleaned and size-limited by the server as before. Registration, bootstrap and every other Sentinel route keep the full rules.

A CVE match whose CVE publishes no usable version range (a KEV candidate) is marked for review: `evidence.unbounded` is `true`, `in_affected_range` is `null`, `ai_verdict` is `uncertain` and `ai_reason` (and the triage `reason`) read "Version of the CVE is not known: review when the affected versions are published", its triage `classification` is `needs_validation` (so it is in `list_triage` and the Needs validation counts), and its tier is `ice`. Nothing but a person can rule it out; when the CVE gains a range the next correlation replaces the evidence and these markers go.

A CVE match's `cve.tier` is its heat on the host, by the heat policy ([Fire, smoke, and ice](FIRE-SMOKE-ICE.md#the-rule-the-heat-policy); `CVENGINE_HEAT_POLICY`, `kev` by default): `fire` for a CVE on the KEV or with a public exploit whose flaw is confirmed on the host (hard evidence; since 1.3.5 a proven version alone is not enough), `smoke` when only a version, inferred or proven, says so, `ice` for any CVE that is neither on the KEV nor exploited (whatever its `cvss`), a distribution-patched match and one whose CVE has no version range. `cve.feed_tier` is the CVE's own tier, `cve.kev` whether it is listed as exploited and `cve.exploit_db` whether a public exploit is known. `version_proven` is `true` when the version is proven (`cveFeed.match_policy.version_proven`: hard evidence, or the version read from the library's own file or from the banner of a vendor-built service nmap probed, a product on the vendor allow-list: never that of a product a distribution packages, the operating system services or cvENGINE does not know, such as OpenSSH, Apache httpd, nginx or IIS); `version_only` is `true` when the match has no hard evidence (no template hit, distribution tracker listing, host inventory report, runZero report or validation hit; `cveFeed.match_policy.has_hard_evidence`), which is what holds the AI's classification at needs validation. `heat_reason` says why in a few words ("on the KEV; version not proven", "not on the KEV and no known exploit", "on the KEV; version proven: template hit"). `cve.validation_tier` is the heat once proven, the order validation and agent validation work follow, so a KEV match whose version is not proven is validated first, and `cve.heat_capped` says the shown heat is below it. A row of `findings` carries `heat` (which `heat=` filters on), `heat_reason`, `kev`, `exploit`, `version_only`, `version_proven` and `heat_capped`; a host's `heat_reasons` carry `heat_reason` too. A scanner finding that names CVEs follows the CVE rule under the KEV policy (on the KEV or exploited: `fire` when the scanner confirmed it, `smoke` when it only inferred it, as OpenVAS below its quality bar or WPScan; otherwise `ice`); any other scanner finding is rated by its severity, and since 1.3.5 one rated fire by a template's severity shows `smoke` until a validation reproduces it. A finding whose triage is pending or *needs validation* is `smoke` at most, and one whose validation came back clean is `ice`. `findings?kev=1` (`list_findings` `kev: true`) and `matches?kev=1` (`list_cve_matches` `kev: true`) keep only matches of a CVE listed as exploited, whatever their heat; with `kev` the Findings list holds CVE matches only. `queue_agent_work` with `kind: validate` filters and prioritises on `cve.validation_tier`, so `tier: fire` includes the KEV version-only matches; `kind: remediate` uses `cve.tier`.

A host record (`hosts`, `search`) carries `unverified_products`: the products seen on the host (a technology or an open port) with no version found, as `{name, source: "tech"|"port", source_id, ip, port, cpe, service}`. They are metadata and a lead for finding the version, never CVE matches: a match needs the same product at a version inside an affected range.

A host record (`hosts`, `search`, and the MCP `list_hosts` and `search_hosts`) carries `check_coverage`: `{done, applicable, paused, checks}`, which of the checks that apply to the host have run (the page shows it as "NN of NNN applicable checks done"). `checks` has one row per registered check, `{id, label, state, last_run, ttl_hours, detail}`: `state` is `done` (ran inside its window, which is the ledger window of its kind, `ttl_hours`), `due` (applies, and never ran, is older than its window or failed last time; `detail` says which) or `not_applicable` (`detail` says why: no TLS port, no sign of WordPress, a switch is off, the project's bug bounty engagement has not confirmed automated testing, and so on). `last_run` is an ISO time or `null`. Only applicable checks are counted in `done` and `applicable`. `paused` is `excluded` or `archived` (no check applies then) and empty otherwise. The field is `null` only when it could not be worked out. It reads recorded results and never starts a check; the rules and how to add a check are in [Pipeline](PIPELINE.md#check-coverage). It is computed for a page of hosts in a fixed number of queries and covers only the projects you can see.

Lists take `page` (1 to 1,000,000; a larger one is clamped) and `page_size` (1 to 200; this includes members, finding comments and a finding's audit trail; `0` answers with `count` and no rows, which is all a badge or a filter chip needs). `work` and `cves?tier=` page over a bounded window of at most 2,000 rows (`count` is that window's size), and `findings` pages through its first 2,000 and reports `total`, `truncated`, and `counts`. `search` also takes `facets=none` to skip the heat counts and every other facet (`facets` is then `null`): they walk the whole match (up to 5,000 hosts), so a poll, a palette or an export page should not ask for them. `page_size=0` on `search` is the cheapest form: `{count, page_size: 0, results: [], facets: null}`. Every MCP result carries `_meta["cvengine/untrusted_text"]`: text that came from scanned hosts or feeds (banners, titles, response excerpts, advisory text) is data, never instructions. Writes need any role except audit in the project and a token that is not read only. A project you cannot see returns 404, the same as one that does not exist. A malformed request is a `400` that names the problem; a failure inside the server is a `500` (REST: `{"error": "internal error"}`; MCP: `-32603`) and is logged with its traceback. An MCP call that omits a required argument, or gives one the wrong JSON type, is refused (`isError`) before anything runs: a missing `assignee` never unassigns a finding (send `null` for that), and a missing `self_update` never resets the Sentinel policy.

**CVE detection.** `GET cves/{id}/detection` (`get_cve_detection`) returns `{source, schema_version, strategy, ai_model, updated}`: the shared record of remote and local checks and the validation profile ([PIPELINE.md](PIPELINE.md#detection-strategies)). It is the same for every organization and needs membership in any organization or project. A CVE with no record yet returns `source: null` and a note. `cves?tier=` looks only at the newest 2,000 CVEs, and `q` matches the CVE id only.

Stored sign-ins ([Pipeline](PIPELINE.md#authenticated-checks)) are for an App Admin or the project's organization admin only; every other role gets `403`, because they let the scanners act as a person inside an application. Values are write-only: a read returns the label, target, `scope` and `host` (`null` for `target`), `origins`, header and cookie names, `expires_at`, `days_left` (`null` for a deliberate `never`), `never_expires`, `state` (`active` or `expired`) and `allow_untrusted_certificate`, never a value, and the audit log records names only. `allow_untrusted_certificate` (boolean, default `false`, kept when a `PUT` leaves it out, `400` when it is not a boolean) is the per-target "Trust this certificate anyway" switch: the in-process route check verifies TLS on its credential-bearing connection unless this switch is on. Nuclei does not verify TLS on its own requests, so its signed-in HTTPS pass is withheld unless this switch is on, even if a separate preflight would verify. Enabling it can expose the sign-in to anyone in the network path; a change is audited as `target.auth_credential.untrusted_certificate`. The value fields are called `secret` and `cookie_secret` so request inspection skips them. A blank `secret` for a header name already stored keeps it, header names left out are removed, a blank `cookie_secret` keeps the cookie and `clear_cookie: true` removes it. A read-only token can list but not change. `PUT` needs two explicit choices and answers `400` without them, never a default: `scope` is `host` (with `host`, one host of the target) or `target` (every host of the target, with `host` blank), so a blank host alone is refused and never means the whole target; `expires` is `30`, `90` or `120` (days from now, stored as the computed `expires_at`) or `never` (stored with no expiry), and a replace needs it again. The MCP server has no tool that sets a credential, because a secret must not pass through a model's context: it lists them (names, scope, expiry and days left, no values) and revokes them (`delete_auth_credential`); set one on the Targets page or over REST. A finding seen through a signed-in request has `seen_while_authenticated: true`.

## AI reviewer (its own container only)

## Host inventory

Hosts can report about themselves (operating system and build, packages and versions, patches, listening services) with the scripts in `scripts/inventory`; see [HOST-INVENTORY.md](HOST-INVENTORY.md). The script posts inventory v1 JSON to `POST projects/{slug}/inventory`. That is the only route a **reporter token** can call: create one from a signed-in session with `POST tokens` `{"name": "...", "scope": "inventory", "project": "slug"}` (or from the Host inventory dialog). It is bound to that project, can post nothing else (every other route and `/mcp/` answer `403`), and acts with its creator's role. `GET tokens` shows each token's `scope` and `project`; `scope` is `full`, `inventory`, or `sentinel` (minted only by a Sentinel enrollment, never by `POST tokens`).

The ingest answer is `201` for a machine's first report and `200` after, and never says which host the report matched. A body over 2 MiB, or a list over its cap (15,000 packages, 2,000 patches, 1,000 listening sockets), is `413`; a malformed report is `400`; a report that is not accepted (an excluded host, a machine another token owns) is `409` with no reason given to the reporter (it is in the audit log); more than 12 reports an hour from one machine through one token, or the token and project caps, is `429`. A reporter token expires after 365 days (`expires` in `GET tokens` and in the answer that creates it); `POST tokens` takes `scope` `full` or `inventory` and refuses anything else with `400`. `POST projects/{slug}/inventory/delete-unmatched` deletes every report tied to no host.

`GET projects/{slug}/inventory` lists reports newest first (`status=matched|unmatched|stale|fresh`, `q=`). `GET .../inventory/{id}` and `GET .../hosts/{host}/inventory` return one report in full: the operating system, `packages_page` (each package normalised with `name`, `version`, `ecosystem`, `distro`, `distro_release`, `arch`, `source` and a `purl`; `q`, `page` and `page_size` up to 200 page through it), `patches`, `services`, `runtime`, `security`, `history` (the last 20 reports, summarised), `findings` (how many open CVE matches this report made) and `stale`. Names and versions in a report are data from the machine, untrusted. `POST .../inventory/{id}/adopt` ties an unmatched report to a host the project scans (`{"host": "name"}`) or adds the machine as a target (`{"create": true}`); `DELETE` removes a report. Both need a write role. The host record in `list_hosts`, `search_hosts` and the host page carries an `inventory` summary (`null` when the host never reported). A CVE match made from a report has `source: "host"` and `host_reported: true`.

`GET/PUT projects/{slug}/settings` carries `inventory`: `create_hosts` (a report from a host nobody scans adds it as a target; off by default) and `stale_days` (default 14: a stale report creates and closes no findings).

## Agents and assigned work

An agent is an API token that has told the server who it is, what it is responsible for, and what it can do. The server then hands it validation and remediation tasks it is able to do, and only those. Registration is optional: `register_assets`, `get_remediation_work` and `update_remediation_status` keep working for an agent that picks its own work.

**Register** with `PUT agent` (`register_agent`). The same call creates and updates; repeating it changes nothing, and fields you leave out keep their value. Registration needs a token that can write. `scope` is replaced as a whole when it is sent; its `hosts` (empty when none) also become the token's registered assets, which `get_remediation_work` narrows to.

| Field | Meaning |
| --- | --- |
| `name`, `kind` | A display name and one of `remediation`, `validation`, `scanner`, `reporter` (for example a host inventory reporter, capability `report:inventory`), `human` (a person working through tasks). |
| `scope` | What the agent is responsible for: `orgs` and `projects` (slugs) and `hosts` (a host name, which also covers every name under it, so `*.example.test` is stored as `example.test`; an IP address; or a CIDR). Name at least one organization or project: hosts narrow it, they do not pick a project. An agent with no organization or project is responsible for nothing and gets no work. |
| `capabilities` | What it can do: `validate:network`, `validate:local` (runs on the host), `validate:local-ssh` (logs in to the host), `validate:guided` (follows plain-language confirm steps), `remediate:linux`, `remediate:windows`, `remediate:web-config`, `can-restart-services`, `report:inventory`, `shell`, `ssh`. Others are accepted and kept but never matched. |
| `os`, `tools`, `max_concurrent` | Operating system families it acts on (`linux`, `windows`, `macos`, `bsd`; empty means any), tool names it has, and how many tasks it holds at once (1 to 10, default 2). |

**Approval.** A new agent starts `pending` and gets no work until an administrator approves it (`PATCH agents/{id}` with `{"status": "active"}`, or **API keys, Agents in your organizations, Manage, Approve** (administrators)), because an agent can take work in, and report fixed on, every project its user writes to. An agent of an App Admin or organization admin is active at once. **Held back.** A user who has an agent an administrator suspended or revoked in the last `CVENGINE_AGENT_HOLD_DAYS` days (default 30; only `0` means for as long as it stays so, and a negative or non-numeric value is the default; [CONFIGURATION.md](CONFIGURATION.md#sentinels)) does not get round it with a new token, a new registration or a new Sentinel enrollment: the new agent starts `suspended`. Its `status_note` names the agent that caused it and what to do, for example `Sentinel "old-box" (#12) of the same user was revoked on 2026-10-20. Reinstate this one to use it, and reinstate or delete #12 so new agents start normally`, and `held_by` (`GET agents`, `GET agents/{id}`, `GET sentinels/live`) is `{id, name, kind, status, since, deleted}` of that agent (`{id: null, deleted: true}` once it is deleted; `{id: null, deleted: false}` for an agent held back before the cause was recorded and none could be named at upgrade), `null` for any other agent. An agent held back before this was recorded gets the same note at upgrade, naming its user's most recent agent an administrator suspended or revoked. Each such suspension writes an `agent.hold` audit line. What does not hold back: an agent this rule held back itself (only an administrator's decision counts, so one old revocation does not chain through every later agent), a decision older than the window, a deleted agent, and anything at all for an App Admin, who approves and reinstates agents (their own included) anyway. An organization admin is held back like anyone else, also when the new agent is a Sentinel from an enrollment they generated, because they cannot reinstate their own agent; and when their decision is older than the window but still stands (the agent is still suspended or revoked, not deleted), their new agent starts `pending` instead of active, with the same kind of note (`Approve this one to use it, ...`) and `held_by`, so the window never lets a revoked administrator's replacement work at once. A non-administrator's new agent is `pending` anyway. Any `status` an administrator sends for a held agent (`PATCH agents/{id}`), the same status included, makes it their decision: `held_by` is cleared and the automatic note goes unless a new one is sent, and from then on that agent holds back new ones itself (until it is reinstated or deleted). **Who sees the note.** The automatic note names another agent of the same user, who may also work for another tenant. It and `held_by` are shown in full to the owner, to an App Admin and to an administrator who may decide on the agent (`can_manage` in `GET agents/{id}` and `GET sentinels/live`: not their own agent, and every organization of its user is theirs to administer); any other administrator gets the general note `held back because another agent of this user is suspended or revoked; an App Admin can see which and decide` and `held_by: {id: null, deleted: false, hidden: true}`. `GET projects/{slug}/sentinels` returns `status_note` only on rows with `manageable: true`, which now means the caller may decide on that Sentinel (the same test), and an empty note on the others. **Delete.** `DELETE agents/{id}` (MCP `delete_agent`; **Manage, Delete** under API keys, Agents in your organizations, or **Delete <name>** on a held Sentinel's card) removes a *revoked* agent and revokes its API token, so that token cannot register a fresh agent in its place, and it no longer holds anything back; any other status is a `409` (revoke it first). The same administrators as `PATCH` (not for their own agent, except an App Admin). The reply is `{deleted, id, token_revoked, released_tasks, still_held: [{id, name}]}`: the agents it held back stay suspended (or pending) until reinstated (or approved). It is audited as `agent.delete`. Every agent also carries `status_changed_at`, when its status last changed. A user may have at most 10 agents. A suspended or revoked agent cannot unregister or re-register to clear that decision, and an administrator cannot approve, limit or reinstate their own agent (another administrator or an App Admin does). An organization admin can administer only users who belong to organizations they all administer; for others they see only their own organizations' part of the scope.

The scope is checked against what the token's user can already reach: naming an organization or project outside that is a `403`, the same answer for one that does not exist. The check runs again every time work is handed out, so a user who loses a project loses the agent's claim to it at once. An administrator (an App Admin, or an organization admin for the users of their organizations) can `PATCH agents/{id}` with `status` (`active` to approve or reinstate, `suspended`, `revoked`), a `note`, and `limits` (`capabilities`, `projects`, `max_concurrent`, each `null` for no limit). A suspended or revoked agent loses its leases at once; a revoked token does too. `whoami` (and `GET me`) now carries `agent`: its registration, what it may reach right now, warnings, and its open assignments.

**Work.** `POST projects/{slug}/agent-tasks` (`queue_agent_work`, needs a write role) queues `kind` `validate` or `remediate` for CVE matches, either `match_ids` or the open matches filtered by `tier` and `host`, up to 200 at a time. Each task records what it needs, from the work itself:

- A validation uses the CVE's shared detection record. Checks that run on the host (`mode` `local`) need `validate:local` or `validate:local-ssh`; checks that probe from the network (`network`) need `validate:network`; a CVE with only plain-language confirm steps (`guided`) needs `validate:guided`. A CVE with none of these cannot be queued.
- A remediation needs `remediate:linux` or `remediate:windows` from the host's operating system (the fingerprint and distribution the scans recorded; when unknown, either), or `remediate:web-config` and `can-restart-services` when the fix is a setting in a web server's configuration file.

Work already queued or running for the same match and kind is skipped. A task whose finding is fixed, accepted or ruled out is cancelled instead of handed out.

**Assignment.** `POST agent/tasks/next` (`get_next_task`, body `{wait, kinds}`) leases the best task the caller may take: its scope covers the host, its user has a write role in the project, its capabilities and operating systems fit, and it is below its concurrent limit. Fire work comes first. If another live agent with room has less to do, the task is left for it, so the agent that polls fastest does not take everything. `wait` holds the call for up to 20 seconds until work appears (long polling: the MCP transport here has no server push); inside an MCP batch of several messages `wait` is ignored (each call answers at once), so one request never holds a web thread for the sum of its waits; at most six calls wait at once, and any more answer immediately with `retry_after_seconds`. The claim is atomic: two agents asking for one task, exactly one gets it.

A task is **leased**. A claimed task must be accepted (`accept_task`) within two minutes. An accepted task stays leased while the agent sends `agent_heartbeat` (about once a minute; each extends the lease of its running tasks by five minutes, up to four hours after acceptance). An agent silent for three minutes is offline and gets no new work. If an agent's user loses the write role or the project, or a limit tightens, the next heartbeat hands its tasks back, and an accept or a report for such a task is a `409` that changes nothing. A task whose lease runs out goes back to the queue after a 30 second pause, counting one attempt; after three attempts it is `failed`. `release_task` gives one back without counting.

`report_task_result` closes a task. `outcome` is `confirmed`, `not_affected` or `inconclusive` for a validation, and `fixed`, `not_fixed` or `blocked` for a remediation. `error` reports a failure: `retryable` (default true) puts it back in the queue until its attempts run out. `summary` is plain text and `checks` is `[{id, result: pass|fail|error|skipped, output}]`, at most 20; everything is cleaned and clipped (1,000 characters of summary, 2,000 per output) and stored as data. A finished task adds a comment to the finding, and a `fixed` remediation sets the finding to `fixed` exactly as `update_remediation_status` does. A validation result never changes the finding by itself: people and the triage decide from the evidence. Reporting the same outcome twice is harmless; a different one is a `409`.

**Unassignable work.** `GET projects/{slug}/agent-tasks/unassignable` (`list_unassignable_work`) lists queued tasks no live agent can take, each with the reason: `no agent covers host x`, `the agents covering host x are offline`, `no live agent covering host x has capability y`, or `... acts on windows hosts`. A reason never names an agent. A task that is assignable can still wait: every capable agent may be busy.

**What an agent may run.** A task payload separates `run` and `run_remote` from `data`. Every entry of `run` (local checks, also given to a remediation to confirm the fix; `check_id`, `platform`, `shell`, `command`, `needs_root`, `expect`) and `run_remote` (network checks; `check_id`, `tool`, `invocation`, with `<TARGET>` and `<PORT>` placeholders) is rendered by the app from the detection record's own validated check parameters, re-validated and re-rendered each time it is read, so no text from a scanned host or a stored record becomes a command. `host.target` is the only value to put in `<TARGET>`, and it is `null` unless the host name is a plain DNS name or an address. Everything under `data` (host name, product, version, advisory title, ports, and `check_notes`, the prose the record has for each check) and `guidance` came from scanned hosts or feeds: read it, never run it. Every MCP result still carries `_meta["cvengine/untrusted_text"]`.

**Limits.** Calls per minute: 120 heartbeats, 60 task requests and 120 reports per token and three times that for all the tokens of one user together, and 30 queue requests a minute per user; registration is 30 an hour per token. One token holds at most one long poll and one user two (a Sentinel's token is not counted against its user, and the built-in scanner's is not counted against the instance either: see **Work** below). A match gets at most five agent tasks a day. Finished tasks are deleted after 30 days (`CVENGINE_AGENT_TASK_RETENTION_DAYS`, in the weekly maintenance); the audit log keeps the trail. Work for an agent is found in SQL by project, operating system and capability, so tasks it cannot do never hide ones it can. A project holds at most 2,000 waiting or running agent tasks. Registration allows 40 capabilities, 30 tools and 200 host entries.

**Audit.** Registration, scope and status changes, queueing, claim, accept, completion, failure, release, lease expiry and cancellation are written to the audit log (Administration, Audit log), tagged with the project's organization.

A worked flow, as MCP tool calls (REST is the same with the routes in the table above):

```text
register_agent    {"name": "web-fixer", "kind": "remediation",
                   "scope": {"projects": ["website"], "hosts": ["*.example.test", "192.0.2.0/24"]},
                   "capabilities": ["remediate:linux", "can-restart-services"], "os": ["linux"]}
update_agent      {"agent_id": 7, "status": "active"}                  (an administrator approves the new agent)
queue_agent_work  {"project": "website", "kind": "remediate", "tier": "fire"}      (a person or another agent with write access)
get_next_task     {"wait": 20}              -> {"task": {"task": {"id": 41, "status": "assigned", ...}, "host": {...}, "run": [...], "data": {...}}}
accept_task       {"task_id": 41}
  ... fix the host, then run the commands in "run" to confirm ...
report_task_result {"task_id": 41, "outcome": "fixed", "summary": "upgraded nginx to 1.24.0",
                    "checks": [{"id": "package-nginx", "result": "pass", "output": "NOT-AFFECTED"}]}
agent_heartbeat   {}                         (about once a minute while working)
```

In the web app, **API keys** (account menu) shows, to administrators, **Agents in your organizations**: it lists agents (not Sentinels, which are on Scanners) with their scope, capabilities, last seen and task counts, with approve, limit, suspend and revoke, plus the work no agent can take and what is queued or running. The same page lists your own keys and agents. Sentinels also have their own page, **Scanners, Sentinels**. A finding and a host show which agent holds work on them.

## Sentinels: scan-stage agents

The result and target contract of every kind below is the library's `cvengine_scanner/contract/sentinel_contract.json`, installed from the commit pinned in `web/requirements.txt` (see [SENTINELS.md](SENTINELS.md#the-result-contract)). A Sentinel is an `Agent` with `kind: "scanner"`: the same identity, scope, capabilities, admin approval, suspend/revoke, live/heartbeat window and rate limiting as any other agent ([Agents and assigned work](#agents-and-assigned-work)), but the work it is leased is scan-stage work, not a CVE match. Covered: `nmap`, `naabu`, three nuclei passes (`nuclei_light`, `nuclei_targeted`, `nuclei_deep`), testssl.sh's TLS audit (`testssl`), the background UDP exposure sweep's `nmap -sU` (`nmap_udp`, a separate capability from `nmap` since it needs its own fixed flag set), WPScan's WordPress audit (`wpscan`), the optional OpenVAS add-on's GVM scan (`openvas`, see [OpenVAS](OPENVAS.md)), and the host sweep of a declared internal network (`discover`, see [ARCHITECTURE.md](ARCHITECTURE.md#sentinels)); `waf`, the WAF fingerprint (contract version 2); and, from contract version 3, the in-process probes `http_probe` (a batch of the version and identity probes the server planned) and `dns_resolve` (a batch of names to resolve), each carrying a scope policy (`target.scope`) the Sentinel enforces at every hop, the background full port sweep (`nmap_full`), service detection with the reviewed NSE scripts on named ports (`nmap_verify`), the node2shell check (`node2shell`), the RDP pre-authentication screenshot (`rdp_shot`, a PNG the server reads), the one credential-less database connection (`db_probe`), whether a retired name's last known addresses still answer (`alive_check`: a GET of `/` as the old name, or a bare connect), the anonymous checks of cloud storage buckets at the platforms' documented endpoints (`bucket_check`), the other sites an address serves for the project's own names (`vhost_probe`: a GET of `/` as each name, no body or cookie sent, redirects never followed), the applications mounted under well-known subdirectories of a web host (`subdir_probe`: one GET per curated path, `robots.txt` and `sitemap.xml`), the passive posture checks of a third-party supplier's public names (`supplier_check`: the certificate, email authentication, the front page's security headers and a short fixed list of well-known pages, per name, plus what the page announces for the server's CVE match), the anonymous web route check (`route_probe`: a batch of up to 25 hosts with up to 20 routes each, answered with each route's state, the sensitive data it serves and the libraries its front page's scripts state), the TLS and email half of a target's hygiene sweep (`hygiene_check`: a batch of TLS endpoints and mail names), the rating of bbot's dangling-DNS findings (`dangling_dns_check`), the read-only inspection of SSH services the port stage found open (`ssh_probe`: a batch of up to 25 address and port pairs, one `sshamble` handshake read each on the Sentinel, answered per endpoint with observations, each marked verified or not, and the badkeys blocklist hits of the host key; the server installs no SSH tool), the validation re-test's page reads (`page_read`), the name and certificate reads of a name or address (`identity_check`), the screenshots of a host's web pages (`web_screenshot`: Playwright's headless Chromium, up to six pages per task), the thorough WPScan pass of one site (`wpscan_thorough`: hours, its own time limit in the target), and three kinds only the built-in scanner is offered: the scan path check (`path_probe`), the AI template check and approved-template test (`nuclei_validate`) and the web route check signed in (`route_probe_signed`: one stored sign-in read once, sent only where it was stored for) - thirty-six `SentinelTask` kinds in all with the streamed bbot run (`bbot_discovery`), and its `capabilities` are drawn from those names (plus `network:internal`, which a Sentinel sitting inside a private network is credited with: the server grants it, a Sentinel's own claim is ignored). A `SentinelTask` (its own queue, separate from `AgentTask`) is one run of one tool against a server-built target; nothing it contains, and nothing a Sentinel reports back, is ever built from, or interpreted as, a command. The downloadable Sentinel client is this exact REST contract's reference implementation: a small Docker Compose service in its own repository, [hevnsnt/cvengine-sentinel](https://github.com/hevnsnt/cvengine-sentinel) (its `README.md` has the setup steps), not a per-OS package.

`openvas` is unlike the other kinds: it is not a single bounded-wait stage, but a long-running GVM task (up to `CVENGINE_OPENVAS_MAX_HOURS` per host, 24 hours by default) tracked across many ticks of `cveFeed.openvas_scan.tick`, polled over many ticks (`OpenvasRun.sentinel_task`, `dispatch_to_sentinel`/`poll_sentinel`). The Sentinel runs its own complete GVM stack against the exact host set (at most 16 hosts per task, which the client enforces: `CVENGINE_OPENVAS_MAX_HOSTS` is held to 16) and excluded-NVT-family list the task's `target` names (this instance's own `EXCLUDED_FAMILIES`, never a copy a Sentinel might carry out of date), and reports its results once; cvENGINE imports them through `_apply_import`.

**Who is inside a private network.** `network:internal` is the server's to grant. A Sentinel is internal (`Agent.network = internal`) when the administrator who provisioned it chose `internal` (the enrollment records the choice, `?network=internal` on the enroll routes and the MCP tool), or when an administrator later changes it (`PATCH agents/{id}` with `settings: {network: "internal"}`). What a Sentinel declares in `capabilities` or reports in its settings never grants it: the claim is kept as data and ignored, and the settings reply tells the client the server's value. A Sentinel that declared `network:internal` before the server decided it, and was already running, is carried over as internal by migration `agentapi 0007`.

**How dispatch works.** Since 1.4 every scan stage hands its work to a Sentinel and none runs a tool on the server. Before a stage hands work over it asks once: is there a live, eligible Sentinel for this project with the matching capability (the built-in scanner counts, as the last resort)? If not, the stage waits and its targets stay due (`ScannerUnavailable`; nothing is recorded as done or failed). If there is one, the stage creates a `SentinelTask`, the Sentinel claims and reports it, and the typed result is persisted through the stage's own function (the nmap and naabu results flow into `persist_inventory`/`persist_open_ports`; a nuclei finding is reconstructed into the same result-line shape nuclei's own JSON output takes and runs through the stage's own per-line loop). The wait has three budgets (see [Configuration](CONFIGURATION.md); all readable at `GET sentinels/dispatch`, MCP `get_sentinel_dispatch`): a short `CVENGINE_SENTINEL_CLAIM_TIMEOUT` (default 8s) for a Sentinel with a free slot to claim the task; **a queue wait**, `CVENGINE_SENTINEL_QUEUE_TIMEOUT` (default 300s), when every live, eligible Sentinel is at its `max_concurrent` (a Sentinel at its limit is busy, not missing: the task waits for a slot, and the wait ends early if the last live Sentinel goes away); and, counted from the moment a Sentinel claims the task, the completion ceiling of its kind (nmap 900s, naabu 600s, ...) plus a per-target allowance for each target beyond the first. Tasks already waiting in the queue for a kind are promised the free slots. A running task's lease is extended by the Sentinel's heartbeat (at most for the longest its kind is waited for, plus ten minutes, so a task the Sentinel dropped without reporting does not hold a slot for ever), and a Sentinel that stops heartbeating loses it after five minutes. A task nobody claims is expired after its dispatcher's queue budget plus five minutes (an OpenVAS task after an hour), so an orphan left by a restarted worker neither stays claimable nor counts as waiting work. On any timeout or failure the `SentinelTask` is marked `expired` or `failed` and the targets stay due; the stage is never run on this server. A target inside a declared internal network can only be claimed by a Sentinel that holds `network:internal`. Each Sentinel row (`GET agents`, `list_sentinels`) carries `slots: {max, in_use, free, by_kind}` (its `max_concurrent`, less an administrator's lower limit, against the tasks it holds now), and `GET agents/{id}` (`get_sentinel`) `queued_for_it` (the tasks waiting in the queue that it could take, by kind). The server counts the slots from the leases it granted, so a Sentinel need not report them. See [Architecture](ARCHITECTURE.md#sentinels) for the full design note.

**Register.** `PUT sentinel` (`register_sentinel`) is `PUT agent` with `kind` forced to `scanner`; the same fields (`name`, `scope`, `capabilities`, `os`, `tools`, `max_concurrent`) and the same approval rule apply (a new Sentinel of a non-administrator starts `pending`). A brand new Sentinel with no token yet instead bootstraps from a one-time enrollment secret, scoped to a project, an organization, or (App Admin only) the whole instance:

1. Pick the scope and call the matching endpoint:
   - **Project**: an org admin or App Admin calls `GET`/`POST projects/{slug}/sentinels/enroll` (`generate_sentinel_enrollment` with `project`).
   - **Organization**: an admin of that organization, or an App Admin, calls `GET`/`POST orgs/{slug}/sentinels/enroll` (`generate_sentinel_enrollment` with `org`). The resulting Sentinel covers every project of that organization, present and future: `agentapi.agent_scope.project_slugs_in_scope` resolves `scope.orgs` dynamically at claim time, so a project the organization gains after enrollment needs no new enrollment.
   - **Instance**: an App Admin (superuser) calls `GET`/`POST sentinels/enroll` (`generate_sentinel_enrollment` with neither `project` nor `org`). The resulting Sentinel covers every organization and project on the server, present and future.

   Generating an enrollment needs a token that can write: a read-only token gets `403` on all three routes even though they answer `GET` (the secret buys a token that is not read only). Each returns `{enrollment_token, server_url, expires_at, scope: "project"|"org"|"instance"}`, plus `project` or `org` where the scope names one. The secret is single-use and expires 30 minutes after it is generated (documented, not yet configurable). `?format=blob` requires `network` (`external` or `internal`) and `profile` (`full` or `light`) and answers `400` if either is missing, blank or unknown, before any secret is created (the **Provision** form never picks them for the person). It returns the same payload plus `{blob}`: the same fields base64-encoded as compact JSON (`agentapi.sentinel_broker.encode_enrollment_blob`, no custom framing, no new crypto), the one opaque string the **Sentinels** page's **Provision** button shows for `CVENGINE_SENTINEL_BLOB`. Each `generate_*_enrollment`'s own contract is unchanged either way; the blob is purely a presentation layer over the same secret. The `generate_sentinel_enrollment` MCP tool takes optional `project`/`org` arguments (at most one; neither means instance-wide) and always returns the blob form, plus a `setup` block of four ready-to-run shell commands (clone the client repository, write the blob into `.env`, `docker compose up -d`, tail the logs), so an agent with Docker and shell access to a target machine can provision a Sentinel from the tool's response alone, with no other context; see [hevnsnt/cvengine-sentinel](https://github.com/hevnsnt/cvengine-sentinel)'s `AGENTS.md`.
2. The Sentinel calls `POST /api/v1/sentinels/bootstrap` (REST only; no bearer token, the secret itself is the credential) with `{enrollment_token, name, capabilities, os, tools, max_concurrent}`. The server redeems the secret, creates an `Agent` (`kind: scanner`) pre-scoped to exactly what the secret was generated for (one project, one organization, or, with neither, the whole instance), never to what the Sentinel's own body claims, owned by the administrator who generated it, and returns `{token: "cve_...", ...}` once, like any other token creation. Every field of the body is checked before the secret is redeemed, so a bad value (a `max_concurrent` above 10, say) is a `400` and the same secret can be sent again; redeeming it and creating the Sentinel are one transaction. The token has the **`sentinel` scope**, not the enrolling administrator's full access: it can call only the Sentinel loop (`GET/PUT/DELETE sentinel`, `POST sentinel/heartbeat`, `sentinel/tasks/next`, `sentinel/tasks/{id}` and its `accept`, `partial`, `result` and `release`) and answers `403` on every other REST route and on `/mcp/`, so a token taken from a Sentinel's machine is not its administrator's token. It expires 90 days after it was issued and every heartbeat that finds less than 60 days left renews it, so a Sentinel that keeps running never expires and one taken out of service does. Tokens of Sentinels enrolled before this change are narrowed to the same scope by the migration. A Sentinel may narrow its own `scope` (`PUT sentinel`, for instance with `hosts`), but never widen it past what its enrollment granted (`403`). The MCP loop tools (`sentinel_heartbeat`, `get_next_sentinel_task`, `accept_sentinel_task`, `report_sentinel_task_result`) are for a Sentinel run by a person with their own token, since a `sentinel` token does not reach `/mcp/`; the Sentinel client uses REST.

**Work.** `get_next_sentinel_task` (body `{wait, kinds}`) leases the best queued `SentinelTask` the caller's scope and capabilities cover, the same bounded long-poll (`wait` up to 20 seconds, taking one of the few waiter slots the other agents share, except for the built-in scanner, which is never turned away for want of one: with none free the call answers at once with `retry_after_seconds: 5`) and atomic claim as `get_next_task`. A Sentinel whose updater reported `draining` or `updating` in the last 30 minutes is handed nothing new. Every task the Sentinel receives carries a `trace_id` (a 32 character id of the task, new for each one); the server writes it into its audit rows and activity lines about the task, so a Sentinel can quote it in its own log. A nuclei task's `target` carries `targets`, the `tags` and `severities` the server's own pass of that kind runs with (the light pass is `tags: ["tech"]`, `severities: ["info"]`; a pass the server runs at its default severities sends them, `["info", "low", "medium", "high", "critical"]`, never an empty list, so `unknown` is left out as it is here), `etags` (tags never to run, `dos`) and `template_policy` (`{rev, read_only, bundle_sha256}`: the policy the server applies to the templates it runs, and the sha256 of the approved template bundle described under **Template policy and bundle**; `bundle_sha256` is `null` until the server has built that bundle, see below). `accept_sentinel_task` within two minutes, then `sentinel_heartbeat` about once a minute to keep the lease (it is the same call as `agent_heartbeat`: one heartbeat extends both AgentTask and SentinelTask leases of that agent). `report_sentinel_task_result` takes `{task_id, outcome: "done"|"error", ...}` (sent again after the task finished it answers `duplicate: true` and changes nothing; a body that does not fit the schema is refused with 400 and ends the task as failed, so send `outcome: "error"` rather than a result that cannot be accepted); on `done`, the fields its `kind` expects:

| `kind` | result fields |
| --- | --- |
| `nmap` | `hosts: [{ip, os_guess, ports: [{number, protocol, service_name, product, version, state}]}]` (at most 64 hosts, 500 ports each) |
| `naabu` | `ports: {ip: [open port numbers]}` (at most 64 addresses, 500 ports each) |
| `nuclei_light`, `nuclei_targeted`, `nuclei_deep` | `findings: [{template_id, name, severity, host, matched_at, description, matcher_name, extracted_results, tags}]` (at most 500 findings are kept, strongest first, and a result carrying more is not rejected: the rest are counted in `dropped_findings`; more than 5000 is refused. 20 extracted results and 20 tags each. Optional: `cve_ids`; `type` (nuclei's protocol type: http, tcp, javascript, dns, ssl...); `request` and `response`, the matched request and the answer, kept up to 4096 characters each as the finding's evidence. A result without them is accepted and stored as before) |
| `testssl` | `items: [{id, severity, finding, cve}]` (testssl.sh's own raw report items, at most 300) - never chunked, one `host:port` per task |
| `discover` | `hosts: [{ip, hostnames}]` (at most 512): the live addresses a Sentinel inside a private network found in one /24 chunk of a declared internal range (target `{cidr}`); the server keeps only addresses inside that chunk and drops the network and broadcast addresses |
| `nmap_udp` | `xml: "<nmaprun>...</nmaprun>"` (nmap's own raw XML report text, at most 4 MiB) - the only kind reported as XML rather than typed JSON; parsed server-side by the same `cveFeed.nmap_scan.parse_xml` (hardened against a custom ENTITY declaration) the stage's XML goes through, so UDP's `open`/`open|filtered`/`closed` states and NSE script output are read identically either way |
| `wpscan` | `report: <WPScan's own JSON report, or null>, returncode: <int>, stderr_tail` (report at most 8 MiB) - the raw, unclassified outcome; `cveFeed.wpscan_scan._classify` turns it into a report or `NotWordPress`/`Blocked`/an error, as the exit code of any run would |
| `openvas` | `results: [{oid, name, family, address, hostname, port, port_number, severity, threat, qod, qod_type, result, summary, insight, impact, affected, solution, solution_type, cvss_vector, cves, urls}]` (at most 5000, the shape `cveFeed.openvas_scan.parse_result` reads), plus `scanned_addresses` (the hosts GVM actually reached, at most 64), `without_cve` and `unusable` counts, and `partial: true` when the scan stopped at its time budget |

A result is also held to what the task asked about: an nmap host, a naabu address or a nuclei finding on a host that was not among the addresses or targets the server dispatched is dropped and counted in `dropped`, never stored. The result route (`POST sentinel/tasks/{id}/result`) is the one route that takes a body up to 24 MB (its own nginx location and Django's `DATA_UPLOAD_MAX_MEMORY_SIZE`); every other route stays at 4 MB. A nuclei task on a Sentinel runs with `-etags dos` and the approved-template snapshot (see **Template policy and bundle**), like the server's own pass, and a signed-in nuclei pass (authenticated checks) is dispatched only to the built-in scanner, which reads the stored sign-in once through the secure read ([SENTINELS.md](SENTINELS.md#secure-read-of-a-stored-sign-in-built-in-scanner-only)). Every string is clipped (template id 80 characters, name 200, description 500, matcher name 80, a product or version 80 to 120) and every list capped before it is stored or used anywhere; an unexpected shape is a `400`, never stored as given. `matcher_name` is the nuclei matcher that fired (nuclei's own `matcher-name`, for example a tech-detect template's matcher): `sentinel_dispatch._finding_to_nuclei_line` carries it through to the reconstructed result line exactly as a locally-run nuclei `-jsonl` line already supplies it, so a Sentinel-reported tech-detect hit names a `Technology` the same way a local one does (`cveFeed.nuclei_scan.tech_name_from`). A `SentinelTask`'s own target descriptor is server-built from the same scan the stage is already running: a Sentinel never receives the project's stored sign-ins (`AuthCredential`), another project's data, or raw database access, only the addresses, hosts or templates for the one task it holds. `release_sentinel_task` gives a task back without counting against it; a Sentinel that stops heartbeating has its leased tasks marked `expired` the same way `agent_heartbeat`'s silence does, and the dispatching stage, having already timed out waiting, has moved on to running the tool locally.

**Streamed work: bbot discovery (`bbot_discovery`, contract version 3).** A discovery runs for up to six hours and finds things all along the way, so it does not fit one result per task. The Sentinel posts numbered batches to `POST sentinel/tasks/{id}/partial` while it runs, `{seq, scan_name, subdomains, ips, ports, urls, technologies, resolutions, edges, findings, http, events, screenshots}` (`$defs/partials/bbot_discovery` in the contract), and the usual `result` at the end, `{outcome: done, partials, mode, incomplete, scan_name, web_events, problems, hard_failures}`, where `partials` is the `seq` of its last batch. `seq` starts at 1 and grows by one: a batch at or below the last one the server took is answered `{accepted: false, duplicate: true}` and stored once (a retry whose answer was lost), any other number than the next is a `400`, and a final result that names another count than the server has is refused, so nothing found is lost to a dropped answer. A `409` means stop the run: the task was cancelled, its lease ran out, or its scan was stopped (a batch of a stopped scan ends the task there and then). A `429` means earlier batches are still being stored (at most 40 wait per task): send it again shortly. A batch that does not fit (a list over its cap) is a `400` and fails the task. Every batch also extends the task's lease like a heartbeat, up to the run's own time limit plus ten minutes.

The task carries the scope it must keep to (`$defs/scope_policy`): the target as the one in-scope domain (only the target itself when it was added as exactly one host), the organization's exclusions and a bug bounty program's out-of-scope names under it, and the project's internal ranges and the program's out-of-scope addresses as ranges never touched. The scanner applies it on every hop, and the server applies it again to every batch (`agentapi.sentinel_stream.clean_partial`): a name outside it, an address in a denied range, a URL that is not `http` or `https` or carries a user name, and a screenshot that is not the PNG or JPEG it says (at most 2 MiB, four per batch) are dropped, every string is clipped and every list capped. The stage that dispatched the task (the discovery worker) reads the batches in order and stores each through the same code as a local bbot run, so the inventory, the live feed and the screenshots fill in while it runs. The `partial` route, like `result`, takes a body up to 24 MB and is exempt from the input guard's attack-string scan (it carries what scanned hosts returned). A project's API keys for bbot's modules are never in the task: a task of a project that stored some has `secret_ref` `bbotkeys:<project id>`, so only the built-in scanner is offered it, and it reads them once through `POST sentinel/tasks/{id}/secret`, which answers `{bbot_config: {modules: {<module>: {<option>: <key>}}}, task_id}` for such a task under the same single-use, audited rules as a stored credential.

**Token renewal.** A Sentinel's token is renewed by its own heartbeat, in place: the token string stays the same, only its expiry moves (to 90 days from the renewal, done once less than 60 days are left). The heartbeat reply carries no new token and the Sentinel never has to store one. A `401` on any call means the token is expired or revoked: the Sentinel cannot recover on its own and must enroll again with a fresh enrollment secret.

**Heartbeat body.** `POST sentinel/heartbeat` takes an optional JSON object. Every field is optional and an empty body is a plain "alive" signal:

```json
{
  "info": {"version": "1.4.0", "update": {"status": "idle"}},
  "running": [4211, 4215]
}
```

`running` is the list of SentinelTask ids the Sentinel is working on right now: a list of at most 100 whole numbers, each above 0; anything else is a `400` whose message names `running`. When it is present, each of this Sentinel's own tasks in status `claimed` or `running` that is not in the list, and that was accepted more than 120 seconds ago (a task never accepted is judged by when it was claimed), is ended as `expired` with the error `the Sentinel no longer reports this task`, the same way a task whose lease ran out is: the dispatching scan stops waiting and falls back to running that stage locally, and the Sentinel's slot is free again. An empty list means "I am running nothing". Tasks younger than 120 seconds are left alone, ids of other Sentinels' tasks (or no task at all) in the list are ignored, and no other Sentinel's task is ever touched. Without `running` (or with `null`) nothing is ended, exactly as before. The reply lists `leases` for the tasks still held, so an ended task is no longer in it.

**Template policy and bundle.** A nuclei task says which template policy applies (`target.template_policy`), but a Sentinel cannot rebuild the approved set from a name, so the server offers that set as one archive. Both routes answer only to a Sentinel's own token (any other token, or a session, gets `403`; a revoked or expired token `401`), are rate limited per token like the other Sentinel routes (`429`), and are not audited.

`GET /api/v1/sentinel/template-policy` returns:

```json
{
  "rev": "readonly-2",
  "read_only": true,
  "bundle": {
    "sha256": "9f2c0c1ad3b5e0c7a4f1b86d2e7c5a0b3d4e8f9a1b2c3d4e5f60718293a4b5c6",
    "bytes": 3145728,
    "templates": 8421,
    "path": "/api/v1/sentinel/template-policy/bundle"
  }
}
```

`rev` is `readonly-2` (only the read-only templates the server itself runs, `read_only: true`) or `all-1` (an administrator allowed every installed template, `read_only: false`); the bundle differs between the two, so a changed `rev` or `bundle.sha256` means "fetch again". `sha256` is the hash of the archive's bytes, `bytes` its size, `templates` the number of templates in it.

`GET /api/v1/sentinel/template-policy/bundle` streams that archive from disk: `Content-Type: application/gzip`, `Content-Length`, and `ETag` set to the same sha256 in double quotes (`"9f2c...b5c6"`). Send the sha256 you already hold as `If-None-Match` (quoted, bare, weak or in a list all match) and the server answers `304` with no body when it is still current. The archive holds only regular template files (`.yaml` or `.yml`) with relative paths, no `..` or absolute path, no directory or link entries, in sorted order with fixed times and owner, so identical content always gives the same sha256. Extract it into an empty directory and run nuclei with that directory as the template path. Verify the downloaded bytes against the `ETag` before using them (the set can change between the two calls; the `ETag` of the download is the truth for what you got).

The archive is built once per approved snapshot of the template library and kept on disk beside it, never per request; the first policy request after the server started may therefore take longer while the snapshot is built. A nuclei task's `template_policy.bundle_sha256` is that archive's sha256 when it already exists at the time the task is created, so a Sentinel knows when to fetch again without an extra call; it is `null` when the server had not built the archive yet (call `GET sentinel/template-policy`, which builds it, and use the `sha256` it returns). The approved set is capped (100,000 files, 512 MiB of templates, 256 MiB of archive); over a cap, or with no template library installed, both routes answer `503` with the reason.

**Admin.** A Sentinel is administered exactly like any other agent: `list_agents?kind=scanner` (`list_sentinels`), `GET/PATCH agents/{id}` (`get_sentinel`, and `suspend_sentinel`/`revoke_sentinel`, thin aliases of `update_agent`); suspending or revoking releases its in-flight `SentinelTask`s immediately, the same call that already releases `AgentTask`s. `GET projects/{slug}/sentinel-tasks` (`list_sentinel_tasks`) lists scan-stage work for a project (`status`, `kind`, `agent_id`, `scan_id`); `GET agents/{id}` includes a Sentinel's recent `SentinelTask`s under `recent_tasks`. `GET projects/{slug}/sentinels` lists the Sentinels whose scope covers one project (any role in it may read; no scope or owner is shown, and `manageable` says whether the caller may `PATCH agents/{id}`), which is what the project's Sentinels tab shows. `generate_sentinel_enrollment` (and `?format=blob` on the three `sentinels/enroll` routes) also takes `network` (`external` default, or `internal` for a machine inside a private network) and `profile` (`full` default, or `light` to skip the OpenVAS stack); they choose the `.env` lines in the returned `setup.configure`, and `setup.configure_alternative` is the same as one `./setup.sh` command. **Settings and updates.** A Sentinel's settings can be changed from cvENGINE after it checked in, so nothing has to be touched on its machine: `PATCH agents/{id}` with `{"settings": {"name", "network" (`external`|`internal`), "profile" (`full`|`light`), "kinds" (the capability policy, below), "disabled_kinds" (the older list: each kind is `deny`), "max_concurrent", "self_update" (`off`|`manual`|`automatic`)}}` (`null` restores the provisioned network grant for `network`, or external without a matching enrollment; for other settings it hands the value back to the Sentinel). The same settings can be set in the Sentinel's own `.env`, and **the most recent change wins for settings except the server-authorized network grant**: a Sentinel reports only its own values (`settings` in `PUT sentinel`), cvENGINE keeps the time each last changed on this server's clock, a restart with an unchanged `.env` never undoes a later dashboard edit, and the effective values come back in the registration and heartbeat replies (`settings: {values, rev}`; `GET agents/{id}` shows each with its `source` (`server` or `sentinel`), time and who set it). The Sentinel applies them within a heartbeat and registers again. Every edit is audited. A Sentinel also reports its client `version` and its host-side updater's state (`info: {version, update: {status, phase, detail}}` in the heartbeat); the heartbeat reply's `update: {mode, requested}` says whether the instance is on Automatic updates (the same choice the main updater follows) and whether an administrator asked this Sentinel to update now (`PATCH agents/{id}` with `{"update": "now"}`, cleared once the Sentinel runs a different version or reports a failed attempt). The Sentinel's updater drains its running tasks first. **Self-update** is its own setting, `self_update`: `off` never changes the Sentinel's code (and `update: "now"` is refused with `409`), `manual` updates it only when an administrator presses Update now, `automatic` updates it when a new version is out. A Sentinel with no value of its own takes the instance default, `GET/PUT sentinels/defaults` (`PUT` is App Admin only: `{"self_update": "off"|"manual"|"automatic"|null}`, `null` follows the instance's own Automatic or Manual update choice; MCP `get_sentinel_defaults`, `set_sentinel_defaults`). The heartbeat reply's `update` is `{setting, mode, requested}` (`mode` is the same answer as `auto` or `manual` for a client that predates `setting`). While **Keep Sentinels on the newest version** is on (`keep_newest` in `GET/PUT sentinels/defaults`, a boolean, true by default, App Admin to change) a Sentinel that runs a build behind the newest published one is asked to update, and `update` then also carries the optional `target` (the commit) and `reason` (`newest` or `admin`): a client that does not know them ignores them, and the contract version is unchanged. `GET agents/{id}` shows `auto_update: {code, text, running, newest, requested_at, flagged, next_after}`. See [UPDATES.md](UPDATES.md#keeping-sentinels-on-the-newest-version). **The updater's state is visible**: a Sentinel reports `info.updater` `{installed, running, last_run, last_result, detail}` in its heartbeat, and every Sentinel row of `GET agents` and `GET agents/{id}` carries `version`, `self_update` and `updater: {state, last_run, last_result, detail, install_command, warning}`. `state` is `running`, `stopped` (installed, not running), `not_installed` or `unknown` (a client that does not say). `warning` is set when self-update is Manual or Automatic and no updater is running, so a Sentinel that cannot update itself shows instead of silently never updating; `install_command` is the fixed text cvENGINE renders (`cd <the Sentinel checkout> && sudo ./scripts/install-updater.sh`), never anything the Sentinel sent, so an administrator can copy it safely. The **Sentinels** page (`/cve/sentinels/`) shows this with suspend/revoke buttons and a way to generate and copy an enrollment secret; see [Front end](FRONTEND.md#sentinels).

**Capability policy.** An administrator chooses what each Sentinel may take, per kind, for the built-in scanner as for an external one. `PATCH agents/{id}` with `{"settings": {"kinds": {kind: {"mode": "allow"|"deny"|"prefer", "max_concurrent": 1-10|null} | null}}}` (MCP `update_agent`) sets it, merged per kind (`null` for a kind removes the Sentinel's own policy for it and hands it back to the default; `"kinds": null` clears them all); `mode` and a known kind are required, and `max_concurrent` is a per-kind cap inside the Sentinel's own `max_concurrent`. `allow` offers the kind (the default for a declared kind), `deny` never does (it is what `disabled_kinds` always meant: a stored `disabled_kinds` still reads as `deny`, and `disabled_kinds` can still be set, which folds into the policy), and `prefer` offers it and holds a queued task of the kind back from every Sentinel that does not prefer it for up to `CVENGINE_SENTINEL_PREFER_DEFER_SECONDS` (60, a ceiling; `0` is off; for every kind but `openvas` also at most the stage claim window less two seconds, 6 by default) while a preferring one is live, in scope and has room. A change is last-write-wins like every managed setting and audited (`agent.settings`, with `kinds_before` and `kinds_after`). Only what a Sentinel declares can be allowed or preferred: a kind it does not declare (its tool is missing or off on the machine) or one its machine turned off (`CVENGINE_SENTINEL_DISABLE`, which the server cannot lift) is refused with `409`; `deny` and removing a policy are always accepted. A Sentinel cannot send `kinds` itself (`400`: it can only turn kinds off, with `disabled_kinds`). `GET agents/{id}` (MCP `get_agent`, `get_sentinel`) carries `kinds`: `{kind: {declared, effective, mode, source, cap, held, state, note, by, at, retry_at}}`, with `source` one of `agent` (the Sentinel's own policy), `instance default`, `machine` (turned off on the machine), `contract` (its client is too old), `cool-off` (it kept failing; `retry_at`) or `default`, and `state` one of `on`, `denied`, `machine_off`, `unavailable`, `cool_off`, `outdated`; `settings.kinds` is the stored policy. The instance defaults, for a Sentinel with no policy of its own for a kind, are `builtin_kinds` (the built-in scanner; shipped as `{"openvas": {"mode": "deny"}}`) and `external_kinds` (every other Sentinel; empty allows every declared kind) in `GET/PUT sentinels/defaults` (App Admin; `PUT` replaces a whole map, `builtin_kinds: null` restores the shipped one; MCP `get_sentinel_defaults`, `set_sentinel_defaults`): a Sentinel's own policy wins as a whole, then the default of its class, then allow. The wire reply to a Sentinel is unchanged: `settings.disabled_kinds` in its registration and heartbeat replies is every denied kind, derived from the policy, and nothing else of it is sent. **The built-in scanner.** Its registration and heartbeat `info` may carry `builtin: true` and `features` (`secret_read`: it reads a stored sign-in through `POST sentinel/tasks/{id}/secret`; `vantage`: it applies the vantage settings); unknown features are dropped, and whether a Sentinel is the built-in scanner is decided by its enrollment, never by `info`. Its settings reply alone carries `values.vantage` (`proxies`, the URLs of Settings > Proxy, which may carry a login; `bypass`; `proxy_private`; `private_ranges`), derived at every reply and stored nowhere. A task it is handed carries `signed_in: true` when it names a stored sign-in (`secret_ref` is never sent); only a built-in scanner that reports `secret_read` is offered one. When no live Sentinel can take a kind, the stage message names why (`disabled`, `offline`, `withheld`, `inactive`, `never`), and the scanner state's `disabled` and `disabled_message` say "X is turned off on every Sentinel that has it" apart from "Scanner offline".

For `network`, the server grant and the machine setting are separate limits. `GET agents/{id}` reports the actual usable location as `settings.network.value`, the authorization as `server_grant`, and the Sentinel's own setting as `machine_value`. `managed` says whether an administrator override remains in place, even when the machine currently limits it. An external machine setting limits an internal grant, so the heartbeat reply and internal task eligibility both remain external until the machine reports internal. A machine reporting internal cannot override an external server grant.

## Targets and scans

`targets/bulk-org` takes `{"text": "##Organization\n#Project\nexample.com\n10.0.0.0/28\n#Project2\n...", "current_project": "slug"}`. A paste may carry up to 10,000 entries across at most 50 projects (more is `400`, checked while the text is read, after the caller is known to belong to an organization). A line `#Name` (no space after the hash) opens a project, and the lines under it are domains, IPs, CIDRs, ranges, or URLs. `# a note` is a comment. A `##Organization` line is optional. Without one, or with a name the caller cannot see, the caller's current organization is used, and `organization_note` says so when a name did not resolve. Missing projects are created, which needs the admin role in the organization. Each project is checked on its own, so a section the caller cannot write to is reported in `projects[].error` and the rest still go in.

Bulk adds start discovery by default. A single add starts it only when `discover` is true. `mode` is `standard` (default), `deep`, `passive` or `manual`, and any other value is `400`. The mode is kept on each target it creates (`discovery_mode` in every target record) and is what every later scan that starts on its own uses, the work conductor's rescans included: a passive target is never rescanned in standard, and a `manual` target ("just add them, do not scan yet") is added and never scanned automatically; `manual` starts no discovery even with `discover` true. A request with no `mode` stores `standard`, whether or not discovery starts now, and adding a name that already exists does not change its mode. `POST .../targets/{id}/discovery-mode` (`set_target_discovery_mode`) changes it afterwards and starts nothing. `POST .../targets/{id}/discover` (and `discover_target`) takes `mode` (`standard`, `deep` or `passive`; `400` for anything else, `manual` included) and keeps it on the target; the answer says what happened: `discovery_mode` is the mode stored afterwards and `scan_mode` the mode the returned scan runs in (they differ when a scan was already going in another mode, and an internal target's scan has no mode and leaves the stored one unchanged); with no `mode` it runs the target's own, and for a `manual` target (and `POST .../scans`, `start_scan`, on one) answers `409` until a mode is chosen. Targets queue first in, first out, and a target that already has a queued or running scan keeps it. A queued scan has `status` -1 and a `queue_position` (0 is next). `GET .../scans` lists running scans first, then queued, then the rest newest first. Stopping a scan marks it aborted and ends its scanner processes so the next queued scan can proceed.

Each target carries `scope_mode` and `host_scoped`. See [Shared provider domains](PIPELINE.md#shared-provider-domains) and [Exact-host targets](PIPELINE.md#exact-host-targets).

**Scope at add time.** `POST .../targets` (`add_target`), `POST .../targets/bulk` (`add_targets`) and `POST targets/bulk-org` (`add_targets_by_org`) take an optional `scope_mode`: `auto` (the default, what every target was created with before), `host` or `parent`, validated as `POST .../targets/{id}/scope` (`set_target_scope`) validates it (anything else is `400`, checked before any line is applied). It is stored on each new domain target. An entry written with a leading `=` (`=example.com`, `=app.example.com`, also as a `value` or an item of `targets`) is created as `host` whatever `scope_mode` says, and wins over the same name written without it in the same request. An IP, CIDR or range has no subdomains: the mark and `scope_mode` are ignored for it (it keeps `auto`). Adding a name that already exists does not change its scope. The single add returns the created targets with their `scope_mode`; the bulk adds return `scope_mode` (the batch's) and `scope_modes` (name to stored scope for the targets created, the first 200, per project for `bulk-org`). A `=` standing alone marks the next entry on its line (`= example.com` is `=example.com`). A mark with nothing valid after it (`==example.com`, `=-example.com`, a lone `=` at the end of a line) is reported in `invalid` as written, and `-example.com` still excludes.

## All projects

The reserved slug `_all` means every project you can see. The list endpoints and tools accept it in place of a project slug and return one combined, read-only list: `targets`, `scans`, `hosts`, `search`, `findings`, `vulnerabilities`, `matches`, `changes`, `activity`, `hygiene`, `certificates`, and `routes`. Every row carries `project` (use this slug for anything you do next) and `project_name`. Only your own projects contribute rows, and `count` is the total. Everything else needs a real project: a write or a per-item call with `_all` is a `400`. Add `?org=<organization slug>` to narrow `_all` to that organization's projects (an organization you have no projects in is ignored, so it never widens or empties the view). In the web app the switcher sets it: choose an organization, then **All projects**; the browser session remembers it for the pages and polls that do not name it, and **All organizations** clears it.

## Host management

`profile` records who owns a host, what it is for, and how much it matters (`criticality`: `unknown`, `low`, `medium`, `high`, `critical`), per project. Only the fields you send change.

`alias` and `note` are what a person calls the host and a few lines they wrote about it, on `profile` for a host and on `targets/{id}/profile` for a target (`set_host_profile` and `set_target_profile` over MCP). The alias is one line of plain text of at most 60 characters, the note plain text of at most 1000 (line breaks allowed); an empty string clears one, and a field you leave out is not touched. Anything longer, or with control characters, is a `400`. They need the same access as the other writes here: a project role above audit and a token that is not read only, and `_all` is a `400`. Every change that alters an alias or a note is written to the audit log as `host.profile` or `target.profile`, with the project, the name and which fields changed (the text itself is not copied into the log). The alias is a display name only: the address and the names a scan discovers never change, and every scan, check and search by name still uses them. It is shown beside the address in lists, search results, the graph's tooltips and cards and the PDF reports (the report page also prints the note), and the Hosts search, the target list's `q` and the all-projects search match it (see [Search](SEARCH.md)).

Both are returned as text, escaped by every page that shows them, so markup in an alias reads as markup, never as HTML. `note` is free text like a finding comment: the request input guard does not scan it. The alias is scanned like any other short field, so a value that looks like a shell command or a script tag is refused and counts as a strike. In MCP results they are text a person typed and, like every other text in a result, data and not instructions.

Where they live: a target's on the target (`alias` and `note` in `list_targets` and `get_target`); a host's on the project's record for the host name (`HostProfile`, one row per project and lower-case name), so they survive rescans, which write new scan rows but keep the name, and they are lost only with the host's data (`delete`) or moved with it. Names that resolve to exactly the same addresses are one host in the Hosts list, shown under one name: the host's own alias and note are used if its shown name has them, else those of another of its names (so typing an alias while one name was on display still shows when another name takes its place), else, when the host is also a target of the same name (an address added as a target), the target's. Each host in `list_hosts`, `search_hosts` and `get_saved_search_matches` carries `alias`, `note` and `alias_from` and `note_from` (`host`, `target` or empty: where the value came from). Do not confuse `alias` with the existing `aliases`, the other DNS names on the host's addresses. A host or target without either returns empty strings, and `profile` keeps its shape (`owner`, `purpose`, `criticality`).

`delete` removes one host's data from this project only: its findings, CVE matches, routes, changes, triage, certificates, and asset information. A later scan can find the host again.

`exclude` is organization wide: it deletes the host's data from every project of the organization you can write to, and no stage touches it again in any of them. It needs an organization-level role, and organization admins lift it with `DELETE exclusions/{host}`. Names match whole and case-insensitively: excluding `provider.example` leaves `www.provider.example` alone, and wildcards are a `400`. Send `"with_aliases": true` to take the other names the project shows as the same host (same addresses) with it, and `"include_subdomains": true` to exclude a whole domain (`provider.example`, every name under it and the targets named like them; scans of those targets are stopped; `co.uk`-style suffixes and addresses are a `400`). `delete` takes `with_aliases` too. In `add_targets` a line starting with `-` (`-provider.example`) does the whole-domain exclusion and the response lists it under `excluded`. Removals are audit logged.

**Addresses we must never scan.** `GET projects/{slug}/excluded-addresses` (MCP `list_excluded_addresses`) is the organization's do-not-scan list of IPv4 and IPv6 addresses and CIDR networks, each stored normalised (a bare address is a /32 or /128, host bits are cleared, IPv6 is compressed) with its note, who added it and when. It is read only here; organization admins and App Admins edit it in Administration (Organizations, "Addresses we must never scan"), where every change is audit logged. A name list cannot protect an address, so this one is matched on the address: the server creates no Sentinel task of any kind for an address inside a listed network, nor for a host whose resolved addresses (the inventory's stored ones, or the answer of a lookup a task made) fall inside one; a queued task is not leased once its address is listed, and a result that comes back for a listed address is dropped and logged. A list that cannot be read refuses address work for that project and says why; it never lets work through. Adding an entry cancels the tasks already queued for it, with the reason on each task. `?host=<name or address>` answers `{host, excluded, reason}`. Private ranges are valid entries; `0.0.0.0/0` and `::/0` are never accepted, a network broader than /8 (IPv4) or /32 (IPv6) needs an explicit confirmation, and a list holds at most 500 entries. The activity feed says `Skipped N hosts that resolve to an address on the organization's do-not-scan list` once per host, and the host row shows `scan_blocked` with the reason.

## Hosts and search

Hosts carry `score` (0 to 100) and `score_detail`, and come highest score first (`sort=name` for name order). Names that resolve to the same addresses are one host, so the list returns one row per host that covers all its current rows, with the other names in `aliases`. `labels` holds short informational detections such as a WAF or federated sign-in. See [Host score](PIPELINE.md#host-score).

`search?q=...` returns hosts with `matched` showing what each query hit. Terms are separated by spaces and ANDed. A bad value for `sev:`, `auth:`, `sensitive:`, or `zombie:` is a 400. The full syntax, with examples, is in [SEARCH.md](SEARCH.md).

| Term | Matches |
| --- | --- |
| `php` | a bare word in hostname, IP, technology, headers, cookie names, port product, service, version, CPE, banner and script output, OS, finding name, CVE id, or page title |
| `tech:nginx` | anything the host runs: technology, `Server` and `X-Powered-By` headers, product, version, CPE, banner, script output, cookie names |
| `product:nginx`, `service:mysql`, `os:linux` | port product, service name, OS guess |
| `banner:"anonymous"` | service banner, script output, or extra info on an open port |
| `port:3306` | open port number (a number only; `port:ssh` is a 400) |
| `cve:CVE-2024-1234` | CVE match |
| `ip:10.0.0.5`, `ip:10.0.0.0/24`, `ip:10.0.` | an IP, any IP in a CIDR range, or an address prefix |
| `host:www` | hostname |
| `vuln:rce`, `sev:high` | finding name, severity |
| `auth:<state>` | hosts with a web route in that state (any state listed under Routes) |
| `sensitive:any`, `sensitive:credentials`, `sensitive:pii`, `sensitive:internal` | hosts with a route serving that kind of sensitive data |
| `secret:any`, `secret:s`, `secret:p`, `secret:i`, `secret:live`, `secret:<provider>` | hosts that serve an exposed secret the inventory counts (a class, a validated live one, or a provider) |
| `zombie:yes`, `zombie:no` | hosts whose name is gone but whose last address answers |
| `country:US`, `country:Germany` | the ISO code or name of a host IP's geolocated country |
| `-term`, `"apache tomcat"` | negate a term, or match a phrase |

`?heat=fire|smoke|ice|clean|unscanned` narrows the page to that heat, the same value each host's own `heat` field carries. The response's `facets.heat` always counts every one of those five values over the whole match of `q`, ignoring `heat` itself, so a UI's heat chips keep their real totals while one is selected. Both the filter and the facet count stop after 5,000 matched hosts (`facets.truncated: true`); a search that wide needs narrowing with `q` regardless.

Any field filter's value takes a comma-separated list for OR within that one filter, Shodan-style: `port:80,443` is port 80 or 443, still ANDed with every other term. Quote the value to keep a literal comma (`tech:"foo,bar"`): it is then never split.

`?facets=port,product,tech,os,country` (comma-separated) adds the same whole-match, heat-chip-style counting for those fields: the response's `facets.port`, `facets.product`, and so on are each `[{value, count}]`, highest count first, up to `?facet_size=` values (default 10, max 50); `count` is the number of distinct hosts with that value, over the same (and equally 5,000-capped) match `facets.heat` counts. `org:`, `asn:`, and `hosting:` filters and facets were asked for too, but nothing in CVEngine looks up an IP's ASN or hosting provider today (only its country, via `geoiplookup`), and adding that is its own feature, not implemented here.

Ports are stored per IP, so `product:nginx` finds only hosts whose own IP runs it.

## Saved searches

A saved search is a `search_hosts` query kept on the server, re-run on a schedule, with alerts through the notification channels ([SEARCH.md](SEARCH.md#saved-searches-and-alerts)). It is private to its owner inside one project: another member, or a user of another project, gets 404 for it, and `_all` is a 400. Reading (`list`, `get`, `matches`) needs the access the search itself needs. Creating, changing, deleting and running one need any role except audit and a token that is not read only, because a run can notify.

`POST projects/{slug}/saved-searches` takes `name` (clipped to 80 characters), `query` (checked like a live search: an empty query, an unusable filter value, more than 15 terms or 1,000 characters is a 400), and optionally `enabled` (default true), `alert_new` (true), `alert_gone` (false), `threshold` (null, or 1 to 1,000), `channels` (a list of `slack`, `discord`, `telegram`, `lark`; empty means every channel Settings has on) and `frequency` (`hourly`, `daily` default, `weekly`). Unknown fields, a wrong type, a duplicate name (per owner and project, ignoring case) and the caps (25 per user, 100 per project) are 400s. `PATCH` takes any subset; a new `query`, or switching `enabled` back on, restarts the baseline.

A saved search row has `id`, `project`, `name`, `query`, `enabled`, `alert_new`, `alert_gone`, `threshold`, `channels`, `frequency`, `baseline` (false until the first check), `last_run_at`, `next_run_at`, `last_match_count`, `last_status` (`ok`, `too_broad` for more than 1,000 matches, `error`, `disabled`), `last_error`, `last_alert_at`, `created` and `updated`. The list also returns `limits` and `channels_available` (names only). A search whose owner lost access to the project, or whose account is deactivated, is switched off at its next check: `enabled` is false, `last_status` is `disabled`, and `last_error` says why.

`POST .../{id}/run` evaluates the search now, as the schedule would: it compares with the last check, alerts if asked, and answers `{status, count, new_count, gone_count, baseline, alerted, new: [up to five names], saved_search}`. The first run only records the baseline (`baseline: true`, `alerted: false`). A disabled search is a 400, a second run within 30 seconds is a 429, and one that is being checked right now is a 409. `GET .../{id}/matches` is `search` with the saved query (`page`, `page_size`, `sort`, `heat`, `facets`, `facet_size`) plus `saved_search`; it never touches the baseline.

## Routes, changes, and activity

- **`routes`** lists web routes with `auth_state` (`open`, `login`, `session_required`, `sso`, `redirect`, `not_found`, `catch_all`, `error`), `redirect_to`, and `evidence` (markers, never page content). `sensitive` holds `{type: {count, sample}}` with the sample already masked, and `sensitive_score` runs 0 to 25. Raw values are never stored or returned. `retired_at` and `zombie_since` mark route lifecycle, and `sensitive=1` or `zombie=1` filter.
- **`changes`** lists inventory changes newest first. `since` is an ISO 8601 datetime or `24h`, `7d`, `4w`. `kind` is one of the kinds in [Changes](PIPELINE.md#changes), and `host` matches part of a hostname. Each row has `before` and `after`.
- **`activity`** is the AI activity log for the project plus system-wide entries. `kind` is `feed`, `inventory`, `target`, `confirm`, `write_check`, `run_check`, `validate`, `discovery`, `scan`, `hygiene`, `changes`, `remediation`, `saved_search`, or `runzero` (one line per runZero sync).

## Triage and remediation

List endpoints (`vulnerabilities`, `matches`, `routes`, `hygiene`, `work`) carry a `triage` object with `classification` (`confirmed`, `likely`, `needs_validation`, `likely_false_positive`, `not_applicable`), `status`, `validation_status`, `overridden`, `first_seen`, and `last_seen`. `vulnerabilities` and `matches` accept `?classification=`, and `vulnerabilities` accepts `?severity=actionable` to skip info rows. `ai_verdict` on a match is the older view: `confirmed` and `likely` are `affected`, `needs_validation` is `uncertain`, and the false-positive classes are `not_affected`. See [Triage and validation](PIPELINE.md#triage-and-validation).

`findings/{kind}/{id}` returns one finding in full: why it matters, how it was found (with request and response excerpts capped at 4 KB, returned only here), its history, the AI's classification and whether a rule overrode it, remediation, and every validation check with the command a person can repeat. A CVE match also includes the feed description, affected products and ranges, HTTPS advisory links, feed sources, and nullable exploitation signals. Those signals describe the CVE; they do not prove a particular host is vulnerable.

**Validate a match.** `POST projects/{slug}/matches/{id}/validate` queues the same workflow as **Validate now**: an AI plan, the checks it chose from those the scope and template policy allow, and an AI review of the evidence. Without a provider, the policy-approved checks run on their own. `GET .../validate/{request_id}` returns `queued`, `running`, `completed`, or `failed`, with the plan, the checks that ran, and the resulting classification. A match with an active request, or one finished in the last 5 minutes, returns that request. Each project allows 10 in progress and each user 20 requests an hour (429). The worker rechecks the requester's current access before it runs anything, and `retriage` uses the same queue.

**Diagnostics.** When an AI call fails, the finding keeps a retriable `error` status and an `ai.diagnostic` object (also shown as **Copy diagnostic**). It names the stage and a category such as `provider_auth` (check the key), `output_truncated` (check the model's output limit), or `schema_invalid` (the reply did not fit the triage format). It never contains credentials, prompts, model output, or target content, so it is safe to share.

`validation_status=observed` means a check read a banner or version without running a CVE-specific detector: it records what was seen, not a verdict.

**Remediation loop**

1. `register_assets` with the hosts, IPs, or CIDRs the agent is responsible for.
2. `get_remediation_work` returns open CVE-on-host items for those assets, fire first, with the host's IPs and the CVE's fixed versions. Fixed, accepted-risk, false-positive and closed matches are left out, and `?include_fp=0` also drops likely false positives. There is one item per upgrade: if the same upgrade of the same component on one host fixes several CVEs (CVE-2020-11022 and CVE-2020-11023 on jQuery 3.4.1, both fixed in 3.5.0), they are one item. Its `cves` and `match_ids` list them all and `upgrade_to` is the version that fixes them. `count` counts items and `matches` counts the matches behind them. With `?tier=fire|smoke|ice` the tier narrows the query in the database (the same heat rule as every other list), so a fire item is found however low it ranks. At most 2,000 matches of the project are read, best ranked first (highest confidence); `truncated` is `true` when the project has more than that, so the list is the best-ranked part. It refers to the project-wide 2,000, before `?assets=` narrows them: with `assets` set it can be `true` even when none of the 2,000 belong to those assets, and the asset filter only looks at the 2,000. `count` and `matches` of a tier on a project with more than 2,000 open matches are higher than they were, because the old tier filter ran after the 2,000 were cut.
3. `update_remediation_status` (once per id in `match_ids`) sets `open`, `in_progress`, `fixed`, `accepted_risk` or `false_positive` with a note on why.

Matches also carry `distro_status` (`patched`, `vulnerable`, `unknown`, `no_data`), `distro_label`, `evidence`, and the template test result (`vulnerable`, `no_match`, `error`).

**Remediation status on scanner and hygiene findings.** CVE matches, scanner findings, and hygiene findings each carry the same `remediation_status` (`open`, `in_progress`, `fixed`, `accepted_risk`, `false_positive`), `remediation_note`, and `remediation_updated` fields, driven entirely by people or agents, never by a scan. They are independent of the finding's own auto-managed liveness signal (a CVE match's `ai_verdict`, a scanner finding's `open`, a hygiene finding's `status`): a scan re-detecting a finding never undoes a `fixed`, `accepted_risk` or `false_positive` mark (the next scan's copy of the finding inherits it, note included), and marking one of those statuses drops the finding out of `findings?status=actionable` (and the host's heat, score, exposure counts, fire notifications, OpenVAS selection and remediation work) immediately, whether or not the underlying check still finds it. The one exception is a hygiene finding marked `fixed` that a later check finds again after it was resolved: that is a regression and reopens; a `false_positive` or `accepted_risk` one stays closed.

**Closing a finding: false positive and the closure note.** `fixed`, `accepted_risk` and `false_positive` close a finding. `false_positive` says the finding is not real on this host (the scanner or the correlation got it wrong), as opposed to `accepted_risk` (real, and the project lives with it) and `fixed`. Any status change takes an optional `note` on why: at most 2,000 characters, stripped, with control and invisible formatting characters removed (`400` for a longer one or one that is not text, before anything is written). The API accepts a closure without a note, `false_positive` included; the web UI asks for a note on every closure and will not mark a false positive without one. Every match, scanner and hygiene response (list rows, `findings` rows and detail, where it is also under `remediation`) carries `closure_note`, `closed_by` (`{id, username, name}`), `closed_at` and `closed_automatically`: for a finding a person closed, the note, who and when; for one the engine closed on its own, the reason it stored (a CVE match the AI or a correlation rule ruled out, `ai_reason`, such as "Closed automatically: different product"; a scanner finding a later scan no longer reports; a hygiene finding a later check no longer finds), `closed_by` `null` and `closed_automatically` `true`; all `null` for an open finding. An automatic closure keeps its own reason and is never labelled `false_positive`; a person's closing status wins over it. Each change is written to the audit trail (`before {status}`, `after {status, note}`, the note left out when none was sent) and to `activity` (`kind=remediation`, its detail `before`, `after` and `note`). The same role gate as every other write applies: a read-only token or the audit role gets `403`. `findings?status=` also takes `closed` (any closing status) and each closing status alone (`fixed`, `accepted_risk`, `false_positive`), and `matches?status=` takes any status or `closed`. Reports with closed findings print each one's status and closure note ("Why it was closed") and a count by status.

`PATCH projects/{slug}/findings/{kind}/{id}` (`update_finding_status`, `kind` one of `match`, `vulnerability`, `hygiene`) sets one finding's status and note; `kind=match` is identical to `PATCH .../matches/{id}`, kept as its own endpoint for the simpler single-kind case. `POST projects/{slug}/findings/status` (`bulk_update_finding_status`) sets the same status and note on up to 200 findings in one call, `{items: [{kind, id}, ...], status, note}`, and answers `{updated, failed: [{kind, id, error}]}` so one bad id never blocks the rest. A web route has no remediation workflow (its `auth_state` already says what it needs), so `kind=route` is a `400`. Every write here is logged to `activity` as `kind=remediation`.

**Retest on fix.** Setting a CVE match, scanner finding or hygiene finding to `fixed` (`PATCH .../findings/{kind}/{id}`, `PATCH .../matches/{id}`, the bulk call, `update_remediation_status`, `update_finding_status`, or an agent's `fixed` report) queues a retest: the same check that produced the finding's proof runs again on a Sentinel, through the validation dispatch. Every finding row, finding detail and match carries `retest`: `{state, label, text, at, sentinel, reason, can_retest}`. `state` is `""` (not marked fixed), `verifying` (queued or running), `verified_fixed` (the check ran, the host answered, and it no longer reproduces the finding; the only state that means fixed), `still_reproduces` (it does: the finding was reopened with `remediation_status` open, the new exchange replaced the old proof in `validation.evidence`, and the audit trail has a `status` event with no actor and a `retest` event), `not_verified` (fixed, not verified: no Sentinel could take the check, the host did not answer, the check failed or is gone; `reason` says which; tried again after a day, then two, four and seven, six tries at most, never more than once a day) or `no_check` (marked fixed, cannot be re-checked automatically: no stored check or evidence; never verified). `GET .../findings/{kind}/{id}/retest` answers `{kind, id, status, retest, history}` where each try in `history` (newest first, ten at most) has `outcome`, `reason`, `source` (`automatic`, `manual` or `retry`), `sentinel`, `checks`, `evidence` (a summary and the request and answer of the new exchange), `attempt`, `requested`, `finished`, `next_attempt` and `requested_by`. `POST` the same path is Retest now: 202 with the same body plus `queued`; 400 unless the finding is fixed; a retest already running is not queued twice; it needs the permission that changes a status. `list_findings` takes `status=verified_fixed`, `unverified_fixed` or `reopened`, and answers `retest` with the three counts. An agent should treat only `verified_fixed` as fixed, and the AI reviewer never closes a finding on "marked fixed" alone.

**Re-rating a finding by hand (heat override).** cvENGINE derives a finding's heat ([Fire, smoke, and ice](FIRE-SMOKE-ICE.md)); when a person or an agent has reviewed it and knows better, `POST projects/{slug}/findings/{kind}/{id}/heat` (`set_finding_heat` with `kind` and `id`; `kind` `match` or `vulnerability`) with `{heat: "fire"|"smoke"|"ice", reason}` sets the heat it shows, and `{heat: null}` (or `""`) clears it back to the derived one. `reason` is required when setting (at most 1,000 characters, cleaned like a closure note); `400` for any other heat, a missing reason, or `kind` `hygiene` or `route` (they have no heat). `POST projects/{slug}/findings/heat` (`set_finding_heat` with `items`) sets one heat and one reason on up to 500 findings, `{items: [{kind, id}, ...], heat, reason}`, and answers `{updated, unchanged, failed: [{kind, id, error}]}` (one bad id never blocks the rest; another project's finding is a `404` in `failed`). One finding answers `{kind, id, heat, heat_reason, heat_override, changed}`; the same heat and reason again change nothing (`changed: false`). The same role gate as a status change applies (a read-only token or the audit role gets `403`, `_all` a `400`, another project's finding a `404`). The heat set wins everywhere a heat is read: `findings` rows, its `heat=` facet and `counts`, a match's `cve.tier` and `cve.validation_tier` (so the validation and OpenVAS order follow it), host heat, score and `heat_reasons`, the dashboards, reports and the graph. `heat_reason` then reads `set to smoke by alice: <reason>`, and match, scanner-finding, `findings` row and finding-detail responses carry `heat_override`: `{heat, reason, by: {id, username, name}, at}`, or `null` while the heat is derived (`get_finding` also carries `heat` and `heat_reason` for a match or scanner finding). Each change is written to the finding's audit trail (`event: heat`, `before {heat, override}`, `after {heat, override, reason}`, `heat` being the heat shown) and to `activity` (`kind=remediation`). A CVE match that a change makes show fire (raised by hand, or cleared back to a derived fire) is paged like any match that becomes fire, once (claimed under the heat rule in force, so it is never paged again by a later read, a re-rating or proof arriving); a closed or ruled-out match is never paged, and lowering a heat never pages. Triage, a fresh AI review and validation never clear a heat set by hand, and a rescan's copy of a match keeps it when the evidence is the same (the AI review's record carries over the same way); a rescan that changes the match's evidence starts it over with the derived heat.

`note` on every one of these routes, `update_remediation_status` included, is a true partial-update field: leave it out of the body and the stored note is untouched; send `""` (or any string) and it replaces it. Earlier, an omitted `note` was treated the same as an explicit `""` and silently cleared it.

Every match, scanner, and hygiene response (detail and `findings` rows alike) also carries `status_changed_at` and `status_changed_by` (`{id, username, name}` or `null`): the same moment and actor as `remediation_updated` and the write that made it, under names that read naturally for aging and SLA display. `findings` rows carry `first_seen` alongside the existing `detected` (the same moment); the type-specific list and detail endpoints already had `first_seen`.

**Assignee, comments, and audit trail.** Every match, scanner, and hygiene response (rows and detail alike) carries `assignee` (`{id, username, name}` or `null`) and `comment_count`. `PATCH projects/{slug}/findings/{kind}/{id}` (and `PATCH .../matches/{id}`) now takes `status`, `note`, and `assignee` as independent partial-update fields, at least one of `status`/`assignee` required: `assignee` is a user id, or an explicit `null` to unassign, and an id naming someone who cannot see the project is a `400`. `GET/POST .../findings/{kind}/{id}/comments` (`kind` one of `match`, `vulnerability`, `hygiene`; body `{text}`, up to 4,000 characters) lists comments oldest first and adds one; commenting is a write like any other, so read-only tokens and the audit role get `403`. `GET .../findings/{kind}/{id}/audit` answers the finding's trail newest first, `{results: [{id, event, actor, before, after, created}]}`, `event` being `status` (`before`/`after` `{status}`), `assignee` (`before`/`after` `{assignee}`), `comment` (`after` `{comment_id, text}`) or `heat` (a heat set or cleared by hand: `before {heat, override}`, `after {heat, override, reason}`); bulk status changes are audited per finding. `GET projects/{slug}/members` lists the project's direct members and its organization's, for an assignee picker (a superuser with no membership row is not listed). Validation runs are not yet written to the audit trail; the event enum can grow without changing any shape. `finding_detail` (`GET .../findings/{kind}/{id}`) now also reports `remediation.status`/`note` for scanner and hygiene findings, not only matches.

**API keys and runZero.** A project's own key replaces its organization's for every scan of the project, so `PUT` and `DELETE` need the project or organization admin role (`403` for a plain member; `can_edit` in the list says which the caller is). `GET projects/{slug}/api-keys` lists every service with `configured`, `scope` (`project`, `org` or `null`), `used_in_scans`, `used_by_sync` (the runZero key is read by the scheduled sync, not a scan) and `retired` (`null`, or the reason: BinaryEdge was shut down in March 2025, so `PUT` for it answers `410` and a key saved earlier is listed, unused, and can be deleted). `GET projects/{slug}/runzero` answers the runZero sync of the project: `{configured, import_enabled, search, state: never|running|ok|error, last_sync_at, last_ok_at, last_error, counts, interval_hours, import_max}`; `counts` is `{assets, matched_hosts, updated_hosts, cve_reports, corroborated_matches, truncated}` plus, when import is on, `imported` and `skipped` (`already_known`, `blocked`, `excluded`, `invalid`, `name_out_of_scope`, `over_cap`, `rejected`). `PUT` takes `import_enabled` (boolean, default off: add the addresses runZero knows and cvENGINE does not as targets, through the checks Add targets applies) and/or `search` (runZero inventory search limiting the import, at most 300 characters, blank means `alive:true`). `POST projects/{slug}/runzero/sync` queues a sync (`202 {queued: true}`; `409` while one runs, `429` within a minute of the last start, `400` with no token saved). All three need the organization admin or App Admin role (`403` for anyone else) and never return the token. A host's `ips[].runzero` carries runZero's facts for that address (`os`, `os_version`, `hw`, `type`, `tags`, `site`, `names`, `last_seen`, `vulns`: runZero's own CVE reports, evidence only), or `null`. A host record also carries `probes` (what version and identity probes found: `probe`, `kind` version, identity or edge, `product`, `version`, `variant`, `outcome` found, hidden, edge, challenged or absent, `source`, `confidence`) and `wordpress` (`status` with the state, why and when WPScan ran, `core`, `plugins` and `themes` with versions), or `null`.

**Third-party suppliers.** A supplier is a vendor the project depends on, never an owned host: it is not a target and none of the host, finding, hygiene, stats or remediation routes ever list it ([Pipeline](PIPELINE.md#third-party-suppliers)). `GET projects/{slug}/suppliers` answers `{count, page, results: [{id, name, tier, domains, contact, notes, added_by, created, last_checked, findings: {open, accepted, false_positive, critical, high, medium, low}, hosts}], can_edit, limits: {max_suppliers, max_domains}, checks_enabled}`. `POST` takes `{name, domains: [...], tier: critical|high|normal, contact?, notes?}` and answers `201`; it is refused with `400` for a domain that is one of the project's own targets (or under one), an address, range, wildcard, URL, private name or excluded name, `409` for a duplicate name or the cap, `403` for anyone but the organization admin or App Admin (the audit role, a member and a read-only token included). `DELETE .../suppliers/{id}` removes a supplier with its cards and findings. Everyone with access to the project can read. `GET .../suppliers/hosts` answers the **host cards**: `{domain, supplier: {id, name, tier}, state (ok, unreachable, no_address, blocked, challenged, excluded), addresses, http: {https_status, http_status, status, title, server, powered_by, headers, cookies, ...}, tls: {subject, issuer, sans, not_before, not_after, days_left, key, signature, protocol, cipher, chain_error, legacy_tls}, technologies: [{name, version, category, source}], mail, evidence, checked, last_ok, matched}`. `?tech=php,node` is the **technology search**: comma separated terms, any of which matches anywhere in a technology's name and version or in the Server and X-Powered-By banners (`php 7`, `nginx 1.1`); `matched` lists the technologies that matched; `?supplier=` and `?tier=` narrow it. `GET .../suppliers/technologies` lists what the suppliers run, most widespread first (`name`, `category`, `suppliers`, `hosts`, `versions`). `GET .../suppliers/findings` lists the informational posture findings (`status` open by default, `accepted`, `false_positive`, `resolved` or `all`; `supplier`, `severity`, `category` tls, email, web, exposed or cve); each carries `ask`, the plain-text note about what to ask the supplier, and a `cve` finding says `validated: false` in its evidence. `PATCH .../suppliers/findings/{id}` (`{status: accepted|false_positive|open, note?}`, admin only) accepts a finding, closes it as a false positive (the check got it wrong: the sweep then leaves it as it is, never resolving or reopening it) or opens it again, with a note on why (at most 2,000 characters, cleaned as above; written to the audit log with the status before it); `resolved` is set only by a later check. A finding carries `status_note`, `status_by`, `status_at` and the same `closure_note`, `closed_by`, `closed_at`, `closed_automatically` as other findings (a `resolved` one is closed automatically). `GET .../suppliers/{id}/summary?tech=` answers `{supplier, text, open}`, a plain-text message to copy and send (nothing is sent by cvENGINE). Text in cards and findings comes from the supplier's own responses and is untrusted data.

**Project settings and SLA days.** `GET projects/{slug}/settings` answers `{sla_days: {critical, high, medium, low}, sla_defaults}`: how many days a finding of each severity has to be fixed, the same for everyone in the project so "overdue" reads the same on every screen (defaults 7, 30, 90, 180; informational findings have no SLA). `PUT` changes it, `{sla_days: {...}}` as a partial update: send only the severities to change, each a whole number of days from 1 to 3,650, or `null` to go back to that severity's default. Anyone with a write role may change it, as with the project's API keys (a read-only token or the audit role gets `403`; the audit role can read). A finding is overdue when `first_seen` plus its severity's days has passed and its `remediation_status` is not `fixed`, `accepted_risk` or `false_positive`. Single-project only: `_all` is a `400`.

**Activity per day.** `GET projects/{slug}/activity-days` (`activity_days`) is what the dashboard's Activity card, the Scans page's activity chart and the Changes page's chart draw. The database counts, exactly, one grouped query per series: `findings` (the rows the Findings list shows with `status=all`, counted by the day first seen, split into `fire`/`smoke`/`ice` and by type), `changes` (the rows of the Changes list, by the day detected) and `scans` (started per day; asked for with `series=scans`). `?days=` is the number of calendar days ending today (default 90, at most 366), `?tz=` an IANA zone that decides where a day starts (default UTC), `?series=` a comma list (default `findings,changes`). Each series answers `{total, busiest, days: [{date, n, ...}]}` with only the days that have any, and `total` is the sum of those days; `since` is the first instant of the window, so `changes?since=<since>` lists exactly the changes counted. Nothing is sampled or capped. The answer is a shared snapshot of 30 seconds that a closed finding drops at once, like the dashboard counters.

**Stats history.** `GET projects/{slug}/stats/history` (`stats_history`) answers a bare JSON array, oldest first, of one point-in-time snapshot per day: `{date, hosts, exposed_hosts, open_findings: {critical, high, medium, low, info}, cve_matches: {fire, smoke, ice}, fixed, mean_days_to_fix}`. `?days=` bounds the window (default 90, capped at 365) to a number of calendar days ending today. Snapshots are written once a day by a beat task (`cveFeed.tasks.snapshot_daily_stats`, `cveFeed.stats_history`); a day before the feature existed, or one the task missed, is simply absent rather than backfilled. `_all` sums every visible project's rows per date; its `mean_days_to_fix` is the unweighted mean of the projects that have one that day, since the per-finding durations themselves are not stored.

- `scanning` and `update`. An App Admin gets `scanning` with paused, reason, who, since when, the last error, and whether an update's drain paused it, and `update` with the phase and its detail. Also `version`, `at` (when the snapshot was taken), and `scope` (`instance` or `projects`).
- `projects`: for up to 100 of the projects the caller can see, `targets`, `hosts`, `exposed_hosts`, `scans` (`running`, `queued`, `stalled`), `open_findings` by severity and `cve_matches` by heat; `totals` adds up those 100. These per-project counts are reused for each caller and project for `CVENGINE_STATUS_CACHE_SECONDS` (default 60, `0` turns the cache off), so a poll is not a fresh count every time; the `system` block is never cached.
- Each project's row carries `screenshots`: `{hosts_with_web, hosts_with_screenshot, queued, failed, blocked, nla_required, pages (by outcome), last_error, available, unavailable_reason}`, how many of the hosts with a web page have a browser picture, what waits, what failed and why the last page failed ([Web screenshots](PIPELINE.md#web-screenshots)). - Each project's row carries `wordpress`: `{hosts, scanned, never_scanned, reasons}`, the WordPress hosts WPScan covered and, by state (`blocked`, `failed`, `waiting`, `detected`, `candidate`, `unavailable`), why the rest were not.
- `system`, for an App Admin only (anyone else gets `null` and a `system_note`): `database` and `broker` (reachable, latency), `queues` (messages waiting per Celery queue, and taken but not acknowledged), `workers` (which worker answers and whether it consumes its queue), `jobs` (pending validation, retest, scan and host-assessment work), `work` (the work conductor: `wanted_depth`, `running`, `queued`, `paused`, `targets` (any target in a project), `due` (a target is due to start now, by the conductor's own rules: not scanned inside the minimum gap, not manual, excluded, bounty-blocked or internal-only; `null` if it could not be read), `last_round` and `last_round_age_seconds`; a problem is raised only for a due target with nothing running or queued, a last round older than five minutes while beat ticks, or a last round with an error, never for an idle conductor with nothing due, and it states the time as a span, not a clock time), `schedules` (how many are enabled and which are past due), `memory` per scanner container (total, used, available, the job budget, jobs running and waiting, memory kills in 24 hours, how old the report is), `disk` for the scan results volume, `feeds` (CVE count and last feed dispatch), `ai` (whether a provider is on, today's validation attempts, and `autotune_advisor_today` `{used, cap, since}`), `autotune` (the auto-tuner: `mode`, `effective_mode`, `killed`, the advisor, `sized_for` (what this machine was sized from), `targets` per setting, `last_run_at`, `held` (why the last run changed nothing, for example scanning paused), `changes_last_run`, `why_not_raised` per setting, `pinned`, and the last five decisions), `work` (the work conductor: scans running and queued, the wanted depth, and the last round), `certificate` (the web interface certificate as the host's renewal check reports it: `known`, `not_after`, `days_left`, `state` of `ok`, `expiring` under 30 days, `expired` or `unknown`, `last_checked_at`, `last_renewed_at`, `last_result` of `kept`, `issued`, `external` or `failed`, `error`, `problem`; **Outbound connection log.** `GET egress/connections` (`list_egress_connections`), App Admin only (403 for anyone else, read-only tokens may read): one record per outbound connection this server's scanners open to a logged port (not its own mail notifications) (`CVENGINE_EGRESS_LOG_PORTS`, default 25, 465 and 587), newest first, `{id, at, address, port, outcome, mode, kind, project, scan_id}`. `outcome` is `sent`, `paced` (held back by the hourly budget; the paced pass probes it later and logs that too) or `skipped` (on `CVENGINE_LOCAL_SKIP_PORTS`). `mode` is `exact` when this server's own code opened, or refused to open, that very connection (the in-process probes, the database checks, a held connection) and `estimated` when an external tool (nmap, naabu, testssl.sh, nuclei) was handed that address and port in its probe plan: the tool's own packets are not watched, so an estimated record says it was planned and sent to the tool, not how many packets left. Filters `port`, `project` (slug), `since` and `until` (ISO 8601 or epoch seconds); `limit` up to 1000 (default 100) and `cursor` (the `next` of the previous page). `?format=csv` downloads every matching record (`time_utc, destination_address, destination_port, outcome, exact_or_estimated, tool, project, scan_id`), as does the link on Settings, configMaxxing, **Outbound connections**. Kept `CVENGINE_EGRESS_LOG_DAYS` days (14) and at most `CVENGINE_EGRESS_LOG_MAX` records (200,000), the oldest dropped first, in Redis.

Problems include a web interface certificate with fewer than 30 days left, expired, or whose automatic renewal failed, a disk under 10 percent free, a CVE feed older than 48 hours, nuclei templates not refreshed for over 36 hours, and "nothing running or queued though targets exist".

Each probe is independent: one that fails or times out comes back as `{"error": "<exception name>"}` and a line in `problems`, never as a failure of the whole call. It returns no address, credential or task argument. Asking the workers takes up to ten seconds when none respond. A read-only token may call it.

**Auto-tuning.** The throughput settings of Settings, configMaxxing are tuned by the instance itself unless a person pinned them ([Configuration](CONFIGURATION.md#auto-tuning)). It belongs to the whole instance, so every route and tool below is for an App Admin (403 for anyone else, also for reading) and a change needs a token that can write; each change is audited.

- `GET tuning` (`get_tuning_status`): `mode` (`off`, `suggest` or `auto`, the default) and `effective_mode` (`off` while `CVENGINE_AUTOTUNE=0`, the kill switch, with `killed: true`), `advisor` (`enabled`, `provider`, `used_today`, `cap`, `interval_hours`, `last_at`, `last_error`), `tuned` (the numbers it chose that apply now), `pinned` (settings a person saved, or an environment variable set to something other than its default, with `by` and `from`: `saved` or `environment`), `managed` (each tuned setting with `min`, `max`, `step`), `last_run` (per setting: value, state, `target` sized for this machine with `target_reason`, and `why_not_raised`), `sized_for`, `facts` and `recent_decisions`.
- `GET tuning/decisions?setting=&limit=&offset=` (`list_tuning_decisions`): newest first, each with `old_value`, `new_value`, `source` (`controller`, `ai` or `person`), `action` (`raise`, `lower`, `apply`, `revert`, `release`), `phase` (`aim_high`, `back_off`, `probe`, `cap`, `emergency`: backed off from Redis while the database did not answer, `recover`: restored after it), `applied`, `pressure` (a back-off forced by trouble), `reason`, `resolution`, `can_apply` (an open recommendation) and `can_revert` (the newest applied change of its setting).
- `PUT tuning/mode` (`set_tuning_mode`): `{"mode": "off"|"suggest"|"auto"}` and/or `{"advisor": true|false}`. Leaving `auto` drops the tuned numbers at once.
- `POST tuning/decisions/{id}/apply` (`apply_tuning_suggestion`): in `auto` the recommendation becomes the tuned number; otherwise it is saved as your value, which pins the setting. 409 when the setting changed since the recommendation.
- `POST tuning/decisions/{id}/revert` (`revert_tuning_decision`): the newest applied change of a setting only (409 otherwise); its layer gets back exactly what it held, and the tuner does not raise that setting for 24 hours.
- `POST tuning/release` (`release_tuning_pin`), `auto` only: `{"setting": "<key>"}` removes the saved value of a pinned setting and gives the same number to the tuner.

### Grouped findings

The same library file on sibling hosts of one site (jQuery 3.2.1 on `www.`, `blog.`, `info.`, `careers.`, `learn.` and `donate.example.com`) is one problem, but it is one CVE match per host. `GET projects/{slug}/findings?group=cve` (MCP `list_findings` with `group: "cve"`) folds those matches into one row. The default, `group=none`, is one row per host exactly as before, so existing callers see no change.

**What is grouped.** Only a technology fingerprint of a web page (`source: tech`) with a version whose product is a client-side JavaScript library or framework the browser downloads: an explicit allow-list (`CLIENT_SIDE_LIBRARIES` in `web/cveFeed/finding_groups.py`: jQuery, jQuery UI and Migrate, Bootstrap, AngularJS and Angular, React, Vue, lodash, Underscore, Moment, DataTables and the like, plus every name of the fingerprint table's `javascript library` category). Web servers, languages, CMSs, proxies and CDNs, databases, server-side frameworks and any product the list does not name are never grouped, whatever their evidence: nginx 1.18.0 on `www.` and on `mail.` is two machines and stays two rows. Port banners, host inventory reports and CPE matches are never grouped either. Library matches are grouped by project, CVE, product, version, the host's registrable domain and the script identity: the evidence's `script_sha256` when the probe recorded the file's hash, else its `script_url` (the path when the script is served from the site's own registrable domain, host and path when it comes from elsewhere such as a CDN), else nothing more (then by CVE, library, version and site). A group never crosses projects (so never organizations) or registrable domains. The registrable domain comes from the public suffix list bundled with `tldextract` (no network) including its private section, so each tenant of a hosting provider (`acme.github.io`, `x.blogspot.com`, `a.ngrok.io`, `a.trycloudflare.com`, `*.herokuapp.com`, `*.netlify.app`, `*.vercel.app`, `*.pages.dev`, `*.workers.dev`, `*.web.app`, `*.firebaseapp.com`, `*.azurewebsites.net`, `*.cloudfront.net`, `b.s3.amazonaws.com`) is its own site; so is a host under `targetApp/shared_domains.py` and an IP address. Names are compared in punycode (`bücher.example.de` and `xn--bcher-kva.example.de` are one site). A suffix the list does not know (`corp.local`) uses the last two labels. Limit: a multi-tenant provider in neither the bundled list's private section nor `shared_domains.py` groups its tenants under the provider's domain. A match with hard evidence of its own (a template check that answered `vulnerable`, a validation `hit`, a `confirmed` classification) is never folded in: it stays its own row, so what was proven on one host is not hidden behind its siblings and an action on the group cannot sweep it along. The facets (`heat`, `severity`, `status`, `host`, `internal`) apply to each host's finding before grouping.

**The row.** A group row is its hottest member's ordinary row (`kind: match`, `id`, `host`, `heat` and the rest are that member's, and `get_finding` on that id shows it) plus `group`: `{id, registrable_domain, identity (sha256 | script_path | script_url | library), script, hosts, findings, member_ids, member_status ({id: remediation status} for every member), ruled_out_ids, members: [{kind, id, host, heat, status, remediation_status, classification, validation_status}], members_truncated, heat_counts, status_counts, classification_counts, validation_counts, first_seen, last_seen}`. `member_ids` always lists every member; `members` lists the first 100 in full. A match alone in its group is an ordinary row with no `group`.

**The counts.** `counts` stays per host finding, as without grouping. `row_counts` is the rows of each type the grouped list has, `total` and `count` count rows (they page the list), `findings_total` is the host findings behind them, `groups` the rows standing for more than one host and `grouped_findings` the host findings inside those. The pass reads at most 20,000 matches (hottest first); past that the rest stay one row each and `group_scan_truncated` is true (the Findings page then says so above the list). The dashboard's `/cve/api/stats` adds `match_groups` (the exposed CVE matches as the grouped list counts them) and `match_groups_truncated`; the page hides the grouped number when that is true.

**Acting on a group.** Grouping is only how the list is drawn: every host keeps its own match, triage, validation, remediation status, assignee, comments and audit trail. To act on a group, send its `member_ids` to `POST projects/{slug}/findings/status` (`bulk_update_finding_status`, 200 items a call) or to `PATCH .../findings/match/{id}` one by one (`set_finding_assignee` for the assignee): each member goes through the same role gate and project check and is audited on its own, and one host can still be reopened or assigned alone. Choose the members yourself: `member_status` says each one's status, and the Findings page sends only the open and in-progress members whose status the action changes (fixed, accepted-risk and ruled-out hosts are left as they are unless the person picks the row menu's "including closed hosts" entries). The bulk route's activity line counts findings and hosts.

## PDF reports

`POST projects/{slug}/reports` (`export_report`) queues a PDF report of one project, or of one host of it (`host`, an exact name from the inventory). It lists open findings only; `include_closed: true` also lists fixed, accepted-risk and false-positive ones, each with its status and closure note, and a count by status. The answer is `202` with `{id, status: "queued", status_url, download_url: null, ...}`; asking again for the same report while one is queued or running gives that one back with `200`. The report is built by a worker, so poll `GET projects/{slug}/reports/{id}` (`get_report`, `report_id`) until `status` is `done` (`queued`, `running`, `failed` with a short `error`, or `expired`). A finished report carries `size_bytes`, a `summary` (hosts and findings printed, the total, and `omitted`, what the caps left out) and `download_url`. `GET .../reports/{id}/download` returns `application/pdf` as an attachment with the same bearer token; MCP clients fetch it over REST.

A report is a read. Any role that can read the project (audit included) may ask for one, and so may a read-only token. It holds only that project's rows, and the worker checks the asker's role again when it runs: access removed in between is a failed report with no file. Only the user who asked can read it (anyone else, even an App Admin, gets `404`, the same as a missing report), and the file is deleted after 24 hours (`CVENGINE_REPORT_TTL_HOURS`; a download after that is `410`). `_all` is a `400`. More than 3 reports in progress per user, 20 an hour per user or 8 at once overall is `429` ([Configuration](CONFIGURATION.md#pdf-reports)). Each request is recorded in the audit log.

A report prints at most 500 hosts, 1,000 detailed findings (CVE matches and scanner findings, hottest first) and 500 hygiene findings; the summary counts always cover every finding, and the PDF and `summary.omitted` say what was left out. Text that came from scanned hosts is escaped and printed as text: the renderer is a separate process that fetches no URL and reads no file. See [Front end](FRONTEND.md#pdf-reports) for the contents.

## Limits

A domain name is unique within an organization (two organizations may each track the same name, as separate records). A range or CIDR target is capped at 10,000 addresses per call, and a bulk request at 10,000 lines or expanded rows (`CVENGINE_MAX_TARGETS_PER_ADD`). IP, CIDR, and range targets in loopback, link-local, multicast, reserved, or cloud metadata space are refused, along with any range in `CVENGINE_BLOCKED_CIDRS`. Private ranges (`10/8`, `172.16/12`, `192.168/16`, `100.64/10`, `fc00::/7`) need `CVENGINE_ALLOW_PRIVATE_TARGETS=1`, and tailnet addresses (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`) cannot be added by hand even then: only a connected tailnet imports them ([Tailscale](TAILSCALE.md)). Domain names are checked when they resolve. A search takes at most 15 terms of 200 characters each and 1,000 characters in all. Pasted target text is capped at 2,000,000 characters and each token at 2,048. Notes are cut at 2,000 characters, comments at 4,000, and an exclude or archive reason at 300. A paste or bulk request carries at most 100 `-domain` exclusion lines, checked before any is applied. A bulk request takes up to 50 projects, a delete up to 5,000 ids, a rescan up to 200 hosts, and `register_assets` up to 500 assets. A project administrator can declare a private network internal to the project (`POST projects/{slug}/internal-ranges {cidr, description}`: inside the private space above, at most a /16, never touching loopback, link-local or metadata addresses); addresses inside it may then be added as targets of that project. Hosts and findings inside a declared range carry `internal` (and hosts a `network`), and `?internal=1|0` filters them on `hosts`, `search`, `vulnerabilities` and `findings` (see [Front end](FRONTEND.md#internal-hosts)). Declaring a range does not make it scannable from this server: those targets are never queued for discovery, started by hand, or picked by the work conductor, and every local scanner keeps refusing them. Only a Sentinel deployed inside the network scans them (see [ARCHITECTURE.md](ARCHITECTURE.md#sentinels)).

The API does not expose instance settings, the AI key, bug bounty actions, or user management. It can set a project's own OSINT service keys (write-only) and read which services are configured.

See also: [TENANCY.md](TENANCY.md) for roles, [PIPELINE.md](PIPELINE.md) for what a scan does, [documentation index](README.md).

`get_cve_detection` returns the shared record of a CVE (summary, identify, confirm steps, true and false-positive signs, remote and local checks with rendered commands, scope). `update_cve_detection` (App Admin; `PUT cves/{id}/detection`) changes it with `guidance` (text the AI folds in: the AI reviewer container revises the record, the answer carries `revision: {state: queued, job_id}`, and the record changes when the revision lands, usually within a minute) or a whole `strategy`. CVEs only usable from the host itself carry `local_only: true` in `list_cves` and are never matched to a host. See [CVE-INTAKE.md](CVE-INTAKE.md).

**Conditional reads of the polled lists.** `GET sentinels/live` and `GET projects/{slug}/scans` send an `ETag` and `Cache-Control: private, no-cache`, and answer `If-None-Match` with `304` and no body when nothing changed. The tag is computed from the answer without its clocks (`server_time`, `seconds_since_seen`), so an idle Sentinel fleet and an unchanged scan list are 304s. Each row of `sentinels/live` also carries `revision`, which moves when what the Sentinel's detail (`GET agents/{id}`: settings, version, update request) shows may have, so a poller asks for a detail only then.

**OpenVAS on the Sentinels page.** `GET sentinels/live` carries `openvas`: `null` while the add-on is off, else `{running: {run, project, hosts, progress, status, started_at, budget_hours, via}|null, hosts_per_task, budget_hours_per_host, max_checks, next: [{project, host, heat, order, ready: true}], not_due: [{project, host, heat, ready: false, reason}], counts}` over the projects the caller may read. `next` is in scan order (Fire before Smoke); `reason` says in words why a host is not due ("not Fire or Smoke (clean)", "a CDN edge", "scanned 3 days ago"). A Sentinel's `result` for an `openvas` task may carry `partial: true` (stopped at its time budget; what it found is kept and nothing earlier is closed by it), and its heartbeat `info.openvas: {ready, reason}` says whether its GVM stack can scan.

**Load on the Sentinels page.** Each Sentinel row of `GET sentinels/live` carries `load`: `held` (tasks claimed or running now) and the last hour's `utilisation_1h` (0 to 1: the time its slots were busy over an hour of every slot it has; a running task counts from its start, or from the start of the hour), `tasks_1h` (finished, done or failed), `wait_p50_seconds` and `wait_p95_seconds` (queue wait, `claimed_at - created_at`, of the tasks it claimed in the hour, `null` for none) and `wait_by_kind` (`{kind: {n, p50_seconds, p95_seconds}}`); the response also has `kinds`, `{kind: {queued, tasks_1h, wait_p50_seconds, wait_p95_seconds}}` (`queued` counts only the projects the caller may read), and `stage_runs`, the same block as the system status's `sentinels.stage_runs` over the projects the caller may read (a sweep over every project counts for an App Admin only). They are what least-loaded claiming balances on, together with `max_concurrent` ([SENTINELS.md](SENTINELS.md#sharing-work-between-sentinels-least-loaded-first)); an older server sends none of them.

**Task rows on the Sentinels page.** Each row of `current` and `recent` in `GET sentinels/live` carries the task `id`, `kind`, `status`, `host` and a `label` (the host, else the hosts an OpenVAS task was chosen for, else its addresses), `project` (slug) and `project_name`; a `recent` row also has `outcome`: `completed`, `completed at its time budget (partial)`, `stopped before it finished` (gvmd or the Sentinel stopped the scan), `failed`, plus `error` for the detail. `outcome` for a task cancelled by an administrator (`cancelled by an administrator`) or lost with its Sentinel (`lost (the Sentinel stopped answering)`) is on the task itself (`GET sentinel/tasks/{id}`'s `error`), as an expired task no longer belongs to a Sentinel. Every Sentinel row carries `version` (the build's commit or the updater's version, `null` when neither is known) and `version_label` (that, or `unknown (built without the updater)`).

**The built-in scanner.** Every Sentinel row of `GET sentinels/live` and every agent of `GET agents` and `GET agents/{id}` carries `builtin`: `true` only for the install's own scanner (the one enrolled by the server, [BUILTIN-SCANNER.md](BUILTIN-SCANNER.md)), `false` for every other Sentinel and agent, whatever it calls itself.

**Is the Sentinel current.** Every Sentinel row carries `version_state`: `{status: current|behind|unknown, version, latest, latest_message, latest_url, latest_date, behind_by, checked_at, repo, detail}`. `latest` is the head of the Sentinel repository's branch (`CVENGINE_SENTINEL_REPO`, default `hevnsnt/cvENGINE-sentinel`, branch `CVENGINE_SENTINEL_BRANCH`, default `main`), asked of GitHub every six hours and once when a page finds nothing cached, never while a page is built (a slow or unreachable GitHub shows as `unknown` with the reason in `detail`); `behind_by` is the number of commits between the Sentinel's reported commit and `latest`. `unknown` also covers a Sentinel that reports no version ("unknown (built without the updater)") or one whose version is not a commit. `CVENGINE_SENTINEL_VERSION_CHECK=off` turns the check off for an instance with no route to GitHub; a private repository needs `CVENGINE_SENTINEL_REPO_TOKEN` (else the token of the update check is tried).

## Settings through the MCP (App Admin)

cvENGINE is meant to be run by agents as well as people, so every setting on the Settings and Administration pages has an MCP tool. `list_settings` names each one (what it is, whether it can be read, changed or removed, and what its `id` means). `get_setting` (`get_setting(name)`) reads it. `change_setting` (`change_setting(name, values)`) changes it, or runs the action it names (a test mail, an update check), with the limits, the audit entry and the secret masking of the page: a secret is never returned, only whether one is saved. `remove=true` deletes the object an entry names (an allowlist entry, an organization key). An entry that names one object takes `id`, for example `3/shodan`. A change needs an App Admin (an administrator for audit, activity, health, organization keys and excluded addresses) and a token that is not read only. Left out on purpose: factory reset and file upload or download. A route added to the Settings or Administration tables without a tool fails `tests/test_settings_bridge.py`.

### The AI reviewer's verdict on a finding

A row of `findings` and the `get_finding` detail carry `ai_review`: `null` while the AI reviewer has not reviewed the finding, else its newest verdict as `verdict`, `confidence`, `reason_code`, `note`, `model`, `outcome` (`recorded`, `closed`, `disputed` or `held`), `held_reason`, `at`, and in plain words `verdict_text` and `outcome_text`, with `disputed` (it called the finding a false positive and the server kept it open) and `says_real`. `findings?ai=disputed` (`list_findings` `ai: disputed`) keeps the disputed ones, `ai=real` the ones it called real. The note is text: show it as text.
