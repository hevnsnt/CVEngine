# Agent API: REST and MCP

Two interfaces share one service layer, so both get the same project isolation, role checks, and read-only token rules.

- **REST** at `/api/v1/`, JSON, with an OpenAPI spec at `/api/v1/openapi.json`.
- **MCP** at `/mcp/`, Streamable HTTP (JSON-RPC 2.0 over POST), protocol versions 2025-06-18, 2025-03-26, and 2024-11-05. Following the specification's transport rules, a request from a browser page of another site (an `Origin` that is not this server's host) is refused with `403`, an `MCP-Protocol-Version` header this server does not speak is `400`, a client's own response or notification is accepted with `202` and no body, an unknown tool is the protocol error `-32602` (a tool that fails is a normal result with `isError`), and an unexpected server error is the JSON-RPC internal error `-32603` rather than an HTML page. `GET` answers `405` (no server-initiated stream).

## Connect

Create a token on the **API tokens and MCP** page (`/cve/agents/`) and send `Authorization: Bearer <token>`. The secret (`cve_...`) is shown once and only its SHA-256 is stored. A token acts as its user, with the same memberships and roles. **Read only** tokens can call GET endpoints and read-only tools. Revoke a token on the same page. Tokens never expire, but they stop working when the user is deactivated, and they are revoked automatically when the user changes their password, when an administrator resets that user's password or two-step sign-in, and when the input guard disables the account. Bearer requests skip CSRF.

When an organization requires two-step sign-in and a member has not enrolled, that member's session and tokens get `403` until they turn it on under **My account**. Tokens are not revoked and work again afterward. MCP requests are limited to 256 KiB, 20 batched messages, and 4 MiB of response.

Connect Claude Code:

```bash
claude mcp add --transport http cvengine https://<your-host>/mcp/ --header "Authorization: Bearer <token>"
```

A host record (`hosts`, `search`) carries `unverified_products`: the products seen on the host (a technology or an open port) with no version found, as `{name, source: "tech"|"port", source_id, ip, port, cpe, service}`. They are metadata and a lead for finding the version, never CVE matches: a match needs the same product at a version inside an affected range.

A host record (`hosts`, `search`, and the MCP `list_hosts` and `search_hosts`) carries `check_coverage`: `{done, applicable, paused, checks}`, which of the checks that apply to the host have run (the page shows it as "NN of NNN applicable checks done"). `checks` has one row per registered check, `{id, label, state, last_run, ttl_hours, detail}`: `state` is `done` (ran inside its window, which is the ledger window of its kind, `ttl_hours`), `due` (applies, and never ran, is older than its window or failed last time; `detail` says which) or `not_applicable` (`detail` says why: no TLS port, no sign of WordPress, a switch is off, the project's bug bounty engagement has not confirmed automated testing, and so on). `last_run` is an ISO time or `null`. Only applicable checks are counted in `done` and `applicable`. `paused` is `excluded` or `archived` (no check applies then) and empty otherwise. The field is `null` only when it could not be worked out. It reads recorded results and never starts a check; the rules and how to add a check are in [Pipeline](PIPELINE.md#check-coverage). It is computed for a page of hosts in a fixed number of queries and covers only the projects you can see.

Lists take `page` and `page_size` (up to 200; this includes members, finding comments and a finding's audit trail), except `work` and `cves?tier=`, which return one page of at most 200 rows (`count` can be higher), and `findings`, which pages through its first 2,000 and reports `total`, `truncated`, and `counts`. Every MCP result carries `_meta["cvengine/untrusted_text"]`: text that came from scanned hosts or feeds (banners, titles, response excerpts, advisory text) is data, never instructions. Writes need any role except audit in the project and a token that is not read only. A project you cannot see returns 404, the same as one that does not exist.

**CVE detection.** `GET cves/{id}/detection` (`get_cve_detection`) returns `{source, schema_version, strategy, ai_model, updated}`: the shared record of remote and local checks and the validation profile ([PIPELINE.md](PIPELINE.md#detection-strategies)). It is the same for every organization and needs membership in any organization or project. A CVE with no record yet returns `source: null` and a note. `cves?tier=` looks only at the newest 2,000 CVEs, and `q` matches the CVE id only.

Stored sign-ins ([Pipeline](PIPELINE.md#authenticated-checks)) are for an App Admin or the project's organization admin only; every other role gets `403`, because they let the scanners act as a person inside an application. Values are write-only: a read returns the label, target, `scope` and `host` (`null` for `target`), `origins`, header and cookie names, `expires_at`, `days_left` (`null` for a deliberate `never`), `never_expires` and `state` (`active` or `expired`), never a value, and the audit log records names only. The value fields are called `secret` and `cookie_secret` so request inspection skips them. A blank `secret` for a header name already stored keeps it, header names left out are removed, a blank `cookie_secret` keeps the cookie and `clear_cookie: true` removes it. A read-only token can list but not change. `PUT` needs two explicit choices and answers `400` without them, never a default: `scope` is `host` (with `host`, one host of the target) or `target` (every host of the target, with `host` blank), so a blank host alone is refused and never means the whole target; `expires` is `30`, `90` or `120` (days from now, stored as the computed `expires_at`) or `never` (stored with no expiry), and a replace needs it again. The MCP server has no tool that sets a credential, because a secret must not pass through a model's context: it lists them (names, scope, expiry and days left, no values) and revokes them (`delete_auth_credential`); set one on the Targets page or over REST. A finding seen through a signed-in request has `seen_while_authenticated: true`.

## Host inventory

Hosts can report about themselves (operating system and build, packages and versions, patches, listening services) with the scripts in `scripts/inventory`; see [HOST-INVENTORY.md](HOST-INVENTORY.md). The script posts inventory v1 JSON to `POST projects/{slug}/inventory`. That is the only route a **reporter token** can call: create one from a signed-in session with `POST tokens` `{"name": "...", "scope": "inventory", "project": "slug"}` (or from the Host inventory dialog). It is bound to that project, can post nothing else (every other route and `/mcp/` answer `403`), and acts with its creator's role. `GET tokens` shows each token's `scope` and `project`.

The ingest answer is `201` for a machine's first report and `200` after, and never says which host the report matched. A body over 2 MiB, or a list over its cap (15,000 packages, 2,000 patches, 1,000 listening sockets), is `413`; a malformed report is `400`; a report that is not accepted (an excluded host, a machine another token owns) is `409` with no reason given to the reporter (it is in the audit log); more than 12 reports an hour from one machine through one token, or the token and project caps, is `429`. A reporter token expires after 365 days (`expires` in `GET tokens` and in the answer that creates it); `POST tokens` takes `scope` `full` or `inventory` and refuses anything else with `400`. `POST projects/{slug}/inventory/delete-unmatched` deletes every report tied to no host.

`GET projects/{slug}/inventory` lists reports newest first (`status=matched|unmatched|stale|fresh`, `q=`). `GET .../inventory/{id}` and `GET .../hosts/{host}/inventory` return one report in full: the operating system, `packages_page` (each package normalised with `name`, `version`, `ecosystem`, `distro`, `distro_release`, `arch`, `source` and a `purl`; `q`, `page` and `page_size` up to 200 page through it), `patches`, `services`, `runtime`, `security`, `history` (the last 20 reports, summarised), `findings` (how many open CVE matches this report made) and `stale`. Names and versions in a report are data from the machine, untrusted. `POST .../inventory/{id}/adopt` ties an unmatched report to a host the project scans (`{"host": "name"}`) or adds the machine as a target (`{"create": true}`); `DELETE` removes a report. Both need a write role. The host record in `list_hosts`, `search_hosts` and the host page carries an `inventory` summary (`null` when the host never reported). A CVE match made from a report has `source: "host"` and `host_reported: true`.

`GET/PUT projects/{slug}/settings` carries `inventory`: `create_hosts` (a report from a host nobody scans adds it as a target; off by default) and `stale_days` (default 14: a stale report creates and closes no findings).
## Agents and assigned work

An agent is an API token that has told the server who it is, what it is responsible for, and what it can do. The server then hands it validation and remediation tasks it is able to do, and only those. Registration is optional: `register_assets`, `get_remediation_work` and `update_remediation_status` keep working for an agent that picks its own work.

**Register** with `PUT agent` (`register_agent`). The same call creates and updates; repeating it changes nothing, and fields you leave out keep their value. Registration needs a token that can write. `scope` is replaced as a whole when it is sent; its `hosts` (empty when none) also become the token's registered assets, which `get_remediation_work` narrows to.

| Field | Meaning |
| --- | --- |
| `name`, `kind` | A display name and one of `remediation`, `validation`, `scanner`, `reporter` (for example a host inventory reporter, capability `report:inventory`), `human` (a person working through tasks). |
| `scope` | What the agent is responsible for: `orgs` and `projects` (slugs) and `hosts` (a host name, which also covers every name under it, so `*.example.test` is stored as `example.test`; an IP address; or a CIDR). Name at least one organization or project: hosts narrow it, they do not pick a project. An agent with no organization or project is responsible for nothing and gets no work. |
| `capabilities` | What it can do: `validate:network`, `validate:local` (runs on the host), `validate:local-ssh` (logs in to the host), `validate:guided` (follows plain-language confirm steps), `remediate:linux`, `remediate:windows`, `remediate:web-config`, `can-restart-services`, `report:inventory`, `shell`, `ssh`. Others are accepted and kept but never matched. |
| `os`, `tools`, `max_concurrent` | Operating system families it acts on (`linux`, `windows`, `macos`, `bsd`; empty means any), tool names it has, and how many tasks it holds at once (1 to 10, default 2). |

**Approval.** A new agent starts `pending` and gets no work until an administrator approves it (`PATCH agents/{id}` with `{"status": "active"}`, or **Administration, Agents, Manage, Approve**), because an agent can take work in, and report fixed on, every project its user writes to. An agent of an App Admin or organization admin is active at once. A user who already has an agent suspended or revoked does not get round it with a new token: the new agent starts `suspended` and an administrator must reinstate it. A user may have at most 10 agents. A suspended or revoked agent cannot unregister or re-register to clear that decision, and an administrator cannot approve, limit or reinstate their own agent (another administrator or an App Admin does). An organization admin can administer only users who belong to organizations they all administer; for others they see only their own organizations' part of the scope.

The scope is checked against what the token's user can already reach: naming an organization or project outside that is a `403`, the same answer for one that does not exist. The check runs again every time work is handed out, so a user who loses a project loses the agent's claim to it at once. An administrator (an App Admin, or an organization admin for the users of their organizations) can `PATCH agents/{id}` with `status` (`active` to approve or reinstate, `suspended`, `revoked`), a `note`, and `limits` (`capabilities`, `projects`, `max_concurrent`, each `null` for no limit). A suspended or revoked agent loses its leases at once; a revoked token does too. `whoami` (and `GET me`) now carries `agent`: its registration, what it may reach right now, warnings, and its open assignments.

**Work.** `POST projects/{slug}/agent-tasks` (`queue_agent_work`, needs a write role) queues `kind` `validate` or `remediate` for CVE matches, either `match_ids` or the open matches filtered by `tier` and `host`, up to 200 at a time. Each task records what it needs, from the work itself:

- A validation uses the CVE's shared detection record. Checks that run on the host (`mode` `local`) need `validate:local` or `validate:local-ssh`; checks that probe from the network (`network`) need `validate:network`; a CVE with only plain-language confirm steps (`guided`) needs `validate:guided`. A CVE with none of these cannot be queued.
- A remediation needs `remediate:linux` or `remediate:windows` from the host's operating system (the fingerprint and distribution the scans recorded; when unknown, either), or `remediate:web-config` and `can-restart-services` when the fix is a setting in a web server's configuration file.

Work already queued or running for the same match and kind is skipped. A task whose finding is fixed, accepted or ruled out is cancelled instead of handed out.

**Assignment.** `POST agent/tasks/next` (`get_next_task`, body `{wait, kinds}`) leases the best task the caller may take: its scope covers the host, its user has a write role in the project, its capabilities and operating systems fit, and it is below its concurrent limit. Fire work comes first. If another live agent with room has less to do, the task is left for it, so the agent that polls fastest does not take everything. `wait` holds the call for up to 20 seconds until work appears (long polling: the MCP transport here has no server push); at most six calls wait at once, and any more answer immediately with `retry_after_seconds`. The claim is atomic: two agents asking for one task, exactly one gets it.

A task is **leased**. A claimed task must be accepted (`accept_task`) within two minutes. An accepted task stays leased while the agent sends `agent_heartbeat` (about once a minute; each extends the lease of its running tasks by five minutes, up to four hours after acceptance). An agent silent for three minutes is offline and gets no new work. If an agent's user loses the write role or the project, or a limit tightens, the next heartbeat hands its tasks back, and an accept or a report for such a task is a `409` that changes nothing. A task whose lease runs out goes back to the queue after a 30 second pause, counting one attempt; after three attempts it is `failed`. `release_task` gives one back without counting.

`report_task_result` closes a task. `outcome` is `confirmed`, `not_affected` or `inconclusive` for a validation, and `fixed`, `not_fixed` or `blocked` for a remediation. `error` reports a failure: `retryable` (default true) puts it back in the queue until its attempts run out. `summary` is plain text and `checks` is `[{id, result: pass|fail|error|skipped, output}]`, at most 20; everything is cleaned and clipped (1,000 characters of summary, 2,000 per output) and stored as data. A finished task adds a comment to the finding, and a `fixed` remediation sets the finding to `fixed` exactly as `update_remediation_status` does. A validation result never changes the finding by itself: people and the triage decide from the evidence. Reporting the same outcome twice is harmless; a different one is a `409`.

**Unassignable work.** `GET projects/{slug}/agent-tasks/unassignable` (`list_unassignable_work`) lists queued tasks no live agent can take, each with the reason: `no agent covers host x`, `the agents covering host x are offline`, `no live agent covering host x has capability y`, or `... acts on windows hosts`. A reason never names an agent. A task that is assignable can still wait: every capable agent may be busy.

**What an agent may run.** A task payload separates `run` and `run_remote` from `data`. Every entry of `run` (local checks, also given to a remediation to confirm the fix; `check_id`, `platform`, `shell`, `command`, `needs_root`, `expect`) and `run_remote` (network checks; `check_id`, `tool`, `invocation`, with `<TARGET>` and `<PORT>` placeholders) is rendered by the app from the detection record's own validated check parameters, re-validated and re-rendered each time it is read, so no text from a scanned host or a stored record becomes a command. `host.target` is the only value to put in `<TARGET>`, and it is `null` unless the host name is a plain DNS name or an address. Everything under `data` (host name, product, version, advisory title, ports, and `check_notes`, the prose the record has for each check) and `guidance` came from scanned hosts or feeds: read it, never run it. Every MCP result still carries `_meta["cvengine/untrusted_text"]`.

**Limits.** Calls per minute: 120 heartbeats, 60 task requests and 120 reports per token and three times that for all the tokens of one user together, and 30 queue requests a minute per user; registration is 30 an hour per token. One token holds at most one long poll and one user two. A match gets at most five agent tasks a day. Finished tasks are deleted after 30 days (`CVENGINE_AGENT_TASK_RETENTION_DAYS`, in the weekly maintenance); the audit log keeps the trail. Work for an agent is found in SQL by project, operating system and capability, so tasks it cannot do never hide ones it can. A project holds at most 2,000 waiting or running agent tasks. Registration allows 40 capabilities, 30 tools and 200 host entries.

**Audit.** Registration, scope and status changes, queueing, claim, accept, completion, failure, release, lease expiry and cancellation are written to the audit log (Administration, Audit log), tagged with the project's organization.

A worked flow, as MCP tool calls (REST is the same with the routes in the table above):

```text
register_agent    {"name": "web-fixer", "kind": "remediation",
                   "scope": {"projects": ["website"], "hosts": ["*.example.test", "192.0.2.0/24"]},
                   "capabilities": ["remediate:linux", "can-restart-services"], "os": ["linux"]}
update_agent      {"agent_id": 7, "status": "active"}                  (an administrator approves the new agent)
queue_agent_work  {"project": "website", "kind": "remediate", "tier": "fire"}      (a person or another agent with write access)
get_next_task     {"wait": 20}              -> {"task": {"task": {"id": 41, "status": "assigned", ...}, "host": {...}, "run": [...], "data": {...}}}
accept_task       {"task_id": 41}
  ... fix the host, then run the commands in "run" to confirm ...
report_task_result {"task_id": 41, "outcome": "fixed", "summary": "upgraded nginx to 1.24.0",
                    "checks": [{"id": "package-nginx", "result": "pass", "output": "NOT-AFFECTED"}]}
agent_heartbeat   {}                         (about once a minute while working)
```

In the web app, **Administration, Agents** lists agents with their scope, capabilities, last seen and task counts, with approve, limit, suspend and revoke, plus the work no agent can take and what is queued or running. **API tokens and MCP** lists your own agents. A finding and a host show which agent holds work on them.

## Sentinels: scan-stage agents

A Sentinel is an `Agent` with `kind: "scanner"`: the same identity, scope, capabilities, admin approval, suspend/revoke, live/heartbeat window and rate limiting as any other agent ([Agents and assigned work](#agents-and-assigned-work)), but the work it is leased is scan-stage work, not a CVE match. This phase covers three tools: `nmap`, `naabu`, and the two nuclei passes, `nuclei_light` and `nuclei_targeted` (its `capabilities` are drawn from those four names). A `SentinelTask` (its own queue, separate from `AgentTask`) is one run of one tool against a server-built target; nothing it contains, and nothing a Sentinel reports back, is ever built from, or interpreted as, a command. The actual downloadable Sentinel client (a Docker image) is a follow-up build against this REST/MCP contract; this phase is the server-side foundation and admin surface only.

**How dispatch works.** Before a scan runs nmap, naabu or a nuclei pass locally, it asks once: is there a live, eligible Sentinel for this project with free capacity and the matching capability? If not (no Sentinel registered, none live, none with room), the stage runs locally exactly as it always has: this is the single most important property of the design, and it holds for every install until it registers a Sentinel. If there is one, the stage creates a `SentinelTask`, the Sentinel claims and reports it, and the typed result is persisted through the *exact same* function local execution already uses (the nmap and naabu results flow into `persist_inventory`/`persist_open_ports`; a nuclei finding is reconstructed into the same result-line shape nuclei's own JSON output takes and runs through the stage's own, unmodified per-line loop). The wait is bounded (`CVENGINE_SENTINEL_DISPATCH_TIMEOUT`, default 90 seconds, see [Configuration](CONFIGURATION.md)); on timeout, failure, or no Sentinel, the stage falls back to running the tool locally, and the `SentinelTask` is marked `expired`. See [Architecture](ARCHITECTURE.md#sentinels) for the full design note.

**Register.** `PUT sentinel` (`register_sentinel`) is `PUT agent` with `kind` forced to `scanner`; the same fields (`name`, `scope`, `capabilities`, `os`, `tools`, `max_concurrent`) and the same approval rule apply (a new Sentinel of a non-administrator starts `pending`). A brand new Sentinel with no token yet instead bootstraps from a one-time enrollment secret:

1. An org admin or App Admin calls `GET` or `POST projects/{slug}/sentinels/enroll` (`generate_sentinel_enrollment`) and gets `{enrollment_token, server_url, expires_at}`. The secret is single-use and expires 30 minutes after it is generated (documented, not yet configurable).
2. The Sentinel calls `POST /api/v1/sentinels/bootstrap` (REST only; no bearer token, the secret itself is the credential) with `{enrollment_token, name, capabilities, os, tools, max_concurrent}`. The server redeems the secret, creates an `Agent` (`kind: scanner`) pre-scoped to the project the secret was generated for (never to what the Sentinel's own body claims), owned by the administrator who generated it, and returns `{token: "cve_...", ...}` once, like any other token creation. From there it is a Sentinel like any other: `sentinel_heartbeat`, `get_next_sentinel_task`, `accept_sentinel_task`, `report_sentinel_task_result`.

**Work.** `get_next_sentinel_task` (body `{wait, kinds}`) leases the best queued `SentinelTask` the caller's scope and capabilities cover, the same bounded long-poll (`wait` up to 20 seconds) and atomic claim as `get_next_task`. `accept_sentinel_task` within two minutes, then `sentinel_heartbeat` about once a minute to keep the lease (it is the same call as `agent_heartbeat`: one heartbeat extends both AgentTask and SentinelTask leases of that agent). `report_sentinel_task_result` takes `{task_id, outcome: "done"|"error", ...}`; on `done`, the fields its `kind` expects:

| `kind` | result fields |
| --- | --- |
| `nmap` | `hosts: [{ip, os_guess, ports: [{number, protocol, service_name, product, version, state}]}]` (at most 64 hosts, 500 ports each) |
| `naabu` | `ports: {ip: [open port numbers]}` (at most 64 addresses, 500 ports each) |
| `nuclei_light`, `nuclei_targeted` | `findings: [{template_id, name, severity, host, matched_at, description, extracted_results, tags}]` (at most 100 findings) |

Every string is clipped (template id 80 characters, name 200, description 500, a product or version 80 to 120) and every list capped before it is stored or used anywhere; an unexpected shape is a `400`, never stored as given. A `SentinelTask`'s own target descriptor is server-built from the same scan the stage is already running: a Sentinel never receives the project's stored sign-ins (`AuthCredential`), another project's data, or raw database access, only the addresses, hosts or templates for the one task it holds. `release_sentinel_task` gives a task back without counting against it; a Sentinel that stops heartbeating has its leased tasks marked `expired` the same way `agent_heartbeat`'s silence does, and the dispatching stage, having already timed out waiting, has moved on to running the tool locally.

**Admin.** A Sentinel is administered exactly like any other agent: `list_agents?kind=scanner` (`list_sentinels`), `GET/PATCH agents/{id}` (`get_sentinel`, and `suspend_sentinel`/`revoke_sentinel`, thin aliases of `update_agent`); suspending or revoking releases its in-flight `SentinelTask`s immediately, the same call that already releases `AgentTask`s. `GET projects/{slug}/sentinel-tasks` (`list_sentinel_tasks`) lists scan-stage work for a project (`status`, `kind`, `agent_id`, `scan_id`); `GET agents/{id}` includes a Sentinel's recent `SentinelTask`s under `recent_tasks`. The **Sentinels** page (`/cve/sentinels/`) shows this with suspend/revoke buttons and a way to generate and copy an enrollment secret; see [Front end](FRONTEND.md#sentinels).

## Targets and scans

`targets/bulk-org` takes `{"text": "##Organization\n#Project\nexample.com\n10.0.0.0/28\n#Project2\n...", "current_project": "slug"}`. A line `#Name` (no space after the hash) opens a project, and the lines under it are domains, IPs, CIDRs, ranges, or URLs. `# a note` is a comment. A `##Organization` line is optional. Without one, or with a name the caller cannot see, the caller's current organization is used, and `organization_note` says so when a name did not resolve. Missing projects are created, which needs the admin role in the organization. Each project is checked on its own, so a section the caller cannot write to is reported in `projects[].error` and the rest still go in.

Bulk adds start discovery by default. A single add starts it only when `discover` is true. `mode` is `standard` (default), `deep`, or `passive`. Targets queue first in, first out, and a target that already has a queued or running scan keeps it. A queued scan has `status` -1 and a `queue_position` (0 is next). `GET .../scans` lists running scans first, then queued, then the rest newest first. Stopping a scan marks it aborted and ends its scanner processes so the next queued scan can proceed.

Each target carries `scope_mode` and `host_scoped`. See [Shared provider domains](PIPELINE.md#shared-provider-domains).

## All projects

The reserved slug `_all` means every project you can see. The list endpoints and tools accept it in place of a project slug and return one combined, read-only list: `targets`, `scans`, `hosts`, `search`, `findings`, `vulnerabilities`, `matches`, `changes`, `activity`, `hygiene`, `certificates`, and `routes`. Every row carries `project` (use this slug for anything you do next) and `project_name`. Only your own projects contribute rows, and `count` is the total. Everything else needs a real project: a write or a per-item call with `_all` is a `400`.

## Host management

`profile` records who owns a host, what it is for, and how much it matters (`criticality`: `unknown`, `low`, `medium`, `high`, `critical`), per project. Only the fields you send change.

`delete` removes one host's data from this project only: its findings, CVE matches, routes, changes, triage, certificates, and asset information. A later scan can find the host again.

`exclude` is organization wide: it deletes the host's data from every project of the organization you can write to, and no stage touches it again in any of them. It needs an organization-level role, and organization admins lift it with `DELETE exclusions/{host}`. Names match whole and case-insensitively: excluding `provider.example` leaves `www.provider.example` alone, and wildcards are a `400`. Send `"with_aliases": true` to take the other names the project shows as the same host (same addresses) with it, and `"include_subdomains": true` to exclude a whole domain (`provider.example`, every name under it and the targets named like them; scans of those targets are stopped; `co.uk`-style suffixes and addresses are a `400`). `delete` takes `with_aliases` too. In `add_targets` a line starting with `-` (`-provider.example`) does the whole-domain exclusion and the response lists it under `excluded`. Removals are audit logged.

## Hosts and search

Hosts carry `score` (0 to 100) and `score_detail`, and come highest score first (`sort=name` for name order). Names that resolve to the same addresses are one host, so the list returns one row per host that covers all its current rows, with the other names in `aliases`. `labels` holds short informational detections such as a WAF or federated sign-in. See [Host score](PIPELINE.md#host-score).

`search?q=...` returns hosts with `matched` showing what each query hit. Terms are separated by spaces and ANDed. A bad value for `sev:`, `auth:`, `sensitive:`, or `zombie:` is a 400. The full syntax, with examples, is in [SEARCH.md](SEARCH.md).

| Term | Matches |
| --- | --- |
| `php` | a bare word in hostname, IP, technology, headers, cookie names, port product, service, version, CPE, banner and script output, OS, finding name, CVE id, or page title |
| `tech:nginx` | anything the host runs: technology, `Server` and `X-Powered-By` headers, product, version, CPE, banner, script output, cookie names |
| `product:nginx`, `service:mysql`, `os:linux` | port product, service name, OS guess |
| `banner:"anonymous"` | service banner, script output, or extra info on an open port |
| `port:3306` | open port number (a number only; `port:ssh` is a 400) |
| `cve:CVE-2024-1234` | CVE match |
| `ip:10.0.0.5`, `ip:10.0.0.0/24`, `ip:10.0.` | an IP, any IP in a CIDR range, or an address prefix |
| `host:www` | hostname |
| `vuln:rce`, `sev:high` | finding name, severity |
| `auth:<state>` | hosts with a web route in that state (any state listed under Routes) |
| `sensitive:any`, `sensitive:credentials`, `sensitive:pii`, `sensitive:internal` | hosts with a route serving that kind of sensitive data |
| `zombie:yes`, `zombie:no` | hosts whose name is gone but whose last address answers |
| `country:US`, `country:Germany` | the ISO code or name of a host IP's geolocated country |
| `-term`, `"apache tomcat"` | negate a term, or match a phrase |

`?heat=fire|smoke|ice|clean|unscanned` narrows the page to that heat, the same value each host's own `heat` field carries. The response's `facets.heat` always counts every one of those five values over the whole match of `q`, ignoring `heat` itself, so a UI's heat chips keep their real totals while one is selected. Both the filter and the facet count stop after 5,000 matched hosts (`facets.truncated: true`); a search that wide needs narrowing with `q` regardless.

Any field filter's value takes a comma-separated list for OR within that one filter, Shodan-style: `port:80,443` is port 80 or 443, still ANDed with every other term. Quote the value to keep a literal comma (`tech:"foo,bar"`): it is then never split.

`?facets=port,product,tech,os,country` (comma-separated) adds the same whole-match, heat-chip-style counting for those fields: the response's `facets.port`, `facets.product`, and so on are each `[{value, count}]`, highest count first, up to `?facet_size=` values (default 10, max 50); `count` is the number of distinct hosts with that value, over the same (and equally 5,000-capped) match `facets.heat` counts. `org:`, `asn:`, and `hosting:` filters and facets were asked for too, but nothing in CVEngine looks up an IP's ASN or hosting provider today (only its country, via `geoiplookup`), and adding that is its own feature, not implemented here.

Ports are stored per IP, so `product:nginx` finds only hosts whose own IP runs it.

## Saved searches

A saved search is a `search_hosts` query kept on the server, re-run on a schedule, with alerts through the notification channels ([SEARCH.md](SEARCH.md#saved-searches-and-alerts)). It is private to its owner inside one project: another member, or a user of another project, gets 404 for it, and `_all` is a 400. Reading (`list`, `get`, `matches`) needs the access the search itself needs. Creating, changing, deleting and running one need any role except audit and a token that is not read only, because a run can notify.

`POST projects/{slug}/saved-searches` takes `name` (clipped to 80 characters), `query` (checked like a live search: an empty query, an unusable filter value, more than 15 terms or 1,000 characters is a 400), and optionally `enabled` (default true), `alert_new` (true), `alert_gone` (false), `threshold` (null, or 1 to 1,000), `channels` (a list of `slack`, `discord`, `telegram`, `lark`; empty means every channel Settings has on) and `frequency` (`hourly`, `daily` default, `weekly`). Unknown fields, a wrong type, a duplicate name (per owner and project, ignoring case) and the caps (25 per user, 100 per project) are 400s. `PATCH` takes any subset; a new `query`, or switching `enabled` back on, restarts the baseline.

A saved search row has `id`, `project`, `name`, `query`, `enabled`, `alert_new`, `alert_gone`, `threshold`, `channels`, `frequency`, `baseline` (false until the first check), `last_run_at`, `next_run_at`, `last_match_count`, `last_status` (`ok`, `too_broad` for more than 1,000 matches, `error`, `disabled`), `last_error`, `last_alert_at`, `created` and `updated`. The list also returns `limits` and `channels_available` (names only). A search whose owner lost access to the project, or whose account is deactivated, is switched off at its next check: `enabled` is false, `last_status` is `disabled`, and `last_error` says why.

`POST .../{id}/run` evaluates the search now, as the schedule would: it compares with the last check, alerts if asked, and answers `{status, count, new_count, gone_count, baseline, alerted, new: [up to five names], saved_search}`. The first run only records the baseline (`baseline: true`, `alerted: false`). A disabled search is a 400, a second run within 30 seconds is a 429, and one that is being checked right now is a 409. `GET .../{id}/matches` is `search` with the saved query (`page`, `page_size`, `sort`, `heat`, `facets`, `facet_size`) plus `saved_search`; it never touches the baseline.

## Routes, changes, and activity

- **`routes`** lists web routes with `auth_state` (`open`, `login`, `session_required`, `sso`, `redirect`, `not_found`, `error`), `redirect_to`, and `evidence` (markers, never page content). `sensitive` holds `{type: {count, sample}}` with the sample already masked, and `sensitive_score` runs 0 to 25. Raw values are never stored or returned. `retired_at` and `zombie_since` mark route lifecycle, and `sensitive=1` or `zombie=1` filter.
- **`changes`** lists inventory changes newest first. `since` is an ISO 8601 datetime or `24h`, `7d`, `4w`. `kind` is one of the kinds in [Changes](PIPELINE.md#changes), and `host` matches part of a hostname. Each row has `before` and `after`.
- **`activity`** is the AI activity log for the project plus system-wide entries. `kind` is `feed`, `inventory`, `target`, `confirm`, `write_check`, `run_check`, `validate`, `discovery`, `scan`, `hygiene`, `changes`, `remediation`, `saved_search`, or `runzero` (one line per runZero sync).

## Triage and remediation

List endpoints (`vulnerabilities`, `matches`, `routes`, `hygiene`, `work`) carry a `triage` object with `classification` (`confirmed`, `likely`, `needs_validation`, `likely_false_positive`, `not_applicable`), `status`, `validation_status`, `overridden`, `first_seen`, and `last_seen`. `vulnerabilities` and `matches` accept `?classification=`, and `vulnerabilities` accepts `?severity=actionable` to skip info rows. `ai_verdict` on a match is the older view: `confirmed` and `likely` are `affected`, `needs_validation` is `uncertain`, and the false-positive classes are `not_affected`. See [Triage and validation](PIPELINE.md#triage-and-validation).

`findings/{kind}/{id}` returns one finding in full: why it matters, how it was found (with request and response excerpts capped at 4 KB, returned only here), its history, the AI's classification and whether a rule overrode it, remediation, and every validation check with the command a person can repeat. A CVE match also includes the feed description, affected products and ranges, HTTPS advisory links, feed sources, and nullable exploitation signals. Those signals describe the CVE; they do not prove a particular host is vulnerable.

**Validate a match.** `POST projects/{slug}/matches/{id}/validate` queues the same workflow as **Validate now**: an AI plan, the checks it chose from those the scope and template policy allow, and an AI review of the evidence. Without a provider, the policy-approved checks run on their own. `GET .../validate/{request_id}` returns `queued`, `running`, `completed`, or `failed`, with the plan, the checks that ran, and the resulting classification. A match with an active request, or one finished in the last 5 minutes, returns that request. Each project allows 10 in progress and each user 20 requests an hour (429). The worker rechecks the requester's current access before it runs anything, and `retriage` uses the same queue.

**Diagnostics.** When an AI call fails, the finding keeps a retriable `error` status and an `ai.diagnostic` object (also shown as **Copy diagnostic**). It names the stage and a category such as `provider_auth` (check the key), `output_truncated` (check the model's output limit), or `schema_invalid` (the reply did not fit the triage format). It never contains credentials, prompts, model output, or target content, so it is safe to share.

`validation_status=observed` means a check read a banner or version without running a CVE-specific detector: it records what was seen, not a verdict.

**Remediation loop**

1. `register_assets` with the hosts, IPs, or CIDRs the agent is responsible for.
2. `get_remediation_work` returns open CVE-on-host items for those assets, fire first, with the host's IPs and the CVE's fixed versions. Fixed, accepted-risk, and closed matches are left out, and `?include_fp=0` also drops likely false positives.
3. `update_remediation_status` sets `open`, `in_progress`, `fixed`, or `accepted_risk` with a note.

Matches also carry `distro_status` (`patched`, `vulnerable`, `unknown`, `no_data`), `distro_label`, `evidence`, and the template test result (`vulnerable`, `no_match`, `error`).

**Remediation status on scanner and hygiene findings.** CVE matches, scanner findings, and hygiene findings each carry the same `remediation_status` (`open`, `in_progress`, `fixed`, `accepted_risk`), `remediation_note`, and `remediation_updated` fields, driven entirely by people or agents, never by a scan. They are independent of the finding's own auto-managed liveness signal (a CVE match's `ai_verdict`, a scanner finding's `open`, a hygiene finding's `status`): a scan re-detecting a finding never undoes a `fixed` or `accepted_risk` mark, and marking one of those statuses drops the finding out of `findings?status=actionable` (and the host's heat) immediately, whether or not the underlying check still finds it.

`PATCH projects/{slug}/findings/{kind}/{id}` (`update_finding_status`, `kind` one of `match`, `vulnerability`, `hygiene`) sets one finding's status and note; `kind=match` is identical to `PATCH .../matches/{id}`, kept as its own endpoint for the simpler single-kind case. `POST projects/{slug}/findings/status` (`bulk_update_finding_status`) sets the same status and note on up to 200 findings in one call, `{items: [{kind, id}, ...], status, note}`, and answers `{updated, failed: [{kind, id, error}]}` so one bad id never blocks the rest. A web route has no remediation workflow (its `auth_state` already says what it needs), so `kind=route` is a `400`. Every write here is logged to `activity` as `kind=remediation`.

`note` on every one of these routes, `update_remediation_status` included, is a true partial-update field: leave it out of the body and the stored note is untouched; send `""` (or any string) and it replaces it. Earlier, an omitted `note` was treated the same as an explicit `""` and silently cleared it.

Every match, scanner, and hygiene response (detail and `findings` rows alike) also carries `status_changed_at` and `status_changed_by` (`{id, username, name}` or `null`): the same moment and actor as `remediation_updated` and the write that made it, under names that read naturally for aging and SLA display. `findings` rows carry `first_seen` alongside the existing `detected` (the same moment); the type-specific list and detail endpoints already had `first_seen`.

**Assignee, comments, and audit trail.** Every match, scanner, and hygiene response (rows and detail alike) carries `assignee` (`{id, username, name}` or `null`) and `comment_count`. `PATCH projects/{slug}/findings/{kind}/{id}` (and `PATCH .../matches/{id}`) now takes `status`, `note`, and `assignee` as independent partial-update fields, at least one of `status`/`assignee` required: `assignee` is a user id, or an explicit `null` to unassign, and an id naming someone who cannot see the project is a `400`. `GET/POST .../findings/{kind}/{id}/comments` (`kind` one of `match`, `vulnerability`, `hygiene`; body `{text}`, up to 4,000 characters) lists comments oldest first and adds one; commenting is a write like any other, so read-only tokens and the audit role get `403`. `GET .../findings/{kind}/{id}/audit` answers the finding's trail newest first, `{results: [{id, event, actor, before, after, created}]}`, `event` being `status` (`before`/`after` `{status}`), `assignee` (`before`/`after` `{assignee}`) or `comment` (`after` `{comment_id, text}`); bulk status changes are audited per finding. `GET projects/{slug}/members` lists the project's direct members and its organization's, for an assignee picker (a superuser with no membership row is not listed). Validation runs are not yet written to the audit trail; the event enum can grow without changing any shape. `finding_detail` (`GET .../findings/{kind}/{id}`) now also reports `remediation.status`/`note` for scanner and hygiene findings, not only matches.

**API keys and runZero.** `GET projects/{slug}/api-keys` lists every service with `configured`, `scope` (`project`, `org` or `null`), `used_in_scans`, `used_by_sync` (the runZero key is read by the scheduled sync, not a scan) and `retired` (`null`, or the reason: BinaryEdge was shut down in March 2025, so `PUT` for it answers `410` and a key saved earlier is listed, unused, and can be deleted). `GET projects/{slug}/runzero` answers the runZero sync of the project: `{configured, import_enabled, search, state: never|running|ok|error, last_sync_at, last_ok_at, last_error, counts, interval_hours, import_max}`; `counts` is `{assets, matched_hosts, updated_hosts, cve_reports, corroborated_matches, truncated}` plus, when import is on, `imported` and `skipped` (`already_known`, `blocked`, `excluded`, `invalid`, `name_out_of_scope`, `over_cap`, `rejected`). `PUT` takes `import_enabled` (boolean, default off: add the addresses runZero knows and cvENGINE does not as targets, through the checks Add targets applies) and/or `search` (runZero inventory search limiting the import, at most 300 characters, blank means `alive:true`). `POST projects/{slug}/runzero/sync` queues a sync (`202 {queued: true}`; `409` while one runs, `429` within a minute of the last start, `400` with no token saved). All three need the organization admin or App Admin role (`403` for anyone else) and never return the token. A host's `ips[].runzero` carries runZero's facts for that address (`os`, `os_version`, `hw`, `type`, `tags`, `site`, `names`, `last_seen`, `vulns`: runZero's own CVE reports, evidence only), or `null`. A host record also carries `probes` (what version and identity probes found: `probe`, `kind` version, identity or edge, `product`, `version`, `variant`, `outcome` found, hidden, edge, challenged or absent, `source`, `confidence`) and `wordpress` (`status` with the state, why and when WPScan ran, `core`, `plugins` and `themes` with versions), or `null`.

**Third-party suppliers.** A supplier is a vendor the project depends on, never an owned host: it is not a target and none of the host, finding, hygiene, stats or remediation routes ever list it ([Pipeline](PIPELINE.md#third-party-suppliers)). `GET projects/{slug}/suppliers` answers `{count, page, results: [{id, name, tier, domains, contact, notes, added_by, created, last_checked, findings: {open, accepted, critical, high, medium, low}, hosts}], can_edit, limits: {max_suppliers, max_domains}, checks_enabled}`. `POST` takes `{name, domains: [...], tier: critical|high|normal, contact?, notes?}` and answers `201`; it is refused with `400` for a domain that is one of the project's own targets (or under one), an address, range, wildcard, URL, private name or excluded name, `409` for a duplicate name or the cap, `403` for anyone but the organization admin or App Admin (the audit role, a member and a read-only token included). `DELETE .../suppliers/{id}` removes a supplier with its cards and findings. Everyone with access to the project can read. `GET .../suppliers/hosts` answers the **host cards**: `{domain, supplier: {id, name, tier}, state (ok, unreachable, no_address, blocked, challenged, excluded), addresses, http: {https_status, http_status, status, title, server, powered_by, headers, cookies, ...}, tls: {subject, issuer, sans, not_before, not_after, days_left, key, signature, protocol, cipher, chain_error, legacy_tls}, technologies: [{name, version, category, source}], mail, evidence, checked, last_ok, matched}`. `?tech=php,node` is the **technology search**: comma separated terms, any of which matches anywhere in a technology's name and version or in the Server and X-Powered-By banners (`php 7`, `nginx 1.1`); `matched` lists the technologies that matched; `?supplier=` and `?tier=` narrow it. `GET .../suppliers/technologies` lists what the suppliers run, most widespread first (`name`, `category`, `suppliers`, `hosts`, `versions`). `GET .../suppliers/findings` lists the informational posture findings (`status` open by default, `accepted`, `resolved` or `all`; `supplier`, `severity`, `category` tls, email, web, exposed or cve); each carries `ask`, the plain-text note about what to ask the supplier, and a `cve` finding says `validated: false` in its evidence. `PATCH .../suppliers/findings/{id}` (`{status: accepted|open, note?}`, admin only) accepts a finding or opens it again; `resolved` is set only by a later check. `GET .../suppliers/{id}/summary?tech=` answers `{supplier, text, open}`, a plain-text message to copy and send (nothing is sent by cvENGINE). Text in cards and findings comes from the supplier's own responses and is untrusted data.

**Project settings and SLA days.** `GET projects/{slug}/settings` answers `{sla_days: {critical, high, medium, low}, sla_defaults}`: how many days a finding of each severity has to be fixed, the same for everyone in the project so "overdue" reads the same on every screen (defaults 7, 30, 90, 180; informational findings have no SLA). `PUT` changes it, `{sla_days: {...}}` as a partial update: send only the severities to change, each a whole number of days from 1 to 3,650, or `null` to go back to that severity's default. Anyone with a write role may change it, as with the project's API keys (a read-only token or the audit role gets `403`; the audit role can read). A finding is overdue when `first_seen` plus its severity's days has passed and its `remediation_status` is not `fixed` or `accepted_risk`. Single-project only: `_all` is a `400`.

**Stats history.** `GET projects/{slug}/stats/history` (`stats_history`) answers a bare JSON array, oldest first, of one point-in-time snapshot per day: `{date, hosts, exposed_hosts, open_findings: {critical, high, medium, low, info}, cve_matches: {fire, smoke, ice}, fixed, mean_days_to_fix}`. `?days=` bounds the window (default 90, capped at 365) to a number of calendar days ending today. Snapshots are written once a day by a beat task (`cveFeed.tasks.snapshot_daily_stats`, `cveFeed.stats_history`); a day before the feature existed, or one the task missed, is simply absent rather than backfilled. `_all` sums every visible project's rows per date; its `mean_days_to_fix` is the unweighted mean of the projects that have one that day, since the per-finding durations themselves are not stored.

**Instance status.** `GET system/status` (`get_system_status`) answers one read-only snapshot, so an agent can tell "idle" from "broken" without guessing:

- `overall` (`ok` or `degraded`), `problems` (what is wrong: a late schedule, workers not consuming a queue, a probe that failed, low memory or disk, a stalled scan, a stale CVE feed) and `notes` (state worth knowing that is not a fault: scanning paused, an update in progress, messages waiting in the queues).
- `scanning` and `update`. An App Admin gets `scanning` with paused, reason, who, since when, the last error, and whether an update's drain paused it, and `update` with the phase and its detail. Everyone else gets only `paused` and `paused_by_update`, and only the update `phase`. Also `version`, `at` (when the snapshot was taken), and `scope` (`instance` or `projects`).
- `projects`: for up to 100 of the projects the caller can see, `targets`, `hosts`, `exposed_hosts`, `scans` (`running`, `queued`, `stalled`), `open_findings` by severity and `cve_matches` by heat; `totals` adds up those 100.
- Each project's row carries `wordpress`: `{hosts, scanned, never_scanned, reasons}`, the WordPress hosts WPScan covered and, by state (`blocked`, `failed`, `waiting`, `detected`, `candidate`, `unavailable`), why the rest were not.
- `system`, for an App Admin only (anyone else gets `null` and a `system_note`): `database` and `broker` (reachable, latency), `queues` (messages waiting per Celery queue, and taken but not acknowledged), `workers` (which worker answers and whether it consumes its queue), `jobs` (pending validation, retest, scan and host-assessment work), `schedules` (how many are enabled and which are past due), `memory` per scanner container (total, used, available, the job budget, jobs running and waiting, memory kills in 24 hours, how old the report is), `disk` for the scan results volume, `feeds` (CVE count and last feed dispatch), `ai` (whether a provider is on and today's validation attempts), `work` (the work conductor: scans running and queued, the wanted depth, and the last round), `tools` (when the nuclei templates were last refreshed, and the nuclei, nmap, and WPScan versions), and `last_activity`. `runzero` lists each project with a runZero token (`state`, `last_sync_at`, `last_error`, `import_enabled`, `assets`) and the sync interval; a failing sync is also a line in `problems`.

Problems include a disk under 10 percent free, a CVE feed older than 48 hours, nuclei templates not refreshed for over 36 hours, and "nothing running or queued though targets exist".

Each probe is independent: one that fails or times out comes back as `{"error": "<exception name>"}` and a line in `problems`, never as a failure of the whole call. It returns no address, credential or task argument. Asking the workers takes up to ten seconds when none respond. A read-only token may call it.

## PDF reports

`POST projects/{slug}/reports` (`export_report`) queues a PDF report of one project, or of one host of it (`host`, an exact name from the inventory). It lists open findings only; `include_closed: true` also lists fixed and accepted-risk ones. The answer is `202` with `{id, status: "queued", status_url, download_url: null, ...}`; asking again for the same report while one is queued or running gives that one back with `200`. The report is built by a worker, so poll `GET projects/{slug}/reports/{id}` (`get_report`, `report_id`) until `status` is `done` (`queued`, `running`, `failed` with a short `error`, or `expired`). A finished report carries `size_bytes`, a `summary` (hosts and findings printed, the total, and `omitted`, what the caps left out) and `download_url`. `GET .../reports/{id}/download` returns `application/pdf` as an attachment with the same bearer token; MCP clients fetch it over REST.

A report is a read. Any role that can read the project (audit included) may ask for one, and so may a read-only token. It holds only that project's rows, and the worker checks the asker's role again when it runs: access removed in between is a failed report with no file. Only the user who asked can read it (anyone else, even an App Admin, gets `404`, the same as a missing report), and the file is deleted after 24 hours (`CVENGINE_REPORT_TTL_HOURS`; a download after that is `410`). `_all` is a `400`. More than 3 reports in progress per user, 20 an hour per user or 8 at once overall is `429` ([Configuration](CONFIGURATION.md#pdf-reports)). Each request is recorded in the audit log.

A report prints at most 500 hosts, 1,000 detailed findings (CVE matches and scanner findings, hottest first) and 500 hygiene findings; the summary counts always cover every finding, and the PDF and `summary.omitted` say what was left out. Text that came from scanned hosts is escaped and printed as text: the renderer is a separate process that fetches no URL and reads no file. See [Front end](FRONTEND.md#pdf-reports) for the contents.

## Limits

A domain name is unique within an organization (two organizations may each track the same name, as separate records). A range or CIDR target is capped at 10,000 addresses per call, and a bulk request at 10,000 lines or expanded rows (`CVENGINE_MAX_TARGETS_PER_ADD`). IP, CIDR, and range targets in loopback, link-local, multicast, reserved, or cloud metadata space are refused, along with any range in `CVENGINE_BLOCKED_CIDRS`. Private ranges (`10/8`, `172.16/12`, `192.168/16`, `100.64/10`, `fc00::/7`) need `CVENGINE_ALLOW_PRIVATE_TARGETS=1`, and tailnet addresses (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`) cannot be added by hand even then: only a connected tailnet imports them ([Tailscale](TAILSCALE.md)). Domain names are checked when they resolve. A search takes at most 15 terms of 200 characters each and 1,000 characters in all. Pasted target text is capped at 2,000,000 characters and each token at 2,048. Notes are cut at 2,000 characters, comments at 4,000, and an exclude or archive reason at 300. A bulk request takes up to 50 projects, a delete up to 5,000 ids, a rescan up to 200 hosts, and `register_assets` up to 500 assets.

The API does not expose instance settings, the AI key, bug bounty actions, or user management. It can set a project's own OSINT service keys (write-only) and read which services are configured.

See also: [TENANCY.md](TENANCY.md) for roles, [PIPELINE.md](PIPELINE.md) for what a scan does, [documentation index](README.md).

`get_cve_detection` returns the shared record of a CVE (summary, identify, confirm steps, true and false-positive signs, remote and local checks with rendered commands, scope). `update_cve_detection` (App Admin; `PUT cves/{id}/detection`) changes it with `guidance` (text the onboard AI folds in) or a whole `strategy`. CVEs only usable from the host itself carry `local_only: true` in `list_cves` and are never matched to a host. See [CVE-INTAKE.md](CVE-INTAKE.md).
