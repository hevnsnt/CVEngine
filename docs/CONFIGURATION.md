# Configuration

Every value in `.env` reaches the `web`, `celery`, and `celery-beat` containers. To change a setting, add a line such as `CVENGINE_TTL_NUCLEI=48` to `.env` and run `make up`. This needs Docker Compose 2.24 or newer. Compose fixes a few values and ignores them in `.env`: the broker URLs, `CELERY_BACKEND`, `DEBUG` (0 in production, 1 in the development stack), and `GUNICORN_WORKERS`. Avoid `#` and `$` in passwords, because `make` and Compose both parse `.env`.

## Basics

| Variable | Purpose |
| --- | --- |
| `DOMAIN_NAME` | A hostname such as `scanner.example.com`, or an IPv4 address. It is the certificate name and the host in notification links. The installer sets it to this machine's detected address (or `--domain`); change it in `.env` and run `make certs up` to use a name. The certificate also covers `localhost` and `127.0.0.1`, and any names in `CERT_EXTRA_SANS` (comma separated). |
| `CVENGINE_ALLOWED_HOSTS` | Extra hostnames Django accepts, comma separated. Any other name or IP gets 400 ([UPGRADE.md](UPGRADE.md#accepted-host-names)). Never use `*` on an Internet-facing install. |
| `CVENGINE_SETUP_DWELL_SECONDS` | `90` | How long the setup wizard waits for the first discovery before it opens the dashboard with nothing found yet (0 to 900; `0` turns the wait off). |
| `CVENGINE_HSTS_SECONDS` | HTTPS policy lifetime in seconds (3600 in production, 0 in development). Raise it only once every public route reliably uses HTTPS. |
| `POSTGRES_PASSWORD` | Database password. Set it before the first start, because changing it later does not update the existing database. |
| `AUTHORITY_PASSWORD` | Encrypts the key of the certificate authority that `make certs` creates (`secrets/certs/ca.key`, AES-256). An authority made by an older version keeps an unencrypted key until you delete `ca.key` and `ca.crt` in `secrets/certs` and run `make certs` again (browsers then need the new CA). Protect the directory either way. |
| `DJANGO_SUPERUSER_USERNAME`, `_EMAIL`, `_PASSWORD` | Used by `make admin` and `sudo ./install.sh`. Leave the password empty and `make admin` generates one and prints it once (you choose your own at first sign-in); set it to choose the first one yourself. `make admin-password` resets only the account named by `DJANGO_SUPERUSER_USERNAME` (`admin` by default), ignores `DJANGO_SUPERUSER_PASSWORD`, and always makes that account choose a new password at its next sign-in. For another user run `docker compose exec -T web python3 manage.py create_admin --reset --username NAME` or `make changepassword`. A plain `make username` asks instead. |
| `COMPOSE_PROJECT_NAME`, `POSTGRES_DB`, `POSTGRES_USER` | Name the Docker volumes and the database. Change them only before the first start. Leave `POSTGRES_HOST=db` and `POSTGRES_PORT=5432` as they are. |
| `AUTHORITY_NAME`, `COMPANY`, `COUNTRY_CODE`, `STATE`, `CITY` | Subject of the certificates `make certs` creates. |
| `CVENGINE_CERT_CHECK_SECONDS`, `CVENGINE_CERT_RETRY_SECONDS` | `43200`, `3600`. How often `scripts/renew-certs.sh` checks the web interface certificate (it is valid for 397 days and renewed when fewer than 30 remain), and the wait after a failed check. See [Deployment](DEPLOYMENT.md#https). |

`make certs` and `make username` refuse to run while the database or certificate password still says `change-me`. `./scripts/init-env.sh` (which `install.sh` and `make` run for you when `.env` is missing) fills those two with random values, also generates `CVENGINE_FIELD_KEY` and (when no Redis container exists yet) `REDIS_PASSWORD`, and leaves any other value alone. `STATE` and `CITY` stay `change-me`, which only affects the certificate subject. **Do not run `init-env.sh` or `install.sh` on an install made from an older `.env.example` that still has `change-me` as the database password:** it would replace that password, and PostgreSQL reads it only when the database is first created. Set the password you actually use in `.env` first.

## Memory and workers

**Where these settings live.** Some of the numbers below can be set in two places: in `.env` as before, or in the web interface under **Settings, configMaxxing** (App Admins only; collapsed until you open it, or go to `/cve/settings/#configmaxxing`). A value saved there wins over `.env`, and `.env` wins over the built-in default (the saved value wins over `.env` for every setting, always). Each row on the page shows the default, the allowed range, the environment value if one is set, where the number in effect comes from (saved here, the environment or the built-in default), who saved it and when, and whether it applies live; **Reset to default** removes the saved value, and a change is recorded in the audit log. These are instance-wide numbers, not per project or organization. Six cards live there today:

- **Auto-tuning**: the mode (Auto by default, Suggest, Off), the AI advisor switch, the last run and the tuning history with **Revert**. See [Auto-tuning](#auto-tuning) below.
- **Scan concurrency**: `DISCOVERY_CONCURRENCY`, `HEAVY_MAX_<KIND>`, `CVENGINE_ASSESS_BATCH` and `CVENGINE_WORK_DEPTH`.
- **AI spend**: the daily caps on triage and validation (`CVENGINE_TRIAGE_MAX_PER_RUN`, `_PER_PROJECT_DAY` and `_PER_DAY`, and the same three for `CVENGINE_VALIDATE_MAX_`), `CVENGINE_VALIDATE_MIN_GAP_HOURS`, `CVENGINE_TEMPLATE_GEN_MAX_PER_DAY` and `CVENGINE_AUTOTUNE_AI_MAX_PER_DAY`. They cap the calls to your AI provider, so they are the dial on what an installation spends. The provider, the model and the planning and CVE guidance budgets stay on the AI model tab. They are never auto-tuned.
- **Scan pacing**: `CVENGINE_STAGE_PARALLEL`, `CVENGINE_WORK_MIN_GAP_HOURS`, `CVENGINE_SENTINEL_REFRESH_GAP_HOURS` and `CVENGINE_BULK_DISCOVER_NOW`.
- **Auto-tuning pace**: `CVENGINE_AUTOTUNE_COOLDOWN_MINUTES`, `CVENGINE_AUTOTUNE_RAISE_COOLDOWN_MINUTES`, `CVENGINE_AUTOTUNE_WINDOW_HOURS` and `CVENGINE_AUTOTUNE_AI_INTERVAL_HOURS`.
- **Outbound connections**: `CVENGINE_LOCAL_PORT25_PER_HOUR`: how fast this server's own code may open connections to port 25. See [Cloud hosts and port 25](#cloud-hosts-and-port-25).
- **Heat policy**: `CVENGINE_HEAT_POLICY`, the rule that makes a CVE finding fire, smoke or ice (1 the KEV rule, the default; 0 legacy). Never auto-tuned.

The AI spend and Scan pacing numbers are read every time the code uses them (a saved value reaches every worker within about five seconds, with no restart; the web process publishes it to Redis and the 30 second tick publishes it again, so a flushed Redis heals). A setting that is only read when a process starts would say "Applies after the next restart" on its row; none of the numbers above is one. The page checks the range (the rows below name it) and refuses anything else; a value in `.env` is not range-checked, as before, so the page may show an environment value above its range or a fraction of an hour: it is shown as it is, a box you do not touch is never sent, and a value that fits can be pinned with **Save this value**. An integer setting in `.env` must be a whole number (`7.9` or `1e6` is not one, so the default applies, as it always did), and a number of hours is held to ten years. The daily caps show how much has been used so far (since UTC midnight; the template drafts over the last 24 hours), and the page warns, without blocking the save, when a cap is under a quarter of its default (work over the cap is deferred), more than ten times the environment value or default (it raises spend above the documented default), or when the conductor gap is 0 (rescans become continuous). A save is published with the database row's version, so a slow 30 second tick cannot overwrite it; if Redis loses the published copy, a process reads the database (at most once every five seconds) and publishes it again instead of falling back to `.env`, and only a Redis that cannot be reached keeps the last copy a process had. The numbers the page does not hold are still read from `.env` only. See [Scan more targets at once](DEPLOYMENT.md#scan-more-targets-at-once) for safe scan concurrency values by machine size.

### Auto-tuning

**On by default.** Every ten minutes (the `autotune` task on `cve_feed_queue`, one run at a time) the auto-tuner measures this instance and moves the throughput settings of configMaxxing that no person pinned. Nothing needs to be done to turn it on, on a new install or after an update. To tune by hand, open **Settings, configMaxxing, Auto-tuning** and choose **Off**; to keep one number as it is, type it in its box and save it, even if it is the number already shown (a saved number is **pinned**: the tuner never moves it, and the row says *Pinned by <user>* with a **Let auto-tune manage this** button that hands the same number back to the tuner). An environment variable in `.env` set to anything other than its built-in default pins its setting too (*Pinned by the environment (NAME=value): remove it from .env, or save a value here*); one set to the default is not a pin, because the compose files pass some variables with the default as a fallback (`DISCOVERY_CONCURRENCY=${DISCOVERY_CONCURRENCY:-8}`) and the two cannot be told apart. So a number saved on the page or chosen in `.env` before the update is pinned from the start and never overridden; a setting left at its default is tuned. `CVENGINE_AUTOTUNE=0` in `.env` turns it off for the whole instance (the kill switch; `make up` to apply).

**Modes.** **Auto** applies the changes itself. **Suggest** works out the same changes and shows each one on its row with the reason and an **Apply** button, and changes nothing (Apply saves the number as yours, which pins it). **Off** measures and changes nothing. Leaving Auto drops the tuned numbers at once: every setting goes back to its saved value, else `.env`, else the default; coming back to Auto starts again from there. Precedence for a tunable setting: saved by a person > `.env` when it is not the default > tuned (Auto only) > `.env` > default. The tuned numbers are published to Redis like the saved ones and reach every worker within about five seconds; a tuned discovery pool is resized live like a save.

**What it tunes** (auto-tuning range in brackets, inside what the page allows; in the registry next to each setting as `auto_tunable`, `auto_min`, `auto_max` and `auto_optimistic`). `HEAVY_MAX_<KIND>` for `nmap` (1 to 8), `nuclei` and `nuclei-light` (1 to 4), `bbot-standard` (1 to 4), `bbot-passive`, `wpscan` and `testssl` (1 to 6), `bbot-deep` (1 to 2), `route-probe` (1 to 16) and `screenshot` (1 to 4); not the background sweeps `nmap-full-bg` and `nmap-udp-bg` (they wait behind everything on purpose), not `naabu` (its raw SYN packets would double on the network) and not `template-test` (it runs AI-written checks). `DISCOVERY_CONCURRENCY` (4 to 32, two at a time), `CVENGINE_ASSESS_BATCH` (4 to 32, four at a time), `CVENGINE_WORK_DEPTH` (1 to 16; `0` stays off), `CVENGINE_STAGE_PARALLEL` (2 to 16), `CVENGINE_WORK_MIN_GAP_HOURS` (1 to 12 hours) and `CVENGINE_SENTINEL_REFRESH_GAP_HOURS` (2 to 24 hours; `0` stays off). `HEAVY_TUNE_MIN_<KIND>` and `HEAVY_TUNE_MAX_<KIND>` narrow or widen a scanner kind's range. The AI spend caps, `CVENGINE_BULK_DISCOVER_NOW` and the auto-tuning pace itself are never tuned.

**Aim high, then scale back** (`web/cveFeed/autotune_policy.py`; the deterministic controller needs no AI provider).

1. **Sized for this machine.** `size_for` works out an ambitious but sensible target for every setting from what the machine really has. A scanner kind gets as many runs as both the scanning container's memory budget holds at the kind's real peak (the learned peak plus 20%, or the estimate) and its share of the CPU carries: the kinds run side by side, so they share one CPU budget (the container's CPU limit, read from cgroup v2 `cpu.max` or the cgroup v1 CFS quota, times `CPU_BUDGET` = 1) by fixed shares (nmap 30%, nuclei 25%, nuclei light and bbot standard 10% each, the others 5% or less) at a core a run for nuclei and bbot deep, half a core for nmap, nuclei light and bbot standard, a quarter for passive bbot, WPScan and screenshots, a tenth for testssl and a fortieth for route probes (they mostly wait on the network); at 16 cores that is nmap 8, nuclei 4 and route probes 16, at 32 cores every kind but bbot deep reaches its auto-tuning maximum. **Nothing aims below what it ships with:** sizing from the CPU or the Sentinels never puts a target under the setting's built-in default (nmap 2, the discovery pool 8, and so on); only the memory budget at a kind's real peak, the database's connections and a small instance (the limits that protect the machine), and trouble, go lower. The discovery pool gets twice the live Sentinels' slots plus four (without Sentinels, two per core), never more than the database gives: the connections in use now (`pg_stat_activity`) plus the growth to 70% of `max_connections`, counted from the tasks the pool really runs and not from its ceiling (when the discovery worker did not say how many it runs, that headroom is not known and neither limits nor lowers anything), and never more than 70% of `max_connections` less 30 kept for the web server and the other workers (an install whose database still has `max_connections=100` gets 40 at most, so the page's 32 still fits beside the other workers; with `POSTGRES_MAX_CONNECTIONS=60` it would get 12). The assessment batch gets twice the Sentinel slots (at least 8), the work conductor half a scan per core plus one per three Sentinel slots (never more than the discovery pool), the chunks of one stage the Sentinel slots, the rescan gap 1 hour with four cores or more (else 2) and the Sentinel refresh gap 3 hours with four Sentinel slots or more (else 6). A small instance (under 100 hosts and targets) keeps the pool at 8 and the conductor at 3; under 10% free disk nothing goes above its optimistic value. A fact not reported yet (no worker has published its memory, no Sentinel is live) gives the setting's documented optimistic value, never the minimum, and the memory gate keeps holding work back meanwhile. So a 4 GB box starts well below a 64 GB one, and two Sentinels with nine slots get a pool of 22, not the page's 32. Each row shows *sized for this machine: N cores, X GB memory budget, Y Sentinel slots (target N)*.
2. **Aim high, after a short warm-up.** Once a restart or update is ten minutes old and the scanning container's memory and the Sentinels have reported (or after 30 minutes, with the optimistic values for what is still missing), every setting goes straight up to that target (never higher than a level that caused trouble, below). The jump only ever goes up, and a target that is only an optimistic stand-in never lowers anything. A setting a person just handed over with **Let auto-tune manage this** does not jump: the hand-over counts as a change.
3. **Scale back on evidence, at once.** Memory kills of a scanner kind, its runs failing for load (timeouts, out of memory, exit -9), memory pressure (a memory kill or under 10% free) or a CPU overload twice in a row while it runs, or its runs waiting for memory for half an hour with none running: that kind backs off. The database above 80% of its connections, a discovery worker that stopped answering twice, memory pressure or CPU load: the discovery pool and the conductor back off. Sentinel waits that timed out (two in one measurement, or one in each of two): the chunks of one stage, the assessment batch and the refresh gap back off. A back-off cuts a quarter to a half at once (at least two steps; for a gap the wait grows), waits for no cooldown and has no daily limit, then holds for 20 minutes before another one.
4. **Probe up slowly.** One step at a time, and only after two hours without trouble for that setting, `CVENGINE_AUTOTUNE_RAISE_COOLDOWN_MINUTES` (120) after its last change, with work waiting and room to spare (35% of memory free, the database under 60%, CPU load under the probe threshold) in the last three measurements in a row, at most twice per setting in 24 hours, never above the target, and never back to a level that caused trouble in the last 24 hours. The thresholds that allow a probe are far from the ones that force a back-off, so a setting does not swing back and forth.
5. **Brought down to the target at once.** A setting above its current target (from reported facts), a remembered bad level, or what the memory budget holds at a kind's real peak is lowered to it at once, without a cooldown: when the Sentinels leave, the discovery pool and the chunks of one stage follow. A Sentinel still counts for sizing until it has been missing from the measurements for 25 minutes (three runs in a row), so one that misses a heartbeat or restarts does not pull the settings down (they would otherwise only climb back one probe at a time, since the aim-high jump happens once per restart). Nothing changes while scanning is paused or an update is being applied. A person's **Revert** puts the last change back and holds that setting for 24 hours.
6. **When the database does not answer** (out of connections, or down) in two runs in a row (one failed run, such as a Postgres restart, is not an emergency), the run cannot read or record anything there, so it backs off from Redis alone: the tuned discovery pool and conductor (each of their tasks holds a connection) take one back-off step, then hold 20 minutes before another, like any back-off. While the database is away the source of truth is `cvengine:autotune:emergency` in Redis: every reader of the tuned numbers (the published copy, the 30 second tick that resizes the discovery worker, a container that starts) lowers those two settings to the emergency numbers, and the discovery workers are resized directly. The first run that reaches the database again writes them into the tuned numbers and the history (phase *backed off (database away)*; a number is only ever lowered there) and clears the key. Such an outage was transient once the database answers with room again, so after the 20 minute hold and three measurements in a row with room and no trouble the number before the emergency comes back in one step (phase *restored*), without waiting two healthy hours and outside the two probes a day, which stay for normal probes. That quick restore happens at most once a day per setting: if the database stops answering again within 24 hours of one, the restored level is remembered like a level that caused trouble, so the setting stays a step under it and comes back only by normal probes (no flapping between the two levels). A pinned or untuned setting is not touched, and the discovery workers are never resized below a pin: a value saved on the page (read from its Redis copy, as the workers read it, since the database is away) or an environment variable set to anything other than its default.

CPU load is the share of the container's CPU limit it used since the last measurement (cgroup accounting); a probe needs it under 0.7 and pressure is over 0.95 twice in a row. Where the cgroup cannot be read, the one-minute load average per core of the limit is used instead, with the thresholds 1 and 2.

**The AI advisor** ("AI tuned"). When an AI provider is set up and **Ask the AI advisor** is ticked (the default), every `CVENGINE_AUTOTUNE_AI_INTERVAL_HOURS` the tuner sends the provider a compact summary of its measurements (numbers and setting names only: no host name, address, finding or text from a scanned host; the prompt also passes the usual secret redaction), the target sized for this machine and, per setting, the lowest and highest number it may choose now, and asks it to be ambitious first: the highest allowed number unless the numbers show trouble. The answer is untrusted: it must be the JSON asked for, name only settings it was offered and stay inside that range (from one step down up to the controller's own target, the memory cap included); anything else is refused and recorded. It is never asked about a setting that is backing off. In Auto an accepted recommendation is applied (source `ai`). The calls count against `CVENGINE_AUTOTUNE_AI_MAX_PER_DAY` (AI spend; stage `autotune_advisor` on the AI usage page) and show in the system status. Without a provider, over the budget, or when the advisor fails, the controller tunes alone.

**Every change is visible.** A change is a row in the tuning history (kept 90 days) with the numbers before and after, its phase (aimed high, backed off, probed up, brought down to the target or the memory budget, backed off while the database was away, restored after it came back), its source (controller, AI advisor or a person) and its reason, an audit entry (`autotune.change`, `autotune.mode`, `autotune.apply`, `autotune.revert`, `autotune.release`) and a line in the activity feed; the row of the setting shows *Auto-tuned: 12 (was 8)* with the reason, the time and what it was sized for. The REST API (`/api/v1/tuning`, App Admin) and MCP (`get_tuning_status`, `list_tuning_decisions`, `set_tuning_mode`, `apply_tuning_suggestion`, `revert_tuning_decision`, `release_tuning_pin`) do the same ([Agent API](AGENT-API.md)); `get_system_status` shows the mode, what the machine was sized for, the targets, the last run, its last decisions and why each setting was not raised.

**What to expect on a typical install** (nothing to set). On a single server with a 4 to 5 GB scanning container (`CELERY_MEM_LIMIT`, a job budget of about 3.4 GB), an 8-core CPU limit and two Sentinels with nine slots, the first run after the update (about ten minutes in) sets nmap to 4, nuclei to 2, route probes to 8, testssl to 2, the discovery pool to 22, the batch to 18, the conductor to 7 and the chunks of one stage to 9, keeps every other kind at its default (bbot deep 1, bbot standard and passive and WPScan 2), then backs off whatever shows trouble. On a 4-core box nothing is set below what a fresh install runs. A setting you already saved by hand, or set in `.env` to something other than the default (for example **Hosts assessed at once** at 16), stays pinned and is not moved.

`<KIND>` is the kind in capitals with `-` as `_`: `BBOT_DEEP`, `BBOT_STANDARD`, `BBOT_PASSIVE`, `NUCLEI`, `NUCLEI_LIGHT`, `NMAP`, `NMAP_FULL_BG`, `NMAP_UDP_BG`, `NAABU`, `TEMPLATE_TEST`, `ROUTE_PROBE`, `WPSCAN`, `TESTSSL`. The OpenVAS add-on runs on a Sentinel, outside this budget. Estimates adjust to the peak each kind actually reaches, plus 20%. **Settings, Resources** shows them. The numbers of runs allowed at once are in **Settings, configMaxxing**.

## Scanning

Windows are hours. Every window is `CVENGINE_TTL_<SERVICE>` and a scanner skips a host it covered inside its window. Switches are not all read the same way: `CVENGINE_FULLSCAN`, `_UDPSCAN`, `_BUCKETS`, `_BUCKETS_GUESS`, `_WAFW00F`, `_RDP_SHOT`, `_ARCHIVE_LOOKUP`, `_AUTO_VALIDATE_ALL_MATCHES`, `_CVE_SEED`, and `_SENTINEL_VERSION_CHECK` are off for `0`, `false`, `no`, or `off` (`_VHOST`, `_SUBDIR_APPS`, and `_SUPPLIERS` also when empty); `CVENGINE_INTEL`, `_BOUNTY_CATALOGUE`, and `_HYGIENE_RDAP` are off only for exactly `0`; `CVENGINE_NAABU` and `CVENGINE_ALLOW_PRIVATE_TARGETS` are on only for `1`, `true`, or `yes` (naabu also `on`); `CVENGINE_NODE2SHELL` is off only for `0`, `false`, `no`, or `off`, so an empty value turns it on.

### Cloud hosts and port 25

**Since 1.4 the server sends no scan traffic** (every scan runs on a Sentinel, which is never paced because it runs on another network), so the ledger, the connection log and the governor below normally read near zero. They remain for the connections this server itself opens and for the settings that name them. What follows was written for a server that scanned by itself.

Many hosting providers (Contabo, AWS, GCP, Azure, DigitalOcean, Hetzner and others) watch the outbound connections of a server and throttle or block port 25, the SMTP port, when a server opens many of them: a burst of connections to port 25 on many addresses is what a spam bot looks like. A cvENGINE server that scans by itself does exactly that: nmap's fingerprinting pass and naabu's full port sweep touch port 25 on every address, testssl.sh tests STARTTLS on it, and a stage no Sentinel takes in time runs on the server (the local fallback). Some providers will not tell you their limit. cvENGINE keeps scanning port 25 by default (nothing that was scanned before is skipped) and does four things about it:

- **It measures.** The egress ledger counts the new outbound TCP connections this server's own scanners open, per hour for seven days: per watched port (`CVENGINE_LOCAL_WATCH_PORTS`, default 25, 465, 587, 23 and 3389), for all ports together, and per source (scan kind and project). `get_system_status` (MCP, `GET /api/v1/system/status`) shows the last hour, 24 hours and seven days under `egress`, and Settings, configMaxxing, **Outbound connections** shows port 25's use this hour. In-process probes are counted exactly; nmap, naabu, testssl.sh and nuclei are external tools, so they are counted from their probe plan (addresses times ports, before retries): an estimate. Use it to answer your provider, and to tune the budget below.
- **It logs every scanner connection to the mail ports.** Each outbound connection this server's scanners open to port 25, 465 or 587 (not the server's own mail notifications) (`CVENGINE_EGRESS_LOG_PORTS`) is one record in the connection log: the time, the destination address and port, whether it was sent, paced or skipped, the tool, the project and the scan, kept 14 days and at most 200,000 records (`CVENGINE_EGRESS_LOG_DAYS`, `CVENGINE_EGRESS_LOG_MAX`). Each record says whether it is **exact** (this server's own code opened, or refused to open, that very connection: the in-process probes, the database checks, a connection the budget held back) or **estimated** (nmap, naabu, testssl.sh or nuclei was handed that address and port; those tools send their own packets, retries included, which cvENGINE does not see one by one). Download it as CSV from Settings, configMaxxing, **Outbound connections** (or `GET /api/v1/egress/connections?format=csv`) to show your provider what ran and when.
- **It paces port 25.** A shared budget (`CVENGINE_LOCAL_PORT_BUDGETS`, default `25:400/hour`) is asked before a local nmap pass, naabu sweep, background full sweep, testssl.sh run, nuclei target on port 25, nmap probe, validation check or in-process connection touches port 25. **What is promised, exactly:** across every worker of this server (one window, on the Redis server's clock), any 60 minutes: at most 400 new port-25 connection attempts started by this server's own local scans; any 15 minutes: at most 100, or one testssl.sh run alone (the attempts of nmap, naabu, testssl.sh and nuclei are the estimates charged below). Attempts are charged when the process that makes them starts, after its wait for memory: a pass is planned first (which addresses get port 25 now and which are owed), and then each nmap chunk, naabu group, testssl.sh run, nuclei run and paced-pass run asks the window again as its process starts, giving back what its pass was granted when planned. With no room at that moment, that process runs without port 25 (`--exclude-ports 25`, `-exclude-ports 25`, `host:25` targets left out; a testssl.sh run or a run of port 25 alone is not started) and the port is owed or stays due, logged `paced`. A run held two hours in the memory wait is charged in the minute it starts, and two chunks of one pass started 20 minutes apart are charged each in its own minute. **What is charged:** one per address per nmap or naabu run whose own port plan includes port 25 (the SYN; when port 25 is open, nmap's version detection and banner script add a few more connections to that same service, and retries of unanswered SYNs are not counted); one per in-process connection (exact); `25` per nuclei target `host:25` (`NUCLEI_TARGET_CONNECTIONS`, an estimate, not a measurement: nuclei's HTTP probe of the port, http and https, plus about ten ssl and tcp templates that run against the port the target names, each retried at most once, rounded up); and `240` per testssl.sh run (`TESTSSL_CONNECTIONS`: testssl.sh 3.2.4 with this app's arguments, `-p -s -S -U -f --starttls smtp`, opened 159 connections against a modern TLS mail server and 231 against a legacy one, rounded up). A testssl.sh run is granted whole or not at all, and alone: only when the 60 minutes have 240 left and nothing was granted to port 25 in the 15 minutes before it, and nothing else is granted to port 25 in the 15 minutes after it. So at the default at most one run fits in any 60 minutes (beside up to 160 other attempts), a run waits for a quiet 15 minutes: the TLS audit asks every minute, without holding memory, and once it has waited 60 minutes it gets priority (ordinary new port-25 grants are held, paced and owed or due, until it starts, which the window then allows within at most another 61 minutes; it gives up after 122 minutes and stays due), and a budget below 240 means testssl.sh never tests STARTTLS on port 25 from this server (a Sentinel can); from a budget of 960 up, 240 fits in the ordinary quarter and a run is held to it like everything else. A nuclei target and the other single checks are granted whole too (all or nothing). On naabu's path an address is probed on port 25 only when port 25 is open on it (not because a chunk neighbour has it open, which nmap's per-chunk port list used to do), and a chunk nmap is stopped on for memory is retried without port 25 (owed instead), so every probe nmap is handed was charged. Within the budget the scan is the scan of before. Over it, the remaining addresses are scanned now without port 25 and port 25 is owed to a paced pass (queued every ten minutes by the background sweep, one pass at a time) that probes it as the budget allows, until every host has had it; a single check (testssl.sh, a probe, a validation check, a nuclei `host:25` target) stays due and runs on a later pass (a nuclei target with the host's next nuclei run; `host:25` targets are admitted least recently admitted first, so with room for four per quiet 15 minutes every target runs within ceil(N / 4) such runs). Owed entries are judged one by one: an address whose project is gone, that is no longer on a host of its project, or that was excluded or archived leaves the list with a log line; one not scannable right now stays owed without holding back newer ones; each is forgotten 30 days after it was first owed. A run is charged, counted and logged as sent only once it is let start (after its memory wait and, for the paced pass, its last scope check); a run refused there sent nothing and is neither charged nor logged as sent. The window lives in the broker's Redis and fails open: if Redis cannot be read, a run goes ahead unpaced (the worker log says so), as it did before this release; with the broker down, no new scan work is dispatched either. The activity log says `port 25 paced: n of m hosts this hour`, and again at 50, 80 and 100 percent of the hour's budget. 400 an hour is a cautious starting point, not a number any provider published (about one new connection every nine seconds when spread out, a small mail server's outbound pattern). Raise or lower it once the ledger shows what your server really sends; `0` turns the pacing off.
- **It can skip a port entirely, if you ask.** `CVENGINE_LOCAL_SKIP_PORTS=25` stops this server from ever connecting to port 25; a Sentinel does those checks instead.

What is not counted, paced or logged (every remaining path from this server to port 25 that the governor does not see): the nuclei network, ssl and javascript templates that connect to a port they declare themselves (in the nuclei passes and in validation and template tests; only a `host:25` target is governed), bbot's deep preset (its port scan), OpenVAS (gvmd's own port list), UDP (not a TCP connection to port 25), and this server's own mail (Settings, Email: the notifications it sends through your mail relay are not scanning). A port 25 the paced pass finds newly open is stored like any open port but does not start the new-port re-test the background full sweep starts. The ledger, the connection log and the owed ports live in the broker's Redis: a Redis restart without persistence loses them, and an owed port 25 then waits for its address's next regular rescan (up to seven days).

The better answer is to run SMTP-heavy scanning where port 25 is allowed: put a Sentinel on a network that permits outbound port 25 (an office line, a server with a provider that allows it), and keep the server's own scanning for what no Sentinel takes. To change these numbers, set the variables in `.env` and restart, or save them under Settings, configMaxxing, **Outbound connections** (port 25's budget and the fallback caps apply within seconds).

The AI key, the instance-wide Chaos, Netlas and HackerOne keys, per-organization and per-project API keys, update token, webhook URLs, Telegram bot token, the proxy list (its passwords), the two-step sign-in seeds, the Tailscale credentials, the OpenVAS login and the headers and cookies stored for authenticated checks are encrypted in the database. An installation that predates it keeps reading its old values with the key derived from `web/secret`, and `make rotate-field-key` moves everything under a dedicated key: it writes a new key to `.env`, keeps the old one in `CVENGINE_FIELD_KEY_PREVIOUS` (which only decrypts), recreates the services and re-encrypts every stored secret. What this protects: a database dump, a backup, or SQL injection reads only ciphertext, and a file read in `web/` no longer includes the key. What it does not: code execution inside a container that decrypts the secrets (the web service or a worker) can use the key that container holds. The settings API never returns a secret, only whether one is set.

## AI requests

Each variable below has a counterpart in **Settings, AI model** (the same name in the settings API: `request_timeout`, `connect_timeout`, `max_tokens`, `context_tokens`, `structured_mode`, `reasoning`). **The setting wins over the variable**: a value saved on the page replaces the variable, so a change made in the browser is not undone by an old line in `.env`; an empty setting follows the variable, and with neither set the request is exactly what earlier versions sent. A saved value is checked against the range written below when it is saved and again when it is used. The page and `GET /cve/api/settings/ai` show, for each setting, the value in force and where it comes from (the setting, the environment variable, or the provider's default). One more setting has no variable: `keep_alive` (Ollama: how long the model stays loaded after a request: `30m`, `1h`, `90s`, `0` to unload at once, `-1` to keep it loaded; empty is the server's default, five minutes). The settings apply to every stage and to the connection test; every change is recorded in the audit log (`ai.settings`, the names of what changed and the new value of the numbers and words, never a key or an address). These variables are read by the server containers, which is where the `.env` reaches; for the stages whose model calls the AI reviewer container makes (triage and local-check suggestions, [AI-REVIEWER.md](AI-REVIEWER.md)), the server resolves them and hands the result to the container with each configuration it reads, so they are set in the same place as before and nothing is set on the reviewer.

| Variable | Default | Purpose |
| --- | --- | --- |
| `CVENGINE_AI_TIMEOUT` | `120` (`300` for LM Studio) | Seconds one AI request may wait for its answer, 10 to 3600. A local model on a laptop can go past 120 seconds on a long stage; the setting applies to every provider. |
| `CVENGINE_AI_CONNECT_TIMEOUT` | `10` | Seconds to reach the server, 1 to 300, apart from the wait for the answer above (which stays 120 for Anthropic), so a server that is down fails at once. Raise it when the route to the provider goes through a slow proxy or a distant network. |
| `CVENGINE_AI_MAX_TOKENS` | `2048` for Anthropic, vLLM, LM Studio and Ollama; none for OpenAI and OpenRouter | A limit on the length of a reply, 64 to 32768, for every provider: `max_tokens` for Anthropic, vLLM, LM Studio and OpenRouter and for OpenAI behind a proxy, `max_completion_tokens` for OpenAI's own API, `num_predict` for Ollama. Unset, Anthropic gets 2048 as it always did, a self-hosted server and Ollama get 2048 (400 for a finding triage, whose answer is a short JSON object), and OpenAI and OpenRouter get none, so a hosted reasoning model keeps its own limit. A value you set replaces all of these, the triage's too. A triage reply cut off at a limit is asked once more with twice the limit; one that is still cut off, or has no text at all (a reasoning model that never answered), is reported as `output_truncated` or `empty_response`, not as an invalid answer. See [Local models](DEPLOYMENT.md#local-models). |
| `CVENGINE_AI_STRUCTURED` | `auto` | Whether a triage request carries a JSON Schema the reply must follow. `auto` sends it to the self-hosted servers (vLLM and LM Studio as `response_format`, Ollama as `format`), where it makes a small model reliable at the format; a server that refuses it is asked in JSON mode and then without, and that is remembered for an hour per server and model. `all` also sends it to OpenRouter and OpenAI, `off` to nobody. Hosted providers are never sent it by default: their models follow the prompt, and a refusal there costs a paid request. The reply is validated either way. |
| `CVENGINE_AI_REASONING` | unset (nothing is sent) | Opt-in reasoning control for the model that answers: `off`, `low`, `medium`, `high` or `max`. Unset or any other value sends nothing, as every earlier version did. Applied by what the provider and model take: OpenAI's o-series and gpt-5 models get `reasoning_effort` (`max` is sent as `high`; `off` is not sent, since those models cannot be switched off from here); Claude 4.6 and later (Haiku, Sonnet, Opus, Fable 5.x) get `thinking: {"type": "adaptive"}` and `output_config: {"effort": ...}` (never `budget_tokens`, never a temperature, top_p or top_k), and `off` sends `thinking: {"type": "disabled"}` only to the models that think by default and accept it (Opus 5, Sonnet 5, Haiku 5.5), nothing to the others; Claude 3.7 to 4.5 get `thinking: {"type": "enabled", "budget_tokens": N}` with N of 1024 (`low`), 4096, 8192 or 16384 (`max`), cut so that N is at least 1024 and leaves 1024 tokens of `CVENGINE_AI_MAX_TOKENS` for the answer (at the default 2048 that is 1024 for every level: raise the limit to use the higher ones); Ollama gets a top-level `think` (true, false, or a level for gpt-oss) for qwen3, deepseek-r1, gpt-oss and magistral models. vLLM, LM Studio and OpenRouter are sent nothing: set it on the server. A model that has no such control, or a level that cannot be sent, ignores the setting and says so once in the log. Thinking spends the reply limit, so raise `CVENGINE_AI_MAX_TOKENS` with it. See [AI models](DEPLOYMENT.md#ai-models). |
| `CVENGINE_OLLAMA_NUM_CTX` | unset | The context window to ask Ollama for, 512 to 1048576 tokens. Ollama sizes it by the machine's memory (4k tokens under 24 GiB, 32k from 24 to 48 GiB, 256k above) and cuts a longer prompt at its start without an error; set it when a host-context prompt does not fit. When it is set, a prompt that came within 5% of it is logged. |

A finding's triage on a self-hosted server (Ollama, vLLM, LM Studio) is asked with temperature 0 and a fixed seed, so the same evidence gets the same verdict (llama.cpp's seed is random unless set).

| `CVENGINE_CSRF_TRUSTED_ORIGINS` | none | Your public https address when you use your own proxy or CDN, such as `https://scanner.example.com`. |
| `CVENGINE_GUARD_STRIKES` | `3` | Points within 15 minutes before the input guard disables the account, revokes its tokens, and blocks a public client address for 24 hours. A command injection attempt is worth 3. Points are counted per account for the account and per address for the address, so one person's strikes never disable another's account. The free-text fields of an authenticated API or MCP call (comment `text`, `note`, `summary`, `output`) are not inspected. Superusers are only logged. |

## Settings in the app

**Sentinels.** Not a Settings tab: the **Sentinels** page (and a project's own Sentinels tab, shown once a Sentinel covers the project) holds enrollment, each Sentinel's settings (name, where it runs, size, what it may take per task kind (allow, deny or prefer, with a cap), concurrency, self-update; the most recent change wins, whether made there or in the Sentinel's own `.env`), and for App Admins the instance-wide self-update default. Who may do what is in [TENANCY.md](TENANCY.md#newer-surfaces); the dispatch waits, the version check, and the retention listed above are this server's environment settings for them.

**API keys for outside services.** Add them under **Settings, API keys** (App Admins) or **Administration** (organization admins), per organization; a project's own key wins, field by field, and a project that sets only part of a pair keeps the rest from its organization. A key is stored encrypted and never shown again. During discovery cvENGINE writes the keys of the project into a private preset file (mode 0600, deleted when the scan ends) that bbot merges with its own presets, so a key never appears on a command line. The services and what each key switches on:

| Service | What uses the key | Notes |
| --- | --- | --- |
| Shodan | bbot `shodan_dns` | `shodan_idb` (InternetDB) needs no key and always runs. |
| Censys | bbot `censys_dns` | bbot uses the legacy Search API, so enter the **API ID and secret** of a legacy account. A new account that has only a personal access token cannot be used by bbot. **Censys has announced the end of the legacy Search API** ([legacy search deprecation](https://censys.com/blog/legacy-search-deprecation)) and bbot 3.0.2, the newest release, has no module for the replacement platform API, so this key may stop working: if Censys results disappear, that is why. cvENGINE will switch as soon as bbot supports the new API. |
| VirusTotal, SecurityTrails, FullHunt, LeakIX, Hunter.io, Chaos, AlienVault OTX, C99, BeVigil, BuiltWith, BufferOver.run | the bbot module of the same name | Chaos also accepts one install-wide key (the **Instance-wide fallback** line on the API keys page), used when no organization or project has its own. |
| GitHub | bbot `github_codesearch` and `github_org` (and the other GitHub modules in a deep scan) | A personal access token. |
| WPScan | cvENGINE itself, against WordPress hosts | See WPScan below. |
| runZero | cvENGINE's own scheduled sync, not bbot | See runZero below. |
| BinaryEdge | retired | Nothing reads a stored key. See below. |

A module whose key the service refuses is skipped by bbot and the scan carries on. cvENGINE now reports it: an activity entry names the service ("VirusTotal: the key was not accepted") with the reason bbot gave. The older lookups keep an instance-wide key each: Netlas (WHOIS), Chaos (the fallback above) and HackerOne (bounty submissions). There is no API vault tab any more: only the Chaos fallback has a place in the app, and the settings API (`/cve/api/settings/keys`, App Admins) still reads and writes all of them.

**RDP screenshots.** When nmap shows an RDP server accepts a connection without Network Level Authentication (the same finding as "RDP does not require Network Level Authentication"), cvENGINE captures its pre-authentication login screen with no credentials sent, stores the image, and asks the configured AI model whether it shows an account already signed in and what it is called. A server that requires NLA is never attempted: there is nothing to see before authentication, and nothing is guessed. The username, when the screen shows one, is not a secret; anyone who can reach the port already sees it. Needs the configured AI model to support image input; without one, the screenshot is still taken and stored, just not read.

**Database metadata.** nmap's own scripts read each database's pre-authentication greeting (MySQL, Microsoft SQL Server, MongoDB, Redis, Memcached, and CouchDB) and cvENGINE parses it into the version, role, and, for MySQL and Microsoft SQL Server, the Windows identity its NTLM negotiation discloses. This fills in `Port.version` and `Port.product` only when nmap's own probe came back empty, and is shown on the host page next to the port. It never sends a credential and answering says nothing about whether one is required. That question is answered separately: alongside the existing Redis, Memcached, PostgreSQL, Elasticsearch, and CouchDB checks, cvENGINE makes one read-only, no-credential attempt against MySQL (`root` with no password) and MongoDB (an unauthenticated `listDatabases`), and a server that lets it straight through is a critical finding, the same as the others.

**WordPress scan.** The WordPress scan is the primary WordPress assessment, and it runs on a Sentinel only: this server never runs the tool (the `wpscan` kind is in `sentinel_dispatch.NEVER_LOCAL`, so `CVENGINE_LOCAL_FALLBACK` does not bring it back). cvENGINE sends a Sentinel every host that shows any sign of WordPress (a technology tag, a header or page signature, the login page, the REST API, plugin paths in crawled URLs, a title, the web archive's memory of the host, or an earlier probe) and every name of a grouped host that a read-only probe finds to be WordPress, positive probes first, and every candidate ends in a recorded state (scanned, detected, blocked by the edge, failed with its reason, waiting, not WordPress) shown on the host page and counted in the system status. The Sentinel runs the quick pass: the core version, the plugins and themes the site's own pages reference (passive detection, with versions, no token needed), config backups, database exports and the first author ids, with a random user agent and a throttle, and it finishes in minutes with a report. The **thorough pass** then asks the site for every plugin and theme the scanner knows (mixed detection, plus timthumbs: about 170,000 requests, hours per site). It is its own Sentinel task kind, `wpscan_thorough` (contract version 3, a Sentinel that declares it), also never run on this server: a background task on its own queue (`wpscan_queue`) sends one site at a time and one pass per project at a time, with its own time limit (`CVENGINE_WPSCAN_THOROUGH_TIMEOUT`, 12 hours by default, held between ten minutes and a day) that travels with the task, and a partial report if it is cut short. The server keeps the task's lease for that time plus a short grace to report, and no longer, so no new lease setting is needed. It never blocks the scan, correlation or triage, stops while scanning is paused (the host stays waiting), is repeated every 30 days, and its state (queued, running, finished, stopped early, blocked, failed) is on the host page and in the system status. With no scanner able to take either kind the work waits and stays due (a thorough pass is asked again a little later, a few times, then at the next scan). No password guessing. Plugin and theme versions need no token. Vulnerability data comes from a vulnerability API: add the token under **Settings, API keys, WordPress vulnerability data** (per organization or project; a project's own token wins). The free plan allows 25 requests a day and each site costs one request for the core plus one per plugin and theme: when the budget is spent the scan still runs on the remaining sites without the token, and each says "not checked: API token budget exhausted" and is repeated after a day (`CVENGINE_TTL_WPSCAN_PARTIAL`); a clean run is repeated after a week (`CVENGINE_TTL_WPSCAN`, 168 hours), a failed run at the next scan. The scan checks at most 20 sites per scan (`CVENGINE_WPSCAN_MAX_SITES`) and the whole stage has a one hour budget (`CVENGINE_WPSCAN_STAGE_SECONDS`); a candidate beyond either limit is recorded as `waiting` and goes first next time. If an edge (Cloudflare, Akamai, Sucuri, Imperva) answers the scan or the probe with a challenge or a block, the host says "the edge challenged the scanner" and what to allow (the scanner's address or user agent in the WAF or bot rules); cvENGINE never tries to solve a challenge or get past a WAF. Findings appear in Findings with the source `wpscan`: CVE ids, the fixed version, remediation text, exposed backups, usernames, XML-RPC and outdated components. The core, plugin and theme versions are also versioned sightings: a CVE for a plugin matches only when the plugin (by its slug, or the title in its readme) is the product the advisory names and its version is inside the advisory's bounded range. The token travels with the one task that needs it and is scrubbed from the stored task when it ends, never put on a command line or in a log. The Sentinel reports the scan's JSON report, its exit code and the tail of its stderr; the server classifies them (0 clean, 5 vulnerabilities found, 4 the scan did not finish: not WordPress, blocked, unreachable, the report says which, 1 bad option, 2 interrupted, 3 unexpected error). The scan's licence is free for testing your own systems and for penetration testing, and a commercial licence is needed to use it in a managed or hosted service, so check it before offering cvENGINE to others as a service.

**OpenVAS (Greenbone).** An optional, off-by-default add-on that a **Sentinel** runs (kind `openvas`, in `sentinel_dispatch.NEVER_LOCAL`: this server opens no GMP session and never runs the scan, whatever `CVENGINE_LOCAL_FALLBACK` says; [docs/OPENVAS.md](OPENVAS.md)). An App Admin switches it on in Administration > OpenVAS and the organizations choose what to scan. A task that runs longer than its time budget, `CVENGINE_OPENVAS_MAX_HOURS` (24) per host, is stopped by the Sentinel and what it found so far is kept. `CVENGINE_OPENVAS_MAX_HOSTS` (1) caps the hosts in one task (at most 16, the most a Sentinel takes in one OpenVAS task: a larger value is held to 16 with a warning), `CVENGINE_OPENVAS_MAX_CHECKS` (4) the checks run at a time against a host, only Fire or Smoke hosts are scanned (see [docs/OPENVAS.md](OPENVAS.md#what-gets-scanned)), `CVENGINE_OWN_ADDRESSES` lists this instance's own addresses OpenVAS must refuse (besides what `DOMAIN_NAME` resolves to), and `CVENGINE_TTL_OPENVAS` (168 hours) and `CVENGINE_TTL_OPENVAS_FAILED` (72) say how long a scanned and a failed host stay fresh. The GMP login is the Sentinel's own; this server stores none.

Keys for outside services are saved under **Settings, API keys**, for an organization (its projects inherit it) or for one project (which overrides the organization's); changing either needs the admin role for that organization or project. Secrets are encrypted at rest, write-only (the app only says whether one is set) and never put on a command line or in a log.

| Service | What reads the key |
| --- | --- |
| Shodan, Censys, VirusTotal, SecurityTrails, FullHunt, LeakIX, Hunter.io, Chaos, GitHub, OTX, C99, BeVigil, BuiltWith, BufferOver.run | The matching bbot module during discovery. A service without a key is skipped or runs without one. |
| WPScan | The WPScan stage of a scan (see below). |
| runZero | The scheduled runZero sync (see below), not a scan. |
| BinaryEdge | Nothing. Retired: see below. |

**BinaryEdge is retired.** Coalition shut BinaryEdge down as a standalone service on 31 March 2025 (accounts closed that day, as Coalition's [transition FAQ](https://help.coalitioninc.com/hc/en-us/articles/34383910057371-BinaryEdge-Transition-FAQ) says; the old API host no longer serves API answers), and bbot has no BinaryEdge module, so there is nothing to connect a key to. New BinaryEdge keys are refused (`410`), the page and the API mark it `retired` with that reason and `used_in_scans: false`, and a key someone saved earlier is kept, shown as retired and can be removed, but is never used.

### runZero

[runZero](https://www.runzero.com/) is an asset inventory: it knows devices, operating systems and hardware that an outside scan cannot see. cvENGINE reads it, read-only, with the project's **runZero Export API token** (an `ET...` or `XT...` token from runZero's Account, Organization or Export token pages; organization and account tokens also work). It talks only to runZero's hosted console, `https://console.runzero.com/api/v1.0`, over HTTPS with the token in the `Authorization: Bearer` header; the address is fixed so it cannot be pointed at another host, and **self-hosted runZero consoles are not supported yet**.

A sync runs every `CVENGINE_RUNZERO_SYNC_HOURS` hours (default 6) for each project that has a token, and on **Sync now** (the runZero card on the API keys page, `POST projects/{slug}/runzero/sync`, or the `run_runzero_sync` tool). Each project syncs on its own: an organization token shared by several projects is read once per project, which is a few API calls each, against runZero's daily limit of calls per licensed asset and its limit per source address (a 429 is waited out, then reported; when runZero's `X-API-Usage-Remaining` header says the day's quota is nearly spent, the sync stops early, says `quota_low` and carries on at the next one; a sync that stopped early, hit the 50,000 record cap or got an empty answer stores what it read but removes nothing, since an absent record then does not mean runZero dropped it). It does two things:

1. **Enrichment (always on once a token exists).** For every runZero asset whose address is an IP cvENGINE already holds for the project (an address of the same organization that one of the project's own hosts resolves to; another organization's row for the same address is never touched), runZero's OS and version, hardware, type, tags, site, names and last seen are stored on the address. The OS also fills the address's OS guess when nmap has none. They appear on the host page (Overview and Services) and in the host's `ips[].runzero` in the API. runZero's own CVE reports for those hosts (`vulnerabilities.json`: CVE, service address, port, severity, CVSS 3) are listed there as **runZero reports**. They are additional evidence only: a CVE match cvENGINE already found for the same host and port gets its confidence raised by 0.1 (once, capped at 1.0, never for a match the AI ruled out or a distribution patched), which orders it higher, and the boost is taken back when the report or the asset disappears from runZero (an asset that left the inventory stops describing the host, too); a report never creates a match, never sets an AI verdict, and never confirms a finding.
2. **Import (off until you turn it on per project).** With **Add runZero addresses cvENGINE does not know as targets** on, addresses runZero lists that are not yet targets of the organization are added through the same code as Add targets, so organization exclusions, `CVENGINE_ALLOW_PRIVATE_TARGETS`, `CVENGINE_BLOCKED_CIDRS` and organization-wide uniqueness all apply, and each new target is queued for discovery. The **runZero search** (runZero inventory search syntax, default `alive:true`) limits which assets are imported; enrichment always reads the whole inventory. A sync imports at most `CVENGINE_RUNZERO_IMPORT_MAX` new targets (default 500; the rest wait for the next sync). A runZero name is imported only when it sits under a domain the organization already has: names on a network are chosen by whoever runs the device, so they are never accepted as a scope decision. **A public address is imported only inside a network the organization already has as a target** (a CIDR block or an address): an inventory search such as `alive:true` can hold third-party addresses (a partner's range, a cloud address a device talked to) that nobody authorized scanning, so those are skipped as `not_owned`. The result lists what was skipped and why: already known, blocked (loopback, link-local, or private without the setting), not owned, excluded, a name out of scope, over the cap.

The API keys page shows the last sync, its counts and any error; `get_system_status` lists each project's runZero state for an App Admin and reports a failing sync as a problem; every sync writes an activity entry. A rejected token (401 or 403), a rate limit (429), an unreachable console, malformed JSON and an oversized reply (more than 32 MB, or more than 50,000 records per call) are each reported in plain words, the next scheduled sync tries again, and none of them stops the worker. Managing the sync (status, settings, Sync now) needs the organization admin or App Admin role. Needs migration 0087 (`RunZeroSync`) and the beat entry it creates, `cvengine-runzero-sync`.

Superusers set the rest under **Settings**, one tab each: AI model, API keys, Tailscale, OpenVAS, Notifications, Email, Scan policy, IP allowlist, Proxy, Reports, Resources, Updates, and Factory reset. There is no Scan engines tab: every scan runs the same fixed pipeline, and the engine editor that earlier versions inherited from reNgine was removed because nothing read it (an old `#engines` link opens Scan policy). The proxy list shows a password as `***` (`http://user:***@host:8080`); leave that text as it is to keep the stored password, or type the full URL to replace it. With **Proxy** on, the scans that run on this server send their traffic to targets through one of the listed proxies (`http://`, `https://`, `socks5://` or `socks5h://`, one per line, picked per request in turn; the list is stored encrypted, and a change applies within a few seconds). What is covered and what is not is listed on the card and in [Pipeline](PIPELINE.md#keeping-scans-fast-and-polite): the web probes and checks, nuclei, bbot, WPScan, testssl.sh and wafw00f go through it; nmap, naabu, the UDP sweeps, the database and RDP checks and OpenVAS need raw sockets and still leave from this server directly, a Sentinel runs on its own machine and keeps its own egress, and calls to outside services (CVE feeds, AI providers, Shodan, GitHub and the like) are not proxied. A proxy that is down fails the request instead of falling back to a direct connection, and a tool that cannot use any listed proxy does not run (testssl.sh takes only an `http://` proxy without a login, and the in-process checks do not take an `https://` proxy). Loopback, this stack's own services, private, link-local and tailnet addresses (unless `CVENGINE_PROXY_PRIVATE=1`) and anything in `CVENGINE_PROXY_BYPASS` or `NO_PROXY` are never proxied. A scan marked running counts as stalled once it is older than the discovery and nuclei timeouts set under Administration, Timings, plus an hour (11 hours with the defaults).

**Nuclei templates.** **Settings, Scan policy** has one switch, **on by default** since 1.3, that lets scans run every installed Nuclei template, including checks that send more than plain GET, HEAD, or OPTIONS requests. Turn it off to run only the read-only templates. It applies to the broad scans and to validating a CVE match. AI-written templates always stay read-only, Nuclei's denial-of-service templates stay excluded, and out-of-band checks stay off. Changing it is recorded in the audit log and makes hosts due for a new Nuclei pass. An install where an App Admin had already chosen keeps that choice when it updates to 1.3 ([UPGRADE.md](UPGRADE.md#upgrading-to-13)). The Reports tab only sets report branding.

**Other sites and subdirectory applications.** Both sweeps are switched on and off with their environment variable above (`CVENGINE_VHOST`, `CVENGINE_SUBDIR_APPS`), the same way as the other slow sweeps (`CVENGINE_FULLSCAN`, `CVENGINE_WAFW00F`): there is no page switch, and `get_system_status` shows for each project whether each is on and what it holds (`web_discovery`). They run on their own `vhost_queue`, stop while scanning is paused, never touch an excluded or archived host or an address the scannable gate refuses, send only GET requests with no body, cookie or credential, and record an edge that challenges them as `challenged` (what to allow in the WAF is shown on the host page) without retrying. The whole set of questions, what they find and how it reaches CVE matching are in [Pipeline](PIPELINE.md#other-sites-and-applications-on-a-host).

**AI planning budget.** Settings, AI model has two limits on how many times a day the model may be asked to plan **Validate now** checks: 200 across all projects and 20 per project by default (0 to 100000; 0 turns AI planning off). The day starts at 00:00 UTC. Once a limit is reached, only a vetted CVE-specific template runs until the next day, and the message points here. The auto-fire card on the same tab sets **Max hosts tested per CVE** (200 by default, 1 to 5000). The same tab sets how many CVEs the model may write guidance for per day (25 by default, 0 to 100000, 0 turns it off; **Write now** queues a batch), and builds the CVE catalog seed a new install can load.

**Development stack.** `CELERY_AUTORELOAD=1` restarts workers on every `.py` edit and kills any scan in flight. The development compose file sets it to 0. `CVENGINE_DOMAIN` gives `scripts/init-env.sh` the address when you do not pass one, and `CVENGINE_NO_START=1` makes `scripts/install-updater.sh` install only the cron entry. `CVENGINE_DETECT_IP` makes `scripts/init-env.sh` use that address instead of detecting one (a test hook).

**node2shell (CVE-2026-111497).** Off by default (`CVENGINE_NODE2SHELL=0`): see above for why. When on, it runs [Assetnote's own read-only detector](https://github.com/assetnote/node2shell-scanner) against hosts already fingerprinted as Node.js or Express. It never executes a command and never sends a credential; a host is reported vulnerable only when the detector's own controls establish a real, stable signal first.

Notification channels (Slack, Discord, Telegram, Lark) get at most one message per feed sync, scan, or automatic template-test run, naming up to five matches. A match is announced only with evidence it exists: a version in the affected range, a template hit, or the distribution tracker calling it vulnerable. A [saved search](SEARCH.md#saved-searches-and-alerts) gets at most one message per search per check (up to five new hosts named), under the "Interesting findings" switch.
