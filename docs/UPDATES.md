# Updates

**Nothing changes the code of an install on its own.** Under Settings, Updates, *How updates are installed* is **Manual** by default: CVEngine tells you when a new version exists and installs nothing until an administrator clicks Approve. Choose **Automatic** there, and only then, to have a found update approved for you; automatic deployment (below) deploys only while it is set to Automatic too. The choice is stored in `web/.update-mode`, and a missing or unreadable file counts as Manual.

Three ways to stay current. Pick one. Running `install.sh` again is not an update: it rebuilds the code you already have checked out and does not fetch anything new.

| Way | Who acts | Script | Best for |
| --- | --- | --- | --- |
| [Automatic deployment](#automatic-deployment) | nobody, once Settings is set to Automatic | `scripts/update.sh`, started by a timer | A server that should always run the latest `master` |
| [Approval in the app](#approval-in-the-app) | an administrator clicks Approve | `scripts/apply-update.sh`, started by cron | Installs that want a human in the loop |
| [By hand](#by-hand) | you run one command | `scripts/update.sh` | Everything else |

All three keep the database and Redis in place and need a Git checkout, because every updater works through Git. The release page also offers `.zip` and `.tar.gz` source archives and a software bill of materials, with a `SHA256SUMS` file, for reading, mirroring, and offline transfer. They cannot be updated in place. Moving an old install across the PostgreSQL 18 change is in [UPGRADE.md](UPGRADE.md).

The two scripts differ in how carefully they restart:

| | `update.sh` (manual, automatic) | `apply-update.sh` (approval) |
| --- | --- | --- |
| Builds | while everything keeps running | after merging the new commit |
| Waits for | all active, reserved, and scheduled tasks (workers and scheduler paused), up to 3 hours by default (`CVENGINE_UPDATE_DRAIN_SECONDS`, 1 to 10800) | work that runs on this server (an on-demand validation, a deferred re-test, a triage call, a scan whose stage is not waiting on a Sentinel), 30 seconds to settle and 60 at most; **not** scans that run on Sentinels (see "Updates never wait for Sentinel scans" below). With the opt-in *Wait for scans to finish before updating* it waits for every running scan, up to 5 minutes by default (`CVENGINE_UPDATE_DRAIN_SECONDS` in the environment or `.env`, whole seconds), after which it goes ahead and interrupts them; the watcher asks again about every 15 seconds while it waits, 30 seconds after a refusal |
| Checks for an old PostgreSQL 12 volume | yes | no (read [UPGRADE.md](UPGRADE.md) first) |
| Checks free disk first | no | yes, twice: the Update screen says it before you approve, and the updater before it stops anything. About 14 GB for the first update to 1.4 (see "Small hosts" below; `CVENGINE_UPDATE_MIN_FREE_MB` replaces the figure) |
| Dumps the database before the migrations | yes (`CVENGINE_UPDATE_BACKUPS`, default the last 3; automatic deployment makes its own dump instead) | yes, the same |
| Verifies afterward | the site, every worker queue, and the scheduler answer | web, the workers, the scheduler, and the proxy are running (10 checks, 2 seconds apart), then the web service answers with a status under 500 (up to 90 checks) and no migration is waiting |
| Maintenance page for visitors | no | yes, from the instant the updater starts changing files (before the fast-forward) until the new site answers and is verified |
| Removes the replaced image afterward | no | yes, once the update is verified |
| Stops scans | only with `--stop-scans` or `--force`; automatic deployment always does | only work on this server that is still running after the 60 second cap, or (with the opt-in) scans still running after the drain limit: the update then goes ahead and interrupts them. A scan on a Sentinel is never stopped by an update |

## Automatic deployment

Needs a Linux host with systemd. Install the timer once, as root, in the checkout:

```bash
scripts/install-auto-deploy.sh            # checks master every 3 minutes
scripts/install-auto-deploy.sh --remove   # turn it off
```

The timer first fires 5 minutes after boot, then 3 minutes after each run ends. It does nothing while Settings, Updates is set to Manual (the default; the journal says so once). When it is Automatic and `origin/master` moves ahead of the checkout, `scripts/auto-deploy.sh`:

1. backs up the database and the Django secret (the last 7 dumps are kept in `.git/cvengine-auto-deploy/backups`, mode 0700; the secret is one file, `secret`, replaced when it changes). The folder is for rolling back on this machine. `.env` holds `CVENGINE_FIELD_KEY` and is not part of it, so back `.env` up separately and keep it apart from the dumps;
2. runs `scripts/update.sh --stop-scans`, which stops running scans cleanly, applies and verifies the update, and queues the stopped scans again.

With backups turned on (the default) it never deploys without one. A failed backup is retried on the next timer run. It only deploys `master`: a checkout that was moved to another branch (Settings, Updates, Update source) makes the timer do nothing, and the journal says so once. The timer is not the watcher: on a host that has only the timer, an Approve click in Manual mode has nothing listening to it. Choose Automatic, or use the watcher (`scripts/install-updater.sh`) instead of the timer. A commit whose update failed is retried after an hour. It waits while another update holds the lock (`.git/cvengine-update/update.lock`, shared by all updaters), and its drain limit is 30 minutes. The installer runs `scripts/update.sh --check` first and refuses an install that is not ready. Logs: `journalctl -u cvengine-auto-deploy`. Tuning variables are in [CONFIGURATION.md](CONFIGURATION.md#updates). Use this or the approval updater, not both.

## Approval in the app

cvENGINE checks its GitHub repository twice a day (05:23 and 17:23 UTC) and tells superusers when something newer exists. In Manual mode (the default) it installs nothing by itself; in Automatic mode it approves what the check finds, as an administrator would, and the host script below installs it.

1. **Check.** The check reads the head of the configured branch (default `hevnsnt/CVEngine@master`) and compares it with the installed commit (the first line of `web/.commit`; for a server with commits of its own see "A server with commits of its own" below). `make up`, `make build`, `update.sh`, and `apply-update.sh` write it. A plain `docker compose up` does not, and the installed commit then shows as unknown. A private repository needs a fine-grained read-only token under **Settings, Updates, Update source**, stored write-only.
2. **Ask.** A bar at the top of every page shows the newest commit message and how many commits are new. **Settings, Updates** lists up to 20 of them and is the only place to **Check now**. Superusers can approve, dismiss (offered while an update is available, until a newer commit appears), or check again.
3. **Apply.** Approving writes the commit id to `web/.update-approved`. The web container has no Git or Docker access, so the host script `scripts/apply-update.sh` does the work. It turns on the global scanning pause, waits for running scans (5 minutes by default, then goes ahead and interrupts what is left), fast-forwards to that commit, checks that there is room for the new image, builds, takes a database dump (`scripts/db-backup.sh`), migrates, and recreates the application containers, then checks that the web service answers. Migrations are not rolled back: the dump is the way back. It recreates only `web`, the workers, the scheduler, and the proxy: it never touches `db`, `redis`, the `tailscale` service, or the OpenVAS add-on.

**The pause.** It is the same global pause as **Activity, Resume scanning**. Work that touches targets or spends AI budget (scans, validation, triage, reviews, the certificate watch, scheduled work) waits and retries every 60 seconds. Anything already running continues, and feeds and bookkeeping carry on. A pause you set yourself is neither claimed nor released by the update.

**Progress.** While an approved update runs, an orange bar on every page (superusers) starts with "Update approved, pausing new scans", then shows four steps (Pause, Settle, Rebuild, Resume; the second is Drain scans with *Wait for scans to finish before updating* on) with the time since approval, and ends with "Updated. Scanning has resumed" and a reload. A failure turns it into "The update did not finish". It greys out the page while the services restart. **Settings, Updates** lists each step with what it waits on and how long it usually takes (about 3 to 6 minutes), and when no host updater is reporting it shows the command to run. The same data is in `GET /cve/api/settings/updates`: `phase` (`idle`, `draining`, `applying`, `done`, `failed`), `phase_detail`, `phase_scans_running` (work on this server the update is settling, not Sentinel scans), `phase_changed_at`, `scans_paused_by_update`, `wait_for_scans`, `sentinel_tasks_open`, `sentinel_scans_running`, `sentinel_results_held`, and `host_updater` (`seen`, `alive`, `age_seconds`). Only `apply-update.sh` reports phases, and only `update-watch.sh` the heartbeat.

**Work in flight.** Workers are stopped by the restart, and the messages they had taken but not started would stay hidden in Redis until its visibility timeout (12 hours). The worker container returns them to their queues when it starts (`python3 manage.py requeue_unacked`, run by `celery-entrypoint.sh` before the workers; the same entrypoint turns a stop into a warm shutdown of the four workers, within the 60 second stop timeout, and exits when any one of them dies, so `restart: always` brings back all four lanes instead of leaving a queue unconsumed), and the reaper queues a host assessment again once it has waited 30 minutes (`cveFeed.reaper`), so nothing stays "queued" because of a restart. A worker that acknowledges a message on receipt takes its reserved tasks with it when it is killed and leaves nothing in Redis to return, so the reaper asks the broker and the workers which task ids still exist (`cveFeed.broker_recovery.live_task_ids`: the queues, the unacknowledged hash, and each worker's reserved, active and scheduled tasks) and queues again only the rows whose task is gone. The same answer keeps such a row from counting toward the host-assessment capacity limit (10 minutes after it was queued); when no worker answers, every active row counts as before.

**What visitors see.** `./web` is a bind mount into the web, celery and celery-beat containers, so the moment the updater changes any file (the branch switch, the fast-forward, or a rebuild of files that were already pulled) the running containers read the new code on the old image. The updater therefore shows the maintenance page **first**: once the scans have drained (the drain wait is not part of it; the site is unchanged then), it writes `config/nginx/state/maintenance`, stops the Celery workers, beat and the scanner (scans are already paused and drained, and a worker that restarted would load new code on an old image), and only then touches a file. The proxy answers every request with status 503 and the page (`web/static/cve/maintenance.html`: two engineers over a blueprint, "We are rebuilding cvENGINE") from its own container and its own mounted copy of the page, so nothing depends on the web container, which may be old, stopped or restarting. The page holds for a build of any length (nothing times it out; a cold build on a small host is 7 to 25 minutes) and polls the site every few seconds, reloading itself when the site answers. API clients such as external Sentinels get the same clean 503 with `Retry-After: 120` and ask again later, not a 500 or a hang; the Update screen's own status poll fails the same way, which it treats as the site being down and keeps polling. The flag is removed only after the new web service answers and no migration is waiting (`verify_serving`); this is the honest trade, the old site cannot safely keep running on new files, so visitors wait behind the page for the build rather than get a mismatched site. If the update fails before the services were replaced (the build failed, the disk check failed) the updater puts the files back at the previous commit (and the previous branch), starts the workers it stopped, checks that the previous version answers and removes the page: the old version serves again with no second build (if a build moved the image tag, or the old services do not answer, it redeploys the previous commit instead). If the update fails after the database was migrated, or the previous version cannot be restarted, or the updater is stopped part way, the page stays up and says **"The update did not finish. The administrator is fixing it."** (the proxy shows it while `config/nginx/state/maintenance-failed` exists next to the flag); it never shows a normal page on a mismatched build. Recovery on the host: read `.git/cvengine-update/update.log`, fix the cause, then approve again or run `make up`, which clears a leftover flag (`rm -f config/nginx/state/maintenance config/nginx/state/maintenance-failed` does the same). The host that is updating FROM a version before this one still runs its old `scripts/apply-update.sh` up to the merge; the new `scripts/update-deploy.sh` it reads then puts the page up as the first step after the merge (before the build, which used to come first), and the whole sequence applies from the update after. A stack without the proxy service (the dev compose file) has no page. `scripts/update.sh` and automatic deployment do not use the approval updater and do not set the flag.

**What the page shows while it waits.** The updater writes a small status file, `config/nginx/state/status.json`, next to the flag, and the proxy serves it as `/maintenance-status.json` (no-store) from its own files, so it works with the web container old, stopped or restarting. The page polls it every 2 seconds. It shows the steps the scripts really go through (checking, pausing work, building, backup, database, starting, verifying, scanner) with the current one marked and a plain sentence for it, how long the update has run, when it started in the visitor's local time, and the short commit being installed. A build that has run longer than 12 minutes says so calmly and that it is still working; a build that has produced no output for 5 minutes (another step: 3 minutes) shows a "No output for N minutes" warning, and a status that has not been refreshed for 90 seconds says the updater itself has not reported. When an update fails the page flips to one plain sentence for what failed, whether the previous version is running again, the one-line recovery, and a **Details** disclosure with the last 20 lines of the update log. **The file is public** while the page is up, so nothing free-form goes in it: step names and every sentence come from fixed tables in `scripts/update-status.py`, the commit is a 7 to 12 character hex string, and the only text taken from the host is the log tail, shown only after a failure, which is cut down line by line: a line that mentions a password, token, key, secret, cookie or the like is replaced by a marker, and URLs, addresses, paths, host names, e-mail addresses, long identifiers and `NAME=value` settings are redacted in the rest (stack traces are dropped). An older proxy (before this version) has no status file and shows the plain page. With JavaScript off the page shows the plain message and reloads itself every 30 seconds. The full, unredacted log stays on the host in `.git/cvengine-update/update.log` (published in part to **Settings > Updates** for administrators).

Before the page, and in an update that predates it, a request that needs a column or table the migration has not created yet is answered 503 with `Retry-After: 30` by `reNgine/schema_guard.py` (only while migrations are really waiting, so a genuine bug stays a 500). An administrator watching the update (the orange bar) gets the same scene over their page from the moment the host picks the update up, with the current step as its status line, and is sent back to `/cve/` when the update is done.

**Failure.** Before the migration (the build, including the free-disk check), a failure puts the previous commit back and restarts it, deletes the approval, and scanning resumes (the log says "update failed before the database was migrated"; the phase reads `failed` with the reason when there is one an administrator can act on, such as too little disk space or a build that failed, and `done` otherwise). The way back does not repeat the free-disk check, so a build that stopped for lack of space is put back with what is already on the host. A database dump that cannot be made counts as such a failure, so nothing is migrated without a restore point (`CVENGINE_UPDATE_BACKUPS=0` in `.env` turns the dump off). If the restart also fails, the phase becomes `failed` and scanning stays paused. A migration that fails is a failure before the migration only when it changed nothing: every migration commits on its own, so when a later one fails after earlier ones were applied (or the count of applied migrations cannot be read), the previous code is never put back on that schema. The update keeps the new commit, scanning stays paused, the log says so, and the dump taken just before is renamed `premigration-failed-...` in `.git/cvengine-update/backups`, which is never pruned. After the migration it keeps the new commit and retries the whole deploy once (build, migrate, restart). If that also fails, the approval stays for the next run, the phase becomes `failed`, and scanning stays paused. The watcher does not retry for ever: after 3 runs for the same commit that failed this way (`CVENGINE_UPDATE_MAX_ATTEMPTS`) the approval is removed and the phase says why; fix the cause, then approve again. If a pause is left behind, an App Admin releases it under **All projects, Activity, Global scanning control, Resume scanning**. These rules live in `apply-update.sh` and `update-watch.sh`, which only take effect for the update after the one that delivers them (see "Who applies an update" below); `update-deploy.sh` (the dump, the migration rule, the proxy pull) takes effect at once.

The host side is a watcher that cron starts every minute (`scripts/update-watch.sh`). It sees an approval within about two seconds, and tells the app it is alive every 15 seconds, also while an update runs (which takes minutes), so **Settings, Updates** says when nothing on the server is listening and shows the command to run. The same watcher carries out a switch of the OpenVAS add-on made in the app (`scripts/openvas-sync.sh`, in the background, so a first start that pulls several gigabytes never delays an update or the heartbeat). `./install.sh` installs it, into root's crontab. The checkout is normally owned by the user who ran `git clone`, and git refuses to work as root in another user's repository ("dubious ownership"); the scripts name their own checkout as safe for the commands they run, and `install-updater.sh` checks that the watcher can start the way cron starts it (no `SUDO_UID`) and refuses to install when it cannot. An install made before v1.2.0 has none, and the first update it needs by hand installs it: `scripts/update.sh` leaves the watcher behind when it succeeds, so that one manual update is the last one. To install it without updating:

```bash
scripts/install-updater.sh            # a watcher the cron entry starts every minute
sudo scripts/uninstall-updater.sh     # remove it again (the cron line install.sh added to root's crontab); also: sudo make uninstall-updater
```

It logs to `.git/cvengine-update/update.log` (a copy is published as `web/.update-log`). It keeps the approval and retries when the checkout has uncommitted changes to tracked files other than `.env`, when scans are running, or when it cannot verify them. For an id that is not a full commit id, a commit not on `origin/<update branch>` (the branch set in Settings, Updates; a different branch than the checkout triggers a branch switch, see below), or one that is not a fast-forward, it refuses and deletes the approval file. A failed fetch keeps the approval and retries. A checkout with local changes keeps it too and shows "The update did not finish" with the files named. The app can keep showing "approved" after a refused or rolled-back update: cancel the approval and approve again once the cause is fixed. Approvals and cancellations are in the audit log. Without the host script an approval simply waits. It uses the Compose layout described below, or the three `CVENGINE_COMPOSE_*` settings (the older single `CVENGINE_COMPOSE_FILE` still works).

## Small hosts: disk, memory and stuck scans

On a server with a few gigabytes of disk and memory the update looks after three things for you. Nothing here needs a terminal; the Update screen is the place to look.

**Disk.** The update builds a new image of a few gigabytes next to the one it replaces, and a build that runs out of space fails half way. So the host measures the free space where Docker keeps its data (`docker info`, Docker Root Dir, then `df`) once a minute and the Update screen shows the result before you approve. When there is not enough, the screen says so in plain words and **Approve update** stays off with that reason on it:

> This update needs about 14 GB of free disk; this server has 9 GB free. Free some space or add disk, then try again.

The server also refuses an approval into a full disk (and automatic updates do not approve one), and the updater checks again before it pauses scanning or stops anything, with the same sentence. Below the figure the updater first removes what is safe to remove, **untagged ("dangling") images and the build cache** (`docker image prune -f`, `docker builder prune -f`), measures again, and goes on if that was enough. It never removes a tagged image, a volume or a container.

*How much is needed* is an estimate, not a prediction: 8,900 MB (the new server image 1.6 GB, the AI reviewer 0.25 GB, a cold build cache about 4.7 GB, and 2 GB to work in) plus 5,100 MB for the built-in scanner's image when the scanner is on and that image is not on this host yet. That is **14 GB for the first update from 1.3 to 1.4**, and 8.9 GB for one that already has the scanner image, has the scanner off, or answers "Sentinels of your own only". The sizes of an image that is going to be pulled are not known before it is pulled, so they are the sizes measured on the first 1.4 update. `CVENGINE_UPDATE_MIN_FREE_MB` in `.env` replaces the figure (the way back from a failed update uses 0: it needs no new space).

**Memory.** On a host under 7 GB (the same rule as the scanner's 1 GB ceiling, [DEPLOYMENT.md](DEPLOYMENT.md#memory)) the build of the server image needs about 2 GB, and the workers keep their memory after the scans drain, so the build could be starved or push the host into swap and get the workers or the build killed. After the drain and before the build the updater therefore stops the **celery workers and the built-in scanner**, builds with the memory that frees, and starts them again right after the build, whether it worked or not. The database, Redis, the web service and the proxy are never stopped: the site keeps answering (scheduled tasks wait in the queue, and scanning is paused anyway). If the build fails, celery and the scanner are started again at once, nothing else has changed, the previous version keeps running, and the Update screen says "The new version could not be built (see the update log). Nothing was changed: the version that was running is still running." `CVENGINE_UPDATE_STOP_CELERY=0` in `.env` turns the step off.

**Updates never wait for Sentinel scans.** Scanning runs on Sentinels, so an update does not wait for it. On approval the host pauses the queues (the existing *update pause* of `cveFeed/scan_control.py`): no new scan or stage starts and no Sentinel is handed new work. It then lets work that runs on this server settle, 30 seconds normally and 60 at most (`CVENGINE_UPDATE_DRAIN_SECONDS` can only shorten that; a scan that waits on a Sentinel, because it has an open Sentinel task or an open stage run, is not counted), and goes to the maintenance page and the rebuild. Meanwhile:

- A Sentinel that is mid-task keeps running its tool. When it finishes and the server is down it keeps the result in its spool on disk (6 hours by default, `CVENGINE_SENTINEL_SPOOL_HOURS`; see the Sentinel README) and delivers it, oldest first, before anything else when the server answers again. Its heartbeat, poll and delivery retry quietly with a backoff that tops out at 60 seconds.
- The server keeps the Sentinels' leases through the update: starting the update opens an *update window* on the scan control row (`update_started_at`; the update's end closes it and starts a grace of `CVENGINE_UPDATE_GRACE_SECONDS`, default 600), and while the window is open or in its grace nothing is expired for a missing heartbeat or an unlisted task, a lapsed lease is taken up again by the first heartbeat, and a result is accepted. The budgets of a stage that waits on Sentinels count wall-clock time minus the outage.
- A result that arrives for a task nothing waits for any more (its stage ended with the restart, or its scan was closed as *interrupted by an update*, and no stage run holds it) is **adopted**: it is filed through the persistence the stage itself uses (nmap hosts and ports, naabu ports, nuclei findings, bbot batches, each with the ledger marked done where the stage would have), the task becomes `done`, and one activity line per project says *Adopted N results a Sentinel held during the update*. A second delivery is answered `duplicate` and files nothing. A kind with no adopter keeps its result on the task row and its host is due again by the ledger as usual. A task held by a stage run is left to the stage run, which continues after the restart as before.
- During the pause an operator's own *Pause all scanning* still stops stages as before; only the update's pause leaves Sentinel work alone.

The banner says *Pausing new work. Your Sentinels keep what they finish and hand it over when cvENGINE is back*, names how many tasks keep running on Sentinels, and its steps are Pause, Settle, Rebuild, Resume. The maintenance page says the same to visitors. The Sentinels page shows *Holding N results until cvENGINE is back* for a Sentinel whose heartbeat reports a spool (`info.spool`, optional; a Sentinel without it simply shows nothing).

**Wait for scans to finish before updating** (Settings, Updates; off by default, stored in `web/.update-wait-scans`) restores the old drain for people who want it: the update waits for every running scan, up to `CVENGINE_UPDATE_DRAIN_SECONDS` (300 by default), then interrupts what is left. The first update that delivers this change is still applied by the `apply-update.sh` already on the host, which waits as before; every update after it uses the new rules.

**Stuck scans.** A scan marked "running" whose worker is gone never finishes, so the update used to wait out its whole drain limit (5 minutes) for it. Before it counts what is still running, the updater now closes a running scan as failed, with the reason *interrupted by an update*, only when all of these hold: no Celery task for it exists anywhere (not queued, not held, not on any worker), it is not waiting on a Sentinel, and it has shown no activity for `CVENGINE_UPDATE_GHOST_MINUTES` (default 5). Each one is written to the update log. A scan that shows progress, or whose task a worker holds, is never touched, and the update waits for it as before. When the workers cannot be asked, nothing is closed.

**What applies to the first update from 1.3.** The Update screen, the host's own disk check before pausing, and the stuck-scan closing live in files the host already has (the 1.3 copy of `apply-update.sh`, the 1.3 screen), so they take effect from the update after the one that delivers them (see "Who applies an update" below). The disk check inside the deploy and the stop-and-start around the build live in `scripts/update-deploy.sh`, which is read after the new files are merged, so **they apply to the first update from 1.3 itself**. On that first update a disk that is too small is therefore found after the files were merged, still before anything is built or stopped; the 1.3 script then puts the previous version back (it restarts the containers once, from images that are already built).

**From the command line.** `scripts/update.sh` is unchanged: it has no disk gate and does not stop the workers; free the space and, on a small host, stop them yourself (`docker compose stop celery scanner`, then `docker compose build web celery celery-beat`, then `docker compose start celery scanner`) if you update by hand. `docker system df` shows where the space is.

## By hand

From a clean `master` checkout:

```bash
scripts/update.sh --check        # preflight: layout, ports, database, scans; changes nothing
scripts/update.sh                # update, waiting for running scans to finish
scripts/update.sh --stop-scans   # update now: stop scans cleanly and queue them again afterward
scripts/update.sh --force        # do not wait: stop scans and the workers, then update
```

It:

1. fetches the code and builds the images while everything keeps running;
2. checks that no host service holds a port the stack publishes, and that no old PostgreSQL 12 volume needs [UPGRADE.md](UPGRADE.md) first;
3. pauses the scheduler and the workers' queue consumers and waits for active, reserved, and scheduled tasks, reporting every 30 seconds (up to three hours). With `--stop-scans`, every running and queued scan is stopped through the app first, so the wait takes seconds. It stops, and resumes the old workers, when the time limit passes, a worker misses 12 status polls in a row, a worker keeps consuming after three pauses, or a worker cannot be inspected or paused. The error names the worker or queue;
4. applies migrations, publishes static files, and recreates web, the workers, the scheduler, and the proxy;
5. waits up to ten minutes until the site, every worker queue, and the scheduler answer, then queues any stopped discovery scans again, as new scans in their original mode. Other kinds of scan stay stopped.

`--force` skips the wait. It stops scans (discovery scans are queued again afterwards), pauses what it can, and stops the workers with a 10-second grace. Any other task running at that moment is lost and runs again when its schedule next fires. A failed migration still stops the update.

New work stays queued in Redis throughout. If the wait times out or the update stops before the migration, the checkout is put back with `git reset --keep`, the previous workers resume untouched, and stopped scans wait in a private file under `.git/cvengine-update` for the next successful update. A failure after the migration leaves the new code in place and says what to check.

### A server with commits of its own

An installation that carries commits on top of a release (a fork, a local patch) never has the commit GitHub's branch has, and GitHub has never seen its own commits: asked how far behind such a build is, it answers "not found". Only the host has git, so the host compares instead: every 30 minutes while the watcher runs, after each deploy and as soon as Settings names another source, `scripts/update-state.py upstream` fetches the tracked branch (from `origin` when that is the tracked repository, otherwise from `https://github.com/<repo>.git`, public repositories only, objects checked, into a private ref `refs/cvengine/upstream/<branch>`) and compares the running build (`web/.commit`) with it. It publishes `web/.upstream-state.json`: the commit the build shares with the branch (`base`), the commits of its own (`ahead`) and the branch's commits it lacks (`behind`). The check then asks GitHub about `base`, which it knows, and Settings, Updates reports one of:

| Status | Meaning | Banner | Approve |
| --- | --- | --- | --- |
| up to date | the branch has nothing the build lacks, with or without commits of its own on top | none | no |
| available | the branch has commits the build lacks and the build has none of its own | yes | yes |
| diverged | the branch has new commits and the build has commits of its own | yes, dismissable, no Approve | refused, with the merge to run by hand |
| unknown | GitHub has never seen the build's commit and the host has not said which commit it shares with the branch (no host updater, or it could not fetch) | none | refused |

An update moves the checkout forward and never merges: a checkout with commits of its own that the approved commit lacks is refused before scanning is paused or anything is rebuilt, with the phase naming what to run (`git fetch origin`, `git merge origin/<branch>`, then `make up`). A checkout that has already merged the branch is level with it: nothing is offered and nothing is retried. `update.sh --check`, `update.sh` and automatic deployment use the same test (is the remote head contained in this checkout), so a checkout with commits of its own is no longer redeployed, and backed up, at every run; automatic deployment says once, per remote commit, that a merge by hand is needed.

The tracked repository and branch come from the app (`web/.update-source`, one line, written by every check) and are validated again on the host. The host fetches nothing else, and writes only into the checkout's object store and `web/.upstream-state.json`.

### What the host trusts

An update runs as root on the host: it merges a commit, builds from that tree and runs the deploy script in it. So whoever can get a commit onto an accepted branch, or can write the approval, can run code on the host. Three things limit that, none of which the web container can change (they are read from the environment or from `.env` on the host):

- **What can be merged.** Only a fast-forward to exactly the approved 40-character commit, which must be reachable from `origin/<update branch>`. `update.sh` and automatic deployment only ever take `origin/master`.
- **Which branches.** The branch name comes from Settings, Updates, Update source (it is written to `web/.update-branch` by the web container). With no setting any origin branch is accepted, as before. `CVENGINE_UPDATE_BRANCHES=master` (comma separated) in `.env` makes the in-app updater refuse every other branch. Without it, tracking a branch other than `master` or `main` is allowed but flagged: Settings, the Approve dialog and the update banner say that it is not a release branch, and the audit entry of the approval records the branch.
- **Signatures.** `CVENGINE_UPDATE_REQUIRE_SIGNED=1` in `.env` makes `apply-update.sh` and `update.sh` run `git verify-commit` on the commit and refuse it unless the signature is valid, with the signer's public key in the keyring of the user that runs the update (root, for the watcher and the timer). Off by default.

Automatic deployment applies every new `master` commit without anyone reading it: leave Settings on Manual, or turn on the signature check, if repository write access is not trusted that far.

### Custom Compose layouts

With none of these set, `update.sh`, the in-app updater, and automatic deployment use the files, env file, and project the running `web` container was started with, and `docker-compose.yml` only when that cannot be read. An install with its own Compose files, a separate env file, or a project name can set them once in `.env`:

```bash
CVENGINE_COMPOSE_FILES=docker-compose.yml,docker-compose.host.yml
CVENGINE_COMPOSE_ENV_FILE=.env.production
CVENGINE_COMPOSE_PROJECT=cvengine
```

For the development stack use `CVENGINE_COMPOSE_FILES=docker-compose.dev.yml`. `update.sh` and `apply-update.sh` both use the files, env file and project the running `web` container was started with when none of the three settings is given (an install that sets them uses what it set). `apply-update.sh` (the in-app updater) reads the same three settings, and without them it recreates the stack with the files, env file and project the running `web` container was started with, so a host with an overlay needs no setting. It refuses, keeps the approval and says what to set when the checkout holds an overlay (an untracked `docker-compose.*.yml`) that nothing says to use, or when the running stack came from files outside the checkout. A restart that leaves a service created but not running (a published port that is already taken) is a failed update, not a finished one.

## The built-in scanner

Every path that updates the server updates the built-in scanner too ([BUILTIN-SCANNER.md](BUILTIN-SCANNER.md)): `scripts/update.sh`, an update
approved in the app (`scripts/update-deploy.sh`, run by `scripts/apply-update.sh`), and `make up`. They all use `scripts/scanner.sh`:

1. **Before anything is stopped**, the newest published image is pulled: the moving tag `ghcr.io/hevnsnt/cvengine-sentinel:main`, which the Sentinel
   repository's publish workflow re-points at every build of its `main` branch (a branch that only receives code after its checks pass; the images
   carry an SBOM and build provenance). A pull that fails (an offline host, a registry that refuses) is logged and the scanner keeps the image it has.
2. **After the server is back** (celery recreated, the site answering), the scanner is recreated, after celery, because it shares celery's
   network namespace. Before that, the image that works is kept under a name of its own (`cvengine-sentinel-rollback:previous`), because the moving
   tag will name the new one. The update then waits up to five minutes (`CVENGINE_SCANNER_READY_SECONDS`) for the new scanner to be healthy **and** to
   check in with a contract version the server accepts (not below the floor in `scanner.lock.json`, not older than the server still speaks).
3. **If it does not, it rolls back** to the image the scanner ran before: it writes `CVENGINE_SCANNER_ROLLBACK_IMAGE=cvengine-sentinel-rollback:previous`
   to the env file Compose reads (and `.env`), recreates the scanner on it (from this host, never from the registry) and reports the reason to the server
   through the restored scanner, so the Sentinels page shows it. The next update removes the line and pulls the newest image again. A first start (an
   update from 1.3, a new install) has no previous image: the scanner keeps trying, and the work that needs it waits.

None of this ever fails an update: the scanner is retried at the next one, and until it runs the scans that need it wait (nothing is marked
failed). `CVENGINE_BUILTIN_SCANNER=0` makes every path remove the container instead. An image an administrator set with `CVENGINE_SCANNER_IMAGE`
is used as it is: never pulled over and never rolled back. `make up` starts the scanner; on a first start it does not wait, and when the image
changes it checks the new one like an update does.

**Between server updates** the scanner is brought to the newest image by the *Scanner update* (`scripts/scanner-update.sh`, `make scanner-update`):
the same pull, and only when the image is a new one, a wait for the scanner to finish its tasks, the same start, check-in wait and rollback. The updater timer
(`scripts/install-auto-deploy.sh`) runs it about daily whatever the update mode (`CVENGINE_SCANNER_UPDATE_HOURS`, `0` to turn it off); a host without the
updater runs the one cron line in [BUILTIN-SCANNER.md](BUILTIN-SCANNER.md#keeping-it-current-the-scanner-update).

The scanner's own self-update stays off, and its card on the Sentinels page has no **Update now** button: the host does the update, so there is one
updater. "Behind" for the built-in scanner means "the newest build of the Sentinel's main branch the server saw is a descendant of the one that runs" (a build equal to or ahead of that head is current; a failed compare or a commit GitHub never saw is unknown, not behind). The verdict is cached per installed commit and branch, dropped when the scanner reports another version, redone by the background refresh when the head was checked before that, and shown with when the head was last checked. Nobody re-pins a digest for a
Sentinel fix to reach an install. **To hold the scanner at one version,** set `CVENGINE_SCANNER_IMAGE` in `.env` to a digest or a tag; nothing here then
pulls over it. `scanner.lock.json` is the known-good floor the release was tested with (its commit, the contract version it speaks, and the digest it was
published as, for provenance); `python3 scripts/scanner_lock.py raise-floor --commit C --contract N` moves it up, which a release does when it needs a
newer Sentinel, and CI checks that the floor commit exists on the Sentinel's `main` and that the compose default is the moving tag.

### Which scanners run, asked by the Update button

The server works out three facts before the button starts anything: the host's memory, how many Sentinels of your own are live (the same set the last-resort rule uses: an active Sentinel heard from in the last three minutes, not the built-in scanner), and whether anybody already chose (`CVENGINE_BUILTIN_SCANNER` or `CVENGINE_SENTINEL_PLAN` in `.env`). When nobody chose and the host has under 7 GB or a Sentinel of yours is live, **Approve update** opens a dialog (*Which scanners should run?*) with the memory line, three radio choices and **Update now**. The answer travels with the approval in `web/.update-sentinels` (one word), is checked by the server (App Admin only, CSRF protected, audit logged as `update.approved` with the choice), and is read by `scripts/update-deploy.sh` before anything is stopped and applied with `scripts/host-fit.sh`, the same rules `install.sh` uses. The status line says what was decided (*scanners: Sentinels of your own only*, or *the built-in scanner is limited to 1g for this host's memory*).

When there is no question, or it cannot be asked (an older server, automatic updates, `scripts/update.sh`), the updater applies the safe default and removes nothing; see below. At the end of every update the memory limits of the running containers are added up against the host, and a warning names the largest one and the setting to change when they pass 90 percent.

**Settings > Sentinels** has the same three choices under **Which scanners run**. The page asks the host to apply it (`web/.scanner-plan-wanted`, picked up by the update watcher within seconds, `scripts/apply-scanner-plan.sh`): the choice is written, the server's processes are recreated once no scan is running, and the scanner container is removed or started. The page shows the result.

### From the command line

Almost everyone uses the buttons above. Everything they do can be done from a terminal, and an update run by hand, by cron or by systemd never asks a question and never waits for an answer.

The three choices are keys in `.env` (the same ones `install.sh` writes):

| Choice | `.env` |
| --- | --- |
| Use the built-in scanner only | nothing, or `CVENGINE_SENTINEL_PLAN=internal` (and `CVENGINE_BUILTIN_SCANNER=1` if it was off) |
| Use both | `CVENGINE_SENTINEL_PLAN=both` (and `CVENGINE_BUILTIN_SCANNER=1` if it was off) |
| Use my own Sentinels only | `CVENGINE_BUILTIN_SCANNER=0` and `CVENGINE_SENTINEL_PLAN=external`; the next update removes the `scanner` container |

`SCANNER_MEM_LIMIT` is the built-in scanner's memory ceiling (`1g`, `2g`, ...). To answer the question in a script, pass it to the updater: `scripts/update.sh --sentinels external` (or `internal`, `both`), or set `CVENGINE_INSTALL_SENTINELS=external` in the environment. Either writes the keys above exactly as the dialog would, before anything is stopped. Anything else is refused before the update starts.

**An update with no answer** (cron, `scripts/update.sh` with no flag, an automatic update, an update approved by a server too old to ask) applies the safe default: a host under 7 GB gets `SCANNER_MEM_LIMIT=1g` unless you set one, and a scanner is never removed. When it finds two or more Sentinels of your own live and nobody has chosen, it keeps the scanner, prints the finding and the exact flag (`scripts/update.sh --sentinels external`), and leaves a notice in `web/.update-notice.json` that Settings > Updates and Settings > Sentinels show until somebody chooses. The count of live Sentinels is read from the server's database by a one-off container of the new web image (the running container, still on the old image, cannot start the new code, and a 1.3 server has no such command). When it cannot be read (the database is not reachable), the updater prints that and changes nothing about which scanners run.

Read the state from a terminal: `scripts/update.sh --check` prints the memory the updater sees, whether it will write `SCANNER_MEM_LIMIT`, and how many Sentinels of your own are live when the running server can say (it changes nothing); `grep -E '^(CVENGINE_BUILTIN_SCANNER|CVENGINE_SENTINEL_PLAN|SCANNER_MEM_LIMIT)=' .env` shows the choice; `docker compose run --rm --no-deps -T --entrypoint python3 web manage.py external_sentinels` prints `EXTERNAL_SENTINELS_LIVE n` (read only). The memory budget line (see [DEPLOYMENT.md](DEPLOYMENT.md#memory)) is in the update's output (`scripts/update.sh`) or in the update log under Settings > Updates (`.git/cvengine-update/update.log` on the host).

## Keeping Sentinels on the newest version

On by default, and one switch: **Settings, Sentinels, Keep Sentinels on the newest version**. While it is on, a Sentinel that follows the instance default has self-update
**Automatic**, and cvENGINE asks any Sentinel that runs a build behind the newest published one to update. "Behind" is the verdict the Sentinels page already shows (the newest
build of the Sentinel repository's `main` is a descendant of the one the Sentinel reports); nothing is asked of a Sentinel that is current, ahead, unknown or on a commit GitHub
could not compare. The Sentinels page shows, per Sentinel, `running abc1234, newest def5678, update requested 10:42` (or `updating`, `current`, or the reason nothing is asked), and each
card keeps its **Update now** button.

**How a Sentinel is asked.** In its heartbeat answer: `update: {setting, mode, requested: true, target: <commit>, reason: "newest"}`. `target` and `reason` are optional keys of an object
every client already reads: a Sentinel that does not know them ignores them and still acts on `requested`, so the result contract version is not bumped. What the Sentinel does with
the request is its own machine's business:

| Sentinel | What acts | How |
| --- | --- | --- |
| External, host updater installed (the default of its `setup.sh`) | `scripts/update.sh` on the Sentinel's host | It sees `requested` at its next hourly run, builds, drains and swaps, as for **Update now** |
| External, `CVENGINE_SENTINEL_UPDATE_EXIT=1` and a supervisor that replaces the image | the Sentinel daemon | It takes no new work, waits for its running tasks, exits with code 76; `scripts/pull-on-exit.sh` (or any puller) brings the newest image and starts it |
| The built-in scanner | this server's host | The server writes `web/.scanner-update-requested`; `scripts/update-watch.sh` runs `scripts/scanner-update.sh` (drain, swap, rollback if the new image does not check in) |

**Safety rails** (`agentapi/sentinel_autoupdate.py`, each one a test):

- **Never during a heavy task.** A Sentinel running OpenVAS, a full port sweep, a UDP sweep, a thorough WPScan, bbot discovery, a deep nuclei pass or a secrets scan is not asked; it is asked at a later heartbeat. What is left is drained by the Sentinel's updater or daemon before anything stops (a task that outlasts the drain limit keeps running and the update waits for the next try).
- **At most one request per Sentinel every 6 hours.**
- **A Sentinel that does not come back is flagged and not asked again.** If it has not reported a new version 90 minutes after the request (`CVENGINE_SENTINEL_UPDATE_GRACE_MINUTES`, 5 to 1440), the Sentinels page says so in plain words (`Did not report a newer version within 90 minutes of the request (its updater or supervisor may not be running), so cvENGINE stopped asking. Press Update now to try again`) and the server stops asking until an administrator presses **Update now**, or the Sentinel updates on its own. A Sentinel that never comes back sends no heartbeat, so a sweep every few minutes (the `ensure_builtin_scanner` task) flags it too, and the page shows the flag from the moment the grace period ends.
- **Never a downgrade.** A request is made only when the newest build is a descendant of the one the Sentinel runs.
- **Never to a build this server cannot run.** The server reads the result contract of the newest build; when its version is above what this server speaks the page says `The newest Sentinel build is newer than this server, waiting for the server update`, and when the contract cannot be read nothing is asked.
- **Opt-out per Sentinel.** Set its self-update to Off on the Sentinels page (`PATCH agents/{id}` with `{"settings": {"self_update": "off"}}`); the server never asks it, and a machine's own `CVENGINE_SENTINEL_UPDATE=off` is a ceiling the server cannot raise.
- **Audited.** Each request is a `sentinel.update_requested` entry (the version it ran, the commit asked for, how), each flag a `sentinel.update_flagged` entry, the switch a `sentinel.defaults` entry, and an administrator's press an `agent.update_requested` entry.

**Command line equivalents** (the interface is the Sentinels page and Settings; these do the same): `PUT /api/v1/sentinels/defaults` with `{"keep_newest": false}` (App Admin) turns the switch off,
`PATCH /api/v1/agents/{id}` with `{"update": "now"}` presses Update now, `scripts/update.sh --now` on a Sentinel's host updates that Sentinel,
`scripts/scanner-update.sh` (`make scanner-update`) updates the built-in scanner, and `touch web/.scanner-update-requested` on the server's host is what the server does to ask the watcher.

## The Sentinel library in the server image

The server reads the Sentinel result contract from the installed `cvengine-scanner` library. `web/requirements.txt` pins it to a full commit sha: the known-good **floor**, which CI,
`pip install` and the tests use, so a check is the same on every run. The image build installs the **newest** Sentinel `main` over it: the `SENTINEL_REF` build argument
(default `main`; a branch, a tag or a full sha) is resolved to a commit when the image is built (`scripts/sentinel-ref.sh`, passed as `SENTINEL_SHA`, so Docker rebuilds that layer when `main` moved; empty,
the Dockerfile resolves it itself), and `make up`, `make build`, `scripts/update.sh` and the approved update all build that way. A server updated today therefore reads the contract of today's Sentinel.

The commit that was installed is read back from the install (pip's `direct_url.json`), so it cannot disagree with what runs: the About page and the Sentinels page say `Result contract version 3, read from Sentinel <sha>`. The image carries the labels `com.cvengine.sentinel.ref` and `com.cvengine.sentinel.sha` (what it was asked for). To hold a server at one Sentinel library, set `SENTINEL_REF` in `.env` to a commit, a tag or a branch.

Why not `@main` in `web/requirements.txt`: three CI places read a 40 character commit there (`build-pr.yml` fetches the Sentinel Dockerfile at it, `test_about_page.py` and `test_scanner_script.py` tie it to the floor in `scanner.lock.json`), the Sentinel repository checks that it is on `main`, and a moving requirement would let any Sentinel commit turn the server's CI red and make a build differ from the next one with no change here. Docker also caches an unchanged `@main` line, so the image would not move. The pinned floor keeps all of that, and the build argument is what makes the image follow.

## Branches and releases

- `master` holds released versions only. Each release is tagged (`v1.0`, `v1.1`, ...); pushing the tag, or running the Release workflow by hand, publishes the GitHub release with that version's section of the [changelog](../CHANGELOG.md) as its notes (`.github/workflows/release.yml`). A patch such as `v1.0.1` keeps the notes of `v1.0` and adds its own short section at the end. The tag must match `web/.version`. A release that has to be made again, because a fix had to be in it, is re-run with the workflow's `recut` option: it deletes the version's release and tag and publishes again from the tip of `master`, so the tag and the downloads change. Use it only before the release has been relied on.
- `develop` is the next version in progress (`web/.version` reads the next version with a `-dev` suffix, such as `v1.2-dev` once `v1.1` is released). Changes go to `develop` by pull request, and `develop` is merged into `master` for a release.
- **The How it works page.** `web/cveFeed/templates/cveFeed/how.html` (linked from the Live page) is the high-level, marketing-style description of the pipeline. Every release: reread it against what the release changed, correct anything that is no longer true, then set `HOW_REVIEWED_VERSION` in `web/cveFeed/views.py` to the release version. `tests/test_how_it_works.py` fails until it matches `web/.version`, so a release cannot ship a stale page.
- **Releases.** The release workflow attaches `cvengine-<tag>.zip`, `cvengine-<tag>.tar.gz`, `cvengine-<tag>.sbom.cdx.json`, and `SHA256SUMS` listing all three (the archives are made with `git archive` of the tag, so nothing from a working copy is in them). A manual run must be on `master`, a pushed tag must point at a commit on `master`, and a `web/.version` that does not match the tag fails it. When the tag already exists, the notes, archives and bill of materials are built from that tag, not from the tip of `master`. `build-pr.yml` runs the tests and builds the image for amd64 and arm64 without pushing it, on pull requests and on pushes to `master` and `develop`, and again every Monday without the layer cache so the pinned tools and runtime-fetched templates are fetched from scratch. `tool-releases.yml` runs every Monday at 05:23 UTC and keeps one open issue listing the pinned tools that are behind (the list below). `branch-cleanup.yml` is a manual tool that refuses `master`, `develop`, and unusual names.
- **Before a release is merged into `master`** the *Upgrade rehearsal* workflow (`.github/workflows/upgrade-rehearsal.yml`) runs on the pull request. It installs the released version (with `init-env.sh`, `make certs`, `make up`, and `create_admin`, not `install.sh`), puts data in it (including the duplicate IP addresses a newer migration has to merge), merges the release candidate the way the release will, updates with the real scripts (`scripts/update.sh`, and `scripts/apply-update.sh` for an install behind a host proxy with an overlay and its own env file on a taken port 443), then checks that every service runs, the site answers, no migration is pending, the workers answer, the data is still there and the overlay is still used, and, where the candidate has the built-in scanner, that it came up, enrolled itself and checks in within ten minutes with nobody running anything (for 1.4, run it by hand with the base `v1.3.5` and the candidate `1.4-develop`). It also runs a functional smoke test inside the updated install (`.github/rehearsal/smoke.py`: the MCP endpoint and its token lookup, tools that read the tables the update changed, the main pages: none may answer 500), checks the schema for columns the old code cannot live with, checks that rows stored under an older wording were rewritten, starts the update the way cron does (the watcher, with a bare environment), applies a second update with the scripts the first one installed, and approves that commit again to see that nothing is rebuilt. It also runs `make redis-auth` in the overlay job and checks that Redis refuses a client with no password. A merge conflict between `develop` and `master` shows up there too. A candidate already in the base is reported as nothing to release. Do not merge a release whose rehearsal is red. It can also be run by hand for any two refs (Actions, Upgrade rehearsal, Run workflow).
- **Who applies an update: the version already installed.** The update INTO a version is run by the update scripts of the version being replaced (`scripts/apply-update.sh` is read by the shell before it merges anything, and the deploy steps it runs are the ones it already has). `scripts/update-deploy.sh` is read after the merge, so a change there applies in the update that brings it, but a change to `apply-update.sh`, `update-watch.sh` or `update-state.py` only protects the update AFTER the one that delivers it. A fix to how updates are applied therefore ships as its own small release first, so that the large release is applied by the fixed scripts; and anything the large release needs from the old scripts (a new image, a new queue, a migration) has to work with what they do: build, migrate, collect static files, recreate. The rehearsal installs the released version for exactly this reason: it is the one that applies the update.
- **What a release may change in the database.** The old containers keep running on the new schema between the migration and the restart, and for as long as a failed restart is retried. So a migration only adds: new tables, new columns that are nullable or carry a database default (`db_default=` on the field, not only `default=`: Django drops its own default after the column is added, and the old code's inserts then fail), never a rename, a drop or a tighter constraint on a table the old code writes. The rehearsal compares the schema before and after the update and fails on a new `NOT NULL` column without a database default on an existing table.
- **Pinned tools, checked before every release.** The server image carries one tool, nuclei (it refreshes and reads the template set), built at a pinned version in a throwaway stage with a checksum-verified Go toolchain, so a rebuild does not change it. Every scan tool (nmap, WPScan, naabu, bbot, wafw00f, testssl.sh, Playwright's Chromium and the rest) runs on a Sentinel and is pinned in the Sentinel image, not here. This repository also pins, for the optional OpenVAS add-on, `python-gvm` and the digest-pinned Greenbone program images (which the weekly check cannot read, see [OpenVAS](OPENVAS.md)), and the Tailscale image. The About page lists every tool of both images with its version (`web/cveFeed/software.py`), and `tests/test_about_page.py` fails when a tool pinned in `web/Dockerfile` or in the Sentinel's Dockerfile (read at the commit `web/requirements.txt` pins) is missing from it or shown at another version, so re-pinning the Sentinel means updating that list in the same pull request. Only nuclei's templates, the CVE feeds and, on a Sentinel, WPScan's vulnerability database and the badkeys blocklist refresh at runtime, on purpose. A weekly check (`.github/workflows/tool-releases.yml`) opens one issue listing the pins that are behind. When a release is prepared, at any level, the *Tools up to date for release* check (`.github/workflows/tool-release-gate.yml`) fails the pull request into `master`, and the Release workflow refuses to publish, while any pin is behind, **a pin cannot be found in its file, or a newest version cannot be read** (the gate fails closed: a renamed pin or an unreachable site must not pass a release; the weekly report shows such a row as `?`). Bump the pin (`python3 scripts/check_tool_versions.py` prints the table), rebuild and run the tests; if a newer version was looked at and deliberately not taken, label the pull request `tools-reviewed` (or tick `tools_reviewed` when running Release by hand) and say why. Bumping the Go toolchain means replacing `GO_SHA256_AMD64` and `GO_SHA256_ARM64` in `web/Dockerfile`.
- **What is not pinned.** Be clear about the limits: the base image is a tag (`ubuntu:26.04`), not a digest, and its operating system packages (apt) are those of the day the image was built; the service images `postgres:18-alpine`, `redis:alpine` and `nginx:alpine` are moving tags (the proxy image is meant to move: every update pulls the current one before it builds, and keeps the image on the host when the registry cannot be reached); the optional OpenVAS add-on's feed images (`registry.community.greenbone.net`, `:community`) float on purpose so its vulnerability definitions keep updating, and an update never pulls or restarts them; Python packages are pinned in `web/requirements.txt` but their own dependencies are not locked or hashed (`Pillow` is a range); GitHub Actions are referenced by tag (`actions/checkout@v4`), not by commit; `pip`, `setuptools` and `wheel` are upgraded unpinned in the image build. They are listed as unpinned in the SBOM. Closing them (digests, hashed lockfiles, commit-pinned Actions) is a larger supply-chain hardening step than the tool pins and has not been done.
- **Bill of materials (SBOM).** Every release carries `cvengine-<tag>.sbom.cdx.json`, a CycloneDX 1.5 document of the pinned tools (with the checksums of what is downloaded), the Python packages and the service images, and it is listed in the release's `SHA256SUMS`. `python3 scripts/generate_sbom.py` writes the same file for any checkout, and the build job of every pull request keeps it as the `sbom` artifact. It is reproducible (the same commit gives the same document) and marks what it cannot vouch for with `cvengine:pinned` = `false`: nuclei's templates, the floating tags of the base and service images, and Python packages given as a range. It names the direct Python requirements (not their dependencies) and the operating system packages `web/Dockerfile` asks apt for by name, unpinned (apt installs the base release's current version; for the PDF reports that is `fonts-dejavu-core`), not what those packages pull in, not the base image's own packages and not what the nmap binary has linked in statically (`nmap --version` lists those: OpenSSL, libssh2, PCRE2, Lua, libpcap); for those scan the built image, for example `syft cvengine/web:latest -o cyclonedx-json`.
- Keep an installation on `master` (the default update source); `update.sh` and automatic deployment only work on `master`. Use `develop` only on a test server. Approving an update from another branch than the one checked out on the server (the branch set under Settings, Updates, Update source) makes the host script move its checkout to that branch first, as long as it is an upgrade: the branch must contain the installed commit (or, when the histories differ, still have every database migration the installed code has) and the local branch must not hold commits that are not on `origin`. A branch that does not exist, a detached checkout, a dirty checkout and a would-be downgrade are refused with the reason shown in Settings, Updates, and nothing moves. Migrations are never rolled back, which is why going back to an older branch is not done for you.

See also: [DEPLOYMENT.md](DEPLOYMENT.md), [CONFIGURATION.md](CONFIGURATION.md), [documentation index](README.md).

## Workers that are missing after an update

The celery container runs four workers (`discovery_worker`, `cve_feed_worker`, `validation_priority_worker`, `classic_worker`), one per group of queues, under `celery-entrypoint.sh`. All four must be there: a container that is up with a lane gone leaves its queues unconsumed and nothing scans.

- **The entrypoint checks each worker itself** every two seconds (`CELERY_SUPERVISE_INTERVAL`), not just "something exited". When any one is gone (crashed, killed for memory, failed to start) it stops the others with a warm stop that is **bounded** by `CELERY_STOP_GRACE` seconds (45, under the 60 s `stop_grace_period`), kills what is still there, and exits non-zero so `restart: always` brings all four back. The log names the lane. Before 1.4 the stop was an unbounded `wait`: the discovery worker holds assessments that wait on a Sentinel for hours, so after one lane died the container stayed up with only that worker and the restart policy was never reached.
- **The container has a health check** (`python3 celery_healthcheck.py`): all four lanes must answer a ping and consume their queue, or `docker ps` says `unhealthy` and the output names the lane.
- **The update does not finish without them.** After the web service answers, `verify_workers` runs the same check in the recreated container for up to ten minutes (`CVENGINE_VERIFY_WORKERS_SECONDS`). If a lane never answers, the update is not "done", the maintenance page stays up and the log says which worker and what to run: `docker compose restart celery`.
- **A notice appears** in the status strip for App Admins (check `workers_down`) when lanes stay down, and clears when they answer.

## A DISCOVERY_CONCURRENCY left over from 1.3

On 1.4 a host assessment holds a discovery slot while it waits for a Sentinel. A `DISCOVERY_CONCURRENCY` of 1 to 3 in `.env` (the 1.3 era, when that pool only ran discovery) lets one to three hosts be assessed at a time for the whole instance while the Sentinels idle, and it pins the value so the auto-tuner will not raise it. The update never edits `.env`; it says so in the update log (`warn_discovery_pin`), the Update panel in Settings, the Scanners page and the system status show the same line, and the "host assessment queue is at capacity" error names the pin. Remove the line or set it to 4 or more and restart.

## An approved update that never starts

The web app has no Docker or git access, on purpose. When you click **Approve update** it only records the approval; a small watcher on the server (`scripts/update-watch.sh`, started by cron every minute, installed by `./install.sh` and by `scripts/install-updater.sh`) sees it within about two seconds and runs the update: scans are paused, running ones finish, the files are updated, the containers are rebuilt and restarted, and scanning resumes. It also writes a heartbeat every 15 seconds, and Settings > Updates shows "Host updater: listening" or, when it does not report, says so and what to do. Approving also writes `web/.update-branch`. Changing the update repository or branch in Settings clears the stored check and cancels any approval. An older updater (a cron entry that runs `scripts/apply-update.sh` every 5 minutes) does not report but still works, with up to 5 minutes before an approval starts; run `scripts/install-updater.sh` again to switch it to the watcher.

### First time, or a server that has never had the updater

A server that was installed before the watcher existed has no `scripts/install-updater.sh` and nothing that reads the approval, so Approve does nothing there. Bring it up to date by hand once, from the CVEngine folder on the server:

```
cd /opt/cvengine && git pull --ff-only && sudo scripts/install-updater.sh
```

`scripts/install-updater.sh` edits root's crontab, so run it with `sudo`.

That pulls the current code, installs the watcher and starts it at once. A pending approval is then applied straight away: the script sees that the files are current but the running build is older (`web/.commit`) and rebuilds the services. Settings > Updates shows this command with a Copy button whenever no host updater is reporting, plus the steps an update goes through, what each one is waiting on and about how long it takes (about 3 to 6 minutes; a scan that runs on a Sentinel is not waited for).

If the bar says the host updater is not reporting, or an approval does not start:

1. `sudo crontab -l | grep cvengine` on the host (the installer runs as root, so the entry is root's): no line means the updater is not installed; run `sudo scripts/install-updater.sh`.
2. `tail -30 web/.update-log`: the script writes why it refused (local changes to tracked files, an unreachable origin, a commit that is not on the branch) or which command stopped it. Each reason is written once, not on every check.
3. `scripts/apply-update.sh` run by hand prints the same lines to the terminal, and applies a pending approval at once.
4. `git status --short` in the checkout: a modified tracked file (other than `.env`) blocks the update until it is committed or stashed.

## When the files are new but the database is not

Symptoms: Settings > Updates shows the new commit as installed, but pages or `/mcp/` return 500 and the database log says a column or relation "does not exist". An earlier update was interrupted after the files were merged and before `migrate` ran. Updates from the version that adds the deploy record on detect this and deploy again by themselves; a host already in this state is repaired once by hand, from the install directory (add the `-f` and `--env-file` options your install starts with):

```
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' | gzip > ~/cvengine-before-repair.sql.gz
docker compose build web celery celery-beat
docker compose run --rm --no-deps --entrypoint python3 web manage.py migrate --noinput
docker compose run --rm --no-deps --entrypoint python3 web manage.py collectstatic --noinput
docker compose up -d --no-deps --force-recreate web celery celery-beat proxy
```

Build first: the new code can need packages and tools the old image lacks, so migrating and restarting the old image is not enough. Migrations are never rolled back, which is why the dump comes first.
