# cvENGINE 1.4: notes for the operator

What you need to know before and after you upgrade to 1.4.0, in one place. The longer, per-change account is in [UPGRADE.md](UPGRADE.md#upgrading-to-14) and the [changelog](../CHANGELOG.md). 1.4 is still on the `1.4-develop` line; the version it reports (`v1.4.0`) is a string only, and nothing here says a release exists.

## What changed, in plain words

- **The server no longer runs scans.** Every scan runs on a Sentinel, the scanner program. The install includes one, the built-in scanner, so a single-machine install keeps working with nothing to set up. If no scanner can take the work, scans wait and a strip on every page says **Scanner offline**; nothing is marked failed and the targets stay due.
- **The server image is smaller.** nmap, naabu, bbot, WPScan and the other scan tools moved to the Sentinel image.
- **A setup wizard** opens at the first App Admin's first sign-in on a new install. A finished wizard is not shown again: `/cve/welcome/` goes to the dashboard (open `/cve/welcome/?again=1` to run it on purpose).
- **Addresses we must never scan.** Each organization has a list of addresses and networks the server never sends work to, whatever name leads there (see below).
- **Scale work for big installs.** Sentinel pages and polling are much cheaper, the report PDF no longer runs out of memory on thousands of hosts, and small hosts have tuned database settings.
- **A simpler interface:** six entries in the left rail, one Scanners page, and a Settings page whose AI model section says which model does which job.

## New and changed settings

All are set in `.env` and take effect on `make up` or the next update, except where a Settings page is named. Defaults are what you get when you set nothing.

| Variable | Default | What it does, and when to change it |
| --- | --- | --- |
| `CVENGINE_DB_CONN_MAX_AGE` | `60` for the web service, `0` for the workers | Seconds a web database connection is kept for the next request. It saves about 4 ms and a database process per request. Set `0` if you put a connection pooler in front of the database or see "too many connections". |
| `CVENGINE_AGENT_TASK_RETENTION_DAYS` | `30` | Days a finished, failed or expired Sentinel and agent task row is kept (1 to 365). A task row is about 1 KB; a week of scanning 3000 targets is about 300,000 rows. Lower it (7 to 14) on a small disk. Also on Settings, configMaxxing, **Data retention**. |
| `CVENGINE_NUCLEI_AI_MAX_PER_DAY` | `400` | The most calls per UTC day the AI may make to choose Nuclei tags. A failed call and the one retry after a cut-off answer count. Raise it only if the AI usage page shows the cap being hit and you accept the cost. Also on Settings, configMaxxing, **AI spend**. |
| `CVENGINE_REPORT_MAX_HOSTS`, `CVENGINE_REPORT_MAX_FINDINGS` | `500`, `1000` | The most hosts in the table and the most detailed findings in one PDF report. The renderer now works in chunks, so these no longer protect memory; they keep a report readable and its build time near 25 seconds. Raise them for a bigger report, and expect it to take longer. |
| `CVENGINE_BULK_DISCOVER_NOW` | `50` | How many targets from one bulk add start discovery at once; the work conductor takes the rest. It is not new in 1.4, and is listed because a large import is where it matters. Lower it on a small host, raise it (up to 500) when Sentinels have free slots. Also on Settings, configMaxxing, **Scan pacing**. |
| `POSTGRES_SHARED_BUFFERS`, `POSTGRES_EFFECTIVE_CACHE_SIZE`, `POSTGRES_MAINTENANCE_WORK_MEM`, `POSTGRES_RANDOM_PAGE_COST` | `256MB`, `768MB`, `64MB`, `1.1` | Database memory and planner settings, tuned for a 2 GB host and safe from 1 GB (use `128MB` shared buffers at 1 GB, and `POSTGRES_RANDOM_PAGE_COST=4` on a spinning disk). Changing one recreates the `db` container once, a few seconds of downtime and no data change. |
| `POSTGRES_MAX_CONNECTIONS` | `300` | Not new, but now matters: lower it to `100` on a 2 GB host if you also keep the worker pools small. |
| `SCANNER_MEM_LIMIT`, `REVIEWER_MEM_LIMIT` | `3g`, `256m` | Memory ceilings of the built-in scanner and the AI reviewer containers ([DEPLOYMENT.md](DEPLOYMENT.md#memory)). The scanner weighs each kind of work against its ceiling and starts only what fits, so a smaller ceiling means less runs at once, not a crash. |
| `CVENGINE_BUILTIN_SCANNER`, `CVENGINE_BUILTIN_FALLBACK_SECONDS`, `CVENGINE_REVIEWER`, `CVENGINE_SSH_PROBE` | `1`, `120`, `1`, `1` | Turn the built-in scanner, its last-resort delay, the AI reviewer container and SSH inspection on or off. With the built-in scanner off and no Sentinel enrolled, nothing scans. |

Every other 1.4 variable is in [CONFIGURATION.md](CONFIGURATION.md); [DEPLOYMENT.md](DEPLOYMENT.md#small-hosts-1-to-2-gb) has the measured numbers behind the small-host values.

## Addresses we must never scan

A list of names cannot protect an address: several names can lead to one machine. So each organization has a list of **addresses and networks** (IPv4 or IPv6, a single address or a CIDR range) that the server never sends work to, and never sends work to a host name that resolves to one.

- **Where to edit it:** Administration, Organizations, then the button **Addresses we must never scan** on the organization's row. An organization admin or an App Admin can edit it; every change is written to the audit log.
- **What it does:** no Sentinel task of any kind is created for a listed address, a queued task is not handed out once its address is listed, and a result that comes back for a listed address is dropped. Adding an entry cancels the tasks already waiting for it. The host page shows **Not scanned** with the reason.
- **Limits:** at most 500 entries; a note of at most 300 characters; `0.0.0.0/0` and `::/0` are refused; a network broader than /8 (IPv4) or /32 (IPv6) asks you to confirm. Private ranges are valid entries.
- **If the list cannot be read,** address work for that project is refused with the reason; it never lets work through.
- A read-only copy is available to scripts and agents (`GET projects/{slug}/excluded-addresses`, [AGENT-API.md](AGENT-API.md)).

### On the Sentinel itself

A Sentinel can also refuse addresses on its own, whatever the server sends, which protects an address even from an old server. On the machine that runs the Sentinel, set `CVENGINE_SENTINEL_DENY_RANGES` in its `.env` to comma separated CIDRs, for example `203.0.113.0/24,2001:db8::/32`. Every kind of task checks every address it is about to connect to (the target, each address a name resolves to, each redirect hop) and a task refused this way ends with an error that starts `refused:`. The list joins the ranges the task itself carries. A list with an entry that is not a network refuses every task until it is fixed. This variable belongs to the Sentinel, not to this server's `.env`; the full description is in the Sentinel repository's README, and it needs a Sentinel image that has it.

## Upgrade steps

1. **Back up first.** Copy `.env` and `web/secret` somewhere safe and apart from the dump, and take a database dump ([DEPLOYMENT.md](DEPLOYMENT.md#backups)). The update takes its own dump just before it migrates (the last 3 are kept in `.git/cvengine-update/backups`), but that stays on the same disk.
2. **Check free disk.** At least 6 GB where Docker keeps its images; the built-in scanner image is about 4.5 GB and is pulled before anything is stopped.
3. **Update** the way you always do: the in-app updater, `scripts/update.sh` or automatic deployment ([UPDATES.md](UPDATES.md)). In the rehearsal on a 1.3.5 install it took 50 seconds. `agentapi` 0020 builds its indexes concurrently, so a large Sentinel task table does not block Sentinels.
4. **Remove dead variables** from `.env` ([the list](CONFIGURATION.md#ignored-or-removed-in-14)); nothing warns about them.
5. **Check afterwards:** `docker compose ps` shows `scanner` and `reviewer` running; **Scanners** shows a Built-in scanner checking in; `docker compose exec -T web python3 manage.py migrate --check` is silent; no **Scanner offline** strip.

## Rolling back

A migration is never rolled back by going back to the old code: the old code against the new schema is not supported, so the way back is the dump taken before the update.

1. Stop the application containers (`web`, `celery`, `celery-beat`, `reviewer`, `scanner`) and leave `db` running.
2. Put the original `.env` (with `CVENGINE_FIELD_KEY`) and `web/secret` back.
3. In the `db` container, drop and recreate the database named in `.env`, then load the dump into it (the dump has no drop statements, so a populated database would collide):

```bash
docker compose exec -T db sh -c 'dropdb -U "$POSTGRES_USER" "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
gunzip -c path/to/the-dump.sql.gz | docker compose exec -T db sh -c 'psql -U "$POSTGRES_USER" "$POSTGRES_DB"'
```

4. Check out the previous version and start it with `make up`.

Scan result files (screenshots, raw output) are in the `scan_results` volume and are not in the dump. A restore returns the database to the moment of the dump: anything written since, including findings, is gone.

## What the status banner says about waiting

- **Scanner offline** (the strip on every page): no scanner is able to take the work. Scans wait, nothing fails, and the strip says which kinds are waiting.
- **Sentinel tasks are waiting for a free slot** (a note, not a problem): in the last six hours a task expired only because every Sentinel slot was busy, or none claimed it in time. The targets stay due and are asked again. Add a Sentinel or give the one you have more slots. The count is also in the system status as `finished_24h.waiting_for_slot`.
- **Sentinel tasks are failing** (a problem): tasks failed, or a Sentinel took a task and stopped reporting it ("the dispatch wait timed out", "the lease expired without a report"). That is the one to look into.
- **No work is queued** is a problem only when a target is really due and nothing runs; an idle conductor with nothing due is healthy and says nothing. A scanner for OpenVAS that never registered is not reported while OpenVAS is off.

## The AI settings page, and which model to choose

Settings, AI model now has one **Connection** block (provider, API key, server address, a status line such as "Connected: 13 models available", and one **Test connection**) and then a table, **Which model does which job**, with three rows, each a drop-down filled from the provider's own list:

| Row | Used for |
| --- | --- |
| **Everything else** (the default model) | Finding triage, CVE confirmation, validation and Nuclei planning, CVE guidance, template drafts. |
| **Finding review** | The AI reviewer's review of open findings. |
| **Operations check** | The AI reviewer's four-times-a-day check of the queue and Sentinels. |

The first entry of a drop-down is **Newest cheapest (recommended)**: the newest model of the cheapest tier the provider lists (for Anthropic, the Haiku tier). One **Save AI settings** saves the page. The list is fetched when you open the page and when the provider, key or address changes; **Refresh list** asks again. For your own servers, and for a gateway or a list that would not load, choose **Other (type a model name)**. A key you have saved is only sent to the address it was saved for.

**Model refusals.** The AI that chooses Nuclei tags for a scan can answer with no text. When the stop reason is `refusal`, the model declined the task. It is never retried; the request is not repeated for 5 minutes, then 10, up to an hour; and the scan uses the standard templates, with the reason in the activity feed and on the AI usage page (the plain reason and the stop reason). On the instance this was seen on, Anthropic's Sonnet and Opus models declined the Nuclei targeting task and Haiku answered it. So, to choose:

- Keep the default model (**Everything else**) on the recommended cheapest tier (Haiku for Anthropic) if the AI usage page shows `refused` for Nuclei targeting. It is also the cheapest for the high-volume jobs that use it.
- Use a larger model for **Finding review** and **Operations check** if you want deeper reasoning there; they are separate rows for that reason.
- A cut-off answer is a different failure (`output_truncated`): raise `CVENGINE_AI_MAX_TOKENS` or lower the model's reasoning ([CONFIGURATION.md](CONFIGURATION.md)).
