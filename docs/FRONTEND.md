# Front end

The interface is server-rendered page shells plus plain ES modules that fill them from the REST API (`/api/v1`) and a few UI-only JSON endpoints under `/cve/api/`. The UI and agents share the same project-scoped code. There is no build step, no framework, and no CDN.

## Design

`web/static/cve/cve.css` is a light, monochrome design system: ink on neutral grays, wide-tracked caps for labels, and fine corner marks on the main panels. Color is rare and means something: red and amber for severity and threat tier, slate for low, a green dot for healthy, and brand orange for running state and the active navigation marker. Type is [Geist](https://github.com/vercel/geist-font), vendored.

- **Shell** (`base.html`, `shell.js`): a sidebar from 1024px wide, a top bar, a bottom tab bar, and a "More" sheet below that. The top bar holds the palette (Ctrl/Cmd+K or "/") and Add targets. The palette jumps to pages, projects, organizations, and actions (Add targets, Keyboard shortcuts, Select several rows, and **Run saved search: <name>** for each saved search), and from two characters on it runs a [host search](SEARCH.md) with filter suggestions (Tab completes), a live preview of up to six hosts, and a syntax help sheet. Enter runs the highlighted row; pick the **Search hosts for "<query>"** row to open the Hosts page with the query. When your projects span two or more organizations, an **organization switcher** in the top bar narrows the project list to one organization (or **All organizations** in the All projects view).
- **Dashboard** (the **Live** page): opens on **All projects** when you can see two or more, and on one project with `?project=<slug>`. It has these parts, polled every few seconds:
  - **Counters.** An **Exposed hosts** tile with a meter (a host is exposed when a CVE matches it that the AI has not ruled out, or an open finding is medium or worse), then **CVE matches**, **Scanner findings**, **Hygiene issues** (with the three biggest), **Scan coverage** (the share of hosts a scan has looked at; hosts with no address a scanner can use are counted apart, not as neglected), **Certs expiring 30d**, **Oldest critical or high, days open**, and **Queued, none running**, which appears only when scans are waiting and nothing is running. Each opens the matching page. Once a project declares an internal network, an **Internal** group adds internal host, finding and CVE match counts and, per network, whether a Sentinel inside it is online (an unscanned network is never shown as clean).
  - **Attack surface map.** One square per live host that scores over 40, highest score first, colored by threat: up to 400 are built and as many as fit are shown, in richer tiles when there is room. Hover for the score, the worst CVE or finding, and the score reasons. The rest of the hosts are on the Hosts page.
  - **AI activity.** The engine's current work, newest first, with repeats folded into a "x N" count.
  - **Live discovery.** The live asset graph (with a **Group CVEs** toggle), a **Scanning now** row of chips (click one to find it on the graph), host, IP and open-port counts, and a ticker of what discovery just saw. A badge beside the title shows the followed scan while it is queued ("queued, N ahead"), running or failed, and links to it; a finished scan shows no badge. **Watch it live** after Add targets follows the new scan.
  - **CVE feed.** Fire, Smoke and Ice buttons filter the feed (catalog advisories, not findings on your assets), and a link opens [How cvENGINE works](#how-cvengine-works).
  - The AI activity and discovery ticker each keep their last 100 lines; older activity is on the Activity page. A strip says how many changes happened since you last looked. A 90-day activity strip shows new findings (by heat) and inventory changes per day, and the CVE matches and Scanner findings counters carry 14-day sparklines. With one project selected, **Download PDF report** sits in the page header ([PDF reports](#pdf-reports)).
  - The Changes page has a 7 and 30 day area chart, and the Scans page an 18-week scan heatmap.
- **Mobile**: 16px gutters, 44px touch targets, stacked-card tables, visible focus rings, and reduced-motion support.
- **Safe by construction**: DOM is built with `textContent` (the only `innerHTML` uses are the QR image on My account and fixed icons in the row menu and the Add targets dialog), and destructive actions use an in-page confirmation.

Static files are content-versioned and nginx sends `Cache-Control: no-cache` for `/staticfiles/`, so a CDN cannot serve one release's stylesheet with the next release's pages.

## Polling and counts

Every poller on the live pages (the dashboard, the graph page and its SOC highlight, the Sentinels page, the scan notifications on every page) uses `static/cve/poll.js` instead of a bare `setInterval`: one request in flight at a time, the next round armed when the last finishes, every wait jittered by x0.85 to x1.15 so a room of tabs does not fire in step, no polling in a hidden tab (it starts again, at once, on `visibilitychange`; the scan notifications are the exception: they slow to a quarter of their pace instead of stopping, so a finished scan is still announced), the wait doubled (up to 16 times) after each failed request, and a `Retry-After` on a 429 or 503 honoured (capped at two minutes). The shared `get` remembers each URL's `ETag` and sends `If-None-Match`; a `304` resolves to `null`, which a poller reads as "nothing changed" and returns before parsing or redrawing (the stats, graph-live, discovery and activity endpoints, the Sentinels live overview and the scans list send one). The Sentinels page asks for a Sentinel's detail card only when its live row's `revision` (or `version_state`) moved, with a two-minute safety net. The Live graph and the graph page send the graph `?v=<version>` so an unchanged graph answers 304. A Scans list that is waiting on a running scan and the live counters stop while `document.hidden` too. On a list page the headline numbers (`/cve/api/stats`) are read every 8 seconds; the filter chip counts and a list's own count, which each cost a list query, are read when a headline number moved and otherwise every fourth tick. Findings reads its four type chips with one request. The coverage figure on Live and the trend strip are computed from what the API returns: when the Findings list is cut off (it is ordered by heat, not date) or the host search stopped counting at its cap, the page says so instead of presenting the numbers as exact.

## Working in lists

- **URL carries the view.** Hosts reads `?q=`, `sort=name`, `heat=fire|smoke|ice|clean|unscanned`, `internal=0|1`, `view=gallery`, and `host=<name>`. Defaults stay out of the link, so a bookmark is short.
- **CSV export** on Hosts and Findings downloads the current filter (UTF-8 with a BOM, 20,000 rows at most, 2,000 for Findings). A leading `=`, `+`, `-`, or `@` is escaped so spreadsheets do not run it.
- **Row menu**: the `...` button on a row, or `.` on a focused row. Copy name or link, open in a new tab, pin, archive, or set a status.
- **Undo**: pin, archive, criticality, owner, and status changes offer Undo for 10 seconds when every row succeeded.
- **Keys**: `g` then `l` Live, `a` graph, `h` Hosts, `c` Changes, `v` Activity, `m` matches, `f` Findings, `y` Hygiene, `t` Targets, `s` Scans, `b` Bug bounty (a letter works only when its page has a link in the side rail). In lists `j` and `k` move, Enter opens, `x` selects, `f` focuses the filter. On a host `1` to `7` switch tabs. On a host or finding `y` copies the name (a finding's link is `Y`), and on a CVE match `e` focuses the remediation status. `Esc` leaves Select mode. `?` shows the sheet. Keys are off while you type.

## PDF reports

**Download PDF report** is on the Live page once a project is selected (not in All projects) and on a host's **Manage** tab. It asks the server for a report, shows Queued and Building while it polls, and downloads the file when it is ready. A switch, **Include fixed and accepted-risk findings**, is off by default: a report lists open findings only. The report is built in a background task (`generate_report`, queue `cve_feed_queue`), stored under `/usr/src/scan_results/.reports/` with a random name, and offered only to the person who asked for 24 hours; each new report, and the weekly maintenance, remove whatever has expired. Any role that can read the project can export it, audit included. The same report is available to agents ([AGENT-API.md](AGENT-API.md#pdf-reports)).

A project report has, in order:

1. **Cover**: project and organization, generation time, scope (targets, hosts, last completed scan) and whether closed findings are included. The company name, accent colour and footer come from Settings > Reports.
2. **Executive summary**: counts by fire, smoke and ice and by severity, the ten hottest findings, hosts on fire or smoke, and how many candidates triage ruled out as false positives.
3. **Hosts**: a table by score with heat, findings, open ports and owner, repeated header on every page, the host's alias under its address when it has one. A host report adds the alias and note, the host's services (with banners) and the lines of its score. Targets in the cover are listed as `name (alias)`, and a finding's host is followed by its alias.
4. **Findings**: one section per CVE match or scanner finding, hottest first: CVE ids and CVSS, exploitation signals, the basis ("confirmed: a check reproduced it" or "version-based"), evidence, the exact command or probe that showed it when one was recorded, remediation text and fixed versions, and the status, assignee and notes people recorded.
5. **Hygiene**: TLS and certificate findings and email (SPF, DKIM, DMARC) findings, with the same status columns.
6. **Method and validity**: completed scans, the last run of each scanner, and the caveats: version-based findings can be backported fixes, the scan is outside-in and unauthenticated, results are point-in-time, checks are read-only, and AI text is guidance.

Matches the AI ruled out, and findings triage classed as a likely false positive or not applicable, are never listed (the summary says how many). Limits per report: 500 hosts, 1,000 detailed findings, 500 hygiene findings ([CONFIGURATION.md](CONFIGURATION.md#pdf-reports)); the counts always cover everything, and the PDF says what the limits left out, so a very large project is best reported host by host. Banners, titles, response text and finding text come from the hosts that were scanned, so they are escaped and printed as text, and the renderer runs in its own process with no network access and no file access beyond the page it was given.

## Internal hosts

A host inside a network its project declared internal (`projects/{slug}/internal-ranges`; scanned only by a Sentinel deployed there) is marked everywhere the API describes a host: **`internal`** (boolean) and **`network`** (the declared range, such as `10.20.0.0/24`, or null) on host rows (`hosts`, `search`, and the graph's `subdomain` nodes) and **`internal`** on findings (`vulnerabilities`, `findings`). `?internal=1` keeps only internal hosts, `?internal=0` only the others, on `hosts`, `search`, `vulnerabilities` and `findings`. The Hosts page shows a scope filter (All, External, Internal) once a visible project declared a network (`has_internal` in the search response), and both Hosts and Findings show a dashed **Internal** badge on the row; the Findings page has a Scope select.

`/cve/api/stats` carries an **`internal`** object: `has` (false when no visible project declared a network: leave the group out), `hosts`, `hosts_live`, `findings` (actionable scanner findings), `matches` (exposed CVE matches), `last_scan_at`, `sentinels_online`, and `networks`: one entry per declared range with `org`, `project`, `cidr`, `description`, `hosts`, `last_scan_at` (the last finished internal scan, or null), `last_error` (the error of the latest internal scan when it failed, else empty), `last_discovery_at`, `last_discovery_hosts` and `last_discovery_error` (the last live-host sweep of the range) and `sentinel: {state, online, total, last_seen}`, where `state` is `online` (an internal Sentinel is live), `offline` (some are registered, none live: the network is not being scanned, so a quiet network is not a clean one) or `none`. The headline totals in the same payload still include internal hosts; `internal` is the subset.

## Sentinels

`/cve/sentinels/` shows what every Sentinel you manage is doing, from `GET /api/v1/sentinels/live` (refreshed every 5 seconds). A summary bar counts the Sentinels that are checking in, the ones working now, and the tasks waiting for a Sentinel. Each Sentinel is a card with an animated orb for its state (Working, Idle and waiting for work, Offline, Waiting for approval, Suspended), an **Internal network** badge when it is internal (the server decides that: see [AGENT-API.md](AGENT-API.md#sentinels-scan-stage-agents)), its last check-in and version, the tasks it is running now and for how long, any problem it reported, counts (done and failed in the last hour, done in 24 hours, average task time), its recent tasks, and its tools, operating system and concurrency. Cards are grouped by the organizations each one covers (an instance-wide Sentinel sits under **Every organization**); a group folds, and the page remembers which in this browser. Each group also lists the internal networks its projects declared, with the host count, the last live-host discovery of the range (and its error, if any), and whether a Sentinel inside is checking in. **Suspend**, **Revoke**, and **Approve** or **Reinstate** (for a pending or suspended one) call the same `PATCH /api/v1/agents/{id}` the Agents admin surface uses. When a Sentinel reports its version and settings, its card also has **Update now** (it finishes the tasks it is running, then updates; in Manual update mode this is the only way) and **Settings** (name, where it runs, size, the task kinds it never takes, and tasks at once from 1 to 10; the most recent change wins whether it was made here or in the Sentinel's own `.env`, and each setting can be handed back to the Sentinel).

The page also provisions Sentinels. A scope selector (**Project**, **Organization**, or **Instance (everything)**) with the matching field (a project picker, an organization slug, or nothing), **Where it runs** (external or internal) and **Size** (full, which also runs OpenVAS, or light) selectors, and **Provision** call `POST /api/v1/projects/{slug}/sentinels/enroll?format=blob` (needs the admin role in the project or its organization), `POST /api/v1/orgs/{slug}/sentinels/enroll?format=blob` (needs the admin role in that organization), or `POST /api/v1/sentinels/enroll?format=blob` (App Admin only), with `network` and `profile` parameters that choose the `.env` lines the setup uses. They show the one-time, 30-minute provisioning blob to copy, with the matching `./setup.sh` command and a short instruction to paste the blob into `CVENGINE_SENTINEL_BLOB` in the Sentinel client's `.env`. The blob is exactly the matching `sentinels/enroll` endpoint's own JSON payload, base64-encoded (`agentapi.sentinel_broker.encode_enrollment_blob`; no new crypto, no custom framing): the page does not build or serve a download itself, since the Sentinel client is a Docker Compose service that lives in its own repository, [hevnsnt/cvengine-sentinel](https://github.com/hevnsnt/cvengine-sentinel), not a per-OS package the web app ships. The `generate_sentinel_enrollment` MCP tool takes optional `project`/`org` arguments (at most one; neither means instance-wide) and returns the same blob plus the clone URL and the exact `docker compose` setup steps, so an agent with only Docker and shell access to a target machine (no prior context on Sentinels) can provision one unattended. See [AGENT-API.md](AGENT-API.md#sentinels-scan-stage-agents) and the [Sentinels guide](SENTINELS.md).

**Per project.** Once any Sentinel whose scope covers a project (named directly, via its organization, or instance-wide; pending, active or suspended, not revoked) has registered, that project gains a **Sentinels** link (More sheet, and the side rail under Work) to `/cve/{slug}/sentinels/`. The page lists the Sentinels covering the project from `GET /api/v1/projects/{slug}/sentinels` (status, live or offline, last heartbeat, the level it covers the project at, capabilities, and this project's task counts; another tenant's scope and the owner are not shown), with **Approve**/**Suspend**/**Revoke** only on the rows the caller may administer (`manageable`), plus this project's recent work from `GET /api/v1/projects/{slug}/sentinel-tasks`. Provisioning stays on the global page. A project administrator also sees an **Internal networks** card there: list, declare (CIDR plus description) and remove the private networks the project owns, via `projects/{slug}/internal-ranges`; the card stays hidden for anyone else (the API answers 403).

## Settings and extending

Under **Settings** (App Admins) there is one tab for each of these:

- **AI model**: the provider (Anthropic, OpenAI, OpenRouter, Ollama, vLLM, or LM Studio) with **Load models** and **Save and test**, the daily budgets for validation planning and for CVE guidance written by the model, the **CVE catalog seed** card, and the **Auto-fire** card. The provider list is grouped (**Hosted**: Anthropic, OpenAI, OpenRouter; **Your own server**: Ollama, LM Studio, and "vLLM, llama.cpp or another OpenAI-compatible server", which is also where LiteLLM and gateways go). The **Request settings** section (collapsed until something in it is set) holds the request timeout, connect timeout, reply limit, context window (Ollama only), JSON mode, reasoning and keep-alive (Ollama only). Each box says in the line under it what is in force and why: set here, from a `CVENGINE_AI_*` variable in the server's environment (a value here replaces it), or the provider's default (an empty box). A value out of range is flagged under its box and nothing is saved until it is fixed; a short reply limit, or reasoning on a limit under 4,096 tokens, shows a warning. **Save and test** keeps its result on the page: "Connection OK", or the failure with what to change, and the line above the buttons says when the connection was last verified. The settings are saved by `PUT /cve/api/settings/ai` and described in [Configuration](CONFIGURATION.md#ai-requests).
- **API keys**: the one place for OSINT and scanner keys. Choose **Organizations** (a key applies to all their projects, present and future) or **Projects** (a key overrides the organization's), then add, change or remove a key per service. Secrets are write-only. The Chaos key also has an instance-wide fallback. Organization admins set organization keys from Administration, Organizations.
- **Tailscale**: connect a tailnet to a project ([TAILSCALE.md](TAILSCALE.md)).
- **OpenVAS**: switch the optional add-on on or off and choose which organizations and projects it scans ([OPENVAS.md](OPENVAS.md)). Organization admins choose what their own organizations scan from Administration, OpenVAS.
- **Notifications**: Slack, Discord, Lark and Telegram.
- **Email**: the SMTP server cvENGINE sends through. A person added with an email address gets an onboarding email with their username and a one-time link to choose a password ([Tenancy](TENANCY.md#onboarding-email)).
- **Scan policy**: the **Nuclei templates** switch (the whole installed library by default, or only the read-only templates). There is no Scan engines editor: every scan runs the same fixed pipeline, and the per-scan engine configurations inherited from reNgine were removed because nothing read them. An old `#engines` link opens this tab.
- **IP allowlist**, **Proxy** (the proxies that the scans run on this server leave through; private and tailnet addresses and the raw-socket tools stay direct, see [Pipeline](PIPELINE.md#keeping-scans-fast-and-polite)), and **Reports** (company name, accent colors, executive summary text and footer for [PDF reports](#pdf-reports)).
- **Resources**: memory use and the job budget of each worker container.
- **Updates**: sets how updates are installed (Manual or Automatic), the update source (repository, branch, token), and shows a six-step timeline after you Approve (approved, the host picks it up, scans pause and drain, files update, services rebuild, scanning resumes), usually 3 to 6 minutes. When no host updater reports, it shows the one command to run, with a Copy button. For App Admins a slim bar on every page announces a new version (Review and update, Dismiss) and, once approved, shows the progress and greys the page while services rebuild ([UPDATES.md](UPDATES.md)).
- **Factory reset**.

The tabs that hold settings are described in [CONFIGURATION.md](CONFIGURATION.md#settings-in-the-app).

The **Add targets** dialog takes an organization and project, `#Project` and `##Organization` grouped pastes, a file (`.txt`, `.csv`, `.list`), a live count, a discovery mode (Standard, Deep, Passive, or Just add), which is kept on each target and used for its later automatic scans (Just add means manual only: nothing scans it until a person picks a mode), and an authorization tick (sent as `authorized: true` with the request; the server does not record it yet), then links to **Watch it live**.

`/cve/settings/` is backed by `cveFeed/settings_api.py` (`/cve/api/settings/...`), needs an App Admin session and CSRF, and is not part of the agent API. Secrets are write-only: responses say whether one is set, and a blank value keeps the stored one.

Page logic lives in `web/static/cve/app.js`. To add a section, add an entry to `SECTIONS` in `cveFeed/views.py`, a URL pattern, and a function in `pages`. The pages inherited from reNgine are retired and forward to their cvENGINE equivalents. The scan report (`/scan/create_report/<id>`) and the plain-text exports (`/scan/export/{subdomains,urls,endpoints}/<id>`) remain.

## How cvENGINE works

`/cve/how-it-works/` is a short explainer for people new to the tool, linked from the CVE feed card on the dashboard. It walks through five steps (discover everything you own, map every exposed service, match against the world's CVEs only when it fits, prove it safely, fix the right thing first) and a list of reasons to trust a finding. It carries a "Reviewed for version" stamp, `HOW_REVIEWED_VERSION` in `cveFeed/views.py`, which `tests/test_how_it_works.py` forces to match `web/.version` so the page is reread at every release.

## The rebuilding page

While an update is applied or the site stops answering, visitors see a "We are rebuilding cvENGINE." scene (two engineers in hard hats hold up a blueprint while a crane lifts the next piece into place, and trade a random line of banter every two seconds, one exchange at a time, with a "Usually 2 to 5 min" note) instead of an error. There are two paths to the same scene (`static/cve/maintenance.html`, one self-contained file that needs nothing from the application):

- **nginx** answers every path with it (status 503, `Retry-After: 120`) while the update flag file exists, and for any 502, 503 or 504 from the application. Served alone, it asks for its own address every few seconds and reloads the moment the real site answers.
- **Every page** loads the scene while the site is up (`static/cve/sitewatch.js`), asks `GET /cve/api/alive` every 15 seconds, and after two misses in a row covers itself with the scene (inert page, status line "The site is not answering. This page comes back by itself."). After two answers in a row it reloads. An App Admin's page that is watching an approved update drives the same cover itself with the update's phases (`updatebar.js`).

See also: [AGENT-API.md](AGENT-API.md), [TENANCY.md](TENANCY.md), [documentation index](README.md).

## Themes, preferences and the keyboard

Light is the default and is always on. Dark applies only when the viewer picks Dark, or Auto while the system is dark (account
menu, Theme). `static/cve/theme.js` runs in the head before the stylesheet and sets `data-theme` on `<html>`, so there is no flash.
Every color in `cve.css` is a token: the dark palette is one block of overrides after `:root`. `--ink` is the high-contrast
foreground and also the fill of selected rows and primary buttons, so in dark it becomes light and `--on-ink` (the text on that
fill) becomes dark. Text on solid fire, smoke, ice and ok fills stays white through `--on-solid`. Do not add a raw hex or `rgba()`
outside the token blocks; the one allowed exception is the QR code, which must stay black on white.

Per-browser preferences (localStorage, nothing sent to the server): theme (`cve.theme`), time zone (`cve.tz`, local or UTC),
saved views on Hosts and Findings (`cve.views.v1.<project>.<page>`, 12 per page), the last project used in each organization (`cve.org.last.v1`), Live graph pin positions (`cve.pins.<project|all>`), the "new since you last looked" baseline (`cve.seen.v1.<project>.<page>`), which Sentinels groups are folded (`cve.sentinels.folded`), the scope last chosen on the API keys page (`cve.keys.scope`) and
desktop notifications (`cve.notify.desktop`).

Modules: `views.js` (filters in the URL and saved views), `saved-searches.js` (saved searches with alerts, kept on the server), `bulk.js` (select mode and the action bar; actions run the single-item
request four at a time, although `hosts/bulk` exists), `keys.js` (vim-style keys and the `?` sheet), `seen.js` (new markers), `notify.js` (scan notices),
`prefs.js` (time zone formatting, theme chooser), `charts.js` (area chart, heatmap, sparkline; days are calendar days in the zone the page displays), `csv.js` (CSV export of the current filter, formula-safe), `rowmenu.js` (row actions menu), `palette-search.js` (Shodan-style filters, suggestions and host preview in Ctrl+K), `finding-glance.js` (the three cards at the top of a finding), `suppliers.js`, `inventory.js` (host inventory), `authcheck.js` (target sign-in), `report-export.js` (PDF report button), `sentinel-live.js` and `sentinel-settings.js` (Sentinels page), `api-keys-panel.js` and `openvas-panel.js` (shared by Settings and Administration), `sitewatch.js` and `updatebar.js` (rebuilding page and update bar). Script URLs are content-hashed, so restart the
web container after editing a static file.

Checks used while building these: axe-core (WCAG 2.0 and 2.1 A and AA) on 18 pages in light, dark and auto, with zero
violations, plus a computed-style comparison showing the light theme is unchanged by the token work.
