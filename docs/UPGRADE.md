# Upgrading from an older install

Older installs (reNgine and pre-release cvENGINE builds) ran PostgreSQL 12. The current release runs PostgreSQL 18, which cannot open a version 12 data directory, so the data is dumped and loaded into a new volume. The old volume is not converted or deleted. A fresh install needs none of this.

1. Back up the database, then `git pull`. Do not use the in-app updater or automatic deployment until the move is done.
2. `make up`. It moves the database to PostgreSQL 18, keeps a dump in `backups/`, then rebuilds and starts everything. The first build takes a few minutes. For a development install, run `scripts/upgrade-postgres.sh --dev` and then `docker compose -f docker-compose.dev.yml up -d --build`.
3. When you have checked the data, remove the old volume: `docker volume rm <project>_postgres_data` (the project is `COMPOSE_PROJECT_NAME` in `.env`, default `rengine`).

To roll back, check out the previous commit and start it. It still uses the untouched old volume, without anything written since the upgrade.

## Upgrading to 1.4

### Each Sentinel is auto-tuned

After the update, auto-tuning (when in Auto, the default) also tunes each Sentinel's tasks at once and the slots of its memory-heavy kinds, from the machine numbers a current Sentinel client reports in its heartbeat. Nothing is stored or migrated: a Sentinel nobody tuned keeps running at its machine's own setting, and the tuner only lowers it on trouble and brings it back. A Sentinel whose tasks at once (or a kind's cap) you set on the Sentinels page stays as you set it. A Sentinel on an older client sends no machine report and is left as it is until it updates. To stop it, choose Off or Suggest under Settings, configMaxxing, Auto-tuning (every Sentinel goes back to its own numbers at once).

### Duplicate rows merged before unique constraints

`startScan` 0031 to 0035 make the database refuse a second row for a key the scans always treated as one row: a host in a scan (`uniq_sub_scan_dom_name` on scan, target and name; hosts stored without a scan are not covered), a technology name (`uniq_technology_name`, exact name; spellings in another case stay separate rows as before) and the tag, CVE id and CWE id names of findings (`uniq_vulntag_name`, `uniq_cveid_name`, `uniq_cweid_name`). Before, two writers that stored the same host or name at the same moment (or a discovery copied into a scan twice by a resumed stage) left two rows, and a later lookup could fail with "returned more than one".

Each migration first merges the duplicates, in its own transaction: the oldest row stays (the one every page and lookup already used), the empty fields of a kept host are filled from its copies, and every row that pointed at a copy (findings, endpoints, CVE matches, subscans, address, technology and WAF links) is moved onto the kept row; a link the kept row already has is dropped rather than doubled. Nothing that has rows pointing at it is ever deleted: if moving a finding or a CVE match would make it a duplicate of one the kept host already has, the migration stops with the ids to merge by hand and changes nothing (we found no such case in the data we checked). Then the unique index is built with `CREATE INDEX CONCURRENTLY`, so scans keep writing while it builds, and the constraint is attached to the built index, a short metadata change. If a build is interrupted, or a scan stored a new duplicate between the merge and the build, `migrate` stops: run `DROP INDEX CONCURRENTLY IF EXISTS <name>;` with the name it gives and run `migrate` again (the merge runs again first). Rolling back (`migrate startScan` to the migration before 0031) drops the constraints; merged rows stay merged.

Ports are not constrained: a port's key (the address it is on, its number and protocol) spans the address link table and the port row, which one unique constraint cannot express.

### Autovacuum on the busiest tables

`cveFeed` 0190 and `agentapi` 0027 set `autovacuum_vacuum_scale_factor` and `autovacuum_analyze_scale_factor` to `0.05` on the six tables that churn the most: agent activity, Sentinel tasks, service runs, CVE detections, triage and asset changes. The server wide default of `0.2` let a fifth of such a table go dead before autovacuum cleaned it (on one production host 49.8k dead rows of 494k in agent activity, and 9.4k of 116k in the 1.7 GB Sentinel task table); now it is a twentieth. `ALTER TABLE ... SET (...)` changes only the table's storage options: it takes a short `SHARE UPDATE EXCLUSIVE` lock, which lets reads and writes go on and waits only behind a running vacuum or index build on that table, and rewrites nothing. The first autovacuum after the update may run longer on those tables, once. Rolling back (`migrate cveFeed 0189`) runs `ALTER TABLE ... RESET (...)`, which puts the server wide defaults back. `SELECT relname, reloptions FROM pg_class WHERE reloptions IS NOT NULL;` shows them.

### The application image runs Python 3.14.10

The `web`, `celery` and `celery-beat` image no longer uses Ubuntu's `python3` (CPython 3.14.4). It installs a pinned CPython build, 3.14.10 (`PYTHON_VERSION` in web/Dockerfile, a python-build-standalone build that uv fetches and checks in a build stage), and makes `/opt/venv` from it. CPython 3.14.0 to 3.14.4 shipped an incremental cyclic garbage collector that 3.14.5 reverted to the generational one of 3.13; under the gevent pool of the celery workers it crashed a worker with *Fatal Python error: Segmentation fault* inside the collector, and each crash restarted every lane. The minor version is the same, so the same wheels install and the paths under `/opt/venv/lib/python3.14` do not change. The update rebuilds the application image (the first build fetches the interpreter, about 35 MB, from GitHub) and restarts the web server and every worker once. Nothing is migrated. `docker compose exec celery python -c 'import sys; print(sys.version)'` shows 3.14.10 afterwards.

### Database roles: the server no longer runs as the database owner

Until now `web`, `celery` and `celery-beat` connected to PostgreSQL as `POSTGRES_USER`, the role the database image created, which owns every table and on a stock install is a superuser: a bug or an SQL injection in the server could run programs on the database server, read its files, create roles or change its settings. From this update on the server connects as `cvengine_app`, an ordinary role that can only read and write the application's tables ([CONFIGURATION.md](CONFIGURATION.md#database-roles-and-logs) lists every grant and why). `POSTGRES_USER` stays the owner and is used only for the migrations, `createsuperuser` and the backups.

What the update does, in order, all by itself:

1. It writes a new random password, `CVENGINE_DB_APP_PASSWORD`, to `.env` (and to the Compose env file the install uses, such as `.env.vps`). Nothing else in `.env` changes. It does not do this when `CVENGINE_DB_APP_USER=` is set empty.
2. It recreates the `db` and `redis` containers once, a few seconds each, with their data kept: their compose definitions changed (the database now logs every connection, both move to a network of their own, and every container's log now rotates). **Docker deletes a container's log when it recreates it**: if you need the database's current log (for example for an investigation), save it first with `docker compose logs --no-color db > db-before-update.log`.
3. It takes its usual database backup, as the owner.
4. It migrates, as the owner. The migration ends by creating `cvengine_app` with that password and granting it what the server needs.
5. It recreates `web`, `celery`, `celery-beat` and the proxy, as every update does. Each checks at start that `cvengine_app` can log in and then runs as it. The AI reviewer and the built-in scanner are recreated as on every update; the reviewer is no longer on the network the database and Redis are on (it never had their passwords, and it only talks to `web`).
6. The update log ends with one line per service, `Database role of web: app cvengine_app`, and a warning if any still runs as the owner.

So the switch happens in this one update with the one restart of the application it always does; nothing has to be restarted a second time. If the role cannot be created (an owner that may not create roles) or cannot log in, nothing is locked out: those containers keep the owner role and say so in the update log.

The database's connection log (`log_connections`, `log_disconnections`) is on by default (`POSTGRES_LOG_CONNECTIONS`, `POSTGRES_LOG_DISCONNECTIONS`). A value turned on earlier with `ALTER SYSTEM` is now also set on the database's command line, which wins over `ALTER SYSTEM`; set either to `off` in `.env` to turn it off. Every container's Docker log now keeps at most 5 files of 50 MB (`CVENGINE_LOG_MAX_FILE`, `CVENGINE_LOG_MAX_SIZE`).

**To go back to the owner role**, set `CVENGINE_DB_APP_USER=` (empty) in `.env` and in the Compose env file, then `docker compose up -d web celery celery-beat` (with your usual `-f` and `--env-file`). The role stays in the database unused; the owner can remove it with `DROP OWNED BY cvengine_app; DROP ROLE cvengine_app;`. Going back to an older version needs nothing: it ignores these settings and uses the owner role. A database dump made after this update names `cvengine_app` in its grants: loading it into an empty new database prints errors for those lines (the role does not exist there yet) and loads everything else, and the next update or `make up` creates the role and grants it again.

### Questions after an update

The server health check (part of the AI question's first line) may now also propose performance changes to the auto-tuned settings. It adds no AI call and costs nothing extra. It is treated as an AI agent: what it proposes follows the setting for AI agents (Settings, configMaxxing, Auto-tuning, **Suggest** by default, asked after an update), so **on an install that already had the AI reviewer on, the proposals appear as suggestions in the Auto-tuning History that a person applies; nothing is changed by itself** unless a person sets AI agents to Automatic (and auto-tuning is in Auto mode). With AI agents Off the proposals are ignored.

An update never switches on, by itself, something that costs money or changes what is scanned. Such a feature ships **off** (or in its no-cost mode) and stays there until an App Admin answers a question about it, on an upgrade and on a new install alike. The first App Admin who opens the dashboard after an update is taken once per session to **A few questions about this update** (`/cve/update-questions/`); everyone else sees nothing and is never blocked. **Save answers** is all or nothing: if the Settings refuse one answer, none is saved and the message names that question (the scanner plan is carried out last). **Decide later** leaves everything off and keeps a reminder at the top of the app ("2 questions about this update are waiting. Answer them") until the questions are answered; **Settings > Questions about updates** opens the page again to change an answer. The page is never an obstacle: the API, the MCP, static files and the updater are never sent to it, and it is skipped with `?skip=1`. On a new install the setup wizard asks the AI question as soon as a model is connected, and its "Where it runs" step is the scanner question.

The questions of 1.4.0:

- **Which scanners will you use?** The same choice, with the same words, as Settings > Sentinels, **Which scanners run**: *Use the built-in scanner only* (internal: it runs on this server), *Use my own Sentinels only* (external: scanners you install on your own machines, and one inside your network also sees what an outsider cannot; the built-in scanner is removed, which frees its memory, and nothing else is switched off) or *Use both*. The plan in force is pre-selected ("Keeps what runs now") and the answer stored is the plan itself (`internal`, `external` or `both`). With no live Sentinel of your own, choosing *my own Sentinels only* changes nothing until the first one checks in (nothing is left unscanned), and then it is applied and audited. After an answer that uses Sentinels the page links to the Sentinel enrolment and, if you scan inside your network, to the project's internal ranges (the server itself never scans private addresses). The host helper carries the plan out; the server restarts briefly only when the built-in scanner goes on or off. It is not asked when the installer, the update dialog or the setup wizard's plan step already set it.
- **Do you want AI validation?** Asked only when an AI model is connected (otherwise there is nothing to switch on: turn it on later in Settings > AI model). *Off*: nothing is billed. *Recommend only*: the AI gives a verdict on each finding (at most 300 findings a day, one provider call each) and checks the server's health 4 times a day; a person applies the verdicts. *Act on safe steps*: as above, and the AI may close a finding as a false positive when it is sure and the evidence is not hard proof; it is also the only answer that switches on the AI-written checks (below), because a check that passes its own validation runs on your hosts with no person approving it. *Recommend only* leaves the AI-written checks off, and you can switch them on in Settings > AI model. Your AI provider bills every call. This covers what is new since 1.3.6: the AI reviewer (`ReviewerSettings`, Settings > AI model) now ships off; the migration switches off only a reviewer row that no person ever saved, and never undoes a choice made in Settings. The question has three lines: the finding review with the health check, the AI host review, and the **AI-written checks**. That last one is the automatic validation of the checks the AI wrote (`validate_template_drafts`): in 1.3.6 such a draft waited unused for a maintainer's explicit approval and nothing ran it, while 1.4 validates it by itself (two AI calls per draft, more when a try is repeated, at most 10 drafts a day by default) and a draft that passes becomes a check that runs on your hosts. So it ships **off** and the drafts wait as before, nothing is asked of the AI and no draft expires until an administrator switches it on (Settings > AI model, or this question; an agent cannot switch it on). An administrator who answered this question before is asked again for the lines added since, and the earlier lines are not changed by the new answer, except that a "Decide later" from a development build counts as no answer, so the whole question is asked again. Checks that already passed (from a 1.4 development build) keep working. Features that already existed in 1.3.x (triage, template drafts, auto-tuning advice) keep working exactly as they did.

An answer is carried out through the same Settings handler the Settings page uses (same checks, same audit entry, plus `setup.question`) and is recorded in `SetupAnswer`. REST: `GET`/`POST /cve/api/settings/setup_questions` (App Admin; `{key, answer}` or `{later: true}`). The MCP can read the questions (`get_setting setup_questions`) but an agent can never answer one: only a person switches a paid feature on.

**Settings that do not fit your host are put right during the update.** You do not have to find them. Before anything is stopped the updater runs a host review (`scripts/host-review.py`, the same for the Update button, `scripts/update.sh`, cron and unattended runs). It looks at the host's cores, memory and free disk and puts right only what is plainly wrong for it, and each change is backed up first (`<file>.cvengine-review-<time>`) and written to the update log with the line it replaced:

- A leftover `DISCOVERY_CONCURRENCY` below 4 in `.env` or the env file (a pin from 1.3, when that pool only ran discovery). On 1.4 a host assessment holds a discovery slot while it waits for a Sentinel, so the pin let one host be assessed at a time while the Sentinels idled. The line is removed and the number follows auto-tuning. Left alone on a host with under 4 GB of memory, and when nothing scans on the host.
- A container memory ceiling below what its service needs: the database under 1 GB on a host with 6 GB or more (768 MB below that), the web server under 768 MB. The kernel kills a process that reaches its ceiling; a database held to 512 MB was killed this way. The value is raised in the file that sets it (your own compose overlay, or the env file when the ceiling is an environment default). A ceiling above the floor is yours and is never touched.
- The database's memory settings (`POSTGRES_SHARED_BUFFERS`, `POSTGRES_EFFECTIVE_CACHE_SIZE`, `POSTGRES_WORK_MEM`, `POSTGRES_MAINTENANCE_WORK_MEM`) still at the small defaults are sized for the memory the database can use (its container ceiling, else its share of the host), always inside that ceiling. A value you set is left and nothing is lowered. The update log says *Postgres settings changed, the database restarts once during this update*. See [DEPLOYMENT.md](DEPLOYMENT.md#sizing-the-database).
- Said, never changed: container ceilings that together exceed 90 percent of the host (they are ceilings, not use), and a disk with less free space than the first 1.4 update needs.

To see what it would do without changing anything, run `python3 scripts/host-review.py` in the install directory; add `--apply` to let it. It never asks a question and never blocks an update.

What an operator needs to know in one place is in [1.4-OPERATOR-NOTES.md](1.4-OPERATOR-NOTES.md). Update from 1.3.x the way you always do: the in-app updater, `scripts/update.sh`, or automatic deployment ([UPDATES.md](UPDATES.md)). The update takes a database dump just before it migrates (`scripts/db-backup.sh`, the last 3 are kept) and a migration is never rolled back. The version it reports is `v1.4.0` (`web/.version`, shown on the About page). A fresh install needs none of this.

**The one change that matters: the server no longer scans.** Every scan runs on a Sentinel ([SENTINELS.md](SENTINELS.md), [SCANNER-ARCHITECTURE.md](SCANNER-ARCHITECTURE.md)).

- **The built-in scanner is added by the update.** The new `scanner` compose service runs the newest published Sentinel image, `ghcr.io/hevnsnt/cvengine-sentinel:main` (about 5 GB; the update pulls it before anything is stopped, starts it once the server answers and rolls back to the image it had when the new one does not check in with a contract this server accepts; to hold it at one version set `CVENGINE_SCANNER_IMAGE` in `.env`). The server enrols it with nobody typing a secret. It has a network of its own (shared only with the web service): every scan leaves from it, and the server's containers carry no scan traffic. Make sure at least 6 GB are free where Docker keeps its images, and that the host has the memory for it (`SCANNER_MEM_LIMIT`, 3 GB by default; [DEPLOYMENT.md](DEPLOYMENT.md#memory)).
- **The built-in scanner drops `NET_ADMIN`.** It runs with `cap_drop: [ALL]` and only `NET_RAW` and `SYS_CHROOT` (nothing to do). A scanner image older than this release, which you hold with `CVENGINE_SCANNER_IMAGE` or which a rollback put back, has nmap and naabu that cannot start without `NET_ADMIN`; `scripts/scanner.sh` notices and gives that image `NET_ADMIN` for itself by writing `CVENGINE_SCANNER_EXTRA_CAP=NET_ADMIN` to `.env`, and removes the line when a newer image runs. Only if you start a held old image with a plain `docker compose up` before any update script has run must you set `CVENGINE_SCANNER_EXTRA_CAP=NET_ADMIN` yourself ([BUILTIN-SCANNER.md](BUILTIN-SCANNER.md#capabilities)).
- **The built-in scanner is the path of last resort.** If you run external Sentinels, they take work first; the built-in scanner takes it when no external one can, or after `CVENGINE_BUILTIN_FALLBACK_SECONDS` (120) ([SENTINELS.md](SENTINELS.md#the-built-in-scanner-is-the-last-resort)). With nothing but the built-in scanner, it takes everything at once.
- **Scans wait instead of falling back to the server.** Before 1.4 a project with no live Sentinel scanned on the server. Now no kind has a local path (`sentinel_dispatch.NEVER_LOCAL`): with no scanner able to take the work a stage waits, nothing is marked failed, its targets stay due, and a strip on every page says **Scanner offline** until a scanner is back. If you turn the built-in scanner off (`CVENGINE_BUILTIN_SCANNER=0`) and enrol no Sentinel, nothing scans.
- **Tools left the server image.** nmap, naabu, bbot (with gowitness and its Chromium), WPScan and Ruby, testssl.sh, wafw00f, aardwolf, Playwright and the Python packages only they used are gone; the image keeps nuclei, which the server uses to update and read its template set. The image is much smaller. `docker image prune` removes the replaced one. The scan tools, with their pins, are in the Sentinel image ([ARCHITECTURE.md](ARCHITECTURE.md)); the About page lists both sets.
- **The Settings, Proxy proxy applies to the built-in scanner only** (the server sends no scan traffic); external Sentinels keep their own egress.
- **External Sentinels need the matching client** (result contract version 9, 40 kinds; contract 4 and 5 add no kind, 6 adds `java_runtime`, 7 adds `version_read`, 8 adds `version_digest`, 9 adds `version_rows`). A Sentinel on contract 1 or 2 keeps every kind it had and is never offered a newer one, so the new kinds run on the built-in scanner or on an updated Sentinel. Update them from the Sentinels page. The server installs the contract from the Sentinel repository (`web/requirements.txt` pins its commit), so it no longer ships its own copy.

**Service features (HTTP/2) need no step.** The update adds the empty `ServiceFeature` table (cveFeed migration 0177). Readings arrive with the next daily hygiene check of each target by a Sentinel at the release this server pins; until then every match of a CVE that needs HTTP/2 stays as it was (unknown changes nothing). Each reading re-evaluates its host's matches when it is stored, so no backfill runs, and which CVEs need HTTP/2 is read from their advisories directly (stored detection records are not rewritten). A Sentinel older than that release sends no reading, which is unknown, never "no".

**OpenVAS** is off by default and runs on a Sentinel only. This server opens no GMP session; the 15 `openvas-*` containers this repository's compose file once had are gone from it, and an update removes any that still run (their data volumes stay; [OPENVAS.md](OPENVAS.md#images-pins-and-updating) has the command that frees them). A run an earlier version started against them is closed as failed and its hosts go to a Sentinel that declares `openvas` ([OPENVAS.md](OPENVAS.md)). `make openvas-user` and the `openvas_*` management commands are removed.

**Installer and setup wizard.** `sudo ./install.sh` is a thin bootstrap (`--sentinels=internal|both|external`, `-n`, `--no-builtin-scanner`); the first App Admin's first sign-in opens a setup wizard that asks for the organization, project and one seed domain (a discovery starts at once), how you scan, what runs, and optional extras ([DEPLOYMENT.md](DEPLOYMENT.md#setup-wizard)). An existing install with targets is never sent to it.

**The interface.** The left rail has 8 entries (Overview, Findings, Hygiene, Hosts, Suppliers, Scans, Scanners, Bug bounty); Settings, Administration and About sit in the footer. Live is **Overview**, the account menu says **About** (not Help); Hygiene and Suppliers keep their own entries and are also tabs (under the same names) beside the pages they relate to; Sentinels is a tab of **Scanners**; **API keys** (MCP and agents) is in the account menu and the old Administration Agents tab is gone (`#agents` opens the Sentinels page); Settings is Essentials plus a collapsed Advanced group ([FRONTEND.md](FRONTEND.md)). Bookmarks keep working: every page keeps its address.

**New services and features.** An AI reviewer container (`reviewer`, [AI-REVIEWER.md](AI-REVIEWER.md); idle until an AI provider is set, `CVENGINE_REVIEWER=0` turns it off) that also makes the triage's model calls; a project **Secrets** inventory fed by Kingfisher on the scanner ([SECRETS-PLAN.md](SECRETS-PLAN.md)); SSH inspection with sshamble (host key check only: it reads the server's own handshake and never logs in or submits a credential; `CVENGINE_SSH_PROBE=0` turns it off); web screenshots by a Sentinel's headless Chromium.

**The server keeps no scan tool, no template set and looks no target name up (contract 11).** The server image no longer builds nuclei or downloads the template library, the `nuclei_templates` volume is no longer mounted (remove it with `docker volume rm` after the update if you like; nothing reads it), and the routes `sentinel/template-policy` and its `/bundle` are gone. The TLS audit and the OpenVAS sweep now name a host's newest stored address instead of looking the name up, and a host added by its name is no longer refused at entry because of what its name resolves to: the Sentinel that scans it refuses one that points at an address no Sentinel may scan, and the stage says so in the activity feed. `NUCLEI_TEMPLATES_DIR` is no longer read.

**Disk and memory on a small host (checked for you).** The first update to 1.4 adds about 11.6 GB: the scanner image (5.1 GB), the new server image (1.6 GB), the AI reviewer (0.25 GB) and a cold build cache (about 4.7 GB), while the 1.3 server image (7.9 GB) is removed only after the update is verified. So the update wants **about 14 GB of free disk** (this is the space to update an install, not the 20 GB recommended for a fresh install) where Docker keeps its data (8.9 GB when the scanner image is already here, the scanner is off, or you choose your own Sentinels only). If there is less, the updater first removes untagged images and the build cache (never a tagged image or a volume), measures again, and otherwise stops before it pauses or stops anything with *This update needs about 14 GB of free disk; this server has 9 GB free. Free some space or add disk, then try again.* (Settings > Updates shows the same sentence once the host has the 1.4 screen, with **Approve update** switched off.) On a host under 7 GB the cold build of the server image needs about 2 GB (a 1 GB cap fails in the nuclei compile), so the updater stops the celery workers and the built-in scanner for the build and starts them again straight after it, whether it worked or not; the web service, database, Redis and proxy stay up. A build that fails leaves the old version running and says so. Details and the command line: [UPDATES.md](UPDATES.md#small-hosts-disk-memory-and-stuck-scans).

**Which scanners run, and the memory (asked during the update).** The update adds a built-in scanner that reserves up to 3 GB, which a small host that already runs the workers near their ceiling cannot spare. Pressing **Update** in Settings > Updates therefore asks one short question first, when there is one worth asking: this server has no scanner choice on record, and either the host has under 7 GB of memory or Sentinels of your own are live. The dialog says how much memory the server has and what the built-in scanner reserves, and offers three choices with one chosen for you from what the server sees: **Use my own Sentinels only** (recommended when two or more of yours are live; it frees up to the scanner's memory), **Use the built-in scanner only**, **Use both**. **Update now** starts the update with that answer. On a bigger host with no Sentinels of your own, or once anybody has chosen, **Update** just updates, as before. The answer is saved by the update itself; nobody edits `.env`. Change it later under Settings > Sentinels, **Which scanners run**.

The first update from 1.3 is approved in the 1.3 screen, which cannot ask. It applies the safe default instead: on a host under 7 GB the scanner is limited to 1 GB, and the scanner is kept. If two or more Sentinels of your own are live, Settings > Updates and Settings > Sentinels then say *The built-in scanner was kept at 1 GB. You have 2 Sentinels of your own: switch to Sentinels only in Settings > Sentinels to free the memory.*, with the control to do it. Nothing is ever removed without an answer. When the update finishes, its log (Settings > Updates, Details) ends with a memory line: either the limits add up to under 90 percent of the host, or a warning that names the largest container and the setting that lowers it.

**From the command line.**

Almost everyone uses the buttons above. Everything they do can be done from a terminal, and an update run by hand, by cron or by systemd never asks a question and never waits for an answer.

The three choices are keys in `.env` (the same ones `install.sh` writes):

| Choice | `.env` |
| --- | --- |
| Use the built-in scanner only | nothing, or `CVENGINE_SENTINEL_PLAN=internal` (and `CVENGINE_BUILTIN_SCANNER=1` if it was off) |
| Use both | `CVENGINE_SENTINEL_PLAN=both` (and `CVENGINE_BUILTIN_SCANNER=1` if it was off) |
| Use my own Sentinels only | `CVENGINE_BUILTIN_SCANNER=0` and `CVENGINE_SENTINEL_PLAN=external`; the next update removes the `scanner` container |

`SCANNER_MEM_LIMIT` is the built-in scanner's memory ceiling (`1g`, `2g`, ...). To answer the question in a script, pass it to the updater: `scripts/update.sh --sentinels external` (or `internal`, `both`), or set `CVENGINE_INSTALL_SENTINELS=external` in the environment. Either writes the keys above exactly as the dialog would, before anything is stopped. Anything else is refused before the update starts.

**An update with no answer** (cron, `scripts/update.sh` with no flag, an automatic update, an update approved by a server too old to ask) applies the safe default: a host under 7 GB gets `SCANNER_MEM_LIMIT=1g` unless you set one, and a scanner is never removed. When it finds two or more Sentinels of your own live and nobody has chosen, it keeps the scanner, prints the finding and the exact flag (`scripts/update.sh --sentinels external`), and leaves a notice in `web/.update-notice.json` that Settings > Updates and Settings > Sentinels show until somebody chooses. The count of live Sentinels is read from the server's database by a one-off container of the new web image (the running container, still on the old image, cannot start the new code, and a 1.3 server has no such command). When it cannot be read (the database is not reachable), the updater prints that and changes nothing about which scanners run.

Read the state from a terminal: `scripts/update.sh --check` prints the memory the updater sees, whether it will write `SCANNER_MEM_LIMIT`, and how many Sentinels of your own are live when the running server can say (it changes nothing); `grep -E '^(CVENGINE_BUILTIN_SCANNER|CVENGINE_SENTINEL_PLAN|SCANNER_MEM_LIMIT)=' .env` shows the choice; `docker compose run --rm --no-deps -T --entrypoint python3 web manage.py external_sentinels` prints `EXTERNAL_SENTINELS_LIVE n` (read only). The memory budget line (see [DEPLOYMENT.md](DEPLOYMENT.md#memory)) is in the update's output (`scripts/update.sh`) or in the update log under Settings > Updates (`.git/cvengine-update/update.log` on the host).

**Cisco builds and Oracle's supported versions are read again after the update (`backfill_exact_builds`).** Cisco's CVE records list every affected build one by one (CVE-2023-20109: 674 IOS builds, 364 IOS XE builds). Before this change the conversion kept 30 ranges per product and dropped every parenthesised build (`15.2(4)M7`, NX-OS `9.3(8)`), so an IOS XE or ASA host whose build came after the first 30, and every IOS and NX-OS host, had no match: a silent miss on KEV CVEs such as CVE-2023-20198, CVE-2024-20353 and CVE-2025-20333. Each product block now keeps the whole list of builds (`builds`, lower-case text compared for equality only) and an Oracle block one range per release line (`reading: oracle_supported_versions`). The update step re-reads the CVE List record of the stored CVEs this concerns, by itself and once: a block with 30 ranges, a Cisco block with none, and an Oracle block with none or with exact versions (about 300 of the 40,867 CVEs of the published catalog, 109 of them KEV; 200 records per pass, resumable from where it stopped). Each changed CVE is marked for re-correlation, so the new matches appear at the next `correlate_refreshed_cves` run, under the same version-only ceilings as any match. A record GitHub does not serve at once (rate limited, a server error, a cut connection) is asked again up to three times, waiting 2, 8 and 30 seconds (longer when GitHub asks for longer), four reads at a time; one still failing after that makes the step fail and be tried again at the next worker start. A record that cannot be read on any try (over the size limit, not JSON) is left as stored and named in the step's summary. **Identities, fingerprints and SSH banners are read from what is stored (`backfill_identities`).** The update step decodes the nmap service fingerprints ports already store (`Port.extra['servicefp']`), reads every current host's stored data again for the network operating system its OS guess, certificates or OS CPEs name, Recog's identities and hardware and a fingerprint's HTTP headers, and the SSH banners the SSH inspection stored (`vsrc:ssh`), then correlates the hosts that gained or lost a reading ([PIPELINE.md](PIPELINE.md#recog-banner-fingerprints)). **Windows releases are read from stored NTLM and SMB script output (`backfill_windows_builds`).** The Windows build the NTLM scripts (`rdp-ntlm-info`, `ms-sql-ntlm-info` and the other `*-ntlm-info` scripts) and `smb-os-discovery` stored is now a version reading of the release it names (`vsrc:ntlm`: release known, patch level unknown; [PIPELINE.md](PIPELINE.md#windows-release-from-ntlm)). The update step reads every current host's stored script output once, by itself, and correlates those hosts: a KEV or critical (CVSS 9.0 or more) network CVE without user interaction whose record names the release becomes a needs-validation candidate of source `windows`, at ice, which never raises a host's heat on its own (about 30 per Windows Server host against the published seed). A host scanned again gets its reading from the scan. To preview or run it by hand: `docker compose exec -T web python3 manage.py backfill_windows_builds` (a dry run that counts the hosts) and `--apply`. No migration, no new variable.

**Recog reads the banners already stored (`backfill_recog_readings`).** Rapid7 Recog's fingerprints (vendored in `web/cveFeed/data/recog/`, [PIPELINE.md](PIPELINE.md#recog-banner-fingerprints)) now read the SSH, SMTP, FTP, POP3, IMAP and telnet banners, the `Server` and cookie lines, `mysql-info`, `ntp-info` and SNMP sysDescr output, the `Server` header and the live routes' headers each host already stores. A product they name with a version that nmap, another reading or a technology did not already state is a `vsrc:recog` reading and a technology, matched CPE first; an operating system is a hint unless it is a network OS. The update step reads every current host's stored banners once and correlates the hosts that gained or lost a reading, so new matches can appear where a banner names a product nmap left unnamed or unversioned. To preview or run it by hand: `docker compose exec -T web python3 manage.py backfill_recog_readings` (a dry run that counts the hosts and prints how many fingerprints loaded) and `--apply`. No migration (the readings are `ProbeObservation` rows), no new variable, no new request.

**Every Shodan InternetDB CPE is a reported reading (`backfill_shodan_cpes`).** A CPE with no version and an operating system CPE were stored as first-party technologies (`http server`, or the raw `cpe:/o:canonical:ubuntu_linux`), losing the vendor. Every Shodan CPE is now a `vsrc:shodan-idb` reported reading labelled "vendor product" (`apache http server`), never a technology ([PIPELINE.md](PIPELINE.md#versions-already-received)). The update step relabels the readings stored before (`openssh` becomes `openbsd openssh`), re-reads the CPEs the discovery feed kept, removes the CPE technologies and correlates the hosts that moved, by itself and once. By hand: `python3 manage.py backfill_shodan_cpes [--apply]`.

**PHP read only from a link to a `.php` page is a lead (`backfill_php_link_tells`).** A front page that linked to one `.php` URL (on another site as often as its own) was recorded as running PHP: a technology "seen via page:.php link", a "PHP, version not stated" probe reading, version-unknown PHP CVE candidates, and hosts on the Overview's threat card under "run PHP, version unknown". The update step turns the stored route answers' marker into a lead, the probe rows into leads, removes the bare `PHP` technology links the route check made on hosts whose own routes do not confirm PHP (an `X-Powered-By` or `Server` header naming PHP, a `PHPSESSID` cookie), on every stored row of the host, and correlates those hosts again, so the candidates close. A host whose server confirms PHP keeps it. A second run changes nothing. [PIPELINE.md](PIPELINE.md#a-php-link-is-a-lead) has the rule. `python3 manage.py backfill_php_link_tells` shows what it would change; `--apply` writes.

**TLS audit findings say what they are (`rewrite_tls_findings`).** testssl.sh's "likely VULNERABLE with 00" for CCS injection was shown raw, titled "may apply", rated Critical and counted by the AI triage as "a deterministic check failed". The update step rewrites every open TLS audit finding (`tlsa_*`) from its stored evidence, with no new test: a plain description instead of the tool's result string, a title that says "confirmed" or "Possible ..., not confirmed", Medium at most for a result that is only likely or potential (testssl.sh's own severity is kept in the evidence and on the page), and the confidence the AI triage reads, so an unconfirmed result is asked again and no longer counts as hard evidence. Closed findings and a person's status, assignee and notes are left alone, and a second run changes nothing. [PIPELINE.md](PIPELINE.md#tls-audit) has the rules. `python3 manage.py rewrite_tls_findings` shows what it would change; `--apply` writes.

**Shodan InternetDB readings are leads, never findings (`cleanup_shodan_matches`).** InternetDB is keyed by IP address, so behind a CDN it describes another site (a Cloudflare-fronted host was shown WordPress 7.0.9 and Update WordPress as the project's first action). Its readings no longer make CVE matches, technologies or product counts, and are found only with `vsource:shodan-idb`; they queue our own checks instead (the WordPress probe, the version source reads), unless the host sits on a shared edge address or our own check ruled the product out, and the host page lists them as "Reported by Shodan (unverified lead)". A match made only from a Shodan reading is held at ice, and runZero's reported readings stay matched at ice until a first-party read or a check confirms them. The update step closes every open CVE match whose only basis is a Shodan reading, as a false positive with a note saying so (a match a person worked or any check confirmed is left alone), by itself and once; it is a backfill, not a migration, so the migration range above is unchanged. By hand: `python3 manage.py cleanup_shodan_matches [--apply]`.

**Archived hosts close their open findings (`close_archived_findings`).** Archiving a host now closes every open CVE match, scanner finding and hygiene finding of it as fixed, with a note that says when and by whom or why it was archived, and leaves it out of searches and counts ([PIPELINE.md](PIPELINE.md#changes)). Hosts archived before kept theirs open. The update step closes them once, by itself, the same way, each archived name on its own (it archives no sibling name); a finding a person closed is never touched, and restoring the host reopens what was closed. By hand: `python3 manage.py close_archived_findings [--apply]`.

**Findings of hosts gone from the inventory close (`audit_finding_hosts`).** A host that dropped out of the latest full scan kept its old rows, and the cleartext check kept filing and re-seeing an FTP finding from their stale ports (ftpr.zebra.com, #14 on Fix first, with no host on the Hosts page). The checks now read only hosts of the current inventory, and the update step closes, once and by itself, the open findings of every host gone from it (missed by two full scans of its target in a row and missing for `CVENGINE_GONE_AFTER_DAYS` days, 7; as fixed, with a note that says when it was last seen; they reopen when the host is back), and of hosts archived before archiving closed findings. A target whose latest full scan failed or is still running decides nothing. `python3 manage.py audit_finding_hosts` counts the open findings per project by cause (`port`, `alias`, `gone` eligible now, `gone_grace` missing but inside the grace period, `archived`, `not_a_host`); `--apply` closes the `gone` and `archived` ones.

**One technology row per spelling, and MariaDB's real release (`backfill_technology_names`).** Technology rows whose names differ only in case and read as the same product and version (`Caddy` and `caddy`, `PHP:8.1.2` and `php:8.1.2`) are folded onto the oldest, and MariaDB's handshake prefix comes off the stored port versions and CPEs (`5.5.5-10.11.19` is 10.11.19); the hosts that moved are correlated. By hand: `python3 manage.py backfill_technology_names [--apply]`.

**Versions nuclei's panel templates extracted become version readings (`backfill_panel_versions`).** An exposed-panel template (tag `panel`) often extracts the product's exact version (Grafana's, Jenkins's), which was kept only in the finding's text. Such a version is now a version reading of the host (`vsrc:panel`, [PIPELINE.md](PIPELINE.md#versions-already-received)) and is matched like any technology. The update step reads the info-level panel findings already stored, by itself and once: their extracted values, template id, name and tags (old findings kept no template metadata: the vendor and product come from the installed template of that id), stores the readings on each host's current row (never over a version another source states for the product) and correlates the hosts that gained one. A dry run by default when run by hand: `python3 manage.py backfill_panel_versions [--apply]`.

**Technology templates' CPEs and panels without a version (`backfill_template_identities`).** A nuclei technology template's metadata names its product's CPE (`tomcat-detect`: `cpe:2.3:a:apache:tomcat`), and a panel template's hit names its product even when it extracts no version; neither was kept ([PIPELINE.md](PIPELINE.md#versions-already-received)). The update step reads the stored info-level findings of the technology templates that name a product and of the panel templates (tag `panel`), by template id (the vendor, product and CPE come from the template index of the pinned Sentinel library): a technology finding gives its template's CPE to the technology of the same name on the host's current row (`source` `nuclei`, and the finding's date when the link has none), a panel finding without a version becomes an identity reading (`vsrc:panel`, no version) and a technology with no version on the current row. The hosts that changed are correlated again: a CPE makes the technology match CPE first, a product without a version is a lead, never a match. It walks the findings by id, 500 a pass, and keeps where it stopped, so a run cut short continues; it is idempotent. A dry run by default when run by hand: `python3 manage.py backfill_template_identities [--apply]` (`--reset` starts from the first finding again).

**Where each technology came from needs no update step.** A host's technology links now record the pass that read them (`source`: `nuclei`, `nuclei:derived`, `vsrc:panel`, `bbot`, `probe`, `vsrc`, `route`, `waf`, `wpscan`, [PIPELINE.md](PIPELINE.md#where-a-technology-came-from)). Links stored before this release keep an empty `source` (the host record shows `scan`): nothing stored says safely which pass made them, since several passes link the same names and a link kept only the host and the technology. They take their source, and a `tech-detect` name its derived CPE, the next time a pass reads the technology, which every scan does for the hosts it covers (the light pass within its window); a link carried onto a new scan's row keeps what it had until then.

**The cve.now window a walk wrongly declared covered is read again (`recover_feed_gap`).** cve.now renamed its list cursor and limited listings without a key to the newest 400, and the coverage walk took the end of its first page for the floor of its window: it moved the feed watermark to the head of the feed, and the CVEs the incremental sync missed since then were never read (the status said the feed was complete). The update step moves the watermark back to 2026-11-06 (the published seed's `covers_through`; a watermark already earlier is left as it is) and queues `recover_cve_feed_window`, which runs the corrected walk until the window is covered (each past day from cve.now's archive page, today from the `since` delta listing, at most 1,500 entry reads a run, 0.5 s apart) and matches every CVE it reads against the inventory, whatever its tier. It needs the cve.now feed to be reachable; a run that is refused or cannot list a day stops, and the hourly backfill carries on from the same watermark. System status (`cve_feed_watermark`) shows the lag until it is done. A dry run by default when run by hand: `python3 manage.py recover_feed_gap [--apply] [--through 2026-11-06T00:00:00Z]`.

**Open ranges from an upper bound written as text are checked (`repair_open_ranges`, issue 696).** A CVE List entry whose `lessThan` is text ("Apache HTTP Server 2.4*") was stored as an open range, so every later release matched. The update step reads the CVE List record of each stored CVE with an open range on a vendor's product (a bounded, resumable walk; it continues with every threat-intelligence run), leaves out each range the record bounds with text, notes the ranges the record means open, and marks the changed CVEs for re-correlation, so their matches outside the real range close. A dry run by default when run by hand: `python3 manage.py repair_open_ranges [--apply]`.

**Matches past a branch fix their own advisory states are re-correlated (`recheck_branch_fixes`).** An advisory that states a fix for one release line beside a wider range (F5's nginx records: 1.13.10 up to 1.31.2 plus 1.30.2 up to 1.30.3) now reads a version at or past that line's fix as outside the wider range; no stored range is rewritten. The update step finds the stored in-range matches this changes, by itself and once (one read of the in-range matches and of their CVEs' ranges: 0.3 s on an install with 10,355 version matches, where it found 162 matches of 12 nginx CVEs), and marks those CVEs for re-correlation; the next `correlate_refreshed_cves` run, which the 30 minute feed sync queues, closes the matches in one batch (it handles 100 CVEs per walk of the inventory). By hand: `python3 manage.py recheck_branch_fixes [--apply]`. No migration.

**Dismissed findings are not counted as open.** A finding the triage classed a likely false positive or not applicable is left out of every open count (the dashboard tiles, the Findings list's Actionable view and its counts, the weekly email, the PDF report, Situations and the hosts that need attention), as the PDF report already did; it is still listed under **All** and keeps its heat. On the install this was measured on, the scanner findings counted fall by 11 (5 in Marino Management). Nothing is stored or migrated.

**Ranges bounded by distribution package builds are typed (`retype_distro_ranges`).** A bound such as `0:8.7p1-38.el9_4.4` was read as the upstream release. The update step types those stored ranges `RPM` or `DEB` (database only, no request) and marks the CVEs for re-correlation. `python3 manage.py retype_distro_ranges [--apply]`.

**After the update** the sync applies cve.now's changes through its delta listing; its first read starts six hours back. The inventory history import runs within six hours of the first sync and reads up to 300 CVEs a run (`CVENGINE_INVENTORY_IMPORT_PER_RUN`, 0 turns it off). System status `feeds` shows each feed's last success; a feed that has not run yet is not judged.

**Discovery screenshots stored under a name a Sentinel chose are renamed or removed (`neutralise_screenshots`).** Before this release a Sentinel's discovery screenshot was written under the file name the Sentinel sent (`sentinel-<name>`), and the host screenshot route took its type from that name, so a Sentinel could store `x.html` or `x.svg` with PNG bytes up front and have it served as a page of this site (security fix, see the changelog). New screenshots get a name of the server's own (`sentinel-<random>.png` or `.jpg`) and are served only as the PNG or JPEG their bytes are. The update step looks once, by itself, at every stored discovery screenshot whose name does not end in `.png`, `.jpg` or `.jpeg`: a real PNG or JPEG is renamed to a server-made name and the host row follows it; anything else (not a picture, missing, or outside the media folder) is removed and the host's screenshot cleared, so the next discovery or the browser screenshot pass takes a new one. It runs before `rerate_findings`. A dry run by default when run by hand: `python3 manage.py neutralise_screenshots [--apply]`.

**OpenVAS behaviour and policy checks no longer confirm the CVEs they only list (`recheck_openvas_reference_checks`).** An OpenVAS NVT that identifies no product and no version (it tests a behaviour: "HTTP Debugging Methods (TRACE/TRACK) Enabled", 1.3.6.1.4.1.25623.1.0.11213) was already kept from confirming CVEs of several vendors, but a CVE whose CVE List record says `vendor: n/a, product: n/a` (CVE-2005-3398) passed as one vendor: the match was a template hit, its triage was floored to confirmed, and a correct AI verdict was overruled. The update step reads every OpenVAS match an NVT confirmed again, by itself and once, and one whose NVT is generic for its CVEs loses the confirmation as a fresh import would store it (no template result, version range unknown, the import's unconfirmed confidence, `generic_check` in its evidence); its triage row starts over and the next triage pass judges it without the floor, and the hosts are rescored. The OpenVAS finding itself stays: the NVT did see the behaviour. It also un-confirms what a **policy check** confirmed (issue 414): a protocol, cipher or end-of-life detection lists CVEs as references ("SSL/TLS: Deprecated TLSv1.0 and TLSv1.1 Protocol Detection", QoD 98, confirmed BEAST and FREAK), and a protocol CPE's version (TLS "1.0") is cleared from the match. The step runs as `recheck_openvas_reference_checks`, so an install that already ran the narrower recheck runs it again. To preview or run it by hand: `docker compose exec -T web python3 manage.py recheck_openvas_reference_checks` (a dry run that lists the matches) and `--apply`.

**VMware ESXi builds and other version script output become readings (`backfill_version_scripts`).** nmap's version scan runs the scripts of its version category by itself, and since 1.4 the ports keep what they printed (`version_scripts`), as text only. `vmware-version`'s ESXi release and build (`VMware ESXi:7.0.3-21930508`), `amqp-info`'s, `docker-version`'s and `wdb-version`'s product versions are now version readings (`vsrc:nmap`, [PIPELINE.md](PIPELINE.md#version-category-scripts)), and VMware ESXi CVE ranges are read by build (VMware names each fix by its build), which needs no change to the stored CVEs. The update step reads the stored output once, by itself, with the firmware hint of the stored runZero blocks, and correlates the hosts that moved and every host whose port or technology names VMware ESXi. runZero's services (product and version per port, from its services export) arrive with each project's next runZero sync; a token that cannot read that export still syncs the rest and says why under the sync's counts (`services_error`). By hand: `python3 manage.py backfill_version_scripts [--apply]`. No migration, no new variable.

**AI-written checks closed only because no scanner could check them go back to validation (`revalidate_ai_drafts`).** A check the AI had written was closed as `invalid` when no Sentinel could run its syntax check at that moment ("not validated: no scanner could take this work ... tried again later"), and that row then held its CVE for `TEMPLATE_GEN_CVE_DAYS` while nothing tried it again. A new draft now waits for its check in the `syntax` stage instead. The update step, by itself and once, gives each such row back to the automatic validation as a draft (due at once, with a fresh expiry window and no try used) when its text still passes the static check, it is the newest such row of its CVE, its CVE has no other draft or valid check and no revision was made of it; the rest stay closed (one whose text fails the static check now says so). A draft never runs on a host: only every automatic gate promotes it, and each gate that asks the AI is a reviewer job billed as usual (with automatic validation off, the drafts simply wait). The same step names every closed row that had no reason (a static-check rejection or a failed provider call stored only the output) and reads a reason that was a tool's warning line ("WARNING: sonic/ast only supports ...") again without it. To preview or run it by hand: `docker compose exec -T web python3 manage.py revalidate_ai_drafts` (a dry run that counts the rows) and `--apply`. No migration, no new variable.

**Validation planning and nuclei targeting are AI jobs.** The last two pipeline stages that called the AI provider from a Celery worker now queue an AI job the reviewer container answers, as triage does ([AI-REVIEWER.md](AI-REVIEWER.md)). A validation request waits for its plan in the queue (at most ten minutes, then the deterministic plan), and a scan's targeted nuclei pass runs on the static table at once and uses the AI's choice from the next pass over the same hosts. Nothing to do: no migration, no new variable. With the reviewer container off (`CVENGINE_REVIEWER=0`) both run as with no AI.

**The triage sweep runs every hour.** It ran once a day at 04:41 UTC, so a finding a probe, a version source, a KEV re-read or a provider error left waiting waited up to a day; 0173 moves `cvengine-triage-sweep` to minute 41 of every hour. Its caps are the same (`TRIAGE_MAX_PER_RUN`, `TRIAGE_MAX_PER_PROJECT_DAY`, `TRIAGE_MAX_PER_DAY`), so the AI spend per day does not grow: the questions are only asked sooner.

**Check afterwards**

1. `docker compose ps` shows `scanner` (healthy once it heartbeats) and `reviewer` running, and **Scanners** shows **CVEngine Scanner** with a Built-in chip, checking in. System status (`GET /api/v1/system/status`) has `scanning.builtin_scanner.live: true` and no **Scanner offline** problem.
2. `docker compose exec -T web python3 manage.py migrate --check` exits without complaint.
3. After a scan starts, the activity feed shows work handed to the Sentinel, and `docker compose exec celery sh -c 'pgrep -af "nmap|naabu|testssl|wpscan|bbot" || echo none'` prints `none`.
4. The About page lists the software the install is built from, with versions.

## Upgrading to 1.3

Update from 1.2.x the way you always do: the in-app updater, `scripts/update.sh`, or automatic deployment ([UPDATES.md](UPDATES.md)). Nothing in 1.3 needs a manual step to start working, and a fresh install needs none of this. The update takes a database dump just before it migrates (`scripts/db-backup.sh`, the last 3 are kept; see [UPDATES.md](UPDATES.md)) and a migration is never rolled back, so that dump is the way back, in particular from the migrations that drop legacy tables (below). The dump stays on the same disk as the database, so copy it elsewhere too, and back the database up yourself first if you can.

**Before you start**

- **Free disk space.** The update rebuilds the image (a few gigabytes) and pulls the current `nginx:alpine` for the proxy. The 1.3 safeguards below do not apply to this one update, because an update is applied by the scripts of the version being replaced ([UPDATES.md](UPDATES.md#branches-and-releases)): make sure at least 6 GB are free where Docker keeps its images.
- **The update into 1.3 is applied by the scripts you have now.** The approval updater of 1.2.1 waits for running scans with no time limit (use **Stop all** on the **Scans** page of each project, or `scripts/update.sh --stop-scans`, to shorten that), visitors see an error page while the services restart, the replaced image stays on disk (`docker image prune` removes it), and success is judged by Docker saying the services run. The database dump is the exception: it is taken by `scripts/update-deploy.sh` (or by `update.sh` itself, which runs the fetched copy of itself), which the update reads after merging, so this update has it. From the update after this one, 1.3's other scripts apply: a disk check, the maintenance page, a check that the web service answers, image cleanup, and a 5-minute drain limit for the approval updater.
- A server installed before v1.2.0 still needs its one manual update first ([Upgrading to 1.2](#upgrading-to-12)).

**What changes in the database.** The migrations add, apart from a few that drop legacy schema (see [Dropped legacy tables and columns](#dropped-legacy-tables-and-columns)): a new app (`agentapi`, migrations 0001 to 0007: agents, Sentinels, their tasks and settings), `dashboard` 0026 to 0030, `startScan` 0021 to 0023, `scanEngine` 0005 and 0006, `recon_note` 0002, `targetApp` 0005, and `cveFeed` 0082 to 0117 (there is no 0101). They add tables for saved searches, runZero, Tailscale, host inventory, probe observations, stored sign-ins for authenticated checks, PDF report exports, OpenVAS, suppliers and internal ranges, plus new columns and indexes, and scheduled-task entries for the new sweeps. Besides schema, four things are written:

- `dashboard` 0030 switches the **Nuclei templates** policy on for an install where nobody ever changed it (the audit log records every change): see below.
- `cveFeed` 0092 rewrites the stored reason of old "invalid product correlation" closures to "different product".
- **Automation that uses an API token or MCP**: since 1.4 a token (an agent) may lower and narrow but not raise or widen. It gets 403 for switching secret validation on, declaring an internal range, lifting an exclusion, approving or reinstating an agent or Sentinel, making an internal Sentinel enrollment, storing a service key or a target's stored sign-in, switching on `inventory.create_hosts`, switching updates to automatic, and applying, releasing or reverting an auto-tuning decision; `ai_test` and `ai_models` are limited to 6 an hour per token. A person does these in the web interface. The full list is in [AGENT-API.md](AGENT-API.md#settings-through-the-mcp-app-admin).
- Every existing API token gets the full scope, except the token of a Sentinel enrolled earlier: `agentapi` 0006 narrows it to the `sentinel` scope. The new reporter tokens are separate.
- `agentapi` 0007 gives every Sentinel a network (`external`, or `internal` when it had declared `network:internal`), because the server, not the Sentinel, now decides that.
- `scanEngine` 0006 encrypts the stored proxy list.
- The new schedules are created enabled, except the OpenVAS sweep, which is created **disabled** and only the OpenVAS switch turns on.

**What starts, and what does not.**

- The stack is the same six services (`db`, `redis`, `web`, `celery`, `celery-beat`, `proxy`) on the same ports (443, 8082, and `127.0.0.1` for 8000 and 5432). `docker compose config --services` on a plain 1.3 install lists exactly those six.
- **Tailscale and OpenVAS are off by default.** They are Compose profiles (`tailscale` and `openvas`, 1 and 15 services). Without `COMPOSE_PROFILES` in `.env`, an update neither creates nor starts them, and `make up` and the updaters never start a profile service. OpenVAS also has no scheduled work while it is off. Turn them on only if you want them ([TAILSCALE.md](TAILSCALE.md), [OPENVAS.md](OPENVAS.md)).
- Two empty volumes are created for the celery container even with both off: `tailscale_status` and `openvas_gvmd_socket_vol`, mounted read-only. The proxy now also mounts the maintenance page and `config/nginx/state`, and pulls its image on every `up`.
- Sentinels, internal ranges, authenticated checks, suppliers, runZero, saved searches and reporter tokens do nothing until someone sets them up. A project with no Sentinel pays nothing for the dispatch code.

**Defaults that change behavior**

- **The whole Nuclei template library is now the default scan scope.** Before, scans ran only the templates that make plain GET, HEAD or OPTIONS requests. The migration turns the new default on for an install where no App Admin ever changed **Settings, Scan policy, Nuclei templates**; an install where one did keeps its choice. Validation uses the same switch, so automatic and on-demand validation can send requests other than plain reads. Denial-of-service templates stay excluded and AI-written templates stay read-only. To keep the old behavior, turn the switch off after the update (it was under **Scan engines** in 1.2; that tab is now **Scan policy**, and an old `#engines` link opens it).
- **Checks that send credentials are off, on a new and on an upgraded install.** Nuclei's `default-login` and `bruteforce` templates no longer run, and the targeted pass never picks them, until an App Admin turns on **Settings, Scan policy, Allow checks that send credentials**. If your scans relied on default-login checks, turn it on after the update.
- **Automatic Sentinels follow a commit cvENGINE names; with nothing newer to name, that is the commit this server pins.** A Sentinel on Automatic (or one you asked to update) is always told its target. With "Keep Sentinels on the newest version" on and the Sentinel behind, the target is the newest build; with that switch off, or when this server cannot read GitHub, it is the build this cvENGINE release was tested with, never anything newer. With the switch on and the newest build known but this Sentinel's build not yet compared with it (the first hour after it changed version), nothing is named until the check knows: the tested build is often older than what the Sentinel runs, and its updater refuses to go back. A Sentinel with no target named reports "waiting: the server named no target" (once a day) and no longer "update failed" every hour. Sentinels older than the `credential_filter` client get no nuclei web work until they are updated.
- **Matches need hard evidence, and old name-only matches close themselves.** A CVE match is made only when the product is the same one the advisory names and its version is inside a bounded range (or a template hit, a distribution verdict, a host inventory report or runZero backs it). A product seen without a version is listed as an **Unverified product** on the host instead. After the update, within about half an hour (the next run of the 30-minute guidance task or the next correlation), the open matches that rest on a name alone, an operating-system fingerprint, a different product, or a local-only CVE are closed with a stored reason ("Closed automatically: no version evidence"), the affected hosts are rescored and the counts drop. A match is never closed if anyone worked it (a status other than open, an assignee, a comment, a manual validation request, an AI "affected" verdict) or if it has a template hit, a distribution "vulnerable" verdict, a runZero report or a host report. Version probes then look for the missing versions, and matches return where a version proves them.
- **The UDP scan is on by default** (`CVENGINE_UDPSCAN=1`): 18 ports, 20 packets a second, one address at a time, each address once a week, riding the background full port scan's schedule. Set `CVENGINE_UDPSCAN=0` to turn it off. It needs the worker to open raw sockets; if it cannot, it says so in the activity feed and does not scan.
- **New background sweeps are on by default**, each slow, polite, paused by the global pause, and skipped for a project whose bug bounty engagement has not confirmed automated testing: the TLS audit (testssl.sh; no environment switch, `CVENGINE_TESTSSL_MAX_TARGETS` caps it), other sites on an address (`CVENGINE_VHOST`), applications under subdirectories (`CVENGINE_SUBDIR_APPS`), cloud storage exposure (`CVENGINE_BUCKETS`), and third-party suppliers (`CVENGINE_SUPPLIERS`, nothing to do until a supplier is listed). The version and identity probes run inside each scan on up to `CVENGINE_PROBE_MAX_HOSTS` hosts. Expect more findings and a little more traffic to your own hosts. The background full port scan and the UDP scan are deferred, instance-wide, while any project still has a host missing its first pass.
- **Sentinel tokens expire.** A Sentinel's token has the scope `sentinel` (the Sentinel routes only, not the rest of the API or MCP) and lasts 90 days; a heartbeat renews the same token in place when under 60 days are left. A Sentinel that was off for more than 90 days is enrolled again. `network:internal` is granted by the server (Where it runs, at provisioning or in the Sentinel's settings), never by what a Sentinel declares. A Sentinel client older than this release keeps working but cannot enforce the template policy: update it from the Sentinels page.
- **Stored sign-ins need a verified certificate.** The in-process route check verifies TLS on its credential-bearing connection. Nuclei cannot verify TLS on that connection, so its signed-in HTTPS pass is withheld unless the owner explicitly enables **Trust this certificate anyway** for that credential. Anonymous Nuclei checks still run. A signed-in Nuclei pass never runs on a Sentinel.
- **The proxy under Settings now applies to scans.** The web probes, nuclei, bbot, WPScan, testssl.sh and wafw00f on this server leave through it; nmap, naabu and the UDP sweeps stay direct, and private, link-local and tailnet addresses skip it unless `CVENGINE_PROXY_PRIVATE=1`.
- **A CVE with no version range is a review item.** It makes a *version unknown* match: Needs validation, lowest heat, a small capped share of the host score, never announced as a new Fire match and never sent to the model.
- **The bug bounty gate works per host** and covers the full port sweep, UDP, the weekly deep nuclei lane, the thorough WPScan pass and OpenVAS ([BUG-BOUNTY.md](BUG-BOUNTY.md#the-scan-gate)).
- **Local models get a reply limit (a later 1.3.x release).** `CVENGINE_AI_MAX_TOKENS` now applies to Anthropic too, and a self-hosted server (vLLM, LM Studio, Ollama) is sent 2048 tokens by default, 400 for a finding triage, where it was sent none. A reasoning model that thinks before it answers can end at that limit with no answer: raise `CVENGINE_AI_MAX_TOKENS` or turn its reasoning off ([Local models](DEPLOYMENT.md#local-models)). The same release adds twelve additive migrations (`cveFeed` 0129 to 0134, `dashboard` 0031, `targetApp` 0006 and 0007, `agentapi` 0008 and 0009, `startScan` 0025) and needs no manual step for them.
- **The update recreates the `db` container once, and workers run as many tasks as they are set to (a later 1.3.x release).** PostgreSQL's `max_connections` is now 300 (`POSTGRES_MAX_CONNECTIONS` overrides it), which changes the `db` service's definition: expect a restart of a few seconds before the migration, once. Workers used to run one task at a time under a gevent autoscaler bug; they now run up to their ceiling, each task holding a database connection. The classic worker's default ceiling (`CLASSIC_CONCURRENCY`) is 10 instead of 20. With many hosts, raise **Hosts assessed at once** (Settings, configMaxxing) to 16 to 24 so Sentinels stay busy.
- **New agents are held back only for a recent administrator's decision (a later 1.3.x release).** An App Admin's new agents are never held back; for others a suspended or revoked agent holds back its user's new agents for `CVENGINE_AGENT_HOLD_DAYS` days (default 30, `0` means no limit). An agent that is still held by the old rule must be reinstated once; a revoked agent can now be deleted.
- **Purge the certificate lookup queue once (a later 1.3.x release).** Messages already in `ctwatch_queue` carry no expiry or marker, so the new bound (`CVENGINE_CT_BACKLOG_MAX`, default 500) does not shrink an old backlog. After the update, run in the celery container `celery -A reNgine.tasks purge -Q ctwatch_queue -f`, and once more after a worker restart (messages a worker holds for their ETA return to the queue then). Nothing is lost: the sweep re-derives its work from the `ct-watch` ledger.
- **bbot no longer live-verifies found credentials (a later 1.3.x release).** Its `trufflehog` module is off in every bbot mode. `CVENGINE_BBOT_TRUFFLEHOG=1` turns it back on for a deep discovery of a project with no bug bounty engagement; a bug bounty project never runs it, whatever the setting.
- **The Live screen has a background refresher (a later 1.3.x release).** A new `live_cache_queue` is consumed by the existing classic worker. If that worker looks starved, set `CVENGINE_LIVE_REFRESH=0` and restart: polls are then computed by the request that finds a snapshot stale, as before ([Configuration](CONFIGURATION.md)).
- **Smaller changes.** A host that crashes OpenVAS three times in a row is set aside for three days. Project API keys can be set and deleted by project administrators only. One paste of exclusions is capped at 100 lines. A host inventory report matches a scanned host by its name alone (`CVENGINE_INVENTORY_STRICT=1` brings the address check back). The per-project counts in the system status are reused for `CVENGINE_STATUS_CACHE_SECONDS` (60 by default).
- **Hosts that never resolve to a scannable address are archived** after `CVENGINE_TTL_UNRESOLVED_HOST` hours (default 72, which is 3 days) of an unbroken streak, and restored automatically if they come back. A name that resolves only into a private network counts like any other name that cannot be scanned from this server; it is archived too and looked at again daily. The streak starts counting after the update.
- **AI guidance for CVEs.** Settings, AI model has a new daily budget, "CVE guidance written by the model per day", 25 by default. With an AI model configured, that is up to 25 paid requests a day; set it to 0 to turn it off. The rule-written guidance for every CVE has no AI cost and finishes on its own after the update.
- **Tools are pinned** (nuclei, naabu, bbot, testssl.sh, python-gvm and others), and on x86-64 the image installs the nmap project's own release binary instead of compiling nmap. The build is minutes faster on x86-64 and the same on arm64, where nmap is still compiled. The image now contains a browser (Playwright's headless Chromium, about 300 MB): rebuild it (`make up` does) or screenshots stay off with a note on the host page. `CVENGINE_SCREENSHOTS=0` turns the whole feature off (default on). New worker queues (`wpscan_queue`, `testssl_queue`, `bucketscan_queue`, `vhost_queue`, `udp_queue`, `openvas_queue`, `supplier_queue`, `ctwatch_queue`, `screenshot_queue`) are consumed by the existing classic worker, which `CLASSIC_CONCURRENCY` sizes.
- **Settings changed.** There is no API vault tab (the instance-wide Chaos key is a line on the API keys page; the Netlas and HackerOne keys keep working but have no page), BinaryEdge is retired (a saved key is kept, shown as retired and never used), and **Settings, Reports** only sets report branding.

**Manual steps.** None are required. These are choices:

- To keep scans read-only as in 1.2, turn off **Settings, Scan policy, Nuclei templates**.
- To turn a new sweep off, set its variable in `.env` ([CONFIGURATION.md](CONFIGURATION.md#scanning)) and run `make up`.
- If you want a Tailscale node or OpenVAS, follow their guides. Neither is started for you.
- If the approval updater needs a longer drain limit than 5 minutes, put `CVENGINE_UPDATE_DRAIN_SECONDS` in `.env` ([CONFIGURATION.md](CONFIGURATION.md#updates)).
- **Updates no longer wait for scans on Sentinels.** From the update after the one that delivers this change, an approved update pauses the queues, lets work on this server settle for at most a minute and rebuilds; the Sentinels keep what they finish (a durable spool, 6 hours by default) and hand it over when the server is back, where it is adopted into the host data ([UPDATES.md](UPDATES.md#updates)). *Wait for scans to finish before updating* in Settings, Updates brings the old drain back. A Sentinel needs the matching client (this change is in the Sentinel repository too) to spool for hours; an older Sentinel still releases a result it cannot deliver after about two minutes, and the stage runs it again. The change adds migration `cveFeed.0157_scancontrol_update_window` (three nullable columns on the scan control row).
- Sentinels run from their own repository and are enrolled from the Sentinels page, which also needs the new 1.3 server.

**Check afterwards**

1. **Settings, Updates** shows the new commit as installed and no problem, and `docker compose ps` shows the six services running and no `openvas-*` or `tailscale` container.
2. `docker compose exec web python3 manage.py migrate --check` exits without complaint.
3. **Settings, Scan policy** shows the Nuclei switch the way you want it.
4. After half an hour, the open CVE count has fallen and closed matches say "Closed automatically" with a reason. Open a few hosts: technologies without a version appear as **Unverified products**.
5. **Activity** shows the new sweeps starting over the next day, and the system status (`GET /api/v1/system/status`, or the MCP tool `get_system_status`) has no new problem. If it says the worker cannot open raw sockets, the UDP scan is not running.
6. **Settings, Resources** shows the memory budget keeps up; raise `CELERY_MEM_LIMIT` if new work waits for memory.

## Upgrading to 1.2

An update takes a database dump, applies the migrations (a migration is never rolled back; when one fails the update says what state the database is in and keeps the dump, see [UPDATES.md](UPDATES.md)) and ends every session once, so everyone signs in again. Three protections are new-install only, because an update cannot switch them on without recreating services:

- **Redis password.** New installs generate `REDIS_PASSWORD` and every service uses it. An older install without one gets one by itself at its next update (1.3.4 and later) or `make up`: Redis is recreated with it together with web and the workers, and the tasks queued at that moment are lost once. `make redis-auth` still does the same by hand.
- **Secret-encryption key.** New installs generate `CVENGINE_FIELD_KEY` in `.env`. An older install keeps reading its stored secrets with the key derived from `web/secret` until you run `make rotate-field-key`, which re-encrypts them under a new key and keeps the old one as `CVENGINE_FIELD_KEY_PREVIOUS` until you have a backup taken after the rotation. Back up `.env` and keep it apart from database dumps.
- **Web interface certificate.** A 10-year certificate made by an earlier installer is replaced once by the first automatic renewal check after the update, with a 397-day one (same key, same authority, same names); from then on it renews itself 30 days before it ends ([Deployment](DEPLOYMENT.md#https)). Nothing has to be copied to browsers again.
- **Certificate authority key.** An authority made by an older version keeps an unencrypted `ca.key`. To replace it, delete `ca.key` and `ca.crt` in `secrets/certs` and run `make certs`. Browsers then need the new `ca.crt`.

The in-app updater of a server installed before v1.2.0 has no watcher, so Approve does nothing there until you run `cd /opt/cvengine && git pull --ff-only && sudo scripts/install-updater.sh` once ([UPDATES.md](UPDATES.md)). On an install with its own Compose overlay, update with `scripts/update.sh` or the in-app updater, never `make up`.

## Accepted host names

The current release accepts only the host of `DOMAIN_NAME`, loopback (for health checks), and the names in `CVENGINE_ALLOWED_HOSTS`. Any other name gets **400 Bad Request** on every page. Before you update:

- Reached by the name in `DOMAIN_NAME`: nothing to do.
- Reached by another name or an IP address: add each to `.env`, comma separated, and run `make up`: `CVENGINE_ALLOWED_HOSTS=scanner.internal.example,192.0.2.10`.
- `DOMAIN_NAME` unset or still an example value: set it to the server's public name.

`python3 manage.py check` prints warning `cvengine.W001` when `DOMAIN_NAME` would leave only loopback accepted. Do not use `*` on an Internet-facing installation.

## Shared provider domains

An earlier build promoted a tenant such as `acme.jfrog.com` to `jfrog.com` in the weekly deep-discovery sweep. The update's migration deletes targets that sweep created on the shared-domain list, with their scans, hosts, and findings, because that data was outside your scope. A shared domain you added yourself is kept and set to `host` scope. Deleted targets do not come back on rollback, so back up first if you want that data.

## Dropped legacy tables and columns

The update's migrations delete schema that nothing writes or reads any more, since the old classic screens and the legacy `/api` routes are gone. The data in them is deleted with them and is not restored by a rollback of the code, so the database backup the update script takes before migrating is the way back:

- Tables: the old per-target **Organization** (`targetApp_organization`, not the organization/project tenancy), the classic **To-do notes** (`recon_note_todonote`), **Wordlist**, **Configuration** and the interesting-keyword lookup (`scanEngine_wordlist`, `scanEngine_configuration`, `scanEngine_interestinglookupmodel`), the old GPT vulnerability reports and **S3 bucket** results (`startScan_gptvulnerabilityreport`, `startScan_s3bucket`) with their link tables.
- Columns: `startScan_scanhistory.cfg_out_of_scope_subdomains`, `cfg_starting_point_path`, `cfg_excluded_paths` and `cfg_imported_subdomains`, and `cveFeed_cveentry.raw` (the cve.now entry stored a second time; the modelled columns already hold what is used).
- The scan report no longer has an "Interesting subdomains" section: its keyword list could only be filled in through the Django admin.
- A later 1.4 update (`dashboard` 0037, `scanEngine` 0008, `startScan` 0027) drops nine more tables nothing reads or writes: the OpenAI, Netlas and HackerOne entries of the old key vault (`dashboard_openaiapikey`, `dashboard_netlasapikey`, `dashboard_hackeroneapikey`; the AI model's key lives in **Settings, AI model**, discovery keys in **Settings, API keys**, and a HackerOne submission uses the person's own credentials under **My accounts**, so a key stored in these entries was never used), the Ollama settings the AI layer never read (`dashboard_ollamasettings`), the search history, per-user preferences and in-app notifications of the classic screens (`dashboard_searchhistory`, `dashboard_userpreferences`, `dashboard_inappnotification`), the classic HackerOne report settings (`scanEngine_hackerone`) and the classic tool command log (`startScan_command`, the command lines and output of reNgine-era tool runs on the server). `PUT /cve/api/settings/keys` now knows only `chaos` and ignores the other names. The instance Chaos key, scans, hosts and findings are untouched.

Scans, targets, hosts, findings and CVE data are untouched. A tool of your own that read one of these tables or columns needs the backup, or its data taken before the update.
