# Changelog

cvENGINE is a fork of [reNgine](https://github.com/yogeshojha/rengine) 2.x. The history of reNgine up to the fork is in [its changelog](https://github.com/yogeshojha/rengine/blob/master/CHANGELOG.md).

## Unreleased

### Added

- **Scan concurrency is a setting: Settings, configMaxxing, Scan concurrency.** A user running cvENGINE locally asked how to scan more than one target at a time; the only controls were environment variables (`HEAVY_MAX_<KIND>`, `DISCOVERY_CONCURRENCY`, `CVENGINE_WORK_DEPTH`) and the web interface showed none. Settings has a new **configMaxxing** section for advanced tunables (App Admins only, collapsed until opened and remembered per person, at `/cve/settings/#configmaxxing`, with a warning that changing these can make scans slower, use more memory or send more traffic to your targets), built as a small registry of cards so more of the environment-only settings can move there later; Scan concurrency is its first card. It has a number for each local scanner kind (nmap, nuclei, bbot deep, standard and passive, naabu, route probes and the rest, 1 to 8, with a lower ceiling for the memory-hungry kinds), **Hosts assessed at once** (`DISCOVERY_CONCURRENCY`, 1 to 32) and **Hosts per assessment batch** (`CVENGINE_ASSESS_BATCH`, 1 to 64) and **Discovery scans kept running** (`CVENGINE_WORK_DEPTH`, 0 to 32). Each shows its default, the allowed range, the value from the environment if one is set, who saved it and when, and has **Reset to default**; **Reset all configMaxxing settings to defaults** resets the section. The page shows the scanning container's memory budget (`CELERY_MEM_LIMIT`) and warns when the chosen limits could want more than twice of it; the memory gate still holds work back either way. A saved value wins over the environment, which wins over the built-in default. The scanner limits and the conductor's depth apply within seconds with no restart (saved in the database, published to Redis, cached 5 seconds in each worker; without Redis the environment and defaults apply as before). The discovery pool is resized live with celery's `autoscale` remote control and the page shows the ceiling the worker reports (an autoscaler ceiling on a gevent pool, not an exact cap), or says that it has not confirmed the change and the number takes effect after the next restart or update; `celery-entrypoint.sh` reads the saved value at every start. The three-hour AI review stays inside the saved number (it becomes the top of the tuning range unless `HEAVY_TUNE_MAX_<KIND>` gives more room), and saving a number for a kind clears the review's last step for it. Every change and reset is audited (`scan_concurrency.set`, `scan_concurrency.reset`, `config_maxxing.reset_all`). It is a session-only settings API (`/cve/api/settings/scan_concurrency`) and is not part of the agent REST API or MCP. Migration `cveFeed` 0131 adds the table; nothing changes until a value is saved. New guide: [Scan more targets at once](docs/DEPLOYMENT.md#scan-more-targets-at-once), with safe values by machine size.
- **An alias and a note on targets and hosts.** On a network where most hosts have only an address, every list, search result and report showed bare IPs. A target and a host can now carry an **alias** (a short display name, one line, up to 60 characters) and a **note** (free text, up to 1000), set from **Alias** on a target row of the Targets page, from the host's **Asset info** on the Hosts page, over REST (`POST` or `PATCH .../targets/{id}/profile`, and `alias` and `note` on `.../hosts/{host}/profile`) and over MCP (`set_target_profile`, and `alias` and `note` on `set_host_profile`), with the same checks as the other writes (a role above audit, a token that is not read only) and an audit entry for each change. The alias is shown beside the address, never instead of it, in the Targets and Hosts lists, the host page, the gallery, the CSV export, the Ctrl+K search, the graph's tooltips and cards, and the PDF reports (the report page also prints the note); the address and the names a scan discovers are unchanged. The Hosts search, the target list and the all-projects search match them: a bare word and `host:` read the alias, and `alias:` and `note:` filter on them. A host's alias lives with the project's record of the host name, so it survives rescans, and when several names on the same addresses are one host, the alias of any of them shows; a host that is its own target (an address added as a target) falls back to the target's alias. Migrations `cveFeed` 0130 and `targetApp` 0006 add the four columns with an empty default. A host or target without an alias is unchanged.
- **The hygiene check now flags cleartext administration services (#282).** A MikroTik with Telnet (23) and FTP (21) open read "0 certificates, 0 issues", because hygiene covered only TLS and mail DNS. It now reports, from the ports the scans already stored and with no probe of its own: Telnet (`cleartext_telnet`), FTP when nmap did not read a certificate over AUTH TLS (`cleartext_ftp`, worded "unencrypted unless TLS is enforced", since a scan cannot prove a server refuses plain logins), rexec, rlogin and rsh on 512 to 514 (`cleartext_rservices`), and a login page the route check saw over `http://` on a host with no HTTPS service (`cleartext_http_login`). Telnet, FTP and the r-services are medium on an internal host and high on a public one (judged from the address, as the host score does); a login over plain HTTP is low and medium. One finding per host and check names every port and address; closed, filtered and unanswered ports, TLS tunnels (`telnets`, `ftps`), excluded and archived hosts, CDN edges and tailnet addresses (the Tailscale check already covers those) are never findings. They are ordinary hygiene findings: remediation status, assignee, comments, triage, reports (a "Cleartext services" group), the host score, the Hygiene page (a new Area filter), `list_hygiene_findings` (`check=cleartext`) and `GET projects/{slug}/hygiene` list them like the others, and they appear at the next hygiene run. `CVENGINE_HYGIENE_CLEARTEXT=0` turns the check off (default on): none is made and the open ones resolve at the next run. Not included: SNMP v1 and v2c in general, which needs an SNMP request the stored data does not hold (the UDP sweep already reports the default `public` community). No migration.
- **How an AI request is made is now a setting, for every provider (Settings, AI model: PR 2 of 3, the page itself follows).** The request timeout (10 to 3600 seconds), the connect timeout (1 to 300), the reply limit (64 to 32768 tokens, for every stage), Ollama's context window (512 to 1048576 tokens), structured output (`auto`, `all`, `off`), reasoning (`default`, `off`, `low`, `medium`, `high`, `max`) and Ollama's keep-alive (`30m`, `1h`, `0`, `-1`; a duration is sent as a string, `0` and `-1` as the integers Ollama accepts for them, because it refuses the string "-1" with a 400) were environment variables in `.env` (and keep-alive was not settable at all), so changing one meant editing a file and restarting. They are now stored with the AI settings (`GET` and `PUT /cve/api/settings/ai`, App Admins only; migration `dashboard.0031`, all nullable or empty). **An empty setting follows the environment variable of the same name, then the provider's default, so an install that sets none sends the same request as before** (the Anthropic, OpenAI, Ollama, vLLM, LM Studio and OpenRouter request bodies and timeouts are unchanged, and a test compares each against the fixed body written out); **a saved value wins over the variable**, so a change in the browser is not undone by an old `.env` line. Values are checked against their range when saved (a bad one is a 400 that names the field and stores nothing, including the other fields of the request) and again when used, so a row edited by hand cannot send what a provider would refuse. The response says, per setting, the value in force and where it comes from (`effective`: setting, environment variable or default), what the environment sets (`env`), each provider's defaults (`provider_defaults`), the ranges, and which settings only apply to some providers (`context_tokens` and `keep_alive`: Ollama). A key is still write-only and still dropped when the provider or host changes; a metadata address is still refused. Each change is recorded in the audit log as `ai.settings` (the names of what changed, and the new value of the numbers and words, never a key or an address).
- **A failed AI connection test says what to change.** "Connection failed: anthropic HTTP request failed (status 401)" is now followed by a sentence by kind of failure: the key was refused, the provider is rate limiting, no answer in N seconds (N is the timeout in force, with the setting to raise), the server could not be reached (inside Docker, `localhost` is the Docker host), the address is not an AI API, the model name or path is wrong, the reply was cut off at the reply limit, or the model answered with nothing (a reasoning model that spent the limit thinking). What the provider said is never repeated. A connect timeout is told apart from a slow answer (it names the Connect timeout and the address, not the Request timeout). The test waits at most 240 seconds whatever the Request timeout is, because it runs inside a web request that the web server ends at 300 seconds, and the result says so. A triage reply cut off at a reply limit already at the 32768 ceiling is no longer asked a second, identical, paid time. A stored provider this version does not know no longer breaks the page or the test.
- **An opt-in reasoning control: `CVENGINE_AI_REASONING` (`off`, `low`, `medium`, `high`, `max`).** Unset, which is the default, every request is byte for byte what it was. Set, it is applied the way each provider takes it: `reasoning_effort` for OpenAI's o-series and gpt-5 models; adaptive thinking with an effort (`thinking: {"type": "adaptive"}`, `output_config.effort`, never `budget_tokens`, never a temperature, top_p or top_k) for Claude 4.6 and later; `thinking` with a `budget_tokens` of at least 1024 and below the reply limit for Claude 3.7 to 4.5; a top-level `think` for Ollama's qwen3, deepseek-r1, gpt-oss and magistral models. vLLM, LM Studio and OpenRouter are sent nothing (set it on the server). A model that has no such control, or a level that is not valid for it (`off` for a Claude model that cannot disable thinking), ignores the setting and says so once in the log. Thinking is paid from the reply limit: raise `CVENGINE_AI_MAX_TOKENS` with it. Configuration and Deployment document each mapping.
- **A Base URL for Anthropic and OpenAI in Settings, AI model.** The field was hidden for both although the code honoured it. Optional, empty uses the vendor's own address; set it for a gateway or proxy (LiteLLM and others), which then receives the key. It is checked like the other providers' (http or https, no link-local or cloud metadata address). For Anthropic a bare address or one ending in `/v1` is the server (the messages endpoint is added); an address with another path is used as written, as before, and `localhost` is mapped to the Docker host as for the local servers. Choosing another provider in the form no longer carries the previous provider's address along.
- **One capability table for the AI providers** (`reNgine/ai_profiles.py`: label, transport, default address, key and URL needs, reply limits, which stages may pin temperature and seed, the structured-output steps, the reasoning mechanism by model name). The provider lists, the model choices and the reply-limit defaults are derived from it, and a test holds them to what they were. No request changes.
- **The chunks of one scan stage now run in parallel across Sentinel slots (`CVENGINE_STAGE_PARALLEL`, default 4).** Even with hosts batched, a stage sent its chunks to a Sentinel one at a time (`wrap_nuclei_stream`, the naabu runner and `try_nmap` each looped over 64-address chunks, and the nuclei technology pass first split its targets 100 at a time), so one scan kept ONE Sentinel slot busy: on a project with several slots, or two Sentinels, most slots idled while a 66-host scan walked a chain of about 40 two-to-four-minute tasks. `agentapi.sentinel_dispatch.dispatch_many` now creates a window of chunk tasks up front and waits for all of them in one poll loop, applying each result as it lands and refilling the window as chunks finish. The window is the smallest of the chunks left, the slots the stage holds plus the project's free slots, twice the instance's slots shared among the scans dispatching, and the setting; free slots are re-read at every refill. The nuclei passes hand the Sentinel wrapper 64 x the setting targets per call (256 by default) and write the ledger after each call. A chunk that fails or expires falls back to local execution alone, no live Sentinel (or none that claims) stops the fan-out, and a stop or global pause expires every outstanding chunk task. `CVENGINE_STAGE_PARALLEL=1` is the old serial behaviour, task for task. Applies to nmap, naabu and the nuclei technology, targeted and deep passes (internal ones too); testssl, UDP and WPScan are one host per task and unchanged. See [Pipeline](docs/PIPELINE.md#sentinel-dispatch) and [Configuration](docs/CONFIGURATION.md).

### Changed

- **The Live screen's polls share their answers, and an unchanged poll costs almost nothing (stage 0 of the live-screen caching).** The headline numbers (`/cve/api/stats`) and the ticker counts (`/cve/api/discovery`) were cached in a dict of each web worker, per user: with two workers and ten people, twenty copies of the same walk over the inventory were recomputed every ten seconds, which is what made a busy moment end in a Cloudflare 502. They now live in the shared cache (Redis), keyed by *scope*: a hash of the project ids the request runs under (an App Admin hashes every project, so a new project changes the key, and never shares with a member), plus the selected project and organization. Two members of one project share one entry, and two scopes never read each other's. One request at a time recomputes a stale entry (it takes a short lock; the others serve the stale copy, kept three times as long as it is fresh, or wait up to two seconds on a cold key), a closed finding (`bump_stats_revision`) makes every entry stale at once, and a cache that does not answer never breaks a poll: it is computed directly, as before. The running and queued scan counts of the headline poll stay fresh on every poll (five queries, one fewer than before: the running window is read once), the graph's version token (`/cve/api/graph`) is kept five seconds per scope, so the 304 path stops paying eight aggregate queries per poll, the graph payload is shared by every viewer of the same projects, and `/cve/api/graph-live` is a two-second snapshot per scope instead of five queries per tab every three seconds. Measured on a small fixture, with the authentication floor (9 queries for a member) included: a warm headline poll 14 queries (15 before), where the cold walk (37 to 39) now runs once per scope per ten seconds instead of once per tab, user and worker; a graph version poll 9 instead of 17; a graph-live poll 9 instead of 15.
- **Unchanged answers are `304`s.** The stats, graph-live, discovery and activity endpoints, the Sentinels live overview (`/api/v1/sentinels/live`) and the scans list (`/api/v1/projects/{slug}/scans`) send an `ETag` and answer `If-None-Match` with `304 Not Modified` and no body, with `Cache-Control: private, no-cache` (not `no-store`, which would forbid the conditional request). The ETag of a snapshot is computed once when it is built, so a 304 does not rerun the walk; clocks that move every second (`now`, `at`, each scan's `elapsed`, `server_time`, `seconds_since_seen`) are left out of it, and the graph page counts a scan's elapsed time from its start instead.
- **The Live pages poll politely.** A new shared module (`static/cve/poll.js`) replaces four bare `setInterval`s (the dashboard's scanning-now chips, the graph page's SOC highlight, the Sentinels page and the scan notifications on every page) with one request at a time that re-arms itself when the last one finishes; every wait is jittered by 0.85 to 1.15, a hidden tab does not poll (the scan notifications slow to a quarter of their pace instead of stopping, and ask at once when the tab returns), the wait doubles up to 16 times while requests fail, and a `Retry-After` on a 429 or 503 is honoured. The shared `get` sends `If-None-Match` per URL and treats a 304 as "unchanged", so the page skips the parse and the redraw. The Sentinels page asks for a Sentinel's detail (settings, version, update) only when its row in the live list says it moved (a new `revision` field, with a two-minute safety net), not every fifteen seconds for each Sentinel.
- **The proxy compresses JSON, scripts and styles.** `config/nginx/rengine.conf` turns gzip on for `application/json`, JavaScript, CSS and SVG above 1 KB (`gzip_vary on`, `gzip_proxied any` because a CDN adds a `Via` header to every request). HTML is deliberately left alone (BREACH: pages carry the CSRF token), and images and archives are already compressed. The updater already recreates the proxy on every update, which picks the new file up.
- **The Sentinels overview looks the viewer's projects up once** (it asked six times per poll: for the queued count, the OpenVAS queue, the organization groups and the task redaction). What each viewer sees, and the redaction of another tenant's tasks, are unchanged.
- **A bare `sk-...` key is no longer taken for an OpenAI key.** First-run setup guessed OpenAI for any `sk-` key of 20 characters or more, so a DeepSeek or other OpenAI-style key pasted there was sent to api.openai.com. Only a prefix that names one vendor is now recognised (`sk-ant-` Anthropic, `sk-or-` OpenRouter, `sk-proj-` OpenAI); any other key makes setup ask which provider it belongs to, and nothing is sent until you choose (the connected provider is no longer tried on a new key either; it is still used when no key is pasted). The `sk-svcacct-` and `sk-admin-` forms are asked too. A Google `AIza` key is still not recognised.
- **A stored key follows the host, for every provider.** Changing the provider or the host of the Base URL already cleared the stored key; the comparison now reads the effective address, so the vendor's own address counts as a host (adding a gateway's address to OpenAI or Anthropic, or removing it, clears the key), the port and scheme count, and a host spelled in another case or with a trailing slash does not. The same rule decides whether the model list may use the stored key.

### Fixed

- **`ctwatch_queue` no longer grows without bound (regression of #272, which gave certificate lookups their own queue).** The sweep (`watch_certificates_all`, every 20 minutes) queued up to an hour of lookups each time with no memory of what it had queued; the ledger row that tells it a domain is done is written only after a successful crt.sh fetch, so a lookup that was queued but not yet run, or that failed, was queued again at the next sweep. The only consumer is the classic worker, shared with WPScan, testssl and others and paced by crt.sh, so any slowdown became a backlog that never drained (one install went from 14,167 to 15,357 messages in 27 minutes). Past 20,000 messages in any queue the reaper's orphan recovery (redispatching queued scans, expiring orphaned running scans) stops, and Redis has no memory limit. Now: the sweep reads the backlog first and queues nothing at `CVENGINE_CT_BACKLOG_MAX` (default 500, or one sweep's batch if that is more), otherwise only what fits under it, oldest first; every publish sets a per-domain marker in Redis (`SET NX`, so the sweep and Add targets, single or bulk, never queue the same domain twice, and a Redis outage queues as before), cleared when the lookup ends, and a domain with a marker does not use one of the sweep's places; every message expires (its interval, or 6 hours when queued by adding a target), retries included; a lookup that ends in failure (its retries used up, a retry that would start after the message has expired, or an error such as a reply over 32 MB or a timeout) is recorded as `ct-watch-failed` and left out of the sweep for 6 hours (`CVENGINE_TTL_CT_WATCH_FAILED`); the system status shows the backlog (`queues.ct_backlog`) and lists a problem above 5,000. Adding targets in bulk is not held back by the backlog cap (it is a person's request); it is bounded by the marker and the 6 hour expiry. The worker inspection note on the health page now says which worker did not reply within 5 seconds and which replied without its queue.

  **Upgrade note: purge the existing backlog once.** Messages already in `ctwatch_queue` carry no expiry or marker, so the fix does not shrink them. After the fix is deployed, run in the celery container: `celery -A reNgine.tasks purge -Q ctwatch_queue -f`. Nothing is lost: the sweep re-derives the work from its ledger (`ct-watch` rows). Messages a worker is holding for their ETA are not in the queue and return to it when the worker restarts (`requeue_unacked`), so run the same command once more after a restart.
- **A KEV match is no longer validated again after every rescan (issue 338).** One finding was validated 83 times in six days (about five a day, three AI calls each, the same answer every time). Four causes, all in how a rescan's new match row finds the validation its predecessor already has. (1) The twin lookup (`triage._twins`) took the row with the newest `updated_at`, and a template run writes `validated_at` and `updated_at` on every Triage row of the CVE on the host, the rows of superseded matches included, so the new row took an old match as its twin and `carried_from` pointed at an old job. The twin is now the row of the newest MATCH of the same project, host, CVE, source, product and version, and a template run writes only the rows of the host's current matches. (2) `enqueue` looked at the new row's own inherited validation only when no earlier job was known at all, so one old job that counted for a day (the AI could not answer) hid a validation minutes old: it is now looked at whenever the match has no job of its own. (3) A validation moved its own match's signature (the probe results and earlier checks it stores are part of the host context the signature is made from) and the job had recorded the signature from before its checks, so the next sweep took the finished job for one of other evidence and queued the same match again (jobs 4750 and 4752 of the report): the job now records the evidence it answered for when it ends. (4) A match a later scan had replaced could still be queued, and one replaced while its plan was being asked for still ran its checks, template draft and final review: both are now skipped (the match is checked before queueing and again before the checks and before the review). A real change still validates at once (a KEV listing or new score, a new version, a new template result, a changed source) and so does **Validate now**; the protection against lifting a version-only match above its ceiling is untouched. New safety net: `CVENGINE_VALIDATE_MIN_GAP_HOURS` (default 12, `0` turns it off) allows at most one automatic validation per host, CVE, product and version in that time unless the evidence changed. Not changed: the port and the web fingerprint match of one CVE on one host (two findings with different evidence, each with its own record and review) are still validated once each, because one validation cannot stand for both reviews. No migration. Reported by camstork in issue 338.
- **The running and queued scans lists no longer cost a query per row.** Each row read the timing settings (`running_window()`) to decide whether a running scan is stalled: 51 of the 65 queries of the running-scans list that every page polls for scan notifications (`/api/v1/projects/{slug}/scans?status=running`), and the Scans page lists paid the same. The window is now computed once per list, so the lists cost the same with two rows or with a thousand (16 queries for a member).
- **A Sentinel is kept busy by a backlog of hosts instead of ~5 one-host pipelines (hosts are now assessed in batches).** With 800 hosts of one project waiting unscanned, its one Sentinel ran about 2 of its 3 slots and its task queue was empty: the feed created one assessment per host, each a one-host pipeline whose Sentinel stages (naabu, nmap, the light nuclei pass, WPScan, the targeted nuclei pass) sent one tiny task and waited for it, and only about five such pipelines ran at once (`DISCOVERY_CONCURRENCY`, shared with discovery). The feed (`feed_sentinels`, the coverage top-up and the refresh of the stalest hosts) now groups the due hosts of one target of one project into a single pipeline run of up to `CVENGINE_ASSESS_BATCH` hosts (default 8, 1 to 64, `1` is the old one-host-per-run behaviour), so every stage hands a Sentinel tasks that name many hosts (nmap and naabu 64 addresses at a time, now sending every chunk of a longer list to a Sentinel instead of only the first, nuclei in chunks). Each host still has its own assessment row, status, `last_assessed`, coverage, attempt streak and Live/Activity lines, and its own outcome: a host whose DNS does not answer, that has no scannable address, or that a gate (exclusion, archive, scope, bug bounty confirmation) drops ends alone and the others go on; the run fails only when no host is left; a stage that fails is every host's, because the scan is shared. The caps now count pipeline runs (a batch is one), so the hosts in flight are at most the caps times the batch size; the per-run and per-project limits still bound the number of pipelines. A host-scoped target, an address typed as a host every host of a project no live Sentinel covers (that work runs on this server, where nmap and nuclei are held to a few at once) and every host of a project that a Sentinel narrowed to named hosts (`scope.hosts`) covers always run alone (a task naming many hosts is claimable by a Sentinel any one of them is in the scope of), and **Rescan host** and `assess_host` stay one run per host. Stopping one host's assessment of a batch stops its run (the others it carried are settled as stopped and are due again at the next sweep); the stuck-job reaper gives a batch six hours per four hosts, never beyond the discovery queue's time limit (twelve hours when task limits are off). One AI triage cap, `CVENGINE_TRIAGE_MAX_PER_RUN`, is per scan and so now per batch (it was per host): the overflow stays queued for the next triage pass. Not measured here: the real throughput gain on a live Sentinel (only the Sentinel's own slot use shows it). No migration. See `docs/CONFIGURATION.md`.
- **The discovery mode chosen for a target is kept, and the work conductor no longer rescans every target in standard.** The Add targets dialog's Passive ("public sources only") and "Just add them, do not scan yet" choices applied to the first discovery only: nothing stored them, so the work conductor started a standard discovery (which sends traffic to the target) of a passive target as soon as the minimum gap had passed, and of a "just add" target in its first round, and a deep target was rescanned in standard. The mode is now stored on the target (`discovery_mode`: standard, deep, passive or manual; migration `targetApp` 0006 gives every existing target standard, so nothing changes for targets added before this) and set by Add targets (dialog, REST `mode`, `add_target`, `add_targets`, `add_targets_by_org`) and by a Discover that names a mode. The conductor, the AI assessment review, a moved target and the Tailscale sweep scan each target in its own mode and never wider; the weekly deep sweep skips passive and manual targets (and their apex rows); "Just add them" is stored as manual only, which no automatic path scans, certificate transparency included (new names under it are recorded but their hosts are not fingerprinted). The Targets page has a Discovery column to change the mode, also `POST projects/{slug}/targets/{id}/discovery-mode` and the `set_target_discovery_mode` tool; changing it starts nothing. Discover and Scan on a target now run in its stored mode, and on a manual only target answer `409` until a mode is chosen. An unknown `mode` is now `400` instead of silently becoming passive, and `mode: manual` is accepted by the add calls. An add with no `mode` stores standard, with or without `discover`, so an integration that adds with `discover: false` and relies on the conductor to scan keeps working. Reported by camstork in issue 284.
- **A soft 404 page that names the path as a bare word is now recognised as a catch-all.** The comparison with a made-up path took the requested path out of a page only with its slash (`/admin`), so a page that says `The page "admin" could not be found`, or a title like `admin - Portal`, differed from the page for the made-up name and the route stayed open (10 of 10 routes on a server that echoed the bare name, 8 of 10 with the echo in the title, whose login routes stayed login pages). The path is now taken out with and without its slash, as the last segment, the whole path or the file name without its extension, in any case and percent- or form-encoded, as a whole word only (`administrator` stays). A real page with its own content on the same template is still another page. Known limits, not changed: a short login-style single-page shell with a small rotating value can leave routes as login pages, and a real `/admin` of about 40 words on a 600 word shell that is also the soft 404 template is read as the template at the 0.9 similarity threshold.
- **The route check's extra requests are bounded for a whole host.** The requests that ask what a missing page looks like were capped per web base (8), so a host on two bases was asked up to 12 on top of its 20 routes with no number in the code for the total. A host is now asked at most 12 of them over both bases and `MAX_REQUESTS_PER_HOST` (32) in all, which a test counts against a local server (a front page's own scripts are read besides). `MAX_URLS_PER_SCAN` still counts routes only.
- **Migration 0123 says what it does.** It only ages the route check's ledger to 60 days; it changes no route row. A route stored as open by a version before the soft-404 comparison stays open, and stays a candidate for scoring and hot validation, until its host is probed again, which the next discovery scan of that host does (the work conductor starts the stalest targets first, so how soon depends on how many targets there are and on `CVENGINE_WORK_DEPTH` being above 0); the probe stores `catch_all` over it without a change event.
- **`CVENGINE_AI_MAX_TOKENS` now applies to every provider, and local models get a reply limit by default.** It did not reach Anthropic (always 2048). It now does, and the default request to Anthropic is byte for byte what it was. A self-hosted server (vLLM, LM Studio as `max_tokens`, Ollama as `num_predict`) is sent 2048 when it is unset, and 400 for a finding triage (the answer is a short JSON object; 300 cut off 14% of them on a local model); a value you set replaces both. A triage cut off at its default limit is asked once more with twice the limit. OpenAI and OpenRouter are still sent none unless you set one (`max_completion_tokens` for OpenAI's own API). **A reasoning model that thinks before it answers now ends at the limit: turn its reasoning off or raise `CVENGINE_AI_MAX_TOKENS`.** The OpenAI provider with another Base URL is not treated as self-hosted (a proxy may front a hosted reasoning model): use the vLLM provider for llama.cpp, LiteLLM or any other OpenAI-compatible server. New `CVENGINE_AI_CONNECT_TIMEOUT` (default 10 seconds, 1 to 300): the 10 second connect limit applies to the connection only, the wait for the answer is still 120 seconds (Anthropic). A "Local models" section in Deployment gives the context size, reasoning, JSON output and what a cut-off reply does.
- **A Sentinel's operating system guess is no longer withheld from the AI on a Docker Desktop install.** The host context dropped every guess when this server's own path was distrusted, including one a Sentinel measured on its own network. A guess now carries where it was made (`os_source`: `nmap` for this server's scanner, `sentinel`), a guess from this server's scanner is withheld on a distrusted path with the note saying why, and a Sentinel's or the machine's own report is kept (`CVENGINE_OS_DETECTION=distrust` still withholds all). boot2docker and moby kernels (docker-machine, the early Docker for Mac) are recognised beside linuxkit, WSL 2 and OrbStack. A VM with an ordinary distribution kernel (Colima, Podman machine, Rancher Desktop on macOS) cannot be recognised by name, and the daily path measurement needs three hosts on three /16 networks, so a lab that is one LAN gets no verdict and detection fails open (Deployment says so).

## v1.3.1 (2026-10-30)

**The camstork edition.** Every fix in this release answers an issue written up by one reporter, camstork, with the code path, the measurements and, for several of them, a tested patch: thank you.

### Fixed

- **A Celery worker no longer loses the log lines of some modules.** The logging configuration switched off every logger that already existed whenever it was applied, and it is applied again when a worker starts (Django's own setup, then Celery's). The AI provider errors (`reNgine.ai_providers`), the AI template writer, the field encryption and the init module therefore logged nothing in a worker. Existing loggers are now kept (`disable_existing_loggers: False`). The same switch-off made three logging tests fail now and then, depending on which tests shared a process.
- **Moving a target now keeps its history.** Move host used to delete the host's findings, notes and state and discover it again in the new project, and refused a target that held other hosts. A target moved to another project of the same organization is now pointed at it with everything it holds (scans, hosts, findings, CVE matches, notes, labels, triage), asking first when it holds other hosts, and the next scan updates the same records. A single host under a larger target, and a move to another organization, still start from scratch.
- **`-example.com` in Add targets no longer returns a 500.** A whole-domain exclusion deleted the targets in one transaction while queued runs started new scans of them, and the commit failed on a foreign key. The exclusion is now committed first, so nothing starts a new scan of those names, and a removal that a running scan got in the way of is retried (then answers 409, not 500).
- **A bbot crash or time limit part way no longer hides what it found.** A discovery that is cut short after it found hosts keeps them and the scan goes on with them (nmap and every later stage run); the discovery stage is recorded as failed, with the reason, in the scan's failed stages, and it does not count as a finished discovery for other targets. A failure that found nothing still fails the scan. (A change merged earlier failed the whole scan, and a failed scan's hosts are not the domain's current inventory.)
- **Hosts scanned through naabu now get an operating system.** nmap's OS detection needs an open and a closed port, and the pass over naabu's open ports alone has no closed one, so with naabu on (the default) no host was ever fingerprinted. Two nearly always closed ports are added to that pass; the top-up pass over ports a Sentinel missed gets none, so it cannot replace the Sentinel's own guess with a weaker one. Measured against real nmap.
- **A Sentinel's tarpit address is no longer clipped into a believable port list.** The server cut a Sentinel's naabu list for an address to 500 ports before the tarpit check (more than 500 open ports) could see it, so the check never fired for Sentinel results and a host that answers on every port was stored with 500 invented open ports. The address now keeps `null` (or the full list) and nmap falls back to its default ports, as for a local naabu pass.
- **A failed validation step of a check that is no longer planned no longer keeps a finding failed for ever.** It would have been retried every day without ever being replaced.
- **More of nmap's real product names are recognised when a version is re-checked** (Tomcat's "Apache Tomcat/Coyote JSP engine", "Node.js Express framework", "VMware ESXi SOAP API", Go, Python, Cisco IOS), after a stricter product match stopped them reaffirming a CVE.
- **A host matched by CVEs in several chunks of an hourly threat-intelligence update is rescored once**, not once per chunk.
- **A Sentinel no longer sits idle once every host has been scanned.** Every Sentinel stage is dispatched from inside a host assessment, and the once-a-minute feed only created assessments for hosts missing their first pass, so with nothing due ('No hosts are due') nothing reached a Sentinel at all. The feed now also queues the stalest hosts for a fresh assessment (the ones assessed longest ago, none inside `CVENGINE_SENTINEL_REFRESH_GAP_HOURS`, 6 by default), up to the same Sentinel-scaled cap, so the Sentinels keep doing the scanning and this server only falls back to doing it when a Sentinel cannot.
- **Old scans are now deleted after 180 days (a change to what is kept).** Every scan stores its own copy of every host it found, and nothing removed them, so the inventory tables only grew. A daily run now deletes finished scans older than `CVENGINE_SCAN_HISTORY_RETENTION_DAYS` (180 by default; `0` keeps everything), with the host copies, findings and matches of that scan. It never deletes a scan whose hosts are in a domain's current inventory, one of a domain's newest three scans, one that is not finished, or one holding work a person did (a remediation status, a note, an assignee, a comment, or an audit event, which also covers a status that was changed and set back to open). The first run after the update clears the backlog over several days; `python manage.py prune_scan_history --dry-run` shows what would go. Set the variable to `0` before updating to keep everything.
- **A Sentinel that keeps failing one kind of work is no longer handed it again and again.** A Sentinel whose nuclei is killed (exit -9, out of memory) or whose tool is missing took each task of that kind, failed it, and left the server to run it anyway after the round trip. After three failures of one kind in a row the kind is withheld from that Sentinel for 15 minutes and this server runs the work at once; then one more task is tried, a success clears it and a failure withholds it again. The Sentinels page says which kinds are withheld and until when. `CVENGINE_SENTINEL_KIND_FAIL_STREAK` and `CVENGINE_SENTINEL_KIND_COOLDOWN_MINUTES` (`0` turns it off) set it.
- **A hung task can no longer hold a worker slot for ever.** Celery tasks had no time limit unless a few declared one, so a socket with no timeout or a subprocess that never exited kept its slot until the worker restarted. Each queue now has a hard limit: the scan queues the longest that is safe (just under the broker's 12-hour redelivery window, because their tasks may wait hours for memory before they run), the API and notification queues half an hour, `run_command` an hour. OpenVAS keeps its own 24-hours-per-host budget. `CVENGINE_TIME_LIMIT_<QUEUE>` tightens or removes one; a task's own limit is kept.
- **Updating from a branch that is not a release is now flagged.** Any branch can still be tracked (a fork's own, develop on a test server), but when it is not `master` or `main`, Settings, the Approve dialog and the update banner say so, and the audit entry of the approval records the branch and that it was not a release branch. `CVENGINE_UPDATE_BRANCHES` still refuses other branches outright.
- **The capacity review lowers a scanner's cap for load failures, not for configuration errors.** A failed stage counted against its scanner whatever the message said, so a missing template library or a policy refusal could step Nuclei's concurrency down, with no effect on the failure. Failures are now read as capacity (a memory wait that ran out, a timeout, a kill by the kernel), configuration, or neither; only capacity failures above 15 % of a kind's runs lower its cap. The review record shows the counts of each, and says when a kind's failures look like configuration.
- **A validation request whose match a rescan replaced while it waited is skipped, not failed.** The queued job found its match gone from the current inventory, raised an error, spent a retry attempt and was logged as a worker failure. It is now marked skipped (no attempt spent, no retry), and the replacing match is validated by the next sweep, which no longer counts the skipped job as handling it.
- **The project you picked follows you to every page.** With All projects chosen on Live, Sentinels, Settings, Agents and About opened on the first project in the list, and their sidebar links pointed at it. The session now remembers the last project (or All projects) you opened and a page with no project in its address shows that choice; a project you can no longer see is forgotten.
- **All projects can be narrowed to one organization.** With two or more organizations, choosing an organization and then All projects showed every organization's projects, and there was no way to see all the projects of one organization together. The switcher now sends the organization with All projects, the browser session remembers it for the section links, the pages with no project and the polls that do not name it, and the combined REST lists (`_all`), the dashboard data and the asset graph follow it (a token caller names it per call with `?org=`). An organization the caller has no projects in is ignored, so the view is never wider than the caller's access and never empty.
- **Internal scans read the organization's own IP rows.** The internal TLS audit and UDP sweep looked an address up by address alone, so two organizations that share a private address could read or store results on each other's row. They now look it up inside the scan's organization, as the nmap stage already did.
- **A scanner is stopped when Celery's hard time limit cuts its task short.** On the gevent pool the limit interrupts the task without the usual timeout exception, so the memory reservation was released while nmap or nuclei was still running and another scanner could start beside it. The scanner's process tree is now stopped first.

- **The CVE feed no longer ends up with holes, after a seed or after any outage.** A new install imports a seed and then the incremental sync reads what is new, but the CVEs published between the snapshot and the first sync were in neither, and the same happened whenever a worker was off for a while or a backlog was bigger than one run read; the coverage check said "covered" because the seed holds entries from 1999. The feed now keeps a watermark (`FeedWatermark`): everything published after it has been read. A seed sets it to the newest publication time it holds (new `covers_through` in its manifest). The hourly coverage run reads the feed back to three days before the watermark (the feed lists by publication time, and an entry can arrive more than a day after it), stores everything it lists, and only then moves the watermark to the head it started from. A run cut short by its limits continues from the same page next time, a failed fetch never moves the watermark, and a walk that reached its floor is not repeated for six hours. `get_system_status` reports how far the feed is complete and whether it is behind. Reported by camstork (#207).
- **A patched release is no longer reported as vulnerable when an advisory lists one fix per branch.** cve.now publishes some advisories (PHP2Shell is one) as a list of fixed versions with no lower bound: fixed 8.2.35, 8.3.36, 8.4.27 and 8.5.12. Read alone, the fix for 8.4 stood for every older version, so a patched 8.3.36 was reported as vulnerable. When the feed gives that shape, the bounds the CNA itself published (`8.2.*` up to `8.2.35`, and so on) are read from the CVE List record and used, and the CVE is marked as having come from it too. Where that record cannot be read, no lower bound is guessed: each fix is compared only with the releases of its own line (8.3.30 is vulnerable, 8.3.36 is not), a branch the advisory does not list is unknown rather than cleared, and the evidence says that no lower bound was published. Reported by camstork (#205).
- **A branch the CVE List splits in two is read as one range.** The CNA writes some branches as two entries, one with the lower bound (`7.13.0`) and one with the fix (`lessThan 7.13.7`), and the conversion kept two ranges. Read alone, the first said "7.13.0 and every later version" and the second "every version before 7.13.7", so the fixed 7.13.7 and 7.18.1 and everything between matched (CVE-2022-26134, Confluence: 43 entries of the feed, 14 of them in KEV, among them several Junos advisories). A range that has only an `introduced` bound is now joined to the `fixed`-only range right after it when the fix is newer, in correlation, in WordPress plugin matching and in the ranges the AI is shown; an `introduced` range with no fix after it stays open. Reported by camstork (#205).
- **A server that answers every path no longer makes every route look open.** NAS web interfaces, single-page apps, WAFs and servers that send every path to a login page answer a route and a made-up path alike, so every probed route (`/admin`, `/wp-login.php`, `/actuator/health`) was stored as open and fed the host score, the heat and hot validation. The route check now does what directory scanners (ffuf, feroxbuster, dirsearch) and Nikto do: it asks for a path that cannot exist beside each route, in the same directory and of the same kind (a bare name, a directory, or the same file extension), at most eight extra requests per host, and compares status, content type, where a redirect leads and the page itself with what changes between two requests taken out (the requested path, ids, nonces, times); a page that still moves is compared word group by word group, and must also share its title and its sign-in form, so a real login page on the same template stays a login page. A route that gets the missing page's answer is stored as **Catch-all**, with that answer in its evidence, and is left out of scoring and validation. The front page is never compared, a mount whose subpaths answer alike is still a route, no change event is raised for a route that was open before, and the next scan of each host reads its routes again. Reported by camstork (#213).
- **A rescan no longer sends every CVE match back for validation.** A rescan makes new host rows and so new match rows, which started with no record: the matches were judged and validated again, every rescan, although nothing had changed (about 3,300 validations a day for 580 unchanged matches on one install). A new match for the same project, host and CVE now takes the verdict, classification, reason and validation result of the one before it as long as the asset evidence is the same, and remembers which match that was (`Triage.carried_from`). Its validation job history carries over too: a job that failed for good is not started again at attempt one by every rescan, a backoff and the attempt count go on, a job finished inside the window (a day when the AI could not answer, otherwise seven) stands for the new match, and the history is followed through scans that queued nothing. Only a changed signature, a feed update or an expired window asks again. The lookup reads one row per finding (a record not touched for 30 days is asked about again) however many scans have run. Reported by camstork (#206).
- **A version number alone no longer makes a finding "likely affected".** A CVE match that stands on a version string inside the advisory's range, with no template hit, no distribution tracker listing, no host-reported inventory and no runZero report, is needs validation at most, whatever the model says (it used to be stored as affected, which made it Fire, showed it as "AI confirmed" and kept the sweeps from closing it). This is enforced in code, as a ceiling next to the existing floor, and not only in the prompt: a model's stated certainty is not calibrated and a version banner is the weakest evidence there is (a distribution backports fixes without changing it). The prompt still tells the model to abstain, so its reasons and remediation text read the same way. Answers stored before the ceiling are brought in line when a worker starts, with no model call and no re-ask; a validation hit still confirms. Reported by camstork (#210).
- **A private address no longer counts as a public IP.** `is_private` is set when an address is stored, the score and the host page read it, and the ranges are the same ones the scanners refuse (documentation ranges stay public). The title of the issue said more than the code did: only the scoring and the label were wrong. Reported by camstork (#212).
- **Operating system detection now checks its own network path, and Linux installs get a way to fix it.** nmap's operating system guess only holds if its probes cross the network unchanged. Docker Desktop's network stack answers them for itself (an Ubuntu server and a NAS were stored as Google Fuchsia, an iDRAC as Apple OS X), and measured with real Docker, the default bridge network on Linux also loses the malformed probe (a NAS ranked above the real Linux guess, and `-sN`, `-sF`, `-sX` scans break). Once a day cvENGINE now sends a plain probe and a FIN+PSH+URG probe to a closed port on a few hosts it already scans and records whether the path is `direct` or `interfering`; Docker Desktop is also recognised from the VM kernel. On such a path a packet guess is not stored or shown to the AI, guesses stored earlier are removed, and the host is named from what survives any path: the distribution in a service banner, the operating system CPE and `ostype`, and SMB and RDP builds, marked as service detection. The system status page reports the verdict and the remedy. `docker-compose.hostnet.yml` (host networking) and `docker-compose.macvlan.yml` (its own LAN address) take the translation out of the scanner's path on Linux, and both give exact results in a real run; Docker Desktop cannot, so a Sentinel on a Linux machine is the answer there (a Sentinel on Docker Desktop reports `os_reliable: false`). `CVENGINE_OS_DETECTION` overrides the check. See Deployment, "Operating system detection and the scan path". Reported by camstork (#214).
- **Local and OpenAI-compatible models are first-class providers.** `CVENGINE_AI_TIMEOUT` (10 to 3600 seconds) and `CVENGINE_AI_MAX_TOKENS` (64 to 32768, unset by default) apply to every provider, and reaching the server has its own 10 second limit so a server that is down fails at once. The reply limit is named for the address, not the provider (`max_completion_tokens` only for OpenAI's own API, `max_tokens` behind a proxy). A triage reply cut off at a limit you set is asked once more with twice the limit; a reply with no text at all (a reasoning model that never answered) is its own error, `empty_response`, and not a schema error. Triage on a self-hosted server runs at temperature 0 with a fixed seed. Triage requests carry a JSON Schema built from the validator's own constants where the server takes one (vLLM and LM Studio as `response_format`, Ollama as `format`; `CVENGINE_AI_STRUCTURED` = `auto`, `all` or `off`): a server that refuses it is asked in JSON mode and then without, remembered for an hour, and hosted providers are not sent it by default. `CVENGINE_OLLAMA_NUM_CTX` sets Ollama's context window, whose default is small on a machine with little memory and silently cuts a long prompt. Reported by camstork (#209).
- **The Nuclei targeting prompt no longer embeds every installed tag, and the short list it offers is the right one.** The prompt listed all of the installed tags (about 9,000, 41,000 tokens), which a model with a 32k context cannot read. It now lists at most 150, ranked: the static table's tags, then the tags the installed templates of the named product carry (read from the templates' own `vendor`, `product` and CPE metadata, as nuclei's own automatic scan maps technology names to tags), then a tag that is a word of a name, two adjacent words run together ("Spring Boot" and `springboot`, "Palo Alto" and `paloalto`, "PAN-OS" and `panos`), a tag with a part that is, and the generic exposure tags last. An alphabetical cut used to drop the tags of products late in the alphabet and miss concatenated names altogether. Words that name a kind of software and no product (`web`, `http`, `server`, `manager`, `proxy`) match nothing, and the model may not pick `cve`, which would run every CVE template on a host (the targeted CVE checks already run for the CVEs that matched). The answer is still checked against every installed tag. Reported by camstork (#208).
- **A server with commits of its own is compared correctly, and told what to do.** The check asked GitHub how far behind the installed commit is; GitHub has never seen a fork's own commits, answered "not found" and the banner offered an update forever (and Automatic mode approved it again and again, each time refused by the host). Only the host has git, so the host updater now fetches the tracked branch (from `origin` when that is the tracked repository, otherwise from its public address) every half hour and after each deploy, and publishes the commit the build shares with it and the commits on either side (`web/.upstream-state.json`). Settings, Updates then says **up to date** (also with commits of its own on top), **available**, **diverged** (the branch moved and so did this server: no Approve, and the merge to run by hand; automatic mode does not approve it) or **unknown** (nothing says whether it is behind). An approval that cannot be fast-forwarded is refused before scanning is paused. `update.sh` and automatic deployment test whether the remote head is contained in the checkout instead of equal to HEAD, so a checkout that has merged master is level with it and one that has not is no longer backed up and retried every run. The first version of this fix kept a second line in `web/.commit`; that is gone. Reported by camstork (#211).

- **A CVE match now needs hard evidence, so a product name alone no longer produces findings.** A match is made only when the product on the host is the same product the CVE names and its version is inside a bounded affected range (or a template hit, a distribution tracker verdict, the host's own inventory report or runZero backs an existing match). ### Changed

- **An AI closure of a match needs concrete grounds.** A version inside an advisory's range is still a floor the model cannot clear, unless the application verified a ground from the host's metadata: a probe showed a look-alike product (plain nginx is not ingress-nginx or nginx-ui), or a CDN, WAF or hosting edge answers for the host on DNS-level evidence (never a response header the host controls) and the match rests on a web response. A match somebody vouches for is never cleared this way. Then the model's judgement stands; a banner that states no version is never a reason to close or to confirm. A new probe result re-asks the question without erasing the earlier validation record.
- **WPScan's enumeration and exit codes follow WPScan 4.** Plugins are no longer enumerated by default in WPScan 4, so the scan now asks for `ap,at,tt,cb,dbe,u1-10`. Exit code 4 (the scan did not finish) is read from the report's `scan_aborted` text as not WordPress, blocked by an edge, or a failure. A clean WPScan result stays fresh for a week (`CVENGINE_TTL_WPSCAN`, previously a day) and the per-scan site limit is 20.

- **BinaryEdge is retired.** Coalition shut BinaryEdge down as a standalone service on 31 March 2025 and bbot has no module for it, so the stored key could never be used. The API keys pages and the API now say so (`retired`, with the reason, and `used_in_scans: false`), no new BinaryEdge key is accepted, and a key saved earlier is kept, shown as retired and can be removed. The runZero key is now described as read by the scheduled sync rather than "not used yet".

### Fixed

- **Host assessments no longer trickle in one per project per three hours.** The three-hour AI review's `host_coverage_gap` offered the model at most one due host per project per window, so a project that picked up dozens of new subdomains from one discovery run (85 hosts, 83 never scanned, in one real case) drained at roughly one host every three hours, competing with triage, validation and discovery for the single model decision. A new, deterministic sweep (`cveFeed.coverage_topup`, task `top_up_host_assessments`, every 5 minutes, queue `discovery_queue`) tops up every project's host-assessment queue directly, with no model call, up to its free capacity (5 per project, 20 instance-wide), skipping a paused or bug-bounty-blocked project. `host_coverage_gap` is now a single-id view of the new `host_coverage_due(project, at, limit)`, which returns an ordered list of due host ids so the top-up sweep can take more than one per project per run; `assess_host` is no longer offered to the three-hour review's model (triage, validate and discover still are), though `dispatch`'s policy-checked `assess_host` entry point stays in place. `host_assessment.enqueue`'s existing active-row check and `IntegrityError` fallback already stop the review and the top-up from double-queuing the same host; a test now proves it. Needs migration 0104.
- **The new background sweeps respect the bug bounty gate.** The virtual host sweep, the subdirectory application sweep and the TLS audit now skip a project whose bug bounty engagement has not confirmed that automated testing is allowed, as the bucket and UDP sweeps and the work conductor already did.

- **A restart no longer leaves host assessments queued for a task that is gone, or blocks new ones.** The 30-minute re-queue now checks the broker and the workers (queues, unacknowledged messages, reserved, active and scheduled tasks) and leaves a row alone while its task still exists. A queued row whose task is gone no longer counts toward the 20 and 5 host-assessment caps, so "host assessment queue is at capacity" clears without waiting for the reaper. If the workers cannot be asked, nothing changes from before.
- **`get_system_status` no longer reports schedules as past due when beat itself is silent.** Beat writes a heartbeat every few seconds; the schedule list now carries `beat` (`running`, `silent` or `unknown`) and a beat silent for two minutes is reported as one problem ("celery beat has not ticked for N minutes") in place of every schedule being listed as late.
- **An update checks for room first and cleans up after itself.** Each update builds a new image of a few gigabytes and used to leave the replaced one behind, so a server that updated regularly slowly filled its disk and a later build failed half way, after the files were merged and scanning was paused. The updater now checks that there is room where Docker keeps its images (`CVENGINE_UPDATE_MIN_FREE_MB`, default 6144) and says so plainly instead of starting, and removes the replaced image once the update is verified.
- **An update no longer breaks the old containers while it is half applied.** Between the migration and the restart (and for as long as a failed restart is retried) the old code runs on the new schema. Seven columns added since v1.2.1 were `NOT NULL` with no database-level default, so the old code could not insert CVE records, detection records, host exclusions, project settings or API tokens in that time (the CVE feed sync failed at its next run). They now carry a database default (migrations `cveFeed` 0093 and `dashboard` 0029), and the upgrade rehearsal fails any release that adds such a column.
- **An update is not "done" until the web service answers.** After the restart the updater now waits for the web service to answer (a container restarting over and over is "running" to Docker) and checks that no migration is waiting; one that is gets applied, and if it still cannot be the update fails visibly and is retried instead of being reported as done. A failure at this point keeps the new code, as every failure after the migration does.
- **A finding marked fixed stays fixed when the next scan names its product differently.** Hosts are stored once per scan, so a new scan's match inherits the decision a person made about the earlier one, but only when the CVE, host, source and product string were all identical. A feed update that renamed the advisory's product, or the product seen on another port, produced a match under a new label that came back open (CVE-2018-16844 on the VPS). A decision now carries over by CVE and host when no match carries the same label, and the newest decision wins.
- **Queued work no longer waits twelve hours after an update restarts the stack.** Redis keeps a message a worker took and never started in its `unacked` list until the visibility timeout (12 hours here), so an update that killed the workers left host assessments, scans and validations "queued" for half a day while they counted toward the host-assessment limit ("host assessment queue is at capacity", with nothing running). The worker container now returns every orphaned message to its queue before its workers start (`manage.py requeue_unacked`), and the 15-minute reaper queues a host assessment again once it has waited 30 minutes, at most every two hours (a second message for a row that already started does nothing). The system status no longer reports a one-minute schedule as past due: beat records a task's last run only every three minutes, so a schedule is late only after that and a five-minute margin.
- **The Scan engines page did nothing, and every scan was labelled "Full Scan".** The editable YAML engines were inherited from reNgine and no part of the scan pipeline reads them; a scan runs one fixed pipeline whatever an engine says. All six inherited engines were also flagged default, so the first of them filed every scan, one-second host retests included, under "Full Scan". The editor and its create, update and delete endpoints are gone, as is the unused auto-fire engine setting. **Settings, Scan policy** keeps the one real setting that was on that page (let scans run every installed Nuclei template, not only the read-only ones), and an old `#engines` link opens it. Scans are filed under "CVEngine Recommended" and the scan detail no longer shows an "Engine" line. The engine rows, `list_engines` and `engine_id` on start scan stay, marked legacy, so existing agents keep working.
- **System status no longer reports healthy nuclei templates as stale, or a warning as the nuclei version.** The template files only change when a new release is published, so their age said nothing about whether the six-hourly refresh works (four quiet days read as "not refreshed for 87 hours" and marked the instance degraded). The refresh task now records when it last ran, whether it succeeded and the tool's last line; the status judges on that (a failed run, or no success for 36 hours, is the problem) and still shows when the files last changed. The nuclei version is the version line: a warning the tool prints first (nuclei does, on a Go release its JSON library has not caught up with) is skipped.
- **"Invalid product correlation closed" now says what happened.** The activity feed and the match detail called every automatic closure an "invalid product correlation", which reads as a parse failure and was also wrong for the local-only and no-version closures. The wording is now "different product", with the product the host was recorded as and the one the advisory covers (for example `"nginx"` against `"ingress-nginx"`), a one-line summary of the actual reason in the feed, and a badge on the detail page that says "different product", "no version evidence" or "local-only vulnerability" to match. The closures themselves are unchanged. Rows closed under the old wording are rewritten by a data migration (the host and product names in them are not stored, so those say "not one the advisory covers").
- **An update that was interrupted is no longer reported as done.** `web/.commit` is written when a deploy starts (the build needs it), so a run stopped after the files were merged but before the database migration left the new code, that marker and the old schema, and the next approval answered "already at" without deploying: the site then ran against a database that lacked the new tables and columns (MCP and the API returned 500). The updater now treats a deploy as finished only when a host-side record written after the services were recreated names the commit and `migrate --check` finds nothing waiting; otherwise it deploys again, and the log says why. An install that has not recorded a deploy yet rebuilds once on its next approval. To repair a host that is already in this state, run the build, `migrate`, `collectstatic` and recreate steps from `docs/UPDATES.md` ("When the files are new but the database is not").
- **The release gate fails closed.** `scripts/check_tool_versions.py --fail-if-behind` passed when a pin could not be found in its file (a renamed `ARG`) and when every version lookup failed. It now fails on a missing pin or an unreadable newest version too; the weekly report still shows such a row as `?`. The docs list honestly what is not pinned (base image digest, apt packages, transitive Python packages, GitHub Actions by commit, the moving service images), and a leftover `pip install tenacity` that ran at every container start (nothing uses it) is gone.
- **Agents: a busy agent no longer leaves work to a free one for ever.** An agent that heartbeats but never polls could hold a queued task indefinitely because the polling agent kept deferring to it; the deferral now lasts a minute.
- **MCP follows the specification's transport rules.** A browser page of another site (an `Origin` that is not this server's host) is refused, an unsupported `MCP-Protocol-Version` is a `400`, a client's own response is accepted with `202`, an unknown tool is the protocol error `-32602`, and an unexpected error is the JSON-RPC internal error `-32603` instead of an HTML page.
- **Host inventory.** A report that names a scanned host of the project is tied to it by that name; `CVENGINE_INVENTORY_STRICT=1` additionally requires an address in common with the host (a reported address, or the one it came from), otherwise the report waits for an administrator to adopt it. Held Debian and Ubuntu packages (`apt-mark hold`, often the stale ones) are now reported, and the Windows quick start downloads the script with `curl.exe` so a private CA is trusted.
- **Tailscale.** The tailnet-wide findings no longer stay on a device that left the tailnet: they move to another device and the old copies are resolved. The tailworm.com notes now say what Tailscale has actually said (acknowledged, fixes merged, no numbered release or bulletin yet as of 2026-10-27).
- **runZero import no longer adds addresses nobody authorized.** An inventory search such as `alive:true` can hold third-party public addresses, and import turned them into scan targets. A public address is now imported only inside a network the organization already has as a target (skipped as `not_owned` otherwise). A closure of a different-product match whose version is in range stays on that match and is never shared with other hosts. A closed match is not reopened by the next correlation unless new evidence (a version, or the KEV exception above) appears. Checked against real header and nmap XML samples.

Checked against bbot 3.0.2 (55 modules load, the keys appear in the merged preset).

- **Censys, project keys and the vault, made truthful.** The Censys key was also mapped to `censys_ip`, which no scan mode enables; it is now only `censys_dns`, and the page says the key is the legacy Search API's ID and secret. - **An update now refreshes the proxy image, with nothing to run by hand.** The proxy (nginx) is a stock image, `nginx:alpine`, that was never re-pulled, so a host kept whatever nginx it first pulled for as long as it ran (one install was still on 1.29.4, behind the host's own nginx 1.24.0, which is also why the scanner saw two different nginx versions depending on whether it connected by address or by name). The proxy service now has `pull_policy: always`, so every `docker compose up` (the in-app updater, `update.sh`, `make up`) fetches the current image; with no network the update stops before anything is recreated and is retried.

The steps now live in `scripts/update-deploy.sh`, which the updater reads after merging the new files, so an update applies its own steps in the same run (migrations were always applied automatically).
- **After an update, CVE guidance and local-only classification finish on their own.** The first CVE task after an update writes the rule-based guidance for every CVE (no AI cost), classifies local-only CVEs and closes their open matches, in batches within the task's time limit. Only the AI guidance spend stays opt-in, through the budget in Settings.
- **Local-only vulnerabilities are never matched to a host.** A kernel, driver or Win32k flaw (a "Windows Elevation of Privilege Vulnerability", a CVE with CVSS attack vector Local or Physical) is decided by software and patch levels an outside scan cannot see, so matching it to a host from a technology label such as "Windows Communication Foundation" was always a false positive (and the validation requests it started could only end "cannot be established"). Each CVE is now classified `local_only` from its CVSS vector, or, when it has none, from its wording and affected product; such CVEs leave the correlation pool, their open matches are closed ("Closed: local-only vulnerability", the host rescored; work a person did is kept) and they spend no AI budget. - **"Remove & exclude" now removes the host you see.** The Hosts page shows names that point at the same addresses as one host, so excluding only the name on display removed that one name and the next name took its place: the host seemed not to go however often you clicked. - **`scripts/update.sh` no longer refuses to update because of the stack's own ports.** Run by an ordinary user (a member of the `docker` group, not root), `ss` cannot name the process behind Docker's own listeners, so the port check took the stack's published port 443 for "an unknown process" and stopped the update before building anything. - **The nuclei WAF and favicon templates no longer lose what they found.** Real hosts showed a technology named just `WAF` or `DNS WAF` (the template's own name, with the vendor that fired dropped), `favicon-detection` with the icon's hash stored as its *version*, and `AWS Service -`. - **The node2shell / HTTP2Shell check (CVE-2026-111497) looks at every runtime that carries the decoder.** The Brotli decoder is compiled into Node.js, Bun and Envoy, but the check only considered hosts fingerprinted as Node.js or Express. It now also takes Bun, Envoy (and the Istio sidecars built on it) and the frameworks that run on Node (Next.js, Nuxt, NestJS, Fastify, Koa and others), and `CVENGINE_NODE2SHELL_SCOPE=all` checks every web host for what a name cannot show (a Python service using Brotli, a container base image). - **`make redis-auth` and `make rotate-field-key` keep the install's Compose layout.** They recreated services from `docker-compose.yml` alone, the mistake that took a host with an overlay down through the updater. Found by the upgrade rehearsal.
- **`scripts/update.sh` keeps the running stack's Compose layout too.** With no `CVENGINE_COMPOSE_*` setting it recreated the stack from `docker-compose.yml` alone (it only noted the difference), the same mistake the in-app updater made. - **A generic "WAF" label no longer matches a named WAF product.** A host that bbot only labelled "WAF" was matched to the MOVEit WAF advisories because "WAF" is a whole word in that product's name. "WAF" and "Web Application Firewall" are now category labels that identify no product; a host that really is MOVEit WAF still matches. - **Changing the update branch moves the server to it.** Choosing another branch in Settings > Updates and approving used to fail with "not on the branch checked out on this server". ### Security

Fixes from an adversarial review of the whole code base.

- **The legacy findings API no longer returns user rows.** Every serializer in the old `/api/` expanded a finding's `assignee`, `remediation_by` and a scan's `initiated_by` into the whole user, password hash included, to any project member (read-only ones too). All of them now return the username only.
- **Sessions are stored under a keyed hash**, not the cookie value, so a copy of the `django_session` table is no longer a list of working logins. Existing sessions are ended once by the update (everyone signs in again).
- **The Django admin shows no stored secret.** Models with an encrypted field (the API keys, webhook URLs, tokens) leave those fields out of their admin forms and lists, and the key models no longer print their value.
- **A dedicated key for stored secrets, with rotation.** New installs generate `CVENGINE_FIELD_KEY` in `.env`: the stored API keys, webhook URLs, update token and two-step sign-in seeds are encrypted under it instead of a key derived from the Django secret, so reading `web/` no longer yields it and the session-signing secret and the encryption key are separate. Existing values keep reading; `make rotate-field-key` (or `manage.py rotate_field_key`) re-encrypts everything under a new key, with `CVENGINE_FIELD_KEY_PREVIOUS` for the old one and `CVENGINE_FIELD_KEY_FILE` for a Docker secret. - **The sign-in form can no longer be used to guess passwords.** Wrong passwords are counted per address and name, per address and per name (5, 30 and 50 in five minutes); past a limit the form answers 429 before it checks the password, and a right password clears the pair's count. Changing a password uses the same counters, and so does the factory reset.
- **Pasted target lists and searches are bounded.** Parsing a list was quadratic on a long run of `[` and ran before authorization; it is linear now, with size caps for the paste and each token. One request can never add more targets than the cap even when the last range is large, and a search accepts at most 15 terms, 200 characters each, 1000 in all.
- **Wrong-typed API fields give a clean 400** (REST and MCP) instead of a 500 or an exception message, and the bulk remediation call no longer returns raw exception text.
- **`system_status` shows non-admins only whether scanning is paused and the update phase.** Who paused it, why, the last error and the instance-wide running count are for App Admins.
- **Nuclei templates may not use YAML anchors or aliases.** A few hundred bytes of nested aliases hung the safety gate (and could exhaust memory). Installed templates that use an anchor are skipped like any template that fails the policy.
- **Page analysis cannot be stalled by a hostile page.** The generator, script and login-form patterns scanned a page in quadratic time; they now read one tag at a time.
- **Mail-hygiene checks have a budget.** An SPF include tree stops after 50 lookups, and the EPSS feed is refused if it expands past 512 MB.
- **The SSRF filter covers more addresses.** IPv6 forms that carry an IPv4 address (NAT64, 6to4, IPv4-compatible) are judged by that address, and the Azure, Oracle, Alibaba and AWS IPv6 metadata addresses, Teredo, benchmarking and reserved ranges are always refused. Name checks now run in parallel with a per-name timeout and an overall budget.
- **The Netlas key is no longer written to the log, the Command table or the history file.**
- **The two-step sign-in seed is encrypted at rest**, and new recovery codes are 80 bits and keyed with the server secret (codes made before stay valid until you make new ones).
- **A stored AI key is never sent to a changed address.** Saving a different provider or server address without typing the key again clears the stored one, and the model list uses the stored key only for the address it was saved for.
- **Every response carries a Content-Security-Policy** (`base-uri`, `object-src`, `frame-ancestors`, `form-action`), and scan results served from `/protected_media/` are sandboxed and never sniffed. Opening a `#...&validate` link now focuses "Validate now" instead of clicking it.
- **Deployment.** nginx accepts 4 MB bodies (was 800 MB), has header and body timeouts and speaks TLS 1.3; the proxy mounts scan results read-only; the celery entrypoint no longer downloads an unpinned third-party template on every start; the installer uses a private temp file, no longer passes the caller's environment through `sudo`, and reuses a certificate only when it really covers the address; `.env` and the PostgreSQL upgrade dump are created owner-only; the development web port listens on loopback; the workflows run read-only by default, release only from master, and the branch-delete tool refuses odd names and long-lived branches.
- **Nuclei templates refresh every six hours** (04:41, 10:41, 16:41, 22:41 UTC) instead of once a day, unless you changed the schedule.

### Fixed

- **Approve update starts the update within seconds.** The host side was a cron job that ran every 5 minutes, was never installed by `install.sh`, and said nothing when it was missing, so on such a machine the button recorded an approval that nothing read and the orange bar waited for ever. Now `scripts/update-watch.sh` (started by cron every minute, installed by `install.sh` and `scripts/install-updater.sh`) listens for the whole minute and starts the update about two seconds after the approval: scans are paused, running ones finish, the files are updated, the containers restart and scanning resumes. While it waits for scans it checks every 15 seconds and writes each reason once, instead of every call. It reports a heartbeat every 15 seconds, and Settings > Updates and the banner say when the host updater is not reporting and what to run. Existing installs run `scripts/install-updater.sh` once to switch from the 5-minute entry.

- **An approved update that the host cannot start now says why, instead of waiting for ever.** The host script ran from cron with its output discarded, so a checkout with local changes, an unreachable origin, or any command that failed early ended the run without a word and the orange bar said "Waiting for the host to start the rebuild" indefinitely. Now a dirty checkout shows "The update did not finish" with the files named, an unreachable origin shows its reason, any other stop writes the failing line to the update log, and after 12 minutes without a start the bar tells you to check the cron entry and run `scripts/apply-update.sh` by hand.

Also from the review.

- **Targets and IP data belong to an organization.** A domain name was unique across the whole instance, so one organization could find out which names another tracks (by being told "already exists") or block them by adding the name first, and an IP address was one shared row, so the banners and service data one organization's scans found were readable through another's hosts. Now the same name can be tracked by several organizations, each with its own separate record; within one organization a name is still held once across its projects. IP rows and their ports are kept per organization, and nmap's freshness and claims are per project. A migration gives each existing row to its organization and, where two organizations shared an address, splits it into a copy for each (with copies of the ports).
- **A lapsed claim can no longer be extended or deleted by its old holder.** The Redis claims that keep two scans off the same domain, IP or host now extend and release in one atomic step on the server, only while the caller still holds them; a holder whose claim was taken over stops refreshing it (and says so in the log) instead of extending the new holder's, and a claim that expired is taken again when nobody else has it.
- **One row per IP address.** Two scans that first saw the same address at the same moment each saved a row, and every later scan that reached that address then failed. A migration merges existing duplicates (keeping subdomain links, ports and facts), the database now refuses a second row, and creating an address, technology or subdomain no longer raises when two workers race.
- **An OpenSSL-style patch letter is no longer dropped from a version.** `1.1.1k` and `1.1.1n` compared equal, so a host on 1.1.1k looked fixed by every advisory that names 1.1.1n. One or two letters after a three-part version (`1.0.2k`, `0.9.8zh`) now order the version; `8.9p1` is unchanged.
- **CVE List wildcards (`2.3.x`, `<= 3.1.x`) name a whole branch** instead of the bound `2.3`, which missed 2.3.5.
- **A scan of one host no longer hides the rest of the inventory** from correlation and from the daily rescore; both read the same current inventory as the host list.
- **A malformed `affected` entry from the CVE feed cannot stop correlation.** Entries that are not objects, and ranges that are not a list, are dropped when the feed is read and again when the index is built. Two sightings of one product on one host keep the stronger evidence, not the last one saved.
- **An operator's pause is the operator's own.** Pausing while an update holds the pause converts it, so the finishing update does not resume scanning; resuming clears the update flag, and resume is refused while the update script is draining or applying.
- **Long banners from a scanned host cannot cost an nmap chunk**: every text value is clipped to its column and one bad port no longer drops the rest.
- **A hygiene finding marked fixed that comes back is reopened**, with a note, instead of staying hidden.
- **A bounty scope entry longer than the column is shown as text** instead of aborting the sync.
- **The findings list no longer fails on 29 February.**
- **Detection accuracy.** CVEs that arrive with no affected-product data are refreshed again for 90 days instead of staying blank; version ranges the CVE List gives only as text are read; CPE and product-name spellings (`Apache httpd`, `OpenSSH_9.6`) resolve to the same product; a match a template or validation already confirmed stays open when a later scan sees a different version; a changed product on a port resets the stored version; portable patch levels (`8.9p1`, `8.9p2`), date versions and MariaDB's `5.5.5-` banner prefix compare correctly.
- **Rejected CVEs are closed** and never matched again, the CVSS score is taken from the best-preferred metric instead of whichever was listed last, and a remediation state (fixed, accepted risk) carries from one scan's finding to the next instead of reopening.
- **A slow AI answer cannot overwrite newer data.** Triage re-reads each row after the provider replies; a finding whose evidence changed meanwhile waits for its next review, and a validation hit that landed meanwhile keeps the finding confirmed.
- **Auto-fire retries a CVE whose run failed** (a provider outage, say) for 48 hours instead of marking it done forever.
- **A host whose DNS check times out is not scanned this pass.** The check that keeps scanners off internal addresses treated a nameserver that stalled as "fine", so a hostile nameserver could delay its answer past the check and then hand the scanner an internal address. A name that does not exist is still simply skipped; a name that does not answer in time is left for the next pass.
- **A hostile certificate cannot abort a domain's TLS review.** The subject, issuer and names of a certificate are the scanned server's own text; they are now clipped to their columns (and the name list to 200) before storing, instead of raising and dropping every later host of the domain.
- **A crafted page cannot stall a route check.** The page title is found with plain string searches instead of a backtracking pattern, so a body of repeated `<title` cannot cost quadratic time.
- **The Elasticsearch and CouchDB exposure checks read at most 64 KB within 10 seconds** from the scanned server, instead of whatever it sends for as long as it takes.
- **Spelling variants of a user name share one sign-in counter.** The throttle keyed on the lower-cased name, so `Ａdmin` (full-width) or a differently composed accent got its own five tries; the name is now normalised the way the login form reads it (NFKC, case-folded) before it is counted.
- **Credential events are in the audit log, and the right admins can see them.** Password resets, MFA resets, enable/disable and bug bounty changes were recorded without an organization, so an Org Admin never saw them for their own users; each is now recorded for every organization of the user. New records: a user changing their own password, turning two-step sign-in on or off, creating and revoking API tokens (never the token or its name), and the attempt that locks a sign-in name or a second factor.
- **Redaction of scanned-host text is bounded.** The bug bounty redactor ran all its patterns over a request or response of any size before cutting it; it now reads the limit plus a margin, and its private-key pattern is bounded.
- **`get_remediation_work` no longer takes a minute and a half with 500 registered assets.** The asset list is read once per call (names as a set, networks parsed once) instead of re-parsing every pattern for every match, and an `assets` argument over 500 entries is a 400.
- **Member, comment and audit-trail lists are paged** (`page`, `page_size`) like the others, and a rescan request reads at most ten times the queue limit of host names.
- **The system-wide activity feed no longer names a tenant's host.** The memory gate's "waiting for memory" and "out of memory" lines, which every tenant can read, carried the label of the job (a domain or host); they now say only which kind of run it was.
- **An Org Admin cannot take over an account by resetting it.** Resetting the password or two-step sign-in (or deactivating) of an account that holds bug bounty access, which only an App Admin can authorize, is refused for Org Admins; and an account that belongs to no organization can be adopted by an Org Admin only while it has never signed in (the onboarding case), so a person removed from another tenant can no longer be adopted and reset.
- **The Redis broker can have a password.** Anything on the Docker network could read and write Redis (queues, caches, counters, and the Discord cache that was unpickled on read). New installations now get a generated `REDIS_PASSWORD` in `.env`, which Redis requires and every service uses; an older installation turns it on with `make redis-auth`, which recreates Redis and the services together (the updater never recreates Redis, so it cannot switch it on by itself). Without a password nothing changes.
- **The Discord notification cache is signed and holds no secret.** Cached embeds and responses carry an HMAC made with this installation's secret and anything else is ignored instead of unpickled, and the webhook object (which held the hook URL in clear) is no longer cached: it is built from the stored setting each time.
- **Backup guidance no longer puts the key beside the ciphertext.** The docs said to back up the database, `.env` and `web/secret` together; they now say to keep the keys apart from the dumps, and that the automatic-deployment backup folder is for rollback on the same machine.
- **A new certificate authority gets an encrypted key.** `ca.key` was written without encryption whatever `AUTHORITY_PASSWORD` said; a new CA now encrypts it with that password, creates it readable by root only, and the password is read from the environment instead of the command line. A CA created by an older version keeps its key as it is (delete `ca.key` and `ca.crt` in the certs volume and run `make certs` to replace it; browsers then need the new CA).
- **MCP tells the agent what is data.** The server instructions and every successful tool result carry a notice that banners, titles, response excerpts and feed text come from scanned hosts and third parties, and must never be followed as instructions or used as a reason to call a tool that changes or deletes anything.

### Changed

- **CI runs the test suite in parallel.** `manage.py test --parallel` now works: a test runner (`reNgine/test_runner.py`, the project's `TEST_RUNNER`) gives every worker two Redis databases of its own, so one worker's `cache.clear()` or held lock can no longer break a test in another (up to 7 workers). On a 4-core machine the suite went from 543 seconds to 213 seconds. CI uses `--parallel auto` and installs `tblib` so a failure in a worker shows its real traceback. A normal one-process run is unchanged.
- **`scripts/update.sh` has a setting for its polling pause.** `CVENGINE_UPDATE_POLL_SECONDS` (default 5, unchanged) is the pause between checks while it waits for workers and readiness; the update script tests set it to 0.2, which cut that module from about 100 seconds to about 34.

### Updater (already released on master as hotfixes)

- **Switching branch works when the branches have diverged, and a past failure is no longer shown for a new approval.** Moving a server from `master` to `develop` was refused as a downgrade because master's hotfix commits are not ancestors of develop (which carries its own copies). A branch is now accepted when it contains the installed commit or, if the history differs, has every database migration the installed code has; otherwise it is refused with the reason, and nothing moves. Settings > Updates showed the failure left by the previous update (for example "not on master") under a fresh approval; a result older than the approval is now ignored. Saving a different repository or branch checks the new source at once.

- **Automatic or manual updates is a setting, and manual is the default.** Settings > Updates has a new *How updates are installed* choice. Manual: CVEngine tells you a new version exists and installs nothing until you approve it. Automatic: the twice-daily check approves what it finds, and the host updater installs it (scans pause and finish first). Automatic deployment (`scripts/install-auto-deploy.sh`) used to deploy every new master commit regardless; its timer now does nothing unless the setting is Automatic, so an install that had it must choose Automatic to keep deploying on its own. The choice is audited, and switching back to Manual withdraws an approval the app gave itself (one a person gave stays).

- **Approve update works without a manual host step.** The host side of the in-app updater was a cron entry nothing installed, so on a normal install the Approve button recorded an approval that no one read and the orange bar waited for ever. `install.sh` now installs a watcher (`scripts/update-watch.sh`, started every minute by cron) that starts the update about two seconds after Approve, and `scripts/update.sh` installs it when it finishes, so the one manual update an existing install needs leaves it behind. The watcher reports every 15 seconds that it is alive, and Settings > Updates and the bar say when it is not and show the command to run.

- **The update page says what happens and how long it takes.** Each step (approved, the host picks it up, scans pause and drain, files update, services rebuild, scanning resumes) with what it is waiting on, how long it usually takes, and the time since approval; the page refreshes on its own.

- **An update that cannot start says why.** An approved commit that is not on the branch checked out on the server (the update branch in Settings differs from it) is reported in Settings > Updates instead of silently dropping the approval; a failed fetch, a dirty checkout or a stopped script are reported the same way, each reason once.

- **A manual `git pull` followed by Approve rebuilds.** The updater compared files, found them current and declared the update done without rebuilding the containers; it now also checks the commit the running build was made from.

## v1.1 (2026-10-25)

### Changed

- **The old reNgine scan engine is retired.** Its scan and subscan tasks, the `/api/action/initiate/subtask/` endpoint, its extra queues, and about 4,000 lines of code that nothing in the current pipeline called are removed, along with the Go tools only it used (httpx, subfinder, chaos, gospider, hakrawler, katana, gau, waybackurls, ffuf, tlsx, gf, unfurl, dalfox, crlfuzz, s3scanner) and the Python tools it cloned at every start (Sublist3r, OneForAll, EyeWitness, CMSeeK, ctfr, GooFuzz, h8mail). The worker image now builds only nuclei and naabu, next to nmap and bbot, so it builds and starts faster.
- **Every CVE match is validated automatically.** Before, only fire and smoke matches were queued for AI validation and the rest waited for someone to press Validate now. Now a match of any confidence or score is queued by itself, hottest first (fire, smoke, then ice at the lowest priority, using the capacity the hot ones leave), except one the AI ruled out or the distribution patched. Ice stops at five active jobs per project so it cannot crowd out hot findings, and the daily validation caps still apply. `CVENGINE_AUTO_VALIDATE_ALL_MATCHES=0` restores fire and smoke only.
- **More nuclei templates run.** Installed templates that follow redirects on the same host (`host-redirects`, at most three hops) now pass the read-only policy, about 1,250 more (6,531 of 13,903 in the current community set, up from 5,280), among them the technology detection template, so hosts get fingerprinted again. A template that merely recognizes an interactsh server by its header is no longer taken for an out-of-band check. Redirects to other hosts stay refused, and AI-written templates still follow none.
- **naabu now runs by default.** A full port sweep ahead of nmap used to be opt-in; nmap's own top-1,000 guess misses real services often enough (8443, 9200, 27017, and the like) that full coverage up front is worth the extra time for most installs. `CVENGINE_NAABU=0` restores the old top-1,000-only behavior for installs scanning many targets on a tight schedule.

### Added

- **Database metadata and two more exposure checks.** nmap now reads MySQL, Microsoft SQL Server, MongoDB, Redis, Memcached, and CouchDB's own pre-authentication greetings for version, role, and, for MySQL and Microsoft SQL Server, the Windows identity their NTLM negotiation discloses, filling in a version or product nmap's own probe missed. Shown on the host page next to each port. Separately, the credential-less exposure check that already covers Redis, Memcached, PostgreSQL, Elasticsearch, and CouchDB now also tries MySQL (`root`, no password) and MongoDB (`listDatabases` with no prior authentication): a server that lets either through with nothing at all is a critical finding.
- **node2shell (CVE-2026-111497).** Checks hosts fingerprinted as Node.js or Express with Assetnote's own read-only detector, no credentials sent and no command executed. Off by default, because its footprint (about 23 MB uploaded per host) is much larger than every other check here; `CVENGINE_NODE2SHELL=1` turns it on.
- **RDP login-screen screenshots.** When nmap shows a server accepts a connection without Network Level Authentication, cvENGINE captures its pre-authentication screen with no credentials sent, stores it, and asks the configured AI model whether an account is already shown signed in and what it is called. A server that requires NLA is never attempted.
- **JavaScript libraries and technology columns.** The web route check reads jQuery, Bootstrap, AngularJS, React, Vue.js, Lodash, Moment.js, and Underscore.js versions from script names and script banners, and Angular from the page, so old libraries reach CVE matching. Technologies now have `version` and `category` columns. The host page shows an overview, a technology table, per-service script output, and what the web archive remembers.
- **Deeper service fingerprinting.** nmap runs at version intensity 7 with the banner, SSH host key and algorithms, TLS certificate, HTTP header and title, anonymous FTP, RDP NTLM, SMB OS discovery, and NetBIOS scripts, and keeps the output per port. Search reaches it with `banner:`. Windows build, computer name, and domain from RDP and SMB fill an empty OS guess, and an FTP server that allows anonymous sign-in is a finding with its listing as evidence.
- **WPScan for WordPress sites.** A host fingerprinted as WordPress is scanned at most once a day (`CVENGINE_TTL_WPSCAN=168` for weekly) for its version, plugins, themes, config backups, database exports, and author names, and for known vulnerabilities when a wpscan.com API token is set under Settings, API keys. Findings and versions flow into Findings and CVE matching.
- **Archived URLs as passive evidence.** The Internet Archive's saved URLs show what a host ran in the past, such as PHP or WordPress. Search finds it and labels it as seen in the web archive.
- **Local checks for CVE matches nothing external can settle.** When validation finds no read-only check exists for a match, such as a CVE in a specific vendor add-on no banner or template can see, cvENGINE asks the AI once for up to three short, read-only commands a person with shell access could run themselves, with what the output would mean. Shown under Confirm it yourself as a suggestion, never as evidence; the model is told never to suggest a command that changes anything or needs a credential, and to say so when it is not confident of the exact way to detect a product rather than invent one.
- **Remediation status on scanner and hygiene findings, and a bulk status route.** CVE matches already had `open`/`in_progress`/`fixed`/`accepted_risk` with a note; scanner and hygiene findings now carry the same fields, set the same way: `PATCH projects/{slug}/findings/{match,vulnerability,hygiene}/{id}` (`update_finding_status`) for one finding, `POST projects/{slug}/findings/status` (`bulk_update_finding_status`) for up to 200 at once, answering `{updated, failed: [{kind, id, error}]}` so one bad id never blocks the rest. Marking one of these two statuses drops the finding out of the actionable Findings view immediately, whether or not a later scan still finds it.
- **A new install starts loading CVEs by itself.** As soon as its workers are up, a once-only `bootstrap_first_run` task pulls the CVE feed and threat intelligence and backfills recent entries (which in turn correlate and auto-fire), instead of waiting for the first scheduled run, up to 30 minutes for the feed and an hour for threat intelligence. It only acts when the CVE table is empty, so an update or a restart never repeats it, a lock keeps several workers from queuing it twice, and a first try that found no network is retried at the next worker start. A global scan pause does not hold it back.
- **The setup wizard has a last, skippable step for search-engine keys.** After the first target is added (discovery has already started by then), one page offers Shodan, VirusTotal and SecurityTrails keys next to a live line showing the discovery's progress (queued, running with hosts and IPs found so far, finished), so the first dashboard visit has findings in it. Keys are stored per project, never shown again, and apply from the next scan on. Adding a target twice, or while the scanner is still starting (a clear "try again in a few seconds" instead of an error page), starts discovery without creating a second scan.
- **A guide to hosting it online.** [docs/HOSTING-ONLINE.md](docs/HOSTING-ONLINE.md) covers a public name with a browser-trusted certificate: DNS and firewall, a Let's Encrypt certificate on the bundled proxy (it must be RSA, because the proxy's cipher list is RSA-only) with a renewal hook, running behind Cloudflare with Full (strict), using your own reverse proxy, checks, and a troubleshooting table.
- **One command installs it: `sudo ./install.sh`.** It asks nothing and no longer needs `.env` edited. It checks the machine (root, memory, disk, free ports 443 and 8082, Docker's registry reachable), installs what is missing on Debian and Ubuntu, generates the passwords, detects this machine's address for `DOMAIN_NAME` (or takes `--domain`), builds the HTTPS certificate, starts everything, waits until the site answers instead of guessing with a sleep, creates the admin account, and ends with one summary: address, username, generated password, and the certificate note. A failed step prints the log lines of the service that failed. Running it again is safe. The certificate now also covers an IP address as `DOMAIN_NAME` (before, an IP never matched), plus `localhost` and `127.0.0.1`, and `CERT_EXTRA_SANS` for more names.
- **A new install tells its owner how to sign in.** Nothing used to generate or print an admin password: the installer left the owner to invent one at a prompt (or set `DJANGO_SUPERUSER_PASSWORD`, which the plain prompt then ignored). Now `./scripts/init-env.sh` (run by `install.sh` and by `make` on first use) creates `.env` with the database and certificate passwords already generated, and `make admin` (also the last step of `install.sh`) creates the admin account, generates a password, and prints it once with the address and username; the owner chooses their own at first sign-in. `make admin-password` generates a new one for a lost password, and the sign-in page says where to look. A password set in `DJANGO_SUPERUSER_PASSWORD` is still used (and validated), and nothing is replaced on an install that is already running.
- **Scanning pauses for an update's own restart, and Settings, Updates shows live progress.** `scripts/apply-update.sh` now requests a drain pause (new scan dispatch stops; whatever is already running is left to finish, never stopped) before it waits for active scans, and releases it once the run reaches a stable state, whichever commit that ends up being. `GET /cve/api/settings/updates` reports the current `phase` (`idle`, `draining`, `applying`, `done`, `failed`), a short detail, how many scans it is waiting on, and whether scanning is paused for this update, so the page no longer looks idle during a long build or migration.
- **Status timestamps on findings.** Every match, scanner, and hygiene finding response (detail and `findings` rows alike) now carries `status_changed_at` and `status_changed_by` (`{id, username, name}`), and `findings` rows also carry `first_seen` alongside the existing `detected`, so aging, SLA-overdue, and time-to-fix can be shown without guessing from scan dates.
- **SOC mode and live scan highlighting on the asset graph.** The domains and hosts a scan is working on right now pulse on `/cve/graph/`, fed by a new `GET /cve/api/graph-live` (running scans, the step each is in, the hosts they are working on, queued count; never cached, tenancy-scoped like the graph). **SOC mode** (a button, or `?soc=1` for a wall display) puts the graph over the whole window with a status bar (scanning, queued, fire, smoke, nodes, clock) and a **Scanning now** list, dims everything not being scanned while a scan runs, and has its own **Full screen** button; Escape leaves it.
- **Bug bounty engagements get their own project in a Bug Bounty organization.** Working a program (`POST /cve/api/bounty/engagements`) now creates, on first use, a **Bug Bounty** organization and one project per program inside it (`bb-<platform>-<handle>`), puts the engagement there, and answers with its `project`, `project_name`, and `org`, so imported scope targets are never mixed into a client's project. The page follows to that project. `GET .../engagements` with no `project` lists every engagement in the Bug Bounty org the caller can see. The creator becomes the project's admin; a second authorized user working the same program gets a `409` naming the project rather than silent access to someone else's drafts. The audit role cannot create one. Existing engagements are not moved.
- **Per-project SLA days.** `GET`/`PUT projects/{slug}/settings` (`get_project_settings`, `set_project_settings`) keep how many days a finding of each severity has to be fixed (critical, high, medium, low; defaults 7, 30, 90, 180) in one place per project, so "overdue" is the same for every user instead of a default baked into each screen. `PUT` is a partial update; `null` restores a severity's default.
- **Screenshot thumbnails.** `/cve/<project>/hosts/<id>/screenshot/?size=thumb` serves a 320 px-wide JPEG, made on first request and kept beside the original (remade when the screenshot changes), so a gallery of hundreds of hosts does not download hundreds of full-size captures. Every screenshot response now carries an `ETag` and a day of private caching, so a revisit is a 304. The same size, pixel, and decompression-bomb limits as screenshot comparison apply; a file Pillow cannot read is served at full size instead. `size` other than `full` or `thumb` is a 400.
- **Assignee, comments, and an audit trail on findings.** Matches, scanner findings, and hygiene findings can be assigned to a project member (`PATCH .../findings/{kind}/{id}` with `assignee`, a user id or `null`), commented on (`GET/POST .../findings/{kind}/{id}/comments`), and carry an audit trail of every status change, assignee change, and comment with who, when, and before/after (`GET .../findings/{kind}/{id}/audit`, bulk status changes included). `GET projects/{slug}/members` feeds an assignee picker. Rows and detail show `assignee` and `comment_count`. `status` is no longer required on that PATCH when `assignee` is sent. Validation runs are not part of the trail yet.
- **Finding detail shows status for scanner and hygiene findings.** `GET .../findings/{kind}/{id}` only reported `remediation.status` and `note` for CVE matches; scanner and hygiene findings now do too.
- **Daily stats history for trend charts.** A new beat task stores one point-in-time snapshot per project per day (hosts, exposed hosts, open findings by severity, CVE matches by heat, fixed count, mean days to fix). `GET projects/{slug}/stats/history?days=90` (`stats_history`) answers the series oldest first, so exposure-over-time and time-to-fix charts have a past to plot instead of only today.
- **Shodan-style comma-OR, a `country:` filter, and general facets on search.** Any field filter's value now takes a comma-separated list for OR within that filter (`port:80,443`), unless quoted. A new `country:` filter matches a host IP's geolocated country (ISO code or name). `?facets=port,product,tech,os,country` adds the same whole-match, heat-chip-style counting `facets.heat` already did, as `facets.<name>: [{value, count}]`, up to `?facet_size=` values (default 10, max 50). `org:`/`asn:`/`hosting:` were also asked for, but CVEngine does not look up an IP's ASN or hosting provider today (only its country), so those are not implemented here.
- **Heat facet counts and a server-side heat filter on search.** `GET projects/{slug}/search` accepts `heat=fire|smoke|ice|clean|unscanned` to narrow the page to that value, and always returns `facets.heat` with every value's real count over the whole match of `q`, ignoring `heat` itself, so the heat chips show accurate totals instead of only counting the rows already loaded on a big inventory.

- **Search guide.** [docs/SEARCH.md](docs/SEARCH.md) documents every search filter with examples and the closest Shodan equivalents, for the Hosts page, the Ctrl+K palette, the REST API, and MCP.

### Fixed

- **The attack-surface map's hover card names the host's project.** With "All projects" selected, the dashboard spans every project the viewer can see, and the card had no way to say which one a host belonged to.
- **CI runs the whole test suite,** not a short list of modules, and the image build no longer waits for it.
- **Search.** A bare word and `tech:` find a host wherever its software was seen (web server and `X-Powered-By` headers, cookie names, banners, NSE output, route fingerprints, port product and version), not only in the technology list, and `banner:` searches service banners. `php` now finds every host running PHP.
- **Findings counted wrongly.** `save_vulnerability` returned the created flag of its last tag, CVE or reference lookup instead of the finding's own, so new-finding counts were off.
- **Test suite.** `tests.test_hard_lockout` calls the current lockout helpers, and the placeholder `tests.test_nmap` is gone with the code it was meant to test.
- **Unreviewed NSE scripts showing up in service output.** nmap's `-sV` silently runs its whole "version" script category (`rpcinfo`, `hnap-info`, `vmware-version`, and more) on top of whatever `--script` asked for, and writes their output to the XML cvENGINE parses, win or error. None of those scripts have been reviewed for the read-only guarantee the rest of this list has, so they are now dropped before anything is stored, searched, or shown. A one-time migration scrubs any already stored on an upgrade, instead of leaving it there until that host's next scan.
- **The dashboard's live-discovery counts undercounted the graph above them.** Hosts, IPs and open ports were totaled from only the scan being followed, so a rescan that added one host to an already-populated project read as "1 host" under a graph showing everything found to date. They now total the same live inventory the graph draws.
- **`PATCH .../matches/{id}` erased a match's remediation note whenever a caller left `note` out of the body.** Every status change had to resend the existing note just to keep it. `note` is now a true partial-update field: omitting it leaves the stored note alone, and an explicit `""` still clears it. Applies to the new scanner/hygiene status routes too.
- **An AI activity row left "running" forever by a killed worker never closed.** A nuclei or validation step whose worker was restarted mid-task (an OOM kill, a lost broker message) had no code path left to mark it done or failed, so it sat "running" in the feed indefinitely even after the scan it described had long since finished. The existing stuck-job reaper (`cveFeed.reaper`, every 15 minutes) now covers `AgentActivity` the same way it already does host assessments and validation jobs, closing any row still "running" after 11 hours.

## v1.0 (2026-10-25)

The most advanced external attack surface assessment you can get for free. cvENGINE continuously discovers your internet-facing assets, fingerprints their services, and tells you which of today's CVEs are actually exploitable on them, with evidence.

### Highlights

- **Continuous discovery.** Subdomains, certificates, IPs, and open ports with [bbot](https://github.com/blacklanternsecurity/bbot), scheduled re-discovery, and a change log.
- **Service and OS fingerprinting.** One host inventory built from [nmap](https://github.com/nmap/nmap), optional [naabu](https://github.com/projectdiscovery/naabu), and bbot.
- **Fire, smoke, and ice.** Every CVE rated by real-world exploitation from CISA KEV, ENISA EUVD, VulnCheck KEV, EPSS, Exploit-DB, and Metasploit, so hosts are matched against historically exploited CVEs, not just the last two weeks.
- **Evidence-based validation.** Each finding is reproduced with a read-only check (a vetted [nuclei](https://github.com/projectdiscovery/nuclei) template, nmap, an HTTP probe, or a database banner). The AI triages it and drafts a template when none exists; a person reviews drafts before they run.
- **One findings view.** CVE matches, scanner findings, and email and DNS hygiene together, hottest first.
- **Exposure checks.** Unauthenticated Redis, PostgreSQL, Elasticsearch, Memcached, and CouchDB, plus a full email-security review (SPF, DKIM, DMARC, MTA-STS, and more).
- **Bug bounty workbench.** Public program scope, a vulnerability rating per finding, and report drafts ([BUG-BOUNTY.md](docs/BUG-BOUNTY.md)).
- **Built for teams and agents.** Organizations and projects with data isolation and roles, a REST API and an MCP server, and Shodan-style host search.
- **Operations.** A pause-all control, scheduler and worker health, an activity and AI-cost log, two-step sign-in, an IP allowlist, an audit log, and automatic deployment of new releases.

### Platform

Python 3.14, Django 5.2 LTS, PostgreSQL 18, nmap 7.992, Go 1.27, and Ubuntu 26.04 LTS. GPL-3.0. See [docs/](docs/), and [docs/UPGRADE.md](docs/UPGRADE.md) to move an older install.

### Security

Hardened against prompt injection and server-side request forgery, with tenant-isolated media, encrypted secrets, bounded scan and probe time, and a static safety gate on AI-generated templates.
