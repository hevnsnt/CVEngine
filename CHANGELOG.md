# Changelog

cvENGINE is a fork of [reNgine](https://github.com/yogeshojha/rengine) 2.x. The history of reNgine up to the fork is in [its changelog](https://github.com/yogeshojha/rengine/blob/master/CHANGELOG.md).

## Unreleased

### Added

- **A software bill of materials with every release.** Each release now carries `cvengine-<tag>.sbom.cdx.json` (CycloneDX 1.5), listing the pinned scanner tools with the checksums of what is downloaded, the Python packages and the service images, and what it cannot vouch for (nuclei's templates, floating image tags) is marked. `python3 scripts/generate_sbom.py` produces it for any checkout, and every pull request's build keeps it as an artifact.
- **Every scanner tool is pinned, and a release checks them all.** nuclei, naabu and bbot (and its `tzdata`) were installed as "latest" at build time, so a rebuild could change what a scan does. They are now pinned to their current releases like nmap, WPScan and wafw00f. `scripts/check_tool_versions.py` compares every pin (also the Go toolchain and the Tailscale image) with the newest release, the weekly check opens an issue for the ones behind, and a release is held until none is: the pull request into `master` fails the new *Tools up to date for release* check and the Release workflow stops, unless the newer version was looked at and the pull request is labelled `tools-reviewed` (or `tools_reviewed` is ticked on a manual run).

### Changed

- **x86-64 images no longer compile nmap.** On amd64 the image installs the nmap project's own release binary (checksum verified), which links its libraries in statically, so a build is minutes faster and runs the exact binary nmap publishes; arm64, for which nmap publishes no binary, still compiles the same release from source. Both end up in `/usr/local` and the build checks that nmap finds its scripts and data.
- **A CVE match now needs hard evidence, so a product name alone no longer produces findings.** A match is made only when the product on the host is the same product the CVE names and its version is inside a bounded affected range (or a template hit, a distribution tracker verdict, the host's own inventory report or runZero backs an existing match). A product seen without a version, for example a bare `nginx` or `next.js` fingerprint, used to become a candidate for every CVE that mentions the name (dozens per host); it now stays on the host as a technology or port and is listed as an **Unverified product** on the host page and in the host record (`unverified_products`), until a version is found. Advisories that give no usable version bound no longer match either. A new fire or smoke CVE is still template-tested on hosts that run its product with no version found, since a template hit is hard evidence without one.
- **Product names are matched as products, not as words.** `nginx` no longer matches `ingress-nginx`, `nginx-ui`, `nginx-proxy-manager` or the NGINX Ingress Controller, `cloudflare` no longer matches a WordPress plugin of that name, `jquery-ui-rails` is no longer read as jQuery UI, and a version is never compared with the ranges of another product. A shorter name still matches a longer one when the extra words only describe the same product (`Apache` and `Apache HTTP Server`, `Tomcat` and `Apache Tomcat`).
- **Operating-system and kernel flaws are host-only.** Linux kernel CVE records (including drivers such as ath11k, rtc, ksmbd), Windows kernel and component records without a network vector, and any CVE whose only product is an operating system are no longer matched from outside, and an OS fingerprint (`Ubuntu`, `Windows Server`, an nmap OS CPE) never matches a CVE by name. They stay decidable from a host's own inventory report. The classification of every stored CVE is redone automatically.

- **WPScan runs on every host that shows any sign of WordPress, and says why when it did not.** Candidates come from a technology tag, a header or page signature, a `wp-login.php` form, plugin paths in crawled URLs, a title, the web archive's memory of the host, or an earlier probe. A read-only probe (login page, `/wp-json/` and its `Link` header, generator tag, readme) with browser-like request headers confirms it, follows apex and `www` redirects, and is run on every name that shares the host's address. Each candidate ends in a recorded state (scanned with when and how many findings, detected, blocked by the edge, failed with its reason, waiting, not WordPress) on the host page and in `get_system_status`. When an edge challenges the scanner (a Cloudflare challenge, a block page, a 202, 403, 429 or 503), the host says "the edge challenged the scanner" and what to allow in the WAF or bot rules; cvENGINE never tries to get past it. Findings say what to do (update to the fixed version, remove the exposed file) and include outdated components, XML-RPC and timthumbs. Plugin and theme versions are also sightings: a plugin CVE matches only when the plugin's slug or readme title equals the product the advisory names and its version is inside the advisory's bounded range. ### Changed

- **An AI closure of a match needs concrete grounds.** A version inside an advisory's range is still a floor the model cannot clear, unless the application verified a ground from the host's metadata: a probe showed a look-alike product (plain nginx is not ingress-nginx or nginx-ui), or a CDN, WAF or hosting edge answers for the host. Then the model's judgement stands; a banner that states no version is never a reason to close or to confirm. A new probe result re-asks the question without erasing the earlier validation record.
- **WPScan's enumeration and exit codes follow WPScan 4.** Plugins are no longer enumerated by default in WPScan 4, so the scan now asks for `ap,at,tt,cb,dbe,u1-10`. Exit code 4 (the scan did not finish) is read from the report's `scan_aborted` text as not WordPress, blocked by an edge, or a failure. A clean WPScan result stays fresh for a week (`CVENGINE_TTL_WPSCAN`, previously a day) and the per-scan site limit is 20.

- **BinaryEdge is retired.** Coalition shut BinaryEdge down as a standalone service on 31 March 2025 and bbot has no module for it, so the stored key could never be used. The API keys pages and the API now say so (`retired`, with the reason, and `used_in_scans: false`), no new BinaryEdge key is accepted, and a key saved earlier is kept, shown as retired and can be removed. The runZero key is now described as read by the scheduled sync rather than "not used yet".

### Fixed

- **Existing false-positive matches close themselves, and never one somebody worked.** After each CVE update, the open matches that rest on a name alone (no version, no usable range, an OS fingerprint, a different product, or a local-only CVE) are closed with a stored reason ("Closed automatically: no version evidence ..."), the affected hosts are rescored, the dashboard counts refresh and the match's triage row reads "not applicable". A match is kept when anything vouches for it: a remediation state other than open, an assignee, a comment, a manual validation request, an AI "affected" verdict, a template hit, a distribution "vulnerable" verdict, a runZero report or a host report. A closure of a different-product match whose version is in range stays on that match and is never shared with other hosts. A closed match is not reopened by the next correlation unless new evidence (a version, or the KEV exception above) appears. The AI's correct "this is a different product" answer is no longer overruled by a "no supported evidence to close" note, but it cannot close a version inside the range or an end-of-life release older than every fixed branch.
- **Correlation over a large CVE catalogue is about seven times faster** in a synthetic 38,000-CVE benchmark: a product name is compared only with the products that share a word with it.
- **Versions present in tool output are no longer dropped or mangled.** An Apache `Server` header's module list (`PHP/5.4.16`, `OpenSSL/1.0.2k`, `mod_wsgi`) was ignored; `Apache-Coyote/1.1` was stored as Tomcat 1.1 (a protocol version, which then matched every old Tomcat advisory); `Jetty(9.4.51.v20230217)` was dropped; only the first generator meta tag of a WordPress page was read; the `X-AspNet-Version` header was never read; a CPE technology from Shodan's InternetDB and `Bootstrap:v3.3.7` were stored under names no advisory matches; a nuclei version with a `v` prefix was lost; a TLS web service on a port such as 8444 was asked over plain HTTP because nmap reports it as `http` with `tunnel="ssl"`; a version that nmap no longer reported (`server_tokens off`) stayed on the port; and the certificate and the runner-up operating system guesses nmap printed were not kept. nmap also now runs `http-server-header` and `http-generator`. Checked against real header and nmap XML samples.
- **A NUL byte in a request now counts as an attack, as intended.** The input guard rejected such a request but could not save its strike (the database refuses a NUL byte in text), so a flood of them never reached the automatic ban. The stored evidence is now cleaned first.
- **Leftovers of the retired tools removed.** The legacy API no longer offers a theHarvester config file (theHarvester was dropped earlier) and a stale amass heading is gone.
- **Outside-service API keys now reach bbot, and the default scan really enumerates subdomains.** Two defects hid each other. The keys were handed to bbot as `-c <file>`, but bbot 3.x accepts only `key=value` after `-c`: it printed a warning, ran no scan and exited 0, so any organization or project with a key stored got a discovery that "succeeded" with nothing found. And the default (standard) scan repeated `-p` once per preset, which bbot reads as "the last one wins", so it ran only the `web` preset and none of the subdomain sources, keyed or not. Keys now travel in a private preset file listed with the named presets after one `-p`, a run bbot refuses is a failure rather than an empty success, and the image build fails if bbot ever stops reading keys this way. Checked against bbot 3.0.2 (55 modules load, the keys appear in the merged preset).
- **A rejected API key is reported.** bbot skips a module whose key the service refuses and carries on, so a wrong key looked like a service that found nothing. An activity entry now names the service and the reason.
- **Censys, project keys and the vault, made truthful.** The Censys key was also mapped to `censys_ip`, which no scan mode enables; it is now only `censys_dns`, and the page says the key is the legacy Search API's ID and secret. A project key that holds only part of a pair no longer blanks the organization's. The install-wide Chaos key in the vault, which nothing read, is now the fallback for bbot's Chaos module; the unused OpenAI vault key is gone from the page (AI models are set under AI model).

- **An update now refreshes the proxy image, with nothing to run by hand.** The proxy (nginx) is a stock image, `nginx:alpine`, that was never re-pulled, so a host kept whatever nginx it first pulled for as long as it ran (one install was still on 1.29.4, behind the host's own nginx 1.24.0, which is also why the scanner saw two different nginx versions depending on whether it connected by address or by name). The proxy service now has `pull_policy: always`, so every `docker compose up` (the in-app updater, `update.sh`, `make up`) fetches the current image; with no network the update stops before anything is recreated and is retried.
- **An update carries its own deploy steps.** The in-app updater ran the deploy code it had already loaded, so a step added to an update arrived one update late. The steps now live in `scripts/update-deploy.sh`, which the updater reads after merging the new files, so an update applies its own steps in the same run (migrations were always applied automatically).
- **After an update, CVE guidance and local-only classification finish on their own.** The first CVE task after an update writes the rule-based guidance for every CVE (no AI cost), classifies local-only CVEs and closes their open matches, in batches within the task's time limit. Only the AI guidance spend stays opt-in, through the budget in Settings.
- **Local-only vulnerabilities are never matched to a host.** A kernel, driver or Win32k flaw (a "Windows Elevation of Privilege Vulnerability", a CVE with CVSS attack vector Local or Physical) is decided by software and patch levels an outside scan cannot see, so matching it to a host from a technology label such as "Windows Communication Foundation" was always a false positive (and the validation requests it started could only end "cannot be established"). Each CVE is now classified `local_only` from its CVSS vector, or, when it has none, from its wording and affected product; such CVEs leave the correlation pool, their open matches are closed ("Closed: local-only vulnerability", the host rescored; work a person did is kept) and they spend no AI budget. Needs migration 0083.
- **"Remove & exclude" now removes the host you see.** The Hosts page shows names that point at the same addresses as one host, so excluding only the name on display removed that one name and the next name took its place: the host seemed not to go however often you clicked. The dialog now offers to remove and exclude those other names too (on by default, with the names listed), the same for **Delete host data**, and a failure shows inside the dialog instead of a toast that is gone in seconds. `exclude_host` and `delete_host` take `with_aliases`.
- **A finding marked fixed (or an accepted risk) no longer keeps its host hot.** The host's colour, score, "why this host is fire" list, the exposed counts and the graph only skipped CVE matches the AI had ruled out; a match or scanner finding someone had closed still counted, so a host with every finding closed stayed "fire". Closed findings now drop out of all of them, and marking a finding fixed, accepted, reopened or in progress rescores its host at once (a bulk update rescores each host once) instead of at the next daily pass. A host closed before this change is corrected by the next rescore.

### Added

- **Archive, restore, pin or unpin many hosts at once.** `POST projects/{slug}/hosts/bulk` and the MCP tool `bulk_host_action` take up to 200 host names and one action. Each host is independent: a pinned host that cannot be archived, or a name that is not in the project, is listed in `failed` and the rest are done.
- **LM Studio as an AI model.** Settings, AI model now offers LM Studio beside Ollama and vLLM: enter its address (port 1234, `/v1`), load the models it holds (embedding models are left out), and optionally the API token its authentication needs. It speaks the OpenAI-compatible API, so triage, validation planning, CVE guidance and screenshot reading (with a vision model) all work, and a model that has to load on its first request gets five minutes instead of two. See [Deployment](docs/DEPLOYMENT.md#ai-models).
- **Saved searches with alerts.** Type a search on the Hosts page, choose **Save search**, and cvENGINE re-runs it every hour, day or week with your own access and tells Slack, Discord, Telegram or Lark when a new host starts to match (or, if you ask, when hosts stop matching or the count reaches a number). The first check only records what matches now, so nothing floods your channel; after that you get one message per search per check, naming up to five new hosts, with a link, plus a line in the Activity feed. Names on the same addresses count as one host. Searches are private to you and one project (25 per person, 100 per project); a search is checked with the same code as the search box and refused at save time if it would not run. If you leave the project the search is switched off, not run. The Saved searches list can run, edit, switch off or delete a search and import the views kept in your browser, which keep working. Over the API: `projects/{slug}/saved-searches` and the MCP tools `list_saved_searches`, `create_saved_search`, `update_saved_search`, `delete_saved_search`, `run_saved_search` and `get_saved_search_matches`. See [docs/SEARCH.md](docs/SEARCH.md). Needs migrations 0085 and 0086 (cveFeed).
- **runZero asset-inventory sync.** Save a runZero Export API token under Settings, API keys, and cvENGINE reads your runZero inventory, read-only, every 6 hours (`CVENGINE_RUNZERO_SYNC_HOURS`) and on **Sync now**. Hosts cvENGINE already holds get runZero's operating system, hardware, type, tags, site and names (shown on the host page and in `ips[].runzero`), and runZero's own CVE reports for them are listed as **runZero reports**: extra evidence that raises the confidence of a CVE match cvENGINE already found on the same host and port, never a new match and never a confirmation. A per-project switch (off by default) also imports the addresses runZero knows and cvENGINE does not as targets, through the same checks as Add targets (exclusions, private ranges, organization uniqueness), limited by a runZero search (default `alive:true`) and at most 500 per sync (`CVENGINE_RUNZERO_IMPORT_MAX`), with the skipped ones counted by reason. The API keys page shows the last sync, its counts and any error; a bad token, a rate limit or an unreachable console is reported in words and retried at the next sync. REST `GET/PUT projects/{slug}/runzero` and `POST .../runzero/sync`, MCP `get_runzero_sync`, `set_runzero_sync` and `run_runzero_sync` (organization admin or App Admin), and `get_system_status` lists each project's sync. Only the hosted console (`console.runzero.com`) is supported. See [Configuration](docs/CONFIGURATION.md#runzero). Needs migration 0085.
- **Attach a Tailscale tailnet and scan it.** Settings > Tailscale connects a tailnet to a project: its devices become targets automatically (named by their tailnet address, with the MagicDNS name, OS, client version, tags, owner, key expiry, routes and online state kept with them), offline devices are marked, devices that leave are archived and come back if they return, and devices shared in from another tailnet, this server's own node and anything an organization excluded are never imported. With auto-scan on, new and changed online devices go through the normal discovery, nmap and nuclei pipeline, up to a per-run cap; the tag and operating-system filters, the cap and a **Test connection** button are on the same page, with the tailnet name, device counts, last sync and last error. A sync runs every 15 minutes (or **Sync now**). Credentials (a read-only OAuth client or an API access token) are stored encrypted and never shown again. Scans reach the tailnet through an optional `tailscale` compose profile (`COMPOSE_PROFILES=tailscale`, the auth key in `.env.tailscale`) that joins the scanner's network namespace; without it the stack is unchanged, and an install whose Docker host is already on the tailnet can choose "Already routed". An address in `100.64.0.0/10` is scannable only for the project that owns that imported device, only while the link has synced successfully in the last 30 minutes and (with the compose profile) the scanner's node is up, and without `CVENGINE_ALLOW_PRIVATE_TARGETS`; a name that resolves into a tailnet, an address typed by hand and every other project are still refused. The node runs with `--shields-up`, a pinned image and no control socket outside it (the worker reads a status file the sidecar publishes), and a sync by hand is limited to one a minute. See [docs/TAILSCALE.md](docs/TAILSCALE.md). Needs migrations 0088 and 0089.
- **Tailscale findings.** Each sync checks the tailnet and its devices and stores hygiene findings with the usual remediation workflow: a client older than a [Tailscale security bulletin](https://tailscale.com/security-bulletins)'s fixed version (only where the feature the bulletin needs is present), a pending client update, key expiry disabled on a user-owned device, a device unseen for 90 days, approved subnet routes of /16 or wider, exit nodes, remote-administration ports found open on a tailnet address, and from the policy file an allow-all rule, broad or root Tailscale SSH accept rules, tag owners that name every member and a Funnel entitlement for every member. Each finding has its severity reason, evidence, a fix and a stable key. The SSH, tag-owner and Funnel checks follow the recommendations of the [tailworm.com](https://tailworm.com/) assessment, which Tailscale has not confirmed; the finding says so.
- **Tailscale for agents.** `GET /api/v1/projects/{slug}/tailscale`, `.../tailscale/devices` and `POST .../tailscale/sync`, and the MCP tools `tailscale_status`, `list_tailscale_devices` and `sync_tailscale`, for project administrators only; no response carries a credential.
- **Hosts can tell cvENGINE what they are.** Run a script on a machine (`scripts/inventory`: a shell script for Linux and macOS, a Python 3.6+ script with no dependencies for the same, and a PowerShell 5.1 or 7 script for Windows) and it sends the exact operating system and build, the kernel, installed packages and versions, installed updates, listening ports, running services, containers and a few security settings over HTTPS. It only reads, prints exactly what it would send with `--dry-run` or `-DryRun`, verifies TLS (`--ca-file` for the installer's private authority; `--insecure` is loud), reads its token from an environment variable or a file and never from the command line, retries with backoff, and prints a cron line, systemd timer or scheduled task (`--install-cron`, `-Schedule`) without applying it. **Hosts, Host inventory** (and **Agent access**) generates the exact command per platform with your server address and creates the token. A **reporter token** belongs to one project, expires after a year, and can do nothing but post that project's reports; a machine belongs to the token that first reported it, a new machine never takes a host another machine already reports for (an administrator adopts it), and the commands it generates never contain the token. The host page has a new **Inventory** tab (operating system, packages with their package URLs, patches, listening services, security settings, report history) and a badge with the report's age that turns orange when it is stale; the host's own operating system replaces the network scan's guess. Reports that match no scanned host wait for an administrator to tie them to one or add the machine as a target (a project setting can do that automatically; an excluded host is refused). REST `GET projects/{slug}/inventory`, `.../inventory/{id}`, `.../hosts/{host}/inventory` and MCP `list_host_inventories`, `get_host_inventory`. See [docs/HOST-INVENTORY.md](docs/HOST-INVENTORY.md). Needs migrations 0088 (cveFeed) and 0028 (dashboard).
- **Local-only CVEs become findings when the host itself reports the version.** cvENGINE still never matches a kernel or other local-only CVE from outside, but for a host with a fresh inventory report, a local-only CVE whose affected product and version range contains an installed package or the exact Windows build becomes a CVE match labelled **Reported by the host** (and the host's packages sharpen the external matches the same way: distribution fixed versions are applied, a patched backport is kept at low confidence). The version must be inside a real range, names must match exactly, and the kernel of a backporting distribution (Ubuntu, Debian, RHEL) is not matched because its version number does not decide its patches. A report older than the project's `stale_days` (default 14) creates and closes nothing. See [docs/CVE-INTAKE.md](docs/CVE-INTAKE.md).
- **Agents say what they are responsible for, and the server assigns them work.** An agent (an API token) registers with `register_agent` (or `PUT /api/v1/agent`): its name, kind, the organizations, projects and hosts it covers, and what it can do (`validate:network`, `validate:local-ssh`, `remediate:linux`, `remediate:web-config` ...). It can only claim what its user can already reach. - **The nuclei WAF and favicon templates no longer lose what they found.** Real hosts showed a technology named just `WAF` or `DNS WAF` (the template's own name, with the vendor that fired dropped), `favicon-detection` with the icon's hash stored as its *version*, and `AWS Service -`. Found by the upgrade rehearsal.

- **A generic "WAF" label no longer matches a named WAF product.** A host that bbot only labelled "WAF" was matched to the MOVEit WAF advisories because "WAF" is a whole word in that product's name. ### Security

Fixes from an adversarial review of the whole code base.

- **The legacy findings API no longer returns user rows.** Every serializer in the old `/api/` expanded a finding's `assignee`, `remediation_by` and a scan's `initiated_by` into the whole user, password hash included, to any project member (read-only ones too). All of them now return the username only.
- **Sessions are stored under a keyed hash**, not the cookie value, so a copy of the `django_session` table is no longer a list of working logins. Existing sessions are ended once by the update (everyone signs in again).
- **The Django admin shows no stored secret.** Models with an encrypted field (the API keys, webhook URLs, tokens) leave those fields out of their admin forms and lists, and the key models no longer print their value.
- **A dedicated key for stored secrets, with rotation.** New installs generate `CVENGINE_FIELD_KEY` in `.env`: the stored API keys, webhook URLs, update token and two-step sign-in seeds are encrypted under it instead of a key derived from the Django secret, so reading `web/` no longer yields it and the session-signing secret and the encryption key are separate. Existing values keep reading; `make rotate-field-key` (or `manage.py rotate_field_key`) re-encrypts everything under a new key, with `CVENGINE_FIELD_KEY_PREVIOUS` for the old one and `CVENGINE_FIELD_KEY_FILE` for a Docker secret. Back up `.env` with the database. See [docs/CONFIGURATION.md](docs/CONFIGURATION.md).
- **The sign-in form can no longer be used to guess passwords.** Wrong passwords are counted per address and name, per address and per name (5, 30 and 50 in five minutes); past a limit the form answers 429 before it checks the password, and a right password clears the pair's count. Changing a password uses the same counters, and so does the factory reset.
- **Pasted target lists and searches are bounded.** Parsing a list was quadratic on a long run of `[` and ran before authorization; it is linear now, with size caps for the paste and each token. One request can never add more targets than the cap even when the last range is large, and a search accepts at most 15 terms, 200 characters each, 1000 in all.
- **Wrong-typed API fields give a clean 400** (REST and MCP) instead of a 500 or an exception message, and the bulk remediation call no longer returns raw exception text.
- **`system_status` shows non-admins only whether scanning is paused and the update phase.** Who paused it, why, the last error and the instance-wide running count are for App Admins.
- **Nuclei templates may not use YAML anchors or aliases.** A few hundred bytes of nested aliases hung the safety gate (and could exhaust memory). Installed templates that use an anchor are skipped like any template that fails the policy.
- **Page analysis cannot be stalled by a hostile page.** The generator, script and login-form patterns scanned a page in quadratic time; they now read one tag at a time.
- **Mail-hygiene checks have a budget.** An SPF include tree stops after 50 lookups, and the EPSS feed is refused if it expands past 512 MB.
- **The SSRF filter covers more addresses.** IPv6 forms that carry an IPv4 address (NAT64, 6to4, IPv4-compatible) are judged by that address, and the Azure, Oracle, Alibaba and AWS IPv6 metadata addresses, Teredo, benchmarking and reserved ranges are always refused. Name checks now run in parallel with a per-name timeout and an overall budget.
- **The Netlas key is no longer written to the log, the Command table or the history file.**
- **The two-step sign-in seed is encrypted at rest**, and new recovery codes are 80 bits and keyed with the server secret (codes made before stay valid until you make new ones).
- **A stored AI key is never sent to a changed address.** Saving a different provider or server address without typing the key again clears the stored one, and the model list uses the stored key only for the address it was saved for.
- **Every response carries a Content-Security-Policy** (`base-uri`, `object-src`, `frame-ancestors`, `form-action`), and scan results served from `/protected_media/` are sandboxed and never sniffed. Opening a `#...&validate` link now focuses "Validate now" instead of clicking it.
- **Deployment.** nginx accepts 4 MB bodies (was 800 MB), has header and body timeouts and speaks TLS 1.3; the proxy mounts scan results read-only; the celery entrypoint no longer downloads an unpinned third-party template on every start; the installer uses a private temp file, no longer passes the caller's environment through `sudo`, and reuses a certificate only when it really covers the address; `.env` and the PostgreSQL upgrade dump are created owner-only; the development web port listens on loopback; the workflows run read-only by default, release only from master, and the branch-delete tool refuses odd names and long-lived branches.
- **Nuclei templates refresh every six hours** (04:41, 10:41, 16:41, 22:41 UTC) instead of once a day, unless you changed the schedule.

- **Approve update starts the update within seconds.** The host side was a cron job that ran every 5 minutes, was never installed by `install.sh`, and said nothing when it was missing, so on such a machine the button recorded an approval that nothing read and the orange bar waited for ever. Now `scripts/update-watch.sh` (started by cron every minute, installed by `install.sh` and `scripts/install-updater.sh`) listens for the whole minute and starts the update about two seconds after the approval: scans are paused, running ones finish, the files are updated, the containers restart and scanning resumes. While it waits for scans it checks every 15 seconds and writes each reason once, instead of every call. It reports a heartbeat every 15 seconds, and Settings > Updates and the banner say when the host updater is not reporting and what to run. - **Targets and IP data belong to an organization.** A domain name was unique across the whole instance, so one organization could find out which names another tracks (by being told "already exists") or block them by adding the name first, and an IP address was one shared row, so the banners and service data one organization's scans found were readable through another's hosts. - **A scan of one host no longer hides the rest of the inventory** from correlation and from the daily rescore; both read the same current inventory as the host list.

Two sightings of one product on one host keep the stronger evidence, not the last one saved.

- **Long banners from a scanned host cannot cost an nmap chunk**: every text value is clipped to its column and one bad port no longer drops the rest.
- **A hygiene finding marked fixed that comes back is reopened**, with a note, instead of staying hidden.
- **A bounty scope entry longer than the column is shown as text** instead of aborting the sync.
- **The findings list no longer fails on 29 February.**
- **Detection accuracy.** CVEs that arrive with no affected-product data are refreshed again for 90 days instead of staying blank; version ranges the CVE List gives only as text are read; CPE and product-name spellings (`Apache httpd`, `OpenSSH_9.6`) resolve to the same product; a match a template or validation already confirmed stays open when a later scan sees a different version; a changed product on a port resets the stored version; portable patch levels (`8.9p1`, `8.9p2`), date versions and MariaDB's `5.5.5-` banner prefix compare correctly.

- **A host whose DNS check times out is not scanned this pass.** The check that keeps scanners off internal addresses treated a nameserver that stalled as "fine", so a hostile nameserver could delay its answer past the check and then hand the scanner an internal address. A name that does not exist is still simply skipped; a name that does not answer in time is left for the next pass.

- **Member, comment and audit-trail lists are paged** (`page`, `page_size`) like the others, and a rescan request reads at most ten times the queue limit of host names.
- **The system-wide activity feed no longer names a tenant's host.** The memory gate's "waiting for memory" and "out of memory" lines, which every tenant can read, carried the label of the job (a domain or host); they now say only which kind of run it was.
- **An Org Admin cannot take over an account by resetting it.** Resetting the password or two-step sign-in (or deactivating) of an account that holds bug bounty access, which only an App Admin can authorize, is refused for Org Admins; and an account that belongs to no organization can be adopted by an Org Admin only while it has never signed in (the onboarding case), so a person removed from another tenant can no longer be adopted and reset.
- **The Redis broker can have a password.** Anything on the Docker network could read and write Redis (queues, caches, counters, and the Discord cache that was unpickled on read). New installations now get a generated `REDIS_PASSWORD` in `.env`, which Redis requires and every service uses; an older installation turns it on with `make redis-auth`, which recreates Redis and the services together (the updater never recreates Redis, so it cannot switch it on by itself). Without a password nothing changes.
- **The Discord notification cache is signed and holds no secret.** Cached embeds and responses carry an HMAC made with this installation's secret and anything else is ignored instead of unpickled, and the webhook object (which held the hook URL in clear) is no longer cached: it is built from the stored setting each time.
- **Backup guidance no longer puts the key beside the ciphertext.** The docs said to back up the database, `.env` and `web/secret` together; they now say to keep the keys apart from the dumps, and that the automatic-deployment backup folder is for rollback on the same machine.
- **A new certificate authority gets an encrypted key.** `ca.key` was written without encryption whatever `AUTHORITY_PASSWORD` said; a new CA now encrypts it with that password, creates it readable by root only, and the password is read from the environment instead of the command line. A CA created by an older version keeps its key as it is (delete `ca.key` and `ca.crt` in the certs volume and run `make certs` to replace it; browsers then need the new CA).
- **MCP tells the agent what is data.** The server instructions and every successful tool result carry a notice that banners, titles, response excerpts and feed text come from scanned hosts and third parties, and must never be followed as instructions or used as a reason to call a tool that changes or deletes anything.

### Changed

- **CI runs the test suite in parallel.** `manage.py test --parallel` now works: a test runner (`reNgine/test_runner.py`, the project's `TEST_RUNNER`) gives every worker two Redis databases of its own, so one worker's `cache.clear()` or held lock can no longer break a test in another (up to 7 workers). On a 4-core machine the suite went from 543 seconds to 213 seconds. CI uses `--parallel auto` and installs `tblib` so a failure in a worker shows its real traceback. A normal one-process run is unchanged.
- **`scripts/update.sh` has a setting for its polling pause.** `CVENGINE_UPDATE_POLL_SECONDS` (default 5, unchanged) is the pause between checks while it waits for workers and readiness; the update script tests set it to 0.2, which cut that module from about 100 seconds to about 34.

### Updater (already released on master as hotfixes)

- **Switching branch works when the branches have diverged, and a past failure is no longer shown for a new approval.** Moving a server from `master` to `develop` was refused as a downgrade because master's hotfix commits are not ancestors of develop (which carries its own copies). A branch is now accepted when it contains the installed commit or, if the history differs, has every database migration the installed code has; otherwise it is refused with the reason, and nothing moves. Settings > Updates showed the failure left by the previous update (for example "not on master") under a fresh approval; a result older than the approval is now ignored. Saving a different repository or branch checks the new source at once.

- **Automatic or manual updates is a setting, and manual is the default.** Settings > Updates has a new *How updates are installed* choice. Manual: CVEngine tells you a new version exists and installs nothing until you approve it. Automatic: the twice-daily check approves what it finds, and the host updater installs it (scans pause and finish first). Automatic deployment (`scripts/install-auto-deploy.sh`) used to deploy every new master commit regardless; its timer now does nothing unless the setting is Automatic, so an install that had it must choose Automatic to keep deploying on its own. The choice is audited, and switching back to Manual withdraws an approval the app gave itself (one a person gave stays).

- **Approve update works without a manual host step.** The host side of the in-app updater was a cron entry nothing installed, so on a normal install the Approve button recorded an approval that no one read and the orange bar waited for ever. `install.sh` now installs a watcher (`scripts/update-watch.sh`, started every minute by cron) that starts the update about two seconds after Approve, and `scripts/update.sh` installs it when it finishes, so the one manual update an existing install needs leaves it behind. The watcher reports every 15 seconds that it is alive, and Settings > Updates and the bar say when it is not and show the command to run.

- **The update page says what happens and how long it takes.** Each step (approved, the host picks it up, scans pause and drain, files update, services rebuild, scanning resumes) with what it is waiting on, how long it usually takes, and the time since approval; the page refreshes on its own.

- **An update that cannot start says why.** An approved commit that is not on the branch checked out on the server (the update branch in Settings differs from it) is reported in Settings > Updates instead of silently dropping the approval; a failed fetch, a dirty checkout or a stopped script are reported the same way, each reason once.

- **A manual `git pull` followed by Approve rebuilds.** The updater compared files, found them current and declared the update done without rebuilding the containers; it now also checks the commit the running build was made from.

## v1.1 (2026-10-25)

### Changed

- **The old reNgine scan engine is retired.** Its scan and subscan tasks, the `/api/action/initiate/subtask/` endpoint, its extra queues, and about 4,000 lines of code that nothing in the current pipeline called are removed, along with the Go tools only it used (httpx, subfinder, chaos, gospider, hakrawler, katana, gau, waybackurls, ffuf, tlsx, gf, unfurl, dalfox, crlfuzz, s3scanner) and the Python tools it cloned at every start (Sublist3r, OneForAll, EyeWitness, CMSeeK, ctfr, GooFuzz, h8mail). The worker image now builds only nuclei and naabu, next to nmap and bbot, so it builds and starts faster.
- **Every CVE match is validated automatically.** Before, only fire and smoke matches were queued for AI validation and the rest waited for someone to press Validate now. Now a match of any confidence or score is queued by itself, hottest first (fire, smoke, then ice at the lowest priority, using the capacity the hot ones leave), except one the AI ruled out or the distribution patched. Ice stops at five active jobs per project so it cannot crowd out hot findings, and the daily validation caps still apply. `CVENGINE_AUTO_VALIDATE_ALL_MATCHES=0` restores fire and smoke only.
- **More nuclei templates run.** Installed templates that follow redirects on the same host (`host-redirects`, at most three hops) now pass the read-only policy, about 1,250 more (6,531 of 13,903 in the current community set, up from 5,280), among them the technology detection template, so hosts get fingerprinted again. A template that merely recognizes an interactsh server by its header is no longer taken for an out-of-band check. Redirects to other hosts stay refused, and AI-written templates still follow none.
- **naabu now runs by default.** A full port sweep ahead of nmap used to be opt-in; nmap's own top-1,000 guess misses real services often enough (8443, 9200, 27017, and the like) that full coverage up front is worth the extra time for most installs. `CVENGINE_NAABU=0` restores the old top-1,000-only behavior for installs scanning many targets on a tight schedule.

### Added

- **Database metadata and two more exposure checks.** nmap now reads MySQL, Microsoft SQL Server, MongoDB, Redis, Memcached, and CouchDB's own pre-authentication greetings for version, role, and, for MySQL and Microsoft SQL Server, the Windows identity their NTLM negotiation discloses, filling in a version or product nmap's own probe missed. Shown on the host page next to each port. Separately, the credential-less exposure check that already covers Redis, Memcached, PostgreSQL, Elasticsearch, and CouchDB now also tries MySQL (`root`, no password) and MongoDB (`listDatabases` with no prior authentication): a server that lets either through with nothing at all is a critical finding.
- **node2shell (CVE-2026-111497).** Checks hosts fingerprinted as Node.js or Express with Assetnote's own read-only detector, no credentials sent and no command executed. Off by default, because its footprint (about 23 MB uploaded per host) is much larger than every other check here; `CVENGINE_NODE2SHELL=1` turns it on.
- **RDP login-screen screenshots.** When nmap shows a server accepts a connection without Network Level Authentication, cvENGINE captures its pre-authentication screen with no credentials sent, stores it, and asks the configured AI model whether an account is already shown signed in and what it is called. A server that requires NLA is never attempted.
- **JavaScript libraries and technology columns.** The web route check reads jQuery, Bootstrap, AngularJS, React, Vue.js, Lodash, Moment.js, and Underscore.js versions from script names and script banners, and Angular from the page, so old libraries reach CVE matching. Technologies now have `version` and `category` columns. The host page shows an overview, a technology table, per-service script output, and what the web archive remembers.
- **Deeper service fingerprinting.** nmap runs at version intensity 7 with the banner, SSH host key and algorithms, TLS certificate, HTTP header and title, anonymous FTP, RDP NTLM, SMB OS discovery, and NetBIOS scripts, and keeps the output per port. Search reaches it with `banner:`. Windows build, computer name, and domain from RDP and SMB fill an empty OS guess, and an FTP server that allows anonymous sign-in is a finding with its listing as evidence.
- **WPScan for WordPress sites.** A host fingerprinted as WordPress is scanned at most once a day (`CVENGINE_TTL_WPSCAN=168` for weekly) for its version, plugins, themes, config backups, database exports, and author names, and for known vulnerabilities when a wpscan.com API token is set under Settings, API keys. Findings and versions flow into Findings and CVE matching.
- **Archived URLs as passive evidence.** The Internet Archive's saved URLs show what a host ran in the past, such as PHP or WordPress. Search finds it and labels it as seen in the web archive.
- **Local checks for CVE matches nothing external can settle.** When validation finds no read-only check exists for a match, such as a CVE in a specific vendor add-on no banner or template can see, cvENGINE asks the AI once for up to three short, read-only commands a person with shell access could run themselves, with what the output would mean. Shown under Confirm it yourself as a suggestion, never as evidence; the model is told never to suggest a command that changes anything or needs a credential, and to say so when it is not confident of the exact way to detect a product rather than invent one.
- **Remediation status on scanner and hygiene findings, and a bulk status route.** CVE matches already had `open`/`in_progress`/`fixed`/`accepted_risk` with a note; scanner and hygiene findings now carry the same fields, set the same way: `PATCH projects/{slug}/findings/{match,vulnerability,hygiene}/{id}` (`update_finding_status`) for one finding, `POST projects/{slug}/findings/status` (`bulk_update_finding_status`) for up to 200 at once, answering `{updated, failed: [{kind, id, error}]}` so one bad id never blocks the rest. Marking one of these two statuses drops the finding out of the actionable Findings view immediately, whether or not a later scan still finds it.
- **A new install starts loading CVEs by itself.** As soon as its workers are up, a once-only `bootstrap_first_run` task pulls the CVE feed and threat intelligence and backfills recent entries (which in turn correlate and auto-fire), instead of waiting for the first scheduled run, up to 30 minutes for the feed and an hour for threat intelligence. It only acts when the CVE table is empty, so an update or a restart never repeats it, a lock keeps several workers from queuing it twice, and a first try that found no network is retried at the next worker start. A global scan pause does not hold it back.
- **The setup wizard has a last, skippable step for search-engine keys.** After the first target is added (discovery has already started by then), one page offers Shodan, VirusTotal and SecurityTrails keys next to a live line showing the discovery's progress (queued, running with hosts and IPs found so far, finished), so the first dashboard visit has findings in it. Keys are stored per project, never shown again, and apply from the next scan on. Adding a target twice, or while the scanner is still starting (a clear "try again in a few seconds" instead of an error page), starts discovery without creating a second scan.
- **A guide to hosting it online.** [docs/HOSTING-ONLINE.md](docs/HOSTING-ONLINE.md) covers a public name with a browser-trusted certificate: DNS and firewall, a Let's Encrypt certificate on the bundled proxy (it must be RSA, because the proxy's cipher list is RSA-only) with a renewal hook, running behind Cloudflare with Full (strict), using your own reverse proxy, checks, and a troubleshooting table.
- **One command installs it: `sudo ./install.sh`.** It asks nothing and no longer needs `.env` edited. It checks the machine (root, memory, disk, free ports 443 and 8082, Docker's registry reachable), installs what is missing on Debian and Ubuntu, generates the passwords, detects this machine's address for `DOMAIN_NAME` (or takes `--domain`), builds the HTTPS certificate, starts everything, waits until the site answers instead of guessing with a sleep, creates the admin account, and ends with one summary: address, username, generated password, and the certificate note. A failed step prints the log lines of the service that failed. Running it again is safe. The certificate now also covers an IP address as `DOMAIN_NAME` (before, an IP never matched), plus `localhost` and `127.0.0.1`, and `CERT_EXTRA_SANS` for more names.
- **A new install tells its owner how to sign in.** Nothing used to generate or print an admin password: the installer left the owner to invent one at a prompt (or set `DJANGO_SUPERUSER_PASSWORD`, which the plain prompt then ignored). Now `./scripts/init-env.sh` (run by `install.sh` and by `make` on first use) creates `.env` with the database and certificate passwords already generated, and `make admin` (also the last step of `install.sh`) creates the admin account, generates a password, and prints it once with the address and username; the owner chooses their own at first sign-in. `make admin-password` generates a new one for a lost password, and the sign-in page says where to look. A password set in `DJANGO_SUPERUSER_PASSWORD` is still used (and validated), and nothing is replaced on an install that is already running.
- **Scanning pauses for an update's own restart, and Settings, Updates shows live progress.** `scripts/apply-update.sh` now requests a drain pause (new scan dispatch stops; whatever is already running is left to finish, never stopped) before it waits for active scans, and releases it once the run reaches a stable state, whichever commit that ends up being. `GET /cve/api/settings/updates` reports the current `phase` (`idle`, `draining`, `applying`, `done`, `failed`), a short detail, how many scans it is waiting on, and whether scanning is paused for this update, so the page no longer looks idle during a long build or migration.
- **Status timestamps on findings.** Every match, scanner, and hygiene finding response (detail and `findings` rows alike) now carries `status_changed_at` and `status_changed_by` (`{id, username, name}`), and `findings` rows also carry `first_seen` alongside the existing `detected`, so aging, SLA-overdue, and time-to-fix can be shown without guessing from scan dates.
- **SOC mode and live scan highlighting on the asset graph.** The domains and hosts a scan is working on right now pulse on `/cve/graph/`, fed by a new `GET /cve/api/graph-live` (running scans, the step each is in, the hosts they are working on, queued count; never cached, tenancy-scoped like the graph). **SOC mode** (a button, or `?soc=1` for a wall display) puts the graph over the whole window with a status bar (scanning, queued, fire, smoke, nodes, clock) and a **Scanning now** list, dims everything not being scanned while a scan runs, and has its own **Full screen** button; Escape leaves it.
- **Bug bounty engagements get their own project in a Bug Bounty organization.** Working a program (`POST /cve/api/bounty/engagements`) now creates, on first use, a **Bug Bounty** organization and one project per program inside it (`bb-<platform>-<handle>`), puts the engagement there, and answers with its `project`, `project_name`, and `org`, so imported scope targets are never mixed into a client's project. The page follows to that project. `GET .../engagements` with no `project` lists every engagement in the Bug Bounty org the caller can see. The creator becomes the project's admin; a second authorized user working the same program gets a `409` naming the project rather than silent access to someone else's drafts. The audit role cannot create one. Existing engagements are not moved.
- **Per-project SLA days.** `GET`/`PUT projects/{slug}/settings` (`get_project_settings`, `set_project_settings`) keep how many days a finding of each severity has to be fixed (critical, high, medium, low; defaults 7, 30, 90, 180) in one place per project, so "overdue" is the same for every user instead of a default baked into each screen. `PUT` is a partial update; `null` restores a severity's default.
- **Screenshot thumbnails.** `/cve/<project>/hosts/<id>/screenshot/?size=thumb` serves a 320 px-wide JPEG, made on first request and kept beside the original (remade when the screenshot changes), so a gallery of hundreds of hosts does not download hundreds of full-size captures. Every screenshot response now carries an `ETag` and a day of private caching, so a revisit is a 304. The same size, pixel, and decompression-bomb limits as screenshot comparison apply; a file Pillow cannot read is served at full size instead. `size` other than `full` or `thumb` is a 400.
- **Assignee, comments, and an audit trail on findings.** Matches, scanner findings, and hygiene findings can be assigned to a project member (`PATCH .../findings/{kind}/{id}` with `assignee`, a user id or `null`), commented on (`GET/POST .../findings/{kind}/{id}/comments`), and carry an audit trail of every status change, assignee change, and comment with who, when, and before/after (`GET .../findings/{kind}/{id}/audit`, bulk status changes included). `GET projects/{slug}/members` feeds an assignee picker. Rows and detail show `assignee` and `comment_count`. `status` is no longer required on that PATCH when `assignee` is sent. Validation runs are not part of the trail yet.
- **Finding detail shows status for scanner and hygiene findings.** `GET .../findings/{kind}/{id}` only reported `remediation.status` and `note` for CVE matches; scanner and hygiene findings now do too.
- **Daily stats history for trend charts.** A new beat task stores one point-in-time snapshot per project per day (hosts, exposed hosts, open findings by severity, CVE matches by heat, fixed count, mean days to fix). `GET projects/{slug}/stats/history?days=90` (`stats_history`) answers the series oldest first, so exposure-over-time and time-to-fix charts have a past to plot instead of only today.
- **Shodan-style comma-OR, a `country:` filter, and general facets on search.** Any field filter's value now takes a comma-separated list for OR within that filter (`port:80,443`), unless quoted. A new `country:` filter matches a host IP's geolocated country (ISO code or name). `?facets=port,product,tech,os,country` adds the same whole-match, heat-chip-style counting `facets.heat` already did, as `facets.<name>: [{value, count}]`, up to `?facet_size=` values (default 10, max 50). `org:`/`asn:`/`hosting:` were also asked for, but CVEngine does not look up an IP's ASN or hosting provider today (only its country), so those are not implemented here.
- **Heat facet counts and a server-side heat filter on search.** `GET projects/{slug}/search` accepts `heat=fire|smoke|ice|clean|unscanned` to narrow the page to that value, and always returns `facets.heat` with every value's real count over the whole match of `q`, ignoring `heat` itself, so the heat chips show accurate totals instead of only counting the rows already loaded on a big inventory.

- **Search guide.** [docs/SEARCH.md](docs/SEARCH.md) documents every search filter with examples and the closest Shodan equivalents, for the Hosts page, the Ctrl+K palette, the REST API, and MCP.

### Fixed

- **The attack-surface map's hover card names the host's project.** With "All projects" selected, the dashboard spans every project the viewer can see, and the card had no way to say which one a host belonged to.
- **CI runs the whole test suite,** not a short list of modules, and the image build no longer waits for it.
- **Search.** A bare word and `tech:` find a host wherever its software was seen (web server and `X-Powered-By` headers, cookie names, banners, NSE output, route fingerprints, port product and version), not only in the technology list, and `banner:` searches service banners. `php` now finds every host running PHP.

- **Unreviewed NSE scripts showing up in service output.** nmap's `-sV` silently runs its whole "version" script category (`rpcinfo`, `hnap-info`, `vmware-version`, and more) on top of whatever `--script` asked for, and writes their output to the XML cvENGINE parses, win or error. None of those scripts have been reviewed for the read-only guarantee the rest of this list has, so they are now dropped before anything is stored, searched, or shown. Applies to the new scanner/hygiene status routes too.
- **An AI activity row left "running" forever by a killed worker never closed.** A nuclei or validation step whose worker was restarted mid-task (an OOM kill, a lost broker message) had no code path left to mark it done or failed, so it sat "running" in the feed indefinitely even after the scan it described had long since finished. ## v1.0 (2026-10-25)

The most advanced external attack surface assessment you can get for free. cvENGINE continuously discovers your internet-facing assets, fingerprints their services, and tells you which of today's CVEs are actually exploitable on them, with evidence.

### Highlights

- **Continuous discovery.** Subdomains, certificates, IPs, and open ports with [bbot](https://github.com/blacklanternsecurity/bbot), scheduled re-discovery, and a change log.
- **Service and OS fingerprinting.** One host inventory built from [nmap](https://github.com/nmap/nmap), optional [naabu](https://github.com/projectdiscovery/naabu), and bbot.
- **Fire, smoke, and ice.** Every CVE rated by real-world exploitation from CISA KEV, ENISA EUVD, VulnCheck KEV, EPSS, Exploit-DB, and Metasploit, so hosts are matched against historically exploited CVEs, not just the last two weeks.
- **Evidence-based validation.** Each finding is reproduced with a read-only check (a vetted [nuclei](https://github.com/projectdiscovery/nuclei) template, nmap, an HTTP probe, or a database banner). The AI triages it and drafts a template when none exists; a person reviews drafts before they run.
- **One findings view.** CVE matches, scanner findings, and email and DNS hygiene together, hottest first.
- **Exposure checks.** Unauthenticated Redis, PostgreSQL, Elasticsearch, Memcached, and CouchDB, plus a full email-security review (SPF, DKIM, DMARC, MTA-STS, and more).
- **Bug bounty workbench.** Public program scope, a vulnerability rating per finding, and report drafts ([BUG-BOUNTY.md](docs/BUG-BOUNTY.md)).
- **Built for teams and agents.** Organizations and projects with data isolation and roles, a REST API and an MCP server, and Shodan-style host search.
- **Operations.** A pause-all control, scheduler and worker health, an activity and AI-cost log, two-step sign-in, an IP allowlist, an audit log, and automatic deployment of new releases.

### Platform

Python 3.14, Django 5.2 LTS, PostgreSQL 18, nmap 7.992, Go 1.27, and Ubuntu 26.04 LTS. GPL-3.0. See [docs/](docs/), and [docs/UPGRADE.md](docs/UPGRADE.md) to move an older install.

### Security

Hardened against prompt injection and server-side request forgery, with tenant-isolated media, encrypted secrets, bounded scan and probe time, and a static safety gate on AI-generated templates.
